# 知是用户文档写作

这份 skill 管知是用户页面**怎么写、怎么配画面**。锚点、摘要句、链接、图片路径和演示里的界面字样由
`.claude/scripts/check-manual-anchors.py` 与 `docs/site` 的构建把关；哪一页负责什么、frontmatter 的规矩在
[`docs/manual/README.md`](../../../docs/manual/README.md)。

样板页是 [`docs/manual/working-with-cheese.md`](../../../docs/manual/working-with-cheese.md)：
写一页之前先读它，拿不准时照它的做法。

## 读者是谁

学生、老师、助教、办公室同事，大多不是程序员：会用浏览器，不一定懂分支、仓库、CI、沙箱。
他们来这一页是为了做成一件事。对标的写法是 Claude Help Center（support.claude.com）和 Anthropic 文档。

写的时候手里放着这个提问：

> 一个第一次用的人，照着这一页做，会在哪一步停下、点错、或者问「那现在呢」？

## 语体

- **简洁的书面说明文。** 不口语，也不压成行话。口语词不用：干活、你得、照着、东西、过目、就行。
  不推销、不共情、不开玩笑、不客套，不用感叹号。
- **用产品自己的词。** 采纳、退回、转为任务、支线、审阅人、负责人……界面上叫什么就写什么，
  不自己换说法（不写「收下」「放进项目」「让它改」）。
- **术语在读者第一次遇到它的地方定义一次**，用一句平实的书面话说清它做什么，
  最好落在本页的例子上：「采纳之后，报名说明才加入项目，任务随之关闭。」之后照常使用，不再解释。
- **具体。** 用本页贯穿的例子说话，不用「处理」「验收」「完成相关操作」这类空动词。

## 每类页面的骨架

一页只讲一件事。页面分四类，各有固定骨架：

| 类型 | 标题 | 骨架 |
|---|---|---|
| 入门 | 名词或动宾短语 | 开头一句 → 前提框 → 两三节最短路径 → 接下来 |
| 做一件事 | 动宾短语（「把一件事交给芝士并验收」） | 开头一句 → 前提框 → 每节一个任务（一列步骤，必要时配画面）→ 建议小节 → 接下来 |
| 功能说明 | 名词或问句 | 开头一句给定义 → 机制或规则 → 限制 → 接下来 |
| 排障 | 读者自己的症状（「芝士一直没回复」） | 现象（照抄提示原文）→ 意思 → 处理 |

- **标题**按上表的类型写，层级最多三级。标题文字可以改，末尾的 `{#slug}` 一律不动：别处的链接指着它。
  新标题的 slug 用小写字母、数字和连字符。
- **开头一句**说这页让读者做成什么，锚在本页的例子上，不出现还没定义的产品术语。
  守卫拿它当摘要，llms.txt 里的那一行就是它。
- **前提**（要老师开启、要管理员批准、要先有项目）放在开头一句下面的 `:::before` 灰框里。
  只写真的需要的：平台默认就有的东西不算前提。
- **段落**最多三句、约一百字，一句一件事。
- **建议和步骤分开。** 「要求怎么写芝士更容易做对」这类建议单独成一个短小节，用建议的口吻写，
  不塞进步骤。
- **最多三个提示框**，按 `> [!WARNING]` 注意 / `> [!TIP]` 提示 / `> [!IMPORTANT]` 重要 选类型
  （构建拒绝超过三个的页面）。
- **结尾**是 `:::cards` 的「接下来」：两到四张，每张一行说去那里做什么。

### 步骤

- 一个任务一列编号步骤，三到七步；超过七步就拆成两节。
- 一步一个动作。最后一步写读者此刻在屏幕上看到的结果。
- 按钮和标签写界面原文，放进「」；位置用「右上角」「左侧栏」「输入框上方」；
  菜单路径写成「设置 → 设备」。
- 一步折行超过三行，就把从句（例外情况、名词解释）挪到这列步骤后面单独一句。
- 要发给芝士的话写成 ```` ```prompt ```` 块，内容具体、可以照抄：具体的课、文件、要求。

## 画面

文字撑起整页，画面是例外：只在读者必须认出一个界面状态时才放。

| 情形 | 用什么 |
|---|---|
| 一列步骤里有几步会改变屏幕 | `:::walk`：步骤列表配一块同步的画面，每步一帧 |
| 单独一个动作 | `demo-panel`，紧跟在它说明的那一步下面 |
| 读者要认出一个静态控件 | 只裁那一块的截图（`docs/site/shots` 拍真界面），不加箭头、框和编号 |
| 只在功能说明页解释一个机制 | 平面的框和箭头，中性色，一个强调色，前面一句引出、后面一段解释 |

写法和字段见 `docs/manual/dev/docs-site.md` 的「交互演示」一节；样板页里的两个 `:::walk` 就是范例。
所有画面都守这几条：

- **一屏放得下。** 画面连同引出它的那句话（`:::walk` 连同整列步骤）放进 1440×900 的一屏，
  画面本身不超过约 450px；390px 宽也看过。浅色、深色都对。
- **只画相关的那一块**（只画聊天栏，或只画验收卡），无关内容画成灰条，没有半空的窗格。
  这一步讲的那一块才写真字，字号不小于 12px。
- **一帧一个提示**：一个按钮被按下，或者正在打字，二选一，不同时加框和浮层。
- **停在结果上。** 不播放的读者（没有脚本、减少动态效果、没滚到）看到的就是结果那一帧。
- **`:::walk` 里没有进度条、没有图注**：步骤本身就是控制器和进度。单独的 `demo-panel` 有且只有一行灰色图注，
  不重复步骤。
- **界面字样照抄产品。** 演示里的按钮、状态、占位字由构建对照
  `frontend/src/i18n/messages/zh-CN/` 检查，对不上就构建失败。
- **内容和当前产品一致**：频道、任务、支线、「开始」、验收卡上的「采纳」「退回」，不出现已经改名的旧叫法。
- 不用 ASCII 图、不用术语对照表、不嵌视频。表格只用来分开两个容易混的概念，或把读者分流到对的页面。

## 核实

页面里每一句关于界面的话都要对得上当前产品：按钮名、位置、点了之后出现什么。
先读 `origin/main` 的前端代码；代码说不清的，在 dev 部署（okcheese.com）上用测试账号的测试项目实际走一遍。
核实不了的就不写；发出去的页面里不留「待确认」之类的标记。

### 走流程时发现 bug

为写文档走流程时碰到的产品 bug，直接修，不先问（项目负责人的决定）：先查有没有开着的 PR 已经在修，
没有就每个根因一个 PR，经合并队列合入，在 dev 上确认修好。文档写产品修好之后的行为，不为 bug 写绕过办法。

## 句子

- **祈使句写操作，陈述句写事实。** 操作句子动词开头（点「发布」、填「项目名称」），
  说明结果才用陈述句。少用「可以」：「你可以点」这类写法去掉「你」和「可以」，
  直接写动作。
- **主语清楚。** 「它」只能指上一句里唯一的那个人或物。指代不明就写回名字，或者换个说法
  把主语省掉：「如果这一轮还没开始，它不会执行」→「这一轮还没开始时不会执行」。
- **一句一件事。** 中文一句话控制在 40 字以内；并列条件多时拆句，别用逗号串成一条长链。
- **肯定句优先。** 「电源已关闭」胜过「请确认没有接通电源」；不要双重否定。
- **少用被动。** 「改动合进项目」而不是「改动被合进项目」。
- **不替读者总结。** 不写「这样就完成了整个过程」；结果用界面上的字样说明。
- **不解释动机。** 除非不做会导致操作错误，否则不写「这么做是为了……」。
- **不用类比开场。** 一个功能是什么，就用它的名字和它的行为说；不要「就像把一件事交给
  一位能干的同事」。
- **一段里第一句就是结论。** 别先铺垫三句再点题。

### 界面文字、标点与空格

- **界面上的字样照抄，包在「」里**：「新建项目」「查看改动」「仍要采纳」。按钮、页签、
  菜单项、提示原文、状态名都属于这一类。拿不准原文时去
  `frontend/src/i18n/messages/zh-CN/` 下核对，不要凭印象改写。
- **代码、命令、路径、文件名、快捷键用反引号**：`cheesehost status`、`index.html`、
  `Ctrl/Cmd+Enter`、`/spaces/<空间号>/tasks/publish`。
- **「」不做强调用。** 普通名词（任务、进度、现场、额度）不加引号，除非它同时是界面上的
  字样（右侧的页签就叫「现场」，那就加）。强调一处内容，先想能不能把话写清楚。
- **加粗只留给漏掉就会做错的地方。** 一页里最多两三处；用**加粗**当小标题、或给每段开头
  加粗一个词的写法，读起来像宣传页。
- **中英文之间留一个半角空格**：`GitHub`、`tokens`、`Ctrl/Cmd+Enter` 前后各留一个。
  半角字符与全角标点之间不留空格。
- **中文标点用全角**（，。：；「」），英文整句用半角；别混用。
- **数字用半角**，单位照界面原文写（`10MB`、`2000 个文件`）；同一种写法在一页里保持一致。
- **链接文字说清楚去哪**：写[验收与采纳](/accept#accept)，不写「点这里」「详见此处」。
  链到某一节时带上锚点，锚点必须是目标页里真实存在的那个 `{#slug}`。
- **不堆引号。** 一句话里出现三个「」，通常说明这句话在罗列界面元素，改成表格或
  列表更好读。

## 「AI 腔」清单

下面每条都出自本仓库真实页面。改的时候先认形状，再改写法；形状认出来了，改法就不难。

| 形状 | 坏例（来自本仓库文档） | 改后 |
|---|---|---|
| 类比开场 | 和芝士协作，就像把一件事交给一位能干的同事：先说清要什么、做到什么算完，中途随时补一句，最后检查交回来的东西。 | 在频道里说清要什么、做到什么算完；芝士执行时可以随时补充要求；交付后检查结果，决定采纳还是退回。 |
| 「不……也不……」排比 | 执行中发的消息会直接并进正在进行的这一轮，不用等它做完，也不用再 `@` 一次。 | 执行中发的消息并进正在进行的这一轮，不用重新 `@` 它。 |
| 替读者总结一遍 | 项目看板把所有任务按「下一步在谁手上」分成几列，一眼能看出哪些在做、哪些在等你。 | 项目看板按「下一步在谁手上」把任务分成几列。（列的意思在下面的表里） |
| 叮嘱句 | 不要只看芝士说了什么，也要看它实际改了什么。 | 芝士的结果说明和它实际改的文件都要看。 |
| 指代不明 | 如果这一轮还没开始，它不会执行。 | 这一轮还没开始时不会执行。 |
| 拟人化 | 芝士接到一件事后，会把它拆成一条或几条「任务」并行推进。 | 芝士把一件事拆成一条或几条「任务」，并行推进。 |
| 软化词 | 收起只是从左侧栏和课程首页隐藏，地址仍然打得开。 | 收起后从左侧栏和课程首页隐藏，地址仍然打得开。 |
| 空泛过渡 | 下面我们来看怎么把文件上传上去。 | 删掉；标题已经说了这是「上传文件」。 |
| 卖点式标题 | 一张图看懂 / 认识频道页面 | 频道页面的区域 |
| 软动词开头 | 芝士会先复述它的理解，再开始干活；你可以随时插话补充要求。 | 芝士先复述它的理解，再开始执行；你随时可以补充要求。 |

更长的清单、每一类的出手方式（哪些该删、哪些该换词、哪些只是语气）见
[references/ai-tells.md](references/ai-tells.md)。

一条总则：**AI 腔不是用词问题，是「说了但没有信息」**。判断一个句子该不该留，
先问它有没有告诉读者一个他能验证的事实；没有就删，而不是换个词。

## 改一篇的流程

1. 读样板页，再读要改的这一页，写下这一页要让读者做成的那件事和贯穿全页的例子。
2. 按页面类型对照骨架；步骤按「步骤」一节改，该配画面的地方按「画面」一节配。
3. 按「核实」一节对一遍每条界面说法。
4. 逐句过语体和「AI 腔」清单。`{#slug}`、站内链接、frontmatter 不动。
5. 过一遍下面的自检清单，再跑「验证」。

## 自检清单

- [ ] 开头一句锚在例子上，没有未定义的产品术语；前提在 `:::before` 里。
- [ ] 每个产品术语第一次出现时有一句书面定义；没有「收下」「放进项目」这类自造说法，没有口语词。
- [ ] 每列步骤三到七步，一步一个动作，最后一步写看得到的结果；没有折行超过三行的步骤。
- [ ] 会改变屏幕的步骤列表有 `:::walk`；单个动作的画面紧跟它那一步；每块画面连同文字放进一屏。
- [ ] 建议单独成节；提示框不超过三个；结尾有「接下来」卡片。
- [ ] 每条界面说法核实过；页面里没有「待确认」。
- [ ] 1440 浅色、深色和 390 宽下各看过一遍截图。

## 验证

在仓库根目录跑：

```bash
python3 .claude/scripts/check-manual-anchors.py   # 锚点、摘要句、死链、图片
cd docs/site && npm run build && npm test         # 站点构建、界面字样检查、演示的 DOM 测试
```
