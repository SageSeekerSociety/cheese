# 知是用户文档写作

这份 skill 管两件事：知是的用户页面**按什么结构写**，以及**什么样的中文算「AI 腔」**。

配套的硬约束（锚点、摘要句、链接、图片路径）由 `.claude/scripts/check-manual-anchors.py`
与 `docs/site` 的构建把关；页面职责、事实验证、frontmatter 的规矩在
[`docs/manual/README.md`](../../../docs/manual/README.md)。这份 skill 只补它没说的部分：
**怎么写**。事实从哪来、哪一页负责什么，仍然以那份 README 为准。

## 读者是谁

学生、老师、助教、团队成员、办公室同事。他们**不一定是程序员**：会用浏览器，不一定懂
分支、仓库、CI、沙箱。有程序员读者，但没有一段可以假定读者是程序员。

读者来这一页是为了完成一件事，不是来理解这个产品。写的时候手里放着这个提问：

> 一个第一次用的人，照着这一页做，会在哪一步停下、点错、或者问「那现在呢」？

语气：一个熟悉产品的人站在旁边说清楚。不推销，不共情，不开玩笑，不客套。
不用「让我们」「下面我们来看」，不要感叹号，不要「你可以试试」这类邀请。

## 一页怎么组织

所有页面共用这几条：

- **第一句说这页讲什么。** 一句话讲完，可以用「这一页……」开头。守卫会拿它当这节的摘要，
  llms.txt 里的每一行就是它，所以它得能脱离上下文读懂。
- **一页一件事。** 一页只解释一个功能或教一件事；其余链接到权威主页面，不在这里重讲。
- **开头写前提。** 需要账号、权限、设备、前置步骤，放在正文开始处，别藏在第三步里。
  只写真的需要的：平台默认就有的东西（比如芝士默认在云端干活）不算前提。
- **一段一件事，一段不超过 7 行。** 一段塞了三个并列要点就拆成列表；一坨 15 行的段落
  读者会跳过去。
- **一个列表里的每一项结构相同。** 全是动宾短语，或全是名词短语，不要混。
- **概念页先定义再展开。** 第一句给一个可以被反驳的定义，再给两三个具体例子。
- **排障小节按「现象 → 意思 → 处理」。** 先照抄提示原文，再解释，再给操作。

### 教程

教程教一件真实的事，读者照着做完，手里就有那件事的结果。知是是对话式的产品，
所以教程的主体是**对芝士说什么、它交回来什么**，不是界面上的一串点击。
样板是 Claude Code 文档的 [Common workflows](https://code.claude.com/docs/en/common-workflows)
和 [Quickstart](https://code.claude.com/docs/en/quickstart)，以及 Tana 的
[Supertags](https://outliner.tana.inc/learn/features/supertags) 页。

- **用一个场景开头。** 第一句照常说这页讲什么，紧接着写读者此刻的处境，比如「你们三个人
  要在两周内交一份数据结构大作业」。不写「本教程将介绍」。
- **步骤用 `:::steps`，标题写目标。** 「讲清作业要求」「让芝士先出一版」「中途改方向」，
  不写「点击某按钮」。每一步的正文先一句话说这一步做什么，再给要发的消息。
- **要发给芝士的话写成 ```` ```prompt ```` 块，和芝士对话的每一步给两三条。** 纯界面操作的一步（建空间、批准、改设置）不硬塞消息。 用学生真会发的内容：
  具体的课、具体的文件、具体的要求。几条之间要有差别（换一种问法、加一个约束、换一种场合），
  读者照抄任意一条都能用。
- **说清芝士会怎么回。** 写读者在对话里会看到什么（它先复述理解、发问题卡让你选、
  结束时列出改了哪些文件），读者据此判断走对没有。
- **界面路径压成一行。** 「团队 → 成员 → 复制链接」这样一行写完，后面接这一步的结果；
  只有路径上真的有岔路或陷阱时才拆成编号小步。完整的点击步骤留在功能页，教程链过去。
- **「完成后：」只在读者分不清做没做完时写。** 一步做完界面明显变了（新页面、新卡片），
  不用再写一行。
- **用到界面的地方必须有画面。** 优先用 `demo-steps` 加 `embed:`（产品真组件演的画面，
  见 `docs/manual/dev/docs-site.md` 的 #demos-embed），其次是 `docs/site/shots` 拍的真截图。
  画面不能代替文字：每一步不看图也读得懂。
- **用提示框放旁支。** `> [!TIP]` 放技巧，`> [!NOTE]` 放读者可能误会的事实，
  `> [!WARNING]` 放做错了会丢东西或丢分的事。一节最多一个，不放正文主线。
- **结尾用 `:::cards` 给下一步。** 两到四张卡，每张一个读者接下来最可能做的事。

### 功能页

功能页回答「这个功能在哪、怎么用、有什么限制」，读者是来查的。

- **点击流程用编号步骤。** 一步一个动作，动词开头，祈使句，读者能立刻做完。
  编号步骤前面要有一句正文；守卫会报「这一节没有开头的说明句」。
- **步骤之后写结果。** 用「完成后：……」一行写读者此刻应该看到什么，不写动机和安慰。
- **限制和例外分开写。** 已确认不支持的操作直接写明。

### 页面组件

`docs/site` 的构建认得下面这些写法，`.md` 原文和 llms.txt 里它们仍是普通 Markdown。

| 写法 | 用途 |
|---|---|
| `:::steps` … `:::`，里面每个 `### 标题 {#slug}` 开一步 | 教程的步骤，自动编号 |
| ```` ```prompt ```` | 一条要发给芝士的消息，带复制按钮 |
| `> [!TIP]` / `> [!NOTE]` / `> [!WARNING]` 开头的引用 | 提示框；不带标记的 `>` 是说明框 |
| `:::cards` … `:::`，里面一个列表，每项 `- [标题](/页面#锚点)：一句话` | 下一步卡片 |
| `demo-steps` 加 `embed: <名字>` | 产品真组件演的画面 |

步骤里的 `###` 标题照常要有 `{#slug}` 和节首说明句。

## 标题

- 用名词短语或动宾短语：「描述目标」「上传文件」「查看提交记录」，不用问句、不用口号、
  不用「你应该知道的……」这类卖点。
- 层级最多三级（`#` / `##` / `###`），跳过一级会让人以为漏了内容。同级标题不要只有一个。
- 每个标题后面必须跟一句正文。写完标题直接接列表、表格、引用或代码块的，补一句开头。
  守卫会报「这一节没有开头的说明句」。编号步骤同样算列表：从「1.」开头的小节就是没有
  摘要句，守卫也会报。
- 标题文字可以改，**标题末尾的 `{#slug}` 一律不动**：那是别处链接过来的地址，
  改了所有旧链接就断。新加的标题按小写字母、数字和连字符起 slug。

## 句子

- **祈使句写操作，陈述句写事实。** 操作句子动词开头（点「发布」、填「项目名称」），
  说明结果才用陈述句。少用「可以」：「你可以点」这类写法去掉「你」和「可以」，
  直接写动作。
- **主语清楚。** 「它」只能指上一句里唯一的那个人或物。指代不明就写回名字，或者换个说法
  把主语省掉：「如果这一轮还没开始，它不会执行」→「这一轮还没开始时不会执行」。
- **一句一件事。** 中文一句话控制在 40 字以内；并列条件多时拆句，别用逗号串成一条长链。
- **肯定句优先。** 「电源已关闭」胜过「请确认没有接通电源」；不要双重否定。
- **少用被动。** 「改动合进项目」而不是「改动被合进项目」。
- **不替读者总结。** 不写「这样就完成了整个过程」；结果用界面上的字样说明。
- **不解释动机。** 除非不做会导致操作错误，否则不写「这么做是为了……」。
- **不用类比开场。** 一个功能是什么，就用它的名字和它的行为说；不要「就像把一件事交给
  一位能干的同事」。
- **一段里第一句就是结论。** 别先铺垫三句再点题。

### 界面文字、标点与空格

- **界面上的字样照抄，包在「」里**：「新建项目」「查看改动」「仍要采纳」。按钮、页签、
  菜单项、提示原文、状态名都属于这一类。拿不准原文时去
  `frontend/src/i18n/messages/zh-CN/` 下核对，不要凭印象改写。
- **代码、命令、路径、文件名、快捷键用反引号**：`cheesehost status`、`index.html`、
  `Ctrl/Cmd+Enter`、`/spaces/<空间号>/tasks/publish`。
- **「」不做强调用。** 普通名词（任务、进度、现场、额度）不加引号，除非它同时是界面上的
  字样（右侧的页签就叫「现场」，那就加）。强调一处内容，先想能不能把话写清楚。
- **加粗只留给漏掉就会做错的地方。** 一页里最多两三处；用**加粗**当小标题、或给每段开头
  加粗一个词的写法，读起来像宣传页。
- **中英文之间留一个半角空格**：`GitHub`、`tokens`、`Ctrl/Cmd+Enter` 前后各留一个。
  半角字符与全角标点之间不留空格。
- **中文标点用全角**（，。：；「」），英文整句用半角；别混用。
- **数字用半角**，单位照界面原文写（`10MB`、`2000 个文件`）；同一种写法在一页里保持一致。
- **链接文字说清楚去哪**：写[验收与采纳](/accept#accept)，不写「点这里」「详见此处」。
  链到某一节时带上锚点，锚点必须是目标页里真实存在的那个 `{#slug}`。
- **不堆引号。** 一句话里出现三个「」，通常说明这句话在罗列界面元素，改成表格或
  列表更好读。

## 「AI 腔」清单

下面每条都出自本仓库真实页面。改的时候先认形状，再改写法；形状认出来了，改法就不难。

| 形状 | 坏例（来自本仓库文档） | 改后 |
|---|---|---|
| 类比开场 | 和芝士协作，就像把一件事交给一位能干的同事：先说清要什么、做到什么算完，中途随时补一句，最后检查交回来的东西。 | 在话题里说清要什么、做到什么算完；芝士执行时可以随时补充要求；交付后检查结果，决定采纳还是退回。 |
| 「不……也不……」排比 | 执行中发的消息会直接并进正在进行的这一轮，不用等它做完，也不用再 `@` 一次。 | 执行中发的消息并进正在进行的这一轮，不用重新 `@` 它。 |
| 替读者总结一遍 | 项目看板把所有任务按「下一步在谁手上」分成几列，一眼能看出哪些在做、哪些在等你。 | 项目看板按「下一步在谁手上」把任务分成几列。（列的意思在下面的表里） |
| 叮嘱句 | 不要只看芝士说了什么，也要看它实际改了什么。 | 芝士的结果说明和它实际改的文件都要看。 |
| 指代不明 | 如果这一轮还没开始，它不会执行。 | 这一轮还没开始时不会执行。 |
| 拟人化 | 芝士接到一件事后，会把它拆成一条或几条「任务」并行推进。 | 芝士把一件事拆成一条或几条「任务」，并行推进。 |
| 软化词 | 收起只是从左侧栏和课程首页隐藏，地址仍然打得开。 | 收起后从左侧栏和课程首页隐藏，地址仍然打得开。 |
| 空泛过渡 | 下面我们来看怎么把文件上传上去。 | 删掉；标题已经说了这是「上传文件」。 |
| 卖点式标题 | 一张图看懂 / 认识话题页面 | 各部分怎么连起来 / 话题页面的区域 |
| 软动词开头 | 芝士会先复述它的理解，再开始干活；你可以随时插话补充要求。 | 芝士先复述它的理解，再开始执行；你随时可以补充要求。 |

更长的清单、每一类的出手方式（哪些该删、哪些该换词、哪些只是语气）见
[references/ai-tells.md](references/ai-tells.md)。

一条总则：**AI 腔不是用词问题，是「说了但没有信息」**。判断一个句子该不该留，
先问它有没有告诉读者一个他能验证的事实；没有就删，而不是换个词。

## 改一篇的流程

1. 读完整页，写下这一页要让读者完成的那件事。
2. 逐节看：节首摘要句在不在、这段讲了几个要点；教程和功能页各按上面那一节的写法对照。
3. 逐句过「AI 腔」清单，只改写法。**事实一个字都不动**：功能、按钮名、路径、限制、
   数值、适用范围、frontmatter、锚点、链接、`demo-*` 围栏里的内容全部保持原样。
4. 信息可以删重复，不能删事实。删之前问：这句话去掉之后，读者会不会少知道一件必须知道的事。
5. 过一遍下面的自检清单，再按「验证」跑构建与守卫。

## 自检清单

改完逐条对，有一条对不上就回头改：

- [ ] 每页第一句仍然说清这页讲什么，每节第一句仍是完整句子（不是列表、表格、引用或代码）。
- [ ] `{#slug}`、站内链接、图片路径、frontmatter 一个都没变；`demo-*` 围栏原样未动。
- [ ] 功能页：步骤是祈使句，一步一个动作；「完成后：……」写的是读者能看到的东西。
- [ ] 教程：场景开头；步骤标题写目标；和芝士对话的每一步有可以照抄的 `prompt` 消息；界面路径压成一行；
      用到界面的地方有画面（真组件演示或真截图）；结尾有下一步卡片。
- [ ] 界面字样与产品一致（不确定的去 `frontend/src/i18n/messages/zh-CN/` 核对）。
- [ ] 每段不超过 7 行、一件事；长段落已经拆成列表或分段。
- [ ] 「」只包界面原文，没拿它当强调；加粗不超过两三处。
- [ ] 中英文之间一个半角空格，全角标点没被写成半角。
- [ ] 感叹号、类比、口号、安慰句、动机解释、替读者总结的句子都删干净了。
- [ ] 没有句子比其他句子明显短一截、单独成段用来「有力」（`X。就是这样。` 这类）。
- [ ] 链接文字说的是去处，不是「这里」。

## 验证

改的是 `docs/manual/` 时，在仓库根目录跑：

```bash
python3 .claude/scripts/check-manual-anchors.py   # 锚点、摘要句、死链、图片
cd docs/site && npm run build && npm test         # 站点构建 + 演示
```

三个都过了才算改完。守卫红了先按它的提示改，不要绕过。

## 来源

结构规则取自[阮一峰《中文技术文档的写作规范》](https://github.com/ruanyf/document-style-guide)
（标题、段落、标点、中英文混排、句子长度）；任务开头、祈使句、第二人称、现在时、
一段一件事这些做法，是 [Google developer documentation style guide](https://developers.google.com/style/highlights)、
[Microsoft Writing Style Guide](https://learn.microsoft.com/en-us/style-guide/top-10-tips-style-voice)
和 Claude Code / OpenAI 文档共同的写法；去 AI 腔的清单改写自
[stop-slop](https://github.com/hardikpandya/stop-slop) 与
[avoid-ai-writing](https://github.com/conorbronsdon/avoid-ai-writing) 的句式表。
