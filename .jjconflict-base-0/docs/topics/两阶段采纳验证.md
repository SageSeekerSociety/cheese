## 进展

### 前提 2（项目已连 GitHub 仓库）：✅ 满足，有证据

`/sandbox/github-token` 返回 **HTTP 200**，`data.permissions = "read-only: actions, checks, metadata"`，token 前缀 `ghs_`（installation token）。该端点只查 `project_git_installations`、无全局兜底，所以 200 就是"本项目已注册 installation + repo"的直接证据。

### 前提 1（批准人已连接个人 GitHub 账号）：⚠️ 沙箱无法直接验证，但代码层面发现拦路问题

**能验证的部分**：`GET /api/users/me/github-account/authorize-url` 现在返回 **401 Login required**，不再是 404。但这只能证明路由挂着（路由是无条件自动发现挂载的，`main.py::_discover_routers`），**证明不了 `github_app` 这个 provider 真的启用了**——`require_auth_user` 在 provider 查找之前就拦下了，沙箱没有用户登录态，到不了那一步。这一条**从沙箱验证不了**，不编。

**代码层面发现的疑似真问题（待真实一跑证实/证伪）**：`_resolve_pr_prerequisites()` 取 token 用的是
`app/domain/oauth/services.py::get_github_user_token_for_handle()`，它 `return getattr(conn, "access_token", None)` —— **拿的是密文，没有解密**。而写入端 `OAuthService.create_connection/update_connection_tokens` 都做了 `encrypt_text(...)`（Fernet）。同一文件里另有一个**正确的**兄弟方法 `OAuthService.get_github_user_token(user_id)`，它 `decrypt_text(...)` 且带过期/refresh 处理——但两阶段采纳这条路没走它。

推论：如果账号确实连上了，`_resolve_pr_prerequisites` 会返回一个**非空但不可用的密文串**（通过 `if not token` 检查），随后 `_open_pr_for_accept` 用它 push / 开 PR 会被 GitHub 401 → 落进 `except Exception` → 静默降级成直推 main。**观感上跟"账号没连"完全一样**，需要靠真实一跑区分。

为什么测试没拦住：唯一覆盖它的 `backend/tests/integration/test_accept_pr.py:150` 直接 monkeypatch 掉了整个 `get_github_user_token_for_handle`，加解密往返从没被跑过。

### 对本次一跑的两条预测（写在前面，便于事后对照）

1. **CI 大概率不会全绿**：`claude-review.yml` 对**所有** PR 无路径过滤地触发，且跑在 `ubuntu-latest`（GitHub 托管额度 2026-07-26 已耗尽）——父话题已观察到它在所有 PR/commit 上全部失败。而 `github_pr._summarize_runs` 的规则是"任一真实失败即 failure"，所以轮询会判 failure → 触发 `_nudge_pr_fix` 来唤醒芝士修 CI。**若我被这样唤醒，我不修，只报告。**
2. 本次改动只碰 `docs/**`，`test.yml` / `e2e.yml` 都有路径过滤（只认 `backend/frontend/e2e/workflows`），所以这两套重的 CI 在 PR 上不会跑——这是刻意选的，为了让"两阶段机制本身"的信号不被已知红掉的 E2E 淹没。合并进 main 后 `build.yml`（push 到 main，无路径过滤）照样会触发，部署链路仍会被完整走一遍。
