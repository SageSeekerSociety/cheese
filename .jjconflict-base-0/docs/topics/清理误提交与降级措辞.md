## 已确认的技术事实（我自己核过的，不是简报转述）

- **区分信号**：`push_topic_branch_for_github_pr` 会吸收**第一次** workflow 权限拒绝（同步 GitHub 默认分支后只重试一次）。因此**能冒泡到 `review/services.py` 捕获点的 workflow 权限拒绝，必然是第二次**——这就是"这张卡真的改了 workflow 文件"的精确信号，不需要 diff 文件树。判定复用 `workspace/service.py::_is_workflow_permission_rejection`。
- **同步失败不会误判**：同步不成功时抛的是「话题分支的 workflow 文件与 GitHub 默认分支不一致且无法同步（…）」，不含 `refusing to allow`，`_is_workflow_permission_rejection` 返回 False → 正确地落进「其它失败」桶（这类确实需要人看）。
- **`_nudge_pr_fix` 去重不受影响（已按代码路径核实）**：`_with_pr_degrade_note` 只在本地合并路径写 note，卡的状态是 `accepted` / `conflict`；而 `_nudge_pr_fix` 只在 `advance_pr_card` 里被调用，后者开头 `if card.status != AcceptStatus.pr_open: return` 早退。两条生命周期不相交，降级 note 永远到不了那个 `startswith("⚠️")` 判断。另外补一条行为测试锁住这个不变量。
- **沙箱限制**：本容器 `jj`/`git` 读不出仓库（`.jj/repo/config-id` 权限拒绝，与父话题记录的是同一个已知问题）。所以"扫 main 文件树"只能用**工作区文件树 + `.gitignore` 比对**做，不能用 `git ls-tree`。工作区是 main 的新检出，没跑过任何服务，因此树里出现的文件基本等同于"仓库里有"。

### 测试环境（沙箱里没有 Postgres，已解决，不是硬磕）

`tests/conftest.py` 有个 session 级 autouse 的 `_pg_schema`，连不上 `:5433` 就把**所有** unit 测试也一起 ERROR 掉。容器里只有 `postgresql-client-15`（没有 server），apt 也没有 server 包。解决办法：从 PyPI 取 `pgserver` 的 cp312 wheel、解出里面自带的 postgres 二进制，用户态 `initdb` + `pg_ctl -p 5433` 起一个（数据目录在 scratchpad，不在工作区）。这条路子值得记住——比在沙箱里跟 PG 缺失纠缠快得多。
