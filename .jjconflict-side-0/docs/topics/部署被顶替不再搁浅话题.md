## 平台问错了问题

两阶段采纳的第二道闸门是「合并之后、部署也成功才归档」。它原来按 `head_sha`
**精确匹配**去找这次合并的部署 run，然后只看那个 run 的结论。

问题不在于判得松还是紧，而在于**问法**：「我这个 sha 的部署 run 怎么样了」取决于
GitHub 调度的偶然（并发组、事件合并、重试），而人真正关心的是「**我这个 commit
到底上线了没**」。后者是事实，前者不是。

2026-08-11 一天里，这个错问法以三种面目出现：

| 现象 | 真相 |
|---|---|
| PR #251 的部署 run 是 `cancelled` | 被更晚的部署顶替（并发组对**排队中**的 run 的正常行为），代码早就上线：`0c194f38` 在成功部署的 `8470ac052` 里 |
| #267/#270/#274 的部署 run **根本不存在** | 并发组名是固定字符串 `deploy-dev`，合并一密集，后来的 `workflow_run` 触发直接被吞掉，**连 run 都不会被创建**。三个提交全是 16:11 那次成功部署 `45b6169a4` 的祖先——代码到了 dev，只是账没销 |
| build 403 推不动镜像 | 这个提交自己的镜像确实没有——但只要后来有包含它的成功部署，它的源码照样在盒子上（见下面第四条边界） |

前两种加起来是同一句话：**run 是否存在、是否被顶替，都不该是归档的依据**。而且第
二种不是偶发故障，是这套并发配置的固有行为——**合并越密集越容易撞上**，也就是说
平台自动合并跑得越顺，卡死的概率越高。#267 就这样躺了三个多小时。

（`deploy-dev.yml` 的 `cancel-in-progress: false` 不动：两个部署同时上盒子会互相
踩，那个配置在保护更重要的事。要修的是平台的判据。）

## 主判据

`_advance_deploy_checks` 现在的顺序是：

1. 自己那次 run 报 `success` → 归档（老路径，一次 API 调用，没变）。
2. **其余一切情况**——cancelled、failure、还在跑、压根没有 run——改问主判据：
   **有没有一次更晚的、真的部署过的成功部署，它的 commit 包含这个合并提交？**
   有 → 代码已上线，闸门满足，归档。
3. 还是定不了案 → 保持 active 交给人，并按情况说清楚是哪一种。

第 2 步是主判据而不是 cancelled 的补丁：它问的根本不是 run，所以一视同仁地覆盖
上面三种面目。包含关系用 GitHub 的 compare 接口判
（`GET /repos/{owner}/{repo}/compare/{base}...{head}`，`base` = 那次成功部署的
commit、`head` = 我们的合并提交，`status` 为 `behind` 或 `identical` 即包含），
**不在平台侧克隆仓库跑 git**——一次 API 调用就有答案，而平台根本没有这个项目
GitHub 仓库的 checkout。

## 五条边界（都有测试钉着）

- **只认更晚的**。早于本次合并的部署跑的时候这个提交还不存在，不可能把它带上线。
  运行列表是新→旧，扫到合并时间就停。
- **完成 ≠ 成功**。只有字面 conclusion 是 `success` 才算；`cancelled` / `skipped` /
  `neutral` 都是「completed」。
- **成功 ≠ 真的部署过**。`deploy-dev.yml` 对 docs-only 提交会跳过登录和部署两步，
  job 照样报 success，盒子上什么都没变。所以每个候选运行都下沉到 **job/step
  一层**核对：必须有某个 job 报 success、跑过至少一步、且**没有任何一步是
  skipped**。这条是名字无关的（job/step 名是项目自己的事）：绿灯 job 里出现
  skipped 步骤，就是 workflow 在说「这部分我故意没做」。
- **一个 commit 不需要有自己的镜像才算上线**。「这个 commit 的镜像有没有被推上
  去」曾经被提为第三类的判据、也在代码里当过一道否决闸，2026-08-11 撤回：它只是
  「代码上没上线」的一个坏代理。build 403 推不动镜像时（`docker login -u
  github.actor` 在 push 事件里取的是提交作者，采纳提交的作者不是仓库主；根因已由
  #276 修掉），这个提交自己的镜像确实不存在——但一个**包含**它、并且真的部署过的
  更晚提交，已经把它的源码送上盒子了。按镜像判，`#267`/`#270`/`#274` 会永远等一个
  自己的镜像，而它们三个都已经是 16:11 那次成功部署 `45b6169a4` 的祖先；按祖先
  关系判，它们因为**正确的理由**归档。
- **失败的方向只能是"不归档"**。整条链路尽力而为：任何一步的 GitHub 故障、拿不到
  token、查不到 job，都退回旧行为（保持 active、告诉人）。它只可能把一次误报变成
  归档，不可能反过来——宁可等人，不可假装上线。

## 人看到什么

- **靠主判据归档时**，卡片和通知不会说「本次部署成功了」，而是说清楚是被哪次更晚
  的成功部署带上线的，并附上那次运行的链接。
- **部署真的失败时**，带上 GitHub 自己的失败 job 名，例如
  「（失败的 job：build-did-not-produce-images）」——报告事实而不是猜原因，人一眼
  能分清「部署跑了但挂了」和「压根没产出镜像」。
- **既没上线也没有结论时**（合并超过 `accept_deploy_stale_after_minutes`，默认
  45 分钟），写一条 `⏳` 备注并通知一次：说明可能压根没有 run、等下去不会有结果。
  一次，不是每轮。默默等着正是这个话题要治的病。
