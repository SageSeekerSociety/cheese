### 3. 评估结论：`SandboxReaperRunner` 暂不需要加磁盘压力触发路径

结论是**不建议加**，理由：

- 任务 1 修完之后，`cheesex-disk-pressure-guard.sh` 本身就是一条已经存在、5 分钟一次、经过双重 active_turns 确认的磁盘压力快速通道，现在两种后端都覆盖了——简报里描述的"从磁盘压力升高到被清理之间完全没有快速通道"这个缺口，标签修好之后已经堵上，不是还缺一条路径。
- 这个 shell 脚本压力触发时是**无差别清空所有** `cheesex-sandbox=1` 容器（不看话题活跃度，只看全局 active_turns==0），而 `SandboxReaperRunner`/`reap_idle_containers` 是**按话题 3 天无活动**才回收单个容器，两者的清理粒度和触发条件设计目标不同。如果给 `SandboxReaperRunner` 也接上磁盘压力触发，会出现两条独立机制（bash systemd timer + Python asyncio 循环）在同一磁盘压力条件下互相竞争同一批容器的局面，收益（多一层保险）远小于复杂度和"两处判断 active_turns/加锁语义不一致导致误杀"的风险。
- `main.py` 里 `reap_sandbox_containers()` 被故意移出启动流程的前车之鉴（重启时误杀在跑任务）说明这类"跨路径清理同一资源"的改动历史上出过事故，调度层不宜在这个任务里顺手加。

按简报要求，这个判断认为超出可以自己拍板的范围（涉及调度器核心逻辑取舍），**只给结论和取舍，不做代码改动**，上报父话题由人确认是否认可"不加"这个结论。
