## 目标

打开长话题时浏览器卡死。实测本父话题 `GET /api/topics/{id}/blocks` 一次返回 **2,198,916 字节 / 2226 条**，且 `pageSize` 参数**根本不存在**（传了也返回全量）。卡的是三件事叠加：2.1MB 传输 + 2226 条 JSON 解析 + 2226 个 DOM 节点常驻。前后端一起改掉。

## 关键设计选择（已定）

**游标式（cursor），而且默认行为保持全量不变。**

```
GET /topics/{id}/blocks                     → 全量（与今天完全一致）
GET /topics/{id}/blocks?limit=50            → 最后 50 条（底部锚定）
GET /topics/{id}/blocks?limit=50&before=<block_id>  → 该 block 之前的 50 条
```

响应在原有 `{data, total}` 上增加 `has_more`（是否还有更早的）和 `oldest_id`（当页最老一条的 id，即下一次的 `before`）。

**为什么是游标而不是 offset**：聊天是底部锚定 + 实时追加的。offset 从尾部数，用户滚上去翻历史的同时新消息在尾部落地，窗口整体位移 → 第二页会重复或漏掉消息（经典的"边聊边翻页错位"）。游标锚在一条具体消息上，尾部插入多少条都不影响"比它更早的 N 条"这个语义。实现代价一样：`(created_at, id) < (游标的 created_at, id)` 的元组比较，走同一个索引。用 `(created_at, id)` 而不是单 `created_at`，是因为 `created_at` 是 Python 侧 `datetime.now(UTC)` 生成的，流式帧成批落库时可能同一微秒撞上，单列排序不是全序。

**为什么默认不变**：这个端点 agent 也在用（`cheese api GET /topics/{id}/blocks`）。默认改成"只给最后 N 条"会让所有 agent 侧查历史**静默截断**。默认全量 + 显式 `limit` 才走分页，兼容性问题从根上不存在，也就不需要改 `SKILL.md`（已核查：`backend/sandbox/skills/cheese/SKILL.md` 全文没有提到 `/blocks`，`cli/` 里也没有调用点）。传了 `limit` 的调用方靠 `has_more` 知道"还有更多"。
