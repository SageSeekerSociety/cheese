## 目标

在项目话题列表接口 `GET /api/topics` 上，给每个话题补两个「跟我什么关系」的布尔字段，让前端能把「我参与的」和「其他话题」分成两组。**纯后端**。前端接线是另一条线的活，本话题一个前端文件都没碰。

## 做成了什么

`TopicOut` 上新增两个正交的布尔（不是一个枚举——枚举每加一种关系就得动前端的分支，布尔各管一件事）：

- **`i_participate`**：这话题跟我有关系。四种命中任一即为真——我在话题名册里 / 我是创建者 / 我是它验收卡上被点名的人 / 我在这话题里被 @ 过。
- **`awaits_me`**：这话题在等我动手。有一张点名给我、状态还是 `pending` 的验收卡，或者有 @我 而我还没读的提醒。

`awaits_me` 为真时 `i_participate` 一定也为真。所以前端那条「需要我行动的永远不折叠」安全线，只看 `awaits_me` 就够。

两个字段由 `list_topics` 和 `get_topic` 填（和 `last_activity_at`、`running` 完全同一套约定），别的返回 `TopicOut` 的端点保持默认 `false`——注释里写明了这一点。`get_topic` 也填是刻意的：深链直接打开一个正等你验收的话题，不该报 `awaits_me: false`。

## 关键发现（简报没覆盖到的）

简报担心「被 @ 过」要全表扫消息内容、代价太大，建议先跳过这一条。**不用跳过**：一个 @ 在落地时就已经写了一行 `alerts`（`kind=mention`，带 `topic_id`、`target_handle`、`read_at`，两个 handle 字段都有索引，见 <&backend/app/domain/agent/chat.py> 的 `_notify_mentions`）。所以「被 @ 过」和「有 @我 的未读」是同一条索引查询顺带得出的。**四种参与关系全部做进去了，没有缺口。**

## 性能：额外代价是 3 条查询，恒定

不管项目里有 1 个还是 100 个话题，相关性判定就多 3 条 SQL——名册一条、验收卡一条、@提醒一条。「我建的」不花钱，`created_by` 本来就在已经取回的行上。

实测：一个已登录用户调 `GET /api/topics`，整个端点一共发 **9 条** SQL（1 条验 token、1 条查项目成员、1 条查项目、1 条列话题、1 条 count、1 条算 last_activity，加上相关性这 3 条）。测试里用 1 个话题和 12 个话题各跑一遍对比，9 条一条不多——N+1 已排除。

## 中途改了一次做法

第一版让 `TopicService` 直接 new 别人的 repository，被仓库自带的架构护栏 `tests/unit/test_domain_import_guard.py` 抓到（跨领域只能调对方的 **service**，不能摸对方的 repository，白名单是棘轮不许加行）。已改成走 `TopicMemberService` / `AcceptService` / `AlertService` 三个 service，各加一个薄读方法。护栏现在是绿的。
