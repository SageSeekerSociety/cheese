# 前端静态资源完整性防护设计

## 问题与目标

2026-08-05 的 dev 白屏并不是 nginx 不可用，而是运行容器里的 `index.html` 来自新构建、`assets/` 仍主要来自旧构建。根路径继续返回 200，原有健康检查因此把无法启动的 SPA 标成 healthy。目标是让这种跨版本、局部覆盖或异常构建在发布前失败，并让已经运行的容器在文件被改坏后自动转为 unhealthy。

## 方案

新增一个只依赖 POSIX shell、`grep` 和 `sed` 的校验脚本。它读取指定静态目录下的 `index.html`，提取本地 `assets/` 的 `src` 与 `href`，要求至少存在一个 JavaScript 入口和一个 CSS 入口，并逐一验证引用文件存在。外部 URL、站点图标和 API 路径不属于 Vite 产物，不参与检查。

同一脚本接入三层：Docker 构建在复制 `dist` 后立即执行，坏镜像无法生成；镜像自身的 `HEALTHCHECK` 同时验证 nginx HTTP 响应和静态引用；各 Compose 文件使用同一健康命令，现有 `deploy-docker.sh` 已等待 Compose healthy 并在失败时回滚，因此无需再复制一份部署校验逻辑。周期性健康检查也能发现运行后通过 `docker cp` 造成的破坏。

## 边界与验证

本改动不尝试禁止拥有 Docker 权限的操作者修改容器；它让这种修改立即可观测并阻止部署验收通过。测试覆盖完整产物、缺失资源、缺少 JS/CSS 入口和缺少 `index.html`。另外解析全部 Compose 配置，并实际构建前端镜像，确认构建门禁、镜像内脚本和健康命令可运行。
