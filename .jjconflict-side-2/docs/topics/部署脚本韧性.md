## 目标

让 `deploy/deploy-docker.sh` 对 2026-08-09 那类瞬时拉取故障有韧性。**不修 containerd、不查"谁删了 ingest 文件"**（那需要宿主机证据，本卡明确不负责）。三件事：

1. 三处 pull 加退避重试；
2. 用 `trap` 保证**失败路径也回收**镜像（本卡最重要的一条）；
3. pull 前后 + 每次回收后打印磁盘水位。

## 约束

- 只动 `deploy/` 下的东西 + 必要测试；不碰宿主机 root、不停 dockerd、不 `rm -rf` containerd 目录。
- 保持 `set -euo pipefail` 语义：重试用尽后**仍然必须非零退出**，错误信息要带重试次数和每次的失败原因。
- 回收本身 best-effort，绝不能因为回收失败把一次本来成功的部署判成失败。

## 现状：改动已完成，测试已跑绿

改了两个文件 + 一个测试假件：

- <&deploy/deploy-docker.sh> — 主体改动
- <&deploy/tests/test-app-tier-health.sh> — 新增 4 个用例

### 1. pull 重试：3 次，间隔 5s / 15s

`retry_pull <描述> <命令…>` 包住三处 pull（`dc pull backend frontend`、两个 sandbox 镜像）。次数/间隔可用 `DEPLOY_PULL_ATTEMPTS` / `DEPLOY_PULL_BACKOFF_SECONDS` 覆盖。

**为什么是 3 次、5s/15s**：这类失败（ghcr 抖动、containerd 把下载好的层 commit 到已消失的 ingest 文件）重发一次 pull 就会开一条**新的 ingest 记录**，不再碰坏掉那条，所以重试的命中率很高、但边际收益衰减快；总共 20s 的等待足够跨过一次瞬时抖动，又不至于让一个真正拉不到的镜像长时间占着 box 上**唯一那个共享 runner**。

重试之间做一次**幂等清理**（`docker image prune -af` + 有上限的 `builder prune`）——跟脚本原本在末尾做的是同一个操作，没有更激进。刻意**没有**去动 containerd 的 ingest 目录、没有停 dockerd、没有碰运行中的容器。

### 2. 失败路径也回收：`trap on_exit EXIT INT TERM`

在第一次 pull 之前挂 trap 并置 `RECLAIM_PENDING=1`；成功路径仍在原位置内联回收一次（保证 `DEPLOY OK` 还是最后一行），回收后清掉 flag，trap 就不会重复做。

选 `EXIT` 而不是 `ERR`：`fail()` 是显式 `exit 1`，`ERR` 覆盖不到。另外挂了 `INT`/`TERM`，因为 build/deploy 被 single-runner 的 `cancel-in-progress` 取消是这个仓库的常态。

`on_exit` 开头存下 `$?`、结尾 `exit "$rc"`，**退出码不被回收动作改写**；回收内部每条命令都 `|| true`。

一处**刻意的不对称**：失败路径上 `DEPLOY_APP_IMAGE_SOURCE=local` 时**不做 image prune**——本地构建的镜像此时还没跑起来、也没法从 registry 拉回来，删了要人重新构建。registry 模式下镜像按定义可重拉，照删。

### 3. 磁盘水位

`log_disk <时机>` 打印 `/` 和 docker data root（同一文件系统时自动去重）。打点在：pull 前、pull 后、**每次 pull 失败时**、每次回收之后。真实样例：

```
[deploy-docker 18:04:13] disk (before pull) overlay on /: size=251.8GiB used=126.6GiB avail=114.6GiB use=53%
[deploy-docker 18:04:13] disk (image pull failed, attempt 1) overlay on /: …
[deploy-docker 18:04:13] image pull: attempt 1/3 failed (exit 1); reclaiming disk, retrying in 0s
[deploy-docker 18:04:13] ERROR: image pull failed after 3 attempts (attempt 1 exited 1; attempt 2 exited 1; attempt 3 exited 1); …
[deploy-docker 18:04:13] deploy exiting with status 1 — reclaiming disk on the way out
```

## 验证（不是"看着对"）

`deploy/tests/` 里已有一套**假 docker 驱动真脚本**的端到端测试。新增 4 个用例：

| 用例 | 证明了什么 |
|---|---|
| `pull-retry` | 注入 2 次 pull 失败 → 部署成功，日志里恰好 3 次 pull，且第一次 prune 出现在最后一次 pull **之前** |
| `pull-exhausted` | 注入 99 次失败 → **非零退出**、报文含"after 3 attempts"和每次退出码、**没有**走到 migration、且 prune 仍然执行了 |
| `failed-reclaim` | 健康检查失败（pull 之后的失败路径）→ 仍然执行了 prune |
| `disk-watermark` | 三个打点都出现在部署日志里 |

全套 `bash deploy/tests/test-app-tier-health.sh all` **15/15 PASS，exit 0**；`bash .claude/scripts/check.sh --no-tests`（ruff + pyright）exit 0。

另外手工验证了 SIGTERM 路径（模拟 runner 的 `cancel-in-progress` 取消）：脚本在退避等待中收到 TERM → **退出码 143**、并且在退出前执行了回收：

```
[deploy-docker 18:07:17] image pull: attempt 1/3 failed (exit 1); reclaiming disk, retrying in 5s
[deploy-docker 18:07:22] deploy exiting with status 143 — reclaiming disk on the way out
[deploy-docker 18:07:22] pruning all unused docker images (failed deploy)…
```

（时间戳差 5 秒是 bash 的固有行为：前台命令执行期间收到的信号要等该命令返回后才处理。真实的 runner 取消是发给整个进程组的，子进程会同时死掉，不会有这个延迟。）

## 顺手修的一个既有坏测试（非本卡改动）

`test-app-tier-health.sh` 里的 `workflow` 用例按全等名字找 `deploy-drift.yml` 的步骤，而那个步骤早已被改名（多了 ", converge on drift"），导致整个 `all` 跑到那里就硬中断。改成前缀匹配。

**顺带暴露的问题（没修，超出本卡范围）**：`deploy/tests/test-app-tier-health.sh` 和 `test-disk-pressure-guard.sh` **没有被任何 workflow 跑过**（只有 `test-db-restore-test.sh` 进了 CI），所以上面那处腐烂才会一直没人发现。要不要把它们接进 CI 需要单独一张卡。
