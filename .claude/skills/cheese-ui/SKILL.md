# CheeseX 界面设计

产品已经有一套写好的设计语言，源头是 `frontend/src/style.css`（token + 工具类）
和 `frontend/src/plugins/vuetify.ts`（组件主题镜像）。**这两个文件是唯一事实来源**，
本 skill 只是把它们的意图讲清楚，并补上它们表达不了的东西：判断、流程、自查。

任何时候两者冲突，以那两个文件为准，并告诉用户你发现了不一致。

## 第一步：先确定这是哪一种界面

两种界面的规则是**相反的**，用错一套会做出很难看的东西。

**产品界面** — 用户登录后使用的一切：视图、面板、列表、表单、对话框、设置页。
判据是"人要在这里长时间工作"。→ 读 `references/product-ui.md`

**宣传页** — 官网首页、赛题推广页、活动落地页、对外介绍页。
判据是"人只看一眼，要留下印象"。→ 读 `references/landing.md`

不确定就问一句，别猜。产品界面用了宣传页的手法（渐变、大色块）会显得廉价，
宣传页用了产品界面的克制会显得没劲。

## 第二步：先出方案，再写代码

直接开写最容易得到"看起来像模板"的东西。写码前先把这四样想清楚，短短几行即可，
不需要长篇文档：

1. **这个页面的唯一职责是什么** — 一句话。用户来这儿要完成什么？
   页面上任何不服务于这件事的元素都该被砍掉。
2. **信息层级** — 哪个是主，哪些是次，哪些是元信息。对应到 `.t-page-title` /
   `.t-title` / `.t-body` / `.t-meta` 这几档，不要自创字号。
3. **琥珀色出现在哪一处** — 产品界面里它是稀缺资源，整屏通常只该出现一次
   （详见 product-ui.md）。先想好给谁，剩下的一律中性。
4. **布局骨架** — 用文字或 ASCII 草图描述一下，比脑内想象更容易发现问题。

想清楚了再动手。如果用户明确说"先给我看看方案"，就把这四条讲给他听再写码。

## 第三步：写代码时的取材顺序

按这个顺序找现成的，越靠前越优先，能不新写 CSS 就不新写：

1. **已有工具类** — `.t-page-title` `.t-title` `.t-eyebrow` `.t-body` `.t-meta`、
   `.c-ink` `.c-text` `.c-muted` `.c-faint`、`.chip-neutral`、`.status-dot`
2. **Vuetify 组件** — 主题已经镜像过 token，默认样式就是对的，别覆盖它的颜色
3. **CSS 变量** — `var(--ink)` `var(--line)` `var(--fill)` 等
4. **新写样式** — 只在前三样都不够时，且必须引用变量

**永远不要硬编码十六进制颜色。** 不是洁癖：token 是唯一事实来源，硬编码的那一处
将来改主题时改不到，会变成一个孤零零的错色元素。这条在 style.css 里写着，
review 时会被抓。

## 提交前自查

对着改动过一遍，这几条最常出问题：

- [ ] 有没有硬编码的 `#rrggbb`？（`grep -nE '#[0-9a-fA-F]{3,8}' 改动的文件`）
- [ ] 琥珀色出现了几次？产品界面里超过一处就要重新想
- [ ] 状态是用 `.status-dot` + 中性文字，还是做成了彩色 chip？后者是错的
- [ ] 字号是从那五个工具类里选的，还是自己写了 `font-size`？
- [ ] 桌面和窄屏都看过吗？
- [ ] 键盘 Tab 过去，焦点环看得见吗？（`:focus-visible` 已全局定义，别覆盖掉）
- [ ] 有没有加动效？加了的话 `prefers-reduced-motion` 下会不会失控？
      （style.css 已全局兜底，但自定义动画要自己确认）

## 关于"好看"

如果用户贴来一段描述理想效果的话术（渐变、毛玻璃、沉浸式、微妙阴影之类），
先判断它属于哪种界面。产品界面里这些手法大多与"95% 中性"直接冲突——
这时候不要闷头照做，也不要照搬，把冲突指出来，让用户选：是要遵守既有设计语言，
还是这次确实想破例。破例可以，但要是明确的决定，不是稀里糊涂做出来的。
