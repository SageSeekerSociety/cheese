# 平台上的 agent：定下来的原则

这份文档记的是**已经拍板、不再重新讨论**的判断。写下来是因为它们此前只存在于对话里——
每个新会话、每个新来的人、以及平台上的芝士自己，都会从同样的错误直觉重新出发一遍，
然后被同样地纠正一遍。

每条的形式是：**结论 → 为什么 → 它具体否掉了什么做法**。最后一栏最重要：
原则脱离了它否掉的东西就会退化成口号。

---

## 一、agent 是独立的参与者，不是谁的分身

它有自己的上下文、自己的判断、自己会犯的错。把这些记在某个人名下是记错账。
块上就该显示是它说的，不是某个人说的。

**否掉的做法**：给每个人签发一张"他自己的 agent 的凭证"，让 agent 以那个人的身份说话。
也否掉靠偷用户浏览器会话上平台的一切方案——那必然导致人和 agent 在平台眼里是同一个。

**例外：一个人自己的芝士（个人助手）。** 它只属于这一个人，三的前提（一个房间里几个人
对着同一个芝士）在它身上不成立，所以它带着主人的权限、以主人的名义做事。条件是可见（四）：
它做的每一件事都标明是它代主人做的：它发的消息，署名旁标「芝士代发」；它开的任务、做的
审阅决定、发的邀请，以及宣布这些的那行字，都写「芝士代 某人」；读房间的 agent 读到的也是
这样（十九）。房间里的 agent 不在此例，仍不拿谁的凭证说话。2026-10-23 定。

## 二、agent 的权限和人一样大

房间里的 agent 就是这个房间的正式成员，能力和人类成员相同。凭证是**认证**的机械需要
（总得知道是谁在连），不是**授权**的分级——凭证不携带任何缩水。

**为什么**：这个平台一路卡住的全部是"权限太小"，没有一次是"权限太大"。App 是 private
导致新人 404、App 缺 workflows scope 导致一整类卡推不上去、外部没有任何申领凭证的入口——
每一条都是闸门造成的停摆。

**否掉的做法**：任何"权限是某人的子集"的委托模型。以及"先给最小权限，需要时再放开"这种
默认收紧的设计姿态。

## 三、"权限来自谁"这个问题问不出来

委托模型的前提是一个 agent 属于一个人。这里不是——一个房间里五个人对着同一个芝士说话。
按说话的人算，它的能力会随谁开口而闪烁；按建房间的人算，它凭什么比房间里另一个人强或弱；
按交集算，它什么都干不了。

**结论**：agent 的权限不从任何人身上流下来，它的作用域是**房间/项目**。

## 四、安全靠可见，不靠限制

它做了什么、说了什么、改了什么，全在房间里留痕，人随时能看、能回滚。用限制换安全，
代价是它什么活都干不成；用可见换安全，它能干活而你看得见。

## 五、采纳 = 合并那个 PR

不是"启动一个稍后会合并的流程"。验收卡是这个 PR 在平台里的视图（diff + checks + 讨论），
人看到一个 CI 已经绿的 PR，点一下，它就合了。

**否掉的做法**：点采纳之后才去开 PR。那样人是在给一份没有任何检查结果的改动点头，
真正的合并发生在之后某个无人参与的时刻。

## 六、平台不跑检查

仓库在自己的 CI 配置里声明检查，forge 跑，平台**读结论**。可合并性由 forge 回答——
分支保护、required reviews、draft 状态都喂这个答案，自己重算必然漂移。

**否掉的做法**：平台自己维护一个 `check_command` 再跑一遍。那是"检查"的第三套私有定义，
而且它跑在一台没有数据库的机器上，只能 `--no-tests`——发出的绿卡意味着 lint 过了，
一条测试都没跑。

## 七、人签字不是产品定律

免审核 / human-out-of-the-loop 是要支持的一档模式。谁来闭合这个环是可配的，
"必须有人点一下"只是当前的默认值。

**否掉的说法**："人工签字是平台唯一的安全支点，替掉它平台就不成立。"

## 八、平台只说两类话：能力，和事件

- **能力**：你能做什么、不能做什么。「这台机器上没有可用的数据库」「你的 git 凭证推不了
  CI 配置文件」「这台机器闲置 N 小时会被回收」。
- **事件**：发生了什么。「上一轮在 X 被中断了」「你上次推送被拒绝了，原因是 Y」。

它**永远不解释某个项目的配置是什么意思**。平台服务所有项目，把某个项目的配置名写进
提示词就是把一家的实现焊进通用产品。

**推论**：项目自己的配置不靠平台念出来，靠 agent 够得着那台机器自己去看。
平台提供的是**通路，不是知识**。意义住在项目自己的仓库里。

## 九、该修的限制不要拿去广播

绝大多数"需要告诉 agent 的限制"其实是"应该被修掉的东西"。沙箱没有数据库 → 给它一个
数据库；凭证读不了 issue → 放宽凭证；App 缺权限 → 去补上。

真正既查不到又修不掉的，只剩物理事实。这一栏应该很短，不该长成一个体系。

## 十、渐进式披露是默认

system prompt 只留**它自己发现不了、且不查就会白干**的东西，其余全部是指针：
项目知识在仓库的 AGENTS.md，平台工具在 `cheese --help`，流程在 skill 里。

**否掉的做法**：因为"弱模型不会主动去读"就把几 KB 的规则内联进 system prompt。
那是在用体积补偿指针不清晰，而补偿从来不是修。指针不清晰就去修指针。

## 十一、记忆和 AGENTS.md 是两种东西，不是两个筐

|  | AGENTS.md | 记忆 |
|---|---|---|
| 是什么 | **我们定的规矩**——事情**应该**怎样 | **实际遇到的事**——当时**发现**是怎样 |
| 时效 | 跟代码一起改，天然是当下的 | 带日期的观察，会过期 |
| 加载 | 每次必加载，所以有体积预算 | 按相关性召回 |

分界不是"这仓库 vs 跨项目"，是**规矩 vs 观察**。记忆可以反过来纠正 AGENTS.md——
库里就有一条记忆记着「CLAUDE.md 第 3 行把仓库描述成三件套，但实际还有 cli/ 和 evals/」。

晋升（观察 → 规矩）的门槛要高，因为 AGENTS.md 每个会话都要付钱。库里另有一条记忆记着
「只写在文档里的规则会被静默突破」——搬进去不等于被遵守。

## 十二、不要把一段对话升格成机械

**如果一件事在"你开口让 agent 干"时它本来就会干，那它不该被做成平台的一个功能、
一种轮次、一个状态机。**

这是这个代码库犯过的最贵的一类错误。已知的四个实例，后三个的代码已经删掉：

| 实例 | 平台替它干了什么 | 代价 |
|---|---|---|
| pre-PR 质量闸门 | 替它跑检查 | `pending_gate` 死锁（连带整个频道再也递不出卡）、孤儿扫底、两个超时常量、一个状态背两个相反含义 |
| 定期巡检（心跳） | 替它想起来该催人 | 按闹钟而非按事件推送；要发现的事平台在状态变化那一刻就已经知道 |
| 项目摘要（一页纸总结） | 替它总结 | 与频道实况文档形成两份互不知情的"项目状态" |
| 活动接入（线下接入） | 替它整理线下内容 | 独立会话覆盖了频道的会话指针，导致主对话再也 resume 不回去 |

四个都不是实现没写好，是**位置错了**。

## 十三、从第一性原理解决，不给症状写说明书

发现"两代路由撞车"时，正确的问题不是"怎么绕开撞车"，是"为什么两个不同的东西叫同一个
名字"。发现"卡片卡死"时，正确的问题不是"怎么给死锁加个出口"，是"这个状态为什么存在"。

给症状写一份权威说明，会让下一个人以为问题解决了。

## 十四、续跑就是把 transcript 接回来，平台只续会自己过去的故障

会话里什么都有：原任务、干到哪、它自己说过的话。所以不需要重建任何"断点简报"：一个频道的
下一轮接着同一个会话（`resume_session_id`），人在房间里重新 @ 就是续跑，芝士看到的是同一份
transcript 里多了一句话。

平台自己不续：一轮失败、超时、被判卡住，各发一次事件（`who=human`）然后停下，不重跑——重跑
要么把同一个缺陷再触发一遍，要么再撞上同一台刚死的机器。例外只有两种，续的都是同一个会话：
模型服务会自己过去的故障（限流、过载、流中断等），退避后续上，连续次数有上限
（`agent/turn_resume.py`）；平台发版替换 runner 时排空超时被打断的那一轮（`runner_replaced`），
立刻续上，不算次数。什么会结束一轮、之后房间看到什么，见 `agent-liveness.md`。

**否掉的做法**：断了就开一个全新的空会话，然后发一句"接着完成原任务"。新会话什么都没见过，
这等于对一个刚推门进来的人说"接着干"。

## 十五、只 care device，本地容器是过渡形态

围绕"后端能直接看到工作区"建立的便利不能作为设计依据。见 #282。

## 十六、平台的水管不许弄脏机器：不是 docker，也要有 docker 的行为

平台落到一台机器上的一切——代理设置、CA、令牌、脚本、文件——必须**关在
screen 的进程树和它自己的目录里**，像 docker 把容器关在自己的命名空间里那样。
HTTPS_PROXY 是进程级 env（只活在那个 tmux 会话里），CA 是 per-topic 目录下的
文件，凭证随会话生灭。机器是用户的；平台只是借一块进程空间，走的时候不留痕。

**否掉的做法**：写 `/etc/hosts`、装系统 CA、改全局 shell profile、注入机器级
环境变量——哪怕它"只是一行"、哪怕更省事。2026-08-13 给 device 接订阅时，
`/etc/hosts` 按名重定向本是最直接的方案，正是被这条否掉的（进程级
HTTPS_PROXY 替代）。

**与 Hosted Machine 不矛盾**：`visibility=host` 让 agent **看得见并操作**整台
机器，那是用户显式授权的能力；平台自己的管线**污染**整台机器则永远不行。
一个是给 agent 的权力，一个是平台的自律，两码事。

## 十七、没有"轮"，只有排队的消息

给 agent 的话进队列，会话读到哪条算哪条；"轮"不是平台的单位。平台的任何决定都不以
"这条指令开启的那一轮结束了"为条件，只取平台核得了的事实：一条输入被读到、会话自己声明的
idle / running（`session_states`）、会话退出、某个工具被调用、卡递上来、被采纳或退回、合并发生了。

**为什么**：一轮结束只说明 agent 停下了，不说明它照指令做了。拿轮的结束当"做完了"，平台记下的
是一件它没核实过的事。Zhifei 反复这样裁定，2026-10-17 起有记录。

**否掉的做法**：#4045 给几件事各配了"自己的一轮"——写总结的那一轮结束就关任务、例行任务的一次
运行按它那一轮记开始和失败、任务的开场那一轮跑起来就算开始了；还有按轮判断的沉默提醒和清单
提醒、卡住判定、看板上房间的「运行中」。#4459、#4526、#4535 把它们换成了上面的事实：关任务等
队友调 `cheese_task(action=close)`，开始看输入被读到，提醒、卡住判定和「运行中」看会话声明的状态。

## 十八、状态来自能核实的事实，agent 的自述只是说明

板和列表上显示什么、该谁动手，先看核得了的事实；agent 自己报的状态只在没有事实说话的地方
填空，事实一出现它就让位，盖不过事实：

- 有一张等审的卡，任务就是「等审」，点到的是验收人，不管 agent 上一次说了什么；
- 没有开着的卡、没有待回答的问题时，这件任务自己那位 agent 的会话在跑就是在做（runner 报的
  `worker_status`），除非它在这一次跑里报了别的：它在上一次跑里报「在等」、这次被叫醒，是在做；它在这一次
  跑里报的「卡住」，照它说的。看的是「哪一次跑」，不是两个时刻谁先谁后；别的 agent 在这件任务里跑，不算；
- 会话停下以后，板上显示它最后报的在做、在等、卡住（卡住点到负责人）；可它报的「在做」点不亮侧栏的灯，
  灯看的是会话真在跑、或卡在交付链上（#4582），会话退出，「在做」旁边标「已离开」；
- agent 只能报在做、在等、卡住（`cheese_task(action=state)`），卡开着的时候报了被拒
  （`taskProgressWhileInReview`）。

**为什么**：自述说的是 agent 以为自己在哪，事实说的是它实际在哪。#4413 引过一项测试：agent
审文件，67.9% 的运行没有读完，其中八成的最终回复对此有误导。照自述显示，人会被一句"在做"
打发走，不去看一件其实没人在推的事。

**否掉的做法**：从 transcript 推活性——侧栏的红灯和"N 分钟没有新输出"，#4459 删了；agent 报的
进度能盖过一张等审的卡，#4459 审查时发现，合并前改掉。自述填空的地方越少越好，同一个方向上还有一步没走：总览的现状卡
仍然照搬 agent 的总结，#4413 提出改为从执行记录生成，关键断言可以点开核对。

## 十九、用户看得到的，agent 也要知道

agent 的任务上，凡是用户看得到的变化，都要让 agent 知道。变化是 agent 自己引起的，工具结果
里说；是别人引起、需要它动手的，发一条能唤醒它的指令；只是知会的，附在它的下一次输入上。

**为什么**：Zhifei，2026-10-21：「改任务状态的 都得跟agent说下…用户能看到的 agent也最好能看到
否则用户说一个事情 agent 根本没意识到更新」。人和 agent 对着同一个任务说话，一方看到的状态
另一方没看到，人接着说下去，agent 对不上。

**否掉的做法**：递卡时平台清掉 agent 报的状态（`room_task.progress.clear`），而递卡的工具结果
不提；作废一张卡、把任务放回「在做」（`back_to_work`），不告诉 agent。这两处要按上面的三条路改。

## 附：这份文档是怎么来的

2026-08-12 的一次长对话。当时的工程侧判断（agent 是分身、人签字是产品根基、权限要收紧、
平台该自己跑检查、限制该广播、规则内联进 prompt）被逐条纠正，上面每一条的"否掉的做法"
都是当时真实提过的方案。十七到十九是 2026-10 定的，出处写在各条里。

同一天还查到一件事，是这些原则为什么必须写下来的直接证据：平台组装的 system prompt
在生产路径上**从未送达过模型**（`HooksTurnProvider.run_turn` 收下 `system_prompt` 形参后
从不使用，两个子类都受影响），所以那 1600 多轮里，芝士既不知道自己是谁，也不知道
自己在什么产品里。写下来的东西没送出去，和没写过是一样的——**这份文档要被真正送达，
才算数**。
