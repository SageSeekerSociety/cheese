## 1. 产品是什么

知是的核心是三个词：**AI**、**全过程**、**一同成长**。

**AI 和全过程互相成就：**

- **没有 AI，全过程是空话。** 1.x 版本的教训很清楚：你让学生自己填进度、写周报、往平台上搬东西，他们不会做。"全过程管理"在没有 AI 的时候只是一句口号。AI 改变了这个前提——当 AI 作为队友参与到项目的每一步里，工作本身就在平台上发生了，过程自然留下来了，不需要任何人额外填表。
- **没有全过程，AI 只是工具。** 今天大部分 AI 产品的问题是：你每次用 AI 都要从头交代背景，它不了解你的项目、不知道之前的决策、不清楚队友在做什么。这样的 AI 只是一个高级搜索框，不是队友。AI 要真的变成队友——比你更了解项目全貌、能替你回答"现在什么状态"、能主动提醒你该做什么——它就必须全程参与，而不是被临时叫来用一下。

**一同成长是这一切的意义：**

- **AI 在成长。** 记忆越来越丰富，对项目和每个人的理解越来越深。用得越久，它越像一个真正了解情况的队友。
- **人和 AI 一起成长。** 在真实项目中学会监督 AI、判断质量、纠正方向——这是 AI 时代最重要的个人能力，只能在实践中练出来。
- **人和人一起成长。** AI 接管了大部分个人执行之后，真正的差异化来自"能不能和别人一起把事做成"——分工、协调、建立共识、解决冲突。2025 年达沃斯年会的官方主题就叫"Collaboration for the Intelligent Age"；WEF Future of Jobs 2025 把协作列为仅次于分析思维的第二核心技能。这些能力只有在真实的团队协作中才能练出来。

知是天然就是这三种成长同时发生的地方——不是一个人和 AI 单独对话，而是一个团队和 AI 一起推进项目。对一个教育平台来说，这是最重要的价值：不是"帮学生省事"，是"让学生在 AI 时代真正具备做事的能力"。

"全过程"有三层意思，AI 既是每一层的手段，也是每一层的受益者：

1. **项目的全生命周期**——从选题、组队、讨论、动手、沉淀到结题汇报，整个过程都在知是上发生，结题后自动变成简历。不是只管其中一段（GitHub 只管代码，飞书只管沟通，Notion 只管文档），而是整个过程。AI 是贯穿这个过程的队友，让每一段都能在平台上发生。
2. **过程自动留痕**——不是事后让学生填表写周报，而是 AI 一边干活一边自动记录。讨论、决策、成果全是副产品，老师看到的进度报告是 AI 从真实工作中提取的，不是学生编的。
3. **连续的记忆和理解**——不是每次开一个新对话从头来，而是 AI 对整个项目有持续的记忆。你一周没管这个项目，回来问"现在什么状态"，AI 直接告诉你，不用翻聊天记录。

一句话描述产品：知是 = 飞书群聊 + 飞书文档 + Cursor 工作台，装进一个 GitHub PR 的壳里，外面套 Linear 的导航 + 管理看板 + LinkedIn 主页，加一个 Notion 风格的会议入口。全程有一个 Claude Code 队友（芝士）贯穿始终。全是你见过的东西，缝在一起，加一个真能干活的 AI。

产品的组成部分，每个都对标一个你已经用过的产品，加上 AI 带来的变化：

**容器：话题**
| 组成部分 | 对标产品 | AI 带来什么变化 |
|---|---|---|
| 话题（§6） | GitHub PR | 不只装代码，能装任何工作；AI 干活、人指挥；验收的是成果 |

**话题里面有三样东西**
| 组成部分 | 对标产品 | AI 带来什么变化 |
|---|---|---|
| 对话（§7） | 飞书群聊 | 群里多了一个真能干活的队友，没人叫它的时候不吵 |
| 文档（§7） | 飞书文档 | AI 自动维护项目状态，随时是最新的；改文档就等于给 AI 下指令 |
| 工作台（§7.1） | Replit / Cursor | 零基础也能用——预览直接展示 AI 做出来的东西（网页、运行结果、数据），不用懂代码；想看技术细节随时能看 |

**话题之外的对话**
| 组成部分 | 对标产品 | AI 带来什么变化 |
|---|---|---|
| 私聊 | 飞书私聊 | 成员和某一个 AI 队友的一对一对话（一个队友一间，也可以和人私聊）。用来设偏好（"设计的先给我看"）、问项目状态、调个人设置。不是讨论具体工作的地方——聊到具体事情时芝士会建议开话题，避免重要信息沉在私聊里 |

**三个全局页面（分属不同层级）**
| 组成部分 | 层级 | 对标产品 | AI 带来什么变化 |
|---|---|---|---|
| 导航和总览（§7.2） | 项目 | Linear（看板+列表） | AI 自动维护，只推送"等你处理的事" |
| 机构看板（§7.3） | Space | 管理仪表盘 | 一个 Space 下几十个小团队/小项目，AI 自动汇总所有团队状态，老师不用催不用问一眼看清 |
| 个人主页（§7.2） | 用户 | LinkedIn / GitHub profile | 入驻时填兴趣/技能/方向，之后芝士在协作中不断加深对每个人的了解；项目过程自动变成简历 |

**基础设施**
| 组成部分 | 对标产品 | AI 带来什么变化 |
|---|---|---|
| 开发环境和算力（§9.1） | Replit / GitHub Codespaces | 每个话题自动分配开发环境，用完回收；机构可以接入自有算力，用量在项目和 Space 层面都能看到 |

**一个入口**
| 组成部分 | 对标产品 | AI 带来什么变化 |
|---|---|---|
| 会议/活动（§6.2） | Notion AI Notes / Granola | 自己做，不依赖外部会议软件；线下活动自动消化成话题 |

**一根线把这些缝起来**：芝士 = Claude Code（§8）——在每个部分里都在：群里聊天、维护文档、在工作台干活、在看板上催进度、把会议变成话题。它就是把这些东西缝成一个产品的线。

## 2. 全过程的积累怎么管理

§1 说了 AI 全程参与项目。但"全程参与"不是把 AI 扔进去就行——一个项目跑几周几个月，中间几十上百次 AI 会话，多个人参与，产出大量的对话、决策、成果。Satya Nadella 自己同时跑 100 个 coding agent，他的感受是："The cognitive load on me managing this is so high."——agent 的能力不是瓶颈，人管理这些 agent 的注意力才是。他的结论是 agent 需要像员工一样管理："You need to give them identities, you need to give them sandboxes, then you need to set policies to govern them."

所以全过程要解决的不只是"让 AI 参与"，而是两个更根本的问题：

1. 这些会话怎么编排成一个连贯的过程——并行、分工、协调——而不是一堆孤立的对话？
2. 过程中积累的知识怎么沉淀下来，让 AI 越来越懂、让人不被淹没？

现有工具都只做了一部分：Claude Code 有 recap 但只是单次会话的总结，下次打开还是要从头交代；飞书文档能沉淀但和工作过程割裂——你在 AI 工具里工作，写完了再手动把结果搬到文档里，文档和工作发生在两个地方。根源是一样的：会话是割裂的，积累没有被系统管理。

知是要同时解决这两件事：

### 2.1 工作流的编排（Sessions）

核心模型很简单：**一个 session 就是一件事，对应一个话题（topic）**。

一件事可以拆成几件小事——每件小事是一个 sub-session，对应房间里的一条支线。做完，结论自动回到房间。这样一个项目就是：根话题是项目本身，下面是各个工作方向（房间），每个房间里并行着若干件具体的活。

每个 session 是持续的、可以恢复的，不是每次从零开始。多个话题可以并行推进。AI 知道整棵树的状态，能在话题之间协调——发现冲突、分配工作、催进度。人可以随时离开再回来，不用重新交代背景。

这个模型本身就是编排：一件事拆成多件事、并行推进、结论汇总，就是项目管理的本质。

### 2.2 知识的沉淀（Docs + Memory）

每次会话都会产出对话、决策、成果。这些积累需要被沉淀下来——核心载体是文档。

聊天和文档的本质区别：聊天是事件流——每条消息是一个瞬间的更新或决策请求，看完就过去了；文档是持续状态——永远反映"现在是什么情况"，随时打开就能看懂。

这个区别对人和 AI 都很关键：

**对人：文档让你瞬间恢复上下文。** 今天用 Claude Code / Cursor 的人，很多已经是这样工作的：给一个任务，然后去干别的事，回来看结果。你可能离开了一天、一周，甚至是一个新加入项目的成员。翻几百条聊天记录才能搞清楚"现在什么状态"；打开一份 AI 持续维护的文档，30 秒就知道了。聊天记录是给在场的人看的，文档是给任何时候来的人看的。人通过文档给 AI 下指令（改文档=改指令），AI 通过文档向人汇报（持续维护的状态摘要，永远反映最新情况）——这就是 Docs-in / Docs-out。

**对 AI：文档就是它的记忆基础。** AI 的项目记忆不是凭空产生的——它建立在这些实况文档上。文档记录了做过什么决定、为什么、现在到哪了。AI 恢复一个 session 的时候，读的就是这些文档，而不是把几个月的聊天记录重新过一遍。文档既是给人看的界面，也是给 AI 用的记忆——两者是同一份东西。

对话不会消失——工作还是在对话里发生的，需要你做决定、审批、处理异常的事件也从对话里推送给你。但对话是过程，文档是状态。你理解项目全貌、做判断的依据，是文档不是聊天。

在单个房间的文档之上还有一层注意力管理：一件活→房间→项目→Space，每一层向上只传摘要。学生看话题细节，组长看项目总览，老师看 Space 看板——各自看各自该看的，不被其他层的信息淹没。

这个设计会越来越对：AI 越强，中间需要人介入的次数越少，人越不需要盯过程，文档的价值越高。以聊天为核心的产品会越来越痛苦：消息刷屏、重要信息被淹没、新人加入完全看不懂在说什么。

## 3. 设计原则

§1-2 讲了"做什么"和"为什么"。这一节讲落地时遵守的几条规则。

**AI 干得越多，你看的越少。** AI 可以产出无限多的内容，但人的注意力是整个系统里最稀缺的资源（§2 已经展开过）。这条原则贯穿所有设计决策：对话正常显示，但 AI 的施工过程（中间推理、调试、执行细节）默认不显示，想看随时能看；AI 发消息按打扰程度分级——默默记下来 / 在对话里轻提一句 / 强提醒@人；只有需要人做决定的事才推到"待处理"里；人的验收（Accept）是注意力最集中的动作。和大部分 AI 产品相反——它们是 AI 干得越多你要看的越多。

**万物皆块。** 平台上的所有内容——一条消息、一段文档、一个决策、一个附件——都是同一种东西，叫"块"。块可以同时出现在对话里和文档里。这是 §2.2 里"对话是过程、文档是状态、两者是同一份内容的不同视图"在数据层的实现（详见 §5）。

**一件事就是一个地点，地点可以长大。** 这是 §2.1 里 session 模型在产品层的体现。一段讨论如果变复杂了，可以升级成一件独立的活；房间里可以并行很多件活；活做完了，结论必须回到房间里（详见 §6）。

**不造 agent 框架，不绑定模型。** 不发明自己的 AI 概念——直接用现有的 coding agent 框架（当前是 Claude Code）。框架和模型是两件事：我们用 Claude Code 作为 agent 框架，但底层模型不绑定——可以跑 Claude、GPT、Gemini 或开源模型，按场景和成本选。芝士的"灵魂"是 skills 和记忆（我们写的），和用哪个模型无关。三条底层规则——发生的事只追加不修改；状态文档可以编辑，编辑就等于给 AI 下指令；成果必须经过人的验收才算数（详见 §9）。

**"一同成长"怎么落地（§1 第三个核心词）。** 避免"能力培养幻觉"——学生觉得什么也没学到只是在点 Accept。实际上在知是上做项目练的是一整套 AI 时代的核心能力：审核产出质量的判断力、推进项目落地的执行力、协调团队分工的领导力、和 AI 及队友有效沟通的协作力。AI 让写代码、做 PPT 这些个人执行技能迅速贬值，但"把一件事从想法变成结果"的能力——定方向、拆任务、盯质量、带团队——反而更稀缺。2025 年达沃斯主题"Collaboration for the Intelligent Age"说的就是这件事。知是给了学生一个在真实项目中练这些能力的场所，而不是在课堂上听理论。

落地需要两件事。一是让成长可见：贡献图区分人和 AI、review 过程有记录、portfolio 上"指挥 AI 做成了什么"是可信的能力信号。二是 AI 必须说人话：用人能看懂的语言汇报做了什么、为什么、改了哪里。如果 AI 的输出过于专业复杂（ChatGPT 5.3、Claude 4.7 都有这个问题），人没法有效 review，"监工"就变成盲签。芝士的对话和文档必须让零基础的学生也能看懂，这是 skill 要解决的核心问题之一。

**自己做核心，借用非核心。** 会议、协作、沟通、文档、进度管理——这些是核心，知是自己做，不接飞书/腾讯/Notion 的 API 当附属品（接了就把命脉交给对手）。只有代码托管（GitHub）、论文编辑（Overleaf）这种自己造不划算、也不构成核心优势的东西才借用别人的，而且随时可以替换。会议记录属于核心，所以自己做（见 §6.2），不外包。

**理想体验：** 新成员加入一个已经跑了 6 周的项目，问"现在什么状态、我能干什么"，AI 答得比组长还快还准，还能根据这个人的能力和兴趣分配合适的任务；组长想问"周报发了吗"，发现 AI 已经发了。AI 不只是队友——它可以承担组长的角色：了解每个人的状态、分配工作、催进度、汇报给老师。人手不够的时候，AI 顶上；人够的时候，AI 退到辅助。

## 4. 产品架构：Space、Task Template、Task、Project

### 4.1 四个实体和它们的关系

```
Space（机构：书院 / 信院 / eTrip）
  └── Task Template（项目集/活动："创研课 2026 秋"、"黑客松第三期"、"书院创新项目入驻"）
        ├── 资源包 + 条件（协议）
        ├── 在 Space 页面里显示为一个独立的栏/板块
        └── Task（具体题目："用 AI 做推荐系统"、"校园数据分析"…）
              └── Project（团队领取后生成，或已有项目链接过来）
```

- **Space** = 机构（书院/信院/eTrip）。做一件事：发布 Task Templates。不直接管理 Projects，不设治理策略。
- **Task Template** = 一个项目集或活动（"创研课 2026 秋"、"黑客松第三期"）。在 Space 页面里显示为一个独立的栏，里面是一系列具体题目。Template 定义资源包和条件——这是一份协议（见 §4.2）。现有代码里的 SpaceCategory 就是这个东西的雏形。
- **Task** = 具体的题目/征集，属于一个 Task Template。团队领取一个 Task 后生成 Project。
- **Project** = 完全独立的实体，就是一个项目（= 根话题 = git repo）。自己管自己的 AI 模式、审批规则、所有策略。可以链接一个或多个 Tasks——拿对应 Template 的资源包，同时接受条件。不链接任何 Task 的项目完全自治。

### 4.2 Task Template 是一份协议

团队链接 Task 就等于接受了 Task Template 的协议——机构提供资源，项目承诺义务：

| 机构提供 | 项目承诺 |
|---|---|
| 算力额度、AI credits、环境模板 | 出现在 Space 看板上（老师能看到） |
| 导师指导、评审机会 | 完成 Template 规定的必做话题/里程碑（比如"中期汇报"话题需在某日前完成、"结题答辩"话题需导师作为 reviewer） |
| 机构背书、portfolio 认证 | 接受可见性要求和其他条件 |

不接受就不链接——完全自由但也没有资源和机构支持。接受了就是签了协议，双方都有义务。

### 4.3 几个场景怎么走

- **创研课**：信院创建"创研课 2026 秋"Task Template（含资源包 + "导师必须审批结题"条件）→ 老师在里面发布多个具体题目（Tasks）→ 学生领取一个 Task → 生成 Project 并链接 → 项目出现在信院看板
- **书院入驻**：书院创建"创新项目入驻"Task Template → 里面可以只有一个通用 Task（"入驻申请"）→ 团队把已有 Project 链接上去 → 等于签了入驻协议
- **黑客松**：主办方创建"黑客松第三期"Task Template，条件很宽松（AI 全自主、无审批要求），资源包可能更大（限时给更多算力）→ 具体题目是各个赛道
- **个人项目**：不链接任何 Task → 完全自治、没有机构资源、不出现在任何看板上
- **退出**：断开 Task 链接 → 资源没了、看板上消失、但项目本身（git repo 和所有工作历史）还是你的

### 4.4 权限与策略

Project 自己管自己的策略。因为所有话题底层是 git 分支，权限直接映射到 git 概念：

| 设置 | 说明 |
|---|---|
| AI 模式 | 自主（AI 全权负责——开话题、干活、merge，人想看就看不看也行）/ 协作（AI 干活，人验收）。项目组长自己定，和机构无关 |
| 验收规则 | 话题创建者是默认 reviewer（你发起的事，做完了你来验收）。除此之外，芝士根据对内容和每个人的了解推荐还需要谁看（类似 GitHub 的 suggested reviewers）。任何成员都可以改推荐、加人——唯一不能动的是 Task Template 的硬性要求（比如"结题必须导师验收"）。AI 从每次修改中学习偏好，越用越准 |
| 主分支保护 | 合并到项目主线需要几个人批准 |

如果项目链接了 Task，Task Template 的条件会叠加——比如要求项目创建"结题答辩"话题且导师必须是 reviewer。这些条件本质上是一组预设的必做话题和审批要求。项目自己设的策略不能违反这些条件，但在条件之外完全自由。

**协作模式下的硬规则：AI 不能验收自己做的东西，必须有人来。** 在教育场景这条尤其重要——学生作为验收人，"判断 AI 做得对不对"本身就是在培养的能力。自主模式下没有这个限制——AI 全权负责，人随时可以回来审计但不阻塞流程。

审计是免费的——git history + 块的记录天然就是审计链。谁做了什么、AI 自主做的还是人指挥的、谁验收的，全有记录。

## 5. 数据模型

对话和协作的体验就是 Slack / 飞书那套——群聊、thread、@、回复、表情——大家已经会用了，不用学新东西。我们不在这一层创新，创新在两个地方：一是对话和文档共享同一份数据（下面讲的"块"），二是讨论可以升级成独立话题（§6）。

底层数据结构：

```
块 = { 内容, 作者, 时间,
       reply_to,        ← 对话树：谁回复谁
       struct_parent,   ← 文档树：在文档结构里的位置
       refs[] }         ← 引用：依据哪个决策、哪个 PR、哪段施工记录
```

- 项目里的所有内容是一池块。这些块用两棵树组织：对话树（reply_to）记录"怎么聊出来的"，文档树（struct_parent）记录"整理成什么结构"。一个块可以同时出现在两棵树里——比如对话里的一句话，同时被钉进了文档的"约束"章节。
- 这两棵树加上时间和引用，驱动四种查看方式：按时间看是消息流；按文档树看是结构化的文档；按对话树看是 Slack 式的 thread；按引用点击就能跳到来源（哪个决策、哪个 PR、哪段施工记录）。
- AI 回复自动带上"回复谁"的关系（它是被哪条消息触发的就回复谁）。人发的消息默认不带回复关系（像群聊一样随便说），想回复特定消息时手动选。结构不是一开始就强制的——先随便聊，需要整理的时候再整理。
- 回复的显示学 Slack 的 thread：主流里只看到顶层消息 + "N 条回复"，点进去打开 thread 侧栏看完整讨论。主流保持干净，细节按需展开。thread 讨论太长太复杂了，可以升级成独立话题（见 §6）。
- @ 和回复是两回事：@ 是叫人过来看（通知），回复是说明这条消息针对哪条。发消息时默认不带 @（群聊本来就是大家都能看到的）；叫 AI 就是在正文里 @ 它，和 @ 一个人写法一样，区别只在于 @ 人是通知、@ 它是真开一轮。
- 整个系统只有两种东西：块，和话题（块升级后的形态）。升级是全有或全无——升级了就同时获得独立的侧栏入口、文档树、AI 会话；不升级就还是普通的块。

## 6. 话题

```
项目 = 根话题（项目总览、AI 定期巡检的大本营）
└── 房间（二级，话题树到这里为止）
    └── 一件活（房间里的一条支线：有自己的对话、工作区和交付，但不是话题树上的节点）
```

一件活**不嵌套**：从一件活里再拆，得到的是同一个房间里的另一件活。房间也只有一层——
房间之下是活，不是另一个房间。

### 6.1 怎么产生和组织话题

- 话题可以从两个方向产生：从下往上——一段讨论越聊越长，升级成独立话题；从上往下——一个大话题的文档里列了几个待办，每个待办拆成独立话题去做。判断标准只有一个：这件事是不是复杂到值得有自己的状态和讨论。
- 块升级后不会搬走，原来的位置变成一个链接，实时显示它变成的那个地点的状态。房间里的一段讨论升级出来的是**一件活**；私聊里的升级出来的是一个房间（私聊不在话题树里，支线在那儿没人打得开）。做完了，结论和成果的链接写回到原来的位置。
- 一件活里工作的是芝士的**分身**（§8.4）——异步运行，房间不用等。多个分身可以并行推进不同的事情。分身做完了，结论自动回流到房间并写进房间的文档。房间只看到结论，想看分身的完整过程随时能展开那条支线。纯粹机械性的内部操作（比如搜索）留在当前会话里做，不派成一件活。
- 项目、房间、一件活都有三样东西：文档（状态摘要）、对话（过程）、成果（经过验收的）。向上只传文档摘要，向下永远可以看到完整对话。房间的文档是共识，一件活的文档是这件活的简报和状态——两级都在，分得清。
- 话题的文档是结构化和半结构化的结合。底部有几个平台自动维护的结构化区域，有语义含义：
  - **引用（Refs）**：这个话题提到的所有文档、文件、外部链接，自动收集。往话题里贴文件（文档、数据、图片、PDF）也会进入这里——AI 自动解析内容，关键信息引用进文档正文，文件本身作为项目的持久资料留在 Refs 里
  - **活**：这个房间里所有的活及其当前状态，自动同步
  
  其余部分由 AI 根据 skill 的指引自由组织——目标、约束、决策记录、进展、待办，AI 根据话题的类型和进展自己判断怎么写、写多少。平台不规定死结构，但 skill 会给 AI 提示（比如"简报应该包含目标和约束"）。
- 话题最好的类比是 GitHub PR。底层实现上也确实就是 PR——所有话题背后都是 git repo，不管产出是代码、调研报告还是设计稿，在实现层面都是文件，采纳就是 merge。比普通 PR 多两样：AI 干活人指挥（不是人自己写）；可以嵌套成树（PR 是扁平的）。

### 6.2 话题的来源

话题可以从多种方式产生：

- **讨论升级**：一段对话越聊越复杂，升级成独立话题。
- **从上往下拆分**：房间的文档里列了几个待办，每个派成一件活去做。
- **线下导入**：①"记一笔"——说一句"今天做了用户访谈，15 人，发现 XX"；②导入聊天记录——粘贴或截图；③录会议——在知是里录音，自动转文字，芝士出摘要、抽待办、标里程碑。

不管从哪来的，进来之后都是一模一样的话题：能接着聊、有文档、能挂附件、能升级、能验收、进时间线。这让知是不只接得住线上的工作，也接得住线下的——书院、商科、设计这些线下为主的团队也能用。

### 6.3 话题的生命周期

- 一件事 = 一件活。它背后自动关联一些技术资源（AI 会话、代码分支、开发环境），用户不用管这些，它们自动跟着这件活走。一个项目对应一个代码仓库。一件活的分支从它所在房间的分支切出来，做完合回去，最终合到主分支。
- 项目也可以**关联一个已有的 git 仓库**（上游）：把外部 repo 的历史拉进项目，之后随时"同步上游"合入新提交。这让"接手一个已有项目/代码库"成为一等公民——不是导入一次性快照，而是保持一条可持续同步的通道。冲突时同步原样中止（不合一半），交由芝士/人在话题里解决。
- **Project delivery:** topic acceptance merges reviewed work into the project's accepted branch. The project-level delivery page publishes a private static Site from a specific accepted revision. Each project owns one Site; its URL stays fixed, and accepted changes reach the live Site only after an explicit publish. Files are copied into persistent release storage, so the Site does not depend on the development machine. Topic previews link to project delivery without publishing their working branches. Automatic builds, backend application hosting, public sharing, PDF export and GitHub mirroring are outside this initial release.
- 话题的核心生命周期事件是"采纳"（Accept）：话题的主要成果被验收通过 = 这件事完成。因为所有产出底层都是 git repo 里的文件，采纳在实现上就是**当场 merge**（#718：点一下就是合并，合的是人看到的那个 commit；"只在绿的时候合"由项目的分支保护规则执行）——不管产出是代码、报告还是设计稿。采纳**不归档**（#442 决定 1）：话题保持活跃，归档是人单独做的动作；归档后工作面冻结，但对话永远可以追加评论（和 GitHub 里 merge 后的 PR 一样）。一件活 = 一件事 = 一次交付；想分批做 = 在同一个房间里再派一件活。没做完的房间也可以归档（打个"草稿"标签）。
- 谁来验收：在项目设定的权限策略范围内（见 §4.4），芝士根据判断把验收卡递给一个具体的人（谁最懂这块/谁没参与过/谁有空），卡上写"等 XX 验收"。组长可以通过私聊告诉芝士偏好（见 §1 私聊）。验收记名、可撤回。
- 冲突处理：芝士先尝试解决（它能看到两边话题的完整上下文）；解决不了就把两边放在一起，@ 相关人来拍板，结论写回文档。总览的定期巡检也会预警"两个话题改了同一个文件"。
- 讨论串里谁先发谁先说，AI 不自动开场；但从讨论升级出来的新话题，第一条必须是芝士的开场白——复述任务、确认理解（和 Claude Code 的 plan 确认一样）。
- 周报、文献追踪这种长期重复的工作也是话题，AI 定期在里面产出内容。

## 7. 界面

### 7.1 话题页面：常驻两列 + 按需打开的工具

之前把八种视图平级排列是错的——把不同类型的东西塞进同一排 tab，所以看着乱。正确的做法是分两层：

- 常驻的两列——对话（按时间排）和文档（按结构排）。这两个是话题的主体，永远显示，不和别的东西竞争。
- 按需打开的工具——预览 / Git diff / 施工现场 / 终端 / 文件浏览 / 资源用量。这些是看底层细节的窗口，从右侧滑出来，用完关掉；想常驻可以"钉住"（比如黑客松钉住预览变成三列，工程团队钉住施工现场）。

```
┌ 左栏：话题树 ──────┬ 对话（常驻）──────┬ 文档（常驻，默认显示）───────┐ ╔工具面板╗
│ ▾ 项目名           │ 消息流            │ AI 维护的文档 + 结构化区域   │ ║按需打开║
│   ├ 话题 A         │                   │                    ▶🌿🔬⌨🗂│ ║预览/施 ║
│   │  └ 活 A1       │                   │ （右上角图标=打开工具）      │ ║工现场  ║
│   └ 项目文档:      │                   │                            │ ║可钉住  ║
│     章程/决策记录   │ ──────────────────┴──────────────────────────── │ ╚════════╝
│                    │ 输入栏（对话+文档区域底部）        [@芝士][发送] │
└────────────────────┴─────────────────────────────────────────────────┘
```

- 三种用户看到的是同一个产品，只是复杂度不同：文科生/零基础 = 就是"聊天 + 一页文档"（技术工具图标可以按场景隐藏，但点开执行卡还是能瞄一眼施工现场，能力没阉割）；创研课 = 多个文献入口；工程团队 = 工具全开，默认钉住施工现场。
- 输入栏在对话栏底部，发的就是这个话题的聊天消息——不做发送目标切换。"插入正在运行的 AI 会话"是平台自己判断的（消息落进正在跑的会话，人不用选），文档评论在文档那边写（§14.3）。默认不 @（人与人对话为主）；叫 AI 就是正文里 @ 它，输入栏的「交给芝士」按钮和 ⌘/Ctrl+Enter 只是替你把那个 @ 写进正文——召唤与否的唯一依据是正文，不是另一个自己存着状态的开关。房间里最后一句没 @ 它时，那条消息下面给一次「让它现在就看」：没 @ 的消息本来就会被下一轮捎上，这一下只是不必等到下一轮。
- 打开工具的入口有三个：点消息流里的卡片（执行卡→施工现场，验收卡→成果/diff）、点文档右上角的工具图标、点验收卡上的"看成果"。临时打开用完关掉，钉住才常驻。
- 各工具的内容：施工现场 = 这个地点 AI 会话的完整记录（只读，房间里能看到它每条支线的，根话题的施工现场就是 AI 的定期巡检日志）；预览 = 芝士**显式指定为当前预览**的那个 artifact 的实时展示（AI 用工具调用点名要展示哪个，平台不去猜哪个文件），可能是网页、运行结果、或数据可视化（可以分享链接，AI 和人看到同一个画面，点选批注对零基础用户特别好用）；Git = 提交历史和完整 diff，可以行级评论；文件 = 文件树浏览器；资源 = 容器和 token 用量，可以重建环境/调配置/看排队情况。任何一列都可以最大化。
- 项目级文档（章程、决策记录、周报集）独立打开成全宽页面，不挂在某个话题下面。章程 = 项目的根文档（建项目时通过访谈生成，改了就等于改指令）；决策记录可以编辑纠错，每条来源可以跳回原始话题。
- 文档评论：对整篇评论 = 发给文档维护者；划词评论 = 发给那段内容的作者和维护者，评论挂在对应的块下面，可以接着讨论或升级成话题。
- 文件上传：所有文件都进 git repo，和代码一样有版本、可 diff、话题采纳时一起 merge。拖到输入栏 = 放到话题对应的分支里，AI 自动解析建索引；拖到项目级"资源"区 = 放到项目根目录下（文献/需求/设计稿，所有话题都能引用）。文件就是文件，不区分"附件"和"代码"。
- 细节：每个话题的每列记住滚动位置；升级事件可以点进它变成的那个地点（那边也能点回房间）；AI 主动发的消息带 👍/👎 反馈按钮。

### 7.2 项目级的三个全局页面

项目管理无非是事、人、时间三个维度。话题树覆盖了"事"，另外两个各需要一个全局页面（都由芝士自动维护）：

- **总览（事）**：项目的根文档——里程碑、各话题的状态、"等你处理的事"（按人分组）、风险。
- **成员页（人）**：每个成员一页——在忙哪些话题、本周贡献了什么、等他处理的事。对外展示的版本就是个人简历页面（"项目过程即简历"的实际体现）；老师视角可以聚合看"全组所有人"。
- **日历（时间）**：项目的截止日期倒排——中期检查/结题/各种 deadline。AI 催人的判断从"凭感觉"变成"对着倒计时催"。

### 7.3 机构管理层：Space 看板

§7.2 的三个页面是一个项目内的。机构方（书院/学院/企业管理员）需要看所有团队的汇总——这是摘要再往上一层。"入驻团队"的定义来自 §4：所有链接了这个 Space 下某个 Task 的 Projects 就是入驻团队，不需要单独的"加入 Space"操作。

- Space 看板 = 所有入驻团队一张表：每个团队一行，列出状态/进度/活跃度/里程碑是否临近/最近的一页纸总结。管理员不用进每个项目，扫一眼就知道哪个团队活跃、哪个停滞、谁快结项、该催谁。数据来自各项目总览的汇总，芝士自动维护，永远是最新的。
- 随手记录里程碑和活动（明理书院最核心的需求）：靠 §6.2 的活动入口——记一笔 / 导入会议纪要 / 导入聊天记录，芝士自动把线下活动标成里程碑、排进日历、显示到看板上。"随手"不是口号，是真的只要说一句话就行，比手填进度表轻一个数量级。
- 每个团队一页纸总结：就是项目总览的对外版本，芝士持续维护（不是学生交的死文档，永远反映当前真实状态）。团队自己看、老师在看板上看，是同一页。

明理书院的四个需求怎么满足：

| 书院要的 | 给谁用的 | 2.0 怎么做 |
|---|---|---|
| ① 过程化管理 | 老师要看见过程 | 团队在话题里推进（含导入的线下活动）= 自动留痕，没人需要填表 |
| ② 时间点/里程碑，随手记录活动 | 学生要能低成本记录 | 活动入口（§6.2）：说一句话/导入纪要 → 芝士自动标里程碑、排日历 |
| ③ 每团队一页纸总结 | 老师 30 秒读懂一个团队 | 项目总览的对外版本，芝士持续维护，永远最新 |
| ④ 统计和洞察 | 老师要一眼看几十个团队 | Space 看板：所有团队汇总，谁活跃/谁停滞/谁快结项一目了然 |

整条链路：学生随手记（②）→ 攒成过程（①）→ 芝士汇成一页纸总结（③）→ 所有团队汇总成老师的看板（④）。源头只要够轻，整条链路就能自动跑通——而活动入口就是把源头做到了"说一句话就行"。这直接替代了 1.x 版本计划中的 ProgressUpdate 表（需要建表+手填，到现在也没启动；2.0 里这些全是自动产出的，零额外功能）。

## 8. AI 队友（芝士）= Claude Code + 知是 skills

### 8.1 我们做什么，不做什么

芝士不是从零写的 AI——是 Claude Code 加上知是专属的 skills 和工具。Claude Code 本来就会对话、会写文档、会调用工具。但"知是的文档该长什么样、什么时候该主动说话什么时候该闭嘴、线下活动导入后怎么消化"，这些是我们写的 skill，是产品的灵魂。所以我们实际造三样东西：

| 我们造什么 | 具体内容 | 性质 |
|---|---|---|
| 平台（壳） | 数据库、话题树、多会话调度、前端、机构汇总 | 把单人的 Claude Code 变成多人、持久、可视化的。正经工程代码 |
| Skills（灵魂） | 见 §8.2 | 教 Claude Code 变成"芝士"。产品的核心知识，用自然语言写，迭代快、谁都能改 |
| 工具（外接能力） | 记忆存储 / 开发环境 / 语音转文字 / GitHub / 机构汇总 | 给芝士接上外部能力 |

### 8.2 Project agents and starting configurations

Each project agent owns its name, role instructions, explicit model and memory. A room selects an agent; the project selects the default agent for new rooms. There is no project default model.

Built-in presets provide starting values when an agent is created. A preset can supply role instructions, a model and existing tool settings. Missing model values are filled from the available supply's creation default and saved on the new agent. Subsequent preset changes do not affect existing agents. There is no editable team or global role catalog.

Users edit an individual agent in AI 队友. Edits take effect from its next turn in every room using that agent. The current turn uses one configuration snapshot. Existing agent IDs, handles and memory remain unchanged, and other agents keep their own configuration. New rooms require an active agent, so the last active agent cannot be retired.

Model choices come from the project's connected supply. An unavailable saved model produces an error requiring a new selection. Device and Cloud execution pass the saved model explicitly. A reused process is refreshed between turns when the agent configuration changes. This guarantees the requested model; provider-side substitutions are outside this setting's guarantee.

Migration copies existing role instructions and the effective model onto each agent. Projects with an implicit default receive a saved agent under the same cheese handle, preserving their memory keys. Original custom roles and project settings remain in archive tables for inspection and rollback.

### 8.3 Skills：产品的配方

这是最该先写清楚、最该测试的部分：

| Skill | 教 AI 什么（Claude Code 默认不会的） | 测试场景 |
|---|---|---|
| 文档形态 | 知是的文档不是通用的 plan——是持续更新的状态摘要，AI 根据话题类型自由组织内容（目标、约束、决策、进展等），底部有平台维护的结构化区域（引用、活的状态）。Claude Code 会写文档，但写的是通用计划书，不是这个 | B1/B2/F1/F2 |
| 对话风格 | 什么时候该说话什么时候该闭嘴、怎么复述确认、少说废话、用卡片而不是大段文字 | C1/C3 |
| 活动消化 | 把线下输入（会议/聊天/随手记）整理成结构化的话题：打时间和类型、提取"做了什么/定了什么/谁负责/下一步"、标里程碑 | E1/E2/E3 |
| 定期巡检 | 对照各话题的文档和里程碑，判断该催谁/该拆什么/有什么风险，按打扰程度分级通知 | G1/G2 |
| 验收分配 | 判断把验收卡递给谁（谁最懂/谁没参与指挥/谁有空） | C5 |
| 升级判断 | 判断一段讨论是不是该升级成一件独立的活，一个房间里的事是不是该派出去做 | A1/A2/A5 |

测试场景里标 🤖 的那些，验的本质就是这些 skill 写得对不对。产品语言写清楚了，skill 就写出来了。

### 8.4 芝士的身份：本体与分身

**用户面的概念：**

每个项目有一个芝士（本体），负责协调全局。当芝士需要同时做多件事时，它会派出**分身**——每件活里工作的就是芝士的一个分身。

- **本体**：根话题里的芝士，了解项目全局，负责协调、分配、巡检
- **分身**：一件活里的芝士，专注做一件具体的事，做完结论回流到本体

用户看到的：本体和分身都叫"芝士"、同样的头像、同样的性格。区别通过 UI 体现——根话题标"本体"，一件活标"分身"，房间时间线上的位置让主次一目了然。

分身之间互不感知是正常的——就像你派了两个人分头办事，他们各忙各的，回来再汇报。用户不需要理解 session、context window 这些技术概念，只需要理解"芝士派了分身去做"。

**让这个感觉成立的工程：**

技术上每个话题是一个独立的 session，并行的话题互不感知。靠三件事弥合：

1. **每次回复前读最新的项目文档和记忆**——分身永远是"跟上了的"。即使这个 session 刚创建，它读完文档就知道全局。
2. **重要决策即时写入项目文档**——一个分身做了决定，几秒内写进文档，其他分身下一轮就看得到。
3. **不知道的时候自然地说**——"那边的细节我看一下"。永远不暴露 session 的概念。

并行分身的一致性靠本体（根话题的芝士）保证：定期巡检各话题文档，发现冲突或不一致时主动提醒。

UI 里没有任何"session"概念暴露——没有 session ID、没有"重新开始会话"、没有"同步状态"按钮。
- 记忆分三层，按需加载（不是每次都全部加载，控制 token 成本）：
  - **个人记忆**（每个用户一份，跨项目）：不只是偏好和背景——芝士在协作中持续建立对每个人的理解。包括：这个人擅长什么（从实际工作中观察到的，不只是自己填的）、做事风格（喜欢独立还是讨论、回复快不快、关注细节还是大方向）、成长轨迹（在 A 项目里学会了前端，在 B 项目里锻炼了领导力）。个人记忆跟着人走，不跟着项目走——一个学生在创研课学到的能力，换到黑客松项目芝士依然知道。这是"一同成长"在个人维度的体现：不只是一个项目的全过程，是这个人整个学习成长的全过程。这个理解用在所有需要判断"谁"的场景：分配任务、推荐 reviewer、判断该 @ 谁、给新成员介绍"找谁问什么"。入驻时用户填的兴趣/技能/方向是起点，之后靠 AI 从协作中观察和积累，越用越准。
  - **项目记忆**（每个项目一份）：章程/决策/进展/知识/话题摘要。就是 §2.2 说的实况文档——AI 的记忆和人看到的文档是同一份东西。
  - **agent 记忆**（每个 agent 实例一份，项目内）：这个芝士自己学到的东西——踩过的坑、这个项目的操作惯例。跟着 agent 走，不跟着话题走：它在五个房间干活，五个房间共用这一份。项目里有第二个 agent（比如一个专职评审）时，两份记忆各自独立，就像两个同事各记各的笔记。
  - **技能记忆**：领域知识、文档模板、场景包的配置。
- 记忆的存储用 OpenViking（文件范式的记忆系统，`viking://` 路径）。按 L0/L1/L2 分层加载控制 token 成本——不是每次都读全部记忆，而是按需加载。数据库里的块树是真正的数据源，OpenViking 里的记忆是为了方便 AI 快速读取的投影，可以随时从块树重建。每次会话结束后自动提取记忆——知识沉淀是记忆系统的副产品。

### 8.5 通知和变更提醒

Ground truth 永远在文档里。对话中的通知只是文档变更的实时提醒——告诉你"什么变了"或"需要你做什么"，点进去看的是文档和 diff。

两种典型通知：

- **变更提醒**：AI 干完活后发一条——一句话总结 + 改了哪些文件 + 需要注意的点 + 一个"看改动"入口。想看更多细节点进去看完整 diff 或施工现场。大部分时候看摘要就够了。这条通知上**没有采纳**：采纳是话题级的一次性动作（§6.3、§14.6 采纳 = 当场 merge，一次交付一次采纳），每轮一个 Accept 和那条规则直接冲突。要说"这不对，重做"，回一句话就是原语（§14.2 的参照系是同事，同事不会给你一排 approve/reject 按钮）。
- **决策请求**：AI 遇到需要人拍板的事，发一条带选项的通知——"方案 A 还是 B？"，人选一个，AI 继续。这是平台提供的工具，不依赖特定 AI 框架。

### 8.6 AI 什么时候主动说话

触发条件：代码提交 / 里程碑临近 / 讨论没人回 / 评审超时 / 新成员加入，加上每天一次定期巡检。按打扰程度分三级：

- 默默记下来，不打扰任何人
- 在对话里轻提一句，带个可操作的按钮
- 强提醒，@ 具体的人，严重时发站外通知

限流：每个话题每天最多 2 条轻提醒、每周最多 1 条强提醒（可以调节为活跃/适中/安静三挡）。限的是 AI 发消息打扰人的频率，不是 AI 接收信息的频率——所有消息 AI 都会收到并更新记忆和理解，只是不一定在对话里回复。没有被 @ 的消息先判断要不要接话（接话 / 只更新记忆不说话），确保 AI 始终了解最新情况。

## 9. 实现架构

芝士 = 一个 coding agent + 知是专属的 skills/tools + 一层我们写的多会话调度。

当前实现用 Python Agent SDK（`claude-agent-sdk`，Claude Code CLI 的 Python 封装）。底层模型不绑定——SDK 通过 `ANTHROPIC_BASE_URL` 环境变量支持 LiteLLM 等网关代理，可以把请求路由到 Claude、GPT、Gemini 或开源模型，代码不用改。按场景和成本选模型：旗舰任务用强模型，巡检和摘要用便宜模型。

下面的映射以 Claude Code 为例，换成其他框架只需适配这张表，skills 和平台代码不用动：

| 知是概念 | 当前实现（Claude Code） | 需要我们做吗 |
|---|---|---|
| 芝士本体 | Agent SDK 的 session | 现成（可替换） |
| 话题 | 可恢复的 session（有持久化存储，可 fork） | 现成 |
| 一件活 | subagent（独立上下文，可持久追踪） | 现成 |
| 对话 | session 的消息历史（只追加） | 现成 |
| 文档 | 工作区文件 + Edit 工具 | 现成 |
| 改文档即下指令 | 文件变更 → 注入 session（streaming input） | 现成 |
| 施工现场 | transcript 流 | 现成 |
| Skills（文档形态/对话风格/活动消化/巡检/验收/升级） | `.claude/skills/` 按需加载 | **我们写（灵魂）** |
| 人格底线/不变规则 | system prompt（SDK `system_prompt` = CLI `--system-prompt`，替换式，平台拼好每次会话注入） | 我们写 |
| 用户 repo 自带的 CLAUDE.md | `setting_sources` 开 `project` 源，Claude Code 原生自动加载（决策：方案 A） | 现成 |
| 权限检查（红线/配额/成果必须过检查才能发布） | hooks + canUseTool | 我们写 |
| 工具（记忆/开发环境/语音转文字/GitHub/汇总） | MCP servers | 我们接 |
| 整个芝士配置 | 打包成一个 plugin | 我们打包 |
| 多话题调度 | Agent SDK 多 session 编排 | **我们造（壳）** |


### 9.1 运行时细节

- 事件循环：事件（消息/文档变更/webhook/定期巡检/活的结果回传）→ 每个地点维护一个串行队列 → 恢复会话（注入发言者标签 + 记忆）→ AI 调用工具（回复/编辑块/记忆/派出一件活/GitHub/搜索）→ 会话结束时自动提取记忆。
- Project environment: project settings hold an initialization script, a workspace startup script, and ordinary variables visible to project members and the agent. Cloud and Hosted Machine use the same runner; Hosted Sandbox remains unavailable. Work rooms pin configuration at creation. Saving affects new rooms; applying to an idle room stops its agent, preserves its checkout, and prepares the environment on its next start. Initialization runs once per successful revision in that environment. Startup runs before every new agent process; attaching to a live process does not rerun scripts. Both run in Bash at the checkout root with the agent's HOME and execution identity. Overview uses the base environment without project scripts or variables so it can diagnose setup failures. A failed work room sends a recovery event to overview, whose scoped API can inspect logs, repair that room's configuration, and restart once while retaining pending messages. A second failure or unavailable repair requires assistance; project defaults and other rooms remain unchanged. Preparation status and logs appear in the room and settings. The implementation retains initialization receipts and package caches, without filesystem snapshots or secret storage.
- 算力调度（平台代码，不是 AI 决定的）：资源池 = 自有 PVE 节点 + 机构/实验室自带的节点；根据环境配置匹配节点，按项目额度限制并发，超额排队。三级可见性：话题里看这个话题的用量 → 项目总览里看整个项目的用量 → 机构看板里看所有项目的用量和节点状态。
- 中途介入：所有入口（@ 某人、改文档、在施工现场插话、给文档段落评论）= 往这个话题的 AI 会话里注入一条消息。现阶段在会话间歇注入，未来用 Agent SDK 的 streaming input 实时注入。
- 调度分两层：确定性的（消息路由/定时任务/生命周期管理）= 平台代码做，不让 AI 当消息总线；需要判断的（该催谁/该拆什么/有什么风险）= 根话题的芝士来判断。
- 平台感知 AI 行为的唯一方式是结构化的工具调用——AI 要创建话题、编辑文档、分配任务、发通知，都必须调用平台提供的工具（内置工具、Agent SDK 自定义工具、MCP server 都行）。平台通过工具的输入输出来记录、控制、审计。绝不靠 regex 解析 AI 的自然语言输出——太脆弱，模型换一个版本就可能全坏。
- 渲染由 AI 显式指定、平台按 type 渲染（不猜）：芝士要"给人看一个东西"——网页 / 图表 / SVG / 幻灯——通过结构化工具调用 `cheese artifact <文件> --as html|svg|slides` 建一个带 mimeType 的 artifact 块，指向工作区文件；平台按 type 选渲染器（html/svg→独立内容域名的 sandboxed iframe）。这和 Claude Artifacts（带 type 的保留标签）、MCP-UI（`ui://` resource + mimeType）是同一条机制：模型发结构化载荷、宿主按 type 渲染，绝不从话术里解析"它想展示什么"。artifact 是"渲染什么"的唯一原语，摆放位有两个——无锚点 = 设为项目当前预览（进预览窗口这个主 / 放大位，替代原先"抓工作区第一个 `*.html`"的隐式猜法）；带 `--anchor <节点>` = 挂在文档该节点旁的内联卡片。内联卡片可"在预览窗口打开"提升到主位；html 渲染器只写一份，两处共用。
- 运行环境预览（已实现）：artifact 的延伸——预览的不是文件而是**跑起来的应用**。分工恪守同一哲学：**怎么跑这个项目是 AI 的现场判断**（读 README / package.json / pyproject，起在那台机器的 `127.0.0.1` 上，然后 `cheese serve <端口> "说明"`）——平台不为任何项目预置启动命令，因此机制天然全项目通用。跑一轮活的机器没有一台是平台的，都在 NAT 后、零入站端口，所以传输是那台机器**再拨出一条 WebSocket**，浏览器的请求在这条连接上分流回去，经话题独立内容域名 `preview-<topic UUID hex>.<SITES_DOMAIN>` 的根路径代理，嵌入 iframe。它**不走连接器那条链路**：那条是一轮活的命脉，静态资源和热更新排在 prompt 前面会把一轮活拖死。**端口只从那台机器的磁盘上读**（`cheese serve` 写的），线上没有主机字段，所以平台没法让一台笔记本去连别的端口；能看的人跟现场同一道门槛，而现场本来就是可写的。机器没拨出通道、和通道在但端口上没服务应答，是分开报的两句话（白框的主要来源）。HTTP、资源与 HMR 保持应用原路径，无需项目适配。预览的授权和文件范围见下。
- 预览授权：平台 `POST /topics/{id}/preview-session` 签发 30 秒、仅该话题可用的授权，通过表单 POST 在内容域名换取 8 小时 HttpOnly、Secure、SameSite=None、Partitioned cookie。登录令牌不进入预览地址或应用；每次 HTTP 请求与 WebSocket 建连都检查当前话题权限，私聊访问者必须在房间名册中。已建立的 WebSocket 最长保留到授权到期。应用 Authorization 和非保留请求 Cookie 转发；响应 Set-Cookie 改为 host-only、Secure、SameSite=None、Partitioned，并保留 HttpOnly、Path 和有效期。平台预览 cookie 与 `X-Cheese-*` 不传给应用，上游不能覆盖预览 cookie。静态文件只开放指定产物所在目录，拒绝隐藏文件、遍历与越界符号链接；工作线程禁用。全屏保留同一个 iframe，新窗口经主站重新授权；浏览器自行管理不同显示上下文的存储分区，不承诺面板和新窗口共享登录状态。部署需要为 `SITES_DOMAIN` 配好通配 TLS 与内容网关。
- 预览 roadmap（对标调研 2026-07：Claude Artifacts / Cursor 2.0 内置浏览器 / Windsurf Previews）：
  1. **元素选取回传**（Windsurf 的核心回路）：在预览里点选一个元素，直接作为结构化上下文发给芝士（"改这个的颜色"）——把"用嘴描述 UI 位置"变成"用手指"。需在代理层注入选取脚本 + 消息回传。
  2. **console / 报错回传**（Cursor 的路子）：预览页的 JS 报错与 console 自动进入芝士上下文，修前端问题不再盲猜浏览器状态。搭在 1 的注入层上。
  3. **廉价新 artifact 类型**：Mermaid、Markdown——一个 mime 一个渲染器，additive。
  - 明确不抄：Claude 的浏览器内单文件 React 仿真（他们没有真环境才那么做；我们有 `cheese serve` 跑真 Vite）。我们的差异化优势保持：artifact 落在 git 里——有版本、可 diff、采纳即 merge，而非会话内的易逝产物。

## 10. 红线、成本与信任

### 10.1 教育红线

自主和协作两种 AI 模式（§4.4），按场景配置（黑客松用自主模式：能指挥 AI 干活就是比赛能力；创研课用协作模式：人必须验收）。AI 产出的内容一律标注来源，贡献图里人和 AI 分开统计，老师在看板上能看到各自的比例。成果必须经过人的验收（学生始终是最终验收人）。施工现场全程透明可审计。简历页上"会指挥 AI 把项目做成"变成一种可信的能力信号。

### 10.2 成本

自有服务器约等于电费，LLM 调用是唯一真实的成本。控制手段：模型分层（主力任务用旗舰模型，巡检和摘要用便宜模型）+ 记忆分层加载（不是每次都读全部记忆）+ 额度挂在项目上 + hooks 强制执行限制。定价等 dogfooding 实测一个月之后再定。

| Task Template | 老师发 Template + 具体题目 | 主办方发 Template + 各赛道 | "创新项目入驻"Template | 企业发需求 Template + 具体任务 |
| 协议条件 | 导师审批结题、中期汇报 | 宽松（限时、无审批） | 定期里程碑汇报 | 企业方 + 导师双审批 |
| AI 模式 | 协作（AI 干活人验收） | 自主（AI 全权） | 协作 | 协作 |
| agent 类型 | 学术研究 | 全栈工程 | 按团队需求自选 | 按企业需求定制 |
| 过程记录 | 实验记录 | 预览就是过程 | 随手记里程碑 + 定期周报 | 进度报告自动生成 |
| 老师/管理界面 | 项目总览 | 排行榜/展示页 | Space 看板（§7.3） | Space 看板 + 企业方 dashboard |
| 交付形式 | 结题报告 = 文档汇编 | 对外公开页 → 简历 | 一页纸总结（永远最新） | 交付物 + 验收报告 |

黑客松是最好的获客场景：冷启动问题在这里不存在（AI 第一分钟就开始产出）。书院场景是 2.0 的零成本适配：1.x 版本最头疼的问题（要建进度表让学生手填，到现在也没做）在 2.0 里全是自动产出的副产品。

## 12. 度量

核心指标：每个项目每周被验收通过的 AI 成果数。辅助指标：@芝士后的验收通过率、主动消息的有用率（👍/👎）、成果被引用次数、周报老师打开率、新成员提问 AI 的准确率。护栏指标：主动消息被忽略的比例、成果被打回的比例、额度耗尽后用户流失率。

## 13. MVP 分阶段

| 阶段 | 做什么 | 怎么算做完 |
|---|---|---|
| 0 基建 | agent 框架接入（CLI stream-json 或 Agent SDK）+ OpenViking 记忆 + 块表（双树结构）+ 话题 session 框架 | 一个话题里能和芝士对话，芝士带记忆回答问题 |
| 1 协作 | Slack 式对话（thread / @ / 回复）+ 文档双列视图 + 记忆沉淀 + 私聊 | 开发团队全部切到知是上协作（dogfooding） |
| 2 文档 | AI 自动维护实况文档（docs-out）+ 改文档即指令（docs-in）+ 逐层摘要 | 离开一周回来看文档 30 秒恢复上下文 |
| 3 房间与活 | 一件活（async sub-session）+ 升级 / 拆分 + 结论回流 + 采纳即 merge | 一个项目能并行推进多个房间，房间里的活做完自动汇总 |
| 4 执行 | 开发环境 + 施工现场 / 预览 / Git / 文件面板 | 芝士提交的 PR 被合并 |
| 5 机构 | Space + Task Template + 协议模型 + Space 看板 + agent 类型 | 首个创研课 / 黑客松 / 书院试点 |
| 6 完整形态 | 个人主页 / portfolio + 匹配市场 + 日历 + 决策通知 | 核心体验全部跑通 |

每阶段结束都做 dogfooding——开发团队自己在知是上用知是。

## 14. 行为规范（dogfooding 拍板汇编）

> 2026-07 首轮 dogfooding 中由 andyl 逐条拍板的产品行为规范。每条都是现场纠偏的结论，
> 约束力等同设计原则（§3）；后续实现与 review 以此为验收标准。

### 14.1 现场三原则

1. **实时**：人发的消息立即显示，绝不排在 AI turn 后面。别的都可以错，现场不能错。
2. **原样**：现场内容一字不改地渲染——换行、格式全部尊重，任何包裹/转写都是 bug。
3. **工作细节不进对话**：工具调用、文件读写等过程细节只进「现场」抽屉；对话流只留人话和成品。

### 14.2 协作软件，而非 AI 软件

- 聊天的参照系是飞书/Slack 里的**同事**，不是 AI 产品的流式气泡：
  - **不实时吐字**。芝士有话说时发一条**完整消息**，一轮可以连发多条（消息边界 = SDK 的
    AssistantMessage 结构化事件，绝不是解析文本）。
  - **收到请求先 ✅**：被 @ 的瞬间，平台自动给触发消息贴 ✅ 表情（结构化动作）；
    禁止用一条"收到/已记录"的文本来代替。
  - **先回应，再干活**：接到任务先给出简短回应/任务清单，让人知道它接住了。
  - 消息支持 **emoji reactions**（人和芝士通用，Slack 语义 toggle）。
- 一件活里分身的内部叙述**永不**漏进房间主线。

### 14.3 唯一输入框

底部主 composer 是**聊天**的唯一输入入口。一个输入框被划词悄悄改掉收件人，是最
容易发错的交互之一，所以批注不共用它：文档的评论输入长在评论所在的地方
（2026-08-18 推翻原「全工作台唯一输入框」的写法）。除此之外不再新增输入框。

### 14.4 引用语法家族（结构化 token）

`<@handle>`（人）、`<#topicId>`（话题）、`<&路径>`（文件）——聊天与文档双端渲染为可点 chip
（文件 chip 打开文件面板并定位）。markdown 源文件保持 token 原文（显示层替换，不改数据）。
文档正文不得用一级标题重复话题名（平台已渲染大标题）。

### 14.5 平台不猜语义（§9.1 的强化）

- 标题、摘要、分类等语义内容必须由 AI 生成（`cheese title` 等），禁止"截取前 N 字"式规则。
- 预览类型由 AI 通过 `cheese artifact`/`cheese serve` **声明**（含 mime），平台绝不按扩展名
  猜测渲染方式；"怎么跑这个项目、起在哪个端口"由 AI 判断。
- 允许解析的只有：我们自定义的结构化 token、纯结构数据。

### 14.6 采纳语义

- **采纳 = 当场 merge**（#718），可撤销；不归档（#442 决定 1，归档是人的另一个动作）。
- **冲突是状态，不是失败**：merge 冲突时话题不归档、卡片进入"冲突"态，芝士被自动派去
  resolve，人再重试采纳。绝不静默归档而工作滞留分支。

### 14.7 面向用户的语言是产品语言

话题的**状态**用产品语言说：「进行中 / 已采纳 / 草稿 / 待采纳」，不说 branch、
merge to main。判据是这个词有没有在教用户平台的内部机制。

不含糊其辞地回避 git 本身的名词：验收卡要显示它开的那个 PR、它在跑的 CI、它撞上
的合并冲突、它将要落下的提交标题——这些是**正在发生的事实**，换个说法只会让人看
不懂自己在批准什么。这些词也不难懂（2026-08-18 拍板）。

### 14.8 记忆可见

芝士记住的每条记忆（项目/个人）用户都能查看与删除（侧栏「记忆」页）。
记忆是从块树可重建的投影，删除是修剪不是数据丢失。

### 14.9 可观测性与可靠性军规

- 事事有日志（structlog + 请求/turn 关联 id），每个 turn 可取证（/debug/turns）。
- **部署绝不吞活**：排空等待 + 进程死亡后的孤儿清点。重启杀掉的只是等回电的协程，
  执行环境里的屏幕还在——所以启动时先把屏幕认回来（`recover_subscriptions`），
  认回来了、而且这一轮的 prompt 确实送到过，那一轮就**不算孤儿**：它照常跑，区间
  照常开着，由那块屏幕后来送回的 Stop 收尾。屏幕没认回来（容器被换掉了）才走收账：
  不发新 prompt，靠 spool/parked-hook 把后续进展和 Stop 落成块。只有确证任务从未
  送达才把**原始消息**原样重发一次，一个话题至多一次。谁发起的不影响这个判断：人说
  的话和平台自己的活（分身开工、验收卡被驳回、CI 红了）在 prompt 没送到时同样凭空
  消失。
- **平台自己收拾干净的事不通报**。判据不是「有没有被打断」而是「平台收完手之后还
  坏不坏」：接线收账和原样重发都不出声（订阅跟着屏幕活，房间里本来就没出现断裂）。
  只有 prompt 确实丢了、而且平台不会再重发时才发事件，标 `severity=error` +
  `who=human`——那时房间里没有任何别的东西会显示这件事。
- 供应商错误结构化呈现（限额恢复时间用北京时间）。平台**不自动重试**：认不出来的
  失败、超时、卡死各发一次事件（`who=human`），交给人看一眼、修好后重新 @——不自己
  连着重跑（重跑要么把同一个缺陷再触发一遍，要么再撞上同一台刚死的机器）。跨部署
  存活是另一回事，照旧靠 recover/replay/adopt 把还活着的那一轮认回来。什么会结束一轮、
  之后房间看到什么，见 `docs/agent-liveness.md`。
- 错误提示永不被裁切/遮挡；前置条件不用错误横幅表达。

### 14.10 切换与导航体验

- 切话题**零白屏**：按话题缓存秒渲染 + 后台补齐；"在底部"是语义位置（新尾块第一帧可见）。
- 跳转（chip、引用）压浏览器历史，返回键原路可退。
- 设置等页面往返不重挂载工作台。
- 未读徽章 = 琥珀色；现场圆点：**琥珀=平台动作，灰=普通干活**（确定性判定）。

## 15. 开放问题

**产品模型**
1. Task Template 的条件怎么表达？结构化配置（JSON schema）、自然语言描述、还是两者结合？
2. 一个 Project 能不能同时链接多个 Task（拿多方资源、接受多方条件）？如果条件冲突怎么办？
3. 私聊的边界在哪？除了设偏好和问状态，还需要支持什么？私聊内容要不要进项目记忆？

**协作与 AI**
4. 多人同时在线和一个 AI 共处一个对话流的体验——消息顺序、并发编辑文档、AI 回复该 @ 谁？没有先例，dogfooding 试错
5. AI 主动说话的具体规则——什么情况接话、什么情况只记不说？需要 dogfooding 调参
6. AI 对每个人的理解怎么让用户看到和纠正？（"芝士觉得我擅长前端"——如果不对呢？）
7. agent 类型的预设怎么做？平台提供哪些、每个包含哪些 skills？需要和实际场景对齐

**实现**
8. Agent SDK 接入方式：CLI stream-json（进程级）还是 Python SDK（`claude-agent-sdk`）？两者的多 session 并发性能差异？
9. OpenViking 的 L0/L1/L2 分层加载策略——每层装什么、加载阈值怎么定？
10. 块表双树结构的工程量评估——比单独的聊天表+文档表重多少？迁移路径？
11. LiteLLM 网关的稳定性和安全性（已知 PyPI 投毒事件），是否需要自建网关？

**落地**
12. V1 的最小范围和梯队排期——阶段 0-1 需要多少人、多长时间？
13. Dogfooding 的具体形态——开发团队切到知是上协作的最小可用版本是什么？
