## 并行聊天加载的正确性

- 断线重连和存在待确认发送时，继续先用历史核对回声再重发。
- 初次加载期间收到的消息、撤回和表情更新覆盖 HTTP 历史快照；历史返回后保持同一条连接。
- 加载代次隔离切换/重连的迟到响应。
- HTTP 权限拒绝关闭提前打开的连接；WebSocket 仍独立执行服务端鉴权。
- 连接前刷新身份令牌。

## 继续测量的边界

新建 API 的代码路径为鉴权、数据库创建和名册初始化、提交；这轮没有 dev box POST /topics 的实际耗时分布。并行加载改善的是创建成功后的页面就绪路径。部署后应分别测量 POST /topics、房间页面加载、WebSocket 就绪及模型首字耗时。

其他审查发现：api.ts 的普通 GET 与令牌刷新仍缺少应用层超时，持续挂起的刷新会阻塞依赖它的请求；工作面板的多个页签组件仍静态导入，首次进入页面的资源体积值得用生产构建分析。上述两项需要独立验证和修复，本次保持现有超时及资源加载策略（新建时预加载房间页面除外）。

验收顺序：新建并连续点击；首条消息及 @ 队友；慢历史下发送与撤回；断线后的回声对账；创建期间列表轮询；归档；后台标签页恢复。真实模型和 dev box 链路通过部署后验收。
