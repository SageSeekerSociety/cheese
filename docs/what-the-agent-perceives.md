# 芝士能感知到什么

平台上一件事出了岔子，谁应该被告知——房间里的人、正在干活的芝士、还是两个都要？

今天这个问题**没有答案**，只有一次次的临时决定，而且决定之间互不一致。这份文档写下今天实际是什么样，以及要定的是哪几件事。

面向零前置知识的读者。

---

## 0. 为什么这是一个问题

芝士在房间里干活。它周围一直在发生事情：有人说话、有人改了文档、CI 红了、它自己推的分支被拒了、平台把它的容器换掉了。

**这些事情里，哪些应该送到它面前？**

送多了，它每一轮都在读跟自己无关的噪音，而这些噪音要占提示词的位置。送少了，它照着一个已经不成立的世界继续干活——**而且它不知道自己不知道**。

这不是个理论问题。下面每一条都真实发生过，而且它们不是五个 bug，是同一个空白的五个切面：

| 发生过的事 | 底下是同一个问题 |
|---|---|
| 房间里不带 @ 的消息被存下来、从不交给芝士 | 人说的话，什么时候算「对它说的」？ |
| 它报告「改动已经进了 PR 分支」，而分支根本没动 | 它对自己动作的结果有没有感知？ |
| 平台判定「这条消息没送到芝士那边」，而芝士自己不知道平台这么判了 | 平台的判断要不要回流给它？ |
| 平台自己发的一句「会话正在启动」被算成了芝士的输出 | 「谁说的话算芝士说的」的边界在哪？ |
| 订阅额度烧完，平台不知道该告诉谁 | 平台自己的故障，收件人是谁？ |

## 1. 今天真正能到达芝士的，只有两类

**一、人在房间里说的话。**

- 这一轮开始时的那条消息
- 这一轮跑着的时候，人又说的话（会被插进正在进行的会话）

**二、平台的通知——但只有一种。**

平台有一条专门的通道把事实送进正在跑的轮次（`notify_running_turn`）。它做得很讲究：内容会被套上一个标记，声明「以下是平台自动发的，不是人手打的」；而且人打的字里如果出现这个标记，会被替换掉，**所以人伪造不出平台的口吻**。

这条通道**今天只有一个调用点**：有人在这一轮进行中改了实况文档。

## 2. 有几种到得了，走的是另一条路

平台内部定义了三十三种事件——CI 失败、闸门失败、合并被拒、采纳冲突、验收卡被驳回、上游冲突、投递回退、轮次失败、轮次超时、部署打断、机器在开、换机器、迁移撞车……

其中几种到得了芝士，但不走上面那条通道：派发的时候带上 `summon=True` 和一句 `nudge_event`，**另起一轮**，那句话就是新这一轮的开场白。今天有这几处：

- 验收卡被驳回、采纳时合并冲突（`api/routes/accept.py`）
- PR 全绿但 GitHub 拒绝合并、PR 的信号（CI 挂了、有人 review 了、有冲突）（`domain/review/services.py`）
- 同步上游时合并冲突（`domain/workspace/upstream_conflict.py`）

**其余的只进房间。** 平台认为它这一轮失败了，**它不知道**。

两条通道的差别是时机，不是权限：`notify_running_turn` 把事实塞进**正在跑**的那一轮，上面这几处**另起**一轮。所以「正在跑的一轮里，芝士能不能知道刚发生了什么」，答案仍然是只有实况文档被改这一件。那条通道的机制是现成的、写得很好的，用在了一件事上。

## 3. 要定的两件事

**一、人说的话，什么算「对它说的」。**

今天靠一个 `summon` 标记，而这个标记是浏览器那边根据「消息里有没有提到芝士」算出来的。所以：房间名册还没加载完、或者用户手打了「芝士」而没从菜单里选——**都会算成没在叫它**。

**二、平台的事实，哪些必须回流给它。**

回流的那几种是一件一件加上去的：最早是验收卡被驳回（#529），后来是采纳冲突、上游冲突、合并被拒、PR 信号，每一次都是有人撞上了一个具体的坑才补的。**判据始终没人定过**，所以下一种事件该不该给它，今天还是只能靠猜测。

**这两件比以前更急。** 芝士自己提交、推送、开 PR 之后（`docs/plans/2026-08-27-retire-jj-design.md`），做事的人和看得见结果的人变回了同一个——但那次改造也把大量「平台知道、芝士不知道」的事情搬到了它那边，今天这五种猜法会在新路径上重新长一遍。

## 4. 一条候选判据（未定，供推翻）

> **凡是会改变芝士下一步该做什么、而它自己又拿不到的事实，它必须收到。
> 它自己一条命令就能查到的，不要推给它。
> 凡是只影响人怎么理解现状的，给人就够了。**

中间那句是后加的（2026-08-28），因为缺了它这条判据会把噪音也算进来：「你的工作树还脏着」确实会改变芝士下一步做什么，但 `git status` 就在它手边。**判据问的是它拿不拿得到，不是这件事重不重要。**

按这条走一遍：

| 事实 | 给谁 | 为什么 |
|---|---|---|
| 推送被上游拒了 | **芝士** | 它得重试或换招，而结果在它的沙箱之外，它查不到 |
| 工作树还脏着 | 谁都不用给 | 它 `git status` 一下就知道；而且提不提交本来就是它的选择 |
| 验收卡被驳回 | **芝士** | 同上，它得改 |
| 平台正在部署 | 人 | 改变不了它做什么 |
| 平台没有模型额度了 | 人 + 运维 | 它已经跑不起来了，告诉它没有意义 |
| 有人改了实况文档 | **芝士** | 已经这么做了，是唯一做对的那条 |

判据的价值不在这五行答得对不对，在于**它让下一个人不用重新猜**——遇到下一种事件时，有一句话可以拿来问。
