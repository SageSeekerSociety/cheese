# #389 剩下的那一半：关掉二次验证要真的重认证

## 目标

<&docs/topics/2FA第二步没有限流-357.md> 把「猜」堵住了：`/auth/sudo`（`method=totp`）和 `/2fa/disable` 都进了 `StepUpTwoFactorRateLimiter` 的独立预算。**但限流管的是猜，这次要修的是「连猜都不用」。**

`/auth/sudo` 三个分支（password / srp / totp）验完只回 `{verified: true}`，**不签发任何服务端能验的凭证，也不存任何 sudo 状态**；而 `/2fa/disable` 的验证码参数是**可选的**，前端 `disableTOTP` 正是不带验证码调的。所以那道「sudo 挡在 disable 前面」的门**只存在于前端**——拿到一个活着的会话（Cookie 被偷、设备没锁）就能直接 POST 把二次验证关掉，一次都不用猜。

## 外部共识

OWASP 对这一族的说法是一致的：敏感操作必须重新认证；会话内的高风险动作用 step-up；**删除或替换 MFA 因子按高风险处理**；以及——**MFA 因子被移除时要通过带外渠道通知用户**。最后一条的理由值得单独记：就算会话已经被偷，攻击者也不能悄无声息地把本人锁在外面。

## 决策

| # | 修法 | 状态 |
|---|---|---|
| 1 | `/auth/sudo` 成功后签发一张**服务端能验的短票**：JWT，`type=sudo`、绑 `sub` 和 `purpose`、5 分钟、一次性 | 已做 |
| 2 | `/2fa/disable` **必须带票**，验证码不再是可选兜底 | 已做 |
| 3 | 关闭成功后**发邮件**告诉账号主人 | 已做 |

## 票为什么长这样

**一次性靠预约，不靠签名。** 票的 `jti` 在签发时 `reserve`、在赎回时 `claim`，用的是 <&backend/app/core/single_use_state.py> 里现成的 Redis 原子 claim——和 #222 修 OAuth state、#357 修 pending 票同一套。签名只能说明「平台铸的」，只有预约能说明「还没被花掉」。Redis 连不上时 `reserve`/`claim` 抛错，两处都当拒绝处理，**fail closed**：分不清首次和重放，就不是「放行」。

**票上写着它是为哪件事签的。** 一次重认证是对**某件事**的在场证明。不写用途的话，本人为「添加通行密钥」验的那一次，同样能拿去关掉二次验证——被执行的仪式不是他同意的那个。所以用途在签发时问、签进票里、在赎回它的入口核对。

**`SudoPurpose` 里只列服务端真的会验的操作。** 其余那些仍然只由前端挡着的操作**不要票**（请求里不带 `purpose`，响应里就没有 `sudoTicket`）：一张没人验的票不是保护，是多配了一把钥匙放在网络上。

**`type` 检查不是形式。** 平台所有 JWT 是同一把密钥签的，所以「这个 JWT 验得过」本身什么都不说明。把访问令牌和票分开的正是 `type`——少了它，「登录着」就等于「刚证明过在场」，而这道门问的恰恰是比「登录着」更多的东西。

**四种拒绝回同一个错。** 票过期、已花掉、用途不对、不是本人，都回 `SudoRequiredError`(403)：一是补救办法完全相同（重新验证再来一次），二是分开说等于告诉一个拿着偷来会话的人，他手里那张截获的票**究竟差在哪**。

## 带外通知

用的是仓库现成的 <&backend/app/core/email.py>（`get_email_sender()`），和忘记密码那条路一样在请求里直接发，不入通知邮件队列——安全通知不该等下一次出队才送到。

**发信失败不回滚。** 走到这一步二次验证已经关掉了，这时候报错等于让本人回去重试一件已经发生的事，而重试的答复是「2FA is not enabled」。所以异常吃掉并记日志。

## 密码那半也不限次

`/auth/sudo` 的 `method=password` 分支在 `bcrypt.checkpw` 前后都没有计数器，`method=srp` 的证明校验同样没有。核过属实。威胁模型和 TOTP 那半完全相同（会话已被偷），所以一并纳入 `StepUpPasswordRateLimiter`（`cheese:sudo_password_*`，5 次 / 15 分钟）。

**三条预算为什么互不相通**：登录那条按 username 计、且每次成功登录都会清零，会话内这条按 user_id 计；密码和 TOTP 又各自一条，共用的话磨掉任一个因子就等于磨掉了另一个，第二因子就不再是第二次机会。

**SRP 和 password 共用一条**：那是同一个密码的两种走法，分开计只会让同一个攻击者换个协议就再拿满一份名额——而协议是客户端替账号选的，不是攻击者选的。**SRP 的初始化那一步不计数**：它只对一个已经握有会话的人吐出 salt 和服务端临时值，什么都没证明；给它计数反而让「开个握手不做完」变成把本人锁在外面的办法。

## 顺手收拾的两处前后端不一致

- **`SudoVerify.vue` 读 `response.data.accessToken`，后端从来不返回这个字段。** 于是每次 sudo 验证成功都执行 `AccountService.accessToken = undefined`，setter 见值为假会 `localStorage.removeItem('accessToken')`——**验证成功反而把自己登出了**。已改为读 `sudoTicket`，`setAccessToken` 整个删掉。
- **`Security.vue` 的 onMounted 在重试跑完之前就 `clearRetryState()` 了。** 重试是异步的，没 await；`clearRetryState` 会同时抹掉票和 `opData`，而重试要在第一个 await 之后才去读它们。票这条目前侥幸不炸——`consumeTicket()` 在 `withSudo` 里是同步取的，跑在清除之前——但只要有人在它前面插一个 await 就会静默变成 403 循环。`update2FASettings` 那条已经在炸了：`await` 之后那行读的 `retryOperation` 已被清空，`alwaysRequired` 拿到 `undefined`。已改成 await 完再清。
- **两处 `console.log` 会把明文新密码打进浏览器控制台。** 改密码走的也是 sudo 重试那条路，`opData` 里装的正是用户刚输入的新密码，而 `stores/sudo.ts` 的 `setRetryOperation` 和 `Security.vue` 的 onMounted 各自把整个 `retryOperation` 打了出来。已删。
- **前端有 `verifySudoPasskey`（`method='passkey'`），后端 `sudo_auth` 只认 password/srp/totp，其余一律 `BadRequestError`。** 而 `SudoVerify.vue` 在浏览器支持且账号有通行密钥时，**默认选中的就是通行密钥**——这条默认路径一直是坏的。已补上后端分支：复用登录那条的 `passkey:auth_challenge:` 挑战与 `PasskeyService.verify_authentication`，并额外核对**断言归属的账号就是当前会话的账号**（一把别人的密钥在偷来的会话里出示，否则就能给那个会话重认证）。它不计名额：WebAuthn 断言是签名不是可猜的秘密，而且挑战本身已经是一次性的。

## 测试

新增 7 个单元测试（票的签名层）+ 8 个集成测试。**负向对照一次只拆一个机制，六次各自命中**：

| 拆掉什么 | 该红的 | 实际 |
|---|---|---|
| `/2fa/disable` 不验票 | 3 条票据测试 | ✅ 红，其余 24 绿 |
| `claim` 短路成永远放行 | 「一张票只花一次」 | ✅ 只红这一条 |
| 去掉 `type` / `jti` 检查 | 3 条单元测试 | ✅ 红 |
| 未知 `purpose` 放行 | 「不认识的用途要拒」 | ✅ 红 |
| 去掉带外通知 | 「关掉后要通知本人」 | ✅ 只红这一条 |
| 去掉密码 step-up 预算 | 2 条预算测试 | ✅ 红 |

关键测试的写法仍是**在第 N+1 次发送正确的凭据**——证明它是在看都不看的情况下被拒的。

**`test_being_signed_in_is_not_having_re_authenticated` 有两份，是故意的**：集成那份把自己的访问令牌当票递进去，但它被挡住其实是靠「这个 `jti` 没被预约过」这一层，`type` 检查在那里看不出效果。单元那份才真正只测 `type`。一层挡住不等于另一层在工作。

**回归**：后端单元 3584 passed / 4 skipped，集成 1741 passed / 24 skipped / 1 failed，contract 61 passed / 6 skipped。唯一那条红的是 `test_market_api.py::test_market_lists_ai_and_compute_pools`——把本次改动的四个后端文件换回 origin/main 再跑，一样红，与本改动无关（它断言默认 AI 池 `available`，而那取决于本机有没有配上凭据）。前端 `pnpm run lint` 0 error、`typecheck` 0 error、`lint:style` 65/65 未上涨、`vitest` 在 `--testTimeout=30000` 下 756 全绿（默认 5 秒时 `router/home.spec.ts` 会超时，是本机负载，不是逻辑）。

## 没验证的

- **SRP 的 sudo 分支没有端到端测试**：测试用户是 bcrypt 建的，跑 SRP 那条要先造一个 SRP 注册的账号。共用预算这件事由 `StepUpPasswordRateLimiter` 同一个类保证，但「SRP 分支确实调了它」目前只有代码可读，没有测试钉住。
