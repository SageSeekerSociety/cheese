## 要堵的洞

两阶段采纳的第二道闸门是「合并之后、部署也成功才归档」。它原来只看**这个提交
自己那次部署运行**的结论，非 success 一律判成「需要人」。

2026-08-11 的真实事故（PR #251）：卡走完两阶段采纳、CI 全绿、平台自动合并，
随后那次部署运行的结论是 `cancelled`，于是平台留下

> ❌ PR #251 已合并，但触发的部署失败：部署 workflow 失败：cancelled。话题保持
> active，需要人判断下一步（不会自动重试）。

然后不动了，话题白白搁浅 4 小时，最后由人手工收尾。**但代码早就上线了**：#251
的合并提交 `0c194f38` 被后来成功部署的 `8470ac052` 包含。那次 `cancelled` 是被
更晚的部署顶替——concurrency 组（`deploy-dev`）对**排队中**的运行的正常行为，
不是故障。

## 现在的判定

`advance_pr_card` → `_advance_deploy_checks` 拿到非成功结论时，不再直接判「需要
人」，先问一句：**有没有一次「更晚的、成功的」部署，它的 commit 包含了这个合并
提交？** 有 → 代码已上线，闸门满足，正常归档。

`cancelled` 尤其如此（被顶替是它最常见的成因）；`failure` 同理——失败之后有人重跑
成功了，代码一样上线了（同一个 commit 上重跑成功走 `identical` 这条）。

包含关系用 GitHub 的 compare 接口判：`GET /repos/{owner}/{repo}/compare/{base}...{head}`，
`base` = 那次成功部署的 commit、`head` = 我们的合并提交，`status` 为 `behind` 或
`identical` 即包含。**不在平台侧克隆仓库跑 git**——一次 API 调用就有答案，而平台
根本没有这个项目 GitHub 仓库的 checkout。

## 同一个症状的另一半：build 没产出镜像，真的没上线

`#267`/`#270`/`#274` 卡住不是被顶替，是 build 阶段就死了（`docker login -u
github.actor` 在 push 事件里取的是提交作者，采纳提交的作者不是仓库主，403 推不动
镜像；根因已由 #276 修掉）。deploy 的守卫 job `build-did-not-produce-images` 忠实
地报了「no images were pushed, so dev is still running the previous commit」——
这一半里「没部署」是真的，盒子上跑的确实还是旧代码。

判据必须能把三种分开：

1. cancelled + **更晚的、真的部署过的**成功部署包含此 commit → 算上线，归档；
2. cancelled + 还没有这样的部署 → 继续等，不判死也不判成功；
3. build 没产出镜像 → 真的没上线，保持 active 交给人，且**说清楚是哪个 job 挂了**。

## 四条边界（都有测试钉着）

- **只认更晚的**。早于本次合并的部署跑的时候这个提交还不存在，不可能把它带上线。
  运行列表是新→旧，扫到合并时间就停。
- **一次更晚的成功部署都没有 → 维持现状**：保持 active、把判断交给人、不自动重试。
  这条路径原样保留，没有回退。
- **完成 ≠ 成功**。只有字面 conclusion 是 `success` 才算；`cancelled` / `skipped` /
  `neutral` 都是「completed」。
- **成功 ≠ 真的部署过**。`deploy-dev.yml` 对 docs-only 提交会跳过登录和部署两步，
  job 照样报 success，盒子上什么都没变。所以每个候选运行都下沉到 **job/step
  一层**核对：必须有某个 job 报 success、跑过至少一步、且**没有任何一步是
  skipped**。这条是名字无关的（job/step 名是项目自己的事）：绿灯 job 里出现
  skipped 步骤，就是 workflow 在说「这部分我故意没做」。查不到就当没有（fail
  closed）。

**判据不落在「这个 commit 自己的镜像有没有被推上去」**，看起来该这么定，但那样
`#267`/`#270`/`#274` 在 registry 修好之后会永远卡住——它们自己的镜像确实不存在，
而一个**包含**它们、并且真的部署过的更晚的提交，已经把它们的源码送上盒子了。
落在「有没有一次真的部署过的成功运行送上了包含我的提交」，它们才会因为正确的
理由自动归档；而 build 没产出镜像、后面又没有这样的部署时，结局和以前一样：
保持 active、告诉人。

## 部署失败时人看到什么

运行级的 tail 只会说「部署 workflow 失败：failure」，两种情况长得一模一样。现在
卡片和通知会带上 GitHub 自己的失败 job 名，例如
「（失败的 job：build-did-not-produce-images）」——是**报告事实**而不是平台去猜
原因，人一眼能分清「部署跑了但挂了」和「压根没产出镜像」。

另外，整个判断是尽力而为的：这一步的任何 GitHub 故障都退回旧行为（保持 active、
告诉人）。它只可能把一次误报变成归档，不可能反过来。归档时的卡片和通知会说清楚
理由——不是「本次部署成功了」，而是「被更晚的那次成功部署带上线了」，并附上那次
运行的链接。
