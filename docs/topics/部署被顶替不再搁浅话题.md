## 要堵的洞

两阶段采纳的第二道闸门是「合并之后、部署也成功才归档」。它原来只看**这个提交
自己那次部署运行**的结论，非 success 一律判成「需要人」。

2026-08-11 的真实事故（PR #251）：卡走完两阶段采纳、CI 全绿、平台自动合并，
随后那次部署运行的结论是 `cancelled`，于是平台留下

> ❌ PR #251 已合并，但触发的部署失败：部署 workflow 失败：cancelled。话题保持
> active，需要人判断下一步（不会自动重试）。

然后不动了，话题白白搁浅 4 小时，最后由人手工收尾。**但代码早就上线了**：#251
的合并提交 `0c194f38` 被后来成功部署的 `8470ac052` 包含。那次 `cancelled` 是被
更晚的部署顶替——concurrency 组（`deploy-dev`）对**排队中**的运行的正常行为，
不是故障。

## 现在的判定

`advance_pr_card` → `_advance_deploy_checks` 拿到非成功结论时，不再直接判「需要
人」，先问一句：**有没有一次「更晚的、成功的」部署，它的 commit 包含了这个合并
提交？** 有 → 代码已上线，闸门满足，正常归档。

`cancelled` 尤其如此（被顶替是它最常见的成因）；`failure` 同理——失败之后有人重跑
成功了，代码一样上线了（同一个 commit 上重跑成功走 `identical` 这条）。

包含关系用 GitHub 的 compare 接口判：`GET /repos/{owner}/{repo}/compare/{base}...{head}`，
`base` = 那次成功部署的 commit、`head` = 我们的合并提交，`status` 为 `behind` 或
`identical` 即包含。**不在平台侧克隆仓库跑 git**——一次 API 调用就有答案，而平台
根本没有这个项目 GitHub 仓库的 checkout。

## 三条边界（都有测试钉着）

- **只认更晚的**。早于本次合并的部署跑的时候这个提交还不存在，不可能把它带上线。
  运行列表是新→旧，扫到合并时间就停。
- **一次更晚的成功部署都没有 → 维持现状**：保持 active、把判断交给人、不自动重试。
  这条路径原样保留，没有回退。
- **完成 ≠ 成功**。只有字面 conclusion 是 `success` 才算；`cancelled` / `skipped` /
  `neutral` 都是「completed」。

另外，整个判断是尽力而为的：这一步的任何 GitHub 故障都退回旧行为（保持 active、
告诉人）。它只可能把一次误报变成归档，不可能反过来。归档时的卡片和通知会说清楚
理由——不是「本次部署成功了」，而是「被更晚的那次成功部署带上线了」，并附上那次
运行的链接。
