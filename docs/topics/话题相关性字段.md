## 目标

在项目话题列表接口 `GET /api/topics` 上，给每个话题补两个「跟我什么关系」的布尔字段，让前端能把「我参与的」和「其他的」分成两组。**纯后端**，产出一个可采纳的 PR。前端接线是另一条线的活，本话题一个前端文件都不碰。

## 结论：字段形状

两个正交的布尔，不是一个枚举——枚举每加一种关系就得动前端的分支，布尔各管一件事：

- **`i_participate`**：这话题跟我有关系。命中任一即为真——我在话题名册里 / 我是创建者 / 我是它验收卡上被点名的人 / 我在这话题里被 @ 过。
- **`awaits_me`**：这话题在等我动手。命中任一即为真——有一张点名给我、状态还是 `pending` 的验收卡 / 有 @我 且我没读的提醒。

`awaits_me` 为真时 `i_participate` 必然也为真。所以前端那条「需要我行动的永远不折叠」安全线，只看 `awaits_me` 就够。

## 关键发现（简报没覆盖到的）

简报担心「被 @ 过」要全表扫消息内容、代价太大，建议先跳过这一条。**不用跳过**：一个 @ 在落地时就已经写了一行 `alerts`（`kind=mention`，带 `topic_id`、`target_handle`、`read_at`，两个 handle 字段都有索引，见 <&backend/app/domain/agent/chat.py> 的 `_notify_mentions`）。所以「被 @ 过」和「有 @我 的未读」是同一条索引查询顺带得出的。四种参与关系全部做进去了，没有缺口。

## 约束

- 不碰 `frontend/`；不建表、不写 migration；不改 `TopicOut` 已有字段的语义。
- 判定必须批量：无论一个项目有多少话题，额外查询条数恒定（不是每话题一条）。
