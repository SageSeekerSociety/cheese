## 一、Buzz 怎么处理 conflict

翻完了，结论很简单：**它没有登记表，它是从 git 算出来的。**

核心是 `scripts/check-branch-skew.sh`（pre-push 钩子，约 30 行）：

```bash
overlap=$(comm -12 \
  <(git diff --name-only "$base" origin/main -- | sort) \
  <(git diff --name-only "$base" HEAD  -- | sort))
```

取「main 自分叉点以来改过的文件」与「本分支改过的文件」的**交集**，非空就拦下 push 并列出重叠文件。没有登记、没有队列、没有锁——**数据本来就在 git 里，不需要谁来声明。**

> 精确一点：该脚本头部注释说明它的初衷是「CI 测的是与 main 合并后的树，本地在落后的分支上跑检查会假绿」——**防冲突是它的副作用，不是它的主目的**。但机制正是我们要的。

> ⚠️ **但别照抄这个脚本，2026-08-11 实证**：它只比对**文件名**。我曾据此建议用它防 alembic 链分叉，**这条是错的**——两个 PR 各加一个不同名的 `versions/*.py`，交集恒为空，一条都抓不到。#264 里落地的是另写的 `check-migration-fork.py`（`ast` 解析 `down_revision`，算 revision 图的 head 数）。
>
> **对本设计的影响：没有。** 本文 §三 的 P2 从一开始就是按**语义冲突**单独设计的，正因为通用文件重叠检测抓不到它。这次的实证反而把 P2 从「我觉得需要」升级成了「已被证明必需，且已有一个可复用的实现」。

除此之外它只有两样：**worktree 隔离**（并行构建互不干扰，`AGENTS.md:574` 的 per-worktree 应用标识）和**社交约定**（`CONTRIBUTING.md:40`「先开 issue，避免两个人并行造同一个东西」）。数据层面用 CAS/409（`CasError::Conflict`）和 NIP-33 last-writer-wins，同样是乐观并发，不是锁。

## 一点五、一次刚发生的实证（2026-08-11）

写完本设计的同一天，@agent 能力发现：补 jj 与 CLI 自描述 报回来一个**没有任何征兆**的坑：

> 它的工作区落后 main 一天，而 PR #260 刚动过它要改的那个文件——**直接改会无声 revert 掉 #260 的改动**。

三点值得记：

1. **它是靠自觉发现的，不是靠机制。** 那一路碰巧在动手前查了 main，换一个不查的分身就直接把别人的改动盖掉了，而且**不会有任何冲突提示**——因为它是在旧版本上编辑，git 眼里这是一次正常的修改，不是冲突。
2. **这正好是 P0 要覆盖的场景**：#260 合并时，如果系统能算出「哪些开着的话题的分支也碰了这个文件」并 summon 它们，这个坑根本不会存在。
3. **它也印证了原方案的第 2 条问题**：这个冲突是**干到一半才发现**的，开工前的登记表登记不到它。



**原方案**：建一个公共文档，按字典形式让 agent 开工前和开工中登记自己要改的部分；两个要改同一处就排队或等 merge 后互相通知；前面的改完就通知后面的。

**方向认同**，贵的冲突都是发现得太晚的冲突；而且「前面的改完就通知后面的」是整个想法里最值钱的一半，反提案原样保留。

但登记表那一半有四个问题：

| # | 问题 | 依据 |
|---|---|---|
| 1 | **自觉的规矩会烂** | 本仓前科：<&.claude/rules/backend-tests.md> 写着「别加第九个 `_auth()`」，实测**同签名 9 个、算上改名 `_login` 和内联的共 14 个**——**而且这条规则正是在它以纯文字形式存在期间被突破的**。一张有人忘记更新的登记表**比没有更糟**：它给虚假的安全感 |
| 1b | **靠名字识别的机制，只抓得住守规矩的人** | 同上：躲过散文规则的那 5 份，恰恰是**已改名或没起名**的。这直接迁移到登记表——**最该被登记的那次改动，正是最可能不登记的那次** |
| 2 | **开工前的声明是预测，而预测不准** | 第三个要改的文件常常是干到一半才发现的。登记表**恰好在最需要它准确的时候是陈旧的** |
| 3 | **僵尸锁** | agent 超时/被杀就留下永不释放的登记。这个学费已经付过：08-09 全项目采纳卡死 1.5 小时，根因是一个 0 字节 `index.lock`，最后要人上宿主机手动删（见 <&docs/topics/采纳合并隔离worktree.md>） |
| 4 | **粒度两头不讨好** | 文件级太粗：两个 agent 改 `services.py` 的不同函数并不冲突，白排队。又太细：抓不到高频的语义冲突——两个话题各基于同一 head 加一条 alembic 迁移，文件名根本不重叠，但合并后迁移链分叉 |

## 三、反提案：同样的目的，算出来而不是报上来

### 地基（全部已存在，已核实）

| 事实 | 位置 |
|---|---|
| `branch_for_topic(topic_id) → f"topic/{hex[:8]}"`，确定性映射 | <&backend/app/domain/workspace/service.py>:118 |
| `merge_topic()` 是采纳合并的唯一入口 | 同上 :831 |
| 同项目所有话题分支在**同一个 git 仓库**里 | `ensure_repo(project_id)` |
| 唤醒话题的通路已建好 | `runner.submit(..., summon=True)`，见 <&docs/topics/后台任务唤醒话题.md> |

所以「话题 A 和话题 B 有没有碰同一批文件」是一条本地 git 命令，无网络、无需任何人声明。

### 核心：一个纯函数

```python
def touched_files(repo, ref, base) -> set[str]:
    mb = _git(repo, "merge-base", ref, base)
    return set(_git(repo, "diff", "--name-only", mb, ref).splitlines())
```

剩下的全是「在哪调它」。

### P0 —— 采纳后通知下游（原方案里最值钱的那一半）

挂在 `AcceptService.accept()` 中 `merge_topic` 成功之后（<&backend/app/domain/review/services.py>:494）：

1. 算出刚合并的话题动了哪些文件
2. 遍历本项目所有**开着的**话题分支，各算一遍
3. 交集非空 → `summon` 那个话题，带结构化消息：「话题 X 刚合并，它改的这 3 个文件你也在改：… 先同步 base 再继续」

**零 agent 配合、不可能忘记更新、没有僵尸锁——因为压根没有锁。**

### P1 —— 轮次开始时提示，但不拦

话题起一轮时算一遍，有重叠就把这句话放进本轮上下文：「你要改的 `services.py`，话题 Y 也在改。」

**这是信息，不是闸门。** 这是与原方案最大的分歧点：

| | 原方案 | 反提案 |
|---|---|---|
| 检测到重叠 | 排队 → 串行 | 双方都知道 → 仍并行 |
| 代价 | 放弃并行收益 | agent 自己决定要不要先聊 / 换顺序 |

### P2 —— alembic 专项

抓那类**文件名不重叠、但必冲突**的：两个开着的话题各自新增迁移且 `down_revision` 相同 → 直接报。

比通用重叠检测更准，因为抓的是**语义**冲突。也是已踩过的坑（<&docs/topics/采纳合并隔离worktree.md> 记着当时得补一条空迁移收敛 DAG）。

> ✅ **P2 的检测逻辑已经有现成实现了**：#264 合进 main 的 `check-migration-fork.py`（`ast` 解析 `down_revision`，注意 merge revision 的是 tuple；把 `origin/main` 和工作树两张图并起来算 head 数）。
>
> 它现在跑在 **CI 上、事后判树**。P2 要做的只是**把同一个判据挪到事前**：不再比「main vs 我」，而是遍历所有开着的话题分支两两算一遍——**复用逻辑，只换输入。** 这让 P2 的估工从「设计 + 实现」缩到只剩「换输入 + 接 summon」。

## 四、三条必须说清的局限

1. **抓不到语义冲突。** A 改了函数签名、B 在调它——文件不重叠，检测不出来。但原方案的登记表同样抓不到；这类只有测试和类型检查能抓。**别指望这套消灭冲突，它只能让冲突早暴露。**
2. **精度取决于快照新鲜度。** 算的是话题分支上**已快照**的状态，agent 刚写还没 snapshot 的改动看不见。缓解：算之前先 `snapshot_worktree`（采纳路径已这么做）。**这是真实的精度损失，不是零成本。**
3. **会有噪音，降噪规则没想透。** 一个碰了 <&CLAUDE.md> 的话题合并，可能一口气通知一大片。需要阈值或「同 hunk 邻近」之类的规则。**这是本方案最不成熟的部分。**

## 五、落地建议

**P0 单独就能成立**、纯增量、不改任何现有行为。建议先只做 P0，跑一两周看通知的信噪比，再决定要不要做 P1——P1 要往每轮上下文里塞东西，噪音大了反而是负担。

**开工第一步必须是量数据，不是写代码**：把我们仓库里开着的话题两两之间的文件重叠分布拉出来。**如果真实重叠率很低，说明遇到的冲突大头根本不是文件级的，方案就得换。**

## 六、明确不做

- 不做锁
- 不做队列 / 串行化
- 不做登记表
