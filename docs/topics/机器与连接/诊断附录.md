## 任务快照备份 500（task 4db75afb，连续三次） {#backup-500}

路径：post-commit → cheese sync → git bundle（只含不在 origin/main 的对象）→ PUT /projects/{id}/git/tasks/{id}/snapshots/{sha}（客户端超时 120s）→ 512MiB 上限、digest/magic 校验失败是 422 → R2 上传带服务端 asyncio.timeout(120)，超时/上传错误未捕获 → 500。

代码层能确定的只有一点：校验失败（digest/magic、超 512MiB）返回 422 而不是 500，所以 500 来自服务端未被捕获的异常。handler 内部还有临时文件、流式写、digest、数据库、private_storage、flush 等多处都可能抛，实际异常类型没读到，落在哪一处 unknown。「大 bundle 超时」「部署窗口」都只是待证假设。push（forge）与备份（R2）是两条独立路径，push 成功、备份 500 不矛盾。要钉死需要 dev 机后端日志异常类型 + worktree cheese-sync.log 时间戳（都要 sudo）。

## 长上下文整理样本（话题 422，2026-09-30）

转录里三条「对话太长，正在整理上下文；整理完会接着处理，期间不会回复」：09:43:38.530Z、09:54:12.966Z、09:55:36.777Z。status 无 live_turn；root 保留远端 506ca48a，未重启。

语义（events.py:118-130、prompt.py:343-366、hook_stream.py:385-505）：每条 = 一次 compaction 开始；一轮内原位复写同一块；结束变成「上下文已整理，接着处理」或「上下文整理没有完成」+原因；轮在整理中结束 →「会话在整理完成前结束了」。发生在会话宿主，与工作机无关。三条消息是三次开始，间隔相加不是模型生成耗时。

在场证据（2026-09-30 10:27–10:30Z）：同一轮（d191d12f…）10:27:06Z、10:28:09Z 继续新增 running 提示，提示块 meta.at 更新到 10:30:10Z；同时 status.turn/live_turn 为 null，GET /agent/control 返回 id:null、connected:false、controls:[]。这组读数推不出「远程会话已死」，也推不出「整理已完成」：control 空是路由在 runtime 为 None 时的兜底，ComputePool 未在话题属主候选里选出 SessionControls（可能没有或陈旧的后端 handle，也可能选择口径如此）；该入口当时是房间级、没有席位枚举，也没有直接 ping runner 的口子。普通鉴权 API 找不到对真实 compaction attempt 的在场核验手段，标 unknown；不借内部 execution token、不开中央宿主 shell。这是状态可观测缺口。另：当前 main（e173aa4，采样 SHA 之后）注册集仍只有 ClaudeCode，Mimo 只是 model 标签，不用未注册骨架解释现场。

## first_output_s 语义（本采样版本） {#first-output-s}

本采样版本（9d035d8）注册集里只有 ClaudeCode，通道一律包在 CentralChannel 外（compute.py:438-468），provisions_machine=False（central_provider.py:51），所以 chat.py:4149 的「云端准备等待」分支对当前注册集不触发。cloud_provider.py 里 provisions_machine=True 的类不在本部署注册集内，不是真实分支，不能拿它解释现场。

计时边界：t0 在 _execute 开始（runtime.py:2336），first_output_s 记在第一个 assistant_block 到达时（runtime.py:2566-2568）。t0 之前还有 admission（_wait_to_start / _admit，runtime.py:2156-2167）：项目并发上限排队、额度闸都在那段。所以 first_output_s 含执行段内的组装、平台准备和模型首块，但不含 admission 排队；用户的实际等候 = admission + first_output_s。它不是 TTFT，也不是用户等待全长。
