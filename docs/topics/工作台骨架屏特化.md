这个房间做了两件事，都由符露夀提出：**骨架屏对不上真内容**（已合并，PR #896），和**对话排版改成气泡 + 左右分栏**（待验收）。

## 一、骨架屏：一种形态被三处共用（已合并）

起因是「工作台上面的 skeleton 是不是没有特化？感觉和实际加载出来的东西差距有点大」。

查下来不是没做特化 —— `<&frontend/src/components/common/LoadingSkeleton.vue>` 本来就按我们自己的行写了 5 种形态。毛病是 `entry` 这一种当初照着「支线进度」那种 55px 的行量的，后来看板和「现场」也拿去用了，而那两处的真内容根本不是这个形状。

尺寸不是读 CSS 推的，是把应用在沙箱里真跑起来、用无头浏览器量的：

| 位置 | 改前骨架 | 真内容 |
|---|---|---|
| 看板的卡 | 54px，两条灰线，无边框 | 101px 的带框块，间距 109 |
| 现场的一条动作 | 54px，还多缩进 8px | 带参数的一条 38.6px，间距 52.6 |
| 一条活 | 4 条等长灰线 | 标题 28.7 + 元信息 28.8 + 简报段 |
| 支线进度 | 行高对，但少画分组小标 | 行到齐时整段下移 28px |
| 文档 | 没有骨架 | 见下 |

拆成 `card` / `site` / `brief` / `doc` 四种新形态，`entry` 留给支线进度并补上分组小标。看板那处改后逐像素重合（骨架 y=165 高 101，真卡同）。

**顺带修的一处「说假话」**：文档那格原来没有骨架，正文区空着，而空编辑器会亮出占位句「芝士会在这里维护文档」—— 那句话的意思是「这篇文档是空的」，于是每一篇有内容的文档在到达之前都被界面说成空的。`<&frontend/src/components/panels/PanelDoc.skeleton.spec.ts>` 钉住了这条。

**判据已写进组件顶部**：一种形态只对一样东西负责，宁可多一个 variant，也不要共用 —— 骨架只存在一瞬间、不会报错，共用赌输了没人会发现。

## 二、对话排版：气泡 + 左右分栏（待验收）

### 决定是怎么定下来的

符露夀问「要不要加气泡、要不要分左右两侧」，让先看千问的多人工作台和 Multica。调研结果：**千问的「多人工作台」不是聊天界面**（它做的是「一句话生成带角色权限/云数据库/管理后台的协作网页」），参照物在这件事上是空的；**Multica** 的对话形态是 issue 下的评论流，全部左对齐无气泡。

我最初建议「只给人加气泡、芝士平铺、不分侧」。符露夀指出**芝士的消息也是靠 `cheese chat send` 一条条完整发出去的**，那它就不该是这一列里唯一没有气泡的那个 —— 这条推翻了我的理由（我给的是「助手面板」的理由，而芝士是队友）。最终符露夀定的是**气泡 + 左右分栏**。

原型（`<&docs/topics/chat-layout-preview.html>`，四档可切、可缩放）留在工作区，没进仓库 —— 它的用处到拍板为止。

### 定下来的形状

- **侧只回答「这条是不是我说的」**。「谁在说」由头像和名字承担，两侧都保留：房间里是「多个人 + 一个芝士」，左边同时坐着好几个人。**芝士在左边**，它是队友里的一个。
- **判据是 handle，不是 `author_type`**：按「是人还是 AI」分，别人说的话会跟着我跑到右边去。这条写成了测试（`<&frontend/src/components/ChatPanel.sides.spec.ts>`）。
- **对侧留白 8%**，不是各家常见的 15% —— 头像已经说明了侧。默认栏宽下正文列 403px（15% 时是 365px，平铺是 470px），代价从 22% 降到 14%。
- **两侧只差一档灰**（别人 `--fill`，自己 `--fill-2`）。不能用颜色编码「我」：别家那一格放品牌色，我们那个位置是琥珀，按设计系统只留给主操作、激活态和品牌。立面靠 `--line-2` 描边（§3.4「卡片只描边，不投影」）。
- **平台行**：单行的两种（一句话事件、轮次小结）居中；带右侧状态列的动作卡、可折叠的报错卡、事故卡留在左轴上 —— 居中会让那一列没有落点。

### 三处是形状拖出来的，读代码看不出来

驱动真界面才发现的：

1. **表情面板会飘出聊天栏**。悬停条在自己那侧镜像到左上角，而面板挂在条上往右展开，整个滑出去盖到侧栏，实测点不到。
2. **悬停会把气泡吃掉**。原来 `.im-row:hover` 把整行刷成 `--fill`，而气泡也是 `--fill`。
3. **代码块和 chip 在气泡里是糊的**。它们原本也是 `--fill`，现在往「面」那一级挪 + 一条更浅的线。

### 跟着改的一处

消息成了气泡，**加载骨架的聊天那一档也得是气泡形** —— 画一条灰线、等来一个带框的块，到货那一刻整列会重排一次。这正是第一件事的同一条规则。

### 验证

沙箱里把应用真跑起来验的：灌了一段多人对话（Bob / carol / 我 / 芝士），无头浏览器逐项量位置和底色，悬停条镜像、表情行靠右、发件箱那一条（断网制造）都在右边，浅色深色各截一张。vitest 147 文件 1178 条全过、vue-tsc 0 error、eslint 0 error、stylelint 63 未超基线、仓库闸门 PASS。后端一行未动。

## 复现手法（下次要量前端的尺寸就照这个来）

不要静态读 CSS 推尺寸。步骤：`eval "$(bash <&.claude/scripts/dev-db.sh> start)"` → 建库跑 alembic → `uv run python -m scripts.seed_fusion_demo` → uvicorn + vite（自选端口，这台机器是共用的）→ playwright 用 alice/demo12345 登录 → `page.route` 把目标接口延迟 10 秒，在骨架和真内容两个时刻各量一次 `getBoundingClientRect` 并截图。

两个自己踩过的坑：**量颜色前先把鼠标挪开**（`:hover` 会混进 `getComputedStyle`，我一度误判芝士的气泡用错了底色）；**在半屏的「预览」格里放按全屏画的原型会失真** —— 那一格只有约 520px，1085px 的舞台被压到 45%，看到的比「拖到最窄」还窄，原型必须整体缩放而不是让栏被压扁。
