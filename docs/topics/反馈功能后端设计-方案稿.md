## 0. 一句话

把 PR #1222 那个纯前端反馈原型（mock 数据 + localStorage 里的 mock 角色）落成真功能：
一组 `feedback_*` 表、一组裸路径 REST（`/feedback`）、一套以 handle 为键的鉴权、
以及 agent 在对话里提案、由人按一下才成立的提交路径。

### 1.3 原型的自相矛盾与缺口（不是挑刺，是必须在这里定掉的）

1. **状态集对不上。** `feedbackMock.ts` 顶部注释自己写着：需求里状态列了 5 个、
   Timeline 写了 4 步（「已收录 → 评估中 → 计划中 → **已上线**」）。原型统一成 5 步
   并把「已解决 / 已上线是否拆开」明确留给了本轮。→ §8.4。
2. **`views` 有字段没有来源。** 整个原型里没有任何一处给 `views` 加一，种子里直接写死
   412 / 305 / …。真做起来要么一张浏览记录表，要么一个计数器，两个都有人刷的问题。
   → §8.5。
3. **`supports` 与 `supportedByMe` 是两个字段，服务端必须拆表。** 原型注释解释得对
   （「每条只算一次，靠 supportedByMe 记」），但那句只说对了 UI 那一半——服务端若只存
   一个计数器，取消支持就是 `-1`，任何人都能把它减成负数。
4. **`tags: string[]` 与仓库现有的 `tag` 表对不上。** 本仓有 `/tags`
   （`backend/app/api/routes/tags.py`、`backend/app/domain/tag/models.py`），而且那张表的
   `name` **没有**唯一约束。「标签去重」没有现成实现。→ §8.8。
5. **附件只记名字。** `draft.attachments: string[]`，注释与验收标准都写着「只做 UI、
   不真的上传」。真做起来要决定走 1.0 的 `attachment` 表还是新开。→ §8.7。
6. **`internalNote` 是一个字符串。** 两个管理员先后写，后写的把先写的盖掉，且没有
   「谁、什么时候」。做成 append-only 的行更贵一点，但不会丢东西。→ §2.3。
7. **`security` 与 `visibility` 正交但实际蕴含。** 种子里两条 `security: true` 的条目
   `visibility` 都是 `private`，而管理后台把「安全问题」做成**与「私密反馈」并列的独立
   一栏**（`adminItems` 的 `private` 分支显式 `&& !i.security`）。所以它更像 `private`
   之下的一个子类。→ §8.3。
8. **私密反馈，提交者自己也看不到。** `publicItems` 把私密条目整个滤掉，
   `FeedbackDetailPage.vue` 的挡板是 `visibility === 'private' && store.role !== 'admin'`。
   一个用户提交了私密反馈，然后自己在列表里找不到它、点直达链接被挡。**需求方已定：
   提交者可以看见自己提交的私密反馈**（§8.0），所以原型这一处要改。
9. **`source: 'agent'` 与「谁提交的」被合并了。** `store.submit()` 里
   `source: draft.fromAgent ? 'agent' : 'user'` —— 人按的按钮，来源记成 agent。这个语义
   是对的（「这是谁发现的问题」），但它丢掉了「谁把它发出去的」。→ §5。
10. **角色开关必须整块删掉。** 原型注释自己写了「真到了接后端那一步，这个字段就该被
    删掉，权限判断回到服务端」。本文按这句话设计。
11. **`assignee` 的来源是写死的。** `ASSIGNEES = ['andylizf', 'n1ctheboy', 'ligan',
    'maxiaoyu', 'chiruotong']`——开发团队的 handle。真做起来这个列表从哪来是个独立问题。
    → §8.9。
12. **列表层过滤 + 详情页挡板，原型自己在注释里说「真接后端时这一层应该在服务端」。**
    照做（§4）。
13. **`related`（相关反馈）是全量算的。** `store.related` 遍历所有公开反馈按标签重合度
    打分。客户端要这么算就得先把全部公开反馈拉下来，服务端算则是另一个查询。→ §7。

## 2. 领域模型：表与字段

### 2.1 放哪

新开一个 domain 模块，照 `backend/app/domain/comments/` 的形状（`models.py` /
`repositories.py` / `services.py`，按需再加 `schemas.py`）：

```
backend/app/domain/feedback/
├── __init__.py
├── models.py
├── repositories.py
├── services.py
└── schemas.py
```

为什么是新模块而不是塞进已有的某个：本仓的分层是 Route → Service → Repository → Model，
**按领域分目录**（`docs/product-impl.md` §4）。反馈既不属话题、也不属评论、也不属通知，
它有自己的状态机和自己的两个受众（用户侧 / 管理侧）。塞进 `comments` 会让那个模块同时
服务两种主键类型（见 §2.3）。

### 2.2 主表 `feedback`

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | `Uuid` PK | 走 `UuidPk`（`backend/app/domain/common.py`） |
| `display_no` | `Integer` + `Sequence("feedback_seq")` | 展示号，`FB-1042` 就是这个 |
| `title` | `String(300)` | 与 `Alert.title` / `Topic.title` 同长度档位 |
| `summary` | `String(300)` | 列表里那一句；原型是正文首行截 60 字 |
| `kind` | `Enum(native_enum=False, length=16)` | `bug` / `suggestion` / `other` |
| `status` | `Enum(native_enum=False, length=16)` | 五个值，见 §2.5 |
| `visibility` | `Enum(native_enum=False, length=16)` | `public` / `private` |
| `priority` | `Enum(native_enum=False, length=16)` | `low` / `normal` / `high` / `urgent` |
| `security` | `Boolean, default false, server_default "false"` | 见 §8.3 |
| `problem` / `why` / `expectation` | `Text` | 提交者/agent 写的内容 |
| `what_happened` / `repro` / `evidence` | `Text, nullable` | agent 发现的现场三段 |
| `logs` | `Text, nullable` | 「附带当前会话的日志与环境信息」勾上时的快照 |
| `session_id` | `String(64), nullable` | **快照，不是外键**（见下） |
| `environment` | `String(255), nullable` | 快照 |
| `author_handle` | `String(64), index` | 发现者；agent 时是它的 handle |
| `author_user_id` | `Integer, nullable` | 有 int id 时冗余存一份，供 join/统计 |
| `author_is_agent` | `Boolean, default false` | 对应原型 `source`；由 `Actor.is_agent` 填 |
| `submitted_by_handle` | `String(64), nullable` | 「谁按下提交的」，agent 提案时是人 |
| `submitted_by_user_id` | `Integer, nullable` | 同上 |
| `assignee_handle` | `String(64), nullable, index` | 指派 |
| `topic_id` | `Uuid FK(topics.id, ondelete="SET NULL"), nullable` | 上下文指针 |
| `project_id` | `Uuid FK(projects.id, ondelete="SET NULL"), nullable` | 上下文指针 |
| `created_at` / `updated_at` | `Timestamps` | `backend/app/domain/common.py` |
| `deleted_at` | `DateTime(timezone=True), nullable` | 软删，照 `Comment.deleted_at` |

**为什么主键是 uuid、展示号另开一列。** 原型的 `FB-<max+1>`（`store.submit()` 里
现算）是原型里唯一能让详情页 URL 有意义的办法。真做起来，人类编号在并发提交下必须唯一，
而 uuid 天生不需要协调。两件事分开：`id` 是键，`display_no` 是人读的。
取号的形状照 `task_seq` / `notification_seq`（`backend/app/domain/task/models.py` 顶部、
`backend/app/domain/notification/models.py`），即 PG Sequence —— 不是在应用层 `max()+1`。

**为什么作者是 handle 而不是 int 外键。** 本仓有两族 token，只有一族带 int id
（`.claude/rules/backend-tests.md` 第一条、`backend/app/auth/caller.py` 的模块 docstring
把这件事讲得最清楚）。handle 是**唯一两族都有的键**，也是全平台唯一在用的授权键。说清楚一点：handle 是
**2.0 那一族的约定**，1.0 族今天仍然是 int 外键（`Comment.created_by_id`、
`Notification.receiver_id`、`AgentBinding.user_id`）——反馈属于前者。另外这些列名是
**新的**：现有表里没有任何一列叫 `author_handle` 或 `submitted_by_*`，对齐的是形状
而不是命名
（`backend/app/api/auth.py` 的注释：「Every authorization key in the platform is the
handle STRING」）。写 `String(64)` 也是既有约定：`TopicMembership.member_handle`、
`TopicReadState.user_handle`、`Alert.target_handle`、`BlockReaction.author` 全是字符串列。

**哪些字段是冗余快照、不是外键——这是本设计最重要的一条判断。**

`session_id` / `environment` / `logs` / `what_happened` / `repro` / `evidence` 全部是
**提交那一刻的字符串快照**。三者的理由**不一样**，分开写：

- `environment` / `logs` 是**没有表可引**：环境是 `Topic.environment` 这个 JSON 列
  （`backend/app/domain/topic/models.py`，由 `project_environment(project.settings)`
  生成并 pin），日志只有 pydantic intake 与内存里的 burst 判定
  （`backend/app/domain/{frontend,backend}_log.py`），没有 `Base`、没有表名。快照是唯一
  可行的形态。
- `session_id` 是**有表，仍然选择快照**。`agent_sessions`
  （`backend/app/domain/agent_session/models.py`）是一条 uuid 行，键是
  `(topic_id, task_id, agent_handle, harness)`，而 harness 自己那个会话 id 落在
  `resume_token` 上——那列的注释明写它是不透明串、不得解析。也就是说今天没有一张表能
  回答「`sess_7c21a4` 是哪一行」，把 `agent_sessions.id` 存进来回答的是另一个问题。
  再加上会话会被归档、机器会退（`docs/where-a-turn-runs.md` 讲的就是这件事）：一条指向
  会话的外键会在会话没了之后让这条反馈读不出东西——**而那是这条反馈唯一的证据**。
- 同一个道理在本仓已经说过两遍：`TopicProgress` 的 docstring（「a turn that dies
  mid-flight must not take the progress with it」）和 `Block` 上那段关于
  `consumed_turn` 的注释（运行时事实不能从别处反推）。

`topic_id` / `project_id` 是可以有的，但它们是**「跳回去看」的指针**，
`ondelete="SET NULL"`，不参与鉴权也不参与渲染。

**提交时仍然要校验上下文。** 快照不等于不检查：如果提交者带了 `session_id` / `topic_id`，
服务端要在**写入时**确认这个会话/话题是提交者能看到的（用 `ActorResolver` 的
`authorize_topic` / `can_access_topic`，`backend/app/api/auth.py`），否则一条反馈可以变成
窥探别人会话的入口。校验通过后存快照，之后不再复验。

### 2.3 子表

**`feedback_supports`** —— 一人一票。

| 列 | 说明 |
|---|---|
| `feedback_id` FK CASCADE, index | |
| `author_handle` `String(64)`, index | |
| `created_at` | |

唯一约束 `(feedback_id, author_handle)`。形状直接照 `BlockReaction`
（`backend/app/domain/block/models.py`）——那张表就是
`UniqueConstraint("block_id", "emoji", "author", name="uq_block_reaction")`，做的正是
「同一个人不重复表一次态」。**借的是形状，不是表**：表情是挂在 block 上的，我们的支持
挂在 feedback 上。

计数：原型列表按支持数排序（`hot` Tab），也按它显示数字。两种做法：

- 每次 `count(*)` 聚合 —— 列表页 N+1，但数据永远对；
- 主表加冗余列 `supports_count`，在**同一个事务里**随 insert/delete 维护。

建议前者（MVP，列表分页 20 条，一个 `GROUP BY` 就完了），把后者留到真慢了再说。理由：
冗余计数器是本仓没有先例的东西（`BlockReaction` 就没有计数列，`comments` 的
`count_votes` 是实时聚合的，见 `backend/app/domain/comments/services.py`）。

**`feedback_comments`**

`(id, feedback_id FK CASCADE, author_handle, author_user_id, author_is_agent, body,
parent_id FK CASCADE 可空, created_at, deleted_at)`，索引 `(feedback_id, created_at)`、
`(parent_id)`。

**`parent_id` 是这一稿补上的**（2026-09-19）：初稿漏了它，而原型的
`FeedbackComment.parentId` 是真的在用——`FeedbackCommentsThread.vue` 靠它分出顶层与回复，
三种评论布局里第三种（楼中楼）整个建立在它上面。漏掉的后果是接后端时才发现「回复」这个
交互没有列可存。自引用外键、`ON DELETE CASCADE`：父评论删了，回复跟着删。

**只允许两层，且这条规则写在服务端。** 原型把规则收在数据层一处
（`stores/feedback.ts::addComment` 的 `parent?.parentId ?? parent?.id`），注释写明了理由：
「三个评论布局里只有一个在乎层级，把这条规则写在数据层就不会出现『甲平铺、丙嵌套、两边的
父子关系还不一样』」。服务端照抄这条：**收到 `parent_id` 时如果父评论自己也有 `parent_id`，
就改挂到父评论的顶层祖先上**，并且只准挂一层——传进来的 `parent_id` 必须是一个顶层评论，
否则 400。这样 `parent_id` 这一列在数据库里永远是「顶层评论 id」，读的时候不需要递归。

（要不要无限嵌套是这一轮评审的问题之一——真要做，改的只是这条校验和前端那一栏，
列本身不用动；这也是为什么不干脆把 `parent_id` 省掉。）

**不复用 1.0 的 `comment` 表**（`backend/app/domain/comments/models.py`）：它靠
`(commentable_type, commentable_id)` 多态，而 `commentable_id` 是 `Integer`。我们的主键是
uuid。要用它就得扩 `CommentableType` 枚举**并且**把 `commentable_id` 改成 uuid 或加一列
—— 那条路上还躺着一个 PG 原生枚举（`create_type=False`，类型本身由另一条迁移建）。
为一个新功能去动 1.0 评论表的主键，是把风险放错了地方。

**`feedback_timeline`**

`(id, feedback_id FK CASCADE, status, at, by_handle)`，索引 `(feedback_id, at)`。
**状态与时间线是两份数据，且必须一起写。**

原型已经踩过这个坑，注释原话：「只改状态不写时间线，右侧那根 Timeline 就会和卡片上的
状态词对不上」（`stores/feedback.ts::setStatus`）。服务端的做法是把这件事从路由层收走：
`status` 是当前值，`feedback_timeline` 是 append-only 的事件流，**改状态与追加事件只在
同一个 service 方法里发生、同一个事务里提交**，路由不暴露任何直接写 `status` 的入口。

时间线里同一状态可能出现两次（回退再推进）。原型的读法是对的并写在了注释里
（前端时间线组件沿用的是「取**最早**那一次，因为时间线记的是什么时候到过这里，不是最后
一次是什么时候改回来的」）。这个读法在服务端不成立——有两条记录就是两条，它回答「到过
这里几次」。要不要保留回退语义，→ §8.4。

**`feedback_notes`**（内部备注）

`(id, feedback_id FK CASCADE, author_handle, body Text, created_at)`，append-only。
主表**不存** `internal_note` 字符串列。理由见 §1.3 第 6 条：一个字符串列在两个管理员
之间会互相覆盖，且留不下作者和时间。UI 上仍然渲染成「一条备注」没有问题——取最新那条。

**`feedback_attachments`** —— 这一轮**没有建这张表**，附件上传整块不做（§8.7/§8.1）。
写在这里的那条硬要求仍然作数，将来做的时候是第一条判据：私密反馈的附件必须不能被一个
公开 URL 读到，否则「私密」是假的。

**`feedback_tags`** —— 本稿**不建**，见 §8.8。MVP 建议在主表上加一个
`tags: JSON` 列（`default=list`），与原型一一对应，筛选先不做。
本仓用 JSON 列装结构化小数据的先例很多：`Alert.payload`、`TopicProgress.items`、
`Block.meta`。

### 2.4 索引

按查询倒推。四个真实查询：

1. 公开列表（`visibility='public'`，按状态/时间过滤，按时间或支持数排）
   → `(visibility, status, created_at desc)`，再按需 `(visibility, created_at desc)`
2. 管理端四栏（公开 / 私密非安全 / agent 来源 / 安全）
   → `(visibility, security, created_at desc)`；`author_is_agent` 单独一个
   部分索引 `WHERE author_is_agent`（agent 发起的反馈是少数）
3. 「我的反馈」→ `(author_handle, created_at desc)`、`(submitted_by_handle, created_at desc)`
4. 未读（§6）→ 在未读那张表上，主表不用管

子表各一个 `(feedback_id, ...)` 索引。加一条：`feedback(assignee_handle)` 部分索引
`WHERE assignee_handle IS NOT NULL`——「指派给我的」是管理端最常见的入口之一。

**搜索**：MVP 用 `ILIKE`，理由与落地细节见 §4.5。这是一次**有意的退化**，不是忘了。

**一处需要更正的事实**（本节初稿写错过，2026-09-19 复核后改）：初稿写的是「本仓也没有任何
全文检索的先例（grep `tsvector` 在 `backend/` 下为空）」——**这是错的**。`backend/app` 下有
11 处 `tsvector`，分布在 `questions/`、`tag/`、`team/`（两处）四个 repository 文件里，从
2026-05-12 起就在；`backend/alembic/versions/b1f2a3c4d5e6_add_fts_gin_indexes.py` 还给
question / tag / team 建了三个 GIN 索引。正确的说法是：**有先例，但那些先例对中文基本不工作**
（`'simple'` 字典把一整串汉字当一个 token），而且全都**只当布尔过滤用、不做相关度排序**。
结论不变，理由变了。

### 2.5 状态集

`received → triaging → planned → in_progress → resolved`，五个值，取原型的
`STATUS_LADDER` 原样（连字符串都不换，`received` 而不是 `new`）。理由：前端已经有
`STATUS_META` 的颜色表和 `STATUS_LADDER` 的顺序表，换词就要同时改前端两张表和
i18n 目录，收益为零。

梯子的**顺序**进了后端：`GET /feedback/meta` 连同 `kinds` / `statuses` / `priorities` /
`visibilities` / `status_ladder` / `tabs` / `admin_tabs` / `hot_supports` 一起给
（`backend/app/api/routes/feedback.py`，实现的就是写稿时说的那一句）。前端只留**颜色**——
那是视觉决定；「有哪些取值」不在前端硬编码，因为加一个状态是后端改一处的事，而前端那张
常量表要靠发版才能跟上。原型注释抱怨的「加一个状态就要改三处，而漏掉的那处不会报错」，
因此不成立了。

## 3. 数据库迁移

### 3.1 本仓怎么迁移

机制在 `.claude/rules/migrations.md`，一句话：Alembic，`backend/alembic/versions/`，
**链必须始终恰好一个 head**。

- 当前 head = `d3f1a7c52e08`（`backend/alembic/versions/d3f1a7c52e08_push_subscription.py`），
  `backend/alembic/HEAD` 这个哨兵文件里写的也是它。这个哨兵文件的唯一用途，是让两个
  并发的迁移 PR **在 git 层冲突**（同一行 → CONFLICTING，GitHub 会持续重算），而不是在
  alembic 层静默分叉。历史上曾有三个「绿但过时」的 PR 把 main 分成了三个 head——
  那就是它存在的理由。
- 新迁移要做两件事：`down_revision` 指向当时的 head；**并且**把哨兵推进
  `echo <新 revision id> > backend/alembic/HEAD`。CI 的 `check-migration-fork.py` 与
  pre-commit 都会断言「哨兵 == 真实 tip」。
- 合并 main 之后要重查 `uv run alembic heads`；main 长了新迁移就把自己接到新 head 上，
  哨兵再推一次。
- **落在 main 上的迁移不可改、不可删**——已部署的库有它的 stamp，只能往前修。

### 3.2 新表怎么加

1. 写 `backend/app/domain/feedback/models.py`。
2. **在 `backend/app/models.py` 里加一行 import**（形如
   `from app.domain.feedback import models as feedback  # noqa: F401`）。这个文件是
   `alembic/env.py` 的 `target_metadata` 的来源，它的 docstring 原话是「Keep this list
   complete when adding a new model」，而 `env.py` 里那句更直白：「Without this,
   autogenerate would see an empty metadata and drop all tables.」
3. `uv run alembic revision --autogenerate -m "feedback"`（`docs/workflows.md` §1 的迁移一节）。
4. 手工审一遍生成的 `upgrade()`——autogenerate 不会替你写索引名、部分索引、CHECK 约束。
5. 推哨兵。

### 3.3 兼容已有部署

**好消息**：全是 `create_table`，没有 `alter_table`。

- 「给已有行加 NOT NULL 列要带 `server_default`」这条（`docs/workflows.md` §1）**用不上**，
  因为没有已有行。
- 循环外键（`projects↔topics`、`topics↔blocks`，`use_alter=True`）**用不上**——
  反馈只单向指向 `topics` / `projects`。
- 部署顺序：dev 是连续部署，**合并即发布**（`CLAUDE.md` 里那段关于 CI/CD 的说明）。
  新表 + 新路由，不存在「旧代码读到不存在的表」或「新代码读到旧表」，所以迁移与代码的
  先后天然安全。

**枚举的两种做法，新表选第二种。** 本仓有两族：

- 1.0（`comments` / `task` / `attachment`）：PG 原生枚举，`create_type=False`，
  类型由另一条迁移 `CREATE TYPE`；
- 2.0（`topics` / `alerts` / `blocks`）：`Enum(SomeEnum, native_enum=False, length=16)`，
  落成普通 `VARCHAR`。

**选 `native_enum=False`**，两个理由：

0. **枚举类的名字避开 `Visibility`**：`backend/app/domain/device/supply.py` 已经有一个
   同名的，撞的是 import，不是数据库。
1. **加一个值不用迁移。** 已核 `backend/alembic/versions/cf93e4735e4a_full_schema.py` 里
   `alerts.level` / `alerts.kind` 的 DDL —— 就是 `sa.Enum(..., native_enum=False,
   length=16)`，生成的是一列 `VARCHAR`，**没有 CHECK 约束**（本仓所有迁移里
   `create_constraint` 一次都没出现，`CheckConstraint` 只有 `machine_limit` 那两条是真正
   业务性的）。而反馈的状态集几乎肯定会动——§1.3 第 1 条就是证据。
2. `TopicStatus` 那条注释讲的是相反方向的教训：值一旦进了枚举就删不掉，
   「an enum that cannot read its own history turns a restore into a crash」。VARCHAR +
   应用层校验让历史值能被读出来。

**种子数据**：要不要把原型那 12 条落进 `backend/scripts/seed_fusion_demo.py`
（CI e2e 用的那个，见 `.claude/rules/e2e.md`）→ §8.14。

## 4. API

### 4.1 路由风格（照本仓既有）

`docs/api-conventions.md` 定的是寻址：

- 后端路由写**裸路径**，`/api` 是网关挂载点，**不在路由文件里出现**；
- **永不发尾斜杠**（`app.main` 建 app 时 `redirect_slashes=False`，且必须保持关闭——
  那段注释解释了为什么 `root_path` 修不了它）；
- 响应封套 `{code, message, data}`，用 `backend/app/api/response.py` 的 `ok()` / `page()`；
- 错误用 `backend/app/core/errors.py` 的类（`BadRequestError` / `NotFoundError` /
  `ForbiddenError` / `ConflictError` / `PreconditionFailedError`）。

路由文件：`backend/app/api/routes/feedback.py`，
`router = APIRouter(prefix="/feedback", tags=["feedback"])`。
`backend/app/main.py::_discover_routers` 用 `pkgutil.iter_modules` 扫这个目录、把每个模块
里**模块级**的 `APIRouter` 自动挂上。所以：一个模块一个 router，不要在一个文件里导出两个
（`_discover_routers` 支持多 router，但 `seen` 去重意味着顺序会决定语义）。

**`/feedback` 这个前缀今天是空的。** 后端 `backend/app/api/routes/` 下没有 feedback
（`grep -rni "feedback" backend/app/api/routes/` 只命中 `alerts.py` 的
`/alerts/{alert_id}/feedback`，前缀不同）；前端的三条是 vue-router 的路由，与后端无关。
`backend/tests/contract/test_api_addressing_contract.py` 会替我们守着这条（它的同类测试
正是为「两条路由悄悄抢同一个 URL」写的）。

**⚠️ 命名冲突（值得知道的坑）。** `feedback` 这个词在本仓**已经被占用了一半**：
`POST /alerts/{alert_id}/feedback`（`backend/app/api/routes/alerts.py`）指的是人对平台
主动消息的 👍/👎，落在 `Alert.feedback` 列上（值 `up` / `down`，见
`backend/app/domain/alert/models.py` 与其 service 里的 `_VALID_FEEDBACK`）。两条路由不撞，
但**词义会撞**：以后谁 `grep feedback` 会搜到另一件事。→ §8.11。

### 4.2 端点

#### 用户侧（登录即可）

**`GET /feedback`** — 反馈中心列表

- query：`tab`（`all` / `hot` / `active` / `resolved`）、`q`、`sort`（`new` / `supports`）、
  `page_start: int | None = Query(default=None)`、`page_size: int = Query(default=20, ge=1, le=100)`
  —— 参数名与约束照 `backend/app/api/routes/tags.py` 与 `comments.py`。
- 输出：`{ "items": [...], "page": {...}, "counts": {"all": n, "hot": n, "active": n, "resolved": n} }`
- **counts 必须一起返回**，不能分四次请求。Tab 上带数字（原型 `store.tabCounts`），四次
  请求会先渲染一排 0 再跳成真值——列表页最先出现的东西闪一下，读的人会以为数据错了。
- `hot` 的定义沿用原型：`supports >= 5` 且按支持数降序。**不按浏览量**——原型的注释
  给过理由（「浏览是路过，支持是表态」），我同意。
- 只返回 `visibility='public'`（§4.3）。

**`GET /feedback/{id}`** — 详情

- 输出：`FeedbackDetail` —— 卡片那一组字段 + `problem` / `why` / `expectation` /
  `what_happened` / `repro` / `evidence` / `logs` / `session_id` / `environment` /
  `topic_id` / `project_id` + `timeline[]` + `thread[]`（评论，层级见 §2.3）。
  **没有 `related`**（§8.2），管理端另加 `notes[]`。
- 不存在的 id **和**不可见的 id 都返回 `NotFoundError`，**不是 403**。理由：403 等于
  确认「存在一条你看不到的东西」，而私密反馈的存在性本身就是信息（种子里那条
  「我的会话记录里出现了别人的文件名」就是典型的「连存在都不该被知道」）。
- `related`：见 §7（建议 MVP 先不做）。

**`POST /feedback`** — 提交

- body（`FeedbackCreate`）：`kind`、`title`、`summary?`、`problem`、`why?`、
  `expectation?`、`visibility`、`tags[]`、以及现场那几项 `what_happened?` / `repro?` /
  `evidence?` / `logs?` / `session_id?` / `environment?` / `topic_id?` / `project_id?`。
  **落地的形状与写稿时的两处不同**：没有 `attachments[]`（附件整块不做）、也没有
  `attach_logs` 这个开关——前端勾了「附带日志」就直接把 `logs` / `session_id` /
  `environment` 三个字段填上，服务端不再猜一个布尔是什么意思。
- 输出：`{"id": "<uuid>", "display_no": 1042}`
- 错误：`BadRequestError`（title 空 / kind 非法 / visibility 非法）、
  `ForbiddenError`（`context.topic_id` 或 `session_id` 不是提交者能看到的，见 §2.2）、
  `NotFoundError`（`context.topic_id` 不存在）。
- **幂等性**：人的提交不做去重——本仓对这件事的判断写在
  `backend/app/domain/idempotency/keys.py` 的 docstring 里：「a human pressing a button
  twice means it twice」。agent 侧会重试（自动 resume），所以 **agent 的路径**才需要
  `Idempotency-Key`（走 `app/domain/idempotency/` 里的 claim，dedup window 恰好是
  「这件事和它的重试」）。
- 服务端生成、前端不该传的：`display_no`、`status`（恒为 `received`）、
  `author_handle`（来自 `Actor`，**绝不从 body 读**）、`author_is_agent`、`created_at`。
  「actor 在信任边界注入，永不从 body 读」是 `backend/app/domain/identity/actor.py`
  模块 docstring 的原话。

**`POST /feedback/{id}/supports`** / **`DELETE /feedback/{id}/supports`**

- **两个方法，不是一个 toggle。** 这是本稿里一个刻意的取舍：原型的 `toggleSupport` 是
  本地状态机，服务端 toggle 在重试/并发下会**翻回去**——而支持数进了排序（`hot` Tab），
  翻错一次就是排序错。POST / DELETE 各自幂等（重复 POST 不重复计，重复 DELETE 是 200）。
  形状上其实和 `BlockReaction` 的 toggle 相反，我选择不照它：表情重复点一下无害，
  支持数会进排序，两者的代价不一样。
- 错误：`PreconditionFailedError`（对 `resolved` 的反馈支持，**落地照做**：原型把按钮
  disable 了，服务端有对应的 412）。

**`GET /feedback/{id}/comments`** / **`POST /feedback/{id}/comments`** /
**`DELETE /feedback/comments/{comment_id}`**

- 形状照 `backend/app/api/routes/comments.py`（同一个作者只能删自己的）。
- 评论的 `author_handle` 同样来自 `Actor`。

#### 管理侧

**`GET /admin/feedback`** — 管理列表

- query：`tab`（`public` / `private` / `agent` / `security`）、`assignee`、`q`、分页。
- 独立一条而不是 `GET /feedback?scope=admin`：管理端的**口径**和用户端不一样
  （原型 `AdminFeedbackPage.vue` 顶部注释讲得很清楚——用户侧问「有没有人也遇到这个」，
  管理侧问「这一条现在该谁动」），把两种语义压进同一个端点的 query 参数里，迟早会有人
  从参数拼出一条它不该走的路。管理端返回的字段也不同（多出 `internal_notes`、
  `security`、`views`）。

**`GET /admin/feedback/{id}`** — 单条，带内部备注与上下文。

**`PATCH /admin/feedback/{id}`** — 改优先级 / 指派 / 安全标记

- body（`FeedbackPatch`）：`{"priority"?: ..., "assignee_handle"?: ..., "security"?: ...}`，
  可部分，`None` 一律解成「不动」。
- **`status` 不在这条 PATCH 上**，落地把它拆成 `POST /admin/feedback/{id}/status`
  （body `{"status": ...}`）。理由正是下面那条：改状态要在**同一个事务里**追加一行
  `feedback_timeline`（§2.3），而 PATCH 的其余字段都只是分诊信息，两者混在一个 body 里
  以后很难保证「带了 status 就一定写了时间线」。
- **不能改 `visibility`。** 原型明写「不给『私密转公开』的按钮——而且不是『先不做』，
  是不该做：公开与否是提交者当场做的决定，管理员能改它就等于那个决定是假的」
  （`AdminFeedbackDetailDrawer.vue` 文件头）。这条我建议**照抄进服务端**：不是不加
  端点，是在 service 层不提供这个方法，并在路由上不接这个字段。

**`POST /admin/feedback/{id}/notes`** — 追加一条内部备注。

#### 元数据

**`GET /feedback/meta`** — `STATUS_LADDER`、各枚举的中文标签、支持数与热门阈值。
（§2.5 末尾：把前端持有的那份顺序表搬到服务端，是接后端时该顺手做掉的事。）

### 4.3 权限模型

**这是全篇最需要说清楚的一节**，因为「谁能看私密反馈、谁能改状态」在本仓**没有现成的
答案**。

#### 本仓的鉴权是怎么做的

- **两族 token**（`.claude/rules/backend-tests.md` 第一条、`backend/app/auth/caller.py`
  的模块 docstring）：主干 access token 的 `sub` 是 int 用户 id，走
  `require_auth_user`（`backend/app/auth/checker.py`）；cheesex session token
  **只有 handle、没有 int id**（`user_id=None`），数字身份层会把它当访客。
  **同一个 header 在两类路由上行为不同**——这是本仓最贵的一个坑。
- **`ActorResolver`**（`backend/app/api/auth.py`）是两族都能认的那一层。
  `resolve()` 按顺序试：人类 bearer token → agent scoped token（`X-Cheese-Token`）→
  Phase-0 的 body handle 兜底。产出的 `Actor`（`backend/app/domain/identity/actor.py`）
  有个关键属性 `authenticated`：`via in ("token", "cheese")` 才是真凭据；兜底的 handle
  「描述作者身份，但不授予任何成员资格或角色」。
- **范围角色**：`ProjectRole`（lead/member）、`TopicRole`（owner/admin/member，
  `backend/app/domain/topic/models.py`）、团队 owner/admin、`SpaceAdminRelation`。
  策略函数住在 `backend/app/domain/authz/policy.py`。

**所以反馈路由要用 `ActorResolver`，不是 `require_auth_user`。** 这是本设计与
`comments.py` / `tags.py`（都用 `require_auth_user` + int id）**不一样**的地方，理由：
反馈是**平台级**功能，没有项目上下文，它的调用者天然落在 handle 那一族里——和
`topics` / `awaiting` 一样。`GET /awaiting-me`（`backend/app/api/routes/awaiting.py`）
是最贴近的先例：它也用 `resolver.resolve(fallback_handle=None)`，并且对访客返回空列表
而不是错误。

#### 「平台管理员」在写稿时不存在，于是新造了一个

这一点必须先说清楚，否则后面全是空中楼阁——**这些都是写稿时对着树查过的现状，也是
「为什么不复用现成的角色」的依据**：

- `SystemRole.SUPER_ADMIN` 在 `backend/app/auth/core.py` 里**定义了**，
  `backend/app/auth/checker.py` 的 `check_permission` 里**读了**它（命中就 `return True`）。
  但**生产路径上没有任何地方给它赋值**：`checker.py` 造 `AuthUserInfo` 的两处给的是
  `GUEST` 与 `USER`，全仓唯一造出 `SUPER_ADMIN` 的是单元测试
  （`backend/tests/unit/test_permission_checker.py`）。也就是说它是一条今天走不到的死路。
- `require_permission(action, resource, ...)` 那套（`PermissionConfig` / `PermissionRule`
  / `Role`）是 1.0 的框架，而且 `Resource` 枚举里**没有 FEEDBACK**，也没法加——它是
  1.0 的资源清单。
- 有的是：Space 的 managers、项目的 lead、话题的 owner/admin、团队 owner/admin。
  **全是有范围的角色**，没有一个「平台管理员」。
- **`/admin/*` 前缀今天不等于「管理员」。** `backend/app/api/routes/scheduler.py` 的
  `router = APIRouter(prefix="/admin/scheduler", tags=["scheduler"])` 下面三个端点
  （`/tick`、`/poll-open-prs`、`/sweep-abandoned-gates`）唯一的依赖是
  `Depends(get_scheduler_service)`，而那个依赖只注入服务、不鉴权——**无门**。想「新路由
  挂在 /admin 下所以有门」是错的。→ §8.1、§8.12。

**落地**：写稿时建议的「新增一个平台级角色，用配置里的 handle 白名单」照原样做了——
`settings.feedback_admin_handles: list[str] = []`（`backend/app/core/config.py:226`），
消费在 `backend/app/domain/feedback/services.py::_admin_handles`（`frozenset(...)`），
管理端每条端点先过 `service.require_admin(handle)`。形状照 `dogfood_owner_handles:
list[str] = []`（消费在
`backend/app/domain/agent/profiles.py` 里的 `frozenset(settings.dogfood_owner_handles)`）。
本仓还有一个更贴近的先例：项目设置里的 `branch_protection.override_handles`
（`backend/app/domain/project/protection.py`），那是一串 handle，**而且真的被当权限门用**
（`backend/app/domain/review/services.py` 里 `allowed = set(protection.override_handles)`）。
两个先例说明「一串 handle 当授权键」在这个仓库不是新发明；差别只在层级——那两个一个有
项目范围、一个是 agent profile，平台级还没有。

理由：它的失败模式最小。白名单在配置里，鉴权失败就是「不在名单里」，不依赖任何一张
可能为空的表；而「复用某个已有范围角色」的语义是错的——反馈说的是**平台本身**，
平台不属于任何一个 Space 或项目。

另外**不要**去把 `SystemRole.SUPER_ADMIN` 点亮：那条路要经过 `PermissionConfig`
那套 1.0 框架，而它没有 FEEDBACK 资源，硬塞就是动 1.0 的权限模型。

#### 私密反馈谁能看

**已定（2026-09-18）：提交者 + 平台管理员**（§8.0）。原型的定义是「只有管理员能看到」，
那被判定为 bug：提交者自己也看不到（`publicItems` 过滤 + 详情页挡板两处，见 §1.3 第 8 条）。
查询条件因此是：

```
visibility = 'public'
  OR author_handle = <我> OR submitted_by_handle = <我>
  OR <我是平台管理员>
```

两个 handle 都要算：agent 提案、人确认提交的那一类，这两个字段不同（§5.2）。

不论选哪个，服务端必须实现三件事：

1. 列表层的过滤（不能只靠前端不画）；
2. 详情层的过滤（直达链接也挡住）——原型注释自己写了「只靠列表不显示，等于谁把链接
   发出来谁就能看。真接后端时这一层应该在服务端」；
3. **404 而不是 403**（§4.2）。

#### agent 与人

- `Actor.is_agent` 是现成的字段（`backend/app/domain/identity/actor.py`，由
  `IdentityService.is_agent(handle)` 判定）。agent 提交的反馈
  `author_handle` = 它的 handle（`cheese` 或 `cheese-<话题hex>`，见
  `docs/topics/agent池方案.md`），`author_is_agent = True`。
- **管理动作 agent 不能做。** 这一条**不能**指望 `_CHEESE_WRITE_PATHS`
  （`backend/app/main.py`）：那张表是 agent 写面的**白名单**，不在表里的路径
  **不是被拦住，是压根不过那个中间件**。本仓已经实证过这一点，症状是**静默放行**而不是
  401。所以管理端点要在**路由内部**用 `ActorResolver` + `not actor.is_agent` 显式拒绝
  （照 `backend/app/domain/review/services.py` 里 `_forbid_ai` 那种两道的做法：不进白名单
  **并且** 在 service 层再挡一道）。
- agent 与人走**同一个** `Actor` 形状，服务不会 `if is_agent` 分叉——这是
  `backend/app/domain/identity/actor.py` 与 `authz/policy.py` 一起立的规矩
  （「Humans and agents resolve to the *same* `Actor` shape so domain services never
  branch on `if is_agent`」）。

### 4.4 管理后台：单独的一个网页，只有平台管理员进得去

需求方 2026-09-18 的原话：「管理员后台应该是单独的网页，仅平台管理员可见，反馈中心是全平台
共享一个」。后半句已经在 §8.10 落定，这一节回答前半句。

**先说实话：仓库里今天根本没有第二个站。**（以下每一条都核实过）

- `frontend/nginx.conf` 整个文件**只有一个 `server` 块**（`server_name localhost`，SPA 兜底
  `try_files ... /index.html`），没有 `/admin` location，没有第二个 server_name；
- `frontend/Dockerfile` 只 `COPY /app/dist` 一份到 `/usr/share/nginx/html`；
- `deploy/docker-compose.prod.yml` 只有一个 `frontend` 服务；
- `admin.okcheese.com` 这个名字在 `deploy/`、`ops/`、`.github/workflows/`、部署文档里
  **零命中**——它只活在注释与设计稿里。`frontend/src/router/feedback.ts` 自己写着：
  「真的拆成独立域名是运维/鉴权的事，不是这一轮要决定的事」。

所以「单独一个网页」有**三档做法**，代价差得很远：

| 档 | 形态 | 代价 | 判断 |
|---|---|---|---|
| 甲 | 同一个 SPA 里的一条路由（今天就是这样：`/admin/feedback`） | 零；门只在数据层 | 现状，但它**不是**「单独的网页」 |
| 乙 | 同一个构建产物的**第二个入口 HTML**（`admin.html`），nginx 加一个 location，共用同一个镜像 | 改 `vite.config` 的 `rollupOptions.input` + `nginx.conf` 加一段；Dockerfile 与 compose 都不用动 | **建议这一档** |
| 丙 | 独立域名 / 独立镜像 / 独立 server 块 | 要动 `deploy/` 的 compose、隧道配置与证书 | 不建议在这一轮做 |

乙档的理由：需求要的是**可见性上分开**——用户不该在反馈中心里看到一个自己进不去的入口，
管理员该有一个自己的界面。第二个 HTML 入口就达到这个效果，且不动部署编排；丙档多出来的收益
（换个域名）在这一轮没有对应的问题要解。

**这一轮停在甲档**：管理端还是同一个 SPA 里的一条路由，`/admin/feedback` 没有单独的 HTML
入口。「可见性上分开」是靠**界面自己不画那个入口**实现的——不是管理员的人看不到管理端的
链接，硬敲 URL 进去也只有一句说明和一条回反馈中心的链接（`AdminFeedbackPage.vue`）。乙档
没做，它不是被否掉，是还没到要动构建入口和 nginx 的时候。

**多入口不是安全边界。** 这一条值得单独写出来，因为本仓有现成的教训：
`backend/app/main.py` 的 `_CHEESE_WRITE_PATHS` 是「靠路径清单兜底」的写法，它的失败模式被
多处注释反复强调——**不在清单里的路径不是被拦住，是压根不过那个中间件**，症状是静默放行。
同理，「管理界面在另一个 HTML 里」不能作为任何一条数据的防线；防线只有一条，在服务端
（§4.3 那三条：列表过滤、详情过滤、404 而不是 403）。

**入口的另一半：前端今天没有任何路由守卫**（写稿时就是这样：`router.beforeEach` 只设页面
标题，「我是不是管理员」读的是 localStorage 里的 mock 值，那个文件自己写着「**不是**一道
权限门」）。落地时补的是两件，不是三件：

1. **「我是谁、我是不是管理员」由服务端回答**：`GET /feedback/meta` 顺带返回 `is_admin`
   （`backend/app/api/routes/feedback.py`），前端启动问一次。反馈中心据此决定画不画管理入口，
   管理页据它决定画界面还是画一句说明——这一条把 mock 角色整个换掉了。
2. **管理端点自己在服务端挡**（§4.3）。
3. **路由守卫仍然没加**：它不是防线，而这里没有要靠它守的东西——绕过去只会看到一句说明。
   真加的话，它守的是「别让人以为自己进错了地方」，那是体验，不是权限。

**管理台做成什么样**：落地就是写稿时建议的**一屏 + 一抽屉**
（`AdminFeedbackPage.vue` + `AdminFeedbackDetailDrawer.vue`）：列表四个 Tab（公开 / 私密 /
Agent 发现 / 安全问题），抽屉里改状态 / 优先级 / 指派 / 加备注。角色开关整块删掉了——它是
原型用来展示两套界面的，接权限后「我是不是管理员」由服务端回答，不是用户自己切。两处与
原型不同：指派是自由输入 handle（§8.9），管理端四栏不显示计数（§8.21）。

一处手工确认过的口径问题：**那四个 Tab 不是互斥划分**（`adminItems` 的实际条件见 §1.3）——
「Agent 发现」会把两条安全问题也算进去，「公开反馈」会把 Agent 提的公开条目算进去，
只有「私密」显式排除了 security。→ §8.21。

### 4.5 搜索：搜什么、怎么排、怎么翻页

需求方点名要打磨这一块（「比如搜索的实现」）。先给结论，再给依据。

#### 4.5.1 结论

| 问题 | 建议 |
|---|---|
| 机制 | `ILIKE`，**不用** PG 全文检索（理由见 4.5.2）。落地在 `repositories.py` 的两处 `or_(title.ilike, summary.ilike)` |
| 搜哪些字段 | `title`、`summary`。**`display_no` 没搜**——写稿时列了它，实现漏了；按编号找只能翻页（§8.2） |
| 排序 | **不按相关度**：命中后仍按当前 Tab 的既有排序（时间倒序 / 支持数倒序）。另：`hot` 不只是排序，它带一个「支持数 ≥ 5」的过滤（`HOT_SUPPORTS`），所以那个数字在服务端 |
| 分页 | `page_start` / `page_size`（默认 20，上限 100），响应是 `page()` 的 `{data, total}`——本仓既有的形状，**不是** `usePaging` 那个 `nextStart` |
| 大小写 | `ILIKE` 天然不区分 |
| 空结果 | 「暂无匹配的反馈」——原型已经把两种空态分开（有筛选 / 没筛选），保持 |
| 计数与搜索 | **落地改了口径**：`counts` 不带 `q`，四个 Tab 的数字永远是全部公开条目的分布。原型算的是「公开 ∩ 搜索」，实现选了更好算也更稳定的一半——代价是搜索时 Tab 上的数字不变，界面上不能把它读成「命中几条」 |
| 不做 | 高亮（`<mark>`）、拼写纠正、同义词、搜索历史。本仓都没有先例，反馈标题又很短 |

#### 4.5.2 为什么不用 PG 全文检索

**先核对事实**（§2.4 的更正说的就是这件事）：`backend/app` 下**有**全文检索——11 处
`tsvector`，在 `questions/repositories.py`、`tag/repositories.py`、`team/repositories.py`、
`team/recruitment_repositories.py` 四个文件里；`b1f2a3c4d5e6_add_fts_gin_indexes.py` 建了
`ix_question_fts` / `ix_tag_fts` / `ix_team_fts` 三个 GIN 索引。本仓的写法是「关键词 ≤ 2 字符
或没有词字符就退化成 ILIKE，其余走 FTS」，那个 `_use_fts` 判断被**复制了四份**，没有共享模块。

但反馈的搜索**不该抄它**，三条理由：

1. **它对中文基本不工作。** `'simple'` 字典把一整串汉字当一个 token，
   `plainto_tsquery('simple','搜索')` 匹配不到 `话题搜索功能`。反馈的标题和正文几乎全是中文，
   抄过来会「英文测试全绿、中文界面静默失效」——这是最难发现的一类错。
2. **它不做相关度排序。** 四个 FTS 路径都是拿 `@@` 当**布尔过滤**，然后 `order by created_at desc`。
   也就是说抄它不会让搜索「更聪明」，只是多了一个对中文失效的过滤器。
3. **GIN 索引要求表达式字符级对齐。** 迁移里 `to_tsvector` 的表达式必须和查询里的**逐字一致**
   才会被用上（`b1f2a3c4d5e6` 就是这么写的）。这是一条写错不报错的约束。

#### 4.5.3 如果以后要做得更好

从便宜到贵：

1. **给 `ILIKE` 建索引**：`ILIKE '%x%'` 用不上普通 B-tree，`pg_trgm` 的 GIN 可以。本仓**没有**
   用 `pg_trgm`（全仓零命中），所以这是一次新引入扩展，要先确认部署的 Postgres 版本与建扩展权限。
2. **中文分词**：本仓唯一处理过中文分词的地方是 `backend/app/domain/memory/keywords.py`
   （汉字切 bigram + 拉丁词，权重 2.0 / 1.0，配 `_CJK_STOPWORDS`），配合
   `domain/memory/store.py` 的候选集 + Python 侧覆盖率排序。它是「没有 Meilisearch 时唯一在树上
   真能用的中文相关度方案」，但排序在应用侧、候选集有上限，规模一大就散架。
3. **Meilisearch**：`domain/search/meilisearch_service.py` 是唯一有中文分词能力的层，但今天
   **只有 questions 在用，而且是半接通状态**——`setup_indices()` 只在集成测试里被调过、启动时
   从不调用；`delete_document` **零调用点**；`index_document` 只在 question **创建**时调，
   更新时没有。也就是说那个索引是「只增、不改、不删、生产上从没建过」。要用它得先补这三件事。

**结论：反馈搜索第一版不碰这三样。** 但值得在文档里留一条：将来嫌搜索不好时，**第一条该走的是
`pg_trgm`，不是 Meilisearch**。

#### 4.5.4 具体到实现

- **路由**：用户侧 `GET /feedback?q=&tab=&page_start=`；管理侧 `GET /admin/feedback?q=&tab=`。
  管理列表今天原型里**没有搜索框**，但接口要留着——反馈条数只会越来越多，没有搜索的管理台迟早要加。
- **归一化**：`q.strip()`；**空串等于不筛选**，不要把它当成「匹配所有」，否则计数会分叉。
- **单号要能被搜到** —— **没做**：用户可能输入 `FB-1042`、`fb-1042`、`fb1042`、`1042`，
  写稿时建议在服务端把 `display_no` 做一次「去前缀 + 大小写折叠」的比较（不新增列），
  实现里没有这一段，所以现在只能搜标题和摘要（§8.2）。
- **`tags` 先不搜**：原型是把 tags 当字符串数组做子串匹配。后端若把 tags 存 JSON 列（§8.8），
  搜它就是拿 `ILIKE` 打一段 JSON 文本——快，但会误命中（搜「安全」命中「信息安全」）。要搜得干净
  就得把 tags 拆成关联表。这件事和 §8.8 一起定，**第一版不搜**。
- **计数与搜索的交互**：落地是**两边都不跟**（`service.counts()` 不收 `q`）——用户侧四个 Tab
  的数字是全部公开条目的分布，管理侧的 `unassigned` 更是全库口径。所以管理端干脆不显示它们
  （§8.21），用户侧则要避免把数字读成「命中几条」。
- **要避免的先例**：`backend/app/api/routes/users.py` 那个搜索是**先分页再在 Python 里过滤**的
  写法——落在当前页之外的匹配永远看不见，`total` 也没算，循环里还 N+1 查用户。别抄。

### 4.6 逐屏字段契约：每块界面需要哪些字段

需求方要求「每个地方需要什么字段或信息」写清楚。写稿时三个界面 + 六个组件读的是
`frontend/src/lib/feedbackMock.ts` 的类型；接后端时，**每个屏幕渲染的字段就是它那个端点响应的
最小集**——多返回一列（比如把 `internal_note` 混进用户侧的响应）就是漏了 §4.3 的过滤。
下面按「屏幕 → 它真正渲染什么 → 由谁承载」列。

**落地与下面各表的差异**（字段名以 `backend/app/domain/feedback/schemas.py` 为准，下表保留
写稿时的叫法）：`FeedbackCard` / `FeedbackDetail` 就是那个最小集，具体是——
`source` → **`author_is_agent`**（布尔）、`support_count` → **`supports`**、
`comment_count` → **`comments`**、`comments[]` → **`thread[]`**（`FeedbackDetail` 上）、
`internal_note` → **`notes[]`**（append-only 列表，只出现在管理端响应里）、
`display_no` → **`display_id`**（`"FB-7"` 这种带前缀的字符串，**所有人**都拿得到——写稿时
以为只有管理员需要它，真做起来它是详情页的标题锚点）。
新增了写稿时没有的两个字段：`supported`（我支持没支持）与 `last_activity_at`（列表排序用）。
**`views` 与 `related` 都没有**，§4.6.2 右栏那两格因此**整格删掉**，不是显示 0。

#### 4.6.1 反馈中心（`FeedbackCenterPage.vue` + `FeedbackCard.vue`）

| 界面上的东西 | 字段 | 备注 |
|---|---|---|
| 4 个 Tab（全部 / 热门 / 处理中 / 已解决）的标签与**计数** | `{all, hot, active, resolved}` | **计数随搜索词变**（原型的口径是「publicItems ∩ 搜索」的基数），这是最容易抄漏的一条 → 见下 |
| 标题 | `title` | |
| 一句话摘要（限两行） | `summary` | 新条目由 `body` 首行截 60 字自动生成（§4.2），**不是用户填的** |
| 状态芯片 | `status` | 颜色与文案来自 `STATUS_META`，服务端给枚举值即可（§2.5） |
| 作者 + 相对时间 | `author_handle`、`created_at` | `created_at` 给 ISO，相对时间前端算 |
| 评论数 | `comment_count` | **聚合值**，别让列表页 N+1 拉评论（§2.4 已留索引） |
| 来源芯片（仅 Agent 发现时出现） | `source` | |
| 标签芯片 | `tags` | |
| 支持按钮：数字 + 我支持没支持 | `support_count`、`supported_by_me` | `supported_by_me` **每个读者不同**，任何缓存都要按人分 |
| 已解决时支持按钮禁用 | `status` | 前端规则：`status === 'resolved'` |

**两条口径必须在服务端定死**（否则两个 Tab 会各长各的）：

1. **计数随搜索变。** 原型的 `tabCounts` 是「公开条目 ∩ 搜索词」的基数，而管理页的
   `adminTabCounts` **完全不受搜索影响**（管理页没有搜索框）。同一个「计数」在两边语义不同，
   接后端要么给一个带 `q` 的计数端点，要么把 counts 塞进列表响应里（**建议后者**，少一次往返，
   且天然与列表同一个筛选）。
2. **热门 Tab 的口径**：`support_count >= 5` 且按 `support_count` 降序，**不按浏览量**
   （原型的注释写明了理由：浏览是路过、支持是表态）。这个阈值是页面口径，放服务端。

#### 4.6.2 反馈详情（`FeedbackDetailPage.vue`）

| 界面上的东西 | 字段 |
|---|---|

| 来源芯片（仅 agent） | `source` |
| 标签芯片 | `tags` |
| **单号（仅管理员可见）** | `display_no`（如 `FB-1042`）——**用户侧不该返回它**（原型的 `v-if role==='admin'`） |
| 作者 + 时间 | `author_handle`、`created_at` |
| 支持按钮 | `support_count`、`supported_by_me` |
| 问题描述 / 为什么需要 / 期望方案 | `problem`、`why`、`expectation`（后两者空就不渲染整段） |
| 现场三段（仅 agent 提案时有） | `what_happened`、`repro`、`evidence` |
| 评论区 | `comments[]`：`id`、`author_handle`、`author_is_agent`、`body`、`created_at` |
| 右栏：进展时间线 | `timeline[]`：`status`、`at`、`by_handle` |
| 右栏：三项统计 → **落地只剩两项** | `supports`、评论数——`views` 不做（§8.5），这一格**删掉了**，没有显示 0 |
| 右栏：相关反馈 → **落地没有这一栏** | 写稿时列了「最多 3 条」，实现不做（§8.2） |

**这里有一处今天就不对的地方**（原型的缺口，值得在契约里点破）：**详情页不渲染
`priority`、`assignee`、`visibility`、`internal_note`、`logs`、`session_id`、`environment`
这七个字段**，而管理抽屉全都渲染。也就是说「管理员在用户侧详情页看一条私密反馈」时，他看到的是
用户视角——原型只在列表层用 `role` 分了岔。真做起来建议：**管理端一律走 `/admin/feedback/{id}`**，
用户侧的 `GET /feedback/{id}` 永远只返回上表里那些字段（不靠前端 `v-if` 遮）。

**相关反馈怎么算**：原型是「同 tag 重合数 > 0，按 (重合数 desc, support_count desc) 取前 3，
且只在公开条目里找」。**分页之后前端就算不了了**（它只能看见当前页），所以要么给一个
`GET /feedback/{id}/related`，要么接受「相关反馈只看当前页」并在界面上别把它说成「相关」。
落地选了第三条：**这一栏不做**，前端把它整块删掉了（§8.2）。

## 5. agent 侧

### 5.0 参照物：cc 的 Claude-drafted feedback（工具名 `SendFeedback`）

需求方点名要看 cc 的最新做法（「Agent 如何实现主动反馈，这里我觉得应该参考 cc 最新的设计」）。
查证结果：cc 里确实有一套 **agent 自己发起**的反馈机制，v2.1.238+ 引入，工具名 `SendFeedback`，
官方文档在 `code.claude.com/docs/en/tools-reference` 里单列一节 `SendFeedback tool behavior`。
它和用户手动敲的 `/bug`、`/feedback` 汇入同一条提交管道，区别只在**谁当作者**：agent 只产出一份
**草稿**排进本地队列，**真正的提交权 100% 在人手里**。

它的形状（§5.4–§5.8 逐条对照）：

| | cc 的做法 | 出处 |
|---|---|---|
| agent 的产出 | 排一份 draft 进本地队列，**不出网、不打断对话**（文档原文「renders no UI and does not interrupt the conversation」，且不许 agent 中途宣布这件事） | tools-reference |
| 人看到的 | 输入框上方一张卡片：`1` 审阅 / `2` 原样发送 / `0` 忽略 | commands |
| 忽略的语义 | **不是删除**，草稿仍在队列里，`/feedback` 能翻出来 | commands |
| 打扰预算 | 默认每会话最多露 3 张卡；上限**服务端可热调、不用发版**；超限时只在输入框 footer 显示「队列里有 N 份」计数 | settings-reference |
| 队列 | 容量 10（跨会话，挤掉最旧的）；草稿 30 天过期；`/exit` 时若有草稿会问怎么处理 | settings-reference |
| 收敛 | 忽略卡片后会问要不要整体关掉这个功能，**用户拒绝两次就不再问** | tools-reference |
| 开关 | `feedbackDrafts` 是**字符串枚举 `notify` / `quiet` / `off`**（不是 boolean）；scope 是 `User or managed`，**管理员设置压过用户自己的设置** | settings-reference |
| 能力边界 | 非交互 `-p`、Agent SDK、云会话**一律不注入**这个工具，理由写得很直白：「which have no screen to review the queue on」 | tools-reference |
| 组织级 | ZDR 组织直接不注入；宁可让工具「不存在」，也不做「发了再删」 | tools-reference / data-usage |

它比我们原型今天那张卡在**一件事上更保守**：原型里「提交反馈」按一下就把三段现场递进抽屉、预填
好了，人接着按抽屉里的「提交」；cc 是**两步都要人做**——先审阅草稿、再决定发。方向一致（人批准
agent 的东西），但「审阅」这一步在原型里是缺的（§5.8）。

### 5.1 `AgentFeedbackCard` 在聊天里出现意味着什么

它已经在树上了：`frontend/src/views/workspace/TopicChatColumn.vue` 渲染
`<AgentFeedbackCard :topic-id="topic.id" />`。写稿时它没有 props、finding 是写死的默认值，
**行为是真的**；接上后端之后 finding 从服务端来（`GET /topics/{id}/feedback-proposals`），
哪一张出现、哪一张已经不用了，都由服务端说了算（配额 + 指纹去重 + 拒绝记忆，§5.3）。

它解决的问题写在文件头：**上下文会丢**。所以这张卡自己带着三段现场，点提交时一并递进
抽屉。三颗按钮的排布也已经在注释里论证过（「不用」必须和「提交反馈」一样容易点到）。

真做起来，缺的只有一件事：**finding 从哪来**。两条路：

- **(a) agent 主动调工具**：芝士在轮次里判断「这更像平台问题而不是使用方式」，调一个
  `cheese_feedback_propose`，卡是平台渲染这个调用结果。→ **建议这条。**
  它正是 `backend/sandbox/skills/cheese/SKILL.md` 描述的既有形状——「你做完一个平台动作
  （记决策/改文档/钉里程碑…），平台会自动在对话里显示一张可点的卡片」，SKILL.md 里连
  措辞都定好了（agent 不要再用文字旁白「已记录」）。
- **(b) 平台从轮次流里推断**：不可行。`docs/what-the-agent-perceives.md` 讲的就是这个
  方向的边界（平台收得到什么、收不到什么），而 `docs/spec.md` §14.5 那条「平台不猜
  语义」是直接相关的行为规范。

### 5.2 谁批准它变成一条正式反馈

**人按「提交」那一刻。** 这条原型已经定好了，实现照抄并且**在数据上记了下来**：

- `author_handle` = 芝士（发现者）、`author_is_agent = true`；
- `submitted_by_handle` = 按下按钮的那个人。

**两个字段都要，不能合并成一个。** 合起来就答不出「芝士提的反馈里有多少真的被人发出去
了」——而那正是判断「要不要继续让芝士提、提多少」的唯一依据。这也不是新发明的形状：
验收卡上就有类似的「谁提的 / 谁采纳的」两分。

**agent 不能自己把它变成公开反馈。** 提案是提案，提交是提交。这条既是产品判断
（原型三颗按钮的排布就是在说「这是一张问一句的卡，不是一条已经发出去的东西」），
也是安全判断（没有它，一个跑歪的 agent 可以直接往公开列表里灌东西）。

### 5.3 如何避免刷屏

四道，从便宜到贵：

1. **平台侧配额。** `alerts` 那套已经有现成的分级限流（`docs/product-impl.md` §3.7：
   每话题每天 ≤2 轻 / 每周 ≤1 强，`AlertRepository.over_quota`）。反馈提案卡照
   同一形状限流：**每个话题每天最多 2 张提案卡**
   （`settings.feedback_proposals_per_topic_per_day`，默认 2，可配置）。理由直接引那一段：
   决策/验收请求不被限流丢弃是因为「有人在等」，而提案卡没有人在等，它可以被丢。
   三道限流（配额 / 指纹 / 记忆）触发时都回 **412** 并说明是哪一道。
2. **指纹去重。** 同一 `what_happened` + `repro` 归一化后的指纹，合并成一张卡。
   形状照 `backend/app/domain/notification/dedup.py` 的 `NotificationDeduplicator`
   （Redis，带 TTL），或者落一列 `proposal_fingerprint` 加唯一索引。
3. **拒绝要有记忆——这一条最重要。** 原型的「不用」只把组件内 `state` 置成
   `dismissed`（`AgentFeedbackCard.vue`），刷新就回来。实现落了
   `feedback_proposal_dismissals` 一行（谁、什么时候、哪个指纹不用了），否则**同一个问题
   每轮都会再问一遍**，这是刷屏最主要的来源，而且它会让人对整张卡产生免疫。前端的
   `dismiss()` 只做即时收起，去重由服务端按指纹说了算。
4. **agent 只能提案。** 见 5.2。

量级参照可以取 cc 那套：每会话露 3 张、队列 10 份、30 天过期、「拒绝两次就不再问」——它们和我们
的话题级配额（每天 ≤2）是同一个数量级，可以互相印证，不必重新发明。

### 5.4 触发时机：芝士什么时候才该提

cc 的系统提示词给了四个时机，可以直译：**（1）某个工具或命令反复失败；（2）它做不到用户要求的
事；（3）用户指出它犯了错，或者它自己发现犯了错；（4）用户让它提。** 官方文档的版本更短：「a tool
or command keeps failing / it can't help with something you asked for / you point out a mistake it
made, or it notices one / you ask it to file feedback」。

**关键在第三条被写成「或它自己发现」**——不必等有人抱怨才有资格提。cc 的训练里还专门列了「自我
观察到的行为失误」清单（先给自信答案又收回、明明能做却半途甩回给用户、拒绝了合理请求、spawn 了
超过任务所需的 subagent 数量、语气不对、澄清问题问太多、超出授权范围扩大改动）。这组清单能直接
映射到 §5.6 那条支线。

要在我们的语境里落地，还要加一条 cc 没有的判据：**芝士必须先确认「这不是用户的使用方式问题」**。
原型那张卡的标题就是这句话，方向是对的——它是「平台坏了」与「用户不会用」之间的分界线。

**明确不该提的**：一轮任务失败但不影响别人（用户自己重试就好）、用户已经知道的事、能从文档里
查到答案的事。理由和 §5.3 第 4 条同源——提案卡没有人在等，它可以被丢。

### 5.5 草稿长什么样：固定骨架 + 「谁说的」必须自证

cc 的 `details` 字段格式是**固定顺序、每项 1–3 行短标签 bullet、明令不许写叙事段落**：

1. **What happened** —— 观察到的 vs 期望的；错误原文短就照抄。**只写事实。**
2. **What the user said** —— 引用用户原话；**没有，就写死一句「User didn't comment; observed by
   the model」**。
3. **Repro** —— 能复现它的最小步骤 / 形态。
4. **Evidence** —— 可追溯的标识符（request id、时间戳、文件路径、版本）；没有就省略。
5. **（可选）Cause** —— **只有在会话内验证过根因时才允许加这条**。

其余结构化字段：`area`（涉及产品的哪一部分，如 "hooks config"、"/help"；不清楚就留空）、
`failure_mode`（**只用于模型行为报告**，纯产品 bug 省略）、`task_category`。

第 2 条是整套设计里最值得抄的一条：**它把「用户说的」和「模型自己观察到的」硬性分开，没有用户
原话就必须写死那句模板**。这是防 agent 编造用户情绪最直接的一道闸——不是靠提示词祈祷它诚实，
而是给它一个「必须填」的位置，且这个位置有一个规定好的、诚实的填法。同一条纪律还有一句更狠的
（出自 cc 给 agent 的起草规则）：**"Everything must be sourced from the user or the session, never
inferred"** —— 不知道的字段**留空**，不许猜。第 5 条同理：`Cause` 有条件才填，就是为了防模型
乱猜根因。

对我们的落法：原型那张卡今天的四段（判断依据 / 发生了什么 / 复现步骤 / 证据）与 cc 是同构的，
但**缺第 2 条的位置**。真接后端时卡片上应该有一行「用户说过什么」，且允许它诚实地写「用户没有就
这个问题说过话；以上是芝士自己观察到的」。**建议不为它单开一列**（cc 也没开，它是把这句话写进
正文的）——一个几乎总是空的列不值得一条迁移，把这个位置做成卡片上的一行文案即可。

### 5.6 要不要给「模型行为问题」分一条支线

cc 把「工具坏了」和「agent 行为不对」拆成两个不同的 issue 模板：`[BUG]`（label `bug`）与
`[MODEL]`（label `model`），后者开篇就声明**不适用于崩溃、API 错误、安装问题**。`model_behavior.yml`
的字段可以直接借：`behavior_type` 九选一（未请求的编辑 / 访问工作目录之外 / 无视指令或配置 /
回退了改动 / 错误假设 / 拒绝 / 会话间漂移 / subagent 问题 / 其他）、`what_you_asked` /
`what_claude_did` / `expected_behavior`、`files_affected`（**分「改了哪些」与「意外读了哪些」**）、
`permission_mode`、`reproducible`、`conversation_log`、`impact`（Critical 数据丢失损坏 / High /
Medium / Low）、`model` / `version` / `platform`。

对我们的建议：**原型今天只有一个 `kind`（bug / suggestion / other），没有这条支线。** 要不要加
取决于这个反馈中心是给谁看的——「芝士这次干得不对」和「平台端点没门禁」是两类不同的东西，看的人
不同、处理路径不同（前者可能改提示词或改工具，后者是改代码）。**建议加，但不开成第二个 `kind`
值**，而是一个独立的维度（就叫 cc 那个词 `failure_mode`），因为两者正交：「芝士越权改了文件」既可
能是 bug（工具没拦住），也可能是建议（该加一道确认）。列入 §8.18。

### 5.7 脱敏：规则要写进 system prompt，不能只靠事后打码

cc 的脱敏是分层的：本地草稿不出网；`/bug` / `/feedback` 发送前有 consent 屏、且让用户选历史范围
（当前会话 / 同项目近 24 小时 / 近 7 天）；草稿审阅屏里 `Send transcript` 默认 yes 但可关；
**从卡片一键发送永不带转录，要带转录必须进更重的审阅屏**（「快捷路径更保守」是刻意的）；上传前对
已知 API key / token 模式打码；工作目录只存本地用来定位转录、不发送。

但最要紧的一层是 **cc 把脱敏规则写进了 agent 的 system prompt**，而不只放在服务端事后打码：

- 不许编造或夸大用户情绪；
- 不许出现 secrets / credentials；
- **提及个人一律用角色**（「a teammate」「the PR reviewer」），**绝不写姓名 / 邮箱 / user id——
  包括在引用用户原话时，也要把名字替换成方括号角色**；
- 允许作为证据的：session / request / run id、时间戳、repo / PR 编号、相对路径或 `~` 开头的路径；
- **安全漏洞只描述问题类别，绝不写可用的 exploit 或提取步骤**；
- 排除客户侧渠道 id、DM id、客户内容片段。

而 cc 对边界说得很老实：官方文档承认 **"Source code, file contents, and other conversation content
are uploaded as-is"** —— 脱敏只打已知的 key/token 模式，**不碰代码内容**。这不是含糊其辞，是明确
声明。我们如果要收会话日志，必须同样明确地把这条边界写出来，否则「附带当前会话的日志与环境信息」
那个勾选框，在用户眼里等于一次不可预期的全文上传。

对我们的直接后果两条：

1. `§2.2` 的 `logs` / `session_id` / `environment` 是**同一批要脱敏的东西**，且作者是 agent、审阅人
   是用户——**脱敏必须发生在 agent 写草稿的那一刻**，落库前再补救已经晚了（自然语言里写进去的
   人名和凭据，事后打码打不掉）。这就是为什么脱敏规则要进 `cheese_feedback_propose` 的工具说明，
   而不是只写在后端。
2. 我们的反馈**默认是公开的**（原型 `SubmitFeedbackDrawer` 的默认 `visibility = public`），这比 cc
   危险得多：cc 的反馈只发给 Anthropic，我们的会挂在平台上给所有登录用户看。所以「安全漏洞只写
   类别」在这儿不是礼貌，是硬要求。原型那条风险提示（`v-alert type=warning`，只在选了附件或日志
   时出现）**认得这件事，但没覆盖正文**——正文里写了一段复现步骤、贴了堆栈，一样会公开。这条要
   在提交前再拦一次（列入 §8.19）。

### 5.8 落成什么形状

按 §5.1 的结论走 (a)，具体形状：

- **工具名**：`cheese_feedback_propose`，接进 `backend/sandbox/skills/cheese/SKILL.md` 那一套
  （「你做完一个平台动作，平台会自动在对话里显示一张可点的卡片」，措辞照旧，agent 不要再用文字
  旁白说「已提了一张反馈卡」）。
- **入参**：`title` / `area` / `details`（§5.5 那五段骨架）/ `kind` / `failure_mode?` /
  `task_category?`。**不含 `visibility`**——可见范围是提交者的决定，不是 agent 的。
- **平台侧**：不直接写 `feedback` 表。**落成的不是一张 `feedback_proposal` 表，而是
  一条 `kind=message` 的 `Block`**（载荷在 `meta.feedback_proposal`，`domain/feedback/proposals.py`），
  原因见 §8.1 末尾：提案的寿命和对话流一样长，**采纳**就是在这块上 accept，
  **拒绝记忆**才是那张单独的 `feedback_proposal_dismissals`（带指纹）。限流见 §5.3。
- **人侧**：卡片上「采纳」进去的那一屏 = `SubmitFeedbackDrawer` 预填（**提交按钮只在这里**）。
  写稿时担心的那件事（卡片上写「提交反馈」、抽屉里又叫一次「提交」，容易让人以为卡片那一下
  已经发出去了）落地时用措辞解决了：卡片上那颗按钮叫**采纳**，抽屉里那颗才叫提交。卡片上
  最显眼的一行是**「你当时说的」**（§5.5 第 2 条的位置），点开抽屉时整段现场已经预填好，
  可见性也预填进去了（§8.19）。
- **能力边界**：照 cc 的判据——**没有屏幕可以审阅的会话不给这个工具**。我们的场景里对应的是无人的
  自动巡检轮次：巡检里发现的平台问题走 `alerts`（平台报告自己），不走反馈提案。这条判据比按权限切
  干净，因为它问的不是「你能不能」，而是「当场有没有人能完成审批」。

### 5.9 这个工具怎么落到三个 harness 上（不用写三遍）

需求里那句「每个不同的 harness 都要有能主动提反馈的渠道」，在本仓的架构下有一个很短的答案：**加一个叶子命令就行。** 三个 harness 取的是同一份东西——平台 CLI 的 argparse 树，不是三套各自维护的工具定义。

三条路，各自的出处：

- **claude_code**：会话里的 MCP 服务器把 `cli {method: "tools/list"}` 发给 executor
  （`backend/app/domain/agent/harness/claude_code/remote_execution/client.py:721`），
  executor 那侧由 `cli_worker` 把 argparse 树转成工具 schema
  （`backend/app/domain/agent/cli_worker.py:177`）。
- **pi**：pi 没有 MCP。`harness/pi/catalog.py` 直接读**这台机器上装着的那个 CLI**
  （`CLI = "cheese"`、`shutil.which`），`harness/pi/runner.py:165` 把读到的 `tools`
  写进 extension spec，`harness/pi/platform.ts` 的 `registerPlatformTools` 再把每个
  注册成 pi 自己的原生工具，调用时 shell 出去执行对应子命令。
- **codex**：`harness/codex/tools.py` 从 executor 的 `native` 服务器和其余 MCP 服务器发现
  工具；平台自己的工具随它那份 CLI 一起来，走的还是同一个 `cli_worker`。

三条路都指向 `backend/sandbox/cheese` 里那份 `build_parser()`
（`add_subparsers(dest="cmd", required=True)` 在 `backend/sandbox/cheese:809`）。
所以 `cheese feedback propose` 加在那一棵树里，三个 harness 同时就有了——**没有任何一处
代码是「为 pi 加的」或「为 codex 加的」**。

几点在实现时值得照着做，都是上面这条链的直接后果：

- **工具名是算出来的，不是起的。** `cli_worker._tool_name` 把命令路径拼成
  `cheese_` + 下划线连接，所以 `feedback propose` 必然叫 `cheese_feedback_propose`。
  想改名只能改命令名。
- **`help=` 就是工具 schema。** `cli_worker._schema()` 把每个参数的 `help` 当
  `description`，叶子 parser 的 `help` 当工具描述。写进 argparse 的措辞直接就是模型看到的
  那一份——文档和实现是同一处，不存在写两遍然后漂移。同理：`choices=` 会变成 `enum`，
  `type=uuid.UUID` 变成 `format: uuid`，`--dry-run` 这类开关变成 `boolean`。
- **没话题的轮次自己就提不了。** `cheese feedback propose` 和 `cheese chat send` 一样要
  `CHEESE_TOPIC`，`_need()` 缺了直接退出——这就是实现里那条「无屏巡检轮次不给这个工具」，
  没有另外写一个「按 harness 裁剪工具清单」的机制（那机制今天也不存在，pi 的清单是启动时
  读一次的）：**门在服务端，不在工具清单上**。
- **上线要按「机器上那份 CLI 换新」来想。** CLI 是 bind-mount 进容器的，
  `cheese --version` 打印的源码指纹就是用来发现 mount 陈旧的。已经在跑的会话不会中途长出
  这个工具，下一次起会话才有。灰度的观察点也是现成的：executor 每次列清单都会往 stderr 打
  `[cheese] native tools/list: N platform tools`（`client.py` 里那句），N 涨了就是到了。
- **和 `cheese ask` 的分工要说清，否则 agent 会用错。** 要人**当场拍板**用 `cheese ask`
  （按钮回到下一轮，阻塞）；要**提交一条反馈**用 `cheese feedback propose`（落
  `feedback_proposal`，人在聊天里的卡片上决定，不阻塞）。两者都是「agent 举手、人决定」，
  区别只在要不要等这一轮。

## 6. 通知与未读

### 6.1 本仓有两套「通知」，别搞混

`docs/product-impl.md` §3.7 和 `backend/app/domain/alert/models.py` 的 docstring
都在讲这件事，后者讲得最清楚：

| | `alerts` | `notification` |
|---|---|---|
| 表 | `alerts`（uuid PK，`backend/app/domain/alert/models.py`） | `notification`（BigInteger + `Sequence`，`backend/app/domain/notification/models.py`） |
| 是什么 | **平台在报告自己**：哪台机器掉了、哪一轮失败了、哪个话题在等人 | **一个人告诉另一个人**：提及、回复、表情（社交 feed） |
| 路由 | `/projects/{id}/alerts`、`/projects/{id}/inbox`、`/alerts/{id}/{read,feedback,resolve}`（`backend/app/api/routes/alerts.py`） | `/notifications`（`backend/app/api/routes/notifications_flat.py`） |
| 分级 | `silent` / `light` / `strong` + 限流 | 无 |

**写稿时打算让反馈进前者**（`alerts`）：`Alert` 有 `target_handle`、`payload`、
`read_at`、`resolved_at`，形状对得上，做法是给 `AlertKind` 加两个值
（`feedback_reply`、`feedback_status`，加值不用迁移——`AlertKind` 落的是 `VARCHAR(16)`
且没有 CHECK，§3.3 已核；注意 `decision_request` 正好 16 个字符，新值不能超过 16）。

**实现没有走这条路。** 原因是下一节那条不匹配，代价落到了无法接受的一侧；结果是 `alerts`
一个字都没改，反馈自己的未读走 `feedback_read_states`。

### 6.2 但 `alerts` 挂在项目上，反馈没有项目

**这是本设计遇到的最硬的一处不匹配。** 已核：
`backend/alembic/versions/cf93e4735e4a_full_schema.py` 里
`sa.Column("project_id", sa.Uuid(), nullable=False)`，
`ForeignKeyConstraint(..., ondelete="CASCADE")`。而原型的路由注释明写「反馈说的是平台
本身，跟我在哪个项目里没有关系」。

三条路：

- **(a) 放开 `alerts.project_id` 为 nullable。** 要改一张在用的表，并且所有读它的查询
  都要能被 NULL 正确过滤。`alerts` 是整个收件箱语义的根（`/projects/{id}/inbox`、
  `docs/product-impl.md` §3.7 的拍板流程），动它的风险不成比例。
- **(b) 反馈不进 `alerts`，未读单独做。** 照 `TopicReadState`
  （`backend/app/domain/topic/models.py`）那个 **cursor** 形状——它的 docstring 解释了
  为什么是 cursor 而不是逐条已读表：「cheap to bump, cheap to count against」。
  反馈这一侧可以是 `(user_handle, last_read_at)` 一条/人 的全局 cursor，或者
  `feedback_read_states(feedback_id, user_handle, last_read_at)`。
- **(c) 只复用投递渠道。** `backend/app/domain/notification/publisher.py` 的
  `RedisEmailQueueNotificationHandler` / `RedisPushQueueNotificationHandler`
  是无状态的队列写入，跟 `alerts` 表没有耦合，可以直接用。

**落地的是 (b)，没要 (c)**：不动 `alerts.project_id NOT NULL`，未读走 `feedback_read_states`
——一人一条 `last_read_at` 的全局 cursor（`UniqueConstraint(user_handle)`），
`GET /feedback/counts` 读它、`POST /feedback/read` 推它。投递队列（邮件/推送）这一轮
**没接**：「我的反馈有没有新动静」只在平台内回答，不发信。

### 6.3 「我的反馈有新进展」到底是事件流还是当前状态

这个问题值得单独想，因为本仓刚为同类问题做过一次选择。

`frontend/src/views/InboxView.vue` 的注释记录了那次选择：`/inbox`「待办」**曾经**接的是
顶栏铃铛那份通知数据（提及与回复），后来改接了 `GET /awaiting-me`
（`backend/app/api/routes/awaiting.py`），理由是「通知是一条条事件记录，答不出『现在还没
处理完的有哪些』：一张验收卡被驳回之后，它那条通知还在」。

`awaiting.py` 的模块 docstring 更直接：它解释了为什么这件事不能由通知表拼出来。

**反馈的「有新进展」更像哪一类？** 我倾向**两边都要，但语义不同**：

- **铃铛**（事件流）：「你提交的反馈收到了一条回复」「状态变成了处理中」——这些是
  **发生过的**事情，读掉就完了。
- **待办**（当前状态）：提案卡等一个「发还是不发」→ 这个**该进 `/awaiting-me`**。
  它和验收卡是同一类东西：一件在等你动手、动完就从清单上消失的事。

**实现只落了「当前状态」那一半，而且比它更轻**：没有事件流（§6.4），未读就是那个 cursor
——「我提的 / 指给我的反馈里，有比这个时间新的动静」。提案卡**没有**进 `/awaiting-me`：
它就在对话流里，点或不点当场就能做，而收件箱是「离开这一屏之后还记得要办的事」；
`AwaitingItem['reason']` 因此还是那三个值（`reviewer` / `reporter` / `asked`）。

### 6.4 谁收到通知

**这一轮没有做事件通知**：没有给 `AlertKind` 加值，没有发信，也没有「被回复了」这种
一条条的事件记录。写稿时想好的收件人是——提交者（`submitted_by_handle`，没有它时退到
`author_handle`）与被指派的人；要真做，就是照着这两条去写。仍然不做的一条是
**「支持数到 5 时通知提交者」**：它会把「支持数」变成一个可以被人为推动的运营数字
（§8.6 是同一个问题的另一半）。→ §8.6。

  检查的是「源码调用的键都能解析」和「目录里没有没人用的键」，**不扫硬编码字符串**。
  所以反馈这几页和另外 99 个视图一样是硬编码中文，闸门是绿的。**落地照办，没迁**（§8.16）。

### 明确「先不做」

| 项 | 理由 |
|---|---|
| 附件真上传 | 原型的验收标准就是「只做 UI」，MVP 保持一致（§8.7 定了再说） |

## 8. 风险与开放问题

**这一节在写稿时是「不定下来就没法开工」的清单。实现替其中大部分作了答**：§8.1 是答案
和它的落点，§8.2 是仍然开着的。小标题沿用写稿时的编号，所以正文里那些 `→ §8.x` 的指针
指的仍是这里对应的那一条。

### 8.0 需求方答复（2026-09-18）

- **私密反馈，提交者能看见自己提交的。**（原 ★8.2 关闭）→ §4.3
- **反馈中心是平台共享的，不以组织（Space）为单位。**（原 ★8.10 关闭）→ §4.3、§8.1
- **默认不展示已解决的 bug。**（原 8.23）→ §8.1

### 8.1 实现已经回答掉的

**★ 8.1 平台管理员是谁。** 已定：配置里的 handle 白名单
`settings.feedback_admin_handles`（`backend/app/core/config.py`，默认空 = 除提交者自己
没人能看私密条目），消费在 `domain/feedback/services.py::_admin_handles`，形状就是当时建议的
那一条。三个管理端点（列表 / 单条 / PATCH / 状态 / 备注）先过 `service.require_admin`，
**凭据没通过鉴权、handle 不在名单里，都是拒**。

**★ 8.3 `security` 与 `visibility` 的关系。** 已定：`security` 是 `private` 之下的
**读时收窄**，不写数据库 CHECK。落在 `services.visible_to`：一条 `security` 的公开条目，
读路径按私密处理。不写约束的理由：它管的是「读的时候按什么口径放行」，而不是「这条记录在
库里长得不一样」；一旦写成 `CHECK (NOT security OR visibility = 'private')`，管理员把
安全标记撤掉这件事就会变成一个 500，而撤回标记是正常操作。

**8.4 状态集。** 已定：五个值照原型；「已解决」与「已上线」**不拆**（`resolved` 一步到
位）；`feedback_timeline` 纯 append-only，**允许回退再推进**——回退就是再记一条，
时间线回答的是「到过这里几次」，不是「最后一次是什么时候改回来的」。改状态与追加时间线
在同一个 service 方法、同一个事务里发生，路由不暴露直接写 `status` 的入口。

**8.5 浏览量 `views`。** 不做。前端已经把那一栏删掉了，服务端没有这个字段。

**8.6 支持数会不会被刷。** 照 `BlockReaction`：一人一票的唯一约束**就是**全部防线，
不另做防刷。这是决定，不是没想到。另加一条原型没有的拒绝：对 `resolved` 的反馈支持，
服务端回 412（原型是把按钮 disable 了，服务端要有对应的拒绝）。

**8.7 附件走哪条路。** 这一轮不做。服务端**没有**字段、没有表、没有路由——不是「存了不
发」，是压根没有这条路径；原型里那个「只记文件名」的字段也没有落库。前端把附件按钮画成灰的
并写明原因。这样「私密反馈的附件不能被公开 URL 读到」那条硬约束这一轮不需要答卷。

**8.8 标签。** 主表一个 JSON 列（`Feedback.tags`，`default=list`），不建 `feedback_tags`
关联表，不做标签筛选。

**8.9 指派给谁。** 管理端是**自由输入 handle**（不是下拉）：平台级的页面拿不到任何项目或
机构的成员名册，能拉出来的名单都会是错的。空值 = 取消指派。被指派的人**不会**因此获得管理
权限——改状态仍然只认白名单，这是 §4.3 的权限模型没有被指派功能撬动的地方。

**8.10 可见范围。** 平台共享。列表查询里**没有** Space / 项目维度，`topic_id` /
`project_id` 只是出处指针（`SET NULL`），不做行级过滤。「公开」= 对所有登录用户公开。

**8.11 命名冲突。** 新的这套在文档和界面上一律叫「反馈」；`/alerts/{alert_id}/feedback`
（消息的 👍/👎）没动，改字段名有迁移成本且与本功能无关。

**8.12 `/admin/*` 前缀不等于「管理员」。** 实现里没有任何一处依赖前缀：`/api/admin/feedback`
的每条端点在**路由内部**过 `require_admin`。也不依赖 `_CHEESE_WRITE_PATHS` 那张表——它是
agent 写面的白名单，不在表里的路径**不是被拦住，是压根不过那个中间件**（症状是静默放行），
所以芝士的凭据在这里是被白名单本身挡住的，而不是被中间件挡住的。

**8.13 e2e 与前端测试。** `backend/tests/integration/test_feedback.py` 覆盖了「提交 →
自己看得到 / 别人看不到」「私密对无权者是 404 而不是 403」「已解决的 bug 沉底」「提案的
配额与指纹去重」这些；前端这一轮是组件测试 + 现有门禁，**没有新增 e2e spec**（原型的三条
前端路由第一次进 CI 时才会有）。

**8.14 种子数据。** 不落进 `backend/scripts/seed_fusion_demo.py`。当时那条顾虑仍然成立：
原型种子里两条 `security: true` 的条目，`evidence` 直接点名本仓真实文件与端点，照抄进演示
数据等于把一段断言写进种子。

**8.15 删除与撤回。** 仍然没做：`deleted_at` 列留着，但没有任何端点会写它。见 §8.2。

**8.16 i18n。** 不做。理由照写稿时那条：覆盖面问题（哪些界面必须双语）没定之前，单迁一个
功能只会让这几个文件在仓库里显得和别人不一样。

**8.18 「模型行为问题」独立维度。** 不做。这一轮只有 `kind`（bug / suggestion / other），
没有 `failure_mode`。见 §8.2。

**8.19 提交前的敏感内容提示 / Agent 卡上的可见范围。** (b) 做了：Agent 提案卡把
`visibility` 一起预填进提交抽屉，人在抽屉里看得见这条会落在公开还是私密——可见范围始终是
**提交的人**的决定，agent 的入参里没有这个字段。(a) 没做：正文没有单独的敏感内容提示，
仍然只有原型那条「选了附件或日志时出现」的警告。

**8.20 管理端要不要有回复 / 评论。** 现在是「管理抽屉里只有内部备注（append-only 的
`feedback_notes`），公开回复由管理员以普通身份去详情页评论」——**没有** `is_internal` 列，
也不存在「以管理员身份回复」这种区分。见 §8.2。

**8.21 管理列表四个 Tab 的口径。** 维持原口径（**不是**互斥划分），四条 query 在服务端
定死：`agent` 只看来源、`public` 只看可见性、只有 `private` 显式排除 `security`。管理端
不显示计数——服务端返回的 `counts` 是**公开栏位**的口径（`all/hot/active/resolved`），拿来
当管理端四栏的数字会误导。

**8.23 默认不展示已解决的 bug。** 已定：只隐藏 `kind = 'bug' AND status = 'resolved'`，
**已解决的建议照常显示**（`repositories.py` 的默认筛选）。前端不自己发明口径，它只是不传
「包含已解决」这个开关。

**提案卡不是一张表。** 写稿时建议的 `feedback_proposal` 表**没有建**：一张提案卡就是一条
`kind=message` 的 `Block`，载荷在 `meta.feedback_proposal` 里（`domain/feedback/proposals.py`）。
「这块卡有没有被采纳」由块上的一次 accept 回答，「不用」的记忆落在单独一张
`feedback_proposal_dismissals`（按指纹）。这样提案的生命周期跟着对话流走，不需要给一条
几小时后就没人看的记录单独维护状态机。

**未读。** 走 `feedback_read_states`（一人一条 cursor，`last_read_at`），**不动**
`alerts.project_id NOT NULL`，也没接邮件/推送队列（§6.2 的 (b) 采纳、(c) 没采纳）。

**配额。** `settings.feedback_proposals_per_topic_per_day`（默认 2），三道限流（配额 /
指纹去重 / 拒绝记忆）不满时都回 **412** 并说明是三道里的哪一道——不是 429，因为它不是
「请求太多」，是「这条现在不该发出去」。

**前端 API 层。** 没有另开 `frontend/src/network/api/feedback/`：反馈后端就是 cheesex
后端（`/api` 前缀），客户端沿用既有的 `src/api.ts` + `src/cx_types.ts`，与工作台其余部分
同一套。

### 8.2 仍然开着的

- **附件真上传**：服务端字段与私密附件的读路径都没设计，前端按钮在等它（§8.7）。
- **按单号搜索**（§4.5.4）：`q` 只打 `title` / `summary`，`FB-7` 搜不到。
- **Tab 计数与搜索解耦**（§4.5.1）：搜索时四个 Tab 的数字不变，界面上要避免让人读成
  「命中几条」。
- **删除 / 撤回**（§8.15）：`deleted_at` 没人写。
- **`failure_mode` 维度**（§8.18）：没有做，所以「芝士这次干得不对」与「平台坏了」在数据
  里还是同一类。
- **管理端公开回复**（§8.20）：做不到「以管理员身份回复」的区分。
- **反馈变成一件活**（§7 后续）：状态集的形状为它留了余地（append-only 时间线、`resolved`
  之后还能回退），但没有做。
- **与 GitHub issue 的关系**：不同步。要同步（比如「被采纳的反馈自动开一个 issue」）是
  独立的一次决定。

## 9. 与现有系统重叠：复用、绕开、避开

| | 对象 | 判断 |
|---|---|---|
| ✅ 直接复用 | `app/api/response.py` 的 `ok()` / `page()` | 封套 |
| ✅ | `app/core/errors.py` | 错误类与状态码 |
| ✅ | `ActorResolver`（`app/api/auth.py`） | 两族 token 的识别 |
| ✅ | `Actor.is_agent`（`domain/identity/actor.py`） | 人/agent 的区分 |
| ✅ | `UuidPk` / `Timestamps`（`domain/common.py`） | 模型 mixin |
| ❌ 没用上 | `publisher.py` 的两个队列 handler | 反馈不发信（§6.2） |
| ✅ | `BlockReaction` 的唯一约束**形状** | 一人一票（§2.3） |
| ❌ 没用上 | `idempotency/` 的 claim | 提案的去重改用指纹（§5.3），没有走幂等键 |
| ✅ | `Sequence` 取展示号（`task_seq` / `notification_seq`） | `display_no`（§2.2） |
| ✅ | `topic_read_states` 的 cursor **形状** | 未读（§6.2b） |
| ❌ 没用上 | `AlertKind` | `alerts` 一个字没改（§6.1、§6.4） |
| ✅ | `settings.dogfood_owner_handles` 的**形状** | 管理员白名单（§4.3） |
| ❌ 绕开 | `alerts.project_id NOT NULL` | 反馈不进 `alerts`，未读自己一张 cursor 表（§6.2） |
| ❌ 不复用 | 1.0 的 `comment` 表 | 多态 + int 主键（§2.3） |
| ❌ | `blocks`（「万物皆块」） | 见下 |
| ❌ | `tag` 表 | 主表一个 JSON 列（§8.8） |
| ❌ | `/admin/scheduler` 的「无门」现状 | 不是可以照抄的先例（§8.12） |

**为什么不用 `blocks` 装反馈。** 「万物皆块」（`docs/spec.md` §5）理论上什么都装得下，
但 `Block` 有 `project_id`（NOT NULL，`backend/app/domain/block/models.py`），它的读写
鉴权走 `authorize_topic`（`backend/app/api/auth.py`）。用 block 装反馈会强迫**每一条反馈
挂在某个项目上**——而原型从路由注释开始就在说反馈不属于任何项目。这是本设计里最值得
写下来的一条「看起来能复用、其实不能」的判断。

**与 GitHub issue 的关系。** `CLAUDE.md` 里写着「**The design that is still being
argued lives in issues**」——issues 承载的是**开发团队自己的**设计争论。反馈承载的是
**产品用户**对产品的意见。两者受众不同、生命周期不同（issue 会关掉，反馈会被「解决」
然后成为可查的历史）。建议**不同步**；要同步的话（比如「被采纳的反馈自动开一个 issue」）
是独立的一次决定。
