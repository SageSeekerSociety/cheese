## 0. 一句话

把 PR #1222 那个纯前端反馈原型（mock 数据 + localStorage 里的 mock 角色）落成真功能：
一组 `feedback_*` 表、一组裸路径 REST（`/feedback`）、一套以 handle 为键的鉴权、
以及 agent 在对话里提案、由人按一下才成立的提交路径。

### 1.3 原型的自相矛盾与缺口（不是挑刺，是必须在这里定掉的）

1. **状态集对不上。** `feedbackMock.ts` 顶部注释自己写着：需求里状态列了 5 个、
   Timeline 写了 4 步（「已收录 → 评估中 → 计划中 → **已上线**」）。原型统一成 5 步
   并把「已解决 / 已上线是否拆开」明确留给了本轮。→ §8.4。
2. **`views` 有字段没有来源。** 整个原型里没有任何一处给 `views` 加一，种子里直接写死
   412 / 305 / …。真做起来要么一张浏览记录表，要么一个计数器，两个都有人刷的问题。
   → §8.5。
3. **`supports` 与 `supportedByMe` 是两个字段，服务端必须拆表。** 原型注释解释得对
   （「每条只算一次，靠 supportedByMe 记」），但那句只说对了 UI 那一半——服务端若只存
   一个计数器，取消支持就是 `-1`，任何人都能把它减成负数。
4. **`tags: string[]` 与仓库现有的 `tag` 表对不上。** 本仓有 `/tags`
   （`backend/app/api/routes/tags.py`、`backend/app/domain/tag/models.py`），而且那张表的
   `name` **没有**唯一约束。「标签去重」没有现成实现。→ §8.8。
5. **附件只记名字。** `draft.attachments: string[]`，注释与验收标准都写着「只做 UI、
   不真的上传」。真做起来要决定走 1.0 的 `attachment` 表还是新开。→ §8.7。
6. **`internalNote` 是一个字符串。** 两个管理员先后写，后写的把先写的盖掉，且没有
   「谁、什么时候」。做成 append-only 的行更贵一点，但不会丢东西。→ §2.3。
7. **`security` 与 `visibility` 正交但实际蕴含。** 种子里两条 `security: true` 的条目
   `visibility` 都是 `private`，而管理后台把「安全问题」做成**与「私密反馈」并列的独立
   一栏**（`adminItems` 的 `private` 分支显式 `&& !i.security`）。所以它更像 `private`
   之下的一个子类。→ §8.3。
8. **私密反馈，提交者自己也看不到。** `publicItems` 把私密条目整个滤掉，
   `FeedbackDetailPage.vue` 的挡板是 `visibility === 'private' && store.role !== 'admin'`。
   一个用户提交了私密反馈，然后自己在列表里找不到它、点直达链接被挡。**需求方已定：
   提交者可以看见自己提交的私密反馈**（§8.0），所以原型这一处要改。
9. **`source: 'agent'` 与「谁提交的」被合并了。** `store.submit()` 里
   `source: draft.fromAgent ? 'agent' : 'user'` —— 人按的按钮，来源记成 agent。这个语义
   是对的（「这是谁发现的问题」），但它丢掉了「谁把它发出去的」。→ §5。
10. **角色开关必须整块删掉。** 原型注释自己写了「真到了接后端那一步，这个字段就该被
    删掉，权限判断回到服务端」。本文按这句话设计。
11. **`assignee` 的来源是写死的。** `ASSIGNEES = ['andylizf', 'n1ctheboy', 'ligan',
    'maxiaoyu', 'chiruotong']`——开发团队的 handle。真做起来这个列表从哪来是个独立问题。
    → §8.9。
12. **列表层过滤 + 详情页挡板，原型自己在注释里说「真接后端时这一层应该在服务端」。**
    照做（§4）。
13. **`related`（相关反馈）是全量算的。** `store.related` 遍历所有公开反馈按标签重合度
    打分。客户端要这么算就得先把全部公开反馈拉下来，服务端算则是另一个查询。→ §7。

## 2. 领域模型：表与字段

### 2.1 放哪

新开一个 domain 模块，照 `backend/app/domain/comments/` 的形状（`models.py` /
`repositories.py` / `services.py`，按需再加 `schemas.py`）：

```
backend/app/domain/feedback/
├── __init__.py
├── models.py
├── repositories.py
├── services.py
└── schemas.py
```

为什么是新模块而不是塞进已有的某个：本仓的分层是 Route → Service → Repository → Model，
**按领域分目录**（`docs/product-impl.md` §4）。反馈既不属话题、也不属评论、也不属通知，
它有自己的状态机和自己的两个受众（用户侧 / 管理侧）。塞进 `comments` 会让那个模块同时
服务两种主键类型（见 §2.3）。

### 2.2 主表 `feedback`

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | `Uuid` PK | 走 `UuidPk`（`backend/app/domain/common.py`） |
| `display_no` | `Integer` + `Sequence("feedback_seq")` | 展示号，`FB-1042` 就是这个 |
| `title` | `String(300)` | 与 `Alert.title` / `Topic.title` 同长度档位 |
| `summary` | `String(300)` | 列表里那一句；原型是正文首行截 60 字 |
| `kind` | `Enum(native_enum=False, length=16)` | `bug` / `suggestion` / `other` |
| `status` | `Enum(native_enum=False, length=16)` | 五个值，见 §2.5 |
| `visibility` | `Enum(native_enum=False, length=16)` | `public` / `private` |
| `priority` | `Enum(native_enum=False, length=16)` | `low` / `normal` / `high` / `urgent` |
| `security` | `Boolean, default false, server_default "false"` | 见 §8.3 |
| `problem` / `why` / `expectation` | `Text` | 提交者/agent 写的内容 |
| `what_happened` / `repro` / `evidence` | `Text, nullable` | agent 发现的现场三段 |
| `logs` | `Text, nullable` | 「附带当前会话的日志与环境信息」勾上时的快照 |
| `session_id` | `String(64), nullable` | **快照，不是外键**（见下） |
| `environment` | `String(255), nullable` | 快照 |
| `author_handle` | `String(64), index` | 发现者；agent 时是它的 handle |
| `author_user_id` | `Integer, nullable` | 有 int id 时冗余存一份，供 join/统计 |
| `author_is_agent` | `Boolean, default false` | 对应原型 `source`；由 `Actor.is_agent` 填 |
| `submitted_by_handle` | `String(64), nullable` | 「谁按下提交的」，agent 提案时是人 |
| `submitted_by_user_id` | `Integer, nullable` | 同上 |
| `assignee_handle` | `String(64), nullable, index` | 指派 |
| `topic_id` | `Uuid FK(topics.id, ondelete="SET NULL"), nullable` | 上下文指针 |
| `project_id` | `Uuid FK(projects.id, ondelete="SET NULL"), nullable` | 上下文指针 |
| `created_at` / `updated_at` | `Timestamps` | `backend/app/domain/common.py` |
| `deleted_at` | `DateTime(timezone=True), nullable` | 软删，照 `Comment.deleted_at` |

**为什么主键是 uuid、展示号另开一列。** 原型的 `FB-<max+1>`（`store.submit()` 里
现算）是原型里唯一能让详情页 URL 有意义的办法。真做起来，人类编号在并发提交下必须唯一，
而 uuid 天生不需要协调。两件事分开：`id` 是键，`display_no` 是人读的。
取号的形状照 `task_seq` / `notification_seq`（`backend/app/domain/task/models.py` 顶部、
`backend/app/domain/notification/models.py`），即 PG Sequence —— 不是在应用层 `max()+1`。

**为什么作者是 handle 而不是 int 外键。** 本仓有两族 token，只有一族带 int id
（`.claude/rules/backend-tests.md` 第一条、`backend/app/auth/caller.py` 的模块 docstring
把这件事讲得最清楚）。handle 是**唯一两族都有的键**，也是全平台唯一在用的授权键。说清楚一点：handle 是
**2.0 那一族的约定**，1.0 族今天仍然是 int 外键（`Comment.created_by_id`、
`Notification.receiver_id`、`AgentBinding.user_id`）——反馈属于前者。另外这些列名是
**新的**：现有表里没有任何一列叫 `author_handle` 或 `submitted_by_*`，对齐的是形状
而不是命名
（`backend/app/api/auth.py` 的注释：「Every authorization key in the platform is the
handle STRING」）。写 `String(64)` 也是既有约定：`TopicMembership.member_handle`、
`TopicReadState.user_handle`、`Alert.target_handle`、`BlockReaction.author` 全是字符串列。

**哪些字段是冗余快照、不是外键——这是本设计最重要的一条判断。**

`session_id` / `environment` / `logs` / `what_happened` / `repro` / `evidence` 全部是
**提交那一刻的字符串快照**。三者的理由**不一样**，分开写：

- `environment` / `logs` 是**没有表可引**：环境是 `Topic.environment` 这个 JSON 列
  （`backend/app/domain/topic/models.py`，由 `project_environment(project.settings)`
  生成并 pin），日志只有 pydantic intake 与内存里的 burst 判定
  （`backend/app/domain/{frontend,backend}_log.py`），没有 `Base`、没有表名。快照是唯一
  可行的形态。
- `session_id` 是**有表，仍然选择快照**。`agent_sessions`
  （`backend/app/domain/agent_session/models.py`）是一条 uuid 行，键是
  `(topic_id, task_id, agent_handle, harness)`，而 harness 自己那个会话 id 落在
  `resume_token` 上——那列的注释明写它是不透明串、不得解析。也就是说今天没有一张表能
  回答「`sess_7c21a4` 是哪一行」，把 `agent_sessions.id` 存进来回答的是另一个问题。
  再加上会话会被归档、机器会退（`docs/where-a-turn-runs.md` 讲的就是这件事）：一条指向
  会话的外键会在会话没了之后让这条反馈读不出东西——**而那是这条反馈唯一的证据**。
- 同一个道理在本仓已经说过两遍：`TopicProgress` 的 docstring（「a turn that dies
  mid-flight must not take the progress with it」）和 `Block` 上那段关于
  `consumed_turn` 的注释（运行时事实不能从别处反推）。

`topic_id` / `project_id` 是可以有的，但它们是**「跳回去看」的指针**，
`ondelete="SET NULL"`，不参与鉴权也不参与渲染。

**提交时仍然要校验上下文。** 快照不等于不检查：如果提交者带了 `session_id` / `topic_id`，
服务端要在**写入时**确认这个会话/话题是提交者能看到的（用 `ActorResolver` 的
`authorize_topic` / `can_access_topic`，`backend/app/api/auth.py`），否则一条反馈可以变成
窥探别人会话的入口。校验通过后存快照，之后不再复验。

### 2.3 子表

**`feedback_supports`** —— 一人一票。

| 列 | 说明 |
|---|---|
| `feedback_id` FK CASCADE, index | |
| `author_handle` `String(64)`, index | |
| `created_at` | |

唯一约束 `(feedback_id, author_handle)`。形状直接照 `BlockReaction`
（`backend/app/domain/block/models.py`）——那张表就是
`UniqueConstraint("block_id", "emoji", "author", name="uq_block_reaction")`，做的正是
「同一个人不重复表一次态」。**借的是形状，不是表**：表情是挂在 block 上的，我们的支持
挂在 feedback 上。

计数：原型列表按支持数排序（`hot` Tab），也按它显示数字。两种做法：

- 每次 `count(*)` 聚合 —— 列表页 N+1，但数据永远对；
- 主表加冗余列 `supports_count`，在**同一个事务里**随 insert/delete 维护。

建议前者（MVP，列表分页 20 条，一个 `GROUP BY` 就完了），把后者留到真慢了再说。理由：
冗余计数器是本仓没有先例的东西（`BlockReaction` 就没有计数列，`comments` 的
`count_votes` 是实时聚合的，见 `backend/app/domain/comments/services.py`）。

**`feedback_comments`**

`(id, feedback_id FK CASCADE, author_handle, author_user_id, author_is_agent, body,
created_at, deleted_at)`，索引 `(feedback_id, created_at)`。

**不复用 1.0 的 `comment` 表**（`backend/app/domain/comments/models.py`）：它靠
`(commentable_type, commentable_id)` 多态，而 `commentable_id` 是 `Integer`。我们的主键是
uuid。要用它就得扩 `CommentableType` 枚举**并且**把 `commentable_id` 改成 uuid 或加一列
—— 那条路上还躺着一个 PG 原生枚举（`create_type=False`，类型本身由另一条迁移建）。
为一个新功能去动 1.0 评论表的主键，是把风险放错了地方。

**`feedback_timeline`**

`(id, feedback_id FK CASCADE, status, at, by_handle)`，索引 `(feedback_id, at)`。
**状态与时间线是两份数据，且必须一起写。**

原型已经踩过这个坑，注释原话：「只改状态不写时间线，右侧那根 Timeline 就会和卡片上的
状态词对不上」（`stores/feedback.ts::setStatus`）。服务端的做法是把这件事从路由层收走：
`status` 是当前值，`feedback_timeline` 是 append-only 的事件流，**改状态与追加事件只在
同一个 service 方法里发生、同一个事务里提交**，路由不暴露任何直接写 `status` 的入口。

时间线里同一状态可能出现两次（回退再推进）。原型的读法是对的并写在了注释里
（前端时间线组件沿用的是「取**最早**那一次，因为时间线记的是什么时候到过这里，不是最后
一次是什么时候改回来的」）。这个读法在服务端不成立——有两条记录就是两条，它回答「到过
这里几次」。要不要保留回退语义，→ §8.4。

**`feedback_notes`**（内部备注）

`(id, feedback_id FK CASCADE, author_handle, body Text, created_at)`，append-only。
主表**不存** `internal_note` 字符串列。理由见 §1.3 第 6 条：一个字符串列在两个管理员
之间会互相覆盖，且留不下作者和时间。UI 上仍然渲染成「一条备注」没有问题——取最新那条。

**`feedback_attachments`**

`(id, feedback_id FK CASCADE, name, url, size, mime_type, created_at)`。
走哪张表 / 怎么存，→ §8.7。**有一个硬要求先写在这里**：私密反馈的附件必须不能被一个
公开 URL 读到，否则「私密」是假的。

**`feedback_tags`** —— 本稿**不建**，见 §8.8。MVP 建议在主表上加一个
`tags: JSON` 列（`default=list`），与原型一一对应，筛选先不做。
本仓用 JSON 列装结构化小数据的先例很多：`Alert.payload`、`TopicProgress.items`、
`Block.meta`。

### 2.4 索引

按查询倒推。四个真实查询：

1. 公开列表（`visibility='public'`，按状态/时间过滤，按时间或支持数排）
   → `(visibility, status, created_at desc)`，再按需 `(visibility, created_at desc)`
2. 管理端四栏（公开 / 私密非安全 / agent 来源 / 安全）
   → `(visibility, security, created_at desc)`；`author_is_agent` 单独一个
   部分索引 `WHERE author_is_agent`（agent 发起的反馈是少数）
3. 「我的反馈」→ `(author_handle, created_at desc)`、`(submitted_by_handle, created_at desc)`
4. 未读（§6）→ 在未读那张表上，主表不用管

子表各一个 `(feedback_id, ...)` 索引。加一条：`feedback(assignee_handle)` 部分索引
`WHERE assignee_handle IS NOT NULL`——「指派给我的」是管理端最常见的入口之一。

**搜索**：MVP 用 `ILIKE`（对 `title` / `summary` / `display_no`），与原型 `matches()`
匹配的四段（id / title / summary / tags）一一对应。**中文没有词边界，PG 的
`to_tsvector` 对中文默认分词基本等于不工作**，本仓也没有任何全文检索的先例
（grep `tsvector` 在 `backend/` 下为空）。这是一次**有意的退化**，不是忘了。

### 2.5 状态集

`received → triaging → planned → in_progress → resolved`，五个值，取原型的
`STATUS_LADDER` 原样（连字符串都不换，`received` 而不是 `new`）。理由：前端已经有
`STATUS_META` 的颜色表和 `STATUS_LADDER` 的顺序表，换词就要同时改前端两张表和
i18n 目录，收益为零。

梯子的**顺序**要不要进后端？建议进：`STATUS_LADDER` 现在住在前端的
`feedbackMock.ts` 里，Timeline 读它、Tab 读它、管理抽屉的下拉读它。接后端之后它应该
由服务端给（一个 `GET /feedback/meta` 或直接写在列表响应里），否则加一个状态就要改
三处前端文件——那正是原型注释在抱怨的事（「那样加一个状态就要改三处，而漏掉的那处
不会报错」）。MVP 可以先让前端继续持有，但把它记成一个**技术债**而不是设计。

## 3. 数据库迁移

### 3.1 本仓怎么迁移

机制在 `.claude/rules/migrations.md`，一句话：Alembic，`backend/alembic/versions/`，
**链必须始终恰好一个 head**。

- 当前 head = `d3f1a7c52e08`（`backend/alembic/versions/d3f1a7c52e08_push_subscription.py`），
  `backend/alembic/HEAD` 这个哨兵文件里写的也是它。这个哨兵文件的唯一用途，是让两个
  并发的迁移 PR **在 git 层冲突**（同一行 → CONFLICTING，GitHub 会持续重算），而不是在
  alembic 层静默分叉。历史上曾有三个「绿但过时」的 PR 把 main 分成了三个 head——
  那就是它存在的理由。
- 新迁移要做两件事：`down_revision` 指向当时的 head；**并且**把哨兵推进
  `echo <新 revision id> > backend/alembic/HEAD`。CI 的 `check-migration-fork.py` 与
  pre-commit 都会断言「哨兵 == 真实 tip」。
- 合并 main 之后要重查 `uv run alembic heads`；main 长了新迁移就把自己接到新 head 上，
  哨兵再推一次。
- **落在 main 上的迁移不可改、不可删**——已部署的库有它的 stamp，只能往前修。

### 3.2 新表怎么加

1. 写 `backend/app/domain/feedback/models.py`。
2. **在 `backend/app/models.py` 里加一行 import**（形如
   `from app.domain.feedback import models as feedback  # noqa: F401`）。这个文件是
   `alembic/env.py` 的 `target_metadata` 的来源，它的 docstring 原话是「Keep this list
   complete when adding a new model」，而 `env.py` 里那句更直白：「Without this,
   autogenerate would see an empty metadata and drop all tables.」
3. `uv run alembic revision --autogenerate -m "feedback"`（`docs/workflows.md` §1 的迁移一节）。
4. 手工审一遍生成的 `upgrade()`——autogenerate 不会替你写索引名、部分索引、CHECK 约束。
5. 推哨兵。

### 3.3 兼容已有部署

**好消息**：全是 `create_table`，没有 `alter_table`。

- 「给已有行加 NOT NULL 列要带 `server_default`」这条（`docs/workflows.md` §1）**用不上**，
  因为没有已有行。
- 循环外键（`projects↔topics`、`topics↔blocks`，`use_alter=True`）**用不上**——
  反馈只单向指向 `topics` / `projects`。
- 部署顺序：dev 是连续部署，**合并即发布**（`CLAUDE.md` 里那段关于 CI/CD 的说明）。
  新表 + 新路由，不存在「旧代码读到不存在的表」或「新代码读到旧表」，所以迁移与代码的
  先后天然安全。

**枚举的两种做法，新表选第二种。** 本仓有两族：

- 1.0（`comments` / `task` / `attachment`）：PG 原生枚举，`create_type=False`，
  类型由另一条迁移 `CREATE TYPE`；
- 2.0（`topics` / `alerts` / `blocks`）：`Enum(SomeEnum, native_enum=False, length=16)`，
  落成普通 `VARCHAR`。

**选 `native_enum=False`**，两个理由：

0. **枚举类的名字避开 `Visibility`**：`backend/app/domain/device/supply.py` 已经有一个
   同名的，撞的是 import，不是数据库。
1. **加一个值不用迁移。** 已核 `backend/alembic/versions/cf93e4735e4a_full_schema.py` 里
   `alerts.level` / `alerts.kind` 的 DDL —— 就是 `sa.Enum(..., native_enum=False,
   length=16)`，生成的是一列 `VARCHAR`，**没有 CHECK 约束**（本仓所有迁移里
   `create_constraint` 一次都没出现，`CheckConstraint` 只有 `machine_limit` 那两条是真正
   业务性的）。而反馈的状态集几乎肯定会动——§1.3 第 1 条就是证据。
2. `TopicStatus` 那条注释讲的是相反方向的教训：值一旦进了枚举就删不掉，
   「an enum that cannot read its own history turns a restore into a crash」。VARCHAR +
   应用层校验让历史值能被读出来。

**种子数据**：要不要把原型那 12 条落进 `backend/scripts/seed_fusion_demo.py`
（CI e2e 用的那个，见 `.claude/rules/e2e.md`）→ §8.14。

## 4. API

### 4.1 路由风格（照本仓既有）

`docs/api-conventions.md` 定的是寻址：

- 后端路由写**裸路径**，`/api` 是网关挂载点，**不在路由文件里出现**；
- **永不发尾斜杠**（`app.main` 建 app 时 `redirect_slashes=False`，且必须保持关闭——
  那段注释解释了为什么 `root_path` 修不了它）；
- 响应封套 `{code, message, data}`，用 `backend/app/api/response.py` 的 `ok()` / `page()`；
- 错误用 `backend/app/core/errors.py` 的类（`BadRequestError` / `NotFoundError` /
  `ForbiddenError` / `ConflictError` / `PreconditionFailedError`）。

路由文件：`backend/app/api/routes/feedback.py`，
`router = APIRouter(prefix="/feedback", tags=["feedback"])`。
`backend/app/main.py::_discover_routers` 用 `pkgutil.iter_modules` 扫这个目录、把每个模块
里**模块级**的 `APIRouter` 自动挂上。所以：一个模块一个 router，不要在一个文件里导出两个
（`_discover_routers` 支持多 router，但 `seen` 去重意味着顺序会决定语义）。

**`/feedback` 这个前缀今天是空的。** 后端 `backend/app/api/routes/` 下没有 feedback
（`grep -rni "feedback" backend/app/api/routes/` 只命中 `alerts.py` 的
`/alerts/{alert_id}/feedback`，前缀不同）；前端的三条是 vue-router 的路由，与后端无关。
`backend/tests/contract/test_api_addressing_contract.py` 会替我们守着这条（它的同类测试
正是为「两条路由悄悄抢同一个 URL」写的）。

**⚠️ 命名冲突（值得知道的坑）。** `feedback` 这个词在本仓**已经被占用了一半**：
`POST /alerts/{alert_id}/feedback`（`backend/app/api/routes/alerts.py`）指的是人对平台
主动消息的 👍/👎，落在 `Alert.feedback` 列上（值 `up` / `down`，见
`backend/app/domain/alert/models.py` 与其 service 里的 `_VALID_FEEDBACK`）。两条路由不撞，
但**词义会撞**：以后谁 `grep feedback` 会搜到另一件事。→ §8.11。

### 4.2 端点

#### 用户侧（登录即可）

**`GET /feedback`** — 反馈中心列表

- query：`tab`（`all` / `hot` / `active` / `resolved`）、`q`、`sort`（`new` / `supports`）、
  `page_start: int | None = Query(default=None)`、`page_size: int = Query(default=20, ge=1, le=100)`
  —— 参数名与约束照 `backend/app/api/routes/tags.py` 与 `comments.py`。
- 输出：`{ "items": [...], "page": {...}, "counts": {"all": n, "hot": n, "active": n, "resolved": n} }`
- **counts 必须一起返回**，不能分四次请求。Tab 上带数字（原型 `store.tabCounts`），四次
  请求会先渲染一排 0 再跳成真值——列表页最先出现的东西闪一下，读的人会以为数据错了。
- `hot` 的定义沿用原型：`supports >= 5` 且按支持数降序。**不按浏览量**——原型的注释
  给过理由（「浏览是路过，支持是表态」），我同意。
- 只返回 `visibility='public'`（§4.3）。

**`GET /feedback/{id}`** — 详情

- 输出：`{"feedback": {...}, "timeline": [...], "comments": [...], "related": [...]}`
- 不存在的 id **和**不可见的 id 都返回 `NotFoundError`，**不是 403**。理由：403 等于
  确认「存在一条你看不到的东西」，而私密反馈的存在性本身就是信息（种子里那条
  「我的会话记录里出现了别人的文件名」就是典型的「连存在都不该被知道」）。
- `related`：见 §7（建议 MVP 先不做）。

**`POST /feedback`** — 提交

- body：`kind`、`title`、`body`（正文，拆成 `problem`）、`why?`、`expectation?`、
  `visibility`、`attachments[]`、`attach_logs: bool`、
  `context: {topic_id?, session_id?, environment?, what_happened?, repro?, evidence?}`。
- 输出：`{"id": "<uuid>", "display_no": 1042}`
- 错误：`BadRequestError`（title 空 / kind 非法 / visibility 非法）、
  `ForbiddenError`（`context.topic_id` 或 `session_id` 不是提交者能看到的，见 §2.2）、
  `NotFoundError`（`context.topic_id` 不存在）。
- **幂等性**：人的提交不做去重——本仓对这件事的判断写在
  `backend/app/domain/idempotency/keys.py` 的 docstring 里：「a human pressing a button
  twice means it twice」。agent 侧会重试（自动 resume），所以 **agent 的路径**才需要
  `Idempotency-Key`（走 `app/domain/idempotency/` 里的 claim，dedup window 恰好是
  「这件事和它的重试」）。
- 服务端生成、前端不该传的：`display_no`、`status`（恒为 `received`）、
  `author_handle`（来自 `Actor`，**绝不从 body 读**）、`author_is_agent`、`created_at`。
  「actor 在信任边界注入，永不从 body 读」是 `backend/app/domain/identity/actor.py`
  模块 docstring 的原话。

**`POST /feedback/{id}/supports`** / **`DELETE /feedback/{id}/supports`**

- **两个方法，不是一个 toggle。** 这是本稿里一个刻意的取舍：原型的 `toggleSupport` 是
  本地状态机，服务端 toggle 在重试/并发下会**翻回去**——而支持数进了排序（`hot` Tab），
  翻错一次就是排序错。POST / DELETE 各自幂等（重复 POST 不重复计，重复 DELETE 是 200）。
  形状上其实和 `BlockReaction` 的 toggle 相反，我选择不照它：表情重复点一下无害，
  支持数会进排序，两者的代价不一样。
- 错误：`PreconditionFailedError`（对 `resolved` 的反馈支持；原型把按钮 disable 了，
  服务端要有对应的拒绝）。

**`GET /feedback/{id}/comments`** / **`POST /feedback/{id}/comments`** /
**`DELETE /feedback/comments/{comment_id}`**

- 形状照 `backend/app/api/routes/comments.py`（同一个作者只能删自己的）。
- 评论的 `author_handle` 同样来自 `Actor`。

#### 管理侧

**`GET /admin/feedback`** — 管理列表

- query：`tab`（`public` / `private` / `agent` / `security`）、`assignee`、`q`、分页。
- 独立一条而不是 `GET /feedback?scope=admin`：管理端的**口径**和用户端不一样
  （原型 `AdminFeedbackPage.vue` 顶部注释讲得很清楚——用户侧问「有没有人也遇到这个」，
  管理侧问「这一条现在该谁动」），把两种语义压进同一个端点的 query 参数里，迟早会有人
  从参数拼出一条它不该走的路。管理端返回的字段也不同（多出 `internal_notes`、
  `security`、`views`）。

**`GET /admin/feedback/{id}`** — 单条，带内部备注与上下文。

**`PATCH /admin/feedback/{id}`** — 改状态 / 优先级 / 指派

- body：`{"status"?: ..., "priority"?: ..., "assignee_handle"?: ...}`（可部分）。
- 改 `status` 会在**同一个事务里**追加一行 `feedback_timeline`（§2.3）。
- **不能改 `visibility`。** 原型明写「不给『私密转公开』的按钮——而且不是『先不做』，
  是不该做：公开与否是提交者当场做的决定，管理员能改它就等于那个决定是假的」
  （`AdminFeedbackDetailDrawer.vue` 文件头）。这条我建议**照抄进服务端**：不是不加
  端点，是在 service 层不提供这个方法，并在路由上不接这个字段。

**`POST /admin/feedback/{id}/notes`** — 追加一条内部备注。

#### 元数据

**`GET /feedback/meta`** — `STATUS_LADDER`、各枚举的中文标签、支持数与热门阈值。
（§2.5 末尾：把前端持有的那份顺序表搬到服务端，是接后端时该顺手做掉的事。）

### 4.3 权限模型

**这是全篇最需要说清楚的一节**，因为「谁能看私密反馈、谁能改状态」在本仓**没有现成的
答案**。

#### 本仓的鉴权是怎么做的

- **两族 token**（`.claude/rules/backend-tests.md` 第一条、`backend/app/auth/caller.py`
  的模块 docstring）：主干 access token 的 `sub` 是 int 用户 id，走
  `require_auth_user`（`backend/app/auth/checker.py`）；cheesex session token
  **只有 handle、没有 int id**（`user_id=None`），数字身份层会把它当访客。
  **同一个 header 在两类路由上行为不同**——这是本仓最贵的一个坑。
- **`ActorResolver`**（`backend/app/api/auth.py`）是两族都能认的那一层。
  `resolve()` 按顺序试：人类 bearer token → agent scoped token（`X-Cheese-Token`）→
  Phase-0 的 body handle 兜底。产出的 `Actor`（`backend/app/domain/identity/actor.py`）
  有个关键属性 `authenticated`：`via in ("token", "cheese")` 才是真凭据；兜底的 handle
  「描述作者身份，但不授予任何成员资格或角色」。
- **范围角色**：`ProjectRole`（lead/member）、`TopicRole`（owner/admin/member，
  `backend/app/domain/topic/models.py`）、团队 owner/admin、`SpaceAdminRelation`。
  策略函数住在 `backend/app/domain/authz/policy.py`。

**所以反馈路由要用 `ActorResolver`，不是 `require_auth_user`。** 这是本设计与
`comments.py` / `tags.py`（都用 `require_auth_user` + int id）**不一样**的地方，理由：
反馈是**平台级**功能，没有项目上下文，它的调用者天然落在 handle 那一族里——和
`topics` / `awaiting` 一样。`GET /awaiting-me`（`backend/app/api/routes/awaiting.py`）
是最贴近的先例：它也用 `resolver.resolve(fallback_handle=None)`，并且对访客返回空列表
而不是错误。

#### 「平台管理员」这个概念在今天不存在

这一点必须先说清楚，否则后面全是空中楼阁：

- `SystemRole.SUPER_ADMIN` 在 `backend/app/auth/core.py` 里**定义了**，
  `backend/app/auth/checker.py` 的 `check_permission` 里**读了**它（命中就 `return True`）。
  但**生产路径上没有任何地方给它赋值**：`checker.py` 造 `AuthUserInfo` 的两处给的是
  `GUEST` 与 `USER`，全仓唯一造出 `SUPER_ADMIN` 的是单元测试
  （`backend/tests/unit/test_permission_checker.py`）。也就是说它是一条今天走不到的死路。
- `require_permission(action, resource, ...)` 那套（`PermissionConfig` / `PermissionRule`
  / `Role`）是 1.0 的框架，而且 `Resource` 枚举里**没有 FEEDBACK**，也没法加——它是
  1.0 的资源清单。
- 有的是：Space 的 managers、项目的 lead、话题的 owner/admin、团队 owner/admin。
  **全是有范围的角色**，没有一个「平台管理员」。
- **`/admin/*` 前缀今天不等于「管理员」。** `backend/app/api/routes/scheduler.py` 的
  `router = APIRouter(prefix="/admin/scheduler", tags=["scheduler"])` 下面三个端点
  （`/tick`、`/poll-open-prs`、`/sweep-abandoned-gates`）唯一的依赖是
  `Depends(get_scheduler_service)`，而那个依赖只注入服务、不鉴权——**无门**。想「新路由
  挂在 /admin 下所以有门」是错的。→ §8.1、§8.12。

**我的建议（需要拍板）**：新增一个平台级角色，用**配置里的 handle 白名单**，
落在 `backend/app/core/config.py` 的 settings 上，形状照 `dogfood_owner_handles:
list[str] = []`（`backend/app/core/config.py`，消费在
`backend/app/domain/agent/profiles.py` 里的 `frozenset(settings.dogfood_owner_handles)`）。
本仓还有一个更贴近的先例：项目设置里的 `branch_protection.override_handles`
（`backend/app/domain/project/protection.py`），那是一串 handle，**而且真的被当权限门用**
（`backend/app/domain/review/services.py` 里 `allowed = set(protection.override_handles)`）。
两个先例说明「一串 handle 当授权键」在这个仓库不是新发明；差别只在层级——那两个一个有
项目范围、一个是 agent profile，平台级还没有。

理由：它的失败模式最小。白名单在配置里，鉴权失败就是「不在名单里」，不依赖任何一张
可能为空的表；而「复用某个已有范围角色」的语义是错的——反馈说的是**平台本身**，
平台不属于任何一个 Space 或项目。

另外**不要**去把 `SystemRole.SUPER_ADMIN` 点亮：那条路要经过 `PermissionConfig`
那套 1.0 框架，而它没有 FEEDBACK 资源，硬塞就是动 1.0 的权限模型。

#### 私密反馈谁能看

**已定（2026-09-18）：提交者 + 平台管理员**（§8.0）。原型的定义是「只有管理员能看到」，
那被判定为 bug：提交者自己也看不到（`publicItems` 过滤 + 详情页挡板两处，见 §1.3 第 8 条）。
查询条件因此是：

```
visibility = 'public'
  OR author_handle = <我> OR submitted_by_handle = <我>
  OR <我是平台管理员>
```

两个 handle 都要算：agent 提案、人确认提交的那一类，这两个字段不同（§5.2）。

不论选哪个，服务端必须实现三件事：

1. 列表层的过滤（不能只靠前端不画）；
2. 详情层的过滤（直达链接也挡住）——原型注释自己写了「只靠列表不显示，等于谁把链接
   发出来谁就能看。真接后端时这一层应该在服务端」；
3. **404 而不是 403**（§4.2）。

#### agent 与人

- `Actor.is_agent` 是现成的字段（`backend/app/domain/identity/actor.py`，由
  `IdentityService.is_agent(handle)` 判定）。agent 提交的反馈
  `author_handle` = 它的 handle（`cheese` 或 `cheese-<话题hex>`，见
  `docs/topics/agent池方案.md`），`author_is_agent = True`。
- **管理动作 agent 不能做。** 这一条**不能**指望 `_CHEESE_WRITE_PATHS`
  （`backend/app/main.py`）：那张表是 agent 写面的**白名单**，不在表里的路径
  **不是被拦住，是压根不过那个中间件**。本仓已经实证过这一点，症状是**静默放行**而不是
  401。所以管理端点要在**路由内部**用 `ActorResolver` + `not actor.is_agent` 显式拒绝
  （照 `backend/app/domain/review/services.py` 里 `_forbid_ai` 那种两道的做法：不进白名单
  **并且** 在 service 层再挡一道）。
- agent 与人走**同一个** `Actor` 形状，服务不会 `if is_agent` 分叉——这是
  `backend/app/domain/identity/actor.py` 与 `authz/policy.py` 一起立的规矩
  （「Humans and agents resolve to the *same* `Actor` shape so domain services never
  branch on `if is_agent`」）。

## 5. agent 侧

### 5.1 `AgentFeedbackCard` 在聊天里出现意味着什么

它已经在树上了：`frontend/src/views/workspace/TopicChatColumn.vue` 直接渲染
`<AgentFeedbackCard />`，没有 props。也就是说**今天它的 finding 是写死的默认值**
（`AgentFeedbackCard.vue` 的 `withDefaults` 里那一大段），而它的**行为是真的**——点
「提交反馈」走的是和反馈中心同一个 `store.submit()`，提交完卡变成凭证并链到那条反馈。

它解决的问题写在文件头：**上下文会丢**。所以这张卡自己带着三段现场，点提交时一并递进
抽屉。三颗按钮的排布也已经在注释里论证过（「不用」必须和「提交反馈」一样容易点到）。

真做起来，缺的只有一件事：**finding 从哪来**。两条路：

- **(a) agent 主动调工具**：芝士在轮次里判断「这更像平台问题而不是使用方式」，调一个
  `cheese_feedback_propose`，卡是平台渲染这个调用结果。→ **建议这条。**
  它正是 `backend/sandbox/skills/cheese/SKILL.md` 描述的既有形状——「你做完一个平台动作
  （记决策/改文档/钉里程碑…），平台会自动在对话里显示一张可点的卡片」，SKILL.md 里连
  措辞都定好了（agent 不要再用文字旁白「已记录」）。
- **(b) 平台从轮次流里推断**：不可行。`docs/what-the-agent-perceives.md` 讲的就是这个
  方向的边界（平台收得到什么、收不到什么），而 `docs/spec.md` §14.5 那条「平台不猜
  语义」是直接相关的行为规范。

### 5.2 谁批准它变成一条正式反馈

**人按「提交反馈」那一刻。** 这条原型已经定好了，我建议照抄并且**在数据上把它记下来**：

- `author_handle` = 芝士（发现者）、`author_is_agent = true`；
- `submitted_by_handle` = 按下按钮的那个人。

**两个字段都要，不能合并成一个。** 合起来就答不出「芝士提的反馈里有多少真的被人发出去
了」——而那正是判断「要不要继续让芝士提、提多少」的唯一依据。这也不是新发明的形状：
验收卡上就有类似的「谁提的 / 谁采纳的」两分。

**agent 不能自己把它变成公开反馈。** 提案是提案，提交是提交。这条既是产品判断
（原型三颗按钮的排布就是在说「这是一张问一句的卡，不是一条已经发出去的东西」），
也是安全判断（没有它，一个跑歪的 agent 可以直接往公开列表里灌东西）。

### 5.3 如何避免刷屏

四道，从便宜到贵：

1. **平台侧配额。** `alerts` 那套已经有现成的分级限流（`docs/product-impl.md` §3.7：
   每话题每天 ≤2 轻 / 每周 ≤1 强，`AlertRepository.over_quota`）。反馈提案卡照
   同一形状限流：**每个话题每天最多 N 张提案卡**（N 待定，建议 2）。理由直接引那一段：
   决策/验收请求不被限流丢弃是因为「有人在等」，而提案卡没有人在等，它可以被丢。
2. **指纹去重。** 同一 `what_happened` + `repro` 归一化后的指纹，合并成一张卡。
   形状照 `backend/app/domain/notification/dedup.py` 的 `NotificationDeduplicator`
   （Redis，带 TTL），或者落一列 `proposal_fingerprint` 加唯一索引。
3. **拒绝要有记忆——这一条最重要。** 原型的「不用」只把组件内 `state` 置成
   `dismissed`（`AgentFeedbackCard.vue`），刷新就回来。服务端必须落一行
   （谁、什么时候、哪个指纹不用了），否则**同一个问题每轮都会再问一遍**，这是刷屏
   最主要的来源，而且它会让人对整张卡产生免疫。
4. **agent 只能提案。** 见 5.2。

## 6. 通知与未读

### 6.1 本仓有两套「通知」，别搞混

`docs/product-impl.md` §3.7 和 `backend/app/domain/alert/models.py` 的 docstring
都在讲这件事，后者讲得最清楚：

| | `alerts` | `notification` |
|---|---|---|
| 表 | `alerts`（uuid PK，`backend/app/domain/alert/models.py`） | `notification`（BigInteger + `Sequence`，`backend/app/domain/notification/models.py`） |
| 是什么 | **平台在报告自己**：哪台机器掉了、哪一轮失败了、哪个话题在等人 | **一个人告诉另一个人**：提及、回复、表情（社交 feed） |
| 路由 | `/projects/{id}/alerts`、`/projects/{id}/inbox`、`/alerts/{id}/{read,feedback,resolve}`（`backend/app/api/routes/alerts.py`） | `/notifications`（`backend/app/api/routes/notifications_flat.py`） |
| 分级 | `silent` / `light` / `strong` + 限流 | 无 |

**反馈要的是前者**（`alerts`）：`Alert` 有 `target_handle`、`payload`、`read_at`、
`resolved_at`，形状完全对得上。做法是给 `AlertKind` 加两个值
（`feedback_reply`、`feedback_status`）——**加值不用迁移**，因为
`AlertKind` 落的是 `VARCHAR(16)` 且没有 CHECK（§3.3 已核）。注意长度：`decision_request`
正好 16 个字符，新值不能超过 16。

### 6.2 但 `alerts` 挂在项目上，反馈没有项目

**这是本设计遇到的最硬的一处不匹配。** 已核：
`backend/alembic/versions/cf93e4735e4a_full_schema.py` 里
`sa.Column("project_id", sa.Uuid(), nullable=False)`，
`ForeignKeyConstraint(..., ondelete="CASCADE")`。而原型的路由注释明写「反馈说的是平台
本身，跟我在哪个项目里没有关系」。

三条路：

- **(a) 放开 `alerts.project_id` 为 nullable。** 要改一张在用的表，并且所有读它的查询
  都要能被 NULL 正确过滤。`alerts` 是整个收件箱语义的根（`/projects/{id}/inbox`、
  `docs/product-impl.md` §3.7 的拍板流程），动它的风险不成比例。
- **(b) 反馈不进 `alerts`，未读单独做。** 照 `TopicReadState`
  （`backend/app/domain/topic/models.py`）那个 **cursor** 形状——它的 docstring 解释了
  为什么是 cursor 而不是逐条已读表：「cheap to bump, cheap to count against」。
  反馈这一侧可以是 `(user_handle, last_read_at)` 一条/人 的全局 cursor，或者
  `feedback_read_states(feedback_id, user_handle, last_read_at)`。
- **(c) 只复用投递渠道。** `backend/app/domain/notification/publisher.py` 的
  `RedisEmailQueueNotificationHandler` / `RedisPushQueueNotificationHandler`
  是无状态的队列写入，跟 `alerts` 表没有耦合，可以直接用。

**建议 (b) + (c)**：不动 `alerts` 的 `project_id NOT NULL`，未读走 cursor，投递走队列。

### 6.3 「我的反馈有新进展」到底是事件流还是当前状态

这个问题值得单独想，因为本仓刚为同类问题做过一次选择。

`frontend/src/views/InboxView.vue` 的注释记录了那次选择：`/inbox`「待办」**曾经**接的是
顶栏铃铛那份通知数据（提及与回复），后来改接了 `GET /awaiting-me`
（`backend/app/api/routes/awaiting.py`），理由是「通知是一条条事件记录，答不出『现在还没
处理完的有哪些』：一张验收卡被驳回之后，它那条通知还在」。

`awaiting.py` 的模块 docstring 更直接：它解释了为什么这件事不能由通知表拼出来。

**反馈的「有新进展」更像哪一类？** 我倾向**两边都要，但语义不同**：

- **铃铛**（事件流）：「你提交的反馈收到了一条回复」「状态变成了处理中」——这些是
  **发生过的**事情，读掉就完了。
- **待办**（当前状态）：提案卡等一个「发还是不发」→ 这个**该进 `/awaiting-me`**。
  它和验收卡是同一类东西：一件在等你动手、动完就从清单上消失的事。

投递渠道（邮件/浏览器的推送队列）复用 §6.2(c)。`AwaitingItem['reason']` 现在有三个值
（`reviewer` / `reporter` / `asked`，见 `InboxView.vue` 的 `REASON_TEXT`），加一个
`feedback_proposal` 是加法，不是改造。

### 6.4 谁收到通知

- 提交者（`submitted_by_handle`，没有它时退到 `author_handle`）：被回复、状态变化、
  被管理员回复。
- 被指派的人：被指派时、被 @ 时。
- **不支持「支持数到 5 的时候通知提交者」**——建议不做。理由：它会把「支持数」变成一个
  可以被人为推动的运营数字（§8.6 是同一个问题的另一半）。→ §8.6。

## 7. 分阶段

### MVP（能替掉原型、能 dogfooding）

后端：

- 表：`feedback`、`feedback_supports`、`feedback_comments`、`feedback_timeline`、
  `feedback_notes`（§2）；
- 端点：`GET /feedback`（含 counts）、`GET/POST /feedback/{id}`、
  `POST/DELETE /feedback/{id}/supports`、评论三件、`/admin/feedback` 四条（列表/单条/
  PATCH/备注）、`GET /feedback/meta`；
- 平台管理员的一条路（§4.3 拍板后）；
- 通知：只做「我的反馈有新评论 / 状态变了」进铃铛，写 `alerts` 或按 §6.2(b) 的方案；
- agent 提案：一条 `cheese_feedback_propose` 工具 + 卡接真数据 + 一次提交
  （`submitted_by_handle` 落库）+ 配额与「不用」的记忆（§5.3）。

前端（这次要改的）：

- `stores/feedback.ts` 里那几行 `// → 将来在这里发请求` 换成真调用；
- `frontend/src/network/api/feedback/{index.ts,types.ts}`，形状照
  `frontend/src/network/api/comments/`；
- 删掉角色开关（原型注释自己要求的）；
- **文案要不要进 i18n 目录**：`.claude/rules/frontend.md` 写着「Never hardcode a
  user-visible string」，但这条规矩在树上**没有被执行**，也不在任何闸门里。已核：
  `frontend/src/views/` 下 128 个 `.vue` 里 117 个含中文、只有 23 个用了 i18n；
  `frontend/src/components/` 是 111 / 125 与 30。`frontend/src/i18n/catalog.spec.ts`
  检查的是「源码调用的键都能解析」和「目录里没有没人用的键」，**不扫硬编码字符串**。
  所以反馈这几页今天和另外 99 个视图一样是硬编码中文，闸门是绿的。→ §8.16。

### 明确「先不做」

| 项 | 理由 |
|---|---|
| 附件真上传 | 原型的验收标准就是「只做 UI」，MVP 保持一致（§8.7 定了再说） |
| `views` 浏览量 | 原型有字段没有来源（§1.3 第 2 条），真做要新增一张表或一个计数器 |
| 标签关联到 `tag` 表 | MVP 存 JSON（§8.8） |
| 相关反馈 `related` | 客户端算要拉全量，服务端算是另一个查询，MVP 不值 |
| 内部备注的多管理员协作 | 先 append-only，不做 @、不做编辑 |
| 全文搜索 | 先用 `ILIKE`（§2.4） |
| `/admin/feedback` 独立域名 | 原型路由注释自己说了「真的拆成独立域名是运维/鉴权的事，不是这一轮要决定的事」 |
| 私密转公开 | 原型明写「不该做」（§4.2） |
| 状态回退语义 | 见 §8.4 |
| 反馈 → 活/验收卡 | 见下面「后续」 |

### 后续

- 附件、浏览量、标签表、相关反馈；
- **反馈变成一件活**：一条被采纳的反馈很可能应该变成 `tasks` 里的一行或一张验收卡，
  而不是留在反馈表里自己维护一个状态机。这件事要单独讨论（它牵动
  `backend/app/domain/room_task/` 与 `review/`），但**如果最后要做，状态集的形状应该在
  MVP 阶段就为它留好余地**——这是我建议 §8.4 现在就定掉的原因。
- 与 GitHub issue 的关系（§9 末尾）。

## 8. 风险、开放问题、需要拍板的点

**标 ★ 的是不定下来就没法开工的。**

### 8.0 已定（2026-09-18，需求方答复）

- **私密反馈，提交者能看见自己提交的。** 原 ★8.2 关闭，§4.3 已按此改。
- **反馈中心是平台共享的，不以组织（Space）为单位。** 原 ★8.10 关闭，见下。
- **默认不展示已解决的 bug。** 见 8.17，还需要一句澄清。

### 8.1 起仍在台面上的

**★ 8.1 平台管理员是谁。**（§4.3）不定，管理端要么没门（照 `/admin/scheduler` 的先例，
那是个已在树上的无鉴权路由），要么我替需求方发明一个角色。建议：`settings` 里的 handle
白名单，形状照 `dogfood_owner_handles`。

**8.2 私密反馈，提交者自己能不能看。→ 已定（2026-09-18）：能。**（见 §8.0；§4.3 已按
此改）原型的答案是「不能」（列表层 + 详情页两处），被判定为原型的 bug。可见的人是
提交者本人 + 平台管理员；查询条件与两个 handle 的写法见 §4.3。

**★ 8.3 `security` 与 `visibility` 的关系。**（§1.3 第 7 条）种子里两条 `security`
都是 `private`，管理后台把「安全问题」做成与「私密反馈」并列且互斥的一栏。那它就该是
`private` 之下的一个子类，而不是第二个开关。要不要写成数据库约束
（`CHECK (NOT security OR visibility = 'private')`）？建议写——本仓有 `CheckConstraint`
的先例（`backend/alembic/versions/d8a6b5c4e731_machine_limit.py`）。

**8.4 状态集。**（§1.3 第 1 条）五个值的字面沿用原型没有争议，有争议的是：
(a)「已解决」和「已上线」要不要拆成两步（需求里 Timeline 写的是 4 步且最后一步叫
「已上线」）；(b) 允不允许**回退**（原型的时间线注释暗示了会发生：「同一状态可能被推进过
两次（回退再推进）」）。这两条都会影响 §2.3 的 `feedback_timeline` 是不是纯 append-only，
以及最后要不要变成一件活（§7 后续）。

**8.5 浏览量 `views` 做不做。**（§1.3 第 2 条）做的话是一张「谁看过」的表（一人一条，
准确但重）还是一个计数器（轻但可刷）。建议 MVP 不做。

**8.6 支持数进排序，要不要防刷。** 进了 `hot` 排序它就是个可以被推的数字。本仓
`BlockReaction` 对表情没有防刷（一个人一个表情一行，唯一约束就是全部防线）。
建议 MVP 照它，但要**知道**这是决定，而不是没想到。

**8.7 附件走哪条路。** 两条：1.0 的 `attachment` 表（`backend/app/domain/attachment/
models.py`，int PK，`url Text` + `meta JSON`，配 `/uploads` 路由）能装，但 2.0 这一侧的
工作区/上传语义完全不同（`docs/product-impl.md` §3.10 讲的是话题工作区）。**硬约束**：
私密反馈的附件不能被一个公开 URL 读到——这一条会决定选哪条路。

**8.8 标签。**（§1.3 第 4 条）`tag` 表（`backend/app/domain/tag/models.py`）已经在做
「给问题/赛题/Space 打标」这件事，但它的 `name` **没有唯一约束**，所以「去重」没有现成
实现，而且要新建一张关联表。MVP 存 JSON 数组、不做筛选是退让，不是结论。

**8.9 指派给谁。** 原型的 `ASSIGNEES` 是写死的五个开发团队 handle。真做起来这个列表
从哪来：平台管理员名单（8.1）？某个 Space 的人？还是任何用户？「指派给一个不是管理员
的人」意味着他也要能改状态——这会反过来改 §4.3 的权限模型。

**8.10 反馈的可见范围。→ 已定（2026-09-18）：平台共享，不以组织为单位。**（见 §8.0）
原稿把这条列为风险最高的一条，担心「A 机构的用户能不能看到 B 机构的反馈」；需求方确认
反馈中心是平台级的共享空间，没有这层切分。落地后果三条：

1. 列表的查询条件里**没有** Space / 项目维度，不能照
   `backend/app/api/routes/awaiting.py` 那个「我能看见的全部项目」的写法抄。
2. `topic_id` / `project_id` 只是**出处**（这条反馈在哪里被提出来），不是可见性范围，
   不能拿来做行级过滤。
3. 「公开」= 对所有登录用户公开；未登录不可见。

**8.11 命名冲突。**（§4.1）`feedback` 一词在 `alerts` 里已经是 👍/👎 的意思
（`POST /alerts/{alert_id}/feedback`）。两条路由不撞，但词义撞。建议至少在文档和前端
文案上把新的叫「反馈中心」、旧的叫「消息评价」。要不要改后端字段名（`Alert.feedback`
→ `Alert.rating`）是另一件事，要单独评估（它有迁移成本）。

**8.12 `/admin/*` 前缀今天不等于「管理员」。**（§4.3）`/admin/scheduler` 三个端点无
鉴权。新路由挂 `/admin/feedback` 不会因此获得任何保护。顺带：那三个无鉴权端点本身是不是
该补门，是**另一个**问题（原型种子里有两条「安全问题」反馈，其中一条的 `evidence` 直接
点名 `backend/app/api/routes/spaces.py` 的三个端点只依赖 `require_auth_user`——那是
mock 数据，但同类问题的真实版本值得单独查一遍）。

**8.13 e2e 与前端测试。** `.claude/rules/e2e.md` 说「A new spec only counts once you've
seen it run in CI」。反馈的三条前端路由
（`/feedback`、`/feedback/:id`、`/admin/feedback`）目前没有 e2e spec；现有的组件测试只钉
了两个窄屏上的静默失效。接后端时至少要有：一条「提交 → 列表里出现」、一条「私密反馈对
非管理员是 404」。

**8.14 种子数据。** 要不要把原型那 12 条 mock 落进
`backend/scripts/seed_fusion_demo.py`（CI 的 e2e 会跑它，见 `.claude/rules/e2e.md`）。
**注意**：其中两条 `security: true` 的条目，`evidence` 字段直接点名了本仓的真实文件与
端点。照抄进种子等于把一段「这个端点没门禁」的断言写进演示数据——将来谁读种子会以为
那是真的（它今天**不**是真的，见 8.12）。

**8.15 删除与撤回。** 原型没有删除。管理员能不能删？提交者能不能删自己的？软删
（`deleted_at`，已在 §2.2 留好列）还是硬删？被删的反馈在时间线/通知里怎么显示？

**8.16 反馈页的文案要不要进 i18n。**（§7）`frontend/src/views/` 里 117/128 个文件
含中文、只有 23 个用 i18n，闸门不扫硬编码——也就是说这条规矩今天管的是「别把已经进了
目录的东西写乱」，不是「所有中文都必须进目录」。建议**不做**：把反馈这 8 个文件迁进
目录，不会让产品变得能换语言，只会让这 8 个文件在仓库里显得和别人不一样。真要做，
应该先定「哪些界面必须双语」这个覆盖面问题，再一次性迁，而不是在接后端这个 PR 里
顺手迁一个功能。

**8.17 默认不展示已解决的 bug。**（2026-09-18 需求方提出）需要一句澄清：是「默认隐藏
所有已解决的反馈」，还是「只隐藏已解决的 bug，而已解决的建议仍然显示」。两者实现不同——
后者要给默认筛选加一个 `kind = 'bug'` 条件，前者只是 `status != 'resolved'`。另外
「已解决」怎么判定要跟着 §8.4 走：如果状态阶梯最后拆成「已解决」和「已上线」两步，
这个默认筛选得一起想清楚。实现上它只是列表端点的一个默认参数，改起来便宜，但**必须
写进 §4.2 的默认值**，否则前端会各自发明一套。

## 9. 与现有系统重叠：复用、绕开、避开

| | 对象 | 判断 |
|---|---|---|
| ✅ 直接复用 | `app/api/response.py` 的 `ok()` / `page()` | 封套 |
| ✅ | `app/core/errors.py` | 错误类与状态码 |
| ✅ | `ActorResolver`（`app/api/auth.py`） | 两族 token 的识别 |
| ✅ | `Actor.is_agent`（`domain/identity/actor.py`） | 人/agent 的区分 |
| ✅ | `UuidPk` / `Timestamps`（`domain/common.py`） | 模型 mixin |
| ✅ | `publisher.py` 的两个队列 handler | 邮件/推送投递（§6.2c） |
| ✅ | `BlockReaction` 的唯一约束**形状** | 一人一票（§2.3） |
| ✅ | `idempotency/` 的 claim | agent 重试去重（§4.2） |
| ✅ | `Sequence` 取展示号（`task_seq` / `notification_seq`） | `display_no`（§2.2） |
| ✅ | `topic_read_states` 的 cursor **形状** | 未读（§6.2b） |
| ✅ | `AlertKind`（加两个值） | 通知分类（§6.1） |
| ✅ | `settings.dogfood_owner_handles` 的**形状** | 管理员白名单（§4.3） |
| ⚠️ 要改才能用 | `alerts.project_id NOT NULL` | 反馈没有项目（§6.2） |
| ❌ 不复用 | 1.0 的 `comment` 表 | 多态 + int 主键（§2.3） |
| ❌ | `blocks`（「万物皆块」） | 见下 |
| ⚠️ | `tag` 表 | 要加关联表且没有去重（§8.8） |
| ❌ | `/admin/scheduler` 的「无门」现状 | 不是可以照抄的先例（§8.12） |

**为什么不用 `blocks` 装反馈。** 「万物皆块」（`docs/spec.md` §5）理论上什么都装得下，
但 `Block` 有 `project_id`（NOT NULL，`backend/app/domain/block/models.py`），它的读写
鉴权走 `authorize_topic`（`backend/app/api/auth.py`）。用 block 装反馈会强迫**每一条反馈
挂在某个项目上**——而原型从路由注释开始就在说反馈不属于任何项目。这是本设计里最值得
写下来的一条「看起来能复用、其实不能」的判断。

**与 GitHub issue 的关系。** `CLAUDE.md` 里写着「**The design that is still being
argued lives in issues**」——issues 承载的是**开发团队自己的**设计争论。反馈承载的是
**产品用户**对产品的意见。两者受众不同、生命周期不同（issue 会关掉，反馈会被「解决」
然后成为可查的历史）。建议**不同步**；要同步的话（比如「被采纳的反馈自动开一个 issue」）
是独立的一次决定。
