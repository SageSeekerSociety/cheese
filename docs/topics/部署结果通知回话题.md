## 目标

`push_back()` 采纳后异步 `subprocess.Popen` 启动 `scripts/on-dogfood-push.sh`（发射后不管），脚本跑完的结果（部署成功 / 检查未过已回滚）只落一行本地日志，没人会被通知。加一层：脚本跑完后把结果插回触发这次采纳的话题时间线。

## 约束

- 不能拖慢 `accept()` API——继续立即返回，结果上报走后台 `asyncio` 任务。
- 成功/回滚要分开说清楚；回滚要说明改动还在 `dogfood/<branch>` 分支、没有丢。
- 不改 `on-dogfood-push.sh` / `redeploy.sh` 本身的检查/回滚/部署逻辑，只加事后报告这一层。
- 比 `sandbox_notices.py` 的纯 best-effort 更强——这条信息更关键，投递要重试。

## 已完成

新增 `backend/app/domain/workspace/dogfood_notices.py`：`push_back()` 里 hook 进程启动后，`create_task` 挂一个 `watch_dogfood_push()`（不 await，不阻塞返回）。它等进程退出（30 分钟超时兜底，防止 hook 卡死/被杀导致话题永久等不到消息），读日志增量内容，按 `on-dogfood-push.sh` 的收尾文案分类：

- 命中 `=== push-back done: ...` → ✅ 成功，带上部署的 commit。
- 命中 `CONFLICT:` / `another push-back is still running` → ❌ 未完成 + 具体原因，改动留在分支上。
- 命中 `ROLLBACK:` 或其它未识别情况 → ⚠️ 已回滚（宁可保守报回滚，不误报成功），改动留在分支上。
- 进程超时未退出/日志读不到 → ⚠️ 结果未知，提示人工查 `tmp_dogfood_push.log`。

写话题时间线用 `BlockRepository.add(..., kind=BlockKind.event)`，失败按 `(0, 5, 30)` 秒重试三次，仍失败才落 `logger.error` 放弃（比 sandbox_notices 的纯 best-effort 更强，符合"这条信息更关键"的要求）。`topic_id` 直接从 `push_back()` 的函数参数拿，不依赖从 8 位分支名反推——按简报里指出的方向做的。

测试：`tests/unit/test_dogfood_notices.py` 13 个用例（桩进程 + 桩日志内容覆盖成功/回滚/冲突/锁超时/未识别输出/进程不退出/话题已被删/投递失败重试后放弃等场景）+ `tests/unit/test_push_back.py` 新增 2 个用例锁定"本地 upstream 且 hook 存在时确实挂了 watcher / hook 不存在时不挂"。
