## 目标

两阶段采纳从来没有自动合并成功过一次。修两处：

1. **合并方式错**：`backend/app/domain/review/github_pr.py` 写死 `merge_method: "merge"`，而本仓库是 **squash-only**（`docs/infrastructure.md` §Merge policy，已核实原文仍在），GitHub 一律回 **405**。
2. **405/409 被静默吞掉**：`merge_pull_request` 直接 `return None`，调用方 `_advance_pr_checks` 直接 `return`，卡片 `note` 一字不写。外部观感是"PR 全绿却永远停在 pr_open"。这条比 ① 更值钱——正是它让 bug 藏了大半天。

## 约束

- 不碰话题 `06522e2d` / PR #217（它是验证样本）。
- 不动 `_repush_if_local_head_moved`、`push_topic_branch_for_github_pr`、`_advance_deploy_checks`、`.github/workflows/`、前端。
- trailer（`Requested-by` / `Reviewed-by` / `Cheese-Topic`，2026-08-09 设计要点5"标清芝士代表谁"）必须仍然出现在最终的 squash 提交里。
- 轮询 60s 一次，note 不许刷屏，且不许覆盖更高优先级的 note（如 `❌ 部署失败`）。

## 核实结论（GitHub 文档，非推测）

- squash 模式下 GitHub 用 `commit_title` + `commit_message` 两个字段。文档对二者的描述分别是 "Title for the automatic commit message." / "Extra detail to append to automatic commit message."，**没有文档化"省略时的默认值"**。
- 默认值实际来自**仓库设置** `squash_merge_commit_title`（`PR_TITLE` / `COMMIT_OR_PR_TITLE`）和 `squash_merge_commit_message`（`PR_BODY` / `COMMIT_MESSAGES` / `BLANK`），且默认标题会**自动缀 `(#N)`**——main 历史里 andylizf 的 `(#213)/(#214)/(#215)` 就是这么来的。
- 显式传 `commit_title` 会**整条覆盖**默认标题，`(#N)` 不会再自动补。→ 所以我们自己把 `(#N)` 缀上，保住仓库的提交信息惯例。

## 方案

**① 合并方式**
- `HttpxGitHubPrClient` 新增 `merge_method` 参数，为 `None` 时按调用时机读 `settings.accept_pr_merge_method`（新配置，默认 `"squash"`）。
- 传参改成 `commit_title` = `采纳 {话题标题} (#N)`，`commit_message` = 纯 trailer 块（标题已单独给出，正文不再重复"采纳 …"）。
- **不做"失败后换一种再试"**：405 也可能是 draft/分支保护等真·不可合并，自动换方式会把这些掩盖掉，还会在两种方式都开的仓库里悄悄产出 merge commit。有了 ② 之后，配错在一个轮询周期内就能看见——可配置足够，自动兜底是过度设计。

**② 405/409 不再静默**
- `merge_pull_request` 返回 `MergeResult(sha | blocked_reason)` 取代 `str | None`，`blocked_reason` 带 HTTP 码 + GitHub 响应体的 `message`。
- `_advance_pr_checks` 把原因写进 `card.note`（`🚫` 前缀）；**去重按整条 note 全等比较**（比 `_nudge_pr_fix` 的 `startswith` 更好：原因变了会更新，原因没变不重写、不重复打日志）；`note` 已是 `❌` 开头则不覆盖。
- 两处误导性注释（`# Not mergeable yet (checks pending / behind base)`）改成 405 的真实含义。
