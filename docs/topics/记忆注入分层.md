# 记忆注入分层：core 每轮常驻，其余按需检索

收编 issue #187。前置于「把每话题的记忆池归并到 agent 名下」——不先改注入方式，
池子一合并大半就进不来。

## 为什么

记忆池的粒度原来是话题，归并到 agent 之后是一个池。本项目实测（2026-08-17）
**180 条 / 50056 字符**，合并当天大半进不来。更要命的不是"进不来"，是**按什么标准
进不来**：原来的规则是 `created_at DESC` 取前 50，于是座位归了"最后写的那批"，跟这
一轮在干什么毫无关系。

## 现在是什么样

记忆条目有 `layer` 字段（`app/domain/memory/models.py` 的 `MemoryLayer`）：

- **`core`** —— 这个 agent 是谁、它的长期规则和目标。**每轮全量注入。**
  预算 4000 字符——"永远在场"只有在它足够小的时候才付得起，撑破这个上限就是
  「有东西不该记成 core」的信号。
- **`fact`**（默认）—— 其余学到的东西。**不注入**，用 `cheese recall` 现查。

注入块只欠一句话：池子里还有多少条、它们一条都不会自己出现、去哪儿拿。没有这句，
prompt 看着是满的，而看着满的 prompt 没人会去搜。

## 为什么不按相关性注一部分

试过。做法是把当轮上下文（最新消息＋标题＋文档，截到 2000 字符）拆成关键词，给非
core 的每条打覆盖度分，填满 20000 字符预算。实测确实有效——本项目 46 个池合并后，
「与本轮最相关的 10 条」的命中从 0–2/10 提到 10/10。

但它的代价是**每轮两万字符，不管猜没猜对都要付**。而这笔钱只有在系统提示每轮都能
重新送进去时才花得出去——它送不进去（见「会话开场 vs 每轮」）。更糟的是它挤掉了
`recall`：一个看着已经满的 prompt，模型不会再去查。

所以现在的分法是「一类全量、一类按需」，而不是「一类全量、一类猜着给」。猜的那部分
删掉了——`rank_facts`、它的 query 拼装、两个后端各一份实现，一起删。`search`（recall
跑的那个）没动，它现在是事实唯一的到达方式。

## 写入侧

`cheese remember "<事实>"` 默认写 `fact`；`cheese remember --core "<事实>"` 写 `core`。
API 是 `POST /projects/{id}/memory` 的 `layer` 字段，非法值直接 422——静默降级会把写
的人以为常驻的东西丢进按需检索的那一层。记忆页（`GET /memory`）每条都带 `layer`。

## 两个后端

- **db（线上默认）**：`layer` 是一列，`recall_core` 是一次带层过滤的查询。
- **openviking**：core 单独占一个 scope space（uid 加 `-core` 后缀）。不在卡片里写
  标记，是因为放置和措辞由它的 extractor 决定、写进去的标记事后信不过；"在哪个
  space"是我们说了算的。

## 明确没做

存量记忆池的归并/迁移、dreaming、自动摘要、向量检索、`(project, handle)` 这个池 key
和 handle 派生、前端。
