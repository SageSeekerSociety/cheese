## 目标

回答 @符露夀 的问题：芝士现在的网页搜索怎么实现的；要不要换成
「Exa → 统一 Search MCP → fetch fallback → planner → 共享 cache」这一套。

**所有结论都来自 2026-09-07/08 的实测，不是读文档推断。**
第二轮按 @符露夀 的要求补了 OpenAI 做法、市面常见 MCP、skills.sh 上的 skill，
**并且推翻了第一轮的 P0 结论**——推翻的过程和证据都保留在下面。

## 一、现状：平台没有写过任何搜索代码

搜索能力 100% 来自 Claude Code 自带的两个工具，平台只把工具名翻译成中文
（<&backend/app/domain/agent/chat.py:285>、<&frontend/src/lib/toolLabels.ts:21>）。
没有搜索服务、没有 fallback、没有缓存、没有 planner，也**没有配置任何 MCP server**。

两个工具机制完全不同，这是理解一切问题的前提：

| | WebSearch（搜） | WebFetch（读） |
|---|---|---|
| 谁执行 | **模型服务商那边执行**，我们的机器不发起搜索 | **沙箱自己发 HTTP 请求**，抓回来再喂给小模型总结 |
| 缓存 | 无 | 同 URL 15 分钟，**仅限单会话**，换话题/分身即失效 |
| 超时 | 有 | **没有**（见第二节） |

补充实测：默认「知是 AI Pool」也支持服务端搜索（带 `web_search_20250305`
打网关，返回了真实结果）。但这个能力是**借上游服务商的**，我们没声明依赖也没检测，
哪天换个不支持的池子，表现是**搜索静默消失**，不报错不告警。
另外计费只统计 token、不统计 `server_tool_use`，所以默认池的搜索开销
对预算刹车不可见（<&deploy/metering-proxy/cheese_billing_core.py>）。

## 二、WebFetch 会永久挂死（本话题现场抓到的真 bug）

本话题里跑了一组带对照的实验，全部数据来自会话记录时间戳：

| 页面 | HTML | 非正文:正文 | WebFetch 耗时 |
|---|---|---|---|
| 知乎（返回 403） | — | — | **1 秒**，干净失败 |
| example.com | 1KB | — | 3 秒 |
| 维基 Rust 词条 | **996KB** | 11:1 | **5 秒，正常返回** |
| skills.sh 第一次 | 920KB | 87:1 | **1028 秒（17分08秒）挂死** |
| skills.sh 第二次 | 920KB | 87:1 | **390 秒（6分30秒）挂死** |

两次挂死都是人工打断才结束的，**所以上限未知**；同一 URL **2 次 2 挂，是稳定复现**。

这组对照否掉了两个直觉解释：**页面大小不是原因**（996KB 秒回，更小的 920KB 必挂）；
**它也不是"没有失败路径"**（知乎 403 一秒就干净返回了）。三个约 1MB 的页面唯一的
共同变量是**非正文与正文的比例**：87:1 和 120:1 挂死，11:1 正常。

同一个 URL 用 curl 下载只要 **2 秒**，所以卡在下载之后。已排除：网络出口（curl 2 秒通）、
计费代理（0 重启、190MB/2GB）、超长无空格串导致的文本处理爆炸（本地实测 <1ms，
**这个假设被我自己的实验否掉了**）。内部确切原因查不到——WebFetch 是 Claude Code
内置工具，源码不在我们手里。

### 上游 issue：不是我们的问题，是已知未修的 bug

Anthropic 官方仓库 **[#86910 "WebFetch hangs forever on a CSS-heavy 1 MB page"](https://github.com/anthropics/claude-code/issues/86910)**，
2026-08-15 开，**至今 open**，标签 `bug` / `has repro` / `area:tools`。里面的现场
和我们一模一样：约 1MB HTML、正文只有 9KB、挂起后 **CPU 接近 0、没有新字节到达**
（有人挂了 **51 分钟**）。跟我们「文本处理实测 <1ms」完全对得上——**不是算不动，是流卡死了**。

讨论串里有三方独立定位，拼出了完整的失效机理：

1. **根因（2026-09-02）**：WebFetch 用 `axios` 抓页面，带
   `Accept-Encoding: gzip, compress, deflate, br`。当响应**声明的压缩格式和实际内容对不上**
   （典型：反爬页面回 `Content-Encoding: gzip` 但内容是明文），解压错误被吞掉，
   那个 Promise **既不 resolve 也不 reject** —— 于是永久挂起。
   gzip / brotli / TLS 记录错误是三条通往同一个坑的路。
2. **另一变种**：卡在最后的总结调用上——`messages.create({stream:true})` 没有超时，
   而流看门狗默认关闭。
3. **「用户拒绝」是误报**：多位报告者确认，打断后的提示
   `The user doesn't want to proceed with this tool use` 和真正的权限拒绝**长得一模一样**。
   —— 我这次就被它骗了，第一反应是「你打断了它」，实际是它挂死了。

我们的补充证据（可以回报给上游，是个新变种）：我们跑 **2.1.224**，
issue 里提到的两个修复（2.1.105 剥离 style/script、2.1.117 转换前截断）**早就在里面了，照样挂**；
而且我们这页 **内联 `<style>` 是 0**、包袱全在一个 149KB 的 `<script>` 里，
brotli 声明诚实、解压正常（942,956 字节），**芝士自己的隧道代理也已排除**
（经隧道和直连拿到的字节数完全相同）。

## 三、怎么修（三层，从今天能做的到该做的）

前提：**我们改不了 WebFetch**。它是 Claude Code 内置工具，二进制里没有任何
针对它的超时开关（`BASH_DEFAULT_TIMEOUT_MS` 只管 Bash；`API_TIMEOUT_MS` 管 API 调用）。

**第 0 层 · 今天就能做，一行**：给沙箱/机器的环境加
`CLAUDE_ENABLE_STREAM_WATCHDOG=1`（已在 2.1.224 二进制里核实存在，4 处）。
落点是 <&backend/app/domain/agent/provider_env.py:138> 那个 env 字典
（注意 <&backend/app/domain/agent/provider_env.py:45> 的 api_key 路径也要一份）。
**诚实说明：它只覆盖上面第 2 个变种**，issue 里有人实测它对「卡在抓取阶段」那个变种
**无效**。所以这是止血，不是修复——但成本一行、风险接近零，没有理由不加。

**第 1 层 · 真正的修复：把抓取换成我们自己的 MCP。**
这是唯一能给抓取加上超时的途径——`.mcp.json` 里每个 MCP server 都有 `timeout` 字段
（`MCP_TIMEOUT` / `MCP_TOOL_TIMEOUT` 也已在二进制中核实）。自己控 HTTP 栈还能顺带拿到：
硬性连接/请求超时、在 DOM 层剥掉 script/style（前面那个 19 倍压缩）、
以及**抓不到时明确报错**而不是把登录墙当正文。
issue 讨论串里就有人这么做了：同一个必挂的页面，他的 Rust MCP 冷启 19 秒、热 8.2 秒返回。
—— 所以 <@wangchangxin> 提的「统一 Search MCP」是对的，但理由不是「结果更好」，
而是「**内置工具根本没法加超时，MCP 可以**」。这是机械性的理由，不依赖口味。

**第 2 层 · 平台侧的兜底看门狗。**
即使前两层都做了，一次挂死仍然会吃掉整轮。我们的轮次看门狗是**按"有没有动静"判活**的，
而 WebFetch 挂死时**一点动静都没有**——于是轮次一路空转到平台超时，
正好落进「本轮到达平台的时间上限仍未结束，已被强制结束」那个循环。
应该加的判据是：**有工具调用挂在外面、且超过 N 分钟零动静 → 在房间里明说「某个工具卡住了」**，
而不是静默空转。这一层才是能让人省下这 17 分钟的东西。

## 四、第一轮的 P0 结论是错的：知乎/CSDN 不是抓取问题，是登录墙

第一轮我测出知乎 403、CSDN 超时，就断定「需要 fetch fallback」。**第二轮拿真实
文章 URL 做对照实验，这个结论站不住**：

| 源 | 裸 curl（≈现在的 WebFetch） | Jina Reader（专业抓取服务） |
|---|---|---|
| 知乎专栏 | 403 | **200，但只有 489 字节，内容是「安全验证 / 请您登录后查看」** |
| CSDN | 无响应 | **200，858 字节，同样是登录墙** |
| 博客园 | 200 / 35KB | 200 / 12KB 干净正文 |
| 个人博客 | 200 / 519KB | 200 / 27KB 干净正文 |

**知乎和 CSDN 是登录墙，不是反爬**。换 Jina 不行，换无头浏览器也不行
（浏览器一样撞登录墙），换 Exa 也不行。除非拿真实登录态去抓，而那是我们不该做的事。

**更要命的是：加了兜底反而更危险。** 现在 403 是明确失败，agent 知道读不到；
接上 Jina 之后变成 **200 + 一段「请您登录」的文本**，agent 很可能把登录提示
当成正文总结掉——**从"明确失败"退化成"静默给错答案"**。

### 而且这些内容其实已经进来了

把 WebSearch 限定 `allowed_domains=zhihu.com` 再搜，它返回了 9 条知乎链接
**和一段正确的中文答案**。也就是说搜索后端读得到知乎，只是我们自己抓不到。
所以「抓不到知乎」的实际影响，比我第一轮说的小得多。

### 那 fetch 层的真价值是什么

不是「能读到」，是「**读得干净 + 不挂死**」：

- 个人博客 519KB HTML → 27KB 正文（**19 倍压缩**）
- skills.sh 942KB HTML → 正文只有 10.8KB（**98.9% 是 JS 包袱**）

省的是上下文和延迟，不是解锁内容。这个价值真实存在，但和「解锁知乎」完全是两码事。

## 五、市面上在做什么（skills.sh 实测数据）

从 skills.sh 的 JSON 接口（`/api/search?q=`）拉的真实安装量：

| 类别 | 代表 skill | 安装量 |
|---|---|---|
| **浏览器 / 抓取** | agent-browser (vercel-labs) | **806,771** |
| | just-scrape (scrapegraphai) | 244,957 |
| | firecrawl 全家 (firecrawl/cli) | ~100,000 |
| | browser-use | 93,955 |
| **纯搜索** | parallel-web-search | 12,849 |
| | brave web-search | 4,297 |
| | langchain web-research | 3,908 |

**差两个数量级，而且方向一致：市场在补"读页面"，不在补"搜网页"。**
原因很清楚——搜索每个 agent 宿主都内置了，读页面没有。这条外部证据和我们
自己测出来的结论指向同一个地方。

MCP 侧：Exa MCP 是搜索类第一，Playwright MCP（微软官方，30k+ star）是浏览器类第一，
整个生态已有一万到两万个 MCP server。

`agent-browser` 的 `read` 命令内置了分级兜底：先要 `Accept: text/markdown` →
试同名 `.md` → 往上找最近的 `llms.txt` → 最后从 HTML 抽正文。**注意 `read` 不启动
Chrome**；真正能处理交互/登录态的是 `open <url>` 走真实浏览器那条路。

## 六、OpenAI 的做法

- **web search 是托管工具**：$10/1k 次（推理模型）、$25/1k（非推理），
  另加检索内容按输入 token 计费，官方口径每次约 8K token。走 Responses API。
- **deep research 是独立 API**，不是把 planner 塞进普通对话。
- **research_bot** 是 Agents SDK 的示例：Planner → 多个 Search agent 并行 → Writer 汇总成
  markdown 报告。

关键对照：**装机量第一的 `research` skill（mattpocock，462,976 安装）全文只有
794 字节，里面没有 planner**。它只说三件事：起一个**后台 agent**、
只认一手来源（官方文档/源码/规范）、把结论写成**带逐条引用的 markdown 文件**。
——这几乎就是芝士现在「分身 + 实况文档」的做法。

## 七、结论（已按第二轮证据重排）

**P0 · 自建 fetch/search MCP —— 理由是超时可控，不是结果更好。**
唯一能给抓取加上超时的途径，直接止住「分身永久挂死」。顺带做正文抽取压缩
（19 倍那个数字）。**明确不指望它解锁知乎/CSDN**。抓不到时必须**明确报失败**，
绝不能把登录墙文本当正文返回——这是设计上的硬要求，不是优化项。

**P1 · 共享 cache**，长在 P0 的 MCP 里。价值不在省钱（订阅包月），
在于同房间几条分身**看到同一份事实**、少等几十秒。
硬约束：缓存 key 只能是纯查询词，**不能带任何项目私有上下文**，否则等于跨项目泄露。

**P2 · agent-browser 作为重武器按需接入**，用于需要登录态/交互的场景，不做默认路径。

**P3 · Exa —— 优先级比第一轮更低。** 实测内置 WebSearch 的中文表现不差
（限定知乎域也能给出正确中文答案），而 Exa 中文索引弱、$7/1k。要上必须先用
20 条真实中文查询做 A/B。

**砍掉 · research_bot 式 planner。** 我们的 agent 本来就会自己规划搜索轮次，
生态里装机量第一的 research skill 也没有 planner。加一层固定 planner 是拿更笨的
硬编码换掉模型已经会做的事，还多一次往返延迟。

## 八、现成方案实测评测（2026-09-08）

按 <@wangchangxin> 的要求，把候选方案真的装上、拿**必挂的那一页**去打，不看 star 数看结果。

### 结论：官方 `fetch` MCP 今天就能用，而且它能读 WebFetch 读不了的页

[modelcontextprotocol/servers 里的 `fetch`](https://github.com/modelcontextprotocol/servers/tree/main/src/fetch)
——纯 Python（`uvx mcp-server-fetch`），**不要浏览器、不要 API key、不接外部付费服务**。
我用一个最小 MCP 客户端直接打，实测：

| 页面 | 耗时 | 结果 |
|---|---|---|
| **posthog（issue #86910 里必挂那页）** | **6.83s** | **5153 字符正文，准确** ✅ |
| 博客园中文文章 | **2.91s** | **8163 字符干净中文 markdown** ✅ |
| skills.sh（我们必挂那页） | 6.08s（热） | 不挂，但只提取到 622 字符碎片 ⚠️ |
| 知乎（登录墙） | **0.32s** | 明确拒绝并说明 robots.txt 不允许 ✅ |
| 不存在的域名 | 5.10s | 干净的连接错误 ✅ |

四个关键性质，正好对上我们前面定的要求：

1. **不挂**——最长 6.83s，包括那个让 WebFetch 永久挂死的页面。
2. **失败是老实的、有界的**——登录墙 0.32 秒明确拒绝，不会把「请登录」当正文返回。
3. **结构上不会撑爆上下文**——`max_length` 默认 5000 字符，配 `start_index` 分段读，
   模型自己决定要不要往下翻。
4. **是 MCP，所以超时归我们管**——`.mcp.json` 的 `timeout` 字段。

**唯一短板要如实说**：客户端渲染的页面（skills.sh 这种）提取质量差，只有碎片。
这类页面要读全，绕不开真浏览器。

### 其它候选的评价

- **browser-use**（★113k，Python）——**不是一类东西，别用来抓页面。**
  它是"用自然语言下达任务、LLM 驱动浏览器点按钮填表单"，README 的例子是"帮我填工作申请"。
  需要**另一条 LLM 计费通道**（`BROWSER_USE_API_KEY` 等），每步调模型。
  真要用是在"需要登录态和交互"的场景，不是"读一篇文章"。
- **Playwright MCP**（微软官方 ★36.9k）、**chrome-devtools-mcp**（Google ★51.3k）、
  **agent-browser**（Vercel ★42.1k，Rust）——都活跃维护，是 JS 渲染页的正解。
  **共同代价：每个沙箱要一份 Chrome，压缩包就 185MB。**
  我们的 HOME 是**按话题分**的（uv 缓存重复占用已经约 72G，见项目记忆），
  照搬就是再来一次同样的浪费。要上必须**按机器共享一份**，这是前置条件不是优化项。
- **Exa MCP / Firecrawl MCP** ——都是接外部付费服务，属于"要不要升级搜索"那个独立决策，
  和"修挂死"无关，不要混在一起做。

### 因此建议的落地顺序（成本从低到高）

1. **接官方 `fetch` MCP**：零成本、零依赖、今天就能接，直接消灭挂死。
2. **观察一段时间**，统计到底有多少页面栽在"客户端渲染"上。
3. **只有在第 2 步证明确实需要时**，才引入浏览器方案，并且**必须先解决 Chrome 按机器共享**。

这个顺序的好处是：第 1 步就把最痛的问题解决了，而且不需要先想清楚搜索要不要换 Exa。
