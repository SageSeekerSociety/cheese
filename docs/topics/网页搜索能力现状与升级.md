## 目标

回答 @符露夀 的问题：芝士现在的网页搜索怎么实现的；要不要换成
「Exa → 统一 Search MCP → fetch fallback → planner → 共享 cache」这一套。

**所有结论都来自 2026-09-07/08 的实测，不是读文档推断。**
第二轮按 @符露夀 的要求补了 OpenAI 做法、市面常见 MCP、skills.sh 上的 skill，
**并且推翻了第一轮的 P0 结论**——推翻的过程和证据都保留在下面。

## 一、现状：平台没有写过任何搜索代码

搜索能力 100% 来自 Claude Code 自带的两个工具，平台只把工具名翻译成中文
（<&backend/app/domain/agent/chat.py:285>、<&frontend/src/lib/toolLabels.ts:21>）。
没有搜索服务、没有 fallback、没有缓存、没有 planner，也**没有配置任何 MCP server**。

两个工具机制完全不同，这是理解一切问题的前提：

| | WebSearch（搜） | WebFetch（读） |
|---|---|---|
| 谁执行 | **模型服务商那边执行**，我们的机器不发起搜索 | **沙箱自己发 HTTP 请求**，抓回来再喂给小模型总结 |
| 缓存 | 无 | 同 URL 15 分钟，**仅限单会话**，换话题/分身即失效 |
| 超时 | 有 | **没有**（见第二节） |

补充实测：默认「知是 AI Pool」也支持服务端搜索（带 `web_search_20250305`
打网关，返回了真实结果）。但这个能力是**借上游服务商的**，我们没声明依赖也没检测，
哪天换个不支持的池子，表现是**搜索静默消失**，不报错不告警。
另外计费只统计 token、不统计 `server_tool_use`，所以默认池的搜索开销
对预算刹车不可见（<&deploy/metering-proxy/cheese_billing_core.py>）。

## 二、WebFetch 会永久挂死（本话题现场抓到的真 bug）

同一次会话里的两次调用，会话记录时间戳为证：

| 调用 | 开始 | 结束 | 耗时 |
|---|---|---|---|
| WebFetch `www.skills.sh` | 03:59:41 | 04:16:49 | **17 分 08 秒，从未返回**，是人打断才结束 |
| WebFetch `example.com` | 04:18:07 | 04:18:10 | 3 秒 |

同一个 URL 用 curl 下载只要 **2 秒**，所以卡在下载之后。已排除：网络出口（curl 2 秒通）、
计费代理（0 重启、190MB/2GB）、超长无空格串导致的文本处理爆炸（本地实测 <1ms，
**这个假设被我自己的实验否掉了**）。内部确切原因查不到——WebFetch 是 Claude Code
内置工具，源码不在我们手里。

**但确切原因不重要，因为真正的缺陷是「它没有超时上限」**：任何一次内部卡顿都会变成
永久挂起，而不是失败重试。这是上游已知问题，社区甚至专门做了 `webfetch-plus`
这个 MCP 来替换它，理由原话就是 timeout-safe，并给出统计「**挂死的子 agent 里
75% 死在 WebFetch 调用上**」。

对我们的意义很直接：**分身在 WebFetch 上会永久挂死，而房间等不到它**。
这不是体验问题，是可靠性问题。

**怎么修**：我们改不了内置工具，settings.json 也没有对应开关
（`BASH_DEFAULT_TIMEOUT_MS` 那类只管 Bash）。**能加超时的唯一途径是换成我们自己的
MCP——`.mcp.json` 里每个 MCP server 都有 `timeout` 字段。**
所以 @符露夀 提的「统一 Search MCP」是对的，但理由不是「结果更好」，
而是「**内置工具根本没法加超时，MCP 可以**」。这是机械性的理由，不依赖口味。

## 三、第一轮的 P0 结论是错的：知乎/CSDN 不是抓取问题，是登录墙

第一轮我测出知乎 403、CSDN 超时，就断定「需要 fetch fallback」。**第二轮拿真实
文章 URL 做对照实验，这个结论站不住**：

| 源 | 裸 curl（≈现在的 WebFetch） | Jina Reader（专业抓取服务） |
|---|---|---|
| 知乎专栏 | 403 | **200，但只有 489 字节，内容是「安全验证 / 请您登录后查看」** |
| CSDN | 无响应 | **200，858 字节，同样是登录墙** |
| 博客园 | 200 / 35KB | 200 / 12KB 干净正文 |
| 个人博客 | 200 / 519KB | 200 / 27KB 干净正文 |

**知乎和 CSDN 是登录墙，不是反爬**。换 Jina 不行，换无头浏览器也不行
（浏览器一样撞登录墙），换 Exa 也不行。除非拿真实登录态去抓，而那是我们不该做的事。

**更要命的是：加了兜底反而更危险。** 现在 403 是明确失败，agent 知道读不到；
接上 Jina 之后变成 **200 + 一段「请您登录」的文本**，agent 很可能把登录提示
当成正文总结掉——**从"明确失败"退化成"静默给错答案"**。

### 而且这些内容其实已经进来了

把 WebSearch 限定 `allowed_domains=zhihu.com` 再搜，它返回了 9 条知乎链接
**和一段正确的中文答案**。也就是说搜索后端读得到知乎，只是我们自己抓不到。
所以「抓不到知乎」的实际影响，比我第一轮说的小得多。

### 那 fetch 层的真价值是什么

不是「能读到」，是「**读得干净 + 不挂死**」：

- 个人博客 519KB HTML → 27KB 正文（**19 倍压缩**）
- skills.sh 942KB HTML → 正文只有 10.8KB（**98.9% 是 JS 包袱**）

省的是上下文和延迟，不是解锁内容。这个价值真实存在，但和「解锁知乎」完全是两码事。

## 四、市面上在做什么（skills.sh 实测数据）

从 skills.sh 的 JSON 接口（`/api/search?q=`）拉的真实安装量：

| 类别 | 代表 skill | 安装量 |
|---|---|---|
| **浏览器 / 抓取** | agent-browser (vercel-labs) | **806,771** |
| | just-scrape (scrapegraphai) | 244,957 |
| | firecrawl 全家 (firecrawl/cli) | ~100,000 |
| | browser-use | 93,955 |
| **纯搜索** | parallel-web-search | 12,849 |
| | brave web-search | 4,297 |
| | langchain web-research | 3,908 |

**差两个数量级，而且方向一致：市场在补"读页面"，不在补"搜网页"。**
原因很清楚——搜索每个 agent 宿主都内置了，读页面没有。这条外部证据和我们
自己测出来的结论指向同一个地方。

MCP 侧：Exa MCP 是搜索类第一，Playwright MCP（微软官方，30k+ star）是浏览器类第一，
整个生态已有一万到两万个 MCP server。

`agent-browser` 的 `read` 命令内置了分级兜底：先要 `Accept: text/markdown` →
试同名 `.md` → 往上找最近的 `llms.txt` → 最后从 HTML 抽正文。**注意 `read` 不启动
Chrome**；真正能处理交互/登录态的是 `open <url>` 走真实浏览器那条路。

## 五、OpenAI 的做法

- **web search 是托管工具**：$10/1k 次（推理模型）、$25/1k（非推理），
  另加检索内容按输入 token 计费，官方口径每次约 8K token。走 Responses API。
- **deep research 是独立 API**，不是把 planner 塞进普通对话。
- **research_bot** 是 Agents SDK 的示例：Planner → 多个 Search agent 并行 → Writer 汇总成
  markdown 报告。

关键对照：**装机量第一的 `research` skill（mattpocock，462,976 安装）全文只有
794 字节，里面没有 planner**。它只说三件事：起一个**后台 agent**、
只认一手来源（官方文档/源码/规范）、把结论写成**带逐条引用的 markdown 文件**。
——这几乎就是芝士现在「分身 + 实况文档」的做法。

## 六、结论（已按第二轮证据重排）

**P0 · 自建 fetch/search MCP —— 理由是超时可控，不是结果更好。**
唯一能给抓取加上超时的途径，直接止住「分身永久挂死」。顺带做正文抽取压缩
（19 倍那个数字）。**明确不指望它解锁知乎/CSDN**。抓不到时必须**明确报失败**，
绝不能把登录墙文本当正文返回——这是设计上的硬要求，不是优化项。

**P1 · 共享 cache**，长在 P0 的 MCP 里。价值不在省钱（订阅包月），
在于同房间几条分身**看到同一份事实**、少等几十秒。
硬约束：缓存 key 只能是纯查询词，**不能带任何项目私有上下文**，否则等于跨项目泄露。

**P2 · agent-browser 作为重武器按需接入**，用于需要登录态/交互的场景，不做默认路径。

**P3 · Exa —— 优先级比第一轮更低。** 实测内置 WebSearch 的中文表现不差
（限定知乎域也能给出正确中文答案），而 Exa 中文索引弱、$7/1k。要上必须先用
20 条真实中文查询做 A/B。

**砍掉 · research_bot 式 planner。** 我们的 agent 本来就会自己规划搜索轮次，
生态里装机量第一的 research skill 也没有 planner。加一层固定 planner 是拿更笨的
硬编码换掉模型已经会做的事，还多一次往返延迟。
