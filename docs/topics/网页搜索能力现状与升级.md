## 目标

回答 @符露夀 的两个问题：芝士现在的网页搜索是怎么实现的；要不要换成
「Exa → 统一 Search MCP → fetch fallback → planner → 共享 cache」这一套。
下面的现状全部是 2026-09-07 在 dev 机上实测出来的，不是读代码推断。

## 现状：平台没有写过任何搜索代码

一句话：**搜索能力 100% 来自 Claude Code 自带的两个工具，平台只负责把工具名翻译成中文。**

- 仓库里跟搜索沾边的代码只有两处，都是显示层：<&backend/app/domain/agent/chat.py>
  第 285 行把 `WebSearch` 显示成「搜网页」，<&frontend/src/lib/toolLabels.ts>
  第 21 行显示成「搜索网页」。没有搜索服务、没有 fallback、没有缓存、没有 planner。
- **没有配置任何 MCP server**（全仓库找不到 `.mcp.json`，机器上也没有）。

两个工具的机制完全不同，这是理解后面所有问题的关键：

| | WebSearch（搜） | WebFetch（读） |
|---|---|---|
| 谁执行 | **模型服务商那边执行**（服务端工具 `web_search_20250305`），我们的机器不发起搜索 | **沙箱自己发 HTTP 请求**，抓回来再用小模型总结 |
| 依赖 | 项目所用模型池必须支持这个服务端工具 | 沙箱的出网能力 + 目标站肯不肯让抓 |
| 缓存 | 无 | 同一 URL 15 分钟，**只在单个会话内**，换个话题/分身就失效 |

### 实测结论一：默认池的搜索是能用的（我原本猜它不能）

我原以为默认的「知是 AI Pool」走 LiteLLM 转 DeepSeek，不会支持 Anthropic 的服务端
搜索工具，那样的话绝大多数用户根本没有搜索。**直接打网关验证，推翻了这个猜测**：
带 `web_search_20250305` 打默认池，返回了真实的 `web_search_tool_result`，搜到了结果。
所以默认池和 dogfood 的 Claude 池都有搜索。

但这个能力是**借来的、隐式的**：它取决于上游服务商顺手支持了这个工具，我们既没有
声明依赖，也没有任何检测。哪天换个池子不支持，表现是**搜索静默消失**，没有报错、
没有告警，用户只会觉得「芝士变笨了」。

### 实测结论二：真正坏掉的是「读网页」，而且中文内容最严重

沙箱出网是通的（example.com / google / bing 直连都是 200），所以问题不在网络，
在反爬。实测抓取成功率：

- ❌ 知乎（含专栏）403 —— WebFetch 报 403，**自己用 curl 加浏览器 UA 照样 403**
- ❌ CSDN 直接超时无响应
- ✅ GitHub / arXiv / 掘金 / 博客园 / 微信公众号文章 200

知乎和 CSDN 是中文技术内容命中率最高的两个来源，现在是完全读不到的。而 WebSearch
搜出来的链接里它们占比不低——**搜得到、打不开**，这是用户体感最差的一环。

### 实测结论三：默认池的搜索花费不在账上

<&deploy/metering-proxy/cheese_billing_core.py> 只统计 token（input/output/cache），
不统计 `server_tool_use`。服务端搜索在 DeepSeek/智谱那边是单独计费的，所以默认池上
的搜索开销**对我们的预算刹车完全不可见**。订阅池不受影响（包月）。

## 判断：这套方案里三件值得做，两件不值得

按「投入产出」排，不是按 @符露夀 列的顺序：

**P0 · fetch fallback —— 唯一一个修的是已实测的真故障。**
其余几项修的都是「理论上更好」，只有这条对应知乎/CSDN 读不到的实锤。但要注意：
**朴素的 curl 兜底救不了知乎**（我试过，带 UA 也是 403），得上真的渲染器
（headless 浏览器）或者付费 reader 服务才有意义。这条要么做对，要么别做。

**P1 · 统一 Search MCP —— 修的是「能力是借来的」这个结构性风险。**
把搜索收成我们自己的 MCP 工具后，搜索就不再取决于项目选了哪个模型池，所有 agent
（芝士本人的轮次、沙箱里的 Claude Code、分身）拿到的是同一个工具、同样的行为。
顺带把上面那笔隐形花费变成看得见的。这是列表里唯一有结构价值的一项。

**P2 · 共享 cache —— 有价值，但价值不在省钱，在省时间。**
订阅是包月的，缓存省不出钱。真正的收益是：一个房间派出三条分身各搜同一个问题，
现在要各等一遍；共享后省几十秒，而且三条分身看到的是**同一份事实**，不会因为
搜索结果抖动而得出互相矛盾的结论。这条应该长在 MCP 里面，所以排在 P1 后面。
一个要提前想清楚的点：缓存跨项目共享时，**key 里不能带任何项目私有的上下文**，
只能是纯查询词，否则等于把 A 项目的问题泄露给 B 项目。

**P3 · Exa —— 需要先评测，不能直接上。**
Exa 的强项是英文/技术内容的语义检索，而且**它直接返回正文**（这一点其实能顺带
解决一部分 P0 的抓取问题，是它对我们最大的价值，不是排序更准）。但它的中文索引很
弱，而我们的用户（人大那批、写 PRD 的）主要搜中文。定价是 $7/1k 次搜索
+ $1/1k 额外结果，签约前应该拿我们真实的 20 条中文查询跑一次 A/B，
用数据决定，别因为它名气大就换。
（定价来源：[Exa AI Pricing Explained 2026](https://fastcrw.com/blog/exa-pricing-explained)、[Web Search API Pricing Compared 2026](https://fastcrw.com/blog/web-search-api-pricing-2026)，2026-03 起标准搜索由 $5/1k 涨到 $7/1k。）

**P4 · research_bot 式 planner —— 建议不做。**
我们的 agent 本来就是 agentic 的，会自己决定搜几轮、怎么改写查询。在前面插一个
固定 planner，是把模型已经会做的事换成一段更笨的硬编码，还平白多一次往返延迟。
这一项是从「一次性问答机器人」的架构里抄过来的，跟我们的形态不匹配。
