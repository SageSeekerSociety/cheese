# @提及前缀误匹配

## 目标

修掉聊天输入框里的一个 @ 解析 bug：@ 一个 handle 时，如果名册上另有一个人的 handle 是它的前缀，短的那个会先被识别掉。@符露夀 报的原始现象是打 `@andylizf` 变成了 andy。

## 现象与根因

符露夀发出来的那条消息，落库的原文是 `<<<<@andy>>lizf>>`，refs 只认出了 `user:andy`。

**是前端的锅，后端是对的。** 用真实名册跑一遍 `frontend/src/components/ChatPanel.vue` 里的 `expandMentions()`，一字不差地复现出了那个字符串；同一段原文喂给后端的 `expand_mention_names`（<&backend/app/domain/mentions.py>）则正确地得到 `<@andylizf>`。后端是作为兜底跑在前端之后的，但它拿到的已经是被毁掉的字符串——`<<@andy>lizf>` 看上去已经是规范化过的，没有任何东西能把它修回去。

前端那个函数用的是 `text.split(pat).join(token)`，比后端少三道保护，其中两道被这个例子踩中：

1. **同一个模式跑了两遍。** andylizf 的显示名和 handle 是同一个字符串，所以 `@andylizf` 这条替换规则进列表两次。第一次得到 `<@andylizf>`，第二次在这个结果里又匹配到 `@andylizf`，包成 `<<@andylizf>>`。后端有 `seen` 集合去重。
2. **短 handle 啃进已生成的 token。** 接着轮到 `@andy`，它在 `<<@andylizf>>` 里照样匹配，于是 `<<<@andy>lizf>>`；因为第 1 条它还会再跑一遍，最终四层括号。后端用 `(?<!<)` 挡住已编码 token，用 ASCII 词边界挡住「andy 啃掉 andylizf 的前半截」。

同一个坑对 `@李甘` / `@李甘-nictheboy` 同样成立。

## 修法

commit `31f9729`。把这段展开抽成共享模块 <&frontend/src/lib/expandMentions.ts>，逐条对齐后端 `mentions.py` 的三道保护（模式去重、`(?<!<)` 跳过已编码 token、ASCII 词边界），ChatPanel 改为调用它。

**为什么不能干脆删掉前端这份、全交给后端**：输入框要在发送前知道「这条草稿叫不叫醒芝士」（`summonOn` 读的是展开后的正文），所以客户端必须有一份。两份实现就是两次分歧的机会，而分歧是无声的——前端产出什么，后端都当作已经规范化。共享模块把两份收敛成一套规则。

测试 <&frontend/src/lib/expandMentions.spec.ts>，13 条：本例的 handle 前缀、显示名前缀（李甘 / 李甘-nictheboy）、短的那个单独用时仍然要认、只是碰巧同前缀的 `@andyzzz` 不能被误认、CJK 名字后面直接接汉字（`@李甘来负责`）仍要认、已规范化的 token 不重复包裹、大小写、群播 `@all`/`@here`、话题标题、空显示名不吞掉所有 @。
