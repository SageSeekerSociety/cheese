## 问题

反馈：验收卡（acceptance card）指定了验收人，但 accept 端点从不校验"当前操作人 == 卡片上指定的验收人"，且该端点疑似无鉴权、操作人由请求体自报。若属实，任何能访问 API 的一方都能采纳任何一张卡——安全漏洞。

## 目标

1. 定位 accept 端点的路由 / service / repository 实现，核实反馈是否属实。
2. 若属实：
   - 路由加 `Depends(require_auth_user)`（或等价鉴权依赖）。
   - service 层校验认证用户 handle == 卡片记录的验收人 handle，不匹配用 `app.core.errors` 里的错误类型拒绝（不用裸 `HTTPException`）。
3. 补充测试：非指定验收人被拒 / 指定验收人成功 / 未认证被拒。
4. `task check` 全绿。

## 约束

- 遵循项目分层约定（route 无业务逻辑，校验放 service）。
- 错误处理走 `app.core.errors`，不要裸 `HTTPException`。
- 测试用真实行为测试，不检查源码实现细节。

## 核实结果（漏洞属实，且比简报描述的范围更广）

`backend/app/api/routes/accept.py` 的 5 个决策端点（approve / accept / reject / revoke / reassign）均无鉴权，`decided_by`/`approver_handle` 直接取自请求体自报字符串，`AcceptService` 从不校验调用者身份：
- `accept()`：从不检查 `decided_by == card.reviewer_handle`。
- `revoke()` 虽有 allow-list（原采纳人/owner/lead），但比对的是**未验证**的自报 `decided_by`，形同虚设。
- 这些端点也不在 `main.py` 的 `_CHEESE_WRITE_PATHS`（`cheese_token_gate` 中间件）覆盖范围内——只有卡片*创建*端点受 `x-cheese-token` 保护。

**好消息**：该 domain 已有一套现成的、其他兄弟路由（`topics.py`/`topic_members.py`/`projects.py`）在用的身份解析机制——`app.api.auth.ActorResolver`（`ActorResolverDep`），从 `Authorization: Bearer` 校验真实登录身份（`via="token"`），只在没有 token 时才退化到自报 handle（`via="handle"`，被标记为 deprecated fallback）。前端（`frontend/src/api.ts`）已经在每次请求上带真实 `Authorization: Bearer <authToken()>`——`accept.py` 只是漏接了这套机制，不需要新造鉴权系统。这正是简报里说的"等价机制"。

## 修复方案

1. `accept.py` 五个决策路由加 `resolver: ActorResolverDep`，用 `resolver.resolve(fallback_handle=...)` 解析出 `actor`；`actor.authenticated` 为假（未持有效 Bearer/cheese token）一律 401（`AuthenticationRequiredError`）。
2. 把解析出的 `actor.handle`（而非请求体自报值）传给 service 层作为 `decided_by`/`approver_handle`——从根上堵住伪造身份的口子（这一步顺带修好了 `revoke()` 原本形同虚设的 allow-list）。
3. `AcceptService.accept()` / `reject()` 新增校验：`decided_by != card.reviewer_handle` → `ForbiddenError`（403，与 `authorize_topic()` 里"你不是这个话题的成员"同款错误类型）。
4. `approve()` / `reassign()` 只要求已认证，不额外限定具体人选——沿用现有设计（`reassign` 代码注释明确"anyone can re-route"），未在简报范围内引入新业务规则。
