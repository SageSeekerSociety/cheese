# 二、两个设计问题的答案（2026-08-25，基于全项目 225 件活的真实数据）

数据来源：`GET /projects/{id}/tasks` 全量，225 件活 / 33 个有活的房间。

## Q1「计划 / 分母」——**不要分母，但「一次派活」这个分组是真的**

数据说分母在我们这儿是假的：

- 一共 **135 次派活**，其中 **92 次只派了一件**。
- 最大的房间派了 **57 件活，分 47 次**派出去 —— 分母会被改写 47 次。
- **174 / 225** 件活是在**还有兄弟活在跑的时候**派出去的。房间是边跑边加，不是先出计划再执行。

Qoder 有 `21` 这个分母，是因为它先由 Lead Agent 出一份计划再派活；我们的活是随时 split 出来的。
硬造分母＝造一个没人维护、天天变小变大的数字。

但**成批派活是真的**：43 次派活一次派了 ≥2 件，**133 件（59%）**是成批来的，最大一批 16 件。

**结论**：显示口径改成 `3 件在跑 · 12 件已交付`（都是「到目前为止」，不假装知道总数），
分组按**「批」**（同一次派出去的一组），不发明「计划」这个新对象。

### 但「批」现在推不出来 —— 一个字段名存实亡

`tasks.upgraded_from_block_id` 全项目 **225 行里只有 1 行有值**。
它的注释说这个字段是为了「让时间线上那个位置一直是通向这条支线的活链接」，
但只有「把一条消息升级成活」那条路写它（<&backend/app/domain/topic/services.py> 约 779 行），
`cheese split` 走的 `dispatch_task` **从来不写**（<&backend/app/api/routes/topics.py> 的 `split_topic`）。

**所以最便宜、也最该先做的一件事：让 `cheese split` 把 `upgraded_from_block_id` 填上。**
一处改动同时买到三样：

1. 房间时间线上的「已派出」有了**永久锚点** —— 现在那个标记是推导出来的，只在派出那一瞬间出现，往下滚就没了；
2. **「批」白拿** —— 同一个 block 派出去的就是一批，不需要新表、不需要人维护；
3. 不需要「计划」这个新对象，Q1 就答完了。

## Q2「活之间的依赖」——**不要。而且理由已经写在我们自己的代码里**

<&backend/app/domain/room_task/models.py> 的模块 docstring 已经明确写了这是**故意不做**：

> Deliberately absent, and not an oversight: **dependencies between tasks**.
> The design names them, but nothing writes or reads one today, and an empty
> join table is indistinguishable from a live one to whoever reads this next.

`TaskStatus` 只有 open/closed 两个值也是同一条理由（「blocked / in review 会是一个没人写也没人读的词」）。

数据同意这个判断：

- 只有 **34 / 225（15%）** 的活是在某个兄弟活关掉后 10 分钟内派出去的；
- **78%** 是在兄弟还在跑的时候派的 —— 并行派活才是主流，A 等 B 不是。

**更硬的一条**：就算标上 `Blocked by Task 10`，**也没有任何机制会在 Task 10 完成时唤醒 Task 11**。
`cheese split` 是单向的，一件活完成时不会去戳别的活。
那个标记会是**一句谎话**，比没有更糟 —— 人看到「Blocked by」会以为它解开时事情会自己动起来。

要做依赖，前提是先有「一件活完成时能唤醒另一件活」这个**机制**，不是一个字段。那是另一个话题。

## 数据顺手挖出来的第三件事（比依赖图重要得多）

- **`owner_handle` 只有 144 / 225（64%）有值** → #614 新做的任务面板上，**36% 的行会显示「暂无负责人」**。
  一个「谁在做」有三分之一答不出来的看板，先修这个比加依赖箭头值钱。
- **交付这一段是真堵点**：215 件已收工的活里，**70 件（32%）根本没有验收卡**，25 件被撤销，120 件已采纳。
  Qoder 的 `Review +8348 -850` 之所以刺眼，是因为它承认「审」是个独立阶段；我们这一段基本是黑的。
- 活的寿命：中位 2.5 小时，p90 26.8 小时，最长 136 小时。

# 三、界面上的结论（问题定完之后）

## 做（按性价比排）

1. **`cheese split` 填 `upgraded_from_block_id`** —— 后端一处，换来永久锚点 + 批分组（见 Q1）。
2. **行里写「它最近干了什么」，不是状态词 + 相对时间。**
   <&frontend/src/components/panels/PanelTasks.vue> 已经在拉每条支线最新那一块
   （`listRoomTasks(roomId, {limit:1})`），却只用了它的 `created_at` 做时间戳、**正文丢掉了**。显示出来几乎零成本。
3. **常驻一条可折叠细条**，放在房间时间线顶部：`3 件在跑 · 12 件已交付`，点开展成现在的任务 tab。
   派活发生在对话里，回执也该在对话视野内，而不是藏在右侧一个 tab 里。
4. **把「要审多少」提前说出来**（`+X -Y`）—— 现在到递卡那一刻才知道攒了多大的 diff。
5. **补 owner** —— 36% 的行没有主。

## 不做

- **分母 `12/21`** —— 见 Q1，我们没有「计划」这个对象，分母是假的。
- **活之间的依赖 / `Blocked by`** —— 见 Q2，没有唤醒机制，标了就是谎话。
- **角色化人名**（`Full-Stack Engineer Tom/Ryan`）—— 那是同一个模型扮的，名字是装饰；
  我们的 `owner_handle` 指向真人，掺假名会让人以为分身能力不同。
- **Expert Canvas 并排卡片墙** —— 它解决「一次并行 8 个 agent 看不过来」，靠给每个 agent 一列。
  我们的模型是人**进房间读上下文**，且本项目已 169 个房间，画布当场就烂。
  真要鸟瞰，缺的是**项目级一张表**（`GET /projects/{id}/tasks` 数据已经有了，界面上还没有全项目视角），不是画布。
