## 结论

根因**在本仓库范围内**，已修复。不是外部容器编排平台的行为——是这个仓库自己的沙箱生命周期代码，在"项目环境镜像变更"这一条路径上用 `docker rm -f` 无预警强杀容器。

## 根因

沙箱容器是每话题一个、`sleep infinity` 长期存活、跨轮次复用的；正常的轮次结束、超时都不会碰容器（这也是反馈里说"只有环境变更会杀"的原因——其它路径确实不杀）。但两处独立实现的生命周期代码，在检测到"当前容器镜像 ≠ 项目配置的镜像"时，会立即 `docker rm -f` 后重建，`-f` 直接 SIGKILL、无优雅期、事发前后都没有任何通知：

- <&backend/app/domain/agent/tmux_provider.py> `_ensure_container`（交互式 tmux 后端，`AGENT_BACKEND=tmux`）
- <&backend/sandbox/claude-sbx>（SDK 后端的 shim 脚本，`AGENT_BACKEND=sdk`，**是默认后端**）

触发时机：不是切换镜像设置的那一刻杀，而是切换后该话题**下一次开始跑轮次**时，在轮次真正开始前同步杀掉旧容器——此时容器里如果还有话题的交互会话或后台进程（比如后台跑的测试、起着的开发服务器），会被一起无声带走。

## 修复

不改变"镜像变了就必须重建容器"这个设计本身（这是合理的，环境要跟着项目配置走），只补上反馈里点名要的东西：**预警，而不是无声杀掉**。

新增 <&backend/app/domain/agent/sandbox_notices.py>：`warn_image_switch_rebuild(topic_id)`，容器因镜像切换被重建时，往话题时间线里插一条系统事件，说明旧会话/后台进程已被终止、需要重新起。两条生命周期路径分别接入：

- tmux 后端：`_ensure_container` 检测到镜像不匹配、`rm -f` 重建完成后，直接 `await` 这条通知（同一个 async 函数里，事件循环里跑，天然顺序正确）。
- SDK 后端（<&backend/app/domain/agent/compute.py> `LocalDockerProvider._sandbox_config`）：Python 侧本来不参与这个判断（判断和 `rm -f` 全在 `claude-sbx` shell 脚本里），补了一个只读的镜像比对（`docker inspect` 镜像名 vs 本轮解析出的镜像），发现要变就在 shim 真正执行 `rm -f` 之前，用 `asyncio.create_task` 异步排一条通知，不阻塞轮次启动。

两条路径都是 best-effort：通知失败（DB 写入异常等）只记日志，绝不影响轮次本身。

## 已知限制 / 未做的事

- 通知只落时间线（DB persist），**没有接实时推送**（其它路径用的 broker publish 没接进来）——用户如果当时没开着这个话题的页面，要等下次刷新/下一轮事件才会看到，不是真正"事前"预警，是"事发后立刻可见"。
- SDK 后端那条是**只读镜像比对的旁路检测**，跟 shell 脚本自己的判断是两份独立实现（本来就是两份重复实现，这次没有合并成一份 — 合并涉及把 shim 的重建决策搬进 Python，改动面更大，超出这次反馈的范围）。
- shim 脚本里还有两条同样 `docker rm -f` 无预警的迁移路径（补发端口映射、补挂载 cheese CLI），只在"旧容器第一次遇到新版本 shim"时触发一次，风险和触发频率都低很多，这次没有一并处理——如果之后还有反馈指向这两条，再补。

## 验证情况

宿主机磁盘从 64G 扩容到 256G 后补跑了验证，磁盘确实是之前的阻塞项——扩容后 `uv sync` 能正常下载、装包了。补跑过程中发现 `.claude/scripts/check.sh` 的 `run_ruff()` 有个已存在的脚本 bug（无 `.venv/bin/ruff` 时硬编码 `uv run --no-sync ruff`，跟 scratch-venv 分支需要的 `uv run` 不一致，导致 ruff 在"从未同步过 `.venv`"的宿主上永远起不来），当时顺手在本工作区改了一行修掉——但这处代码（`check.sh:83`）跟另一个专门拆出去的子话题「check.sh的ruff兜底硬编码no-sync」撞了，为避免两份工作区各自递验收卡合并同一处代码，**已把这处改动撤销**，交给那个专门子话题处理（它的验证更完整）。本工作区现在只保留任务范围内的改动：`sandbox_notices.py` 新增、`tmux_provider.py` 和 `compute.py` 的接入。验证时用的是撤销前临时打的那个补丁，结果如实记录如下（供参考，不代表本工作区最终代码状态含这处修复）；`compute.py` 因新增 `import` 触发的 ruff format 问题（跟 check.sh 那处无关，是本话题自己改动引入的）已单独修好并保留。

修完后（含临时的 check.sh 补丁）`bash .claude/scripts/check.sh --full` 结果：

- **ruff**：PASS（623 files already formatted）
- **pyright**：PASS（0 errors, 0 warnings）
- **pytest**：FAIL——`database unreachable at localhost:5433`。这个沙箱没有 `docker` 命令，Postgres/Valkey 基础设施起不来，和磁盘无关，是这类沙箱本身缺 Docker-in-Docker 能力的已知限制（`check.sh` 注释里"quality gate 环境没有可用 Postgres"说的就是这种宿主）；这次没有条件真正跑集成测试验证行为，只能保证代码通过静态检查。

另外顺带发现一个和这次改动无关、但和"容器重建"这个主题相关的现象：这个仓库用 jj 做版本控制，`.jj/repo` 里存的是指向 `../../../../<某个 UUID>/.jj/repo` 的相对路径，那个 UUID 目录在当前容器里已经不存在了，导致 `jj status`/`jj log` 等命令直接报错、版本控制完全不可用。看起来是沙箱在某次重建后，`.jj` 的仓库存储路径跟容器身份（而不是稳定的挂载点）绑定，换了容器就断链。这个不在这次任务范围内（属于沙箱基础设施，不是仓库代码能修的），只记录下来，没有处理。
