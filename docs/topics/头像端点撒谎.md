修 GitHub issue #417：`GET /api/avatars/{id}` 和 `/api/avatars/default` 在「DB 里有 avatar 行、磁盘上没文件」时，
返回 **200 + `image/png` + 108 字节解不了码的假 PNG + 一年长缓存**。纯后端，一个 PR 交付。

## 状态：代码已改完、测试已绿、自证已做，等全量 pytest 跑完就递卡

## 改了什么

只动了两个文件。

### <&backend/app/api/routes/avatars.py>

同一段坏逻辑原本在 `get_default_avatar()` 和 `get_avatar_by_id()` 里各抄了一份，两处都改了，并且抽成了共用函数——
这样「长缓存只发给真实文件」不再靠两处各自记得，而是**结构上只有一条路径能发出长缓存**：

- `_read_avatar_file(avatar_id)`：读到就返回字节，文件不在返回 `None`。
  用「直接开、捕异常」代替原来的「先 `exists()` 再开」，少一次 stat，也没有中间那段可能过期的窗口。
- `_stored_avatar_response(...)`：**唯一**会发出 `Cache-Control: public, max-age=31536000` 的地方，只在手里真有文件字节时才被调用。
- `_sniff_media_type(content)`：按 magic 字节判断真实类型（PNG / JPEG / GIF / WebP），认不出来返回 `application/octet-stream`，
  不再写死 `image/png`。dev 上的 616 号头像存的其实是 JPEG，之前全靠浏览器自己嗅探才没露馅。
- 两处兜底分支都换成 `raise NotFoundError(...)` → **404**，响应上没有长缓存。

**为什么是 404 而不是占位图**：视觉结果完全一样（今天那 108 字节在浏览器里就是破图图标，404 也是破图图标），
但 404 让监控和排查第一次能看见这个故障。聊天面板那半（PR #414 已上线）的 `@error` 兜底会照常把它换成彩色首字母。

### <&backend/tests/integration/test_avatars.py>

新增 3 条 + 改写 1 条，全部是功能测试（起真库、打真接口、从 HTTP 响应读结论）：

| 测试 | 钉住的行为 |
|---|---|
| `test_get_avatar_with_missing_file_is_404_and_not_cached` | 有 DB 行、无磁盘文件 → 404，且响应里没有 `max-age=31536000` |
| `test_get_default_avatar_without_file_is_404_and_not_cached` | `/avatars/default` 同上（**这条是改写的**，见下） |
| `test_get_uploaded_jpeg_reports_jpeg_and_stays_cacheable` | 传真 JPEG → `content-type: image/jpeg`，**仍然**带长缓存 |
| `test_get_uploaded_png_reports_png` | 传真 PNG → `content-type: image/png` |

`test_get_default_avatar` 原本断言的就是这个 bug（200 + 长 max-age），所以必然要改；
测试里写了注释说明原断言断的是 bug 行为。`test_get_uploaded_avatar`、`test_get_avatar_without_auth`、
`test_avatars_contract.py` 全部保持原样、保持绿。

**一个刻意的取舍**：「无文件」那条用了一个 9 亿以上的显式 id 造行，而不是删磁盘上的文件。
因为上传接口写的是所有 xdist worker 共享、且不随事务回滚的目录，而每个 worker 的 avatar 序列都从 6 开始（seed 迁移 setval 到 5），
去删文件会踩掉别的 worker 正在用的那份。挑一个谁也上传不到的 id，「文件不存在」才是被安排出来的事实而不是运气。
