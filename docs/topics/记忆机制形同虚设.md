机制的准确说法是：**jj 0.42 把它写的所有元数据都创建成 0600，且无视 umask**——宿主机上任何 umask 或默认 ACL 都挡不住；而 backend 跑在 uid 1001、tmux/沙箱镜像跑在 uid 1000，两个 uid 不同组，于是每个 jj 文件对沙箱都不可读，沙箱里 `jj log` 直接 "Permission denied"。（不是"`.jj/repo/config-id` 被硬编码成 0600"，也不是"uid 必须对齐 1000"；`backend/Dockerfile:148` 建的是 uid 1001。）

**这正是论证要的那种知识**：跟角色无关、换谁来都成立、踩一次的代价是全平台停摆几小时，而且已经贵到值得为它单开一个测试文件。把它锁在 per-agent 池里，等于赌下一个 handle 会自己再踩一遍。

### 方案（四步，可分别取舍）

1. **把 `[坑]/[约定]/[事实]` 变成字段。** 加 `kind` 列，老数据按前缀回填、无前缀的归"事实"。**纯加法，不删不改任何内容**（符合简报「不许丢」的约束）。
2. **注入时分块，按会不会咬人排序。** `## 别再踩的坑`（坑）放在最显著位置、靠近约束区；`## 本项目的规矩`（约定）；`## 背景事实`（其余）。同样 50 条，但读的人能一眼分出哪几条是拦路的。
3. **按当前话题做相关性排序，而不是全量平铺。** 直接复用坏法 1 刚做出来的打分器：拿当前话题标题 + 活文档首段当 query 给记忆打分，top-N 提到「**跟你手上这件活最相关**」一节，其余照常。**零新增依赖，零新增模型调用。**
4. **每条带上日期和来源话题。** 27/63 已经自己在正文里写日期了，说明这是真实需求；让芝士能自己判断"这条是不是过时了"。

### 明确不做

**不做自动遗忘、不做自动改写、不做 LLM 摘要压缩。** 60 多条是真实资产，任何自动删改都可能丢掉那条本来能救命的；简报的约束是"不许丢"，压缩是"丢得更好看"，不是不丢。

### 需要确认的两点

- 第 1 步要一次 migration（加列 + 回填）。可逆、不删数据，但要过一次迁移评审。
- 第 3 步会让注入内容随话题变化，可能出现"上一轮看得见、这一轮看不见"。**必须配合坏法 2 的「另有 N 条」提示**（已经做了），且被筛掉的仍然 `recall` 得到——否则是把一个可见的截断换成一个不可见的。
