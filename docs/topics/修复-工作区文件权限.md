## 目标

根治 P0-1：沙箱容器与后端进程用不同 uid 共享同一个 jj store，谁先落下 `.jj/repo/config-id`（0600）谁就把另一方锁死。修完要满足：跑过 jj 之后文件接口仍可读；芝士新建的文件人能保存、人保存过的文件芝士能改。

## 复现与根因（已实测确认，比简报描述更宽）

沙箱里 jj 0.42.0 实跑，证据链完整：

1. **两个 uid 都是写死的**：沙箱镜像 `FROM node:22-bookworm-slim` + `USER node` = **uid/gid 1000**（<&backend/sandbox/Dockerfile>），`tmux_provider` 用 `--user node` 起容器；后端镜像自建 `cheese` 用户 = **uid/gid 1001**（<&backend/Dockerfile> 第 147-148 行）。
2. **两者共享同一个 store**：`sandbox_vcs_mounts()` 把主仓的 `.jj` 和 `.git` **读写**挂进每一个沙箱容器（<&backend/app/domain/workspace/service.py>），所以两个 uid 在同一份 jj store 上读写。
3. **jj 把 store 文件写成 0600，且 umask 管不着**：实测 `umask 022` 下，`op_store/operations/*`、`op_store/views/*`、`index/segments/*`、`index/op_links/*`、`store/extra/*`、`workspace_store/index`、`working_copy/{checkout,tree_state}` 全是 `0600`——jj 走的是「临时文件 + persist」，0600 是显式模式，不是 `0666 & ~umask`（同目录下少数直写文件是 644，正好说明两条路径并存）。
4. **`jj config set --repo` 落下 `.jj/repo/config-id`（0600）**，属主 = 执行者。这正是 `_ensure_jj()` 在仓库初始化时跑的两条命令。
5. **另一方之后跑任何 jj 命令都全废**：把 config-id 设为不可读后，主仓和 workspace 里的 `jj status` / `jj diff` 一律
   `Internal error: Failed to determine the secure config for a repo → Cannot access .../.jj/repo/config-id: Permission denied`（rc=255）。
6. **后端把它翻成 422 并放大到全项目**：`_jj()` 非零退出 → `ValidationError` → HTTP 422（<&backend/app/core/errors.py>）；而 `_tree()` 是 list_files / read_file / write_file / raw 的必经之路，每次都会走 `_catch_up_with_branch` → `_jj(wt, "diff", "-s")`。于是**整个项目每个话题**的文件面板、消息里的文件 chip、文档内嵌图片同时 422。

**做这张卡的过程中，另一半就在现场发作了一次**：本沙箱里 `jj diff -s` 直接报

```
Could not create named temp file in '/de808b13-.../.git/objects'
Permission denied (os error 13)
```

——共享主仓的 `.git/objects` 属主 1001、模式 755，而我是 1000，写不进去。这不是 jj 特有的，`.git` 侧同样中招（所以修复也给 `_git()` 加了同一套权限判定）。不影响本卡产物：平台的快照是后端以 1001 跑的，写得进去。

**方向是对称的，两个方向线上都发生过**：

- config-id 属主 1000 → 后端全废 = 本话题这条 P0。
- config-id 属主 1001 → 沙箱里 jj 全废，已被两个历史话题当成"环境限制"记了下来（<&docs/topics/两阶段采纳PR迭代闭环.md>、<&docs/topics/merge后结果回房间.md> 里都写着"config-id 属主 uid 1001，当前进程 uid 1000，Permission denied"，一整批测试被判成"沙箱环境问题"）。当时的归类是错的，那就是这个 bug 的另一半。

## 方案：uid 对齐，后端向沙箱看齐（1001 → 1000）

沙箱侧的 uid 是我们**不完全控制**的那一侧：基础镜像是 `node:22`（node = 1000），`cheesex-dev` 继承它，项目还能通过 `sandbox_image` 指到别的镜像，而 `_create_container` 已经硬假设镜像里存在 `node` 用户。后端镜像则 100% 是我们自己的。所以把后端的 uid/gid 从 1001 改成 1000，是唯一一处改动、且对未来任何 node 系镜像天然对齐。

### 否决了什么

| 方案 | 否决理由 |
|---|---|
| 调 umask | **实测无效**。jj 的 0600 是显式创建模式，不受 umask 影响（见上面第 3 条证据）。 |
| 共享组 + setgid + POSIX 默认 ACL | 同理无效：显式 0600 会把组位直接抹掉，默认 ACL 也会被创建模式 mask 掉。 |
| 事后/定时 chmod 修回来 | 打补丁：竞态窗口内照样 422，而且每加一个 jj 新文件就要补一次名单。简报也明确否决。 |
| 不把主仓 store 挂进沙箱 | 沙箱里 jj/git 直接不可用，产品倒退。 |
| 后端读文件不走 jj（把 catch-up 从读路径摘掉） | 只缩小爆炸半径，不治本；catch-up 本身有真实用途（机器直推的提交要落到工作区）。 |
| 沙箱向后端看齐（node 改成 1001） | 也能对齐，但把 uid 焊死在我们不完全控制的一侧，且要重建 base + dev 两个镜像；现存 `.sessions/**` 里 1000 属主的会话文件会反过来锁死容器自己。 |

### 迁移代价（必须做，否则改完后端起不来）

> 王昌鑫已确认：属主移交按下面这个脚本的做法走（幂等 + marker + 临时 root 容器，不需要 box 上 sudo），无需改动。

宿主上绑定挂载的历史文件属主是 1001（`WORKSPACES_HOST_PATH`、`UPLOADS_HOST_PATH`），后端改成 1000 后读不了自己的旧数据 → 需要一次性 `chown -R 1000:1000`。已配套：一个幂等的迁移脚本 + 后端启动自检（属主不对时明确报错，而不是等到 422 才发现）。

## 改了什么

- <&backend/Dockerfile>：`cheese` 用户 uid/gid 1001 → 1000，并在同一条 `RUN` 里 `test "$(id -u cheese)" = 1000` 自校验——万一基础镜像哪天占了这个 uid，是构建红，不是线上文件面板红。
- <&backend/sandbox/Dockerfile>：`test "$(id -u node)" = 1000` 把 base image 给的 uid 钉在构建期。`node` 不是我们写的用户，是 node:22 给的，所以只能断言、不能假设。
- <&backend/app/domain/workspace/service.py>：`AGENT_UID`/`AGENT_GID` 作为单一事实来源；新增 `WorkspacePermissionError`，`_jj()`/`_git()` 遇到权限类失败时报出「当前 uid=X，应为 1000」而不是一坨 jj 内部报错；读写文件的 `PermissionError` 收敛成干净的 422，不再 500；`audit_workspace_ownership()` 供启动自检。
- <&backend/app/main.py>：启动时跑自检，store 有当前进程读不了的文件就 ERROR 级点名（非致命，一个野文件不该拦住整个平台起不来）。
- <&deploy/fix-workspace-ownership.sh> + <&deploy/deploy-docker.sh>：幂等、marker 保护的一次性属主移交，在临时 root 容器里做 chown（box 上不需要 sudo），排在换版之前——新后端起来时不能发现自己读不了自己的历史数据。覆盖三个绑定挂载：workspaces、uploads，以及 **apphome**（后端的 `HOME`。`config-id` 只是个 20 位十六进制指针，真正的 per-repo secure config 落在 `$HOME/.config/jj/repos/<config-id>/`——现场核对过，漏了这个挂载等于只搬了半边）。宿主机 git 凭据文件 是运维自己的私密文件（600、不在 git 里），脚本**只查不改**：读不到就直接把 deploy 打红并给出该跑的 `chown`——私有仓 push 静默退化成"git 提示失败"正是这个话题要消灭的那类伪装故障。（**这条已在 2026-08-11 被推翻，见文末《事后：这张卡自己踩了一次》**。）
- <&docs/infrastructure.md>：把「后端必须跑在 uid 1000」写成运维口径。
- 回归测试：<&backend/tests/unit/test_workspace_uid_alignment.py>（10 条）+ <&backend/tests/integration/test_workspace.py> 里一条端到端的。

## 交付为什么卡住（PR #248，2026-08-11 查）

不是这次改动的问题，是采纳链路上的一个死结。实测到的事实：

1. `GET /topics/{id}/pr-checks`（后端拿采纳者的 token 直连 GitHub）返回：PR #248 `state=open`、`checks=[]`、**`mergeable=false`**。
2. 平台的判定链在 <&backend/app/domain/review/github_pr.py> `_resolve_zero_checks`：check-runs 为空 → 再查 check-suites → 没有 `github-actions` 的 suite 且熬过 120 秒宽限 → 判成「没有任何 workflow 会对这次改动触发检查」。线上跑的那版在这之后不再自动合并，改成交给人（这段措辞不在平台 main 里，说明 box 上的镜像领先于 main）。
3. 但这个判定与事实不符：本分支实打实改了 6 个 `backend/**` 文件，而 <&.github/workflows/test.yml> 的 `pull_request` 触发条件正是 `branches: [main]` + `paths: ['backend/**', …]`，**本该触发**。
4. `mergeable=false` 正好解释了差异：`pull_request` 事件的 run 跑在 `refs/pull/N/merge` 上，合并 ref 建不出来（冲突）时 GitHub 根本不会创建 run，也就不会有 check-suite——于是「零检查」和「不可合并」是同一件事的两面，而不是两个独立故障。
5. 而平台**没有任何路径**会把 base 同步进一个已经开着的 PR 分支：<&backend/app/domain/workspace/service.py> `push_topic_branch_for_github_pr` 只在 GitHub 因 `workflows` scope 拒推时才同步 base；`_repush_if_local_head_moved` 只在**本地** head 动了才重推；`_catch_up_with_branch` 追的是话题自己的分支，不是 base。

合起来就是死结：分支一旦落后到与 main 冲突 → 永远零检查 → 永远被零检查门禁扣在「等人」。这不属于本话题的链路（本话题只动 uid/权限），应另开一张卡。

### 已自行解开（2026-08-11）

在工作区里把 GitHub main 合进话题分支（`jj new @ main@upstream`，落成 `同步 GitHub main → topic/7c559d2e（推 PR 分支前）`，与平台自己在 `_sync_remote_base_into_topic_branch` 里用的形状一致）。分支此前落后 upstream main **21 个提交**，合并**确实冲突**——冲突就一处，在 <&backend/app/domain/workspace/service.py>，这就坐实了「不可合并 → GitHub 建不出 merge ref → 不创建 run → 零检查」这条链。平台的 `_repush_if_local_head_moved` 会把本地新 head 推到 PR 分支（芝士自己没有 GitHub 凭据也没有出网，这是设计好的分工），GitHub 重算 mergeable 后 `test.yml` 就该真的跑起来。

**冲突的内容值得单独说**：main 上已经落了针对同一个 bug 的**另一种解法**——`_repair_modes` / `_share_jj_modes`，即每次 jj 调用后把模式 chmod 修回来。那正是本话题简报明确否决的「事后 chmod」路线。合并时**两边都保留**，没有删掉别人已落地的代码：

- 两者可以叠加且不打架：`_jj()` 现在既跑 `_share_jj_modes()`（main 的），失败时也抛指名道姓的 `WorkspacePermissionError`（本话题的）。
- uid 对齐后 `_share_jj_modes` 变成一个廉价的兜底：同一个 uid 下 0600 本来就读得动，它只是多修几个模式位。
- 留一个尾巴给后续：`_share_jj_modes` 的 docstring 还写着「a DIFFERENT uid, sharing no group」，uid 对齐后这个前提不成立了。**没有动它**——那是别的话题落的代码，删/改要走它自己的评审。

## 事后：这张卡自己踩了一次（2026-08-11）

PR #248 合进 main，CI 六项全绿，随后的 deploy-dev（run 31466502982）把 dev 打成了全项目 422——正是这个话题要消灭的那个故障，由这个话题的修复本身造成。

**经过。** 属主移交跑完了（workspaces 220 万个条目、约 10 分钟，uploads、apphome 同批），紧接着的 宿主机 git 凭据文件 可读性检查把 deploy 中止在换版之前。箱子于是停在「旧后端（1001）+ 已经属于 1000 的工作区」：`git` 判定 `detected dubious ownership`，`GET /projects/{id}/files` 422，一直到下一次 deploy 才可能恢复。而下一次 deploy 会在同一个检查上再死一次——递卡本身要跑 git，所以修复卡也递不出来。

**两个真实缺陷。**

1. **顺序错了。** 属主移交是这条部署链路上唯一不可逆的一步，却排在 DB 迁移和凭据检查**之前**。它之前的每一步失败都能让箱子原封不动，它之后的每一步失败都会留下半截状态。现已挪到所有可能失败的步骤之后、紧挨着 `dc up`，中间不留任何会失败的东西；健康检查回滚时先按 `PREVIOUS_AGENT_UID`（1001）把挂载交还再起旧镜像——**且只在本次真的移交过时才交还**，脚本把这个事实回报给调用方（`OWNERSHIP_REPORT_FILE`）。箱子过了迁移期之后，旧镜像和新镜像同 uid，那时候去"交还"才是把回滚弄坏的那一手。移交时顺带清掉其他 uid 的 `.cheese-uid-*` 标记：标记是「这棵树归谁」的断言，走完一次移交只该剩一个，否则回滚后的机器会被下一次部署当成已迁移直接跳过。

2. **「只查不改」这个决定是错的，推翻。** 上面那条写着"不替运维 chown 私密文件"。它对这个文件的性质判断错了：它是**只读挂进后端固定路径**的 mode 600 文件，属主必须就是后端的 uid——当初是 1001，恰恰因为那时后端是 1001。不移交没保护任何东西，只是把 deploy 卡在一条唯一解法是 sudo、而部署链路上没人有 sudo 的路上。现在照常移交，**不动 mode**（600 还是 600）；可读性检查保留、仍然打红、仍然给出该跑的 `chown`，但挪到移交**之后**，于是它只在 chown 修不好的情况下才响（挂载选项、父目录不可读）。`/dev/null`（功能关闭的默认值）是设备节点，跳过，永不 chown。

**为什么 CI 没拦住。** `deploy/tests/` 早就有一套 fake-docker 测试，但 `test.yml` 只在 `backend/**` 上触发——改 `deploy/` 的提交，这套测试一次都没跑过。绿的六项里没有一项碰过这个文件。现已补 `.github/workflows/deploy-scripts-test.yml`（hosted runner，不占箱子那个独苗 runner），把 `deploy/tests/` 三套全挂上，外加对 `deploy/**` `scripts/**` 所有 `*.sh` 的 `bash -n`。新增回归：<&deploy/tests/test-workspace-ownership.sh>（8 条）+ <&deploy/tests/test-app-tier-health.sh> 里三条（移交排在迁移之后换版之前、回滚交还、已迁移的箱子回滚时不碰属主）。都对着改动前的脚本验过会红。
