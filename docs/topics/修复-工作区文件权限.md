## 目标

根治 P0-1：沙箱容器与后端进程用不同 uid 共享同一个 jj store，谁先落下 `.jj/repo/config-id`（0600）谁就把另一方锁死。修完要满足：跑过 jj 之后文件接口仍可读；芝士新建的文件人能保存、人保存过的文件芝士能改。

## 复现与根因（已实测确认，比简报描述更宽）

沙箱里 jj 0.42.0 实跑，证据链完整：

1. **两个 uid 都是写死的**：沙箱镜像 `FROM node:22-bookworm-slim` + `USER node` = **uid/gid 1000**（<&backend/sandbox/Dockerfile>），`tmux_provider` 用 `--user node` 起容器；后端镜像自建 `cheese` 用户 = **uid/gid 1001**（<&backend/Dockerfile> 第 147-148 行）。
2. **两者共享同一个 store**：`sandbox_vcs_mounts()` 把主仓的 `.jj` 和 `.git` **读写**挂进每一个沙箱容器（<&backend/app/domain/workspace/service.py>），所以两个 uid 在同一份 jj store 上读写。
3. **jj 把 store 文件写成 0600，且 umask 管不着**：实测 `umask 022` 下，`op_store/operations/*`、`op_store/views/*`、`index/segments/*`、`index/op_links/*`、`store/extra/*`、`workspace_store/index`、`working_copy/{checkout,tree_state}` 全是 `0600`——jj 走的是「临时文件 + persist」，0600 是显式模式，不是 `0666 & ~umask`（同目录下少数直写文件是 644，正好说明两条路径并存）。
4. **`jj config set --repo` 落下 `.jj/repo/config-id`（0600）**，属主 = 执行者。这正是 `_ensure_jj()` 在仓库初始化时跑的两条命令。
5. **另一方之后跑任何 jj 命令都全废**：把 config-id 设为不可读后，主仓和 workspace 里的 `jj status` / `jj diff` 一律
   `Internal error: Failed to determine the secure config for a repo → Cannot access .../.jj/repo/config-id: Permission denied`（rc=255）。
6. **后端把它翻成 422 并放大到全项目**：`_jj()` 非零退出 → `ValidationError` → HTTP 422（<&backend/app/core/errors.py>）；而 `_tree()` 是 list_files / read_file / write_file / raw 的必经之路，每次都会走 `_catch_up_with_branch` → `_jj(wt, "diff", "-s")`。于是**整个项目每个话题**的文件面板、消息里的文件 chip、文档内嵌图片同时 422。

**做这张卡的过程中，另一半就在现场发作了一次**：本沙箱里 `jj diff -s` 直接报

```
Could not create named temp file in '/de808b13-.../.git/objects'
Permission denied (os error 13)
```

——共享主仓的 `.git/objects` 属主 1001、模式 755，而我是 1000，写不进去。这不是 jj 特有的，`.git` 侧同样中招（所以修复也给 `_git()` 加了同一套权限判定）。不影响本卡产物：平台的快照是后端以 1001 跑的，写得进去。

**方向是对称的，两个方向线上都发生过**：

- config-id 属主 1000 → 后端全废 = 本话题这条 P0。
- config-id 属主 1001 → 沙箱里 jj 全废，已被两个历史话题当成"环境限制"记了下来（<&docs/topics/两阶段采纳PR迭代闭环.md>、<&docs/topics/merge后结果回房间.md> 里都写着"config-id 属主 uid 1001，当前进程 uid 1000，Permission denied"，一整批测试被判成"沙箱环境问题"）。当时的归类是错的，那就是这个 bug 的另一半。

## 方案：uid 对齐，后端向沙箱看齐（1001 → 1000）

沙箱侧的 uid 是我们**不完全控制**的那一侧：基础镜像是 `node:22`（node = 1000），`cheesex-dev` 继承它，项目还能通过 `sandbox_image` 指到别的镜像，而 `_create_container` 已经硬假设镜像里存在 `node` 用户。后端镜像则 100% 是我们自己的。所以把后端的 uid/gid 从 1001 改成 1000，是唯一一处改动、且对未来任何 node 系镜像天然对齐。

### 否决了什么

| 方案 | 否决理由 |
|---|---|
| 调 umask | **实测无效**。jj 的 0600 是显式创建模式，不受 umask 影响（见上面第 3 条证据）。 |
| 共享组 + setgid + POSIX 默认 ACL | 同理无效：显式 0600 会把组位直接抹掉，默认 ACL 也会被创建模式 mask 掉。 |
| 事后/定时 chmod 修回来 | 打补丁：竞态窗口内照样 422，而且每加一个 jj 新文件就要补一次名单。简报也明确否决。 |
| 不把主仓 store 挂进沙箱 | 沙箱里 jj/git 直接不可用，产品倒退。 |
| 后端读文件不走 jj（把 catch-up 从读路径摘掉） | 只缩小爆炸半径，不治本；catch-up 本身有真实用途（机器直推的提交要落到工作区）。 |
| 沙箱向后端看齐（node 改成 1001） | 也能对齐，但把 uid 焊死在我们不完全控制的一侧，且要重建 base + dev 两个镜像；现存 `.sessions/**` 里 1000 属主的会话文件会反过来锁死容器自己。 |

### 迁移代价（必须做，否则改完后端起不来）

宿主上绑定挂载的历史文件属主是 1001（`WORKSPACES_HOST_PATH`、`UPLOADS_HOST_PATH`），后端改成 1000 后读不了自己的旧数据 → 需要一次性 `chown -R 1000:1000`。已配套：一个幂等的迁移脚本 + 后端启动自检（属主不对时明确报错，而不是等到 422 才发现）。

## 改了什么

- <&backend/Dockerfile>：`cheese` 用户 uid/gid 1001 → 1000，并在同一条 `RUN` 里 `test "$(id -u cheese)" = 1000` 自校验——万一基础镜像哪天占了这个 uid，是构建红，不是线上文件面板红。
- <&backend/sandbox/Dockerfile>：`test "$(id -u node)" = 1000` 把 base image 给的 uid 钉在构建期。`node` 不是我们写的用户，是 node:22 给的，所以只能断言、不能假设。
- <&backend/app/domain/workspace/service.py>：`AGENT_UID`/`AGENT_GID` 作为单一事实来源；新增 `WorkspacePermissionError`，`_jj()`/`_git()` 遇到权限类失败时报出「当前 uid=X，应为 1000」而不是一坨 jj 内部报错；读写文件的 `PermissionError` 收敛成干净的 422，不再 500；`audit_workspace_ownership()` 供启动自检。
- <&backend/app/main.py>：启动时跑自检，store 有当前进程读不了的文件就 ERROR 级点名（非致命，一个野文件不该拦住整个平台起不来）。
- <&deploy/fix-workspace-ownership.sh> + <&deploy/deploy-docker.sh>：幂等、marker 保护的一次性属主移交，在临时 root 容器里做 chown（box 上不需要 sudo），排在换版之前——新后端起来时不能发现自己读不了自己的历史数据。覆盖三个绑定挂载：workspaces、uploads，以及 **apphome**（后端的 `HOME`。`config-id` 只是个 20 位十六进制指针，真正的 per-repo secure config 落在 `$HOME/.config/jj/repos/<config-id>/`——现场核对过，漏了这个挂载等于只搬了半边）。`GIT_CREDENTIALS_FILE` 是运维自己的私密文件（600、不在 git 里），脚本**只查不改**：读不到就直接把 deploy 打红并给出该跑的 `chown`——私有仓 push 静默退化成"git 提示失败"正是这个话题要消灭的那类伪装故障。
- <&docs/infrastructure.md>：把「后端必须跑在 uid 1000」写成运维口径。
- 回归测试：<&backend/tests/unit/test_workspace_uid_alignment.py>（10 条）+ <&backend/tests/integration/test_workspace.py> 里一条端到端的。

## 测试怎么钉的

- **跑过 jj 之后文件接口仍可读**：单测里让 agent 在自己的 workspace 里真跑 `jj config set --repo` + `jj status`（这正是往共享 store 里落 config-id 的命令），然后断言 `list_files`/`read_file`/`read_file_bytes` 全部正常、且 config-id 属主就是当前进程。集成测试再从 HTTP 层走一遍 `/files`、`/file`，并且**额外验一个同项目的另一个话题**——爆炸半径是全项目，测试就得覆盖全项目。
- **芝士新建的文件人能保存 / 人保存过的文件芝士能改**：分两条，各自模拟一侧原生工具留下的属主与 0644 模式，再从另一侧改。
- **坏掉时要说人话**：把 config-id 设成不可读（同 uid 下 `chmod 000` 与跨 uid 的 0600 等效），断言抛的是 `WorkspacePermissionError`、消息里同时出现当前 uid 和应有的 uid、code 是 422。以前这里是 `jj diff failed: Internal error…`，读起来像"文件没找到"——这正是全项目挂了一天没人报修的原因。
- **测试本身做了变异验证**：把 Dockerfile 改回 1001，对齐测试立刻红；改回来即绿。不是只会跟着代码走的空测试。
