# 浏览器推送

#1084 第 5 步。一轮活可以跑几十分钟到三小时，这期间人会关掉标签页、去开会、下班回
家。推送是把他叫回来的那条路。

## 链路

```
通知产生（announce / notify_question）
  └─ publisher.build_notification_event_handler
       ├─ InAppNotificationHandler            → 站内通知（铃铛、待办）
       ├─ RedisEmailQueueNotificationHandler   → 邮件队列
       └─ RedisPushQueueNotificationHandler    → 推送队列（只在配了 VAPID 时挂上）
             └─ drain_push_queue（scheduler，15 秒一跳）
                  └─ pywebpush → 浏览器的推送服务商 → service worker 的 push 事件
```

## 只推两种通知

`ROOM_NOTICE` 和 `CHEESE_QUESTION` —— 平台在房间里说的那一句要人动手的话，和芝士停
在那里等回答的一个问题。别的类别码一个都不推（`notification/push.py` 的 `PUSHABLE`）。

判据来自 #1084：芝士跑一轮会产生几十条消息，按消息推送就是几十条推送，人会直接把
这个渠道关掉，之后真正要他动手的那一条也就收不到了。推送的价值全在「收到就意味着该
我动了」。

推送上显示的文字就是站内通知里的、也是房间里那一行的 —— 三处对同一件事只有一种说
法。

## 权限什么时候问

不在首屏。首屏上用户还不知道为什么要授权，多数会拒；而浏览器被拒一次之后基本问不了
第二次（`Notification.permission` 变成 `denied`，再调 `requestPermission` 直接返回
denied、不弹窗）。一次问坏，这个渠道对这个人就永久关闭了。

所以等到这个人**第一次遇到一轮跑过一分钟**，在房间里附理由问：
「本轮运行时间可能较长，完成后通知你〔开启通知〕〔暂不开启〕」
（`frontend/src/components/PushPermissionPrompt.vue`，挂在 `TopicView` 上）。

一个浏览器只问一次，`localStorage` 的 `cheese:push-asked` 记着。说过「暂不开启」就
不再追问 —— 追问是人关掉一个渠道的头号原因。

## service worker

`sw.js` 由 VitePWA 的 generateSW 生成，我们写不进去，所以 `push` 和
`notificationclick` 两个处理函数放在 `frontend/public/push-sw.js`，由 workbox 的
`importScripts` 引进同一个 worker 作用域。

换成 injectManifest、自己写整个 `sw.js` 也能达到同样效果，但那要把
`vite.config.ts` 里四条运行时缓存规则连同它们注释里记着的教训（哪些不能缓存、为什
么、踩过什么）全部手抄一遍。两个监听函数不值这个风险。

`push-sw.js` 不经打包，所以它只能用 service worker 环境里本来就有的东西：没有
import、没有 TypeScript、没有 `@/` 别名。nginx 对它和 `sw.js` 同样 no-cache。

## 部署要配的东西

两个环境变量，缺任何一个这个渠道就整体关闭（订阅接口如实回 `available: false`，前端
因此不去问权限）：

| 变量 | 是什么 |
|---|---|
| `VAPID_PUBLIC_KEY` | 浏览器订阅时要带的公钥，也是推送服务商认出发送方的依据 |
| `VAPID_PRIVATE_KEY` | 「以这个站的身份发推送」的凭据。**不进仓库、不进镜像** |
| `VAPID_SUBJECT` | 联系方式，推送服务商出问题时按它找运营者。默认 `mailto:ops@okcheese.com` |

生成一对（`py-vapid` 随 `pywebpush` 一起装上）：

```bash
cd backend && uv run vapid --gen --applicationServerKey
```

它写出 `private_key.pem` / `public_key.pem`，并打印 `Application Server Key` ——
那一串 base64url 就是 `VAPID_PUBLIC_KEY`。`VAPID_PRIVATE_KEY` 用 PEM 文件的内容。

**换掉密钥会让已有订阅全部失效**：浏览器的订阅是绑着公钥换来的，公钥变了，旧订阅
推不动（投递侧会按 404/410 把那些行删掉），每个人要重新授权一次。所以这一对密钥生
成一次就别动。

## 订阅存在哪

`push_subscription` 一行 = 一台设备上的一个浏览器。`endpoint` 唯一，同一个浏览器重
复订阅换回同一个值，按它 upsert；`user_id` 带 `ON DELETE CASCADE`。

三样都必须存：`endpoint` 是往哪儿发，`p256dh` 和 `auth` 是把内容加密成只有这个浏览
器能解开的样子。**服务端加密完就再也解不开** —— 这是 Web Push 的设定，所以这张表存
的不是「发过什么」，只是「往哪儿发、用哪把钥匙」。

订阅会自己失效（撤权限、清站点数据、换设备），表现是推送服务商回 404 或 410。那不是
「重试一下就好」，投递侧直接删掉那一行：留着它每一轮都白发一次，而且永远不会成功。

退出登录会主动退订（`account.ts` 的 `logout`）：那一行是按 `user_id` 存的，留着就等
于这台浏览器继续替上一个人收他的推送。
