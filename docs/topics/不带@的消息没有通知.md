## 目标

平台上"有人找你"这件事，只有对方记得打 `@` 才传得到。不带 @ 的消息、以及整个私聊房，全平台零通知——人只能一个个房间点进去看。这个话题只解决"该有的通知没有"，**不动已读机制**（254 条未读堆着是另一个问题，混着做两件都做不好，@wangchangxin 定的边界）。

## 已核实的事实（都读过代码/查过数据）

1. **`NotifKind` 只有五种**（change_alert / decision_request / accept_request / heartbeat / mention），没有"新消息"这一类。消息路径上唯一会建通知的地方是 `_notify_mentions`（<&backend/app/domain/agent/chat.py>:1540）。所以今天"被通知" ≡ "被 @"。
2. **CX 通知在前端没有落地面。** 顶栏铃铛读的是社区那套 flat 通知（<&frontend/src/components/common/Navigation/AppBar.vue>:46）；CX 侧前端只调了 `getInbox`，而 inbox 只收 decision_request + accept_request（<&backend/app/domain/cx_notification/repositories.py>:103-107）。**mention 行写进库，但没有任何界面读它。** → 不修入口，加多少种 kind 都没人看得见。
3. **私聊里连 @ 都不通知**：`_post_user_message` 对私聊房把 roster 置空（chat.py:974-978），`_resolve_mentions` 拿空 roster 时两个列表都不放（chat.py:610-614）→ 私聊 100% 静默，且不报"handle 无效"。
4. **`over_quota` 是死代码**（只有测试调它）→ 收敛必须做在生成规则里，不能靠配额。
5. **芝士刷屏是多个 `kind=message` 块，不是工具块**（工具事件是 `kind=event`，本来就不计未读）→ 要收敛按 `turn_id`，不能按块类型。
7. **芝士不丢消息**：没召唤的消息会在下一次召唤时被 `_pending_human_blocks` 全量读进 prompt（chat.py:1611-1614，注释直引 spec §7.1）。它的问题是"没召唤就不动"，不是"收不到"。

## 实测数据（项目「cheese 自建」全量：223 话题 / 37882 块）

人写的 message 块 1326 条：

| | 条数 | 占比 |
|---|---|---|
| 带 `<@>` | 66 | 5% |
| ↳ @ 到另一个人（唯一产生过人找人通知的） | 43 | 3% |
| 带平台 ✅ 回执（真人召唤芝士） | 1151 | **87%** |
| 既没 @ 也没 ✅ | 109 | 8% |
| ↳ 且 5 分钟内芝士也没接话 = 真·说给人听且零通知 | **35** | **2.6%** |

另：同人同文 1 小时内重发 73 对，其中**第一条无 ✅、第二条有 ✅ 的 15 对**，间隔 5–100 秒（中位 14 秒）——"发出去没动静，隔十几秒又发一遍"。

**口径限制**：只统计了一个项目；`/topics` 不含私聊（私聊那类完全没进统计）→ 35 是下限；35 里又混着几条长状态存档帖（写给人看、不一定在等回应）→ 又是上限。真值在几十这个量级。

**两条被数据推翻的说法（已撤回）**：
- "一半是人收不到"——按条数是 2.6%，不是一半。准确说法是两侧都是**几十条**量级（人 35 / 芝士 15+），谁也不比谁大一个数量级。
- "@caisongyang 08-10 的提问挂了两天"——查无此事。他 08-10 在 @credits设计 只有三条，两条带 ✅，芝士当场就跑了，且内容是在提供数据不是提问。

## 定下来的口径

**两档，不是一种通知：**

| | 触发 | 存储 |
|---|---|---|
| **点名**（强） | @ 你 / 私聊对端的每条消息 / `cheese ask` 选项题 / 你召的那轮的结论 | 落 `notifications` 表 |
| **动静**（弱） | 你参与的房间里其他人发言 | **查询时算，不落表**，每个（房间, 人）最多一条 |

- 弱档**不加第六种 kind**。一条消息落一行正是 254 条未读的成因，也跟"聚合成一条『房间有 N 条新消息』"直接冲突。查询时算 = `TopicReadState` + blocks，是 <&backend/app/domain/topic/repositories.py>:143 那个 `unread_counts` 的推广。
- 成员按 `TopicMembership` 名册判，不按"谁在这个房间说过话"（推翻了简报里的候选口径）。"N 分钟没进来"降级为排序权重，不做成员资格规则。
- 芝士的发言按**结构**判（轮边界 / 谁召的 / 是不是结构化动作），永远不读内容判断。

### 合并冲突怎么解的

只有 <&backend/app/domain/topic/repositories.py> 带冲突标记（两边各加了一行 import，取并集即可）。**真正的冲突是无标记的那三处**——main 在我干活期间给整套 per-recipient 接口加了鉴权：

1. **`/private-unread` 会重新捅开 main 刚补的洞。** main 把 `topic-unread` 的收件人改成从**凭据**里取（`ActorResolverDep.resolve_recipient`），注释写明"a caller without one used to read anybody's badge map by naming them here"。我的新接口写的是裸 `handle: str` 直接采信 → 文本上无冲突、语义上是把那个洞在私聊数据上又开一遍，**而且私聊比群未读更敏感**（这张表暴露的是"谁在跟谁私聊"）。已改成同一套 `resolve_recipient`，并补了一个测试：拿别人的 handle 查 → 403，不带凭据 → 401。
2. **`test_cheese_cli.py` 的同一个 bug 被两边各修了一遍**，干净合并成两行重复的 `monkeypatch.delenv`。保留 main 的（它先落地、注释更准），撤掉我的。这个文件现在和 main 完全一致。
3. **我的测试还在用旧的免鉴权调用方式**（`/topics/{id}/read`、`/topic-unread`），撞上 main 的新鉴权 → 2 条失败。已按 main 自己测试里的写法补 `session_auth_headers`。

其余是 main 的加法式改动（`_last_activity()` / `active_since` / `TopicProgressRepository`），与本话题不相交；`unread_counts` 的定义 main 一个字没动，所以 `private_unread_counts` 仍与它同源。

解完自测：相关 36 passed；`check.sh --no-tests` 6/6 passed。
