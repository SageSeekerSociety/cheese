> 状态：已实现，验证中。本文档已从父话题下发的任务简报改写为分身的状态摘要。

## 目标

让流程级操作知识**按话题所处的流程阶段**进 prompt：每一轮只注入当前这一段，而不是把整条流程一次性灌进去，也不是写成一篇没人读的长文档。

## 核心设计：平台主动选，仍然是静态注入

团队立场（写在 `skills.py::load_cheese_cli_rules` 的 docstring 里）是：Agent Skills 的懒加载不可靠，弱模型不会自己去读，所以 always-needed 的东西直接注入 system prompt。

本方案**不违背这条**：模型全程没有「要不要读」的选择权。平台在组 prompt 时，用**已有的、免费的**运行时事实算出当前阶段，把对应那一段 skill body **直接拼进 system prompt**。渐进的是「平台注入哪一段」，不是「模型决定读哪一段」。

钩子用 `skill_library/*.md` 里**早就存在但从没被任何代码读过**的 `scenarios:` 字段——把它从装饰性字段变成真正的选择器。原有四个硬编码名字列表（`ACTIVITY_SKILLS`/`HEARTBEAT_SKILLS`/`PRIVATE_SKILLS`/`DEFAULT_CHAT_SKILLS`）**不动**，阶段 skill 是**叠加**上去的一段，不替换任何现有行为。

## 阶段切分（相对草案有三处调整）

| 阶段 | 判定 | 内容要点 |
|---|---|---|
| `delegating` | `kind ∈ {root, topic}`（房间，不带分支/验收卡） | 拆活：简报单向不可追加、必须一次写全；给子话题留问回来的路 |
| `working` | `kind ∈ {task, subtopic}`，无 open 卡，未归档 | 开工先确认基于最新 main；沙箱里怎么真跑测试；跟父话题怎么沟通；**什么时候递卡**；**采纳者 token 通道**；GitHub 账号校验回环 |
| `gate` | 卡 = `pending_gate` / `gate_failed` | 闸门只跑 lint（`--no-tests`），测试第一次真跑在 PR 的 Actions 上；怎么读失败输出 |
| `awaiting` | 卡 = `pending` | 闸门已过等人采纳期间该做什么、别重复递卡 |
| `pr_open` | 卡 = `pr_open` | 采纳者 token 通道已打开；继续在本分支提交即可，平台会自动重推；CI 怎么读；哪些是假失败 |
| `conflict` | 卡 = `conflict` | 芝士先尝试解决，解完由人重试采纳 |
| `merged` | 话题已 archived | 部署门禁只认 build 成功、不看测试；归档要等部署也成功 |

**调整一：「递卡前」不单独成阶段，并入 `working`。** 草案的触发条件写的是「准备 accept-request」——这是**模型的意图**，平台无从判定，做不出触发信号。而「什么时候递卡」恰恰是最需要提前知道的一条（它会改变你判断「做完了没有」的标准），所以必须在 `working` 阶段就说，不能等到一个不存在的时机。

**调整二：「CI 红了」并入 `pr_open`。** 两者的判定信号是同一个（卡 = `pr_open`），拆成两段只会让注入逻辑多一个分支，而内容高度重叠（都在讲「PR 开着的时候怎么办」）。

**调整三：补了 `conflict` 和 `awaiting` 两个草案没有的阶段**——它们是现成的卡状态，判定零成本，不用白不用。

## 需要平台补的信号：只有一个，而且它本身是个 bug

除下面这一条，**所有阶段的判定信号都已存在**（`topic.kind`、`topic.status`、以及 `chat.py` 已经为「盲飞防护」查出来的 open 卡列表），不需要新增任何查询。

`AcceptStatus.pr_open` 已经在枚举里（两阶段采纳已落地），但 **`_OPEN_CARD_STATUSES` 里没有它**，也没有对应的 `_OPEN_CARD_HINTS` 文案。后果：卡进入「PR 迭代中」之后，芝士在 turn-meta 里**收不到任何信号**——它不知道自己已经有了一条通往 GitHub 的通道，也就不知道「继续在本分支提交就行」。草案设计的 `pr_open` 阶段在今天的代码里**根本没有触发条件**。这是本卡要补的唯一一处平台侧改动，顺带修掉一个真 bug。

## 两条必写内容（简报硬要求）

**① 什么时候递卡 —— 不一定是「任务做完」。** 子话题沙箱的 GitHub token 是只读的，它永远不能自己推代码、开 PR、重跑 workflow。产出到达 GitHub 的唯一路径是递卡 → 人采纳 → 平台用采纳人的 token 去推。所以还有一类递卡时机：**当你需要的下一步动作只有采纳人的 token 才能做时**，即使没「完全做完」也应该递卡，并在理由里写明「递这张卡是为了拿到 X」。

**② 怎么用采纳者 token —— 不是直接用，是通过递卡让平台代用，而且不是一次性的。** 卡进入 `pr_open` 之后，本地分支上的每一次新提交平台都会用采纳人的 token 自动重推到 PR（60 秒轮询）。「采纳」不等于「这张卡结束了」，而是「从现在起你有了一条通往 GitHub 的通道」——继续在本分支改就行。

## 连 GitHub 账号：校验回环

**简报的假设要修正一处**：`GET /users/{userId}/oauth/connections` 有 self-only 鉴权（`users.py:3899`「Only the user themselves can view their OAuth connections」），**芝士没法替采纳人查连接状态**。所以「能查当前连接状态」这条做不到，回环只能靠直接问人——这反而印证了简报选的 `cheese ask` 方案是对的，且确实零平台改动。

触发时机定在**递卡前**（`working` 阶段，跟「什么时候递卡」同一段）：递卡前若要走 PR 路径，先用 `cheese ask` 给采纳人一个「我连好了，帮我验一下」的按钮。

事后信号也写进去：采纳后若卡**没有**进 `pr_open` 而是直接 accepted，说明前提没满足降级成了本地合并，降级原因平台已经写在卡的 note 上（`_TOKEN_UNAVAILABLE_MESSAGES`，如「批准人未连接 GitHub 账号」），照着 note 说就行，不用猜。

**为什么选「新增 scenario 选择器」而不是「加一批场景常量」**：阶段和 skill 是**多对多**的——`parent-link`（跟父话题怎么沟通）在 working/gate/awaiting/conflict 四个阶段都该在。用名字列表就得把同一个名字抄进四个常量里，加一个阶段要改 N 处；用 `scenarios:` 标签，加一个阶段只改 skill 自己的 frontmatter。而且这个字段本来就在，只是没人读——把它接上比新造一套机制诚实。
