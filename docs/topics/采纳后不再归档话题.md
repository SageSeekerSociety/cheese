## 目标

让「PR 合并」只意味着**这次改动交付完成**：话题不再被机器归档、容器不再被机器删掉。
归档变成纯粹由人决定的动作。这是 <@wangchangxin> 2026-08-17 的拍板（「PR 不是话题终态」＋
「归档还是人为决定」＋「话题往往是连续的，机器不应该回收」）。

## 做法（已实现）

一句话：**「交付完成」用已有的 `accepted_by`/`accepted_at` 表达，不加新字段、不加迁移。**

四条改动，全在 <&backend/app/domain/review/services.py>：

1. **三处 accept 收尾都不再归档**（`accept()` 的本地合并、`_finish_pr_accept`、
   `_settle_pr_accept`——简报说两处，实际是三处）。合并那一刻只打交付标记
   `accepted_by`/`accepted_at`，`status` 保持 `active`、`archived_at` 不动。
   现在这个文件里已经没有任何一处写归档状态，只剩两条读的守卫。
2. **交付冻结改由「那张 accepted 的卡」承担**：`create_card` 的阻塞集加入
   `AcceptStatus.accepted`。归档以前兼任「工作面冻结」，现在归档不再自动发生，
   这一半必须自己站住——否则已合并的话题还能再递一张卡，而它的分支已经在 main 上，
   开出来的 PR 没有新提交（GitHub 422 → 平台降级成本地合并 → 卡看着采纳了却什么都没交付）。
3. **采纳不再删容器、不再关设备屏**。原 `_release_topic_compute` 改名
   `_release_billed_compute`，只释放计费云 VM。理由：容器/设备屏是可重建的工作面，
   各自有闲置回收器（`scheduler.reap_idle_containers` / `reap_idle_device_screens`），
   而话题合并后还要接着用；云 VM 按小时计费**且没有任何 reaper**，所以它的释放时机
   按简报要求一点没动。
4. **`revoke` 语义对齐**：只清交付标记（于是话题又能递卡），不再把 status 拉回 active、
   不再清 `archived_at`。跟 `TopicService.unarchive`（「取消归档不改写采纳记录」）对称——
   撤回采纳也不该改写别人「把这个话题收起来」的决定。

顺带清掉三处会变成陷阱的过期文字（CLAUDE.md 要求同一个 PR 里清）：
<&backend/app/domain/topic/models.py> 的 lifecycle docstring、<&docs/accept-is-merge.md>
的流程图＋卡状态表、<&docs/evals.md> 的 A3。

## 查出来但故意没做

- **`resolve_stage` 会退化**（<&backend/app/domain/agent/stages.py>）：它靠
  `status == archived` 判定「已合并」阶段。话题不再自动归档之后，一个已交付的话题会拿到
  「这件事正在做（还没递卡）」的操作说明。修它要动 `stages.py` ＋ `chat.py`（只传 open 卡，
  看不到 accepted 卡），而 `chat.py` 在简报禁区里。后果可控：芝士会尝试再递卡，撞上第 2 条
  那道闸门并读到一条说明出路的拒绝话术，不会造成坏合并。**这是必须紧跟的一张卡。**
- **结论卡「采信即归档」没改**（`conclusion/services.py`）——不是 PR 合并路径，且在禁区外的另一个文件。
- **云 VM 的回收策略**没碰（简报明令）。但要知道后果：交付时 VM 被销毁，而
  `ensure_topic_machine` 要求「有授权的人类调用者」，所以一个跑在云上的话题交付之后，
  下一轮需要有人说句话才能重新拿到机器。这是 #442 decision 3 已有的取舍，不是新增的。
- **第二次交付**：同一个话题交付后不能再递卡。精确一点的做法是「分支头超过已合并的头才放行」，
  能允许第二次交付；没做，因为它依赖递卡时读 git 状态（失败时的兜底策略两难），而简报的
  验收标准明确要求「已交付的话题不能再递卡」。后续要做的话是独立一张卡。
