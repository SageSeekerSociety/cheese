## 一、缺陷确认：两条都成立，而且是同一处结构性对撞

### T. 自动快照落在「长命令还在改工作区」的窗口里

不是巧合，是必然重叠。链路：

```
turn 结束 → chat.py:1953 / chat.py:2081  provider.checkpoint()
          → tmux_provider / compute / device_provider
          → ws.snapshot_worktree()   ← 对 await 一无所知
```

`snapshot_worktree()`（<&backend/app/domain/workspace/service.py>:1806）只做三件事：`jj diff -s` 非空就 `jj commit`、把话题 bookmark 挪到新提交、`git export`。**它不问「现在有没有别的东西正在写这棵树」。**

而 `cheese await` 的整个卖点就是"注册完立刻返回，你可以安心结束本轮"（<&backend/sandbox/cheese>:217 `_await_start`，`start_new_session=True` 的 detached 子进程）。于是：

| | |
|---|---|
| await 的设计意图 | 让轮**尽快结束**，命令留在后台 |
| checkpoint 的触发点 | **轮结束时** |

两者的时间窗必然重叠。13:21:38 开跑、13:21:48 落快照的那 10 秒，就是"注册 → 打印 → 收尾 → 轮结束"的耗时。

**为什么它冻住了两小时没自愈**：正常情况下子进程回报 → 平台唤醒话题 → 新一轮 → 新的 checkpoint 会把自愈后的树提交上去。但那次容器被重建，子进程连同它的日志一起死了（=缺陷 U），**没有回报就没有唤醒，没有唤醒就没有下一次快照**。T 和 U 不只是"一对"，U 还是 T 无法自愈的直接原因。

### U. await 日志写在容器 overlay 层

`_await_log_path()`（<&backend/sandbox/cheese>:208）写 `$HOME/.cheese/await/<run_id>.log`，注释写明"Deliberately OUTSIDE the worktree"——躲开了提交，但也躲开了持久化。

本容器实测（`/proc/self/mountinfo`）：

| 路径 | 存储 | 重建后 |
|---|---|---|
| `/home/node/.cheese/await/` | overlay 上层 | **没了** |
| `/home/node/.claude/` | 宿主机 bind mount（`.sessions/<project>/<topic8>`） | 在（`--resume` 就靠它跨轮） |
| `/work` | 宿主机 bind mount（worktree） | 在 |

**能活下来的地方一直在容器里，日志只是没放进去。** 隔壁 `cheese-spool`（hook WAL）就在这个挂载里。

## 二、处置方案

### T：推迟 + 补一张最终态，而不是只打标记

- **自动快照（每轮结束那张）**：本话题有 await 任务在飞时**不提交、不挪 bookmark**，只记日志。
- **await 回报时补一张**：最后一个任务落地后，立刻补一张"最终态"快照，commit message 写明它覆盖的是后台任务窗口。
- **卡死兜底**：任务过了 `started_at + timeout_s + 60s` 一律不再拦快照——子进程死了不能把话题的版本历史永久冻住。
- **拦不住的路径打标记**：采纳前快照 / PR 快照这类**人触发**的快照不能推迟（推迟等于把采纳卡死），改为在 commit message 上带 `⚠️ 后台任务「x」运行中` 标记，`jj log`、diff、PR 正文都能看见。
- **让 hold 可见**：`cheese status` 增加一节，明说"快照已暂停，因为 X 在跑"。

**为什么是推迟而不是"照落 + 事后补"**（评审 <@wangchangxin> 补强后的版本，2026-08-11 采纳意见）：

可逆性只是次要理由——撕裂的提交进了历史删不掉、整个 await 窗口里 bookmark 一直指着它；"没提交"则可恢复（工作区是宿主机 bind mount，重建也不丢，下一次快照能捡起来）。

**真正决定性的是两种失败"长什么样"**：

| | 产生的东西 | 后果 |
|---|---|---|
| 快照被推迟 | 一个**问句**："我的改动怎么没在分支上？" | 有人会问，会被解答 |
| 撕裂的提交 | 一个**自信的错误结论**："这个修复根本没做。" | 看起来完全正常，**没人会去复查** |

事故本身就是证据：那两个小时不是花在"恢复不了"上，是花在**没人怀疑**上。所以即使在两边都可恢复的假设下，这条也该这么选。与消息链路上的"宁可重复不可丢失"是同一条原则的两次应用——**让失败以看得见的形式出现**。

推论：**hold 本身也必须可见**，否则"我的改动没上分支"只是换个路径变回同一个谜——这就是 `cheese status` 那一节存在的理由，不是锦上添花。

### U：日志搬进会话挂载

`~/.cheese/await/` → `~/.claude/cheese-await/`（宿主机 `.sessions/<project>/<topic8>/cheese-await/`）。

**不放工作区**，理由三条：① 靠 `.gitignore` 挡提交，正是本话题要修的那种"未跟踪文件混进现场"的风险；② 一次全量 check 的日志几十 MB，工作区要进分支/PR；③ 会话目录本来就是"持久但不进版本库"的既有位置，spool 已经在那儿了——一个位置比两个好。

## 四、残留缺口（评审确认，均不阻塞，别读成"已经没有洞了"）

### A. 远端 compute：唤醒被抑制时没有补救

`RemoteCheesedProvider.checkpoint` 在 hold 期间直接跳过本轮；补救靠"回报 → 唤醒 → 下一轮的 checkpoint"。而 `awaited_tasks` 的四道守卫里有两道**只落块、不唤醒**：**归档话题**、**卡已结算**。这两种情况下节点上那棵树就一直没提交，直到碰巧有下一轮跑起来。

判断：**可以接受**——这两种状态下已经没人在读那条分支了。但它是缺口，不是不变量：**不要**把这条路径读成"回报之后总会有一轮"。（本地/tmux/同机 device 三条路径有即时补快照，不受此影响。）

### B. `_ACTIVE` 是进程内注册表：后端重启，所有 hold 消失

重启后若还有一轮 checkpoint 落下来，那棵仍在被写的树照样会被撕裂提交。

注意**不能**套用"重启就等于子进程也没了"那套说辞：子进程跑在 agent 自己的沙箱里，**后端重启它还活着，还在写工作区**，而 hold 已经忘光了。相对改动前的"必然撕裂"，现在是"只有重启撞进窗口才撕裂"，严格变好，所以不阻塞；但它不是理论问题——**本话题自己 2026-08-11 就被平台重启打断过两次**。

要再往前一步，方向是**把 hold 落到持久存储**，**不是**继续加宽 `SNAPSHOT_HOLD_GRACE_S`：后者对重启毫无作用，只会让死掉的子进程冻住历史更久。
