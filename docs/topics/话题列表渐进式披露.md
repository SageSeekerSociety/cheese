## 做法：两份列表，而不是一份过滤过的

原来 `topic_refs` 一份变量同时干两件事——渲染进 system prompt，以及给 `expand_mention_names` 当 `@标题 → <#id>` 的解析表。直接把归档话题删掉会顺手砍掉引用能力（用户自己打 `@某个归档话题` 就不再变成链接）。

所以拆成一个成对返回的函数 `_topic_ref_lists(topics, exclude_id) -> (全量解析表, 渲染子集)`：

- **全量那份**：行为完全不变，仍含归档 / 未命名 / 同名话题，喂给 `expand_mention_names`；
- **渲染子集**：只喂 `_build_system_prompt`。

成对返回是故意的——两份必须从同一批话题推导、且必须保持不同，合成一份就退回老问题。测试直接盯着这个函数，而不是各自复刻一遍推导逻辑。

## 渲染子集的过滤规则

1. 排除 `status == archived`（主要收益）。
2. 排除未命名（标题 == `PLACEHOLDER_TITLE`「新话题」）——按标题根本引用不了。
3. **同名标题全部排除**，不是去重留一个。理由：`expand_mention_names` 对同名只解析第一个，其余静默指向错的那一个；留一个等于在 prompt 里推荐一个会指错的引用。全部不列之后，它们仍可通过查询拿到 id、用 `<#id>` 精确引用。
4. 原有的"不列自己"和 `kind != root` 保持不变。

`TopicRepository.list_for_project` 一行没动（它是通用查询，别处要全量）。

<&backend/app/domain/mentions.py> 第 50-56 行：同名标题在 `subs` 去重时只有**第一个**生效，后面的静默指向那一个。已写测试钉住现状（`test_duplicate_titles_resolve_to_the_first_one_only`）。
