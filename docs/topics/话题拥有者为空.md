
## 这个话题在查什么

@chiruotong 问：新开话题时，拥有者为什么有的有、有的是空的。查下来是**一格数据缺失**加**一处代码漏洞**，不是显示问题。

## 结论：owner 空不空，取决于「谁创建的」，不是「什么时候创建的」

话题的 owner 由 `TopicService._resolve_owner`（<&backend/app/domain/topic/services.py>）按兜底链决定：

1. 创建者本人 —— **但芝士不算**（`looks_like_agent_handle` 把整个 `cheese-<hex>` 分身命名空间排掉，故意的，否则分身会变成房主）
2. 落空 → 父房间的 owner
3. 再落空 → 项目的 `owner_handle`
4. 再落空 → **项目的组长（lead）** —— 2026-08-12 main 上新增的一级，正是拿本话题测出来的数据当依据
5. 还落空 → 空

**这个项目的第 2、3 级同时是空的**：`project.owner_handle` 是 `null`，根话题 `ddfec621` 自己也没有 owner。所以只要创建者不是一个已登录的真人，产出的就是无主房间。@wangchangxin 实测：40 个活话题里 20 个空。

按路径拆：

| 路径 | 现在的结果 |
|---|---|
| 前端「新建话题」，已登录 | 有 owner（第 1 级直接命中） |
| 前端「新建话题」，token 过期/未登录 | 空（前端传的 `created_by` 是空串） |
| 拆子话题（分身发起） | 看父房间：父房间有主就继承，直挂根话题的就是空 |
| 讨论升级 | **曾经必空**（这条路由压根没接兜底梯子）——已修，见下 |

## 为什么不只是显示问题

`owner_handle` 是全仓七处权限判定的依据（`auth.py` / `proxy.py` / `auth/caller.py` / `machines.py` / `connector.py` / `projects.py` / dogfood 档位）。但**不是「谁都做不了」**——其中五处是 `project_members` 优先、owner 只是 `or` 兜底，所以有项目成员行的人照常通过。真正失效的是「项目主人」这一条身份线。

另有一条连锁：`project/services.py:46` 是 `if team_id is None and owner_handle:`，owner 为空导致 `team_id` 也没解析，`machines.py` 的团队分支因此一并断掉。

无主房间也不是死局：`TopicMemberService._require_manager` 有逃生口——房间没有任何管理者时，项目 owner 或 lead 可以接管。这个项目只有 @andy 是 lead。
