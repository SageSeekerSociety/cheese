修掉「话题没有拥有者」——<@maxiaoyu> 反馈存在无 owner 的话题。已复现、定位根因、做完前向修复；存量数据的回填脚本已就绪，等拍板后再跑。

## 现状：不是个案，是系统性缺口

扫了本项目全部 **123 个话题：89 个没有 owner**（其中 4 个连成员表都是空的，是 8 月 3 日之前的遗留话题）。按类型分：`task` 52 个、`subtopic` 21 个、`topic` 15 个，还有项目本体（root）本身。

<@maxiaoyu> 给的那个「credits设计」话题成员表里只有芝士一个 `member`，确实没有 owner，复现无误。

**实际危害**：`can_manage_roster` 要求 owner/admin 才能改成员表。没有 owner，就没有人能给这个话题加人、删人、改角色——房间的成员表被永久冻结，且没有自救路径。

## 根因

三段串起来的链条：

1. `seed()`（<&backend/app/domain/topic_membership/services.py>）**故意**不让芝士当 owner：`if owner_handle and owner_handle != CHEESE_HANDLE`。所以 `owner_handle` 是 `None` 或 `"cheese"` 时，房间只种下芝士，没有 owner。
2. `TopicService.create()`（<&backend/app/domain/topic/services.py>）把 `created_by` 原样传给 `seed()`，**没有任何兜底**。于是两种情况直接产出无主房间：芝士自己开的话题；以及调用方 token 没解析出身份（anonymous）时——前端 `createTopic()` 根本不传 `created_by`，所以任何一次 token 失效都会静默造出无主话题。
3. `split_to_subtopic()` 里子话题的 owner 兜底到**父话题的 owner**。父话题无主 → 子话题也无主，**沿着话题树级联**。这就是 52 个 `task` 全部无主的原因。

值得一提：第 3 条的兜底是之前修「split 端点鉴权缺失」时补的（见 <&backend/tests/integration/test_split_authz.py>），当时只补了 split 这一条路径，**create 这条没补**，所以缺口一直留着。

## 已完成的修复

**前向修复**（<&backend/app/domain/topic/services.py>）：给 `create()` 补上和 split 同样的 owner 兜底链，并多加一级——

> 真人创建者 → 父话题的 owner → 项目的 owner

同时把 `split_to_subtopic()` 的兜底也延长到项目 owner，让"父话题无主"不再往下级联。

**测试**（<&backend/tests/integration/test_topic_owner_seed.py>，5 个功能测试）：真人创建 / 芝士创建 / 完全匿名创建 / 无主房间下再 split / 以及修复后的实际效果——owner 真的能给芝士开的房间加人（修复前这里是无解的 403）。

**存量回填**（<&backend/scripts/backfill_topic_owners.py>）：同一套兜底链，外加一级只对历史数据成立的判据——**话题里第一个真人发言者**。对「credits设计」这种芝士开的、项目本身又没有 owner 的房间，这是唯一能证明房间归属的证据。默认 dry-run，`--apply` 才写库；幂等；判不出来的话题原样保留并单独列出，不瞎猜。（顺带排掉了纯数字 handle——那是 token 降级留下的脏数据，它匹配不上任何成员表。）

### 头两版预览是错的，修了两处

1. **判据太松**：`system` 会以 `author_type=human` 发言但它不是人；`470` 是 token 降级留下的死 handle（`待解决问题清单` 的 owner 就是它，profile 查出来是个空壳）。第一版直接把这两个当 owner 用了，还会往子话题传染。现在所有候选必须是**该项目的成员**，数字 handle 先还原成真实用户名再验证；已有的 owner 同样过这道闸，所以顶着死 owner 的话题也会被一起修。
2. **root 不能靠猜**：root 被判给 andy 之后，整棵树顺着「父话题 owner」全继承成 andy，把 `credits设计→池若彤` 这类本地证据冲掉了——96 个话题全成 andy。现在「首个真人发言」这一级**不作用于 root**：项目本体的 owner 按定义来自项目 owner，猜不出来就保留。

## 上游根因：项目本身没有 owner

排查 root 无主时挖到的：本项目 `projects.owner_handle` 是 **NULL**，`team_id` 也是 NULL。建项目时 `seed_root(owner_handle=None, member_handles=[])`，当时项目还没成员——**root 只种下了芝士，96 个无主话题的源头就在这一行**。

连锁影响不止 root：一串权限判定拿项目 owner 当兜底身份，它是 NULL 就没人能通过——设质量闸门 `check_command` 要求「项目 owner **或** 项目 lead」（<&backend/app/api/routes/projects.py> 第 465 行），而 8 个成员全是 `member`、一个 lead 都没有；云机器管理同理，`team_id` 也是 NULL 所以团队那条路一并断了。

已拆出 @项目 owner 为空 跟踪（简报里带了全部已查实的事实，含「平台没有任何接口能改 `owner_handle`」这个卡点）。

**已执行的临时解锁**（<@maxiaoyu> 拍板）：把 andy 的项目角色从 `member` 提为 `lead`，质量闸门那条判定即刻生效。注意设置闸门的端点明确拒绝 agent，所以要由 andy 本人操作，我验证不了写入这一步。

## 排查途中另外撞见的（已拆出去跟）
