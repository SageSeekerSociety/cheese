# room / task / agent / session：语义、管理与关系

> 本话题的主交付。@fulu 2026-08-17 要求：把四个词的语义定清楚，说明同类之间怎么管理、
> 跨类之间是什么关系。
>
> 每条「现状」都读过代码；核实过程和证据在 <&docs/topics/room与task设计与审批流程.md>。
> 凡是**建议**，都标了它解决的是哪个已经发生过的问题——没有为了整齐而整齐的改动。

## 0. 一句话总纲

> **房间是地方，一件事是交付，芝士是行动者，会话是它此刻的上下文。**
> 前三个是产品概念，第四个不是——用户永远不该看见「会话」这个词。

四者的寿命必须各自独立，这是 issue #184 定下的原则。#184 把「房间」从「一件事」里解放了，
但**没有解放另外两个**：芝士的身份仍然由话题 id 派生，会话仍然与话题一对一。
本方案要补的就是这后半段。

## 0.1 修订（2026-08-17，@fulu 拍板）

三条决定，会推翻下面一部分内容，以这里为准：

1. **容器不回收。** 理由：一个话题往往是连续的。这条有实证支持——容器重建会擦掉容器内现装的
   工具链（`jj`、`procps`、git identity 都要重装，CLAUDE.md 的 Testing 一节记着这件事），
   所以「重建」不是零成本。**下面 §2.4 和 §4 里「按闲置回收」的建议作废**，8 小时的 reaper
   应该关掉或大幅放宽。
   > 唯一的例外必须单独处理：**计费云 VM**。`_release_topic_compute` 的注释写着
   > *"archive is its only reclamation lifecycle"*——归档是它唯一的回收路径。容器不回收没有代价
   > （本机资源），云 VM 不回收是持续烧钱。这一条仍然需要一个策略，见 §6。
2. **agent 和 session 暂时不管。** §1.3、§1.4、§2.3、§2.4、§4 第三步和第五步全部搁置。
   注意 §1.3 那个核实结论仍然成立（记忆的真实粒度是话题，不是芝士），只是不在这一轮修。
3. **本轮要落实的是另外四件事**，见 §8。

## 1. 四个词分别是什么

### 1.1 room（房间）

**是什么**：一个持续存在的协作场所。它有三样东西——成员名册、消息时间线、一份实况文档。
**它自己不做事**，它是事情发生的地方。

**寿命**：永久。人可以归档它，但那纯粹是「从列表里收起来」，不是「它结束了」。

**现状**：`TopicKind.root`（项目本体）和 `TopicKind.topic`（二级房间）。根的孩子是房间，
房间只嵌套一层（`_child_kind`）。

**现状与定义的两处偏差**：
- 房间**也有分支和工作区**：`branch_for_topic()` 对任何话题 id 都给一个分支名，不看 kind。
  按定义房间不该有——它不交付东西。
- 房间**也能递验收卡**：`create_card` 完全不看 kind。挡住这件事的只有注入给芝士的阶段说明。

### 1.2 task（一件事）

**是什么**：一次交付。它有一个分支、一张验收卡、一条进度。

**寿命**：**与卡共存**（@fulu 2026-08-17 定）。卡结束＝这件事结束。

> ⚠️ 必须精确到「卡**被采纳**」。一个 task 生命周期里可以有多张卡：递卡 → 被驳回 → 改完再递
> （`reject()` 之后话题保持 active，而 `create_card` 的阻塞集**故意不含** `gate_failed`）。
> 所以 `rejected` / `revoked` / `void` 都是「卡结束」，但都**不**结束 task。
> 这条不写死，语义当场就漏。

**结束 ≠ 归档**：结束是自动的（卡被采纳那一刻），归档是人为的（整理列表）。这是本次要改的核心。

**现状**：`TopicKind.task` 是一个完整的话题行——有自己的成员名册、自己的会话、自己的 agent 身份。
所以它现在实际是「一个会终止的房间」，而不是「房间里的一张卡」。#184 自己也承认了这一点
（「按设计它应该是话题时间线里的一张卡片」），但把它当成前端待办；实际缺的是**数据层的一条边**：
`cheese split` 不往父话题写任何 block，所以「一件活被派出去」在房间时间线上完全无痕。

### 1.3 agent（芝士 / 分身）

**是什么**：一个有身份的行动者。身份 = 一个 handle + 一条 `AgentBinding` 行
（「是不是 agent」是派生的，不是 user 表上的字段）。

**寿命**：应当**长期存在，跨房间**。它是唯一能跨房间流动的东西——这是 #184 自己的论证：
「聊到哪了」天生跨不了房间，所以「同一个芝士」只能靠「记住了什么」成立。

**现状（这是本方案最重要的一条核实）**：handle = `cheese-<话题 id 前 12 位 hex>`，
**纯函数派生，每个话题自动生一个，一对一**。建房间时 `seed()` → `ensure_topic_agent_seat()`
坐进 roster 的就是「这个话题自己的分身」，docstring 明写着「不是共享的平台账号」。

**于是有一条 #184 没预料到的后果**：记忆池 = `(project_id, agent_handle)`，而 agent_handle 由
话题 id 派生 ⇒ **记忆的真实粒度是话题，不是芝士**。具体地：

- 我在这个房间记的东西，**别的房间的芝士读不到**；
- 一个 task 做完归档后，它的分身再也不会有新的一轮，**它的记忆池永久孤立**——数据还在，但没人再读；
- 跨话题真正共享的，只剩一个**不再增长的 legacy `project` 池**（分池上线前写的那些）。

所以 #184 那句「『同一个芝士』靠记忆跨房间成立」，**在当前实现下不成立**：
分池上线那一刻，跨话题的经验流动就断了，只留下一条会越来越不相关的历史尾巴。
这不是 #184 做错了——它修的是「分不出是哪个芝士」，修对了；但它把身份**绑在了话题上**，
于是身份的寿命又一次等于话题的寿命，正是它自己反对的那个错误的另一种形态。

### 1.4 session（会话）

**是什么**：一段对话上下文。**它是实现细节，不是产品概念。**

**寿命**：可丢弃、可重建，随时可以从头开始。任何依赖「会话还在」的设计都是错的。

**现状**：`topic.session_id`，一个话题一个，靠 `--resume` 续；容器被回收不影响它
（transcript 挂在宿主的 `/home/node/.claude`，工作区是宿主的 jj workspace）。
**没有主动轮换或压缩机制**——撑爆了靠 Claude Code 自己处理，平台不管。

## 2. 同类之间怎么管理

### 2.1 room 之间：扁平集合，不要层级

- **一层就够**：所有房间都挂在项目本体下，互为兄弟。房间之间**没有父子**。
- **管理动作**：建、归档／取消归档（人为，纯整理）、成员进出、`@标题` 交叉引用。
- **不需要**：房间的目录树、房间的依赖关系。房间多了靠搜索和未读，不靠层级。
- **现状缺口**：房间之间没有「这两个房间在做同一件事」的检测。目前唯一的撞车检测在 task 层，
  且只覆盖一种情况（两张未决卡各带一个 alembic 迁移就提醒，`_warn_about_a_second_pending_migration`）。

### 2.2 task 之间：只管两件事——并行度和撞车

- 一个房间里可以**同时跑多个 task**。git 层面它们是扁平的：每个 task 分支都从 main 切、
  都合回 main（`merge_topic` 合进 base branch，不存在「合回父话题分支」）。
- **一个 task 同时只有一张活卡**（`create_card` 的阻塞集），这是对的，保持。
- **task 不能嵌套**——#184 已经宣布，但**代码没有强制**：`split_to_subtopic` 只检查归档、
  不检查 kind，`cheese split` 的帮助文本还写着「没有深度/频率上限」。建议改成直接报错。
- **不需要**：task 之间的依赖图。@fulu 说的「开子话题要慎重」就是这个意思——
  能不拆就不拆，拆出来的每一件都得是独立可交付的。

**判据（建议写进规则，替换「任务大小」）**：一件事该独立成 task，还是交给容器内的 subagent？
问一句：**它的产出会不会落进房间里所有人都能看见的公共记录？** 会 → task；不会 → subagent。
理由是 subagent 的真实成本：它的产出只在容器 transcript 里，房间里的人看不见，跑偏了没人能
中途纠正、挂了没人知道。所以「小任务给 subagent」隐含一个赌注——这件事不会失败到需要人介入；
而 subagent 最常见的失败恰恰是**自信地返回一个错结论**。

还有一条硬判据（现在没人写）：**依赖父话题尚未合并的改动的活，绝对不能拆 task**——
子话题的工作区是从 main 新建的（`_ensure_worktree` 用 `jj workspace add`，没有 parent 参数），
它看不见父话题分支上的改动，只会在旧基线上重做一遍或者直接冲突。
（spec §6.3 那句「子话题的分支从父话题切出来」与代码不符，需要改。）

### 2.3 agent 之间：现在**完全没有管理**，这是最大的缺口

现状是：每个话题自动生一个 agent 身份，**永不复用、永不合并、永不消亡**。
所以「agent 之间的关系」这个问题今天没有答案——它们之间没有任何关系。

**建议：把 agent 身份从话题解绑。**

- 一个项目里有**少数几个长期存在**的芝士：默认一个「项目芝士」，需要时再加专项的
  （比如一个只管运维的）。数量级是「人数量级」，不是「话题数量级」。
- 芝士是**被加进房间**的，不是随房间生出来的。基础设施已经就绪：`topic_memberships` 支持
  多个 agent 座位，`agent_handles()` 返回的就是列表，注释明写「a room may host more than one 芝士」。
- 记忆随身份走：`(project_id, agent_handle)` 这个 key 不用改，改的是 handle 的**来源**——
  从「话题 id 派生」变成「roster 里坐着谁」。
- 这正是 buzz 的选择，也是 places-and-actors 说「我们缺 actor 这一半」的具体所指：
  在 buzz 里 `agents: Vec<Option<OwnedAgent>>` 是**进程槽**，派活时找不到亲和的槽就用任何空闲槽，
  身份（密钥）和进程完全解耦。**同一个 agent ＝ 同一把密钥，不是同一个进程。**

**代价要说清楚**：一旦一个芝士进多个房间，「它在 A 房间说的话，在 B 房间不知道」这件事会更显眼
（今天不显眼，因为每个房间是不同的分身，本来就该不知道）。这个落差只能靠记忆和文档补，
补不满——buzz 也补不满，它连同一个房间内的会话连续都不保证。**这是要接受的，不是要修的。**

### 2.4 session 之间：可丢弃，不承担连续性

- **一个 (地方, 芝士) 对一个 session**。这正好是 buzz 的 `channel_id → session_id` 映射。
- **UI 永不暴露**。用户看到的是房间和消息，不是会话。
- **建议补主动轮换**：按轮数或体积主动重开，而不是等撑爆（buzz 有 `turn_counts` +
  proactive rotation，我们没有）。撑爆之后再处理，代价永远比主动轮换高。
- 轮换后靠什么接上？**记忆 + 房间的实况文档**。buzz 在 session 出生时各注入一次
  （`core_sections` + `canvas_sections`），我们每轮都重新注入，效果更强、成本更高。

## 3. 跨类关系

| 关系 | 应该是 | 现状 | 差在哪 |
|---|---|---|---|
| room × task | 1 : N。房间是容器，task 结束不影响房间；**task 不能跨房间** | 1 : N ✅ | task 是完整话题行而非房间里的卡片；派出去在房间时间线上无痕 |
| room × agent | N : M。芝士被加进房间 | **1 : 1，自动派生** | 身份绑在话题上（§1.3），记忆因此跨不了房间 |
| room × session | 房间自己不干活，但房间里的芝士要说话 ⇒ 每个 (room, agent) 一个 session | 1 : 1（`topic.session_id`） | 一个房间进了两个芝士就没地方放第二个 session |
| task × agent | N : 1。一件事由一个芝士负责（谁做的） | 1 : 1，且是**专为它生的** | 应该是「把已有的芝士派到这件事上」，不是「为这件事造一个芝士」 |
| task × session | 干活的上下文，task 结束即可丢 | 1 : 1 | 现状可接受；但 task 结束时 session 和记忆一起被孤立 |
| agent × session | 1 : N。芝士在每个它所在的地方各有一份上下文 | **1 : 1** | 三者（话题／身份／会话）今天绑死成一根，这是所有偏差的同一个根 |

**一句话看清全局**：今天「话题 = 身份 = 会话 = 工作区」四位一体，#184 只把「房间」拆了出去。
剩下三个仍然是一根绳，所以每解决一个问题都会在另一处冒出来。

正确的形状是两个轴：

```
地方（房间 / 房间里的一件事）   ← 人和芝士在这里说话、交付
行动者（芝士）                  ← 有身份、有记忆，进入若干地方
   会话 = (行动者, 地方) 的交点，可丢弃
   工作区 = (一件事) 的附属物，可重建
```

## 4. 从现状到目标的最小路径

每一步单独可上、单独可验证，且不依赖后面的步骤。

**第一步：止血（各对应一个已发生的事故，建议先做）**

1. **释放算力从「归档」解绑**。今天 `_release_topic_compute` 挂在采纳／归档上，而它做三件事：
   删容器（会自动重建，无所谓）、释放设备屏、**销毁计费云 VM**。最后一个的注释写着
   *"archive is its only reclamation lifecycle"*——归档是计费机器**唯一**的回收路径。
   归档一旦改成人为，机器回收就交给了人的记性。容器已经有闲置回收（8 小时／每小时扫），
   把云 VM 也纳入按闲置回收。
2. **「已交付」冻结点**。卡被采纳时自动冻结工作面，不要等人归档。否则合并后还能在已合掉的
   分支上继续改、继续递卡，开出来的 PR 大概率是空的——PR #257 已经这样空合并过一次。
3. **改 `cheese accept-request` 的帮助文本**，删掉「递卡后平台会自动跑一遍检查」那段。
   平台闸门已经退休（`review/gate.py` 首行写着 NO LONGER DISPATCHED），这段话正在让每个
   芝士以为有兜底而不自己跑测试。

**第二步：把「结束」和「归档」拆成两件事**

4. 给话题加 `delivered_at`：卡 accepted 时自动写，负责冻结工作面 + 触发算力回收 + 进度定格；
   `archived_at` 保持人为，只管列表可见性。
   （另一种做法是话题状态完全由卡推导，但侧栏列表现在只查 topics 表，推导要 join，更复杂。）
5. `revoke` 的文案要说清：撤销的是**这次验收记录**，不是**这次合并**——PR 已经在 main 上了，
   revoke 在 git 层面什么都没撤销。
6. 给「已交付但未归档」一个默认收敛：列表默认折叠，或交付 N 天后自动归档。
   否则没人会去归档，列表只会堆积。

**第三步：agent 身份从话题解绑**（这一步最大，建议单独立 issue）

7. `resolve_agent_handle` 的 fallback 从 `topic_agent_handle(topic_id)` 改成「项目的默认芝士」；
   建房间时不再自动造新身份，而是把项目的芝士加进 roster。
8. 已有的 per-topic 池要有迁移策略：或者归到项目芝士名下，或者保留为只读历史。
   **数量级要先量**（有多少个 `cheese-*` handle、各自多少条记忆），再决定合并还是弃。
9. 顺带解决「跨芝士的运维经验没有落点」：像「沙箱里跑 jj 会把全项目打停」这种经验，
   既不属于任何房间、又太琐碎不值得开 PR 改 CLAUDE.md，今天只留在踩到它的那个分身脑子里。
   身份少了之后，这个问题自然缓解一大半。

**第四步：task 卡片化**（需要前后端一起，#184 已列为待办）

10. `cheese split` 时往父房间写一条 block，让「派出去」成为时间线上的一个事件。
    这是「task 是房间里的一张卡」的**数据前提**，不是渲染问题。
11. `split_to_subtopic` 增加 kind 检查：task 下面不许再 split，直接报错。
    同步改 `cheese split` 帮助里「没有深度/频率上限」那句。

**第五步：session 卫生**

12. 主动轮换（按轮数／体积），别等撑爆。
13. 一个房间容纳多个芝士时，session 的 key 从 `topic_id` 改成 `(topic_id, agent_handle)`。
    这一步依赖第三步。

## 5. 这套设计的已知代价

诚实列出来，免得以后被当成没想到：

- **芝士跨房间之后，「它在别处说过的话」它不知道**——只有记忆和文档能带过去，带不全。
  buzz 也带不全（它连同一房间内的会话连续都不保证）。这是要接受的。
- **少数长期芝士会让记忆池变大**，撞注入预算（50 条 ＋ 20000 字符）的概率上升。
  真正的解法不是提高上限，而是学 buzz 的分层：**一条 core（我是谁／我的规则）每轮在场，
  其余按需检索**——我们现在是把 50 条平铺事实全量注入（本项目 59 条约 13k 字符）。
  这件事和 issue #187（记忆系统三层分工）是同一个问题，**建议合并讨论，不要单独开**。
- **「归档」变成纯人为之后，没人会做**。所以第二步的第 6 条不是可选项。
- **agent 解绑是一次身份迁移**，涉及历史消息的作者归属和记忆池归属，要么迁要么留成只读，
  没有第三条路。这是本方案里唯一一处真正的一次性成本。

## 6. 需要拍板的三件事（按 0.1 的修订更新过）

1. **云 VM 的回收策略**——这是「容器不回收」之后**唯一还没解的**：容器不回收没有代价
   （本机资源），云 VM 不回收是持续烧钱，而它今天唯一的回收路径就是归档，
   偏偏归档正要改成人为。三个选项：保留到人归档 / 授权额度内芝士自动续租 /
   闲置 N 小时释放并提前在房间说一声。
   （我倾向后两者组合：授权一次给**一段额度**——「谁付钱」人只需决定一次，
   「现在要不要一台机器」不需要人参与。）

## 8. 本轮要落实的四件事

### 8.1 一个意外干净的落点

前三条指令（PR 不是话题终态 / 机器不回收 / 归档人为）**全部落在同一处代码**：
`AcceptService._finish_pr_accept`（<&backend/app/domain/review/services.py>）。它在 PR 合并后
连做三件事：

```
card.status = accepted          ← 这件事交付了：对
_release_topic_compute(topic)   ← 释放算力（含销毁计费云 VM）：要拆出去
topic.status = archived         ← 归档话题：要去掉
```

改法就是把后两行拆掉：交付照旧自动，归档交给人，算力回收另走一条路（容器不回收，云 VM 单独策略）。
**这是全部三条指令的最小改动面**，比我原方案里的五步路径小得多。

顺带要跟着改的两处：`AcceptService.accept()` 里本地合并那条路的收尾（同样写 archived）、
以及 `revoke()`（它清 `archived_at`，而话题不再自动归档之后这个动作没有意义了）。

### 8.2 「PR 不是话题终态」的准确语义

合并只说明「这一份改动进了 main」。它**不**说明部署了、生效了、有人验过了。
所以合并之后话题继续活着，接着做的事在同一个房间里继续。

要注意这与 issue #206 的边界：#206 拍板「任务的终态是 merged，部署不是平台语义」，
理由是部署是每个项目自己的 ops 概念，平台定义不了（等部署的卡曾经死等过永远不会出现的
workflow run）。这一条**不矛盾**——#206 说的是「平台不去判断部署成功」，
现在说的是「**话题**不因为合并而结束」。两者可以同时成立：
卡到 `accepted` 就完了（#206 保持），话题保持 active（本条改动）。
部署的可见性仍然走 webhook 原语（`POST /webhooks/{topic_id}`），由流水线自己回吐进房间。

### 8.3 母话题 ↔ 子话题的通讯：**这条路现在是断的**

核实结果，两个方向都有问题：

**子 → 母（能走，机制完整）**：`cheese conclude` 开一张结论卡（`ConclusionCard`，接收方是
**话题**而不是人），父话题那一轮结束时**默认采信**（另有 30 分钟绝对超时），
父话题可以 `need-evidence` 打回一次或 `escalate` 转人。这套是完整的。

**母 → 子（写得进去，但叫不醒）**：唯一的通道是往子话题发评论
（`POST /api/topics/{id}/comments`）。核实发现两个问题：

- 那个端点里 summon 的条件是 **`if not actor.is_agent`** ——只有**人类**评论才会唤醒目标话题的
  芝士。父话题的芝士用自己的 token 去写，走不进这个分支，**评论落库了但没人被叫醒**。
- 这条路由**不在** `app/main.py` 的 `_CHEESE_WRITE_PATHS` 里，所以 agent 调它压根不过那道
  per-turn token 门——是**静默放行**，不是 401。

所以「母话题给已经在跑的子话题追加要求」这件事，今天在机制上不成立
（我在之前几轮里按注入的操作说明转述过「这条会唤醒目标话题」，**那句是错的**）。

**建议**：给一条**显式的、双向对称的**通道，而不是靠评论端点的副作用：

- 新增 `cheese tell <话题> "<内容>"`（或复用 `cheese notify` 的语义），后端写 block + **summon**；
- 路由进 `_CHEESE_WRITE_PATHS`，并且**允许跨话题**——但只允许「父 → 直接子」和「子 → 父」
  两个方向，不做任意话题互发（否则等于放弃话题级隔离）；
- 唤醒要**幂等 + 合并**：同一个子话题连收三条，应该合成一轮，别叫醒三次。

另外一个已知缺口顺手补掉：**退回验收卡（`reject`）不通知任何人**——`reject()` 只改数据库那一行，
既不发消息也不 summon，跟 CI 失败会 summon 的行为不一致。它和上面是同一条通道。

### 8.4 commit 可视化

现状：房间时间线上**已经有**「写文件 / 改文件 / 执行命令」这类现场事件（工具调用流式落 block），
文件面板能看 `topic_diff` 和文件列表。**缺的是「提交」这一层**：这个话题产生了哪几个 commit、
每个 commit 动了什么、现在分支上是什么。

要注意一个前提：平台的快照是 jj 自动做的（每轮把工作区折成提交），所以「commit」在这里
不是人工的动作，而是**平台的记账**。所以可视化的对象应该是：

- **分支现在的状态**：相对 `main` 领先几个提交、动了哪些文件（`topic_diff` 已经能给）；
- **每一轮产生的提交**：一轮结束时在房间里落一条「这一轮改了 N 个文件（+X −Y）」的事件，
  点开是 diff。这条比「commit 列表」对人更有用——**人关心的是「这一轮做了什么」**，
  而不是 jj 的提交拓扑。
- **PR 上的提交**：卡进入 `pr_open` 之后，PR 分支的 head 会随每次重推移动
  （`pr_head_sha`），这个已经在卡上了，只是没渲染成「提交流」。

### 8.5 子话题往母话题的 PR 上提交

技术要害在一处：**分支名是从话题 id 派生的**——`branch_for_topic(topic_id)` 返回
`topic/<hex8>`，工作区由 `_ensure_worktree` 用 `jj workspace add` 从主仓库当前 `@`（即 main）
新建，**没有 parent 参数**。所以今天的模型是「一个话题 = 一条从 main 切出来的分支」，
子话题和母话题在 git 层面是**兄弟**，各自合回 main。

要让子话题往母话题的 PR 分支提交，要改的不是工作区（工作区必须各自独立——
places-and-actors 明说「共享 worktree 保证撞车」），而是**分支的归属**：

- 话题需要一个「我往哪条分支交付」的字段（`branch_name` 这个列**已经存在**，
  只是今天没被当作真相用——真相是 `branch_for_topic()` 那个纯函数）；
- 子话题 split 时可以选择「独立交付」（默认，切自己的分支）或「并入母话题的交付」
  （工作区仍从母话题分支切，提交推到母话题的分支）；
- 后者要接受一个代价：**多个话题往一条分支推，就会有冲突**，需要顺序化或者提前划分文件边界。
  这正是简报里「硬边界」那一段本来该写的东西，只是今天它是建议、不是机制。

**建议的顺序**：先做 8.1（拆 `_finish_pr_accept`）和 8.3（通讯通道），
它们各是十几行、各自独立可验证；8.4 是一条新的 block 类型；8.5 最大，且它的价值依赖 8.3
（并入同一条分支之后，母子之间必须能实时对话，否则冲突没法协调）。

## 9. 要不要把 subagent 改造成子话题（共用一个 room）

**方向对，但「被看见」和「独立成一个话题」是两件事，混在一起会付不必要的代价。**

先说对的部分：subagent 的真实问题**就是**看不见——它的产出只在容器的 transcript 里，
房间里的人看不见，它跑偏了没人能中途纠正、它挂了没人知道。用「进房间」来解决是正解，
而且 places-and-actors 早就写了那条划界原则：**产出会不会落进房间里所有人都能看见的公共记录？**
会 → 平台概念；不会 → 实现细节。把 subagent 拉进房间，就是让它跨过这条线。

「共用一个 room」这个提法也是对的，而且正是那份设计文档的原话：
**一个房间里的多个行动者共享「对话」，不共享「工作区」**——共享 worktree 保证撞车。

但有三条硬约束：

**① 可见性已经有了一半，而且它很便宜。** 核实结果：`Agent`/`Task` 工具调用**已经**会在房间
时间线上落一条现场事件（`_TOOL_VERB` 里 `"Task": "派分身去查"`，参数取 `description`）。
所以房间**已经**能看到「派了一个分身去查 X」。真正缺的只是**它查出了什么**——
subagent 的返回只回到 spawner 的上下文里。
**补法：一条 block。** 把 subagent 的结论摘要也落进房间。这拿到绝大部分收益，
成本是零个容器、零个工作区、零延迟。

**② 独立成话题很贵，而且刚刚变得更贵。** 一个子话题 = 一个 jj workspace + 一个容器
（`--memory 2g --cpus 2`）+ 冷启动。而这一轮刚定下「容器不回收」——容器数只涨不跌。
再叠加「每个 subagent 一个容器」，先崩的是内存：本项目 `pnpm run build` 在 2GB 容器里都会 OOM。
一个「读三个文件回答一个问题」的活，用子话题做，开销是用 subagent 做的几十到上百倍。

**③ 它和「agent/session 先不管」直接冲突——除非走呈现层。** 真正意义上的「一个房间里多个
行动者」需要 `session` 的 key 从 `topic_id` 变成 `(topic_id, agent_handle)`，
而 `topic.session_id` 是一个字段，放不下第二个。
**但有一条不用动 session 的路径**：数据层仍是独立话题（各自 session、各自工作区），
**呈现层共用母房间的时间线**——派出去的活在房间里是一张卡，点开是它自己的对话。
这恰好就是 #184 那件没做完的事（「按设计它应该是话题时间线里的一张卡片」），
也就是 §8.4 里说的那条缺失的边：`cheese split` 今天不往父话题写任何 block。

### 结论：分三档，不要一刀切

| 这件事 | 放在哪 | 代价 |
|---|---|---|
| 纯机械（读文件、grep、格式转换、查一个事实） | subagent，**但结论要回吐房间一条 block** | 几乎为零 |
| 有产出、要被别人看见、可能失败到需要人介入 | 房间时间线上的一张**卡**（数据上是独立话题，呈现上在母房间） | 一个工作区 + 一个容器 |
| 需要多个行动者在同一个房间里并肩对话 | **暂缓**（要动 agent/session 的 key，本轮搁置） | 大 |

判据从「任务大小」换成一句可判定的话：**它的结论要不要被别人看见、要不要能被中途纠正？**
要 → 卡；不要 → subagent + 结论回吐。

### 9.1 母子共用一个容器（@fulu 2026-08-17 提议）：可行，而且是配套的必需项

**先说最大的意外：文件可见性早就不是障碍了。** `sandbox_project_mounts`
（<&backend/app/domain/workspace/service.py>）的 Isolation note 原话：

> every topic sandbox of a project **sees (and can write) its sibling topics' worktrees**.
> That is not a new trust boundary — the same containers already share the project's writable
> `.jj`/`.git` stores, so **same-project topics were never isolated from each other**.

因为 hardlink 不能跨 bind mount（jj 的 store 用硬链接），所以它是**一个 mount 挂整棵**
`.worktrees/<project_id>/` 树。也就是说：**子话题的工作区此刻就已经在母话题的容器里**，
共用容器不需要新开任何访问权限，同项目话题之间本来就没有隔离。

**真正 per-topic、必须改的只有四样**：

| 现在按话题定死的东西 | 改成 |
|---|---|
| 容器名 `container_name(topic_id)` | 按**房间** id 命名 |
| 工作目录（`/work` 这个固定 remap） | 树里的真实路径（`SANDBOX_TOPICS_ROOT/topic_<hex>`，已经在容器里） |
| **容器 env 里烤着的 `CHEESE_TOPIC` + `CHEESE_TOKEN`** | 移到**每个 tmux session 的环境**（tmux 原生支持 per-session env） |
| `/home/node/.claude`（session 目录挂载） | 挂上一层，容纳同房间多个话题 |

第三行是主要工作量，但它**顺带修掉一个已知故障**：`_hook_token_dead` 的 docstring 记着——
token 是容器创建时烤进 env 的、永不刷新，而签名密钥在部署没钉 `SANDBOX_TOKEN` 时是
**每个后端进程一个随机值**，于是**后端每重启一次，所有存量容器的 hook token 同时失效**，
话题从此再也不能回话（现在靠"发现聋了就重建容器"兜底，代价是丢掉 tmux session）。
改成 per-session 注入之后，这个 bug 自然消失。

**最重要的判断：共用容器不是省钱的优化，而是「容器不回收」这条决定的必要前提。**

- 不回收 ＋ 每话题一个容器 ⇒ 容器数只涨不跌，× 2GB，**先崩的是内存**；
- 不回收 ＋ 每房间一个容器 ⇒ 容器数跟着**房间数**走，而房间数是人的数量级。

这两条决定是配套的，应该一起做，不该分开评估。

**要接受的三个代价**：

1. **资源共享**：一个容器 `--memory 2g --cpus 2` 现在要服务整个房间。本项目 `pnpm run build`
   单独就能吃满 2GB（实测 OOM）。所以**共用的同时必须提配额**——建议按房间给 4–6GB / 4 CPU，
   否则「并行拆三个子话题」会变成互相挤。
2. **故障域合并**：一个话题把容器 OOM 掉，同房间其他话题一起死。今天它们是隔离的。
3. **jj 撞锁概率上升**：共享 store 今天就有，但同容器内并发更容易撞。

**推荐的分配规则**：容器的身份从 `topic_id` 换成**房间 id**（root/topic 那一层），
母话题和它派出的所有 task 共用一个。规则明确，不需要「看情况共用」。
后续如果峰值确实挤，可以再加一条「跑全量测试/构建这种重活时临时独占一个容器」——
但那是优化，不是第一版。

## 11. 实测更正：父→子通道不是「不唤醒」，是 **403 根本写不进去**

§8.3 里我根据代码推断「评论落库了但没人被叫醒」。**这一轮真实调用验证，比推断更糟**：

```
cheese api POST /topics/<子话题id>/comments
→ 403 ForbiddenError: 这个 token 属于别的话题，不能在这里操作
```

所以拦住它的不是 `_CHEESE_WRITE_PATHS`（那张表里确实没有 comments），而是
`ActorResolver.resolve` 自己就校验 token 的 topic。**父话题的芝士对子话题连写都写不进去。**

`cheese notify` 也不是出路——它的 `--to` 是**人**的 handle，走通知面板，不唤醒任何话题。

于是有一个很说明问题的死锁：**我这一轮想给「分身产出回吐房间」那件活传一句范围调整，
而我需要的正是「母子话题通讯通道」那件活正在修的东西。** 今天能跨话题传话的只有人——
人的 Bearer 凭据不受 topic 限制。

⚠️ 这条直接影响「母子话题通讯通道」的方案：它简报里拿到的事实是「summon 条件是
`if not actor.is_agent`」（代码确实如此），但**那一层上面还有一道 403**。
它自己会撞到，简报里也写了「发现前提是错的就 `cheese ask` 问回来」。

## 12. agent 类型：buzz 怎么做，我们已经有什么（@fulu 2026-08-17 提的方向）

读的是 `crates/buzz-persona/PERSONA_PACK_SPEC.md`（1153 行）＋ `persona.rs` / `manifest.rs`。

### 12.1 buzz 的做法

一个 **Persona Pack** 是可分发的一整包（zip 或 git repo），是 Open Plugin Spec 的超集。
一个 pack 里可以有多个 agent，每个 agent 一个 `*.persona.md` —— **YAML frontmatter 定义它是谁、
怎么跑，markdown 正文就是它的系统提示**：

```yaml
name: "lep"                  # 机器名，pack 内唯一
display_name: "Lep 🍀"       # UI 上显示的名字
description: "Security-focused code reviewer"
skills: ["./skills/security-review/"]      # 只给这个 agent 的技能
mcp_servers: [{name: semgrep, command: …}] # per-agent 工具
subscribe: ["#security-reviews"]           # 监听哪些频道
triggers: {mentions: true, keywords: [...]}# 什么情况下响应
model: "anthropic:claude-sonnet-4-…"       # 用哪个模型
temperature: 0.3
max_context_tokens: 128000
hooks: {on_start: …, on_stop: …}
```

两个机制值得单独记：

- **继承**：`plugin.json` 里的 `defaults` 是 pack 级默认，persona 没写的字段从那里解析。
  例子里四个 agent 默认 Sonnet，只有一个覆写成 Opus。
- **两层 prompt 的纪律**（这一条比 persona 格式本身更值钱）：每条消息按固定顺序拼
  `[Base]` → `[System]` → 团队说明 → `[Context]` → 会话历史 → 触发事件。
  `[Base]` 是**平台注入、每个 agent 完全一样**（平台身份、工具参考、工作区布局、怎么轮询消息），
  **pack 作者不许写也不许配**；`[System]` 才是 persona 自己的。
  规范里明文警告：**不要在 persona 里重复 base 的内容，否则用户每条消息会看到两遍**，
  并逐条列出「不要再解释」的四类内容。

### 12.2 我们其实已经有一半地基了

**`expert_roles` 和 `custom_roles` 这两张表已经在**（`backend/app/domain/expert_role/models.py`），
而且 docstring 写得很明确：

> `ExpertRole`：a role = a set of preset skills + a role description, **mapping directly to a
> Claude Code agent type**. Platform ships presets（计算机/设计/学术研究/创业…）；leads/teachers
> can define custom ones. A Task Template can name a default role.
>
> `CustomRole`：**Claude Code agents-file semantics stored relationally** —
> (name, title, description) 对应 frontmatter，`body` 就是 persona 系统提示。
> NULL space_id = 个人角色，有值 = 归某个机构。

层次也已经有了：平台预设（`project_id` 为 NULL）→ 项目自定义 → 机构（Space）拥有的 CustomRole。
另外 `.claude/agents/*.md` 里已经有 Claude Code 层面的 agent 定义（`check-runner.md` 的
frontmatter 就写着 `tools: Bash, Read` / `model: sonnet`）。

**所以缺的不是「造一套 persona 格式」，是三件具体的事：**

| 缺什么 | 说明 |
|---|---|
| **角色只管「说什么」，不管「怎么跑」** | `expert_roles` 有 `skills` ＋ `role_description`，**没有 model、没有 effort、没有工具白名单**。而这些今天散在别处：model 在 `.claude/agents/*.md`（Claude Code 层，平台不知道）、effort 根本没有、`compute_profile` 在 topic 上但那是**算力池**（在哪跑）不是**模型档位**（用多强的脑子）——两个不同的轴，很可能正是 issue #282「一个字段挤着四件事」说的问题 |
| **平台不知道 `.claude/agents/` 里有什么** | 于是人在界面上选不了，split 时也没法指定「这件活用哪个类型的芝士做」 |
| **「出厂设置」和「自己长出来的」混在一起** | buzz 把 persona（kind 30175，配置）和 engram（学到的东西）分成两种事件；我们把两者混在一个记忆池里平铺注入 |

### 12.3 建议：抄纪律，不抄格式

**值得抄的：**

1. **两层 prompt 的纪律**（最值钱）。明确划出「平台层」和「角色层」，并规定角色层不许重复平台层。
   我们现在没有这条约定——阶段说明、CLI 规则、记忆、成员表、话题表、活文档全都每轮拼进去，
   没人说得清哪一层归谁、谁该为体积负责。
2. **把「怎么跑」并进角色定义**：`expert_roles` 加 model / effort / 工具白名单。
   这直接就是 @fulu 说的「名称、harness 工程、模型、effort」。
3. **配置与记忆分离**：角色是出厂设置，core 记忆是它自己长出来的那部分。
   这和 §6.2 ① 那条「我们缺 core 这一层」是同一件事，应该一起做（并入 issue #187）。

**不建议抄的：**

- **pack 的打包分发**（zip / git repo / 校验和 / OPS 兼容）：那是为第三方作者生态准备的，
  我们现在没有第三方作者，先做数据库里的角色定义就够。
- **MCP server 配置**：我们的工具是平台内置的（cheese CLI ＋ Claude Code 内置），没有 MCP 生态需求。
- **triggers / subscribe**：我们用 @提及 ＋ summon，语义已经清楚，不需要再加一套触发规则。

### 12.4 @fulu 的 agent 池构想（2026-08-17）：两条对、一条要改

构想原文：①有一个 agent 池，可以自己创建 agent，每个 agent 的 harness 工程 / skill / mcp / memory
分别管理；②创建话题时弹窗选用哪个 agent；③每个话题是一个独立 session，但 session 内它可以管理
自己的记忆，形成良性循环。

**①② 成立，而且和这份文档 §2.3 从代码侧得出的结论撞上了。**
§2.3 的核实结论是：agent handle 今天是 `cheese-<话题 id 前 12 位 hex>`，**纯函数派生、每个话题
自动生一个**，于是记忆池 key `(project_id, agent_handle)` 的真实粒度是**话题**而不是芝士。
「从池里选一个 agent」这个动作，正是把身份从话题解绑 —— 产品侧和代码侧想到的是同一件事。
地基也已经有一半：`expert_roles` / `custom_roles` 两张表（§12.2）、roster 本来就支持多个 agent 座位
（`agent_handles()` 返回列表，注释写着 "a room may host more than one 芝士"）。

**③ 前半句对（每个话题一个独立 session），后半句必须改：记忆要跟 agent 走，不能跟 session 走。**

buzz 就是这么做的，而且证据在加密方式里：engram 事件由 **agent 自己的密钥签名**，
用 `conversation_key(agent_secret, owner_pubkey)` 加密，`d_tag = HMAC(K_c, slug)`
—— **整条链里没有 channel**。同一个 agent 在所有频道共享同一份记忆。
`SessionState.core_sections`（`channel_id → 渲染好的 core`）只是**渲染缓存**
（注释：session 创建时填一次、中途不刷新），不是「每个频道一份记忆」。

为什么这一条不能含糊：**如果记忆在 session 内管理，记忆就绑在 (agent, 话题) 上，
那 agent 池立刻失去意义** —— 同一个 agent 被派去做两件事，两边学到的东西互不知道，
它就不是「同一个 agent」，只是「同一份出厂设置的两个副本」。
而这正是我们今天已经踩到的坑（§1.3），③ 的后半句等于把这个坑固化成设计。

**「良性循环」恰恰要求记忆跨话题**：agent 在 A 话题学到「这个项目的 CI 要跑十几分钟」，
在 B 话题就该知道。记忆锁在 session 里，循环就断在话题边界上。

正确的形状：

```
agent（池里的一个身份）
 ├─ 出厂设置：harness / skills / mcp / model / effort   ← 创建时定，可改版
 ├─ 记忆：跟身份走，跨它所在的所有话题累积            ← 不跟 session
 └─ session：每个 (agent, 话题) 一个，可丢可重建       ← 用完即弃
```

### 12.5 修正我上一轮关于 MCP 的判断

§12.3 里我写「不建议抄 MCP 配置，我们的工具是内置的」。**那是在「只有一个芝士」的前提下说的，
前提变了，结论要改**：一旦有 agent 池，不同类型的 agent 本来就需要不同的外部工具
（一个连飞书、一个连数据库、一个只读代码），per-agent MCP 就有了意义。
Claude Code 本身支持 MCP，落点是把 `.mcp.json` 写进那个 session 的配置。

### 12.6 三件要一起想清楚的

1. **harness 要下沉到 agent 级。** 现在 `settings.agent_backend`（tmux / device / sdk）是**全局**的，
   不是 per-agent。「每个 agent 自己的 harness 工程」意味着这个选择要跟着 agent 走。
2. **谁是主体：agent 订阅房间，还是房间邀请 agent？** buzz 是前者（persona frontmatter 里
   `subscribe: ["#security-reviews"]`，agent 主动订阅频道）；「建话题时弹窗选」是后者。
   后者更贴合我们「话题＝群聊」的产品直觉，但要想清楚：**弹窗选的是初始值，后面还能不能加/换**
   （roster 支持多 agent，所以技术上能）。
3. **session 数量的生命周期又回来了。** ③ 意味着 session 数 = 房间数 × 该房间里的 agent 数，
   叠加「容器不回收」就是只涨不跌。buzz 一个进程的并发 session 上限是 8。
   所以 §2.4 那条「主动轮换 session」不能一直搁置 —— 不是现在做，但要记在账上。

### 12.7 和正在跑的那件活是配套的

「容器按房间分配」那件活正在做的事情之一，就是**把 `CHEESE_TOPIC` / `CHEESE_TOKEN` 从容器 env
移到 per-session 注入**。那正是这套设计的地基：一个容器（房间）里跑多个 session
（每个 agent × 每件活一个），恰好是 buzz 的形状（一个进程挂多个频道的 session）。
所以这三条构想不需要等 —— 地基已经在铺了。

### 12.8 拍板：一个房间最多一个 agent，记忆存到 agent 级（@fulu 2026-08-17）

**这两条一起，把 session 层的改动整个消掉了。**

我在 §2.4 / §12.6 里说过「一个房间放多个 agent，就必须把 session 的 key 从 `topic_id` 换成
`(topic_id, agent_handle)`」。**在「一个房间最多一个 agent」的约束下不需要了**：
一个 topic 最多一个 agent ⇒ `topic_id` 已经唯一确定了「哪个 agent 在哪个地方」这一对，
所以 `topic.session_id` 这一个字段就够，`agent × session = 1 : N` 自动成立。

顺带两个函数的语义也变干净了：
- `resolve_agent_handle(topic_id)` 现在是「取 roster 里第一个 agent handle」——有点随意；
  加上这条约束之后它名正言顺。（注意：**现在代码里没有这个限制**，`agent_handles()`
  返回列表、注释还写着 "a room may host more than one 芝士"，所以约束要新加。）
- `ensure_topic_agent_seat` 从「造一个新身份坐进去」变成「把选中的 agent 请进来」。

**明确放弃了什么**：一个房间里多个 agent 并肩对话。那本来就是我建议暂缓的那一档
（§9 第三档），拿它换掉整个 session 层的改造，这个取舍是对的。

#### 必须回答的一个问题：task 的 agent 从哪来

「一个房间最多一个 agent」约束的是 **roster 的座位数**。而 task 在数据上仍是独立的 topic
（有自己的 roster、自己的 `session_id`），所以它也有一个座位。那么：

- **建议：task 默认继承所在房间的 agent**，需要时可以在 split 时覆盖成别的。
  这样「同一个 agent 在房间主对话 ＋ 它派出的每件活上各有一个 session」自然成立，
  正是 buzz 的形状；而且 task 里学到的东西**自动流回房间**（同一个 agent、同一个池），
  这就是「良性循环」真正闭合的地方。
- 如果反过来让每个 task 自己选，那母子之间的记忆又断了——回到今天的问题。

#### 一个连锁反应：「core ＋ 按需检索」从可选变成必需

记忆到 agent 级之后，一个 agent 的池 = 它所在的所有房间 ＋ 所有 task 的总和。
而注入预算是 50 条 / 20000 字符（本项目现在 59 条就已经约 13k）。
**所以不能再全量平铺注入了**——§6.2 ① 那条（一条 core 每轮在场、其余按需检索）
从「值得考虑」变成「不做就会撞墙」。这件事和 issue #187 是同一个问题。

#### 两件要定的小事

1. **项目默认 agent**：建话题时弹窗选，但必须有默认值，否则每建一个话题都要弹一次，摩擦太大。
2. **存量 `cheese-<topic hex>` 池怎么迁**：今天每个话题一个 handle、各自一个池。
   归到项目默认 agent 名下，还是留成只读历史？**先量数量级**（有多少个 `cheese-*` handle、
   各自多少条），再定。
