# room / task / agent / session：语义、管理与关系

> 本话题的主交付。@fulu 2026-08-17 要求：把四个词的语义定清楚，说明同类之间怎么管理、
> 跨类之间是什么关系。
>
> 每条「现状」都读过代码；核实过程和证据在 <&docs/topics/room与task设计与审批流程.md>。
> 凡是**建议**，都标了它解决的是哪个已经发生过的问题——没有为了整齐而整齐的改动。

## 0. 一句话总纲

> **房间是地方，一件事是交付，芝士是行动者，会话是它此刻的上下文。**
> 前三个是产品概念，第四个不是——用户永远不该看见「会话」这个词。

四者的寿命必须各自独立，这是 issue #184 定下的原则。#184 把「房间」从「一件事」里解放了，
但**没有解放另外两个**：芝士的身份仍然由话题 id 派生，会话仍然与话题一对一。
本方案要补的就是这后半段。

---

## 1. 四个词分别是什么

### 1.1 room（房间）

**是什么**：一个持续存在的协作场所。它有三样东西——成员名册、消息时间线、一份实况文档。
**它自己不做事**，它是事情发生的地方。

**寿命**：永久。人可以归档它，但那纯粹是「从列表里收起来」，不是「它结束了」。

**现状**：`TopicKind.root`（项目本体）和 `TopicKind.topic`（二级房间）。根的孩子是房间，
房间只嵌套一层（`_child_kind`）。

**现状与定义的两处偏差**：
- 房间**也有分支和工作区**：`branch_for_topic()` 对任何话题 id 都给一个分支名，不看 kind。
  按定义房间不该有——它不交付东西。
- 房间**也能递验收卡**：`create_card` 完全不看 kind。挡住这件事的只有注入给芝士的阶段说明。

### 1.2 task（一件事）

**是什么**：一次交付。它有一个分支、一张验收卡、一条进度。

**寿命**：**与卡共存**（@fulu 2026-08-17 定）。卡结束＝这件事结束。

> ⚠️ 必须精确到「卡**被采纳**」。一个 task 生命周期里可以有多张卡：递卡 → 被驳回 → 改完再递
> （`reject()` 之后话题保持 active，而 `create_card` 的阻塞集**故意不含** `gate_failed`）。
> 所以 `rejected` / `revoked` / `void` 都是「卡结束」，但都**不**结束 task。
> 这条不写死，语义当场就漏。

**结束 ≠ 归档**：结束是自动的（卡被采纳那一刻），归档是人为的（整理列表）。这是本次要改的核心。

**现状**：`TopicKind.task` 是一个完整的话题行——有自己的成员名册、自己的会话、自己的 agent 身份。
所以它现在实际是「一个会终止的房间」，而不是「房间里的一张卡」。#184 自己也承认了这一点
（「按设计它应该是话题时间线里的一张卡片」），但把它当成前端待办；实际缺的是**数据层的一条边**：
`cheese split` 不往父话题写任何 block，所以「一件活被派出去」在房间时间线上完全无痕。

### 1.3 agent（芝士 / 分身）

**是什么**：一个有身份的行动者。身份 = 一个 handle + 一条 `AgentBinding` 行
（「是不是 agent」是派生的，不是 user 表上的字段）。

**寿命**：应当**长期存在，跨房间**。它是唯一能跨房间流动的东西——这是 #184 自己的论证：
「聊到哪了」天生跨不了房间，所以「同一个芝士」只能靠「记住了什么」成立。

**现状（这是本方案最重要的一条核实）**：handle = `cheese-<话题 id 前 12 位 hex>`，
**纯函数派生，每个话题自动生一个，一对一**。建房间时 `seed()` → `ensure_topic_agent_seat()`
坐进 roster 的就是「这个话题自己的分身」，docstring 明写着「不是共享的平台账号」。

**于是有一条 #184 没预料到的后果**：记忆池 = `(project_id, agent_handle)`，而 agent_handle 由
话题 id 派生 ⇒ **记忆的真实粒度是话题，不是芝士**。具体地：

- 我在这个房间记的东西，**别的房间的芝士读不到**；
- 一个 task 做完归档后，它的分身再也不会有新的一轮，**它的记忆池永久孤立**——数据还在，但没人再读；
- 跨话题真正共享的，只剩一个**不再增长的 legacy `project` 池**（分池上线前写的那些）。

所以 #184 那句「『同一个芝士』靠记忆跨房间成立」，**在当前实现下不成立**：
分池上线那一刻，跨话题的经验流动就断了，只留下一条会越来越不相关的历史尾巴。
这不是 #184 做错了——它修的是「分不出是哪个芝士」，修对了；但它把身份**绑在了话题上**，
于是身份的寿命又一次等于话题的寿命，正是它自己反对的那个错误的另一种形态。

### 1.4 session（会话）

**是什么**：一段对话上下文。**它是实现细节，不是产品概念。**

**寿命**：可丢弃、可重建，随时可以从头开始。任何依赖「会话还在」的设计都是错的。

**现状**：`topic.session_id`，一个话题一个，靠 `--resume` 续；容器被回收不影响它
（transcript 挂在宿主的 `/home/node/.claude`，工作区是宿主的 jj workspace）。
**没有主动轮换或压缩机制**——撑爆了靠 Claude Code 自己处理，平台不管。

## 2. 同类之间怎么管理

### 2.1 room 之间：扁平集合，不要层级

- **一层就够**：所有房间都挂在项目本体下，互为兄弟。房间之间**没有父子**。
- **管理动作**：建、归档／取消归档（人为，纯整理）、成员进出、`@标题` 交叉引用。
- **不需要**：房间的目录树、房间的依赖关系。房间多了靠搜索和未读，不靠层级。
- **现状缺口**：房间之间没有「这两个房间在做同一件事」的检测。目前唯一的撞车检测在 task 层，
  且只覆盖一种情况（两张未决卡各带一个 alembic 迁移就提醒，`_warn_about_a_second_pending_migration`）。

### 2.2 task 之间：只管两件事——并行度和撞车

- 一个房间里可以**同时跑多个 task**。git 层面它们是扁平的：每个 task 分支都从 main 切、
  都合回 main（`merge_topic` 合进 base branch，不存在「合回父话题分支」）。
- **一个 task 同时只有一张活卡**（`create_card` 的阻塞集），这是对的，保持。
- **task 不能嵌套**——#184 已经宣布，但**代码没有强制**：`split_to_subtopic` 只检查归档、
  不检查 kind，`cheese split` 的帮助文本还写着「没有深度/频率上限」。建议改成直接报错。
- **不需要**：task 之间的依赖图。@fulu 说的「开子话题要慎重」就是这个意思——
  能不拆就不拆，拆出来的每一件都得是独立可交付的。

**判据（建议写进规则，替换「任务大小」）**：一件事该独立成 task，还是交给容器内的 subagent？
问一句：**它的产出会不会落进房间里所有人都能看见的公共记录？** 会 → task；不会 → subagent。
理由是 subagent 的真实成本：它的产出只在容器 transcript 里，房间里的人看不见，跑偏了没人能
中途纠正、挂了没人知道。所以「小任务给 subagent」隐含一个赌注——这件事不会失败到需要人介入；
而 subagent 最常见的失败恰恰是**自信地返回一个错结论**。

还有一条硬判据（现在没人写）：**依赖父话题尚未合并的改动的活，绝对不能拆 task**——
子话题的工作区是从 main 新建的（`_ensure_worktree` 用 `jj workspace add`，没有 parent 参数），
它看不见父话题分支上的改动，只会在旧基线上重做一遍或者直接冲突。
（spec §6.3 那句「子话题的分支从父话题切出来」与代码不符，需要改。）

### 2.3 agent 之间：现在**完全没有管理**，这是最大的缺口

现状是：每个话题自动生一个 agent 身份，**永不复用、永不合并、永不消亡**。
所以「agent 之间的关系」这个问题今天没有答案——它们之间没有任何关系。

**建议：把 agent 身份从话题解绑。**

- 一个项目里有**少数几个长期存在**的芝士：默认一个「项目芝士」，需要时再加专项的
  （比如一个只管运维的）。数量级是「人数量级」，不是「话题数量级」。
- 芝士是**被加进房间**的，不是随房间生出来的。基础设施已经就绪：`topic_memberships` 支持
  多个 agent 座位，`agent_handles()` 返回的就是列表，注释明写「a room may host more than one 芝士」。
- 记忆随身份走：`(project_id, agent_handle)` 这个 key 不用改，改的是 handle 的**来源**——
  从「话题 id 派生」变成「roster 里坐着谁」。
- 这正是 buzz 的选择，也是 places-and-actors 说「我们缺 actor 这一半」的具体所指：
  在 buzz 里 `agents: Vec<Option<OwnedAgent>>` 是**进程槽**，派活时找不到亲和的槽就用任何空闲槽，
  身份（密钥）和进程完全解耦。**同一个 agent ＝ 同一把密钥，不是同一个进程。**

**代价要说清楚**：一旦一个芝士进多个房间，「它在 A 房间说的话，在 B 房间不知道」这件事会更显眼
（今天不显眼，因为每个房间是不同的分身，本来就该不知道）。这个落差只能靠记忆和文档补，
补不满——buzz 也补不满，它连同一个房间内的会话连续都不保证。**这是要接受的，不是要修的。**

### 2.4 session 之间：可丢弃，不承担连续性

- **一个 (地方, 芝士) 对一个 session**。这正好是 buzz 的 `channel_id → session_id` 映射。
- **UI 永不暴露**。用户看到的是房间和消息，不是会话。
- **建议补主动轮换**：按轮数或体积主动重开，而不是等撑爆（buzz 有 `turn_counts` +
  proactive rotation，我们没有）。撑爆之后再处理，代价永远比主动轮换高。
- 轮换后靠什么接上？**记忆 + 房间的实况文档**。buzz 在 session 出生时各注入一次
  （`core_sections` + `canvas_sections`），我们每轮都重新注入，效果更强、成本更高。

## 3. 跨类关系

| 关系 | 应该是 | 现状 | 差在哪 |
|---|---|---|---|
| room × task | 1 : N。房间是容器，task 结束不影响房间；**task 不能跨房间** | 1 : N ✅ | task 是完整话题行而非房间里的卡片；派出去在房间时间线上无痕 |
| room × agent | N : M。芝士被加进房间 | **1 : 1，自动派生** | 身份绑在话题上（§1.3），记忆因此跨不了房间 |
| room × session | 房间自己不干活，但房间里的芝士要说话 ⇒ 每个 (room, agent) 一个 session | 1 : 1（`topic.session_id`） | 一个房间进了两个芝士就没地方放第二个 session |
| task × agent | N : 1。一件事由一个芝士负责（谁做的） | 1 : 1，且是**专为它生的** | 应该是「把已有的芝士派到这件事上」，不是「为这件事造一个芝士」 |
| task × session | 干活的上下文，task 结束即可丢 | 1 : 1 | 现状可接受；但 task 结束时 session 和记忆一起被孤立 |
| agent × session | 1 : N。芝士在每个它所在的地方各有一份上下文 | **1 : 1** | 三者（话题／身份／会话）今天绑死成一根，这是所有偏差的同一个根 |

**一句话看清全局**：今天「话题 = 身份 = 会话 = 工作区」四位一体，#184 只把「房间」拆了出去。
剩下三个仍然是一根绳，所以每解决一个问题都会在另一处冒出来。

正确的形状是两个轴：

```
地方（房间 / 房间里的一件事）   ← 人和芝士在这里说话、交付
行动者（芝士）                  ← 有身份、有记忆，进入若干地方
   会话 = (行动者, 地方) 的交点，可丢弃
   工作区 = (一件事) 的附属物，可重建
```

## 4. 从现状到目标的最小路径

每一步单独可上、单独可验证，且不依赖后面的步骤。

**第一步：止血（各对应一个已发生的事故，建议先做）**

1. **释放算力从「归档」解绑**。今天 `_release_topic_compute` 挂在采纳／归档上，而它做三件事：
   删容器（会自动重建，无所谓）、释放设备屏、**销毁计费云 VM**。最后一个的注释写着
   *"archive is its only reclamation lifecycle"*——归档是计费机器**唯一**的回收路径。
   归档一旦改成人为，机器回收就交给了人的记性。容器已经有闲置回收（8 小时／每小时扫），
   把云 VM 也纳入按闲置回收。
2. **「已交付」冻结点**。卡被采纳时自动冻结工作面，不要等人归档。否则合并后还能在已合掉的
   分支上继续改、继续递卡，开出来的 PR 大概率是空的——PR #257 已经这样空合并过一次。
3. **改 `cheese accept-request` 的帮助文本**，删掉「递卡后平台会自动跑一遍检查」那段。
   平台闸门已经退休（`review/gate.py` 首行写着 NO LONGER DISPATCHED），这段话正在让每个
   芝士以为有兜底而不自己跑测试。

**第二步：把「结束」和「归档」拆成两件事**

4. 给话题加 `delivered_at`：卡 accepted 时自动写，负责冻结工作面 + 触发算力回收 + 进度定格；
   `archived_at` 保持人为，只管列表可见性。
   （另一种做法是话题状态完全由卡推导，但侧栏列表现在只查 topics 表，推导要 join，更复杂。）
5. `revoke` 的文案要说清：撤销的是**这次验收记录**，不是**这次合并**——PR 已经在 main 上了，
   revoke 在 git 层面什么都没撤销。
6. 给「已交付但未归档」一个默认收敛：列表默认折叠，或交付 N 天后自动归档。
   否则没人会去归档，列表只会堆积。

**第三步：agent 身份从话题解绑**（这一步最大，建议单独立 issue）

7. `resolve_agent_handle` 的 fallback 从 `topic_agent_handle(topic_id)` 改成「项目的默认芝士」；
   建房间时不再自动造新身份，而是把项目的芝士加进 roster。
8. 已有的 per-topic 池要有迁移策略：或者归到项目芝士名下，或者保留为只读历史。
   **数量级要先量**（有多少个 `cheese-*` handle、各自多少条记忆），再决定合并还是弃。
9. 顺带解决「跨芝士的运维经验没有落点」：像「沙箱里跑 jj 会把全项目打停」这种经验，
   既不属于任何房间、又太琐碎不值得开 PR 改 CLAUDE.md，今天只留在踩到它的那个分身脑子里。
   身份少了之后，这个问题自然缓解一大半。

**第四步：task 卡片化**（需要前后端一起，#184 已列为待办）

10. `cheese split` 时往父房间写一条 block，让「派出去」成为时间线上的一个事件。
    这是「task 是房间里的一张卡」的**数据前提**，不是渲染问题。
11. `split_to_subtopic` 增加 kind 检查：task 下面不许再 split，直接报错。
    同步改 `cheese split` 帮助里「没有深度/频率上限」那句。

**第五步：session 卫生**

12. 主动轮换（按轮数／体积），别等撑爆。
13. 一个房间容纳多个芝士时，session 的 key 从 `topic_id` 改成 `(topic_id, agent_handle)`。
    这一步依赖第三步。

## 5. 这套设计的已知代价

诚实列出来，免得以后被当成没想到：

- **芝士跨房间之后，「它在别处说过的话」它不知道**——只有记忆和文档能带过去，带不全。
  buzz 也带不全（它连同一房间内的会话连续都不保证）。这是要接受的。
- **少数长期芝士会让记忆池变大**，撞注入预算（50 条 ＋ 20000 字符）的概率上升。
  真正的解法不是提高上限，而是学 buzz 的分层：**一条 core（我是谁／我的规则）每轮在场，
  其余按需检索**——我们现在是把 50 条平铺事实全量注入（本项目 59 条约 13k 字符）。
  这件事和 issue #187（记忆系统三层分工）是同一个问题，**建议合并讨论，不要单独开**。
- **「归档」变成纯人为之后，没人会做**。所以第二步的第 6 条不是可选项。
- **agent 解绑是一次身份迁移**，涉及历史消息的作者归属和记忆池归属，要么迁要么留成只读，
  没有第三条路。这是本方案里唯一一处真正的一次性成本。

## 6. 需要拍板的三件事

1. **云 VM 的回收策略**：保留到人归档 / 授权额度内芝士自动续租 / 闲置 N 小时释放并提前说一声。
   （我倾向后两者组合：授权一次给一段额度——「谁付钱」人只需决定一次，「现在要不要一台机器」不需要人参与。）
2. **agent 身份解绑做不做、什么时候做**。不做也能过，但「同一个芝士」这句话就一直只是说法。
3. **task 卡片化的顺序**：先写 block（数据层，小）还是等前端一起（完整，大）。
