# room / task / agent / session：语义、管理与关系

> 本话题的主交付。@fulu 2026-08-17 要求：把四个词的语义定清楚，说明同类之间怎么管理、
> 跨类之间是什么关系。
>
> 每条「现状」都读过代码；核实过程和证据在 <&docs/topics/room与task设计与审批流程.md>。
> 凡是**建议**，都标了它解决的是哪个已经发生过的问题——没有为了整齐而整齐的改动。
>
> **本方案里的绝大部分建议后来都落地了**（一件活换成房间里的一条支线、agent 从话题解绑、
> 记忆分 core 层、母子传话通道、容器按房间分配、子话题的提交并进房间的 PR）。
> 「现状」各节已在 2026-08-23 对着 main（`3e945077c`）重新核过并改写成落地后的样子；
> 保留下来的是**为什么这么选**的论证，那部分没有过期。

## 0. 一句话总纲

> **房间是地方，一件事是交付，芝士是行动者，会话是它此刻的上下文。**
> 前三个是产品概念，第四个不是——用户永远不该看见「会话」这个词。

四者的寿命必须各自独立，这是 issue #184 定下的原则。#184 把「房间」从「一件事」里解放了，
但**没有解放另外两个**：芝士的身份仍然由话题 id 派生，会话仍然与话题一对一。
本方案要补的就是这后半段。

## 0.1 修订（2026-08-17，@fulu 拍板）

三条决定，会推翻下面一部分内容，以这里为准：

1. **采纳不回收容器。** 理由：一个话题往往是连续的。这条有实证支持——容器重建会擦掉容器内现装的
   工具链（`jj`、`procps`、git identity 都要重装，CLAUDE.md 的 Testing 一节记着这件事），
   所以「重建」不是零成本。落地后的形状是：**采纳不再碰容器**，容器和设备屏各归自己的
   闲置回收管（`scheduler.reap_idle_containers` / `reap_idle_device_screens`）——
   「还有没有人在用」是个关于活跃度的问题，跟某条分支落没落地无关。
   > 唯一的例外仍然单独处理：**计费云 VM**。它是唯一按小时烧钱、又唯一没有 reaper 的东西，
   > 所以释放仍然挂在采纳和归档上（`TopicService._release_cloud_machine`，#442 decision 3），
   > 而且不是 best-effort——MicroCloud 没接受删除，采纳就不许报成功。
   > **回收策略本身至今没定**，见 §6。
2. **agent 和 session 这一轮先不管。** ——**这条后来被推翻并做掉了**：agent 身份已经从话题解绑
   （`agent_types` 出厂设置 + `agent_instances` 项目内的一个身份和它的记忆池），
   §1.3 当时那个「记忆的真实粒度是话题不是芝士」的结论**不再成立**。
3. **本轮要落实的是另外四件事**，见 §8。

## 1. 四个词分别是什么

### 1.1 room（房间）

**是什么**：一个持续存在的协作场所。它有三样东西——成员名册、消息时间线、一份实况文档。
**它自己不做事**，它是事情发生的地方。

**寿命**：永久。人可以归档它，但那纯粹是「从列表里收起来」，不是「它结束了」。

**现状**：`TopicKind.root`（项目本体）和 `TopicKind.topic`（二级房间）——枚举里只剩这两个值在用。
根的孩子是房间，房间之下不能再建房间（`_require_room` 直接拒）。

**当初记的两处「偏差」现在都不是偏差了**：房间**有**分支和工作区、房间**能**递验收卡，
这两件事后来成了设计本身——**开 PR 的就是房间**（一个房间一条分支一个 PR），
一条支线的提交在它的结论被采信时折进房间分支。当时之所以觉得别扭，是因为那时假定
「交付」归一件活；换成 B 方案（见 <&docs/topics/task设计现状.md>）之后，这两条各归其位。

### 1.2 task（一件事）

**是什么**：一次交付。它有一个分支、一张验收卡、一条进度。

**寿命**：**与卡共存**（@fulu 2026-08-17 定）。卡结束＝这件事结束。

> ⚠️ 必须精确到「卡**被采纳**」。一个 task 生命周期里可以有多张卡：递卡 → 被驳回 → 改完再递
> （`reject()` 之后话题保持 active，而 `create_card` 的阻塞集**故意不含** `gate_failed`）。
> 所以 `rejected` / `revoked` / `void` 都是「卡结束」，但都**不**结束 task。
> 这条不写死，语义当场就漏。

**结束 ≠ 归档**：结束是自动的（`status=closed`），归档是人为的（整理列表）。这条已经落地。

**现状**：一件事是 `tasks` 表的一行 ＋ `blocks.task_id` 这个线索键
（<&backend/app/domain/room_task/models.py>）——**不再是一行 `topics`**。
它有唯一的主（`owner_handle`）、自己的对话、自己的分支和工作区、自己的交付戳；
它没有名册、没有未读游标、没有侧栏里的一行——这正是这次改造的全部收益，
一件活不再需要付「一个房间」的成本。

**仍然缺的那一条边**：`cheese split` 不往房间主线写任何 block（`SplitIn` 只有
title / created_by / brief），所以「一件活被派出去」在房间时间线上没有留下任何数据，
前端只能靠支线的 `room_id + created_at` **读时派生**一行「已派出」标记。
#184 说的「它应该是话题时间线里的一张卡片」，缺的就是这条边，不是渲染（详见 §14）。

### 1.3 agent（芝士 / 分身）

**是什么**：一个有身份的行动者。身份 = 一个 handle + 一条 `AgentBinding` 行
（「是不是 agent」是派生的，不是 user 表上的字段）。

**寿命**：应当**长期存在，跨房间**。它是唯一能跨房间流动的东西——这是 #184 自己的论证：
「聊到哪了」天生跨不了房间，所以「同一个芝士」只能靠「记住了什么」成立。

**现状**：身份已经从话题解绑，分成两张表：

- **`agent_types`**＝出厂设置，不属于任何项目：它是谁（`body`，系统提示）、能碰什么
  （`skills` / `mcp_servers`）、怎么跑（`model` / `effort` / `harness`）。
  预设以文件形式发（`library.py`），表里放人自己定义的，同名的行覆盖预设。
- **`agent_instances`**＝这个类型**在这个项目里**干活的那一个，**记忆挂在它上面**
  （`agent_project` scope，`{project}:{handle}`）。三者里只有它的寿命和记忆匹配：
  类型被多个不该互看笔记的项目共用，会话每换个地方就死一次。

**它刻意不是一行 user**：署名仍然归每个地点的分身身份（`cheese-<话题 hex>`），
回答的是「这个动作是谁做的」；`agent_instances` 回答的是「这份记忆是谁的」。
把两者合并会重新把记忆绑回话题——正是这次改动要拆掉的东西。

**所以当初那条核实结论（「记忆的真实粒度是话题，不是芝士」）已经作废。**
它当时是对的，而且正是它推动了这次解绑：#184 修的是「分不出是哪个芝士」，修对了，
但它把身份绑在了话题上，于是身份的寿命又一次等于话题的寿命——正是它自己反对的那个错误的另一种形态。
现在同一个芝士在五个房间学到的东西互相看得见，#184 那句「『同一个芝士』靠记忆跨房间成立」才真的成立。

### 1.4 session（会话）

**是什么**：一段对话上下文。**它是实现细节，不是产品概念。**

**寿命**：可丢弃、可重建，随时可以从头开始。任何依赖「会话还在」的设计都是错的。

**现状**：`agent_sessions`，一个 (地方, 芝士) 一行，靠 `--resume` 续；容器被回收不影响它
（transcript 挂在宿主的 `/home/node/.claude`，工作区是宿主的 jj workspace）。
容器现在按**房间**分配，一个容器里跑多个 tmux session，每个 session 靠
`tmux new-session -e` 拿到自己的 `CHEESE_TOPIC` / `CHEESE_TOKEN`。
**没有主动轮换或压缩机制**——撑爆了靠 Claude Code 自己处理，平台不管。

## 2. 同类之间怎么管理

### 2.1 room 之间：扁平集合，不要层级

- **一层就够**：所有房间都挂在项目本体下，互为兄弟。房间之间**没有父子**。
- **管理动作**：建、归档／取消归档（人为，纯整理）、成员进出、`@标题` 交叉引用。
- **不需要**：房间的目录树、房间的依赖关系。房间多了靠搜索和未读，不靠层级。
- **现状缺口**：房间之间没有「这两个房间在做同一件事」的检测。目前唯一的撞车检测在 task 层，
  且只覆盖一种情况（两张未决卡各带一个 alembic 迁移就提醒，`_warn_about_a_second_pending_migration`）。

### 2.2 task 之间：只管两件事——并行度和撞车

- 一个房间里可以**同时跑多个 task**。git 层面它们不再各自从 main 切：每条支线的工作区从
  **它所在房间的分支**长出来（`_ensure_worktree` 的 `_fork_point`），结论被采信时折回房间分支
  （`fold_into_room`）——**一个房间一条分支一个 PR**。
- **一个 task 同时只有一张活卡**（`create_card` 的阻塞集），这是对的，保持。
- **task 不能嵌套**——现在是机制，不是约定：从一条支线里再拆，拿到的是同一个房间里的另一条支线，
  不是它的子节点；房间之下再建房间被 `_require_room` 直接拒。
- **不需要**：task 之间的依赖图。代码里**故意没有**——空的关联表和活的关联表，
  对下一个读代码的人长得一模一样。@fulu 说的「开子话题要慎重」就是这个意思——
  能不拆就不拆，拆出来的每一件都得是独立可交付的。

**判据（建议写进规则，替换「任务大小」）**：一件事该独立成 task，还是交给容器内的 subagent？
问一句：**它的产出会不会落进房间里所有人都能看见的公共记录？** 会 → task；不会 → subagent。
理由是 subagent 的真实成本：它的产出只在容器 transcript 里，房间里的人看不见，跑偏了没人能
中途纠正、挂了没人知道。所以「小任务给 subagent」隐含一个赌注——这件事不会失败到需要人介入；
而 subagent 最常见的失败恰恰是**自信地返回一个错结论**。

当初还记了一条硬判据：「依赖父话题尚未合并的改动的活，绝对不能拆」——**它已经作废**，
因为支线的工作区不再从 main 新建，而是从房间的分支长出来，它看得见房间分支上的改动。

### 2.3 agent 之间：已经从「完全没有管理」变成一个池

当初的现状是：每个话题自动生一个 agent 身份，**永不复用、永不合并、永不消亡**，
所以「agent 之间的关系」这个问题没有答案——它们之间没有任何关系。

**这条建议落地了**：身份从话题解绑，拆成「类型（出厂设置，跨项目共享）＋ 实例（项目内，带记忆池）」
两层（§1.3）。话题不指向实例：实例作为成员坐在话题名册上（和人同一张名册），
新话题建出来时坐着项目当时的默认实例，再请别的实例进来是往名册上加一行。

论证仍然值得留着：这正是 buzz 的选择，也是 places-and-actors 说「我们缺 actor 这一半」的具体所指——
在 buzz 里 `agents: Vec<Option<OwnedAgent>>` 是**进程槽**，派活时找不到亲和的槽就用任何空闲槽，
身份（密钥）和进程完全解耦。**同一个 agent ＝ 同一把密钥，不是同一个进程。**

**代价要说清楚**：一旦一个芝士进多个房间，「它在 A 房间说的话，在 B 房间不知道」这件事会更显眼
（今天不显眼，因为每个房间是不同的分身，本来就该不知道）。这个落差只能靠记忆和文档补，
补不满——buzz 也补不满，它连同一个房间内的会话连续都不保证。**这是要接受的，不是要修的。**

### 2.4 session 之间：可丢弃，不承担连续性

- **一个 (地方, 芝士) 对一个 session**。这正好是 buzz 的 `channel_id → session_id` 映射。
- **UI 永不暴露**。用户看到的是房间和消息，不是会话。
- **建议补主动轮换**：按轮数或体积主动重开，而不是等撑爆（buzz 有 `turn_counts` +
  proactive rotation，我们没有）。撑爆之后再处理，代价永远比主动轮换高。
- 轮换后靠什么接上？**记忆 + 房间的实况文档**。buzz 在 session 出生时各注入一次
  （`core_sections` + `canvas_sections`），我们每轮都重新注入，效果更强、成本更高。

## 3. 跨类关系

| 关系 | 应该是 | 现状 | 差在哪 |
|---|---|---|---|
| room × task | 1 : N。房间是容器，task 结束不影响房间；**task 不能跨房间** | 1 : N ✅ | 只剩一条：派出去在房间时间线上**没有数据**，标记是读时派生的（§14） |
| room × agent | N : M。芝士被加进房间 | N : M ✅ | — |
| room × session | 房间自己不干活，但房间里的芝士要说话 ⇒ 每个 (room, agent) 一个 session | N : M（`agent_sessions`）✅ | — |
| task × agent | N : 1。一件事由一个芝士负责（谁做的） | N : 1 ✅ | 默认继承房间的那个，可在拆的时候指定别的 |
| task × session | 干活的上下文，task 结束即可丢 | 1 : 1 ✅ | task 收起（`closed`）不冻结，对话照常能接着说 |
| agent × session | 1 : N。芝士在每个它所在的地方各有一份上下文 | 1 : N ✅ | — |

**当初那句「话题 = 身份 = 会话 = 工作区四位一体」已经拆完了**：#184 拆出「房间」，
这一轮拆出「身份」（`agent_instances`）和「一件活」（`tasks`）。剩下的唯一缺口是最上面那一行。

形状是两个轴：

```
地方（房间 / 房间里的一件事）   ← 人和芝士在这里说话、交付
行动者（芝士）                  ← 有身份、有记忆，进入若干地方
   会话 = (行动者, 地方) 的交点，可丢弃
   工作区 = (一件事) 的附属物，可重建
```

## 4. 从现状到目标的最小路径：走完了哪些

当初列的五步十三条，只剩两条没做。已经做掉的不再展开写「怎么做」——那会读起来像还没做：

| 当初的步骤 | 现在 |
|---|---|
| 释放算力从归档解绑 | ✅ 容器和设备屏各归自己的闲置回收；**云 VM 是唯一例外**，仍然只有采纳／归档能回收它 |
| 「已交付」冻结点 | ✅ 采纳盖 `accepted_by`/`accepted_at`，防空 PR 改由「已有一张 accepted 卡」在 `create_card` 里挡 |
| 「结束」和「归档」拆开 | ✅ 支线的结束是 `status=closed`（收起不冻结）；归档只有人能做 |
| `revoke` 的文案 | ✅ 它不再动归档状态，只清交付戳 |
| agent 身份从话题解绑 | ✅ `agent_types` + `agent_instances`（§1.3、§12） |
| 一个房间多个芝士时 session 换 key | ✅ `agent_sessions` 就是按 (地方, 芝士) 建的 |
| task 不许再嵌套 | ✅ 是机制了（`_require_room`），不再靠 docstring |

**还没做的两条：**

1. **`cheese split` 时往房间主线写一条 block**，让「派出去」成为时间线上的一个事件。
   这是「一件活是房间里的一张卡」的**数据前提**，不是渲染问题（§14）。
2. **「已交付但没人去归档」的默认收敛**：列表默认折叠已交付的，或交付 N 天后自动归档。
   否则没人会去归档，列表只会堆积。

**还没做、但当初就说了要单独想的一条：** session 的主动轮换（按轮数／体积），别等撑爆。

**顺带一条帮助文本的债**（不在本方案范围，但它每天在误导人）：
`cheese accept-request` 的帮助还写着「递卡后平台会自动跑一遍检查，红了卡片会被打回」，
而机器闸门早就退役了（`review/gate.py` 第一行就说明了这件事，`run_check_command` 已删）。
这段话正在让每个芝士以为有兜底而不自己跑测试。

## 5. 这套设计的已知代价

诚实列出来，免得以后被当成没想到：

- **芝士跨房间之后，「它在别处说过的话」它不知道**——只有记忆和文档能带过去，带不全。
  buzz 也带不全（它连同一房间内的会话连续都不保证）。这是要接受的。
- **少数长期芝士会让记忆池变大**，撞注入预算的概率上升。真正的解法不是提高上限，
  而是学 buzz 的分层：**一条 core（我是谁／我的规则）每轮在场，其余按需检索**——
  这一条已经做了：`core` 4000 字符每轮在场，`fact` 20000 字符只花在这一轮用得上的事实上，
  两道上限都不静默（<&backend/app/domain/memory/store.py>）。
- **「归档」变成纯人为之后，没人会做**。这条**至今没有默认收敛**，仍然是个真实的代价。
- **agent 解绑是一次身份迁移**，涉及历史消息的作者归属和记忆池归属。落地时选的是把两者分开：
  署名留在每个地点的分身身份上，记忆挂到 `agent_instances`，所以历史消息的作者归属根本不用迁。

## 6. 需要拍板的：只剩一件

**云 VM 的回收策略。** 它是唯一按小时烧钱、又唯一没有 reaper 的东西，
今天的回收路径只有「人去归档」和「采纳时释放」两条。三个选项：
保留到人归档 / 授权额度内芝士自动续租 / 闲置 N 小时释放并提前在房间说一声。
（我倾向后两者组合：授权一次给**一段额度**——「谁付钱」人只需决定一次，
「现在要不要一台机器」不需要人参与。）

**代价要一起说**：现在刚交付完的云话题手上没有 VM 了，而重新开机要一个有权限的人来调
（`ensure_topic_machine` 要求有授权的人类调用者），所以它的下一轮需要人先说句话。

另外两件当初列的已经不用拍了：8 小时那个 reaper 保持原样并各自管好容器和设备屏；
subagent 的可见性两档**都做了**——每轮的改动汇总会落进房间（§8.4），
房间时间线上也有「已派出」标记（只是还不是一张卡，见 §14）。

## 8. 本轮要落实的四件事

### 8.1 一个意外干净的落点（已落地）

前三条指令（PR 不是话题终态 / 机器不回收 / 归档人为）**全部落在同一处代码**：
`AcceptService._finish_pr_accept`（<&backend/app/domain/review/services.py>）。它当时在 PR 合并后
连做三件事——盖交付戳、释放算力、归档话题——后两件被拆掉了：

- **归档那行删了**：合并只说明「这一份改动进了 main」，话题继续活着。
- **释放算力拆成了两半**：容器和设备屏各归自己的闲置回收；计费云 VM 留在这里，
  因为它是唯一没有 reaper 的，丢在这儿不管就是每个合并过的话题变成一笔一直烧钱的泄漏。

跟着改的两处也做了：本地合并那条路的收尾不再写 archived；`revoke()` 不再清 `archived_at`
（它现在只清交付戳）。

### 8.2 「PR 不是话题终态」的准确语义

合并只说明「这一份改动进了 main」。它**不**说明部署了、生效了、有人验过了。
所以合并之后话题继续活着，接着做的事在同一个房间里继续。

要注意这与 issue #206 的边界：#206 拍板「任务的终态是 merged，部署不是平台语义」，
理由是部署是每个项目自己的 ops 概念，平台定义不了（等部署的卡曾经死等过永远不会出现的
workflow run）。这一条**不矛盾**——#206 说的是「平台不去判断部署成功」，
现在说的是「**话题**不因为合并而结束」。两者可以同时成立：
卡到 `accepted` 就完了（#206 保持），话题保持 active（本条改动）。
部署的可见性仍然走 webhook 原语（`POST /webhooks/{topic_id}`），由流水线自己回吐进房间。

### 8.3 房间 ↔ 支线的通讯：**已经通了**

**子 → 母**：`cheese conclude` 开一张结论卡（`ConclusionCard`，接收方是**话题**而不是人），
父话题那一轮结束时**默认采信**（另有 30 分钟绝对超时），
父话题可以 `need-evidence` 打回一次或 `escalate` 转人。这套一直是完整的。

**母 → 子**：当初是断的——评论端点里 summon 的条件是 `if not actor.is_agent`（只有人类评论
才唤醒对方），而且更上面还有一道 403（per-turn token 带着自己的话题 claim，指向别的话题直接拒）。
现在有了一条**显式的、只开父子这一条边**的通道：`cheese tell` → `POST /topics/{id}/tell`
（<&backend/app/api/routes/topics.py>、<&backend/app/domain/topic/relay.py>），写 block **并唤醒**对方。

它的形状值得记住，因为这是「跨话题写」唯一正确的做法：
**URL 里的 id 是发信人**（这一轮是谁在说话，也正是 per-turn token 被 scope 到的东西），
**收信人在 body 里**，由服务层校验它确实在发信人够得着的范围内（自己的房间，或自己派出的支线）。
「一个 id 说的是谁在说话，绝不是这是哪个资源」——放宽 token 的 topic scope 才是错的那条路，
那等于放弃话题级隔离。

**还没补上的**：退回验收卡（`reject`）仍然不通知任何人——它只 `notes.record` 一行，
既不发消息也不 summon，跟 CI 失败会 summon 的行为不一致。

### 8.4 commit 可视化

现状：房间时间线上**已经有**「写文件 / 改文件 / 执行命令」这类现场事件（工具调用流式落 block），
文件面板能看 `topic_diff` 和文件列表。**缺的是「提交」这一层**：这个话题产生了哪几个 commit、
每个 commit 动了什么、现在分支上是什么。

要注意一个前提：平台的快照是 jj 自动做的（每轮把工作区折成提交），所以「commit」在这里
不是人工的动作，而是**平台的记账**。所以可视化的对象应该是：

- **分支现在的状态**：相对 `main` 领先几个提交、动了哪些文件（`topic_diff` 已经能给）；
- **每一轮产生的提交** —— **已落地**：一轮结束时在房间里落一条
  「这一轮改了 N 个文件（+X −Y）」的事件（`_persist_change_summary`，
  <&backend/app/domain/agent/chat.py>），点开是 diff。这条比「commit 列表」对人更有用——
  **人关心的是「这一轮做了什么」**，而不是 jj 的提交拓扑。
- **PR 上的提交**：卡等采纳期间，PR 分支的 head 会随每次重推移动
  （`pr_head_sha`），这个已经在卡上了，只是没渲染成「提交流」。

### 8.5 支线往房间的 PR 上提交（已落地）

当初的模型是「一个话题 = 一条从 main 切出来的分支」，母子在 git 层面是兄弟、各自合回 main。
现在不是了：

- 一条支线的工作区从**它所在房间的分支**长出来（`_ensure_worktree` 的 `_fork_point`）；
- 它的结论被采信时，分支被折进房间分支（`fold_into_room`，
  <&backend/app/domain/conclusion/services.py>）；
- 房间递卡开 PR，一条支线不单独开 PR。**一个房间一条分支一个 PR。**

选 B 而不是「每件活一个 PR」的理由是 CI：本项目队列约 1.7 小时，一件活一个 PR 会把 PR 数量
按活翻上去。

工作区仍然各自独立（places-and-actors 明说「共享 worktree 保证撞车」），
所以代价照旧要认：**多条支线往一条分支合，冲突提前到房间分支上**。
三种情况不会合、但都会在房间里说一句、不会默默算了：房间正在等 CI（现在合会把 CI 打回起点）、
房间工作区有人在改、两条活改到同一处。

顺带说明一件容易搞混的事：`topics.branch_name` 这一列**没有任何代码写过**，每一行都是 NULL——
分支名是派生的（`branch_for_place`）。`tasks.branch_name` 才是真写的那个。

## 9. 要不要把 subagent 改造成子话题（共用一个 room）

**方向对，但「被看见」和「独立成一个话题」是两件事，混在一起会付不必要的代价。**

先说对的部分：subagent 的真实问题**就是**看不见——它的产出只在容器的 transcript 里，
房间里的人看不见，它跑偏了没人能中途纠正、它挂了没人知道。用「进房间」来解决是正解，
而且 places-and-actors 早就写了那条划界原则：**产出会不会落进房间里所有人都能看见的公共记录？**
会 → 平台概念；不会 → 实现细节。把 subagent 拉进房间，就是让它跨过这条线。

「共用一个 room」这个提法也是对的，而且正是那份设计文档的原话：
**一个房间里的多个行动者共享「对话」，不共享「工作区」**——共享 worktree 保证撞车。

但有三条硬约束：

**① 可见性这一档做完了，而且它确实很便宜。** `Agent`/`Task` 工具调用会在房间时间线上落一条
现场事件（`_TOOL_VERB` 里 `"Task": "派分身去查"`，参数取 `description`），
**它查完之后的结论摘要也会落一条**（`_subagent_event_text`：「分身查完了：<问题>」＋摘要，
<&backend/app/domain/agent/chat.py>）。刻意只放摘要——一个 subagent 能返回几千字，
整段贴进房间等于把时间线埋掉。成本是零个容器、零个工作区、零延迟。

**② 独立成一条支线仍然贵，但比当初便宜了。** 一条支线 = 一个 jj workspace + 一个冷启动；
容器已经不再是每条支线一个了（按**房间**分配，同房间的活共用一个）。
但内存这条约束还在：一个容器 `--memory 2g --cpus 2` 现在要服务整个房间，
而本项目 `pnpm run build` 单独就能吃满 2GB（实测 OOM）。
一个「读三个文件回答一个问题」的活，拆成支线做，开销仍然是用 subagent 做的几十倍。

**③ 呈现层那条路仍然没走完。** 数据层是独立的（各自 session、各自工作区），
**呈现层共用房间的时间线**——派出去的活在房间里是一张卡，点开是它自己的对话。
这恰好就是 #184 那件没做完的事（「按设计它应该是话题时间线里的一张卡片」），
也就是那条缺失的边：`cheese split` 至今不往房间主线写任何 block。

### 结论：分三档，不要一刀切

| 这件事 | 放在哪 | 代价 |
|---|---|---|
| 纯机械（读文件、grep、格式转换、查一个事实） | subagent，**但结论要回吐房间一条 block** | 几乎为零 |
| 有产出、要被别人看见、可能失败到需要人介入 | 房间时间线上的一张**卡**（数据上是独立话题，呈现上在母房间） | 一个工作区 + 一个容器 |
| 需要多个行动者在同一个房间里并肩对话 | **暂缓**（要动 agent/session 的 key，本轮搁置） | 大 |

判据从「任务大小」换成一句可判定的话：**它的结论要不要被别人看见、要不要能被中途纠正？**
要 → 卡；不要 → subagent + 结论回吐。

### 9.1 母子共用一个容器（@fulu 2026-08-17 提议）：**已落地**

下面这一节是当初的可行性分析，四项该改的都改完了：容器按房间命名
（`tmux_container_name(room_for_topic(topic_id))`）、工作目录用树里的真实路径、
`CHEESE_TOPIC`/`CHEESE_TOKEN` 移到每个 tmux session 的环境（`tmux new-session -e`）、
session 目录挂上一层。**顺带那个已知故障也修掉了**：签名密钥不再是每个后端进程一个随机值
（`Settings.sandbox_signing_secret`），所以后端重启不再让所有存量容器同时变聋；
`_hook_token_dead` 留成兜底，而且现在恢复只赔掉一个 session 的对话连续性，不用重建容器。


**先说最大的意外：文件可见性早就不是障碍了。** `sandbox_project_mounts`
（<&backend/app/domain/workspace/service.py>）的 Isolation note 原话：

> every topic sandbox of a project **sees (and can write) its sibling topics' worktrees**.
> That is not a new trust boundary — the same containers already share the project's writable
> `.jj`/`.git` stores, so **same-project topics were never isolated from each other**.

因为 hardlink 不能跨 bind mount（jj 的 store 用硬链接），所以它是**一个 mount 挂整棵**
`.worktrees/<project_id>/` 树。也就是说：**子话题的工作区此刻就已经在母话题的容器里**，
共用容器不需要新开任何访问权限，同项目话题之间本来就没有隔离。

**真正 per-topic、必须改的只有四样**：

| 现在按话题定死的东西 | 改成 |
|---|---|
| 容器名 `container_name(topic_id)` | 按**房间** id 命名 |
| 工作目录（`/work` 这个固定 remap） | 树里的真实路径（`SANDBOX_TOPICS_ROOT/topic_<hex>`，已经在容器里） |
| **容器 env 里烤着的 `CHEESE_TOPIC` + `CHEESE_TOKEN`** | 移到**每个 tmux session 的环境**（tmux 原生支持 per-session env） |
| `/home/node/.claude`（session 目录挂载） | 挂上一层，容纳同房间多个话题 |

第三行是主要工作量。

**最重要的判断：共用容器不是省钱的优化，而是「采纳不回收容器」这条决定的必要前提。**

- 每话题一个容器 ⇒ 容器数跟着话题数走，× 2GB，**先崩的是内存**；
- 每房间一个容器 ⇒ 容器数跟着**房间数**走，而房间数是人的数量级。

这两条决定是配套的，应该一起做，不该分开评估。

**要接受的三个代价**：

1. **资源共享**：一个容器 `--memory 2g --cpus 2` 现在要服务整个房间。本项目 `pnpm run build`
   单独就能吃满 2GB（实测 OOM）。所以**共用的同时必须提配额**——建议按房间给 4–6GB / 4 CPU，
   否则「并行拆三个子话题」会变成互相挤。
2. **故障域合并**：一条支线把容器 OOM 掉，同房间其他支线一起死。
3. **jj 撞锁概率上升**：共享 store 本来就有，但同容器内并发更容易撞。

**分配规则**：容器的身份是**房间 id**，房间和它派出的所有支线共用一个。
规则明确，不需要「看情况共用」。后续如果峰值确实挤，可以再加一条
「跑全量测试/构建这种重活时临时独占一个容器」——但那是优化，不是第一版。

## 12. agent 类型：buzz 怎么做，我们已经有什么（@fulu 2026-08-17 提的方向）

读的是 `crates/buzz-persona/PERSONA_PACK_SPEC.md`（1153 行）＋ `persona.rs` / `manifest.rs`。

### 12.1 buzz 的做法

一个 **Persona Pack** 是可分发的一整包（zip 或 git repo），是 Open Plugin Spec 的超集。
一个 pack 里可以有多个 agent，每个 agent 一个 `*.persona.md` —— **YAML frontmatter 定义它是谁、
怎么跑，markdown 正文就是它的系统提示**：

```yaml
name: "lep"                  # 机器名，pack 内唯一
display_name: "Lep 🍀"       # UI 上显示的名字
description: "Security-focused code reviewer"
skills: ["./skills/security-review/"]      # 只给这个 agent 的技能
mcp_servers: [{name: semgrep, command: …}] # per-agent 工具
subscribe: ["#security-reviews"]           # 监听哪些频道
triggers: {mentions: true, keywords: [...]}# 什么情况下响应
model: "anthropic:claude-sonnet-4-…"       # 用哪个模型
temperature: 0.3
max_context_tokens: 128000
hooks: {on_start: …, on_stop: …}
```

两个机制值得单独记：

- **继承**：`plugin.json` 里的 `defaults` 是 pack 级默认，persona 没写的字段从那里解析。
  例子里四个 agent 默认 Sonnet，只有一个覆写成 Opus。
- **两层 prompt 的纪律**（这一条比 persona 格式本身更值钱）：每条消息按固定顺序拼
  `[Base]` → `[System]` → 团队说明 → `[Context]` → 会话历史 → 触发事件。
  `[Base]` 是**平台注入、每个 agent 完全一样**（平台身份、工具参考、工作区布局、怎么轮询消息），
  **pack 作者不许写也不许配**；`[System]` 才是 persona 自己的。
  规范里明文警告：**不要在 persona 里重复 base 的内容，否则用户每条消息会看到两遍**，
  并逐条列出「不要再解释」的四类内容。

### 12.2 Project agent configuration

`agent_instances.configuration` stores the role instructions, model, harness, effort and existing tool settings for one project agent. Memory remains keyed by its project and stable handle. A room's `compute_profile` selects where the work runs; the agent's model selects what it requests there.

Built-in presets in `agent_type/library.py` initialize new agents. The saved `type_name` records which preset was used at creation and is not consulted when the agent runs. Users edit individual agents; there is no mutable shared role catalog or project model default. See spec §8.2 for model validation, turn boundaries and migration behavior.

### 12.3 建议：抄纪律，不抄格式

**值得抄的：**

1. **两层 prompt 的纪律**（最值钱）。明确划出「平台层」和「角色层」，并规定角色层不许重复平台层。
   我们现在没有这条约定——阶段说明、CLI 规则、记忆、成员表、话题表、活文档全都每轮拼进去，
   没人说得清哪一层归谁、谁该为体积负责。
2. **把「怎么跑」并进角色定义**：角色定义上要有 model / effort / 工具白名单。
   这直接就是 @fulu 说的「名称、harness 工程、模型、effort」。（见 §12.2 的实例配置。）
3. **配置与记忆分离**：角色是出厂设置，core 记忆是它自己长出来的那部分。
   这和 §6.2 ① 那条「我们缺 core 这一层」是同一件事，应该一起做（并入 issue #187）。

**不建议抄的：**

- **pack 的打包分发**（zip / git repo / 校验和 / OPS 兼容）：那是为第三方作者生态准备的，
  我们现在没有第三方作者，先做数据库里的角色定义就够。
- **MCP server 配置**：我们的工具是平台内置的（cheese CLI ＋ Claude Code 内置），没有 MCP 生态需求。
- **triggers / subscribe**：我们用 @提及 ＋ summon，语义已经清楚，不需要再加一套触发规则。

### 12.4 @fulu 的 agent 池构想（2026-08-17）：两条对、一条要改

构想原文：①有一个 agent 池，可以自己创建 agent，每个 agent 的 harness 工程 / skill / mcp / memory
分别管理；②创建话题时弹窗选用哪个 agent；③每个话题是一个独立 session，但 session 内它可以管理
自己的记忆，形成良性循环。

**①② 成立并已落地，而且和这份文档 §2.3 从代码侧得出的结论撞上了。**
当时的核实结论是：agent handle 是 `cheese-<话题 id 前 12 位 hex>`，**纯函数派生、每个话题
自动生一个**，于是记忆池的真实粒度是**话题**而不是芝士。
「从池里选一个 agent」这个动作，正是把身份从话题解绑 —— 产品侧和代码侧想到的是同一件事。
现在两张表都在（§12.2），选的那一个坐在话题名册上——roster 本来就支持多个
agent 座位（`agent_handles()` 返回列表），话题自己不指向任何一个。

**③ 前半句对（每个话题一个独立 session），后半句必须改：记忆要跟 agent 走，不能跟 session 走。**

buzz 就是这么做的，而且证据在加密方式里：engram 事件由 **agent 自己的密钥签名**，
用 `conversation_key(agent_secret, owner_pubkey)` 加密，`d_tag = HMAC(K_c, slug)`
—— **整条链里没有 channel**。同一个 agent 在所有频道共享同一份记忆。
`SessionState.core_sections`（`channel_id → 渲染好的 core`）只是**渲染缓存**
（注释：session 创建时填一次、中途不刷新），不是「每个频道一份记忆」。

为什么这一条不能含糊：**如果记忆在 session 内管理，记忆就绑在 (agent, 话题) 上，
那 agent 池立刻失去意义** —— 同一个 agent 被派去做两件事，两边学到的东西互不知道，
它就不是「同一个 agent」，只是「同一份出厂设置的两个副本」。
而这正是当时已经踩到的坑（§1.3），③ 的后半句等于把这个坑固化成设计。

**「良性循环」恰恰要求记忆跨话题**：agent 在 A 话题学到「这个项目的 CI 要跑十几分钟」，
在 B 话题就该知道。记忆锁在 session 里，循环就断在话题边界上。

正确的形状：

```
agent（池里的一个身份）
 ├─ 出厂设置：harness / skills / mcp / model / effort   ← 创建时定，可改版
 ├─ 记忆：跟身份走，跨它所在的所有话题累积            ← 不跟 session
 └─ session：每个 (agent, 话题) 一个，可丢可重建       ← 用完即弃
```

### 12.5 修正我上一轮关于 MCP 的判断

§12.3 里我写「不建议抄 MCP 配置，我们的工具是内置的」。**那是在「只有一个芝士」的前提下说的，
前提变了，结论要改**：一旦有 agent 池，不同类型的 agent 本来就需要不同的外部工具
（一个连飞书、一个连数据库、一个只读代码），per-agent MCP 就有了意义。
Claude Code 本身支持 MCP，落点是把 `.mcp.json` 写进那个 session 的配置。

### 12.6 三件要一起想清楚的

1. **harness 下沉到 agent 级** —— 做了：`agent_types.harness`。留 NULL 表示「这个类型不在乎」，
   部署自己的选择（`settings.agent_backend`）照旧生效。
2. **谁是主体：agent 订阅房间，还是房间邀请 agent？** buzz 是前者（persona frontmatter 里
   `subscribe: ["#security-reviews"]`，agent 主动订阅频道）；我们走的是后者（建话题时选）。
   要记住的是：**选的是初始值，后面还能加/换**（roster 支持多 agent）。
3. **session 数量的生命周期。** session 数 = 房间数 × 该房间里的 agent 数 × 它手上的活数，
   而容器不再随采纳回收，所以只涨不跌。buzz 一个进程的并发 session 上限是 8。
   §2.4 那条「主动轮换 session」**至今没做**，记在账上。

### 12.7 和「容器按房间分配」是配套的（都已落地）

「容器按房间分配」做的事情之一，就是**把 `CHEESE_TOPIC` / `CHEESE_TOKEN` 从容器 env
移到 per-session 注入**（`tmux new-session -e`）。那正是这套设计的地基：
一个容器（房间）里跑多个 session（每个 agent × 每件活一个），
恰好是 buzz 的形状（一个进程挂多个频道的 session）。

### 12.8 记忆存到 agent 级（@fulu 2026-08-17）

记忆的单位是 agent，不是房间：一个芝士在一个项目里有一个池，它在五个房间学到的东西
互相看得见。这条已经落了（`agent_instances`）。

同批拍板里还有一条「一个房间最多一个 agent」，理由是它能把 session 层的改造整个省掉——
一个 topic 最多一个 agent，`topic_id` 就唯一确定了「哪个 agent 在哪个地方」，
一个 `topic.session_id` 字段就够。**这条不再成立**：2026-08-19 定的多 agent 设计
（<&docs/plans/2026-08-19-multi-agent-harness-and-context-design.md> §1）要的正是
「一个房间里 coding agent 和 ops agent 平级共处」，所以 session 的 key 就是
`(topic_id, agent_handle)`，`agent_sessions` 已经这么建了。省下的改造重新被买回来了，
换到的是那一档能力。

`resolve_agent_handle(topic_id)` 取 roster 里第一个 agent handle，在这条约束下本来
名正言顺，现在又变回随意——**它是多 agent 的下一个收口点**：会话已经分得开，
「这一轮是谁在说话」还没有。

#### 必须回答的一个问题：task 的 agent 从哪来

一件活现在是房间里的一条支线，没有自己的名册。答案落成了：**支线跟着房间那一个**
（`resolve_agent_handle` 读的是房间的 roster，支线只在完全没有 agent 就座时才回退到
它自己沙箱 token 里那个 `cheese-<hex>`）。
这样「同一个 agent 在房间主对话 ＋ 它派出的每件活上各有一个 session」自然成立，
正是 buzz 的形状；而且活里学到的东西**自动流回房间**（同一个 agent、同一个池），
这就是「良性循环」真正闭合的地方。
反过来让每件活自己选，母子之间的记忆就又断了。

#### 一个连锁反应：「core ＋ 按需检索」从可选变成必需

记忆到 agent 级之后，一个 agent 的池 = 它所在的所有房间 ＋ 所有支线的总和，
不可能再全量平铺注入。**这条已经做了**：`core` 每轮在场（4000 字符预算，
故意比另一条紧一个数量级）＋ 其余按需检索（20000 字符预算，职责不是装下全部，
而是把位置花在这一轮用得上的事实上）。两道上限都不静默。

#### 两件小事的落点

1. **项目默认 agent**：新话题建出来时把项目当时的默认实例坐进名册；没人被 @ 到时
   房间回落到项目当下的默认，而不是话题自己记住的某一个。
2. **存量 `cheese-<topic hex>` 池**：一个项目的隐式默认 agent 用 `cheese` 这个 handle、
   在 `agent_instances` 里**根本不建行**，所以一个从没配置过任何东西的项目
   继续写、也继续读它本来就有的那个池。

### 12.9 拍板：task 用当前 agent；「芝士」就是池里的默认 agent（@fulu 2026-08-17）

两条都成立。第二条比它听起来更划算：**它同时是存量记忆的归并方案**——不用造新概念，
现状就是「池里已经有一个 agent 叫芝士」，只是今天没被当成「池里的一个」。
而且 `cheese` 这个 handle **已经有 25 条记忆**（见下），不是空的。

#### 实测：这个项目现在有 36 个记忆池、155 条、42455 字符

`GET /api/memory?project_id=…` 实测（2026-08-17）：

| 池 | 条数 | 字符 |
|---|---|---|
| `project:<项目id>`（分池前的共享池） | 59 | 14176 |
| `agent_project:…:cheese`（**平台级 handle 的池**） | 25 | 7806 |
| 其余 **34 个** `agent_project:…:cheese-<话题hex>` | 各 2–11，多数 2 | 合计约 20473 |

两个结论：

**① 34 个 per-topic 池平均 2 条 —— per-topic 分池把记忆碎成了粉末。**
每个话题的分身学到两三条就结束了，然后那个池永久孤立、再没人读。
这组数字本身就是「记忆不该按话题分池」的证据。

**② 归并必须和「core ＋ 按需检索」同一批做，不能先合并后优化。**
当时合并起来是 155 条 / 42455 字符，一次性远超注入预算——
虽然 prompt 会如实报「另有 N 条没放进来」，但那等于告诉芝士「你的记忆大部分不在场」，
比分池更糟。所以顺序只能是：先有 core ＋ 按需检索，再归并。
后来正是按这个顺序做的（`store.py` 里的两层预算，注释拿的就是本项目这组数字）。

#### 还剩四个问题

1. **`cheese` 这个 handle 现在兼任两个身份。** `handles.py` 的注释写着它是
   *"the fallback identity: what a token that names no 分身 resolves to"* ——
   **认不出身份的调用会解析成 `cheese`**。如果 `cheese` 同时是有记忆池的默认 agent，
   那些认不出来的写入就会落进默认 agent 的池。不严重，但最好给「认不出」一个单独的 sentinel。
2. **「换 agent」必须重开 session。** 一个房间跑到一半换成另一个 agent（比如换成运维芝士），
   接着用同一份 transcript 会人格分裂 —— 所以换 agent ≈ 重开会话，是**有代价的动作**，
   不是切个开关。设计上要明说，UI 上要提示。
3. **范围分两层** —— 落地了：类型（出厂设置：harness / skills / mcp / model / effort）
   **不属于任何项目**，所以一个类型能同时撑起每个项目里的一个 agent；
   **记忆必须项目内**（挂在 `agent_instances` 上）。
   正好对应 buzz 的 persona（可分发）vs engram（community-local）。
4. **默认 agent 是项目级可覆盖的**，不是平台硬编码。

## 13. 子话题 ＝ subagent 的可视化（<@wangchangxin> 2026-08-17）

原话：「子话题与母话题共用房间，子话题可视为 subagent 的可视化表现，不过子话题本质上是另一个
session，可以选用不同的 agent，可以与母话题双向交流，可以 commit 到同一个 PR。」

下面先把 Claude Code 那套机制核实清楚，再逐条对我们的可行性。

### 13.1 Claude Code 是怎么派发 subagent 的（核实，2026-08-17）

**证据来源要先说明**：官方文档站 `code.claude.com/docs/en/sub-agents` 在沙箱里抓不到
（网络策略挡住了 claude.ai 系域名），所以下面每条都注明出处等级 ——
【契约】＝我手上 Agent / Workflow 工具描述的原文（一手，就是当前实现的接口本身）；
【仓库】＝本仓库文件；【二手】＝第三方整理，未经官方文档复核。

| 维度 | 事实 | 出处 |
|---|---|---|
| **怎么派** | 母 agent 调一个工具（`Agent`，旧名 `Task`），参数只有两样：`subagent_type`（用哪个类型）＋ 一段自然语言 prompt。没有第二个入口 | 【契约】 |
| **类型从哪来** | `.claude/agents/*.md` 的 frontmatter。原文：*"Each agent type's model, reasoning effort, and tools come from its definition (`.claude/agents/*.md` frontmatter or SDK `agents`)"*。本仓库就有两个，<&.claude/agents/check-runner.md> 的 frontmatter 是 `tools: Bash, Read` / `model: sonnet` | 【契约】【仓库】 |
| **注入什么** | ①它自己那份 .md 正文当系统提示 ②环境信息（工作目录）③派发时那段 prompt ④项目的 CLAUDE.md 与记忆层级 ⑤母会话**开始时**的 git 状态快照 ⑥它 `skills` 字段点名的 skill 全文。**不含母 agent 的对话历史** —— 契约原文：*"a new Agent call starts fresh"* | ④⑤⑥【二手】，其余【契约】 |
| **例外** | 内置的 `Explore` / `Plan` 两个类型**故意跳过 CLAUDE.md 和 git 状态**，为的是快和便宜 | 【二手】 |
| **怎么回来** | **只有最后一条消息**回到母 agent。中间每一次工具调用、读过的每个文件、跑出来的每行日志，全留在它自己的上下文里，永不注入母上下文。Workflow 契约说得更直白：*"Subagents are told their final text IS the return value (not a human-facing message)"* | 【契约】 |
| **能不能嵌套** | 看类型的工具白名单：`Explore` / `Plan` 是 *"All tools except Agent"*，派不出下一层；`general-purpose` / `claude` 是 `*`，能派。所以「不能嵌套」是**配置出来的约定**，不是机制禁止 | 【契约】 |
| **文件系统** | 默认**和母 agent 共用同一个工作目录**；`isolation: "worktree"` 才给它自己的 git worktree（*"auto-cleaned if unchanged"*） | 【契约】 |
| **双向** | 新增了 `SendMessage` —— *"continue a previously spawned agent with its context intact"*，配 `ListAgents` 列出可寻址的 agent。也就是说 **Claude Code 自己已经从「一次性派发」走到「可以续聊」了** | 【契约】 |

最后一行是这一节最值钱的信息：**双向不是我们的发明，是上游已经走到的地方**。

### 13.2 我们的 split 和它是同构的，不是「像」

一一对应，每行都有代码出处：

| Claude Code subagent | 我们的支线 | 出处 |
|---|---|---|
| `subagent_type`（用哪个类型） | 支线用哪个 agent（继承房间那一个，见 §12.8） | 本文档 §12.8 |
| 派发时那段 prompt | `cheese split --brief` | `TopicService.dispatch_task(brief=...)` |
| 项目 CLAUDE.md / 记忆层级 | 房间实况文档的**逐字快照** ＋ 项目记忆注入 | `_seed_brief_doc` |
| 全新上下文 | 全新 session | 支线开工时看不到房间的对话历史，只有简报 ＋ 文档快照 ＋ 房间最近若干条消息（按字符预算截） |
| `isolation: "worktree"` | 每条支线一个 jj workspace ＋ `topic/<hex>` 分支 | `ws._ensure_worktree` / `ws.branch_for_place` |
| final message 回程 | `cheese conclude` → 结论卡 | `ConclusionCardService` |
| 不能嵌套（配置） | 不能嵌套（结构上没有嵌套这回事） | 从一条支线里再拆，得到的是同一个房间里的另一条支线 |

我们还多两种上游没有的：`clone_from`（继承房间**完整 transcript** 的分叉，
docstring 明确把它和 split 对立着写：*"clone instead forks the source's full conversation state"*），
以及 `cheese tell`——**派出去之后还能双向说话**，而 Claude Code 的 `SendMessage` 是同一个方向的能力。

**所以「子话题是 subagent 的可视化」是一句准确的技术陈述，不是类比。**

### 13.3 建议的表达

一句话版本：

> **子话题不是「更小的房间」，是「被看见的 subagent」。**

展开版（可直接抄进对外材料）：

> Claude Code 派一个 subagent 出去，是个黑盒：给它一段话，它回你一段话，中间做了什么——
> 读了哪些文件、试错了几次、卡在哪里——母 agent 看不见，人更看不见。
>
> 我们把这个黑盒换成房间里的一条明线。**隔离照旧**（独立上下文、独立工作区、只带一份简报出门），
> 但**过程是公开的**：任何人随时能点进去看它在干什么，能中途插一句话，能换一个更合适的 agent 来做，
> 它的提交并进同一个 PR。
>
> 换句话说：subagent 解决的是「上下文别互相污染」，我们在此之上多解决一件事——
> **「别人得看得见你在干嘛」**。前者是给模型的，后者是给人的。

要点在于：**不要把它讲成「我们也有 subagent」**，那是把一个更强的东西讲小了。
差异有三条，都对我们有利：

1. **过程可见**：subagent 的中间过程结构性地不可见（只有 final message 回程）；子话题全程可读。
2. **可以换人做**：subagent 绑死在派发时选的类型上；子话题可以换成池里另一个 agent（§12.8）。
3. **产出并轨**：subagent 的产出要么写进共享工作目录（无隔离），要么留在自己的 worktree 里
   （`isolation`，且 *"auto-cleaned if unchanged"* —— 没人接就没了）；子话题的提交进同一个 PR，有人审。

### 13.4 可行性：三条，逐条核实

#### ① 共用房间（容器）—— 已落地

当初容器是**每话题一个**，一个房间拆 5 条支线 ＝ 6 个容器，这就是「太贵」的来源。
但**工作区本来就已经是共用的**：所有话题的 worktree 都挂在同一个 project-tree 挂载下
（`sandbox_topic_workdir` 的 docstring 写明是「REAL path under the project-tree mount，不是每话题重映射」，
为的是和共享的 pnpm / uv 缓存做硬链接）。**物理上一个容器早就能看见全部支线的工作区**，
差的只是「谁来起这个容器、谁负责它的生命周期」。

现在容器按房间命名（`tmux_container_name(room_for_topic(topic_id))`），
`CHEESE_TOPIC` / `CHEESE_TOKEN` 移到了 per-session（`tmux new-session -e`）。
工作区布局没动。

#### ② 双向交流 —— 已落地

- **子 → 母**：`cheese conclude` 开结论卡，房间可采信 / 补证据 / 升级（`ConclusionCardService`）。
- **母 → 子**：当初有两处独立的拦截——per-turn token 的 topic claim 直接 403，
  以及评论端点里 summon 的条件是 `if not actor.is_agent`（只有人类评论才唤醒）。
  现在走 `cheese tell` → `POST /topics/{id}/tell`，写 block **并**唤醒对方，只开父子这一条边。
- 结论卡「补证据」打回也会叫醒了，而且叫醒的是**支线**不是房间。

**为什么不是放宽 token 的 topic scope**：那等于放弃话题级隔离。正确形状是
**以「我」为主语的路由**——URL 里的 id 是发信人，收信人在 body 里，跨话题关联由服务层校验，
不出现在 URL 上。

#### ③ commit 进同一个 PR —— 已落地

当初母子是两条各自从 main 长出来的线，两个 PR，互不相干。现在：
`_ensure_worktree` 从房间的分支长出来（`_fork_point`），支线的结论被采信时分支折进房间分支
（`fold_into_room`），房间递一张卡开一个 PR。

**当初点名的三个风险，两个已经在代码里处理了：**
- **冲突提前了**。多条支线并行改同一批文件，冲突从「两个 PR 之间」提前到「房间分支上」。
  这不是坏事（早发现），但要有预警 —— 正好是 @并行话题冲突预警设计 那件活。
  折不动时**会在房间里说一句，不会默默算了**。
- **房间自己在编辑时会卡住合并**。`_catch_up_with_branch` 只在工作区**没有 pending 改动**时快进，
  「人的未提交编辑绝不能被机器的推送扫掉」是它写死的原则；它的返回值现在有人接，
  刚移动过分支的调用方会知道工作区没跟上。
- **不再和「等 CI 期间不要写工作区」撞车**（#718）：轮询器不再把工作区改动折成提交，
  推送只在芝士 commit 后（`cheese push-fix`，或轮询发现本地分支 head 已前移）发生，
  工作区里写文件不会把正在跑的 CI 掐掉重排。

### 13.5 一句话结论

三条都做完了。②（双向）是其中含金量最高的一条 —— 它正是「一条支线 ≠ 一次性 subagent」
这句话的全部依据所在。

## 14. task 的载体：一张随进展生长的卡，不是一个 PR（<@wangchangxin> 2026-08-17）

原话：「task 是不是应该做成可视化的，给它一个具体的载体，让它可以被房间内所有人看见，
在前端也有一个地方体现，他可能就体现为一个 PR。」

**前半句成立，而且应该做；后半句的时序要往后放一格 —— PR 是这张卡长到后期的样子，不是卡本身。**

### 14.1 为什么 task ≠ PR：三条硬理由

1. **GitHub 不接受空 PR。** 实测：没有 commit 时开 PR 返回 422 `No commits between`。
   而 task 从**派出去那一刻**就存在，那时候一个 commit 都没有。
   所以「开一个空 PR 当占位符 / 当容器」这类设计在**机制层面**不成立，不是工程量问题。
2. **不是每个 task 产出代码。** 调研类 task 的产出是一份结论，没有 diff。
   把载体硬绑在 PR 上，这一类活就直接没有载体了 —— 而它们恰恰是最需要「被看见」的那类
   （做了三小时，房间里的人只看到一句「已派出」）。
3. **和 §13 定下并落地的东西直接冲突。** 现在是「支线的提交折进房间的分支，房间开一个 PR」；
   若 task ≡ PR，那 N 条支线就必须 N 个 PR。两条设计打架，留的是前者。

### 14.2 今天已经有什么（核实）

issue #314 已经在房间时间线上做了一条「已派出《X》」的分隔线
（<&frontend/src/components/DispatchedMarker.vue> ＋ <&frontend/src/lib/splitMarkers.ts>）。
方向是对的，但它的实现注释自己把限制写得很硬：

> 标记只能**读时派生**，不能存：唯一还在的关系是这条支线的 `room_id` ＋ `created_at`。
> 派生得出的和派生不出的，界限很硬：能——「这个时刻，从这个房间派出去了《X》，去那边看」。
> 不能——「以下这几条消息 / 这一项待办不归这里了」。那需要一条从支线指回房间某个
> block 的边，**数据库里没有这条边**。

它能显示的只有：标题、支线状态、一个跳转链接。
**说不了「做到哪了、改了什么文件、检查绿没绿、PR 开了没有」。**
而且因为是读时派生，时间线分页时它还会因为落在窗口外而暂时不显示
（`splitMarkers.ts` 里 `hasMore` 那段的处理）。

一句话：**#314 做到了 1/4，剩下的 3/4 正是这一节要的东西。**

### 14.3 建议的形状：一张卡，随进展长内容

| 阶段 | 卡上显示什么 |
|---|---|
| 刚派出 | 标题、简报第一句、**谁在做**（哪个 agent —— 正好接 §12 的 agent 池） |
| 干活中 | 改了哪些文件、几个 commit ——「commit 可视化」落在这里 |
| 递了验收卡 | 卡的状态。注意机器闸门已经退役，检查全部发生在 PR 的 CI 上 |
| 开了 PR | PR 号、CI 状态、合并入口 —— **这时它长得就像一张 GitHub PR 卡** |
| 完成 | 折叠成一行「已合并」，不再占时间线的视觉预算 |

所以那个直觉是对的，只是位置要摆准：**PR 是这张卡后半段的形态，不是它的定义**。
卡从派出去那一刻就在，PR 半路才出现，有些卡永远不会有 PR。

### 14.4 最小改动：补上那条缺失的边

要从「派生行」变成「真卡片」，只差一件事：**split 的时候在房间主线写一个 block**
（`kind=event`，`meta` 里带支线 id），而不是像现在这样什么都不写
（`SplitIn` 只有 title / created_by / brief，不往房间落任何东西）。

一条边换来三件事：

1. **位置固定**，不再因为分页窗口而错位 —— #314 注释里承认的那个问题直接消失；
2. **能挂状态和产出**，也就是 14.3 那张表；
3. **它是母→子那条通道的 UI 落点** —— 在卡上直接回一句话给那件活，后端走 `cheese tell`
   那条路由。三件事共用一个落点，不用各做各的。

### 14.5 顺带收掉 issue #184 自己留的尾巴

#184 的「你会看到的变化」最后一段写着：

> 暂时没变的一件事：任务现在还显示在侧边栏里。按设计它应该是话题时间线里的一张卡片，
> 但那要连着前端一起改 —— 只做一半会让芝士拆出来的任务变得点不进去，所以先留着，下个 PR 处理。

**这就是那张卡。** 现在侧栏里已经没有活了（侧栏只列房间），
所以「一件活是什么、做到哪了」的第一现场只剩时间线这一处，这张卡的优先级反而更高了。
