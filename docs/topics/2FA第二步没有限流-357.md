# #357：2FA 第二步没有任何限流

## 目标

登录第一步（密码 / SRP）有限流，第二步 2FA 一次都不限。握有正确密码的人可以无限次试 TOTP，期望约 33 万次就能撞开——而"密码已泄露"正是 2FA 唯一要防的场景。本话题把这个洞堵上，并给出能证明"第 N+1 次被拒"的测试。

## 已核实的事实（@wangchangxin 提的四条，逐条对过代码）

| 事实 | 位置 | 结论 |
|---|---|---|
| `POST /users/auth/verify-2fa` 无任何计数器 | <&backend/app/api/routes/users.py> | ✅ 属实 |
| pending 票 300 秒、密码通过后签发、密码成功会清失败计数 | <&backend/app/common/auth.py>、login/SRP 两处 | ✅ 属实 |
| 备用码退到同一条不限次路径 | verify-2fa 里 TOTP 失败 → `verify_backup_code` | ✅ 属实 |
| `LoginRateLimiter` 换 key 前缀就能用 | <&backend/app/domain/user/login_security.py> | ✅ 属实 |

## ⚠️ 校验 2FA 的路径有两条，不是一条

简报只点了 `POST /users/auth/verify-2fa`。核代码时查出**第二条同类洞**：

`POST /users/auth/login` 和 `POST /users/auth/srp/verify` 都接受把 `totp_code` **直接内联在登录请求里**。走这条分支时**根本不签发 pending 票**，直接调 `TOTPService.verify_2fa`。密码对 + TOTP 错在那里：

- 不记任何失败计数（`clear_attempts` 在 2FA 校验**之后**才调，失败会先抛出去）；
- 不受票的约束，因为压根没有票。

所以它和 verify-2fa 一样是无限次的，而且**只修 verify-2fa 的话，攻击者换用这条路径就能把修法 1 和 2 全部绕过**。已一并纳入同一个 `_spend_2fa_attempt`，并有专门的测试（`test_inline_totp_on_password_login_is_budgeted_too`）。

**给以后的人**：校验 2FA 的入口一共四个，分属两个互不相干的预算——

| 入口 | 预算 |
|---|---|
| `POST /users/auth/verify-2fa` | 登录第二步（`TwoFactorRateLimiter`，备用码另计） |
| `POST /users/auth/login`（内联 `totpCode`） | 同上 |
| `POST /users/auth/srp/verify`（内联 `totpCode`） | 同上 |
| `POST /users/auth/sudo`（`method=totp`） | 会话内再验证（`StepUpTwoFactorRateLimiter`，见下） |

漏掉任何一个，攻击者换那条路走就行。

## 决策

| # | 修法 | 状态 |
|---|---|---|
| 1 | 2FA 这一步按 **user_id** 限流（5 次 / 15 分钟锁定），覆盖 verify-2fa **和两条内联路径** | 已做 |
| 2 | pending 票加 `jti`，签发时 reserve、校验时 claim，**验对验错都烧掉**；失败时**连同拒绝回一张新票** | 已做 |
| 3 | 备用码单独计数，上限收紧到 **3 次** | 已做 |

三条各自独立成立：1 关掉总量，2 关掉单张票的放大倍数，3 给高熵一次性凭据一条更紧的独立预算。

**修法 2 的补票是 @wangchangxin 拍板的**，理由是不补票会造出一个更难看的洞：TOTP 输错和输到刚过期的码是高频正常事件，票烧了不给就得从密码重来，而密码那步有自己的 5 次 / 15 分钟限流——**手抖三次就离把自己锁在门外只差两次**，触发的全是合法用户，攻击者手上有密码根本不在乎重走一遍。补票不削弱修复：配额归 user_id 计数器管，放大倍数归 `jti` 管，每张新票仍然只能用一次。

配套两条硬约束（各有一条测试钉住，都做过负向对照）：

1. **新票不重置 user_id 计数器**。一旦补票顺手清零配额，修法 1 等于不存在，而且外表一切正常——比原来的洞更隐蔽。
2. **新票继承原票的到期时刻**，不各自重算 300 秒。否则一直错下去就能让「密码已过、2FA 未过」这个中间态无限续命。

**三种拒绝在响应里可机读区分**（`error.data.reason`）：`invalid_code`（留在本页重试，带新票和剩余次数）/ `session_expired`（回去重新登录）/ `too_many_attempts`（带 `retryAfterSeconds`，等一刻钟）。压成同一个错误码的话，用户会一直重试一个不可能成功的操作。

## 实现要点

- **限流键必须是 user_id 不是 username**：到第二步请求里已经没有用户名了；更关键的是**密码登录成功会清掉 username 的计数器**，共用等于每次登录都把 2FA 预算清零。
- **名额在校验之前扣**（`consume_attempt`，`INCR` 原子）。原来那种"失败后才记一笔"是 check-then-act：一千个请求同时打进来，全都在任何一个写回之前读到 0，5 次的预算一次放行一千个。
- **票的 `jti` 由 `mint_2fa_pending_token` 返回、由调用方 reserve**，模块本身不碰 I/O——照 <&backend/app/core/github_install_state.py> 的先例。签名只能说明"平台铸的"，只有预约能说明"还没被花掉"。
- **fail-closed**：Redis 连不上时 `reserve`/`claim` 抛错，两处都当拒绝处理（500），绝不放行。
- **没有 `jti` 的旧票一律无效**，包括上一版铸出来还没过期的——TTL 300 秒，窗口就是发版后 5 分钟。
- **按码型分流**：6 位纯数字走 TOTP，其余走备用码。备用码是 8 位 hex，两者不存在能互相通过的输入，所以这不是行为变更，但让"这次尝试算在谁头上"变得有确定答案。

## 测试

新增 9 个集成测试 + 9 个单元测试。**负向对照一次只拆一个机制，四次各自命中**：

| 拆掉什么 | 该红的 | 实际 |
|---|---|---|
| `consume_attempt` 不计数 | 3 个预算测试 | ✅ 红，票据测试仍绿 |
| `claim` 短路成永远放行 | 2 个票据测试 | ✅ 红，预算测试仍绿 |
| 补票时顺手 `clear_attempts` | 「补票不重置配额」 | ✅ 红（连带 2 条） |
| 补票用新的 300 秒而非继承 | 「新票继承到期时刻」 | ✅ 红 |

关键测试的写法是**在第 N+1 次发送正确的验证码**——证明它是在看都不看的情况下被拒的，而不只是"错的被拒了"。

**其中一条测试第一版是假的**，值得记一笔：到期继承那条原本直接比较新旧票的 `exp`，但两张票都是 300 秒窗口、又在同一秒里铸出来，所以**重算 300 秒也照样相等**——负向对照没红才暴露出来。改成先等过 1 秒再触发，并补了一条用固定 `expires_at` 的单元测试。**负向对照的价值正在这里：它验的不是代码，是测试本身有没有在验东西。**

**回归**：后端全量集成测试 **1400 passed / 24 skipped / 0 failed**（474 秒，`-n 4`，补票那段之前跑的）。补票落地后跑了 2FA + auth 相关 + contract + 全部单元共 **3101 passed**，失败的 23 条全是已知的沙箱缺 procps（`test_machine_service.py`、`test_tmux_control.py`，与本改动无关，CLAUDE.md 有记）。`check.sh --no-tests`（闸门跑的那条）：6/6 passed。

## 顺手修的一个测试基础设施问题

xdist 每个 worker 有独立的 Postgres，但**共用一个 Redis**。而 Redis 里的键按 user_id 分，user id 在每个 worker 自己的库里都从 1 开始——gw0 的 5 号和 gw1 的 5 号是同一个账号。我新加的 15 分钟锁定键会因此随机打到别的 worker 的测试上。已在 <&backend/tests/conftest.py> 给每个 worker 分一个 Redis 编号库（Redis 自带 16 个）。这是原来就存在的隐患（2FA 密钥、备用码同理），只是我的改动会把它踩响。

## 会话内再验证：第二个预算（#389）

`/auth/sudo`（`method=totp`）校验的是和登录同一把 TOTP 密钥，但攻击者手上不是密码而是**一个活着的会话**（Cookie 被偷、设备没锁）。已走 `_spend_2fa_attempt(..., step_up=True)`。

**为什么不和登录共用计数器**：共用的话，偷到会话的人只要一直猜错，就能把账号主人锁在**登录**外面——限流本身变成了拒绝服务；反过来账号主人在登录页手抖，也会削掉会话内再验证的名额。所以键名另起一族（`cheese:2fa_stepup_*`），上限同样 5 次 / 15 分钟。

**备用码在 sudo 这里不是凭据**：它只调 `verify_2fa`（TOTP），从不查备用码集合。所以给它再挂一条备用码计数，计的是一件不会发生的事。备用码递到这里的实际行为是——当作一个错的 TOTP 拒掉、照常扣一次会话内再验证的名额、而且**不会被消费掉**（压根没人去查它），回到登录页仍然能用。让 sudo 开始接受备用码是**加一种能关掉 2FA 的凭据**，那是产品决策，不是限流，没做。

**限流只管「猜」，管不了「连猜都不用」**：`/2fa/disable` 当时的 `code` 是可选的，闸门 sudo 又只返回 `{verified: true}`，那道门其实只在前端存在。见 <&docs/topics/关掉二次验证要真的重认证-389.md>。
