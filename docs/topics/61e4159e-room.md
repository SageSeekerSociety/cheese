## 一、issue 187 复核结果（子话题已回流）

复核题目是「磁盘不足时平台是否满足 issue 187 的设想」，答案是**一半满足**。

**满足的部分（有实测）**

- 进度层已经在跑：`TopicProgress` 表（<&backend/app/domain/topic/models.py> 第 150 行，注释里就写着 #187）+ `GET /topics/{id}/progress`，子话题实测新建的清单能立刻查回来。
- 平台记忆（`cheese remember/recall`）走 HTTP 写进 Postgres，沙箱不落盘；dev/prod 的 PG 在独立主机，应用机磁盘满不影响它（例外：etrip 是同机容器内 PG）。
- 磁盘满有识别也有刹车：ENOSPC → `storage_exhausted`（host_scoped）；应用机另有 85% 的 systemd 刹车，只在没有活跃轮次时删可重建的沙箱容器。

**不满足的部分**

1. **磁盘满时话题会静默停住** —— 换机和自动续跑两条路同时不通，见下「二」。
2. **芝士的本地文件记忆是空的** —— issue 187 §四说「auto memory 意外地已经持久了」，现在不成立，见下「三」。
3. dreaming / 临终收割在代码里根本不存在（全库无 `dream`/`consolidate`），回收器只做 `docker rm -f`。
4. OpenViking 仍没通电、`.viking` 仍无挂载，与 187 描述一致，无变化。

## 二、磁盘满 → 话题静默停住（已拆子话题）

房间这边逐行核过代码，链条是这样断的：

- `storage_exhausted` 是 `host_scoped=True`（<&backend/app/domain/agent/platform_failures.py>），所以会走换机逻辑；
- 但 `swap_topic_device`（<&backend/app/domain/agent/host_swap.py>）开头就 `old_id = await service.topic_device(topic_id)`，**取不到设备绑定就直接 `NO_SWAP` 返回**；
- 而 `bind_topic_device` 全库只有 device_provider 那一条路径会调用 —— 本地 docker 沙箱的话题从来没有设备绑定，**换机分支在当前部署下根本进不去**；
- 回到 <&backend/app/domain/agent/chat.py>，`resume_after_s` 只在 `swap.resume_after_s` 非空时才设置，`NO_SWAP` 的它是 `None`，**于是也不排自动续跑**。

净效果：磁盘一满，话题留下一条平台提示就停在那里，等人来 @。

## 三、芝士的本地文件记忆是空的（子话题已回流，根因定死）

**结论：不是记忆没保存，是记忆读不到了。** 根因是 2026-08-12 的 PR #311 引入的回归，不需要人上宿主核实。

用大白话讲：芝士的这份记忆存在宿主上一个**按「当前工作目录的名字」命名的文件夹**里。#311 把沙箱的工作目录从 `/work` 改成了 `/topics/topic_<8位>`，文件夹名字跟着变了，于是芝士每次都被指到一个**全新的空文件夹**。旧记忆一个字节都没丢，只是再没人去读它。

**三条证据互咬**（子话题给的）：

1. issue 187 §四在 8/9 写死了当时的路径，里面是 `projects/`**`-work`**`/memory/MEMORY.md` —— 证明那时记忆确实在写。「从来没写过」这条排除。
2. #311（8/12 22:15）改了 cwd，目录名从 `-work` 变成 `-topics-topic-xxxxxxxx`。同一个 PR 顺手加了 `LEGACY_CONTAINER_CWD` 常量 —— **作者知道 cwd 变了，但只给 transcript 做了兼容，没管 memory**。
3. session 目录的路径规则从 7/18 起没动过，所以「session 目录被换掉了」这条也排除。

**影响面**：235 个话题里 **227 个**建于 #311 之前，记忆全躺在旧目录下读不到；其中 12 个至今仍活跃（含跨度近一个月的「cheese 自建 · 项目总览」）。

**更正本文档上一版写的实测**：房间当时在自己沙箱里看到「只有一个 slug 目录、memory 为空」，把它当成了证据 —— 那是个**采样陷阱**。本房间创建于 #311 落地之后 36 分钟，它这辈子就没在 `/work` 下跑过，当然看不到旧目录残留。现象是真的，但它证明不了任何事，作废。

**同时更正 issue 187 §四的措辞**：187 说 auto memory「意外地已经持久了」，像是白捡的。子话题的判断是：8/9 写下时这句话是**对的**，它现在不成立是因为 #311 切断了**可达性**，不是持久性坏了（文件还在宿主盘上）。但它**不是白捡的** —— 它对 cwd 敏感，**每改一次 cwd 就会再断一次**，要留着就得有人管。

**子话题的修复（已写，未合并）**：新增 `claude_memory.py` 的 `consolidate_memory()`，容器起来之前把其它目录下的 `memory/` 搬到当前 cwd 对应的目录。只搬 memory、transcript 一个字节不动（有测试钉住）；不覆盖已有文件；打标记保证幂等、且不复活已删的记忆；再改 cwd 仍然管用。**只覆盖 tmux 这一条现役路径**，另两个 provider 的 cwd 语义不同，有意没碰。ruff/pyright 干净，9 个新单测全绿。

> 为什么不能照抄 transcript 的 glob 兜底：transcript 是**我们**去读，放宽搜索范围就行；memory 是 **Claude 自己**读，它只认当前 cwd 那个目录名 —— 只能把文件搬过去。

## 五、需要人拍板，不是 bug（重要更正）

187 子话题「顺带撞见、建议单开」的那条：`/topics` 整个 worktrees 根目录 rw 挂进每一个沙箱，所以同项目的话题之间能互相读写工作树。

房间这边复核后**不建议按 bug 单开**——它是有意的取舍，代码里写着理由：

- <&backend/app/domain/workspace/service.py> 的 `sandbox_project_mounts` 有一段 Isolation note，明说「同项目的每个话题沙箱都看得见也写得动兄弟话题的工作树，这不是新的信任边界：这些容器本来就共享项目那份可写的 `.jj`/`.git`，同项目话题之间从来就没有互相隔离过；跨项目隔离不变」。
- 单挂一次是**承重**的：硬链接不能跨 bind mount，pnpm/uv 的共享 store 靠这个才省得下空间。拆成一话题一挂载会直接打掉这个共享。

所以这里真正要人回答的是一个产品问题：**同一个项目内部，话题与话题之间要不要互相隔离？** 要，才谈得上怎么改；不要，这条就该关掉。已作为决策抛给 @蔡松洋。
