## 目标

两阶段采纳的轮询器里有三处明确的 bug，合起来的表现就是「采纳之后一直等 CI、合不进去」。一个 PR 修完，**不做设计变更**。

**当前状态：三处代码都改完，测试写完，`backend` 的 ruff / pyright / 相关测试全绿。差最后一次回归确认，然后递卡。**

---

## 改了什么

### ① 换基用了只读 token —— 主因

PR 落后 main 时平台要替它「更新分支」（GitHub 的 Update branch）。这是个**写**操作，代码却传了只读 token，GitHub 直接 403；异常被上层吞成一行日志，而且发生在写卡片之前 —— 所以卡面一个字都不变，看起来就是「还在等 CI」。改成写 token（`backend/app/domain/review/services.py`）。

这类错误以前没有任何东西拦得住：测试里的假 GitHub 客户端根本不看 token。现在它记录每次调用收到的 token，并有一条测试断言 update_branch 拿到的是写的那份。**补这个断言和修那一行同样重要。**

### ② 第三方 check-run 被算成「我们的 CI 红了」

一个 commit 上的 check-run 是块公告板，copilot 的评审机器人、codecov 都往上贴。以前平台一视同仁，于是 PR #506（我们的 test/lint/e2e 全绿，只有 copilot 红）被读成 CI 失败，还去叫芝士修一个它根本修不了的东西 —— 而 GitHub 自己认为那个 PR 是 `clean`。现在判红/判等待只认 GitHub Actions 自己的 check-run（`backend/app/domain/review/github_pr.py`）。

边界照顾到了：过滤完一条都不剩时，落回原有的「零检查」那套（pending → 宽限期 → no_checks），**不会变成 success**。

### ③ 冲突改用 GitHub 现成的判断

以前判冲突是靠「尝试合并被拒 → 解析错误文案」倒推，而红 CI、required 缺席、基线落后都会在合并调用**之前**返回 —— 那一步经常根本走不到，于是真冲突的卡一声不响地停着。

现在直接读 PR 的 `mergeable` / `mergeable_state`（纯 git 判定，跟仓库套餐无关；轮询本来就每轮打这个接口，**零额外 API 调用**）。有冲突就挂 🚫 并叫醒芝士去解，**既不调合并也不调换基**（对冲突的 PR 这两个调用注定失败）。`mergeable` 是 null 时当「还不知道」，照常往下走，不误判成冲突。

顺带：🚫 那条消息原本写死「检查全绿，但 GitHub 拒绝合并」。冲突可能在 CI 还没绿时就进来，文案改成不预设 CI 颜色。

## 顺带核实的一件事（只看不改）

**担心的情形**：人在 GitHub 网页上点 Update branch 之后，PR head 变成 GitHub 侧生成的 merge commit。如果平台本地根本没有这个 commit，`git merge-base --is-ancestor` 会报错，从此永远判「不能快进」、挂上 🌿 分支分叉，而芝士在沙箱里又拉不到 GitHub —— 那就是死锁。

**结论：不是死锁。** `backend/app/domain/workspace/service.py` 加 upstream 远端用的是 `git remote add`，也就是 git 的默认 refspec `+refs/heads/*:refs/remotes/upstream/*`（本地起了两个仓库实测确认）。所以定时的 `git fetch upstream` 会把 GitHub 上的 `topic/*`、`cheesex/*` 一并拉进 `refs/remotes/upstream/*`，那个 commit 在本地是有的，🌿 是诚实的判断。

唯一的小尾巴：upstream 同步每 30 分钟一次，人点完到下一次同步之间本地确实还没有那个 commit，这段窗口里会先挂一次 🌿，同步到了之后能自愈。不影响本卡，没改。
