# 领域包解环与 import 守卫

守卫代码：`backend/tests/unit/test_domain_import_guard.py`（跑在 pytest 里，所以也在 CI 里）。

## 先说结论：守卫治的是分层纪律，不是环

对标 block/buzz 时的说法是「环几乎全是 services 直接调别的领域的 repository 造成的，
加条 lint 就能止血」。**这句话的前半截不成立。** 复测 + 反事实推演如下（2026-08-11，
`backend/app/domain/` 下 42 个领域包、224 条跨包 import）。

### 复测：简报的数字都对

| 被 import 的层 | 条数 |
|---|---|
| `models` | 77 |
| `repositories` | 77 |
| `__init__` | 19 |
| `services` | 16（子图无环） |
| 其余（具体模块名） | 35 |

42 个包、20 对双向依赖、一个 26 个包的强连通分量——全部与简报一致。

### 反事实：环不是 repository 边一家撑的

把某一类跨域边整个**删掉**（不是改道），看环怎么变：

| 场景 | 非平凡强连通分量 | 双向依赖对 |
|---|---|---|
| 现状 | 1 个，26 个包 | 20 |
| 去掉跨域 `repositories` 边 | 1 个，18 个包 | 9 |
| 去掉跨域 `models` 边 | 2 个，17 + 2 个包 | 14 |
| 两类都去掉 | 2 个，各 3 个包 | 3 |

**`models` 边（ORM 关系）贡献的环和 `repositories` 边一样多**，而 `models` 那半边是设计上
难免的、简报自己也说「不管」。所以就算 repository 边全还完，26 个包的大环还剩 18 个包。

### 更要紧的：正路根本不减边

守卫要求的正路是「service 调对方的 service」。但**包和包之间那条边还在**，只是从
repository 层挪到了 services 层——包级依赖图一条边都不会少。

实测佐证：本轮还掉 6 处违规后重新量，强连通分量仍是 26 个包、双向依赖对仍是 20 对，
**一条边都没变**。

真要解环得消除依赖本身（倒置控制、把数据传进来、把逻辑搬家），成本比改道高一个量级，
不在本轮范围内。

**所以：不要拿守卫的通过率当解环进度。** 守卫值钱的地方是别的——它挡住「绕过对方
service 的约束直接读写对方的表」，这是数据一致性问题，不是拓扑问题。

## 守卫怎么设计的

- **范围**：`app/domain/**` 下的文件，不许 import 别的领域包里的 repository 模块。
  本领域内部不受限。`app/api/` 不在范围内（路由没有「自己的领域」，规则套不上）。
- **认哪些模块是 repository**：最后一段是 `repository` / `repositories`，或以
  `_repository` / `_repositories` 结尾。这样 `device/sql_repository.py`、
  `team/recruitment_repositories.py` 也跑不掉——不然改个名就绕过去了。
  （靠这条比按 `repositories.py` 硬匹配多抓到 2 处真违规。）
- **白名单写死在代码里**，不放配置文件：加一条豁免必须改代码、走 review。
- **白名单是棘轮**：多一条会红（新违规），少一条也会红（还完债忘删）。第二条同样重要
  ——债还完了白名单没删，下一个人会以为这条依赖还在。
- **粒度**是 (发起方模块, 被摸的 repository 模块)，不到类名。同一个文件从同一个领域的
  repository 里多拿一个类，架构上还是同一处违规，不值得再走一次 review。

## 本轮还掉的 6 处

挑选标准是客观的：**发起方文件已经 import 了对方的 service，只是顺手又摸了
repository**。这类改动不新增任何依赖边，纯减，风险最低。全仓符合这个条件的正好 6 处，
全部还完。

| 发起方 | 原来摸的 | 改成 |
|---|---|---|
| `agent/chat.py` | `topic_membership.repositories` | `TopicMemberService.list_for_topic` |
| `agent/device_provider.py` | `device.sql_repository` | `device.wiring.sql_device_service` |
| `machine/services.py` | `device.sql_repository` | 同上 |
| `cx_task/services.py` | `project.repositories` | `ProjectService.get`（新增） |
| `project/services.py` | `team.repositories` | `team.services.team_service`（新增接线） |
| `scheduler/service.py` | `review.repositories` | `AcceptService.open_pr_card_ids`（新增） |

两处新增的接线值得单独说：

- **`device.wiring.sql_device_service`** —— `DeviceService` 故意只认 `DeviceRepository`
  协议（storage-agnostic），代价是每个调用方都得自己写
  `DeviceService(SqlDeviceRepository(session))`，于是为了接线去 import 别人的
  repository。全仓有 5 处这么写。补上这个接缝后领域内的 2 处已经改掉；
  `app/api/deps.py`（2 处）和 `app/api/routes/connector.py`（1 处）不在守卫范围内，
  留作顺手清理。
- **`team.services.team_service`** —— 同样的问题，`TeamService` 收的是 repository 不是
  session（路由那边靠 `Depends` 注入）。

`AcceptService.open_pr_card_ids` 不只是改道：「哪个状态算 PR 还开着」本来就是 review
领域的知识，之前泄漏在调度器里。

## 白名单里还剩 70 条，后续怎么还

按被摸的领域看，头部很集中：

| 被摸的领域 | 条数 |
|---|---|
| `user` | 18 |
| `project` | 11 |
| `topic` | 8 |
| `block` | 6 |
| `team` / `space` | 各 4 |
| 其余 12 个领域 | 19 |

按发起方看：`agent` 13、`dashboard` 8、`review` / `space` / `task` 各 5、`project` 4。

建议的还债顺序（**不建议一次性推平**）：

1. **`user` 那 18 条**（`UserProfileRepository` / `UserRepository`）——绝大多数是「拿一批
   用户的昵称头像去拼 DTO」。正确的做法是 `user` 领域出一个批量 profile 查询的 service
   方法，然后 18 处一起改。单点收益最大，且改动形状高度重复。
2. **`block` 那 6 条**——都是「往话题里追加一条 event block」。`block` 领域缺一个
   `append_event` 之类的 service 方法，补上后 6 处一起改。
3. **`dashboard` 那 8 条**——`dashboard` 是横跨 7 个领域的读模型。它直接读别人的
   repository 是**有道理的**（走 7 个 service 会变成 N+1 查询）。建议不还，而是把豁免
   理由写进白名单注释，或者接受「读模型可以跨领域读」这条例外并在守卫里显式建模。
   在没想清楚之前，先留在白名单里。
4. **`agent` 那 13 条**——`agent/chat.py` 一个文件就占 7 条。这个文件是编排层，性质接近
   dashboard，同样需要先想清楚定位再动。
5. 剩下的零散条目，跟着各自领域的改动顺手还，每还一条删一行白名单。

有两类**可能永远不该还**，需要人拍板：读模型（dashboard）和编排层（agent/chat）。
现在把它们和普通违规混在一个白名单里，是记账，不是判决。
