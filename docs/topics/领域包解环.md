## 先说结论：守卫治的是分层纪律，不是环

对标 block/buzz 时的说法是「环几乎全是 services 直接调别的领域的 repository 造成的，
加条 lint 就能止血」。**这句话的前半截不成立。** 复测 + 反事实推演如下（2026-08-11，
`backend/app/domain/` 下 42 个领域包、224 条跨包 import）。

### 复测：简报的数字都对

| 被 import 的层 | 条数 |
|---|---|
| `models` | 77 |
| `repositories` | 77 |
| `__init__` | 19 |
| `services` | 16（子图无环） |
| 其余（具体模块名） | 35 |

42 个包、20 对双向依赖、一个 26 个包的强连通分量——全部与简报一致。

### 反事实：环不是 repository 边一家撑的

把某一类跨域边整个**删掉**（不是改道），看环怎么变：

| 场景 | 非平凡强连通分量 | 双向依赖对 |
|---|---|---|
| 现状 | 1 个，26 个包 | 20 |
| 去掉跨域 `repositories` 边 | 1 个，18 个包 | 9 |
| 去掉跨域 `models` 边 | 2 个，17 + 2 个包 | 14 |
| 两类都去掉 | 2 个，各 3 个包 | 3 |

**`models` 边（ORM 关系）贡献的环和 `repositories` 边一样多**，而 `models` 那半边是设计上
难免的、简报自己也说「不管」。所以就算 repository 边全还完，26 个包的大环还剩 18 个包。

### 更要紧的：正路根本不减边

守卫要求的正路是「service 调对方的 service」。但**包和包之间那条边还在**，只是从
repository 层挪到了 services 层——包级依赖图一条边都不会少。

实测佐证：本轮还掉 6 处违规后重新量，强连通分量仍是 26 个包、双向依赖对仍是 20 对，
**一条边都没变**。

真要解环得消除依赖本身（倒置控制、把数据传进来、把逻辑搬家），成本比改道高一个量级，
不在本轮范围内。

**所以：不要拿守卫的通过率当解环进度。** 守卫值钱的地方是别的——它挡住「绕过对方
service 的约束直接读写对方的表」，这是数据一致性问题，不是拓扑问题。

## 守卫怎么设计的

- **范围**：`app/domain/**` 下的文件，不许 import 别的领域包里的 repository 模块。
  本领域内部不受限。`app/api/` 不在范围内（路由没有「自己的领域」，规则套不上）。
- **认哪些模块是 repository**：最后一段是 `repository` / `repositories`，或以
  `_repository` / `_repositories` 结尾。这样 `device/sql_repository.py`、
  `team/recruitment_repositories.py` 也跑不掉——不然改个名就绕过去了。
  （靠这条比按 `repositories.py` 硬匹配多抓到 2 处真违规。）
- **白名单写死在代码里**，不放配置文件：加一条豁免必须改代码、走 review。
- **白名单是棘轮**：多一条会红（新违规），少一条也会红（还完债忘删）。第二条同样重要
  ——债还完了白名单没删，下一个人会以为这条依赖还在。
- **粒度**是 (发起方模块, 被摸的 repository 模块)，不到类名。同一个文件从同一个领域的
  repository 里多拿一个类，架构上还是同一处违规，不值得再走一次 review。

## 验收受阻：闸门孤儿（平台侧，与本改动无关）

本话题的验收卡永久停在 `pending_gate`。根因：<&backend/app/domain/review/gate.py> 的
`dispatch()` 起的是进程内 `asyncio.create_task`，引用只存在内存的 `_TASKS` 里，什么都不落库。
建卡后几秒后端重启（当时连续两次 connection refused），task 随进程消失，`finish_gate`
永远不会被调用。`GATE_TIMEOUT_S = 600`，所以超过 10 分钟还在 `pending_gate` 的卡**可证明**
是孤儿，不是还在跑。

它自己爬不出来，出口全封死：

| 路径 | 结果 |
|---|---|
| 启动清扫 | 无。<&backend/app/main.py> 的 lifespan 有 `resume_orphans`（注释：a deploy must never silently eat a turn），但只管 turn，验收卡没有对应的清扫 |
| 定时巡检 | 无。scheduler 只有 `tick` / `reap_idle_containers` / `poll_open_prs` |
| `reassign` / `reject` | 拒绝，要求 `status == pending` |
| `revoke` | 拒绝，只吃 `accepted` |
| `accept` | 拒绝，`pending_gate` 直接报「平台检查还在进行中」 |
| 重新递卡 | 拒绝，`create_card` 见到 `pending_gate` 就抛「已有待处理的验收卡」 |
| `approve` | 唯一接受 `pending_gate` 的接口，但只记一票，不改状态 |

即：**一次后端重启卡在 POST 与闸门落地之间，这个话题就再也递不出验收卡了。**
不只是重启——闸门 task 自身异常退出、worker 被杀，结果一样。

### 「人工放行」具体是哪一步

**没有任何接口能做到，只能改库。** 这一节写死，免得下一个人再推一遍。

最容易想到的 `revoke` 走不通——<&backend/app/domain/review/services.py> 的 `revoke` 第一件事就是：

```python
if card.status != AcceptStatus.accepted:
    raise ValidationError("只有已验收的卡才能撤销")
```

`pending_gate` 直接被挡。`reassign` 同理（`只有待处理的验收卡能改验收人`，要求 `pending`）。
以上按 **main**（线上跑的那份）核过，不是本分支的版本。

放行 = 在盒子上执行：

```sql
UPDATE accept_cards
   SET status = 'pending',
       gate_passed_at = now(),
       gate_output = '闸门任务随后端重启丢失，人工放行'
 WHERE status = 'pending_gate'
   AND created_at < now() - interval '20 minutes';
```

不按 id 写、按「可证明是孤儿」的条件写：`GATE_TIMEOUT_S = 600`，闸门自己最多跑 10 分钟。
`status` 列是 `Enum(..., native_enum=False, length=16)`，库里就是 varchar，直接写字符串即可。
跳过闸门不丢 PR：手工翻到 `pending` 只是跳过 `pr_publish.dispatch`，两阶段采纳那条路是人点
采纳时由 `_accept_via_pr` 开 PR 的。

### 和「门禁SKIP不该判绿」的关系

那个话题改的是**跑完之后 exit code 怎么归类**（exit 2 / -1 → `GateOutcome.blocked` → `gate_blocked`），
前提是 `gate._run` 活到了调 `finish_gate` 那一步。**孤儿卡不满足这个前提**——`_run` 随进程消失，
任何 outcome 都不会产生，`gate_blocked` 同样写不上。所以那个话题不覆盖这一格。
（`GateOutcome` / `gate_blocked` 在本仓和 main 里都搜不到，确认那份代码只在它自己的工作区。）

正确的串法：那个话题落地后，下面第 2 层兜底应该判 `gate_blocked` 而不是 `gate_failed`
——闸门任务丢失是「没有结论」，不是「结论是红」。

**本轮决定（<@wangchangxin> 2026-08-11）：不在本话题修，先人工放行这张卡。** 修复另开话题，
按 turn 那套现成做法做两层：

1. **启动清扫** —— lifespan 里扫出所有 `pending_gate` 的卡重新 `gate.dispatch`（重跑检查幂等），
   位置和形状对齐 `resume_orphans`。
2. **超时兜底** —— scheduler 加一跳，把年龄超过 `GATE_TIMEOUT_S` + 余量的 `pending_gate`
   判成 `gate_failed`（附「闸门任务丢失」），让芝士被 nudge 去重递。

第二层不能省：只有启动清扫的话，进程没重启、只是 task 悄悄死了的情况仍然永久卡死。
