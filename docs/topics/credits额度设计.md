> 面向学院客户的 credits 体系：计价口径、采购量估算方法、代码侧落地现状。

## 当前状态一句话

计价口径的方向已定（credit 锚金额，不锚 token 数），代码侧按 issue #218 设计已全量落地，**唯一缺口是部署配置漏赋值导致线上退化成扁平 token 费率**；产品侧待定的是给学院的采购量估算口径与三级可见性。

## 一、计价口径：credit 锚定金额，不锚定 token 数

「1 credit = N tokens」在编程 Agent 负载下会立刻失真——同样 100 万 token，成本能差 50 倍：

| 维度 | 相对价格差异 |
|---|---|
| output vs input token | ~5x |
| cache write vs input | ~1.25x |
| cache read vs input | ~0.1x |
| 高端模型 vs 轻量模型 | ~15–30x |

编程 Agent 恰恰是这些维度波动最剧烈的负载（长上下文 + 高 cache 命中 + output 占比不定）。按裸 token 计价，要么亏在 output 多的任务上，要么客户觉得「同样的活儿怎么贵了 3 倍」。

**结论：credit 锚定金额（`1 credit = $X`），token 通过真实 spend 折算。**

好处是模型换代、供应商调价时只改单价，客户手里的 credit 面值不漂——锚 token 数的话，换个便宜模型等于凭空发钱，换贵模型等于偷偷涨价，两边都是信任问题。

## 二、代码侧现状：issue #218 的 A/B/C/D 四段均已落地

按 `docs/plans/2026-08-10-usage-unification-design.md` 设计：

- route 列
- 订阅侧 `usage.jsonl` 恰好一次入账
- `POST /llm/admission` 准入
- 仓库化的计量代理
- 额度换算与耗尽文案（<&backend/app/domain/usage/credits.py>）

换算函数已实现**双轨**：网关路由且配置了单价时，按 gateway 的**真实 spend**（含 cache 折扣）换算——缓存命中越高烧得越少，且 app 层额度闸与 gateway 的 `max_budget` 刹车完全对齐（两者都是 `credits × price`）；否则回退到扁平 token 费率。

## 三、唯一缺口：`LLM_GATEWAY_CREDIT_USD` 未赋值

`deploy/` 全库无赋值，`settings.llm_gateway_credit_usd` 默认 `None`，后果：

1. `usage_to_credits` **永远走回退分支**，即 `compute_credit_tokens` 默认的 **1 credit = 10k tokens** 扁平费率——正是上面第一节判定会失真的做法
2. gateway 的 `max_budget` 刹车**从未激活**，成本上没有硬闸

设计文档给的取值 **≈ 0.04（USD / credit）**。这是部署配置问题，不是代码问题。

## 四、给学院的采购量估算

学院采购量本质是一个乘法：

```
总量 = Σ(每门课) 学生数 × 作业次数 × 生均单次消耗 × 冗余系数
```

前两项学院自己就有（选课人数、教学大纲），作业次数问任课老师。**唯一未知量是「生均单次作业消耗」**——整个估算问题归结为标定这一个数。

### 标定方法（按可信度排序）

| 方法 | 做法 | 适用 |
|---|---|---|
| **A. 标杆试跑** | 学院给 2–3 份真实作业题，助教用平台完整做一遍参考解法，记录消耗 `B`；生均单次 ≈ `B × 学生倍率` | 最实用，成本最低 |
| **B. 试点班** | 一门课一个班跑完一学期，拿真实生均消耗外推全院 | 最准，需要一学期 |
| **C. 同类课程参考表** | 跨学院积累数据兜底 | 无任何基线时 |

**学生倍率**来自走弯路、重试、需求理解偏差、反复调试，经验区间 **2.5–4**（基础课取高值，高年级取低值）。这是最该用真实数据校准的参数，校准好整套估算就立住了。

### 算例（数字为示例，需用真实数据替换）

《软件工程》60 人，一学期 6 次编程作业 + 1 个课程设计：

| 项 | 值 |
|---|---|
| 标杆试跑（中等作业参考解法） | 40 credits |
| 学生倍率 | ×3 |
| 生均单次作业 | 120 credits |
| 6 次作业 | 720 |
| 课程设计（≈3 次作业量） | 360 |
| **生均学期消耗** | **1,080 credits** |
| × 60 人 | 64,800 |
| × 冗余 1.3 | **≈ 84,000 credits** |

学院拿到的结论只有一句话：**该课生均约 1,100 credits/学期，折合 ¥XX**。「生均成本」正是高校预算审批的通用语言。

### 冗余系数

个体学生用量长尾很重（P90/P50 可达 3 倍），但**班级总量是聚合值，大数定律下方差收敛**：

| 采购规模 | 建议冗余 |
|---|---|
| 单班 ≤30 人 | +40% |
| 单课 60–100 人 | +30% |
| 全院多课合并 | +20% |

这条也是**建议学院整体采购而非逐课采购**的真实论据——合并后波动互相抵消，需要的冗余更少，总价反而更低。

### 用合同结构消化「估不准」

估不准是必然的，真正解决问题的是采购结构：

1. **底量 + 预授权追加包**：先买覆盖 P50 的保守量，框架协议预先约定追加单价与触发条件。高校学期中追加预算走审批几乎走不通，但协议里写好后，追加就从「采购事项」降级为「执行事项」。
2. **首学期按实结算 / 多退少补**：平台承担一学期不确定性，换来消除学院最大顾虑（买多浪费退不掉、买少中途加不上）+ 拿到该学院自己的用量基线，第二学期起可精确报价。
3. **明确「宁多勿少」**：买多的后果是余额闲置（可结转），买少的后果是**学期中教学中断**。代价不对称，应主动讲给学院听。

### 交付物形态

给学院的是一页纸 + 一个可改参数的估算器（Excel 或在线）：课程清单表（填人数/作业次数 → 自动算需求）、一句话结论（全院 X credits/学期，生均 ¥Z）、两条保障条款（追加机制 + 结转/清算规则）。**让教务自己算出来的数，比我们给的数更容易通过审批。**
