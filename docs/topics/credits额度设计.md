> 面向学院客户的 credits 体系：计价口径、采购量估算方法、代码侧落地现状。

## 当前状态一句话

计价口径的方向已定（credit 锚金额，不锚 token 数），代码侧按 issue #218 设计已全量落地，**唯一代码/部署缺口是 `LLM_GATEWAY_CREDIT_USD` 漏赋值导致线上退化成扁平 token 费率**（已拆子话题去修）。

真实用量锚点：生均约 **10,000 credits/学期**，一门 100 人的课约 **¥29 万/学期**。学院计划最大出资 **¥70 万**，该量级可承受——**卖 credit 的模式成立**，但 70 万按当前强度只够约 **2 门 100 人的课（单学期）**，且学院出资后学生停止自费会使需求回流并进一步上涨。因此核心命题不是「能不能卖」，而是 **成本压缩 + 覆盖范围取舍**。待确认：70 万的周期与拟覆盖课程数。

## 一、计价口径：credit 锚定金额，不锚定 token 数

「1 credit = N tokens」在编程 Agent 负载下会立刻失真——同样 100 万 token，成本能差 50 倍：

| 维度 | 相对价格差异 |
|---|---|
| output vs input token | ~5x |
| cache write vs input | ~1.25x |
| cache read vs input | ~0.1x |
| 高端模型 vs 轻量模型 | ~15–30x |

编程 Agent 恰恰是这些维度波动最剧烈的负载（长上下文 + 高 cache 命中 + output 占比不定）。按裸 token 计价，要么亏在 output 多的任务上，要么客户觉得「同样的活儿怎么贵了 3 倍」。

**结论：credit 锚定金额（`1 credit = $X`），token 通过真实 spend 折算。**

好处是模型换代、供应商调价时只改单价，客户手里的 credit 面值不漂——锚 token 数的话，换个便宜模型等于凭空发钱，换贵模型等于偷偷涨价，两边都是信任问题。

## 三、唯一缺口：`LLM_GATEWAY_CREDIT_USD` 未赋值

`deploy/` 全库无赋值，`settings.llm_gateway_credit_usd` 默认 `None`，后果：

1. `usage_to_credits` **永远走回退分支**，即 `compute_credit_tokens` 默认的 **1 credit = 10k tokens** 扁平费率——正是上面第一节判定会失真的做法
2. gateway 的 `max_budget` 刹车**从未激活**，成本上没有硬闸

设计文档给的取值 **≈ 0.04（USD / credit）**。这是部署配置问题，不是代码问题。

## 四、给学院的采购量估算

学院采购量本质是一个乘法：

```
总量 = Σ(每门课) 学生数 × 作业次数 × 生均单次消耗 × 冗余系数
```

前两项学院自己就有（选课人数、教学大纲），作业次数问任课老师。**唯一未知量是「生均单次作业消耗」**——整个估算问题归结为标定这一个数。

### 标定方法（按可信度排序）

| 方法 | 做法 | 适用 |
|---|---|---|
| **A. 标杆试跑** | 学院给 2–3 份真实作业题，助教用平台完整做一遍参考解法，记录消耗 `B`；生均单次 ≈ `B × 学生倍率` | 最实用，成本最低 |
| **B. 试点班** | 一门课一个班跑完一学期，拿真实生均消耗外推全院 | 最准，需要一学期 |
| **C. 同类课程参考表** | 跨学院积累数据兜底 | 无任何基线时 |

**学生倍率**来自走弯路、重试、需求理解偏差、反复调试。经验区间 **10–15**（基础课取高值，高年级取低值）——这是被真实锚点校准后的值，早先的 2.5–4 已证实系统性低估约 10 倍，详见下文《方法论修正》。

### 算例（演示公式用法；倍率已按修正后的 12 取值）

《软件工程》60 人，一学期 6 次编程作业 + 1 个课程设计：

| 项 | 值 |
|---|---|
| 标杆试跑（中等作业参考解法） | 40 credits |
| 学生倍率 | ×12 |
| 生均单次作业 | 480 credits |
| 6 次作业 | 2,880 |
| 课程设计（≈3 次作业量） | 1,440 |
| **生均学期消耗** | **4,320 credits** |
| × 60 人 | 259,200 |
| × 冗余 1.3 | **≈ 337,000 credits** |

学院拿到的结论只有一句话：**该课生均约 4,300 credits/学期，折合 ¥XX**。「生均成本」正是高校预算审批的通用语言。

### 冗余系数

个体学生用量长尾很重（P90/P50 可达 3 倍），但**班级总量是聚合值，大数定律下方差收敛**：

| 采购规模 | 建议冗余 |
|---|---|
| 单班 ≤30 人 | +40% |
| 单课 60–100 人 | +30% |
| 全院多课合并 | +20% |

这条也是**建议学院整体采购而非逐课采购**的真实论据——合并后波动互相抵消，需要的冗余更少，总价反而更低。

### 超额使用与尾部风险：靠 cap 截断，不靠冗余系数

上面「方差随人数收敛」有两个前提在本场景都不成立：分布**重尾**（个别学生做到中位数的 10–20 倍是正常的），且个体**不独立**（同一次作业、同一个坑、同一个 DDL）。因此把冗余从 +30% 加到 +80% 本质是在猜一个猜不准的数——尾部长度取决于最极端的几个学生，不取决于平均值。

正确解法是**不预测他们会用多少，而是设定他们最多能用多少**。有硬上限时总量有确定上界（`≤ 人数 × cap`），估算从「预测」变成「设计」：

| | 无 cap | 有 cap（2× 基准） |
|---|---|---|
| 班级实际总量 | 人数 × 基准 × (0.8 ~ 5+) | 人数 × 基准 × (0.8 ~ 1.3) |
| 需要的冗余 | 300% 都可能不够 | 30% 足够 |

三层限额：

1. **软线（基准 X）**：提示学生、通知老师，**不阻断**
2. **硬线（约 2X）**：需老师批准才能继续
3. **技术熔断（单 turn / 单日）**：防的不是「学生用得多」而是 **Agent 死循环**——一个学生一晚烧掉全班预算不是超额使用，是事故。这层与额度体系相互独立，必须单独存在。

cap 的位置取 `标杆试跑 × 学生倍率上界(15) × 安全余量` ≈ 基准的 2 倍，作用是防失控**不是**省钱。第一学期建议放宽到 3× 用于观测真实分布，拿到数据后再收——第一学期收太紧的代价（教学中断 + 学院不满）远大于超支。

配套告警：单学生触软线 → 通知老师；**单学生单日消耗 > 班级 P95 → 立即告警**（死循环最可靠的信号）；课程池消耗速度 > 剩余周数推算值 → 提前预警学院，留出走追加流程的时间。

### 首个真实锚点（2026-08，caisongyang 提供）

某《计算机系统基础》课，**100 人**，一学期 **4 个大作业**，平台侧订阅 codex 中转站 **$400/月**「够用」，但**几乎所有学生都额外自费购买了其他套餐**。

按面值 `1 credit = $0.04`、学期 4 个月直接换算：`$1,600/学期 = 40,000 credits`，生均仅 **400 credits/学期**。

**这个数不能当基线用**——它测的是「学生自费补足之后，平台侧的残余部分」，而非真实需求。学生几乎全员自费，说明学院侧供给严重不足，且被挪走的恰恰是尾部重度用量。

补充事实：学生自费的套餐**很多是 $60/月的官方订阅，且用量大**（已确认为官方订阅，非中转站转售）。

据此反推——学生侧支出 `$60 × 100 = $6,000/月`；官方订阅对重度用户是**亏本补贴**的，按 API 价折算的补贴系数取 2.5–4；归属本课比例 50–70%；再加平台侧 $400：

| 口径 | 月真实 token 成本 | 学期 credits（100 人） | 生均/学期 |
|---|---|---|---|
| 平台侧观测值 | $400 | 40,000 | 400 |
| 按 $60 官方订阅（下界） | ~$8,000 | ~800,000 | ~8,000 |
| 按 $60 官方订阅（上界） | ~$17,000 | ~1,700,000 | ~17,000 |

**规划基线取生均 10,000 credits/学期** → 100 人班约 1,000,000 credits ≈ **$40,000/学期（≈¥29 万）**。

平台侧观测到的 $400/月，只占真实需求的约 **5%**。

### 方法论修正：学生倍率应取 10–15，不是 2.5–4

早先按「标杆试跑 × 学生倍率 2.5–4」推出生均 1,080，与实测口径（生均约 10,000）差 **约 10 倍**，是倍率给低了。上文算例与冗余小节已按修正值重算。标杆试跑测的是「助教已知正确解法、一次做对」的消耗，而学生是反复试错、走死胡同、推倒重来、开放式探索——系统课尤甚。**学生倍率经验值统一上调到 10–15**，否则每次报价都会系统性低估。

同时注意：4 个大作业**不能均分预算**。CSAPP 系课程里 datalab/bomblab/attacklab 有 autograder、终止条件清晰，用量可控；malloclab、性能优化这类开放式调优没有自然终止点，用量可达前者的 5–10 倍，应单独设预算。

## 五、经济性边界：¥70 万预算能覆盖什么

学院计划最大出资 **¥70 万**（周期待确认）。按生均 10,000 credits/学期换算（`× $0.04 = $400/人·学期 ≈ ¥2,880`）：

| 情景 | 生均 credits/学期 | 生均成本 | ¥70 万可覆盖 |
|---|---|---|---|
| 当前强度 | 10,000 | ¥2,880 | **~243 人·学期** |
| 计入免费化后的用量上涨（+40%） | 14,000 | ¥4,030 | **~174 人·学期** |
| 成本压缩至 40% | 5,600 | ¥1,610 | ~434 人·学期 |
| 成本压缩至 30% | 4,200 | ¥1,210 | ~580 人·学期 |

**关键预期差**：¥70 万听起来很多，但按当前强度只够 **2 门 100 人的课，且是单学期、无冗余**。如果 70 万是一学年预算，连 1 门课都紧张。学院多半以为这笔钱能覆盖整个院系——这个落差必须在谈判前就讲清楚，否则第一学期中途爆预算，信任直接崩掉。

### 学院出资会推高用量，不能按当前观测值规划

前面测到的生均 10,000 是「学生自费 + 平台侧」的合计需求。学院一旦足额供给，会发生两件事：

1. **需求回流**：学生停止自费，原本跑在个人订阅上的用量全部压到学院池
2. **克制解除**：自费时学生会省着用，免费后不会。经验增量 **30–50%**

所以规划口径应取 **生均 14,000 credits/学期**，而不是 10,000。

### 成本压缩是主杠杆：压一半 = 覆盖人数翻倍

从上表看，成本压缩直接线性放大覆盖范围，这已经不是技术优化而是商业核心：

1. **模型分层路由**：并非每个 turn 都需要最贵的模型。读文件、跑测试、格式化、简单修复走轻量档，复杂推理才上高端档。这一项通常能省 **50–70%**。
2. **跨学生前缀缓存（教育场景独有的结构性红利）**：一个班 100 个学生做**同一个作业**，题目描述、starter code、参考文档、评分标准完全相同。cache read 比 input 便宜约 10 倍，若能把这段公共前缀做成跨学生共享的缓存命中，成本下降幅度会非常可观。**这是通用编程 Agent 场景拿不到、教育场景独有的优势，值得优先投入。**
3. **cap 截断尾部**：见上文三层限额，防止个别学生吃掉整池。

### BYOK：从「唯一出路」降级为「扩大覆盖的可选项」

既然学院出得起，BYOK 不再是必需。但混合模式仍有价值——学院池覆盖基础用量，学生自有订阅承接溢出，可让 ¥70 万覆盖更多人。代价是重新引入教育公平问题（自费者占优），需要保底池对冲。

前置风险不变：**多数厂商的订阅条款限制额度只能在官方客户端使用**。本仓库 <&backend/app/core/config.py> 里 `claude_oauth_token` 的注释已经点到这条线——个人 Max/Pro 席位标注为「ToS-compliant **for dogfooding**」，且明确写着 `Not the multi-user product path`。若要走混合模式，须逐厂商核实条款。

### 建议的分配策略

在 ¥70 万这个盘子下：

- **先窄后宽**：第一学期只覆盖 1–2 门课，把它做深做透（拿到真实分布、验证 cap 取值、验证缓存红利），而不是撒到全院每门课都不够用
- **优先选课程结构清晰的课**：有 autograder、终止条件明确的作业（datalab/bomblab 类）成本可控，开放式调优类（malloclab、性能优化）单独设预算
- **预留 20% 不分配**：作为应急池，应对个别学生失控和课程设计阶段的集中爆发

### 用合同结构消化「估不准」

估不准是必然的，真正解决问题的是采购结构：

1. **底量 + 预授权追加包**：先买覆盖 P50 的保守量，框架协议预先约定追加单价与触发条件。高校学期中追加预算走审批几乎走不通，但协议里写好后，追加就从「采购事项」降级为「执行事项」。
2. **首学期按实结算 / 多退少补**：平台承担一学期不确定性，换来消除学院最大顾虑（买多浪费退不掉、买少中途加不上）+ 拿到该学院自己的用量基线，第二学期起可精确报价。
3. **明确「宁多勿少」**：买多的后果是余额闲置（可结转），买少的后果是**学期中教学中断**。代价不对称，应主动讲给学院听。

### 交付物形态

给学院的是一页纸 + 一个可改参数的估算器（Excel 或在线）：课程清单表（填人数/作业次数 → 自动算需求）、一句话结论（全院 X credits/学期，生均 ¥Z）、两条保障条款（追加机制 + 结转/清算规则）。**让教务自己算出来的数，比我们给的数更容易通过审批。**
