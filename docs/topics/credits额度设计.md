## 一、计价口径：credit 锚定金额，不锚定 token 数

「1 credit = N tokens」在编程 Agent 负载下会立刻失真——同样 100 万 token，成本能差 50 倍：

| 维度 | 相对价格差异 |
|---|---|
| output vs input token | ~5x |
| cache write vs input | ~1.25x |
| cache read vs input | ~0.1x |
| 高端模型 vs 轻量模型 | ~15–30x |

编程 Agent 恰恰是这些维度波动最剧烈的负载（长上下文 + 高 cache 命中 + output 占比不定）。按裸 token 计价，要么亏在 output 多的任务上，要么客户觉得「同样的活儿怎么贵了 3 倍」。

**结论：credit 锚定金额（`1 credit = $X`），token 通过真实 spend 折算。** 设计取值 `$0.04 / credit`。

好处是模型换代、供应商调价时只改单价，客户手里的 credit 面值不漂——锚 token 数的话，换个便宜模型等于凭空发钱，换贵模型等于偷偷涨价，两边都是信任问题。

## 二、额度的产品形态

### 2.1 分配模型：软配额 + 课程池共享

不做「老师把额度切成 100 份分给 100 个学生」。切死了必然有人不够有人剩下，而调剂动作全压在老师身上。

正确形态是**老师只设一个数：每人基准额度 X**，底层始终是一个课程池：

| 状态 | 行为 |
|---|---|
| 学生用量 < X | 正常，无感知 |
| 学生用量 > X（软线） | 提示学生 + 通知老师，**不阻断**——从池子自动借 |
| 学生用量 > 2X（硬线） | 需老师批准才能继续 |
| **课程池见底** | 这时才真正阻断，而该找的是**学院**，不是学生 |

「提示学生」起约束作用，「通知老师」起教学信号作用，但都不挡路。这条设计的第一原则是：**绝不能让 credit 余额变成影响成绩的变量。**

### 2.2 心智单位是「作业」，不是「学期」

老师是按 assignment 布置任务的，额度预算也应该按 assignment 建，而不是学期初一次性分完。

好处有三：老师的心智负担从「估一学期」降到「估一次作业」，后者他真的有直觉；每次作业结束都拿到一次实测数据，第 2 次作业的额度就能用第 1 次的真实分布来定；开放式作业（malloclab、性能优化）可以单独给高预算，而不必把整学期的额度都抬高。

### 2.3 任务级预算上限与实时反馈

在单个任务这一层也要有闸：

- **启动前给预估区间**：基于同类任务历史分布，告诉用户「这个任务预计消耗 30–80 credits」。没有预估，客户设 cap 就是瞎设。
- **客户可设任务 cap**：超了**暂停并询问是否继续**，而不是直接失败。暂停可续是关键——直接失败会丢掉已完成的工作。
- **实时消耗显示**：任务执行中可见当前已消耗，不是事后账单。
- **余额 80% / 95% 两级预警**：分别对应「该准备追加了」和「该走流程了」，留出高校审批需要的时间。

### 2.4 硬熔断：单任务 / 单日上限

**这一层必须有，是事故级风险。**

它防的不是「学生用得多」，而是 **Agent 死循环**——一个学生一晚烧掉全班预算不是超额使用，是事故。因此这层与整个额度体系**相互独立**：即使额度充足、即使老师批准过、即使课程池还满着，单任务和单日上限照样生效。

配套告警里最可靠的死循环信号是：**单学生单日消耗 > 班级 P95**。

### 2.5 应急额度通道

学生一键申请 + 老师一键批准。**更好的做法是小额自动批准 + 事后审计**：单次追加不超过基准的 20%，一学期最多 3 次，自动通过，老师只在报表里看到。

理由还是第一原则——老师半夜不回消息、学生作业交不上，这种事发生一次，这门课下学期就不会再用我们的平台。自动批准的额度上限（20% × 3 次 = 60%）已经被 2.1 的硬线兜住，不存在失控空间。

## 三、老师怎么定基准额度 X：让他跑一遍，别让他估

**这是最该做的功能。** 老师对「一次作业要烧多少 credit」没有任何直觉，让他估等于让他猜，猜错的代价由学生承担。

正确流程：

```
老师/助教用平台把这次作业的参考解法完整做一遍
      ↓
平台记录实际消耗 B
      ↓
自动推荐学生基准额度 X = B × 学生倍率
```

**学生倍率取 4–6**（基础课取高值，高年级取低值）。倍率的来源是学生会走弯路、重试、需求理解偏差、反复调试，而助教是已知正确解法一次做对。

> ⚠️ **倍率取值的修正链条**：早先文档里写过倍率应取 10–15，那个数是从「一门课 ¥29 万」反推出来的；而 ¥29 万本身已被推翻（见 §6.5）。反推的前提没了，倍率也要回到自下而上的估计。初始建议 **4–6**，第一次作业跑完后用真实分布替换掉这个经验值——这正是 §2.2「按作业建预算」的价值所在。

这个功能同时是**给老师的教学工具**：如果参考解法本身就烧掉大量 credit，说明题目描述不清或难度失控，这是在学生受影响之前就能拿到的教学反馈。

## 四、老师仪表盘：展示教学信号，不是余额

纯粹的额度管理界面，老师只会觉得是负担。要展示的是他真正关心的东西：

| 展示项 | 教学价值 |
|---|---|
| **谁还没开始动** | 比余额有用得多的早期预警 |
| **班级消耗分布，离群点是谁** | 谁遇到了真困难 |
| **哪次作业整体超预期** | 说明题目太难或描述不清——给老师的教学反馈 |
| **卡在同一个错误上反复消耗的学生** | 需要人工介入的精确定位 |

把 credit 管理包装成教学工具，老师才有动力用它。

## 五、过程可审计性：学院愿意采购的真正理由

我们的定位是「AI 完成整个编程任务」。用在教学场景，教务和任课老师一定会问：**那作业还有意义吗？**

这既是最大阻力，也是相对通用 AI 工具的**最大差异化机会**：

- 通用工具（学生自己开个 Claude/Copilot）**管不着，学生照样用，而且完全不可见**
- 我们的平台可以提供**过程可审计性**：学生的 prompt 记录、交互轮次、是否理解产出、遇到哪些错误、改了几轮

把这个做成**「AI 使用过程报告」**，老师能看到「这个学生问了 15 轮、自己调试了 3 个错误」和「那个学生一句话贴过去直接交」的区别。

**这比 credit 管理值钱得多，也是学院愿意采购的真正理由。credit 只是这套东西的副产品和成本闸门。**

## 六、给学院的采购量估算

### 6.1 公式

```
总量 = Σ(每门课) 学生数 × 作业次数 × 生均单次消耗 × 冗余系数
```

前两项学院自己就有（选课人数、教学大纲），作业次数问任课老师。**唯一未知量是「生均单次作业消耗」**——整个估算问题归结为标定这一个数。

### 6.2 标定方法（按可信度排序）

| 方法 | 做法 | 适用 |
|---|---|---|
| **A. 标杆试跑** | 助教用平台完整做一遍参考解法，记录消耗 `B`；生均单次 ≈ `B × 4~6`（见 §3） | 最实用，成本最低 |
| **B. 试点班** | 一门课一个班跑完一学期，拿真实生均消耗外推全院 | 最准，需要一学期 |
| **C. 同类课程参考表** | 跨学院积累数据兜底 | 无任何基线时 |

### 6.3 算例

《软件工程》60 人，一学期 6 次编程作业 + 1 个课程设计：

| 项 | 值 |
|---|---|
| 标杆试跑（中等作业参考解法） | 40 credits |
| 学生倍率 | ×5 |
| 生均单次作业 | 200 credits |
| 6 次作业 | 1,200 |
| 课程设计（≈3 次作业量） | 600 |
| **生均学期消耗** | **1,800 credits** |
| × 60 人 | 108,000 |
| × 冗余 1.3 | **≈ 140,000 credits** |

学院拿到的结论只有一句话：**该课生均约 1,800 credits/学期，折合 ¥XX**。「生均成本」正是高校预算审批的通用语言。

### 6.4 冗余系数

| 采购规模 | 建议冗余 |
|---|---|
| 单班 ≤30 人 | +40% |
| 单课 60–100 人 | +30% |
| 全院多课合并 | +20% |

这条也是**建议学院整体采购而非逐课采购**的真实论据——合并后波动互相抵消，需要的冗余更少，总价反而更低。

但要注意：「方差随人数收敛」有两个前提在本场景**都不成立**——分布**重尾**（个别学生做到中位数的 10–20 倍是正常的），且个体**不独立**（同一次作业、同一个坑、同一个 DDL）。所以尾部风险不能靠加大冗余解决，只能靠 §2.1 的 cap 截断：

| | 无 cap | 有 cap（2× 基准） |
|---|---|---|
| 班级实际总量 | 人数 × 基准 × (0.8 ~ 5+) | 人数 × 基准 × (0.8 ~ 1.3) |
| 需要的冗余 | 300% 都可能不够 | 30% 足够 |

有硬上限时总量有确定上界（`≤ 人数 × cap`），估算从「预测」变成「设计」。**第一学期建议把硬线放宽到 3× 用于观测真实分布**，拿到数据后再收——第一学期收太紧的代价（教学中断 + 学院不满）远大于超支。

### 6.5 真实锚点与一次重要修正

**观测事实**（2026-08，caisongyang 提供）：某《计算机系统基础》课，**100 人**，一学期 **4 个大作业**，平台侧订阅 codex 中转站 **$400/月**「够用」；**几乎所有学生都额外自费购买了官方订阅，很多是 $60/月且用量大**。

> **已推翻的推算**：早先由「学生自费金额 × 补贴系数 × 归属比例」反推出生均 10,000 credits/学期、一门课 ¥29 万。这个方法**不成立**，原因有二：
> 1. **订阅制下「买」≠「用」**。学生付 $60 很大程度是为了买速率上限和更好的模型档，不代表把等值的 token 跑完了。
> 2. **归属比例取 50–70% 太高**。同一个订阅还服务其他 5 门课和个人项目。
>
> 顺带说明：$400/月对应约 $1/人·月 ≈ 400 credits/学期，**恰好落在下面自下而上估算的下沿**——所以「够用」很可能是字面意义上的够用，早先把它解读成「学生自费后的残余需求」是过度推断。

**改用自下而上按 turn 成本建模**（上下文规模 × cache 命中率 × output tokens × 分档单价）：

| 模型档（**并列待选，非既定**） | 生均/学期 | 一门课（100 人） | ¥70 万可覆盖 |
|---|---|---|---|
| 国产档（GLM / DeepSeek / Qwen 等） | ~160 credits（≈¥50） | ≈¥5,000 | 100+ 门课 |
| Claude Sonnet 级 | ~1,600 credits（≈¥450） | ≈¥4.5 万 | ~15 门课 |
| Claude Opus 级 | ~7,900 credits（≈¥2,270） | ≈¥23 万 | ~3 门课 |

> 两处待坐实：国产档按「约为 Claude 的 1/10」估算，需核实际单价；且这是**单价比**，真实成本比要计入弱模型多走弯路的 turn 数（见 §7.1.1）。选哪一档是 §11 的待拍板项。

**同时注意**：4 个大作业**不能均分预算**。CSAPP 系课程里 datalab/bomblab/attacklab 有 autograder、终止条件清晰，用量可控；malloclab、性能优化这类开放式调优没有自然终止点，用量可达前者的 5–10 倍，应单独设预算（这正是 §2.2 按作业建预算的用武之地）。

## 七、成本结构与经济性边界

### 7.1 决定成本的是模型档，不是学生行为

§6.5 那张表的核心结论：**同样的教学场景，模型档之间差 5–50 倍，直接决定 ¥70 万是覆盖 3 门课还是 100 门课。** 学生用多用少的波动（±40%）在这个量级面前是次要项。

**因此模型档是本方案最大的未决项，且它是一个待做的产品决策，不是可以从现状继承的前提。**

> ⚠️ 代码里 <&backend/app/domain/agent/profiles.py> 的 `TIER_DEFAULT` 目前指向 GLM pool，注释写的是 `the configured pool (**GLM today**)`，且 operator 可改（文件末尾有「pool 干涸时指向别处」的兜底）。这是**当前部署配置**，不代表教学场景该用哪个档。早先文档里据此断言「¥70 万不是约束条件」是把因果搞反了，已删除。

真正要回答的问题是：**教学质量需要哪个档？** 这是教学问题，答案决定预算，而不是反过来。

### 7.1.1 成本比 ≠ 价格比

选档时不能直接拿价目表算账。弱模型在编程 Agent 负载下会**多走弯路**——改错文件、测试跑不过、反复重试，turn 数上去，单价优势被吃掉一部分。极端情况下便宜模型总成本反而更高。

教学场景尤其要注意：开放式调优类作业（malloclab、性能优化）没有自然终止点，**正是弱模型最容易打转的地方，而打转又恰恰是最烧钱的形态**。

结论：**分档的真实成本比必须实测**，做法就是 §6.2 的标杆试跑——同一份作业在各档各跑一遍，比较「总成本 + 是否做对 + 花了几轮」。这是当前最该做的一次测量。

### 7.2 一个候选产品设计：credits 作为高端档的配额

**前提**：存在一个「便宜且教学上够用」的基础档。这个前提**尚未验证**（见 §7.1.1），如果不成立，本节作废、回到总量闸模型。

若前提成立，额度体系的定位可以调整为：

- **基础档（GLM）不限量**，学生放开用
- **高端档（Claude/GPT）按 credits 配额**，学生自己决定什么时候「花掉一次好模型」

这个设计同时解决三件事：成本天然可控；学生有动机**先自己想清楚再调最强模型**，而不是无脑顶格用；老师能从「高端档消耗分布」看出谁真的卡住了、卡在哪——正好接上 §4 的教学信号。

### 7.3 成本压缩杠杆

1. **模型分层路由**：读文件、跑测试、格式化、简单修复走轻量档，复杂推理才上高端档。通常省 **50–70%**。
2. **跨学生前缀缓存（教育场景独有的结构性红利）**：一个班 100 个学生做**同一个作业**，题目描述、starter code、参考文档、评分标准完全相同。cache read 比 input 便宜约 10 倍。**这是通用编程 Agent 场景拿不到的优势，值得优先投入。**
3. **cap 截断尾部**：见 §2.1。

### 7.4 共用订阅 plan：不做

有过「多个学生共用订阅 plan、假定每 plan 用 50% token」的提议。**建议直接排除：**

- **明确违反 ToS**。Claude Pro/Max、ChatGPT Plus/Pro 都是个人席位，多人共用不是灰色地带。学期中途封号 = 教学事故；平台作为服务方**主动组织**共享，风险等级远高于学生个人违规；学院是机构客户，合规是硬门槛。本仓库 <&backend/app/core/config.py> 里已经画过这条线——`claude_oauth_token` 标注为「ToS-compliant **for dogfooding**」且明确写着 `Not the multi-user product path`。
- **经济上也未必划算**。按 50% 利用率：$60 plan 若按 API 价折算值 $150（补贴系数 2.5），打五折后实际发挥 $75——相对直接买 API 只省 20%，却背了封号风险。
- **而且不需要**。§7.1 已说明默认档本来就便宜一个数量级，合规路径（教育折扣、团队版席位、国产模型）能拿到同等甚至更大的成本优势。

### 7.5 BYOK：可选的覆盖扩展项

学院池覆盖基础用量、学生自有订阅承接溢出，可让预算覆盖更多人。代价是重新引入教育公平问题（自费者占优），需要保底池对冲。前置条件是逐厂商核实订阅条款——多数厂商限制额度只能在官方客户端使用。

## 八、报价与合同结构

### 8.1 计价单位

用**「生均 credits / 学期」**，这是学院财务能理解和审批的单位。**别让他们算 token。**

### 8.2 用合同结构消化「估不准」

不要试图一次估准，估不准是必然的。真正解决问题的是采购结构：

1. **底量 + 预授权追加包**。学院先买覆盖 P50 的保守量，框架协议里预先约定追加单价和触发条件。这条对高校**极其关键**——学期中追加预算走审批流程几乎走不通，但协议里已写好的话，追加就从「采购事项」降级为「执行事项」，一个电话就能加。
2. **首学期按实结算 / 多退少补**。预付一个额度，学期末据实清算。我们承担一学期的不确定性，换来两样东西：消除学院最大的采购顾虑（怕买多浪费又退不掉），以及拿到这个学院自己的用量基线。第二学期起就能精确报价。
3. **明确讲「宁多勿少」的理由**。买多的后果是余额闲置（可结转），买少的后果是**学期中教学中断**。两者代价不对称，应该主动讲给学院听。它确实会让我们卖得更多，但理由是成立的。

### 8.3 分配策略

- **先窄后宽**：第一学期只覆盖 1–2 门课做深做透（拿真实分布、验证 cap 取值、验证缓存红利），而不是撒到全院每门课都不够用
- **优先选课程结构清晰的课**：有 autograder、终止条件明确的作业成本可控；开放式调优类单独设预算
- **预留 20% 不分配**：应急池，应对个别学生失控和课程设计阶段的集中爆发

### 8.4 交付物形态

一页纸 + 一个可改参数的估算器（Excel 或在线）：课程清单表（填人数/作业次数 → 自动算需求）、一句话结论（全院 X credits/学期，生均 ¥Z）、两条保障条款（追加机制 + 结转/清算规则）。

**让教务自己算出来的数，比我们给的数更容易通过审批。**

## 九、几个坑

1. **学期开头空、DDL 前爆炸**。消耗曲线会极度不均——作业截止前 48 小时可能是平时的 20 倍。这既是容量规划问题，也意味着**「按月均摊」的思路在这里不成立**。
2. **学生用平台干私活**。需要按课程/仓库范围做限制，至少要能审计出来。
3. **别把省 credit 变成学生的行为目标**。如果学生开始为了省额度而不敢让 AI 多跑，这门课的教学效果就被计费机制扭曲了。**这是额度要给得宽松、阻断要尽量少的根本理由**，也是 §2.1 全部设计的出发点。

## 十、代码侧现状

按 `docs/plans/2026-08-10-usage-unification-design.md`，issue #218 的 A/B/C/D 四段均已落地：route 列、订阅侧 `usage.jsonl` 恰好一次入账、`POST /llm/admission` 准入、仓库化的计量代理、额度换算与耗尽文案（<&backend/app/domain/usage/credits.py>）、ComputeGrant 发放/扣减。

换算函数已实现**双轨**：网关路由且配置了单价时按 gateway 的**真实 spend**（含 cache 折扣）换算，app 层额度闸与 gateway 的 `max_budget` 刹车完全对齐（两者都是 `credits × price`）；否则回退扁平 token 费率。

**唯一缺口**：`deploy/` 全库无 `LLM_GATEWAY_CREDIT_USD` 赋值，`settings.llm_gateway_credit_usd` 默认 `None`，导致 `usage_to_credits` **永远走回退分支**（1 credit = 10k tokens 扁平费率，正是 §1 判定会失真的做法），且 gateway 的 `max_budget` 刹车**从未激活**。设计取值 ≈ 0.04。这是部署配置问题，不是代码问题，已拆子话题去修。

## 十一、待拍板

1. **模型档（最关键）**：教学场景用哪一档？这是教学质量决策，不能从当前部署配置继承。前置动作是 §7.1.1 的分档实测（同一份作业各档跑一遍，比总成本 / 是否做对 / 花几轮）。定了它，§7.2「credits 作为高端档配额」这套设计才知道成不成立。
2. **¥70 万的周期（一学期 / 一学年）与拟覆盖的课程数**
3. 学生能否自费超额充值（现状是学生已全员自费，涉及教育公平争议，学院可能明确禁止）
4. 按课程采购还是学院整体采购（影响冗余系数与跨课程调剂）
5. 面值 0.04 是否需要重定（官方 API 口径 vs 中转站口径 vs GLM 口径）
6. **优先级**：§5 的过程可审计性可能比整个额度体系更值钱，是否应该前置？

## 十二、需要埋的数据

要产出任何参考表都依赖埋点。每次任务应记录：任务类型、模型分布、四类 token 分别的量、cache 命中率、时长、是否成功、产出是否被接受、重试次数、代码库规模特征。一两个月后这批数据同时是定价依据、客户参考表和成本优化抓手。
