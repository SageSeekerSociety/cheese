### P0-1　分支被重置成空提交 → 空 PR → 空合并　【根因已定位并修复，待合并】

**已发生五次**，前四次进了 main：#608 / #610 / #611 / #618 全部 `changed_files=0 +0/-0`。
第五次就发生在本话题的分支上（`36782a379`）。四次的 PR head 提交签名完全一致：
**message 为空、author 芝士、files 0、单父提交=当时的 main tip**——那正是 jj 新建工作区那个 working-copy commit 的签名。

**根因不是「递卡强推了一个空提交」，而是「递卡顺手新建工作区，而新建工作区把分支拽回了那个空提交」。**

链路：递卡 → `push_topic_branch_for_github_pr` → `snapshot_worktree` → **`_ensure_worktree`**
（<&backend/app/domain/workspace/service.py>）。最后这步原本**无条件**做三件事：

```
jj workspace add ...                          # @ 是一个全新的空 working-copy commit
jj bookmark set <分支> -r @ --allow-backwards  # ← 把分支硬拉到那个空提交
jj git export                                 # ← 写回 git ref
```

`--allow-backwards` 正是关掉 jj「不许把分支往回移」保护的开关。**它的原意是对的**——
一棵全新的树需要有一条分支——**错在没先看一眼分支是不是已经有东西了**。

**分支为什么会先有东西？因为那个目录不是分支唯一的作者。**
跑在托管机器上的分身，文件根本不在后端那份 worktree 里，它只能 git push 经项目 git 代理写分支；
而后端那边可能压根没建过这棵树的目录——**递卡时现建，现建就清空**。

> **这就是为什么「递卡前先手动 push」永远挡不住：清空发生在递卡之后。**

**修法两处**（都在 `workspace/service.py`）：① `_ensure_worktree` 在分支已存在时用
`jj workspace add --revision <分支 sha>` 从分支长出来，且不再动 bookmark（真·新树时行为不变）；
② 新增 `_put_the_branch_under_the_working_copy`，在 `snapshot_worktree` 移动 bookmark 之前
把工作区 rebase 到分支上，于是 bookmark 只可能往前走。

**过程中踩的两个 jj 坑**（都有测试兜着）：不能拿 **git 的 ref** 当分支头
（`prepare_upstream_conflict_resolution` 会把 bookmark 挪到一个还没 export 的 merge 上，
照 git 走会把它 rebase 掉、连带丢 upstream 历史），要问 **jj 的 bookmark**；
以及 **bookmark 可能是 conflicted 状态**，revset 要用 `heads(bookmarks(exact:"<分支>") ~ ::@)` 取全部目标。

验证：4 条新测试**修前全红**（头一条的失败就是 `assert [] == ['src/app.py']`，正是线上症状），
跑真实 git+jj 仓库、只断言裸仓里的文件和分支头；后端全量 **5344 passed / 0 failed**；ruff/pyright 全绿。

**⚠️ 修复合进 main 之前这个 bug 一直是活的：采纳任何 PR 前必须先看 `changed_files` 不是 0。**

## 根因：丢的不是「前一条」，是「没 @ 的那条」

<&backend/app/domain/agent/runtime.py> `AgentWorkRunner.submit_message` 原来对 `summon=False` 只落库、只推前端，**不递给会话**。它本该由下一轮组装 prompt 时的 `_pending_human_blocks()`（<&backend/app/domain/agent/chat.py:1220>）捎带——**但那个窗口只在组装 prompt 时才被读**，而带 @ 的消息在有活轮时走 `merge_into_running_turn`（runtime.py:1484），会话一接住就 return，根本不组装。于是话题只要还在干活，没 @ 的那条就永远排在一个不会到来的时刻后面。它没被标 consumed，严格说是无限期延后不是删除；但芝士在回答一句它没看到的话，那就是丢。

方向性因此得解：**不是「先/后」，是「有没有 @」**。人的节奏是先说事、再补一个光秃秃的 @。

## 10:21 那条 system 事件不是同一回事（你要的第二个答案）

它是 `PROMPT_UNDELIVERED`（<&backend/app/domain/agent/platform_failures.py:196>），由 <&backend/app/domain/agent/harness/claude_code/hooks_substrate.py:410> 的投递看门狗在 `DELIVERY_TIMEOUT_S = 25.0` 秒内收不到任何 hook 时发出。10:21:04 → 10:21:31 正好 27 秒。三条证据说明不同源：①它组装了新 prompt（看门狗只盯新 prompt，merge 路径不经过它）→ 当时没走 merge → pending 窗口被读了，10:20:58 那条**在 prompt 里**；②`is_error=True` 时 <&backend/app/domain/agent/chat.py:2261> 的 `mark_consumed` 不执行，块保持 pending 下轮重发，**那一种不丢消息**；③三次事故只产生一条事件，同一根因不会两次静默一次报错。共同点只有一个而且是猜测：两边都是「平台以为的会话状态」对不上现实。

## 修法

`summon=False` 时也调一次 `merge_into_running_turn`——有活轮就当场送进去（**不开新轮**，那一轮已经付过费了），没活轮返回 None 什么都不做、照旧交给 pending 窗口。用 `await` 不用后台任务，因为隔一秒打的两条必须按打字顺序到达会话。**有意没动** `ChatService.converse(summon=False)`：生产里它只用于「额度耗尽把消息落下来」，那条路不该往会话里塞东西。

## 根因：不是「递卡强推了一个空提交」，是「递卡顺手新建工作区，新建工作区把分支拽回了空提交」

链路：递卡 → `push_topic_branch_for_github_pr` → `snapshot_worktree` → `_ensure_worktree`。
最后这一步在 `backend/app/domain/workspace/service.py` 里原本**无条件**做三件事：

    jj workspace add ...                          # @ 是一个全新的空 working-copy commit
    jj bookmark set <分支> -r @ --allow-backwards  # ← 把分支硬拉到那个空提交
    jj git export                                 # ← 写回 git ref

`--allow-backwards` 正是关掉 jj「不许把分支往回移」保护的那个开关。**它的原意是对的**——一棵全新的树需要有一条分支。错在**没先看一眼分支是不是已经有东西了**。

分支为什么会先有东西？**因为那个目录不是分支唯一的作者。** 跑在托管机器上的分身，文件根本不在后端那份 worktree 里，它只能 git push 经项目 git 代理写分支；后端那边可能压根没建过这棵树的目录——递卡时现建，现建就清空。**所以「递卡前先手动 push」永远挡不住：清空发生在递卡之后。**
