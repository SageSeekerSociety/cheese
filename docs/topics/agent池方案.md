# agent 池：方案

> 一页版，给评审用。完整论证、代码核实和逐条出处在
> <&docs/topics/room-task-agent-session-设计方案.md> 的 §12。
> @fulu 拍板方向，2026-08-17。

## 一句话

把「芝士」从**每个话题自动生一个**，改成**从一个池里选一个**——
身份、技能、模型、记忆都跟着池里那个 agent 走，不再跟着话题走。

## 为什么要改：一组实测数字

这个项目现在的记忆存储（2026-08-17 实测）：

| 池 | 条数 |
|---|---|
| 分池之前的共享池 | 59 |
| 平台级「芝士」的池 | 25 |
| **34 个**「每个话题一个分身」的池 | 各 2–11，**多数就 2 条** |

合计 **36 个池、155 条**。

原因在于：agent 的 handle 今天是**话题 id 算出来的**（`cheese-<话题hex>`），
而记忆池的 key 是 `(项目, handle)`。**所以记忆的真实粒度是话题，不是芝士。** 三个后果：

- 一个话题的分身平均学到 2 条就结束了，那个池从此再没人读；
- 在一个房间学到的东西，别的房间读不到；
- issue #184 说「『同一个芝士』靠记忆跨房间成立」——**在当前实现下不成立**。

## 做成什么样：三层，寿命各不相同

| 层 | 是什么 | 范围 |
|---|---|---|
| **类型**（出厂设置） | 名字、系统提示、skills、MCP、模型、effort、harness | **可跨项目共享**（平台预设 ＋ 自定义） |
| **实例 ＋ 记忆** | 这个 agent 在这个项目里学到的东西 | **项目内**，跟身份走、不跟话题走 |
| **会话** | 它在某个话题里「聊到哪了」 | 一个话题一个，可丢、可重建 |

这个分层不是新发明：buzz 就是 persona（可分发的配置）＋ engram（社区内的记忆）两分；
我们的 `expert_roles` / `custom_roles` 两张表已经是「类型」层的一半
（docstring 里就写着它 "maps directly to a Claude Code agent type"），
缺的是 model / effort / 工具白名单这几项——也就是「怎么跑」。

## 分两阶段

### 阶段一：一个话题最多一个 agent

- 建话题时选一个 agent，**默认「芝士」**；
- 拆出去的活（task）用**所在房间的同一个 agent**——这样 task 里学到的东西自动流回房间，
  「良性循环」在这里闭合；
- 记忆归到 agent 名下。

### 阶段二：一个话题多个 agent

会话的键已经从「话题」改成「话题 ＋ agent」（`agent_sessions`），会话层不再是障碍。
剩下的是「这一轮是谁在说话」——`resolve_agent_handle` 今天取 roster 里第一个。

## 一条硬顺序，不能颠倒

**归并记忆之前，必须先改注入方式。**

合并后是 155 条 / 42455 字符，而当时的注入是「按 `created_at DESC` 取前 50 条」。
也就是说，合并当天 **105 条（68%）进不来**，而且进不来的是最旧的那批——跟这一轮
在干什么毫无关系。虽然平台会如实告诉芝士「另有 105 条没放进来」，但那等于通知它
「你的记忆大部分不在场」，比分池更糟。

改法照 buzz：**一条 core 每轮在场**（这个 agent 是谁、它的规则和目标），
**其余按需检索**。已经做完，见 <&docs/topics/记忆注入分层.md>。

这件事和 issue #187（记忆系统三层分工）是同一个问题，**建议合并，不要单独开**。

## 要拍板的四件事

1. **默认 agent 就用现有的「芝士」**（handle `cheese`，已经有 25 条记忆，不是空壳）。
   默认值应当**项目级可覆盖**，不是平台硬编码。
2. **`cheese` 这个 handle 现在兼任「认不出身份时的兜底」**
   （代码注释：*the fallback identity: what a token that names no 分身 resolves to*）。
   建议给兜底另起一个 sentinel——否则认不出来的写入会落进默认 agent 的池。
3. **换 agent 要重开会话。** 换了 agent 还接着用同一份对话记录会人格分裂，
   所以这是个**有代价的动作**，不是切个开关，UI 上要提示。
4. **存量那 34 个 per-topic 池怎么办**：归到默认芝士名下（推荐——它们本来都是「这个项目的芝士」，
   语义对得上），还是留成只读历史。

## 明确不做

- **不做 persona pack 的打包分发**（zip / git repo / 校验和 / Open Plugin Spec 兼容）。
  那是给第三方作者生态准备的，我们现在没有第三方作者；先做数据库里的类型定义就够。
- **不做 triggers / subscribe**（「什么情况下响应」那一套规则）。
  我们有 @提及 ＋ summon，语义已经清楚，不需要再叠一层。
- **不做多 agent 并肩对话**——阶段二再说。

## 和正在做的事的关系

「容器按房间分配」那件活正在把 `CHEESE_TOPIC` / `CHEESE_TOKEN` 从容器环境变量
移到 per-session 注入。那正是这套设计的地基，已经在铺了——**这个方案不需要等它，
但两者是配套的**。
