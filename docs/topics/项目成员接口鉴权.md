## 结论先说

三个写接口（加成员 / 改角色 / 删成员）已经加上鉴权：**只有项目 owner 或 lead、且拿着真 token 的真人**能改项目成员表。匿名调用方、外人、普通成员、mentor、以及带合法 scoped token 的分身（芝士自己）一律 403。读列表不变，仍然开放。

## 为什么这么定（这条是本话题唯一需要拍板的地方）

简报里问「owner 才能改角色、lead 只能加人？」——**没有拆开，owner 和 lead 都能做全部三件事**。理由：本项目 `projects.owner_handle` 就是 NULL，如果把改角色收窄到 owner，这个项目的成员表当场就没人能改了；而 lead 本来就是「组长」，能加人却不能纠正自己刚加错的角色，是个别扭的半吊子权限。

另一个不那么显然的选择：**这个接口不吃 Phase-0 的 body 兜底**。仓库里大部分 2.0 路由都容忍「调用方在 body 里自报 handle」，但这里不行——项目成员身份是话题访问控制的地基（`authorize_topic_access` 只要 `is_project_member` 就放行全项目），如果自报 handle 也算数，攻击者写一句 `actor: "wangchangxin"` 就照样能把自己写进任何项目，等于没修。仓库里已有同款先例：设质量闸门的 `require_quality_gate_admin` 也是「必须是 token 认证的真人 owner/lead」。

**分身被明确挡在外面**，哪怕它拿着本项目合法的 per-turn token。当初就是我（芝士）用这条路把 andy 从 member 提成 lead，才暴露出没有鉴权；分身要改成员表，得让真人来点。

## 改了什么

- <&backend/app/domain/authz/policy.py>：新增纯策略 `can_manage_project_members`（和话题级的 `can_manage_roster` 并排），依赖注入两个读适配器，无 DB、可单测。
- <&backend/app/domain/membership/services.py>：`add` / `update_role` / `remove` 三个方法的 `actor` 是**必填参数**，先 `_ensure_project`（项目不存在仍是 404）再 `_require_manager`。必填是故意的：以后任何新调用方漏传 actor 会直接报错，而不是静默地无鉴权写库。
- <&backend/app/api/routes/members.py>：三个写路由接 `ActorResolverDep`，在信任边界解析 actor 后交给 service。
- <&backend/tests/unit/test_authz_policy.py>：8 条纯策略用例（owner / lead / 无 owner 时 lead / member / mentor / 外人 / 自报 handle / 分身）。
- <&backend/tests/integration/test_members_authz.py>：9 条 HTTP 功能测试，覆盖验收要求的三类——外人被拒 403、owner 与 lead 允许、token 优先于 body 里伪造的字段——外加「匿名直接 403」「普通成员不能自我提权」「分身的 scoped token 也被拒」「读列表仍开放」。
- 另外 9 个测试文件跟着改：它们原来靠「匿名也能写成员表」来做前置数据。现在统一用新加的 `bearer` fixture（<&backend/tests/conftest.py>）以项目 owner 的身份写。按 `.claude/rules/backend-tests.md` 的要求，改路由行为就得把所有调这条路由的测试一起改，不是只改自己那份。

## 影响面

- 前端只读成员列表，不写，**UI 不受影响**。
- 唯一的写入口就是这三个接口，所以：**owner 是 NULL 且一个 lead 都没有的项目，成员表会没人能改**。本项目已经有 andy 当 lead，不受影响；根治要靠 <#bd607b26-cb97-48e2-8d80-834ceeb1402e>（项目 owner 为空）。
- <&scripts/probe_members_ui.py> 这类匿名写成员的探针脚本，之后会拿到 403——这正是本次要的效果。
