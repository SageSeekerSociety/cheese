## 目标

打磨知是的前端设计。当前在修 <@wangchangxin> 报的两个 bug：右上角头像显示不对、切换 AI 队友后名字不变。

## 问题一：头像显示不对（所有人共用同一张脸）

**现象**：右上角的头像不是你自己的，是一张所有人都一样的通用图。

**根因**（已核实到代码）：新用户注册时 `avatar_id` 一律写死成全局默认头像的 id（<&backend/app/domain/user/services.py:173> 等三处 `default_avatar_id: int = 1`）。而 <&frontend/src/utils/materials.ts:1> 的 `getAvatarUrl` 只判空、不判「这是不是那张默认图」，于是：

- <&frontend/src/composables/useUserMenu.ts:23> 算出来的 `avatar` **永远非空**；
- 于是 <&frontend/src/components/common/Navigation/MobileAppBar.vue:43>（手机版右上角）和 <&frontend/src/components/common/Navigation/LeftAppRail.vue:25>（桌面版左栏）里那句「没头像就画彩色首字母」的兜底分支**永远走不到**，成了死代码。

这个坑项目里已经有人踩过并在别处修好了：<&backend/app/domain/project/repositories.py:102> 那段长注释写得很清楚——名册接口会把「指着全局默认头像」的 `avatar_id` 主动置空，好让前端画彩色首字母，理由原文是「让每个没选过头像的人共用一张脸，比按 handle 哈希出的首字母更难分辨人，而分辨人正是头像的全部职责」。聊天面板（<&frontend/src/components/ChatPanel.vue:1053>）就是照这个做的，是对的。**只有全局用户菜单这一处漏了。**

**另一处同类问题**：桌面版话题页右上角的成员头像堆（<&frontend/src/components/TopicMembers.vue> 的 `.members-mini__face`）把底色写死成 `#8a94a3`，既不按人取色、也不显示本人上传的头像——一排一模一样的灰圆圈。它的数据源 `GET /topics/{id}/members`（<&backend/app/api/routes/topic_members.py:26>）压根没返回 `avatar_id`，尽管那里的注释自称是「让界面能标注头像」。

## 问题二：换了 AI 队友，名字还是「芝士」

**现象**：在成员名册里把 AI 队友换成别的，界面上到处还写「芝士」。

**根因**：后端是对的——`PUT /topics/{id}/agent` 返回了新队友的 `display_name`（<&backend/app/api/routes/topics.py:179>）。名字没变是前端三处各自写死：

1. <&frontend/src/components/ChatPanel.vue:1047> — `displayName()` 对所有 AI 消息**直接 return 字符串「芝士」**，完全不看当前是哪个队友。同文件 1734 行的「正在处理」条、1854 行的输入框占位符也是写死的。
2. <&frontend/src/components/TopicMembers.vue> — 名册那一行的名字取自 `GET /topics/{id}/members` 的 `name`，而那是**座位账号的昵称**，创建时写死成常量（<&backend/app/domain/identity/services.py:93> `name=CHEESE_NAME`），换人格不会改它。头像里的「芝」字和顶上的「N 人 + 芝士」也是写死的。
3. <&frontend/src/components/TopicAgentPicker.vue> 换完只更新自己组件内部的状态，**不通知父组件**，所以名册那一行连重新加载都不会发生。

即使修好 1 和 2，不修 3 也得刷新页面才看得到。

# 前端改进方案（2026-09-08）

参照 <@wangchangxin> 点名的两个前端：**agent-orchestrator**（Untrivial-ai，管一队编码代理的 Agent IDE）和 **dsh**（DeepSeek Harness 的 Web UI）。

## 先说我们已经不差的部分（别照抄）

看了之后最意外的一条：**我们的看板在一个地方比 agent-orchestrator 想得更清楚。**

它的列是 Working / Needs you / In review / Ready to merge——四列里两列讲「事情到哪一步」（在评审、可合并），两列讲「该谁动」（在干、等你），两套判据混在一根轴上。我们的列（<&frontend/src/lib/board.ts>）只有一条判据，注释里写死了：**「该谁动」，不是「事情进行到哪一步」**——建设中 / 交付中 / 等你，已完成收在底部折叠行。同一个客观事实，下一步在平台手上还是在人手上，落进不同的列。这条不要改。

另外几样我们也已经有：卡面那句状态词是后端算一次的（<&backend/app/domain/room_task/presentation.py>，15 个短语，含「检查未通过」「等待验收」「解决冲突」），前端没有本地推导的退路；合并态（CI、能不能合、该谁动）有完整模型并渲染在验收卡上（<&frontend/src/lib/mergeState.ts>）；改动 / 现场 / 预览 / 文档四格面板；64px 的常驻侧栏 rail（dsh 是 56px，同一个形态）。

## 三条真正的差距，按性价比排

### P0 · 打开项目第一眼应该是看板，不是一个聊天窗口

现在：桌面端进项目，<&frontend/src/views/workspace/WorkspaceEntry.vue> 直接把你送进「大本营」——一个聊天。看板藏在侧栏一个叫「看板」的链接后面。

两个参照都不是这样。agent-orchestrator 的落地页就是那块活的看板，它自己写的理由是让人一眼看到「**什么在动、什么卡住了、你的注意力放在哪里最有用**」。dsh 更直接地把整个产品定义成「**这不是聊天窗口，是 agent 运行时的前端；你在这里观察和干预**」。

**这条对我们不只是审美问题，有实证**：人大 Hackathon 那批外部用户全部当天流失，三个失败案例是同一个死因——新用户建完项目的落地页是总览（一个聊天），他们在那儿发消息，没有任何东西动，也没有任何东西告诉他们没人接。落地页是聊天，就把「这个产品在替你跑活」这件事藏在了第二屏。

**改法**：项目的默认视图改成看板；大本营降为侧栏里的一个话题（它本来就是）。手机端保持现状（那一层本来就是列表）。

### P1 · 看板自己不刷新（这是它和 AO 差距最大的一条）

<&frontend/src/views/workspace/RunningWorkView.vue> 只有 `onMounted(load)` 和「换项目时重新拉」。外壳 <&frontend/src/views/workspace/ProjectShell.vue:42> 每 30 秒刷一次话题列表（侧栏那个「芝士在跑」的呼吸点就是靠它更新的），**但看板不在那条链路上**。所以你盯着看板看五分钟，它一个字都不会变。

一块整页存在理由是「现在轮到谁」的板，自己是静的——AO 强调它的板是 live state，差距首先差在这里，不在长相。改法：接进外壳那个 tick，或者自己起一个（活的状态比未读更值得刷）。纯前端，很小。

### P1 · 卡上的「谁在做」是一串英文 id

卡面现在写的是 `row.owner_handle`（`n1ctheboy` 这种），不是昵称，也没有头像。而一张卡上最先被扫的就是「谁」。我们刚把头像那套基础设施做好了（按 handle 取色的彩色首字母 + 本人头像 + 名册带昵称），看板是它最该被用上的地方。

### P2 · 同一列里，「在跑」和「闲着」长得一样

色点用的是 `columnDotStyle(row.presentation.column)`——**列级**的，所以「建设中」那一列里每张卡的点完全相同，正在跑和闲着的区别只在那句状态词里。侧栏已经有现成的呼吸点（`.running-dot`），搬过来即可。

（更正我上一轮的两句话：①我说「卡上没有正在动」不准确——词是有的（后端的 `运行中`），缺的是视觉区分；②我说「卡上补分支」是**错的**，代码注释写得很清楚：**一条活没有自己的分支**，多条活共用一棵树、一棵树开一个 PR，照抄 AO 那一行会写出一个假事实。这条撤回。）

### P2 · 没有「只看我的」

一个 169 个房间的项目，「等你」那一列会很长，而里面大部分不是等你、是等别人。AO 把自己的板定义成「你的注意力放在哪里最有用」，靠的就是筛。我们卡上有 `owner_handle`，加一个开关是纯前端。

### P2 · 「等你」不说等你做什么

「等待验收」是一句状态，但不说等谁验收——后端卡上有 `reviewer_handle`。一列叫「等你」，点开才知道不是等我，这一列就白分了。

## 不建议抄的

- **它的四列**：见上，我们的一条判据更干净。
- **每个 worker 一个隔离浏览器配置**：我们的预览面板已经覆盖了这个场景的主要用途，而隔离配置的收益要到「多个活同时开着各自的本地应用并登录不同账号」才显现，我们还没到那一步。
- **原生终端形态作为对话的平级视图**：我们有「现场」和设备实时画面，缺的不是能力是摆放位置，等前面三条落地了再看。

## 右边那半边（工作面板）：不比 AO 差，差的是一格的位置

@符露夀 问过这一半。逐项对过之后结论是**能力不缺，甚至更细**：

| AO 打开一张卡看到的 | 我们 |
|---|---|
| conversation | 对话 ✓ |
| 原生终端 | 现场 + 设备实时画面（有，但没做成对话的平级视图） |
| changed files | 改动 ✓（带自动刷新） |
| preview | 预览 ✓（带自动刷新） |
| PR summary + reviews + CI | **验收卡**，比它描述的更细 |

<&frontend/src/components/TopicAcceptCard.vue> 自己轮询 `/pr-checks`：逐项检查的图标和名字、能不能合、「与主分支冲突」、谁批过、采纳按钮和后端闸门走同一条线。AO 只说「CI、可合并性、评审人状态摆在 worker 旁边」，我们摆得更全。

**真差距是位置**：那张卡挂在**对话时间线的末尾**，不是一个独立的格子。对话一长就得滚到底才看得到「能不能合、CI 红没红、谁批了」。AO 把它作为卡片打开后的平级面板。

改法：给 PR / 验收单独一格，或者有卡的时候把它钉在面板顶部。要动 `TopicAcceptCard` 的位置和 <&frontend/src/components/WorkPanel.vue> 的格子定义。

## 骨架：收过两轮

第二轮（2026-09-09，PR #896）起因是 <@符露夀> 说「和实际加载出来的东西差距有点大」。
查下来第一轮的毛病不是漏了哪一处，是**一种形态被三处共用**：`entry` 当初照着支线进度
那种 55px 的行量的，看板和「现场」也拿去用了 —— 看板的真卡是 101px 的带框块，两条骨架
换来一张卡；「现场」的一条动作是 19–39px，骨架比它高一半。现已拆成各自的形态，尺寸全部

<&frontend/src/components/common/LoadingSkeleton.vue> 的顶部。「文档」那格补上了骨架 ——
它原来空着，而空编辑器会亮出「芝士会在这里维护文档」，那句话的意思是「这篇文档是空的」。

下面是第一轮的记录。

工作台原来 12 处转圈 + 1 处纯文字「加载中…」，现在 7 处画成骨架。每个骨头的尺寸都来自它替代的那一行（侧栏行 36+2px、聊天单行 60px、名册行 49px），所以内容到达时区域不跳。看板那处最见功夫：列框和列头一开始就渲染，骨架只画在卡的位置上——「列头在加载前后是同一串」写成了断言，那是「区域会不会跳」这个问题唯一能用测试问出来的形式。

验证（房间自己重跑一遍，不是采信分身的报告）：vitest **105 文件 878 条全过**、vue-tsc **0 error**、eslint **0 error**（291 warning 是仓库基线）、stylelint **63 未超基线 63**、仓库闸门 PASS。后端一行未动。

## 动效方向：C（<@wangchangxin> 2026-09-08 定）

三选一原本是：A 工作台向老社区靠（加 hover 抬升）、B 老社区向工作台靠（收 `transition: all`）、C **统一规则而不是效果**。

定的是 C，依据是「按照他的来」——即按 <&docs/design-system.md> 那套办法办事：**先把规则写进规范，再让两边各自往规则上收**，而不是直接去改效果。这和那份规范已有的做法是同一套（档位 + token + 机器闸门），也和它的总原则一致（「95% 是中性灰，琥珀是奢侈品」——安静是默认，动是例外）。

规则草案（待写进规范）：**hover 只改颜色，不改位置；位置的变化只留给真的发生了变化的时刻。** 理由是实测出来的：工作台是高密度列表（侧栏一屏几十条话题、聊天一屏几十条消息），鼠标扫过每行抬 2px 整列会跳；而老社区那 18 个文件写的是 `transition: all`，会把布局属性一起带上，放进高频列表是实打实的性能问题。

**这里有个事实要说明**：<&docs/design-system.md> 现在**没有动效这一章**——颜色、字号、圆角、阴影、深色、文案都有规范，动效一条都没有，也没有闸门。<&frontend/src/style.css> 里只有零散的 0.06s/0.15s/0.18s ease 和一条全局 `prefers-reduced-motion` 兜底。所以「按规范来」这件事本身的第一步，就是**把这一章补进规范**。

## 看板改造预览（可点，<&board-preview.html>）

给 <@wangchangxin> 看的原型，右侧预览里能点。三个切换：**改造前 / 改造后**、**现在（真实数据）/ 忙起来（示意）**、**浅色 / 深色**，另有一个「标出改了哪里」的开关。板的 CSS 逐条抄自 <&frontend/src/views/workspace/RunningWorkView.vue>，色值是 <&frontend/src/style.css> 的 token，头像取色跑的是 <&frontend/src/utils/avatar.ts> 那套 OKLCH 算法，状态词取自后端那 15 个短语。已在无头 DOM 里实测过四种组合都正常。

**「现在」那一档暴露了一件事**：这个项目 295 条活里，**当前活跃的只有 3 条**（2 条空闲、1 条失联），其余 292 条全在「已完成」里折着。也就是说落地页改成看板之后，第一屏大多数时候是**三列几乎全空 + 底下一条 292**。这不推翻 P0（板空恰恰说明「现在没什么在跑」，比一个聊天窗口诚实），但空态那句话就不是收尾工作而是第一屏的主要内容——简报里那条「空看板要说清下一步」的分量比写的时候重。

预览里改造后和改造前的差别是四处：谁在做（英文 handle → 头像+昵称）、在跑的卡有呼吸点、「只看我的」（计数写成 `2 / 5`）、以及会自己刷新（预览里用一个按钮模拟，能看到数字变而正在看的列表不动）。

## 看板：已收工（分支 topic/af7fc145，再加 2 个提交）

**自己刷新** —— 视图自己起 15 秒的 interval，没接外壳那条 30 秒的 tick（接进去要把「哪个视图开着」的知识塞进 <&frontend/src/views/workspace/ProjectShell.vue>；而且外壳那条刷的是未读角标，节奏本来就该慢一档）。静默走 `load(silent)`：不碰 `loading`（所以骨架分支不可能再触发）、不清 `rows`、失败不写 `errorMsg`，另有一道 `inFlight` 闸防止慢响应叠着乱序落地。后台标签页 `document.hidden` 时跳过，切回来补一次。`onUnmounted` 清定时器和监听。

**谁在做** —— 头像 + 昵称。`avatar_id == null` 就是没挑过头像，画 `avatarColor(handle)` 的彩色首字母，不走 `getAvatarUrl(undefined)`（那正是 #742 修掉的坑）；图挂了退回首字母；名册里查不到的 handle（含 `session` 这种非人值）原样显示、不去取任何图。

**在跑的卡** —— 用的就是侧栏那一颗：同名 `.running-dot`、6px 实心 `--ok`、`1.6s ease-in-out infinite`。`prefers-reduced-motion` 下单独关掉动画（全局那条压到 0.001ms 对无限循环不够用），关掉后它仍是实心点、旁边是空心圈，区别不靠动。

**只看我的** —— 状态在地址栏 `?mine=1`，所以刷新不丢、这一屏能发给别人。列一个不少，计数写成 `3 / 12`；「已完成」折叠行按整块板的数留着（不会因为筛选把「292」整条抹掉）。取不到登录身份时不画开关。

**落地页** —— 桌面 `replace` 到看板，不等话题列表（原来的转圈和空态一并删掉，没留成不可达分支）。手机端一个字没动。`?topic=` 老链接在两端都仍跳原话题。空板每列自己说「暂无施工中的活」，「施工中」那列另起一行小字说下一步。

**动效规则遵守情况**：全文没有 hover 抬升、没有 `transition: all`。位移只有两处，都不是 hover——开关的拨柄（按下就是「真的发生了变化的时刻」）和呼吸点的 `scale`（状态指示）。

**一处取舍留个记录**：「只看我的」打开时是琥珀（`--accent-wash` 底 + `--accent` 边框）。<&docs/design-system.md> §0 说琥珀只给「当前页唯一的主操作」，这一屏没有别的主操作，所以成立；但同屏「等你」那一列的色点是 `--warn`，浅色下两个橙很接近。预览里就是这个样子，<@wangchangxin> 看过说没问题，所以按原样递。
