## 目标

让 `deploy/deploy-docker.sh` 对 2026-08-09 那类瞬时拉取故障有韧性。**不修 containerd、不查"谁删了 ingest 文件"**（那需要宿主机证据，本卡明确不负责）。三件事：

1. ghcr 登录和 pull 重试到时间预算用完，退避有上限；
2. 用 `trap` 保证**失败路径也回收**镜像（本卡最重要的一条）；
3. pull 前后 + 每次回收后打印磁盘水位。

## 约束

- 只动 `deploy/` 下的东西 + 必要测试；不碰宿主机 root、不停 dockerd、不 `rm -rf` containerd 目录。
- 保持 `set -euo pipefail` 语义：重试用尽后**仍然必须非零退出**，错误信息要带重试次数和每次的失败原因。
- 回收本身 best-effort，绝不能因为回收失败把一次本来成功的部署判成失败。

## 现状：改动已完成，测试已跑绿

改了两个文件 + 一个测试假件：

- <&deploy/deploy-docker.sh> — 主体改动（重试本身在 <&deploy/registry-retry.sh>）

### 1. pull 重试：重试到 600 秒预算用完，间隔 5s / 10s / 20s / 30s / 30s…

`retry_pull <描述> <命令…>` 包住 app 镜像的 pull（`dc pull backend frontend`、`dc pull collab`）。一次部署里所有 pull 共用一个预算，从第一次 pull 开始算：失败后只要「已用时间 + 下一次等待」还在预算内就再试，等待从 5 秒起翻倍、封顶 30 秒。预算和封顶可用 `DEPLOY_PULL_BUDGET_SECONDS`（默认 600）/ `DEPLOY_PULL_BACKOFF_CAP_SECONDS`（默认 30）覆盖。预算只决定还要不要发起下一次尝试，不会打断正在跑的那一次。

**为什么是 600 秒、封顶 30 秒**：dev box 到 ghcr 的线路会一阵一阵地重置连接，一阵持续几分钟。2026-10-24 dev 有六次部署尝试在旧的「3 次、5s/15s」下放弃，都是第一次 pull 之后 37–57 秒内三次全挂在 `read: connection reset by peer`。containerd 把下载好的层 commit 到已消失的 ingest 文件那类失败（2026-08-09），重发 pull 会开一条**新的 ingest 记录**，同样靠重试解决。封顶 30 秒保证一阵过去后最多半分钟就接上。预算按两个跑这个脚本的 job 里更紧的那个定：prod 的 `timeout-minutes: 30`（`deploy-prod.yml`；dev 是 180）。prod 还没有发布跑过这个版本的脚本；2026-10-24（UTC）dev 上 22 次成功的部署里它跑了约 4–7.5 分钟（含全部 pull），之前的步骤约 1 分钟，prod 唯一一次跑它最早版本的发布用了 10 分钟，所以重试 10 分钟再加最后一次尝试，仍然是脚本自己报错并回收，而不是被 runner 掐掉。

重试之前**只有磁盘满才清理**（`docker image prune -af` + 有上限的 `builder prune`）。判据是那次尝试的输出里有 docker 报 ENOSPC 时的 `no space left on device`。连接被重置时不清理：`image prune -af` 会删掉所有没有容器引用的镜像，包括这次部署刚拉完、还没起容器的镜像。2026-10-24 dev 部署 run 40108853373 第 5 次尝试：backend 和 frontend 已经拉完，collab 被重置后的清理把它们删了，接着 `dc run backend` 只好重拉 backend，又被重置，部署失败。清理本身很便宜（dev box 上每次 0.4–0.8 秒），省下来的是重拉。刻意**没有**去动 containerd 的 ingest 目录、没有停 dockerd、没有碰运行中的容器。

### 1a. ghcr 登录：同一个 `retry_pull`

部署前要登录 ghcr（镜像是私有的，box 上存着的凭证是之前某个 job 的 `GITHUB_TOKEN`，job 结束就失效）。登录原来是 `deploy-dev.yml` 里一步 `docker/login-action`，只试一次；它走的是和 pull 同一条会成阵重置连接的线路，2026-10-24 dev 部署 run 40138894358 就死在这一步：`Get "https://ghcr.io/token?...": read: connection reset by peer`。

`retry_pull`、`pull_backoff_delay` 和预算设置搬进了 <&deploy/registry-retry.sh>，`deploy-docker.sh` 和新的 <&deploy/ghcr-login.sh> 都 source 它。`ghcr-login.sh` 把 `GHCR_TOKEN` 从 stdin 交给 `docker login ghcr.io --password-stdin`，token 不进命令行也不进日志，按同样的退避重试。它是单独一个进程，所以预算是自己的一份 600 秒，不和后面的 pull 共用。

登录放在 workflow 里、而且在检出要发布的那个提交**之前**，跑的是 workflow 自己那个提交（main）的脚本：`deploy-dev.yml` 发布任何提交都跑那个提交自己的 `deploy-docker.sh`，回滚或漂移恢复发的是更早的提交，登录要是写在 `deploy-docker.sh` 里，那些提交的脚本根本不登录，拉私有镜像必然被拒。为此「Check out automatic deployment policy」那一步现在每次都跑，不再只在 `workflow_run` / `rebuilt` 时跑。凭证照旧留在 box 上，给后面拉 metering 镜像的那一步用。prod 的 workflow 目前不登录，用 box 上存的凭证。

`retry_pull` 只有一种失败不重试：输出里有 `unauthorized` 或 `denied`，也就是 registry 拒了凭证。同一个 token 下一次照样被拒，等满预算只会让报错晚十分钟。这条对 pull 同样适用。

### 2. 失败路径也回收：`trap on_exit EXIT INT TERM`

在第一次 pull 之前挂 trap 并置 `RECLAIM_PENDING=1`；成功路径仍在原位置内联回收一次（保证 `DEPLOY OK` 还是最后一行），回收后清掉 flag，trap 就不会重复做。

选 `EXIT` 而不是 `ERR`：`fail()` 是显式 `exit 1`，`ERR` 覆盖不到。另外挂了 `INT`/`TERM`，因为 build/deploy 被 single-runner 的 `cancel-in-progress` 取消是这个仓库的常态。

`on_exit` 开头存下 `$?`、结尾 `exit "$rc"`，**退出码不被回收动作改写**；回收内部每条命令都 `|| true`。

一处**刻意的不对称**：失败路径上 `DEPLOY_APP_IMAGE_SOURCE=local` 时**不做 image prune**——本地构建的镜像此时还没跑起来、也没法从 registry 拉回来，删了要人重新构建。registry 模式下镜像按定义可重拉，照删。

### 3. 磁盘水位

`log_disk <时机>` 打印 `/` 和 docker data root（同一文件系统时自动去重）。打点在：pull 前、pull 后、**每次 pull 失败时**、每次回收之后。真实样例：

```
[deploy-docker 16:45:10] disk (before pull) overlay on /: size=251.8GiB used=126.6GiB avail=114.6GiB use=53%
[deploy-docker 16:45:11] disk (image pull failed, attempt 1) overlay on /: …
[deploy-docker 16:45:11] image pull: attempt 1 failed (exit 1), 0s into the pulls' 3s budget; retrying in 1s
[deploy-docker 16:45:12] ERROR: image pull failed after 2 attempts in 2s, the pulls' 3s budget spent (attempt 1 exited 1; attempt 2 exited 1); …
[deploy-docker 16:45:12] deploy exiting with status 1 — reclaiming disk on the way out
```

## 验证（不是"看着对"）

`deploy/tests/` 里已有一套**假 docker 驱动真脚本**的端到端测试。pull 与回收的用例：

| 用例 | 证明了什么 |
|---|---|
| `pull-retry` | 注入 5 次连接被重置 → 部署成功，日志里恰好 6 次 pull，报 `succeeded on attempt 6`，最后一次 pull 之前**没有** prune |
| `pull-disk-full` | 注入 2 次 `no space left on device` → 部署成功，且第一次 prune 出现在最后一次 pull **之前** |
| `login-retry` | 注入 5 次登录时连接被重置 → `ghcr-login.sh` 成功，6 次尝试每次都从 stdin 收到 token，报 `ghcr login: succeeded on attempt 6`，输出里没有 token |
| `login-refused` | registry 拒了 token（`denied`）→ 登录失败，只试一次，报错说凭证被拒 |
| `pull-refused` | registry 拒了 pull（`denied`）→ 部署失败，只 pull 一次，报错说被拒 |
| `pull-exhausted` | 预算 3 秒、注入 99 次失败 → 重试过不止一次、**非零退出**、报文里的尝试次数和日志一致、用时不超过预算、带每次退出码、**没有**走到 migration、且 prune 仍然执行了 |
| `failed-reclaim` | 健康检查失败（pull 之后的失败路径）→ 仍然执行了 prune |
| `disk-watermark` | 三个打点都出现在部署日志里 |

全套 `bash deploy/tests/test-app-tier-health.sh all` **15/15 PASS，exit 0**；`bash .claude/scripts/check.sh --no-tests`（ruff + pyright）exit 0。

另外手工验证了 SIGTERM 路径（模拟 runner 的 `cancel-in-progress` 取消；下面是当时三次重试版本的输出，重试改成按预算之后这条路径没变）：脚本在退避等待中收到 TERM → **退出码 143**、并且在退出前执行了回收：

```
[deploy-docker 18:07:17] image pull: attempt 1/3 failed (exit 1); reclaiming disk, retrying in 5s
[deploy-docker 18:07:22] deploy exiting with status 143 — reclaiming disk on the way out
[deploy-docker 18:07:22] pruning all unused docker images (failed deploy)…
```

（时间戳差 5 秒是 bash 的固有行为：前台命令执行期间收到的信号要等该命令返回后才处理。真实的 runner 取消是发给整个进程组的，子进程会同时死掉，不会有这个延迟。）
