# T2 任务绑定分身与 split 切换

## 目标

「任务=分身」改造的第二阶段：让平台不再为每条活起一个容器，改成房间在自己会话里
起一个分身、把它认领到某条活上，之后这个分身干的每件事都记在那条活的时间线上。
全局方案见房间文档「实施方案」一节，T1（hooks 认分身事件）已合入同一条分支。

## 现在做到哪了

**五件事全部写完并推上分支 `topic/80027df3`**（提交 c5df908bc → 40d3f57ad）：

1. **数据模型**：`tasks.subagent_id`（nullable varchar(64)）+ 迁移 `d7f3a1c05b28`，
   带 `(room_id, subagent_id)` 索引——这个查询按每一条 hook 事件跑，不是按每次开
   页面跑。alembic HEAD 哨兵已移到新 revision。
2. **认领**：`POST /topics/{room}/tasks/{task}/bind` + `cheese bind <task_id>
   <agent_id>`。四条拒绝各有测试：不是房间的调用者、别的房间的活、已收的活、这个
   分身已经在做别的活。
3. **split 切换**：不再 `submit_kickoff`、不再占驻留槽，两段代码直接删掉（不留
   开关）。返回值不再有 `queued`/`queue_position`/`slots_held_by`——排队机制是给
   容器配额用的，容器没了。CLI 输出改成把剩下两步写出来。
4. **事件归流**：带 `agent_id` 的事件查该房间里绑了这个 id 的 open 活，查到就把块
   打上 `task_id`、并把实时帧发到那条活自己的频道。`SubagentStart/Stop` 只对绑定
   过的 id 落块。
5. **结论闭环**：`POST /topics/{room}/tasks/{task}/conclude` + `cheese
   conclude-task`，走现有 `return_conclusion`。**不做任何自动落结论。**

## 定下来的几条（连同为什么）

- **没绑的分身，事件照旧记在房间头上，不丢弃。** 归属粗一点是麻烦，整条跑丢是
  看不见的 bug。
- **`SubagentStart/Stop` 反过来：只认绑定过的 id。** T1 实测（2.1.224 复现两次）
  会收到来路不明的 SubagentStop——会话自己的 Stop 之后才到、id 对不上任何见过的
  分身、type 是空的、"收尾话"是一段提示词碎片。落下去等于用芝士的名义在房间里贴
  一句陌生人的半截话。
- **完成通知 ≠ 活干完了。** 一个分身可以报好几次完成（把长命令丢进自己的后台再停
  下等就算一次），所以 Stop 只落成时间线上的一个事件，不结卡、不收活。由房间验过
  货再 `conclude-task`。
- **`conclude-task` 不叫醒房间。** 调用方就是房间，它正在跑那一轮。结论卡自己有
  超时线，不会因为没人 digest 就永远挂着。
- **归属查询走 `TaskService`，不直接摸 `TaskRepository`。** 跨域摸 repository 会
  撞架构守卫，白名单是棘轮，不该为这个加一行。

## 已知缺口（不在 T2 范围，留给 T3/T4）

- **`need-evidence` 打回会去起那条活自己的会话**（`routes/conclusions.py`
  `submit_kickoff(chat, sub_id, ...)`）。活现在没有自己的会话了，这条路会去起一个
  我们刚删掉的东西。它是个「做什么」的问题（打回应该转达给谁），不是「怎么做」，
  所以没在 T2 里自己拍板。
- **分身的 TaskCreate/TaskUpdate 仍然写进房间的清单**。这是改动前就有的行为，不是
  新引入的回归；按分身分清单要给每个分身单独的 todo 状态，是另一件事。
- **驻留槽机制本体、每任务屏幕启动路径**：split 不再调用它们，但代码还在（T4）。
- `docs/topics/` 下若干旧文档仍按「split 会自动起分身」描述，未清（T4）。
