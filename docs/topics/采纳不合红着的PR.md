# 采纳不合红着的 PR

采纳一个 forge 说没通过的 PR 时，平台不合并。卡挂到 `pr_open` 上等检查转绿，要
现在就合走署名的人工放行。

## 补的是哪个洞

App forge 那条路早就这样了（[App 采纳等 CI 再合](App采纳等CI再合.md)）：采纳 =
授权，轮询器等 CI 全绿才合。那次没动的是 `AcceptService._accept_via_pr` ——
卡上已经有 PR、项目的 forge 不是 `github_app` 时走的那条。它的 docstring 原话写
着 check-runs 的状态 "never used to block"：合并前读一次、把「合并时 CI 检查未
全绿」写进卡片 note 和房间通知，**然后照合**。

也就是说结论早就读到手了，只是刻意没用。那是**最后一条**会把 forge 说没过的改动
合进上游的采纳路。

这条路的可达性很窄：`accept_via_pr` 默认开着，开着的时候绑定 GitHub 的项目走的是
App 那条；要落到这里，得是「卡拿到 PR 之后 `ACCEPT_VIA_PR` 被关掉」这种配置翻转。
窄不等于可以留着——一个只在配置翻转后才生效的直推上游，正是没人会去看的那种。

## 结论决定行为

判据只有一句「forge 说这个 PR 的检查过没过」，**不认名字**。按某一道具名检查判
死活，等于要求每个被托管的仓库都得配上那道检查才配被采纳，而仓库不该为了被托管
而改变（CLAUDE.md 第一条）。

| forge 说 | 平台做什么 |
|---|---|
| 全绿 | 当场合并，和以前一样 |
| 压根没有检查 | 当场合并，和以前一样 —— 没有检查就没有红，这里的采纳本来就纯粹是人的判断 (#363) |
| 红 | 不合。卡进 `pr_open` 等它转绿；轮询器下一轮把失败详情递给芝士去修 |
| 还在跑 | 不合。卡进 `pr_open` 等它跑完，全绿了平台自动合 |
| 读不到 | 不合。卡进 `pr_open`；卡面如实写「没读到」，不写成「红的」 |

### 「还在跑」为什么是等，不是拒

「拒了、让人过会儿再点一次」和「平台自己等」是两种产品，这里选了等。CI 要跑十几
分钟，让人守着标签页重新点，是把平台的活派给人；而平台等 CI 的机器是现成的
（`SchedulerService.poll_open_prs` → `advance_pr_card`），另外两条采纳路（App 与
两阶段）也早就是这么等的。同一个「采纳」按钮在不同项目上意味着不同的事，才是真正
没法向人解释的产品。

### 「读不到」为什么也不合

读不到结论 ≠ 结论是绿的。平台合的必须是 forge 真答过的那个绿。它和「读到了，是
红的」在卡面上必须分开写——把前者写成后者，事后追责会照着一条从没发生过的判断去
问人（`_force_merge_verdict` 为同一个理由存在）。

## 为什么不照 GitHub 的 merge box

GitHub 在没有分支保护时把红点摆在合并按钮上方、把决定留给人。平台以前照抄了这个
姿态。抄不动的地方在于：GitHub 那个页面上按按钮的人和红点在同一屏，合并的也是他
自己的手；平台这边人按下去的是「采纳」，推分支和调合并 API 都由平台代劳——中间隔
着的这段距离正是 PR #414 的形状（PR 开出 25 秒就被合，最后一项检查比合并晚 16
分钟）。一句事后 note 填不上这段距离。

这不是「平台自己跑检查」（`docs/agent-principles.md` 原则六否掉的那件事）。平台
仍然只读 forge 的结论，变的只是读到之后怎么办。

## 红着合的出口：现成的那一个

`POST /accept-cards/{id}/merge-anyway`（卡片上的「人工放行」），默认拒绝、显式
放行，记下谁、什么时候、当时检查是什么状态、以及理由。它只认 `pr_open` 的卡——
这也是拦下来的卡必须挂到 `pr_open` 上、而不是原地报错的原因：原地报错的话，房间
里那句「可以人工放行」就是假的。

## 三个接线点

1. **note 的码不能写成 `checks_failed`。** 那个码正是 `_nudge_pr_fix` 的去重条件；
   在采纳现场提前写上去，会让轮询器那次 nudge 被当成重复的咽掉，于是芝士永远收不
   到失败详情。拦下来的卡写 `waiting_checks`：对这张卡来说红和「还在跑」是同一件
   事——等它转绿，差别只在谁接着动手。
2. **授权基线冻的是推完之后的那个 commit。** 采纳会先把工作区最后的改动推上 PR
   分支，所以 head sha 要在推完之后再读一次；沿用推之前那次 `pr_view` 的 sha，
   轮询器第一轮就会误报「新提交超出授权范围」。这一次读也可能失败——那就让采纳
   可见地停下、可重试（`_stop_accept_pr_unavailable`），因为挂不上轮询的卡会永远
   停在 `pr_open` 而界面上看不出来。
3. **这个决定必须在那个 `except Exception` 之外落地。** `_accept_via_pr` 的兜底
   分支把任何异常翻译成「退回本地合并」，而本地合并是绕开 PR 直推上游。所以拦下
   来的判断在 try 里算、在 try 外执行——否则一次读不到 head sha 就会变成这道闸门
   专门要拦的那次直推。

## 没做

- 没有删 `_accept_via_pr`。它拦下来之后的行为已经和另外两条采纳路一样（不合、
  挂到 `pr_open` 等），差别只剩「全绿就当场合」这一下；是否该并成一条是另一张卡。
- 没有动轮询器选凭据的规则（`_pr_poll_credentials`）。这条路上的采纳用的是平台
  App 的 token，而卡挂上去之后轮询和人工放行按 forge 走验收人自己的 token；验收
  人没连 GitHub 时卡面会写「轮询暂停，下一轮还会重试」，看得见、连上就自愈。
