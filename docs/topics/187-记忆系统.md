## 二、根问题：三层里缺的是"进度"，不是"记忆"

```
记忆    稳定的事实和约定        跨任务、跨房间、跨机器
进度    这个任务做到哪了  ← 缺的就是这一层
上下文  这一轮的细节            丢了就丢了
```

进度层现在**有**的：代码改动（每轮 commit+push）、结论（决策 / 活文档）、完成（验收卡）。
进度层**漏**的：checklist 状态只活在对话记录里，随机器一起死。

这多半就是"换了机器不知道自己做到哪"最直接的原因。而且它是全篇**唯一不依赖任何未决项**的缺口：checklist 本来就该是房间里看得见的东西，#182 的任务卡片上那几个勾就是它的载体。

**误用的代价要说清楚**：把"做到哪了"塞进记忆，记忆会退化成流水账；而记忆是要注入 prompt 的，越长越互相挤，最后真正重要的三条被一百条琐事挤出去。所以这不是"顺手也存进记忆"能糊弄过去的。

## 三、记忆没在长 —— 三个串联开关，全断

准确说法不是"设计如此"，是**配置没到位**：实现齐备、抽取开关默认还是 `True`，但后端一直是 db，等于**自动记忆从没通过电**。这个区别很重要，否则我们会一直误判记忆的健康状况。

要通电需要三样，缺一不可：

1. **一个真的智谱 key**（embedding 用）。key 不设时回落到 `anthropic_auth_token`，而那是 `sk-che...` 开头的 LiteLLM 虚拟 key，OpenViking 默认直连智谱，拿它去调会 401。gateway 暴露的是 `glm-4.6` / `glm-5.2` / `glm-4.5` / `deepseek-chat`，**全是 chat，没有 embedding**——所以 embedding 只能直连，chat 那条倒可以指回 gateway（顺带把用量纳入计费和归属）。**这是唯一的硬阻塞。**
2. **`.viking` 必须挂载出来** ⚠️ 现在它在容器可写层里，每次部署重建容器**记忆全部清零**。这个坑比不启用更糟：它会给人"记忆在工作"的错觉，直到某次部署后大家发现芝士什么都不记得了。
3. **`MEMORY_BACKEND=openviking`**

### 三样必须同时上，不能先切 backend 试试看

issue 的顺序是 通电 → 观察抽取质量 → 补 dreaming。但如果第 2 样没跟上就先切了 backend，**观察期本身会被下一次部署清空**，观察到的"记忆很少"分不清是抽取不好还是被清零了——白跑一轮。

### 两件 issue 没写、但同样会咬人的事

- **切后端没有迁移路径。** `memory_store()` 只是个选择器（store.py:90），db 里已有的 `memory_entries` 不会被搬过去。切换的那一刻，旧记忆不是被删了，是**直接不可见**。切之前得先决定：迁移、还是接受断代。
- **切后端 = 把记忆从"有备份的地方"搬到"没备份的地方"。** PG 有 <&deploy/db-backup.sh>；`.viking` 既没挂载也没有任何备份路径。挂载只解决"重建容器不丢"，不解决"盘坏了不丢"——而"盘会坏"正是 #186 的前提。

## 四、auto memory：已经在写，但归属是错的

Claude Code 自带的 auto memory 默认开启，**已经在 dev 上写了**，落在 session_dir 挂载里，所以本地路径下意外地已经持久了。

问题在归属：`session_dir` 是 **per-topic** 的（路径里就带 `topic_id.hex[:8]`），所以 auto memory 也是 per-topic——**芝士在话题 A 学到的，话题 B 读不到**。这跟 #181 定的 `(账号, 项目)` 拧着，也跟"记忆是唯一能跨房间流动的东西"正好相反。

要点：**它能不能当主干，取决于我们怎么送过去、怎么收回来，而不是 Claude Code 怎么存它。** 平台在机器起来时把记忆放进去、结束时收回来，它就是中心化的——跟 OpenViking 没有本质区别，区别只在传输方式（文件同步 vs HTTP），不在归属。

**当下的真实状态是两份记忆并存**：一份 per-(账号,项目) 在后端、一份 per-topic 在机器上，谁也不知道对方存了什么。这本身就是个待决问题，不是等 OpenViking 通电就自动消失的。

## 五、架构约束：记忆必须中心化 + 强一致

这是排掉一整类做法的结论：远程机器上的记忆**不能是本地副本 + 事后合并**（各写各的、dream 时再解分歧）——那本质是回避一致性，会带来合并冲突和丢失更新。正确的是**每次写入穿透到中心**。

顺带纠正一个容易犯的错：我们之前反对给 worktree 挂网络文件系统（延迟致命），这个理由**在记忆上不成立**，访问模式完全不同：

| | 访问模式 | 走网络的代价 |
|---|---|---|
| worktree | 大量小文件、高频（Grep 扫全树、连读十几个文件） | 乘以成百上千次，致命 |
| **记忆** | **少量文件、低频**（启动读一次索引，偶尔写一条） | 可以接受 |

补一条支持这个结论的事实：OpenViking 是**嵌入在后端进程里**的（store.py 里 lazy import、数据目录在后端本地），所以走 OpenViking 时"中心化"天然成立；分散的那一份恰恰是 auto memory 那些文件。这让"两份并存"的问题更急，不是更缓。

## 六、dreaming：缺的是"整理"，不是"写入"

**为什么写入之外还要整理**：写入路径必须快，所以每次写只看得到当前对话和少量相似记忆，看不到库里其他内容——同一个事实换个措辞就会被存好几遍，这类问题在写入时根本不可见。数据库早就把这事分开了（LSM 的 compaction、Postgres 的 vacuum、git 的 gc），而记忆系统普遍只上了快写入那一半。

现状：**OpenViking 有语义检索、缺整理**（装好的 0.4.7 里只有写时合并算子，没有后台整理进程）；**Claude Code 有整理（Auto Dream）、缺语义检索**（只有精确关键词匹配）。所以我们要的是前者 + 自建后者。

**dreaming 必须跑在有 workspace 的机器上**——要提炼"这个仓库的约定是什么"，光看对话提不出来，得能对着代码验证。但不用额外开机器：挂在回收前。机器即将消失那一刻，是唯一同时握着 workspace、对话记录、auto memory 的时刻，所以这一步不只是整理，是**销毁前的收割**——传回来的是结论，不是流水。时机也天然正确：闲置 8 小时说明这段工作告一段落。

### 挂钩点有两条，别只挂一条

代码里的回收其实是两条路径：<&backend/app/domain/scheduler/service.py> 的 `reap_idle_containers`（本地容器）和 <&backend/app/domain/machine/services.py> 的 `destroy`（MicroCloud 机器）。**只挂在其中一条，另一条路径上的机器就是无声消失。** 而 #186 已经定了本地容器只是过渡形态、MicroCloud 才是主路径——挂错那条等于白做。

覆盖不到的是**意外死亡**（磁盘满、崩溃）——那归 #186 管，两条线不重叠，别指望 dreaming 兜底。

## 七、并发：能借鉴一个内核，但必须自建三样

Claude Code 的实现（源码 + 二进制比对已查证）**没有专门解决 dream 与写入的并发**：`.consolidate-lock` 只防两个 dream 撞车，正常写入路径从不引用它；dream 是**原地重写**，原子性只在单文件层面，崩溃会留下半整理状态且**没有内容回滚**。lost update 基本不发生，靠的是一层白捡的保护——Edit/Write 通用的 mtime 乐观校验（本质是 mtime 版本号 CAS + 由 LLM 做冲突合并），不是记忆系统的设计。

**它在单机下够用，靠四个结构性侥幸：一个仓库一个记忆目录、所有写入方同进程、dream 触发极稀疏、冲突按文件切分。这四条我们一条都不成立。**

- **借鉴**：乐观并发 + 冲突时让**整理方**重读重并（而不是让写入方等）——比悲观锁更适合"整理要跑几分钟"。但载体必须换：mtime 跨机器不可用，换成**服务端 per-file version/etag，写入 compare-and-set，失败返回最新版本让 dream 重新合并**。
- **自建三样**：① inbox/journal（整理期间的新写入落独立区，dream 读快照、结束时归并）；② 整体切换（dream 产出新 generation，改指针原子生效，不原地逐文件改）；③ 内容级回滚（这层 Claude Code 彻底是空的）。
- **锁不要抄**：建议锁、非原子、还兼任"上次整理时间戳"——一次硬杀导致 rollback 没跑，时间门控就赔进去一个 24 小时窗口。

结论：**并发控制该由存储层（服务端）负责，不该靠文件系统约定**——这也是 OpenViking（服务）比 auto memory（文件）更顺的根本原因。
