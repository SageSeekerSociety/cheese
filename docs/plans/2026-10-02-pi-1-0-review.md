# pi 1.0 评估：更新了什么、打断我们哪两处、要不要升

## 一句话

pi 1.0.0 于 2026-10-01 发布（上游 `earendil-works/pi`，MIT）；我们 pin 在 0.85.1。我
把两个版本的真实 build 都下下来、用仓库里那份 `platform.ts` 各跑了一遍同一条端到端流程，
**我们用到的那套接口在 1.0 上能跑通**，但有**两处静默失效**：extension 里靠字符串匹配
pi 系统提示词的两段改写，在 1.0 上匹配不到、什么都不做也不报错。1.0 本身没有我们要的东西
（MCP、codemode、deferred tool loading、virtual models、全屏 TUI 都与我们无关或已有）。

**建议升，排在下一批，不插队**：改动面小且已知（下面第二节），但拖着不升的唯一代价是
delta 越滚越大，而升级的价值是「不再落后 7 个版本」，不是「拿到某个功能」。

## 一、上游变了什么

0.85.1（2026-09-05）到 1.0.0（2026-10-01）中间隔了 0.86、0.87、0.99 三条线。**1.0.0 自己
的 changelog 没有 Breaking Changes 段**；带 Breaking Changes 的是 0.86.0、0.87.0 两个版本，
内容全在 TypeScript 嵌入式 API 上（`pi-ai` 的流输入改成 `TranscriptContext`、`SessionManager`
成为 `AgentSession` 上下文的唯一来源、`shouldStopAfterTurn` 换成 `finishTurn`、
`TurnEndEvent` 加了必填字段）。1.0.0 把实验性 harness（`AgentHarness`、会话存储、durable
runtime、`pico3`、harness tools、compaction、skills、prompt templates）从
`@earendil-works/pi-agent-core` 里摘掉，迁往 `@earendil-works/pi-durable`，并删掉了
`./node`、`./harness/*`、`./experimental/pico3` 三个子路径导出。

**这些都不落在我们身上**：平台不嵌 TypeScript SDK，跑的是 vendor 编译好的二进制，扩展只在
运行时 import `@earendil-works/pi-coding-agent` 的工具工厂。1.0 的功能清单（MCP 支持、
codemode、deferred tool loading、virtual models、Anthropic cache warming、全屏 TUI）里，
MCP 我们自己实现（`mcp.py`，pi 的 MCP 客户端由我们当），其余与平台无关。

发布产物形状没变：v1.0.0 与 v0.85.1 都发了 darwin/linux × x64/arm64 四个 `pi-<平台>.tar.gz`
加 `SHA256SUMS`，所以 `app/domain/machine/pi_dist.py` 的下载与校验逻辑不用改。

## 二、实测：能跑通的部分与断掉的两处

### 方法

把 0.85.1 和 1.0.0 的 linux-x64 官方 build 各解包，用**仓库里这份 `platform.ts`** 启动
`pi --mode rpc`，模型指向一个桩 OpenAI 流式服务，扩展要的 runner socket 用一个只记录、
只回桩数据的 unix socket 顶着。三步剧本：调 pi 自己的 `read` → 调一个平台工具 → 说一句话。
驱动脚本是 `backend/scripts/pi_build_smoke.py`，复核步骤见本文末。

### 跑通的部分

| 面 | 结果 |
| --- | --- |
| extension 加载与 `pi.registerTool` | 两版都注册成功，工具都declared 给了模型（请求体里两个工具都在） |
| `createReadTool(workspace, {operations})` 的注入点 | 两版都走 `files` 的 access → image → read 三次回调，路径是 workspace 下的 |
| `pi.on("tool_call"/"tool_result"/"before_agent_start"/"session_start"/"session_shutdown")` | 两版都触发（hooks 回调次数一致） |
| `pi.sendMessage({customType, content, display})` | 1.0 仍在文档列出的 API 里，`custom_message` 记录格式未变 |
| RPC 命令 `prompt` / `steer` / `abort` / `get_entries` | 两版都接受，`get_entries` 的 `since` 游标语义一致 |
| 流式事件 `message_update` + `assistantMessageEvent`（toolcall_start/delta/end、text_*） | 两版字段一致，房间的 live 帧不受影响 |
| `compaction_start` / `compaction_end` / `auto_retry_start` / `auto_retry_end` 字段 | 两版一致（`aborted`、`errorMessage`、`willRetry`、`attempt`、`maxAttempts`、`delayMs`） |
| 会话记录（`get_entries`）里我们读的几种 | `message`（role user/assistant/toolResult）、`custom_message`、`compaction`、`model_change`、`thinking_level_change` 形状一致；用量仍在 assistant message 上 |

**新增但无害的**：assistant message 上多了一个 `thinkingLevel` 字段；`prompt` 的回应多了
`data.disposition`（`started`/`queued`/`handled`）。

**新增但要留意**：1.0 在每次会话开头写一条 `role: "system"` 的记录（`content` 为空，带
`sections` 和 `toolsAdded` 两个结构化字段），事件流里也发对应的 `message_start`/`message_end`。
`events.py` 对 user/assistant/toolResult 之外的角色直接返回空列表，所以房间不会显示它——
但它会多占一条 journal 记录。会话中途改工具或改提示词时 1.0 还会再追加这类记录；我们今天
不在会话中途换工具，实测只出现一条。

### 断掉的两处（都静默，不报错）

1. **`placeTheSession`（platform.ts:251-265）** —— 它按字面串
   `Current working directory: ${here}` 把 pi 提示词里的目录改写成房间机器上的 workspace。
   1.0 把这一行换成了结构化段：

   | | 模型看到的系统提示词开头 |
   | --- | --- |
   | 0.85.1 | `You are the smoke test agent.\nCurrent working directory: /room/machine/checkout\n\nTHE PROJECT SAYS: ...` |
   | 1.0.0 | `You are the smoke test agent.\n\n<cwd>\n/tmp/.../work/workspace\n</cwd>\n\nTHE PROJECT SAYS: ...` |

   1.0 上那次 `split`/`join` 找不到字面串，于是**模型被告知的是会话机上的目录，不是房间机器上
   的 workspace**——而所有 pi 自己的工具（read/write/edit/bash/ls/find/grep）都在按 workspace
   解析路径。上面两行是同一条流程在同一个桩 workspace 设置下抓下来的请求体原文。

2. **`withoutHands`（platform.ts:1145-1158）** —— 一个人自己的芝士（没有机器）靠
   `prompt.lastIndexOf("\nCurrent working directory: ")` 把 pi 末尾那行目录删掉；1.0 上返回 -1，
   直接 `return`，于是会话机上的目录留在提示词里：

   | | 模型看到的系统提示词 |
   | --- | --- |
   | 0.85.1 | `You are the smoke test agent.\n` |
   | 1.0.0 | `You are the smoke test agent.\n\n<cwd>\n/tmp/.../work/workspace\n</cwd>` |

   `backend/tests/unit/test_personal_sessions.py:247` 断言的就是这件事不在提示词里——那条测试
   会继续绿，因为它喂给扩展的是自造的提示词串。

两处都指向同一个修法：走 1.0 的结构化入口（`before_agent_start` 的
`event.systemPromptOptions` / `sections.cwd`），别再匹配文本。

## 三、升级要动什么

1. `harness/pi/launch.py` 的 `VERSION`，和 `harness/pi/behaviour.py` 的 `VERIFIED_AGAINST`；
   四格 `BuiltIn` 要拿着新 build 重新读一遍（今天 ASK 与 AUTO_SYNC 是
   `NOT_CHECKED_AGAINST_THE_PIN`，TODO/REMINDER 是 `NOT_BUILT_IN`——1.0 新增了内建 MCP 与
   codemode 扩展，`--no-extensions` 的语义也扩到了内建扩展，这两格值得重核）。
2. 上面第二节那两处 `platform.ts`，改成结构化写法。
3. 重核拿 0.85.1 说话的夹具与说明：`backend/tests/unit/fixtures/pi-compaction*.json`、
   `pi-retry-*.json`（夹具抬头写着「按 0.85.1 的 docs/rpc.md 构造」）、
   `harness/pi/project_skills.py`（引 `src/core/package-manager.ts` @ v0.85.1）、
   `docs/manual/dev/harness.md` 的能力矩阵表。
4. 在 dev 上拿一个真房间跑一遍：项目会话（有机器）和一个没机器的人芝士各一次，看模型收到的
   目录是不是房间机器上的路径。

第 1、2 步是必做；第 3 步按项目既有规矩（pin 的版本号只写一处，矩阵过期即红）不能省。

## 四、没核实的

- **真正的 Python runner 端到端没跑**。上面的验证停在 extension 与 RPC 协议这两层；runner
  起的机器、hooks、MCP 客户端、分身（`subagents.py` 起第二个 pi）、技能镜像，都要一台执行机
  才能跑通，我没有。
- **长上下文下的压缩与重试**只对了两版的事件字段与文档，没有在真 provider 上跑过量。那几份
  夹具本来就是按文档构造的，不是录下来的。
- pi 1.0.0 发布才一天。下面第五节的建议不受这个影响，但如果这几天出了 1.0.1，直接用 1.0.1。

## 五、建议

升。理由是按上面第二节的量，升级是一次改了 2 个文件、重核 4 处引用的活，而 1.0 之后我们和
上游的差距只会更难追；不升的理由只有「1.0 里没有我们要的功能」，那是省一次改动的理由，不是
长期站得住的理由。

不要单独为它插队：把它当成一条独立任务，和下一次动 pi 骨架的活排在一起；也别升到一半
（pin 改了、那两处没改），那两处的坏法是静默的。

## 附：怎么自己复核

```bash
# 1. 拿两个 build（vendor 的 linux-x64 自包含包）
curl -fsSL -o pi-1.0.0.tar.gz \
  https://github.com/earendil-works/pi/releases/download/v1.0.0/pi-linux-x64.tar.gz
mkdir -p pi-1.0.0 && tar xzf pi-1.0.0.tar.gz -C pi-1.0.0 --strip-components=1
# 0.85.1 同理，换 tag 与目录名

# 2. 各跑一遍（--workspace 故意给一个会话机上不存在的目录，
#    这样「模型被告知哪个目录」一眼可辨）
uv run python backend/scripts/pi_build_smoke.py --pi ./pi-1.0.0 --tag v100 --out /tmp/pi-smoke \
  --workspace /room/machine/checkout --context "THE PROJECT SAYS: read AGENTS.md before you start."
uv run python backend/scripts/pi_build_smoke.py --pi ./pi-0.85.1 --tag v0851 --out /tmp/pi-smoke \
  --workspace /room/machine/checkout --context "THE PROJECT SAYS: read AGENTS.md before you start."
```

比两份 `/tmp/pi-smoke/*-report.json` 里的 `system_prompt`：0.85.1 那次应当是
`Current working directory: /room/machine/checkout`，1.0 那次是会话机上的临时目录。
再加一次 `--hands false`，看没有机器的那条路是不是也把会话机目录留在了提示词里。
脚本还会打印扩展回调过 runner 的方法、跑过的工具调用和各种会话记录的 type——升级前后
逐项比一遍，比读 changelog 可靠。
