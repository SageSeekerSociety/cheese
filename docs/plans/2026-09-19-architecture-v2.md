## 0. 开头一页

### 0.1 系统是什么

**一句话**：一群**参与者**（人和 agent 没有区别，只按岗位分）在**房间**里推进一件件**活**；
聊天用一个稳定的脑子，做事按活配脑子；平台只有三个提供者接口——
**地点**（这一轮在哪跑）、**骨架**（这一轮由什么驱动）、**托管方**（改动最后落在哪）；
产品语义整个住在这三个接口之上，不随实现变。**平台从不发起一轮，它只投递** [已定] 结论 13。

十个顶层概念，每个正交地带一个**持久层级**（L0 记录 / L1 会话 / L2 执行）：

| # | 概念 | 层 | 一句话 |
|---|---|---|---|
| 1 | **参与者 Actor** | L0 | 能说话、被点名、被通知、被署名的一个 handle。人和 agent 是它的两种到达方式，不是两个类。**只按岗位（role）分，模型不是它的属性** [已定] 结论 3、44 |
| 2 | **席位 Seat** | L0 | 「某个参与者在某个房间担某个角色」。**全系统唯一的授权载体**，凭证只负责认证 [已定] `agent-principles` 二、三 |
| 3 | **项目 Project** | L0 | 一个源仓库、一个资料库、一份产物清单、一份名册、一套配置。**每个项目恰好有一个源仓库（git），但不是项目里的每样东西都进它** [已定] 结论 26 |
| 4 | **房间 Room** | L0 | 一条时间线的容器，里面坐着若干成员，其中一些是 agent。**它不指向任何 agent**。私聊和项目总览是它的两种特例，不占槽位 [已定方向] #1180 |
| 5 | **活 Work** | L0 | 一件要交付的工作：一条分支、一张提案卡、一个唯一负责人。**房间里是平的，没有子卡**。工作树是它在某个地点的缓存。**它用房间的那台机器，不声明自己的环境** [已定] 结论 33、38 |
| 6 | **会话 Session** | L1 | 一个 agent 在一个**线程位**（房间主线，或房间里的一条活）的连续 transcript。**权威副本在平台**，它不拥有机器 [已定] 结论 29 |
| 7 | **地点 Place** | L2 | 一段**有期限、可归还、可休眠**的机器使用权。agent 的一双手，不是它的身体 [已定] 结论 24、39 |
| 8 | **骨架 Harness** | — | 在一个地点上驱动一个 agent 的程序。**开发者选项，不是产品概念**，它不拥有任何产品语义 [已定] 结论 28 |
| 9 | **托管方 Forge** | — | 改动最后落在哪，以及谁回答「能不能合」。平台自己的仓库也是一个实现 [已定] #363 |
| 10 | **事件 Event** | L0 | 发生过的一条不可变事实。**它落在它「关于」的那个东西上**；投递是从事件算出来的纯函数，收件人是 handle，人和 agent 同形 [已定] 结论 14 |

**不占槽位但必须写下来的五样**：
**轮次**（一切易失状态的唯一容身处，1.11）、
**文档**（人和 agent 唯一的共同视野，1.12）、
**私聊**与**项目总览**（房间的两种特例，1.4）、
**模型**（工作的资源绑定，与地点同形，2.5、4.6 与 8.1）。

三层的分配判据（可写成测试）：**一样东西没了，用户失去什么**——
失去历史 → L0；失去连续性 → L1；什么都不失去，只是慢一点 → L2。
故障域严格嵌套，**内层的死亡不得改变外层的任何一行**。

三条边界线，一句话各一条：

- **地点**：平台能在这台机器上写什么（足迹根，平台的自律），和 agent 能在这台机器上看到什么（可见性，用户的授权），**是两件事，永不互相推导**。
- **骨架**：房间里看得见的东西，只能有一条与骨架无关的产生路径。
- **托管方**：平台读结论，不算结论。

以及一条贯穿三者的总纪律 [我提的]：
**机器、harness、forge、算力档、模型都不是参与者，它们是参与者够得着的能力或它这条活绑的资源；
它们的任何差异都不许成为「房间里两个参与者规则不同」的理由。**
这条纪律解释了为什么上面三个接口必须止步于「能力」，也解释了结论 3 为什么把「换模型」从「换 agent」里摘出来——
用第二个 agent 换模型，正是把资源差异伪装成了参与者差异。

| **I24** | 同一件产品功能只有一个实现 | 判据挂在 4.3 那张骨架矩阵上：一行产品能力，在所有骨架列上只允许有一个产生方。没有通用守卫，靠矩阵逐格钉住 |
| **I25** | 机器的状态以**事件**抵达 agent，不以工具报错抵达；**平台不设等待超时器**（结论 23、40） | 三条：①租约消失 / 被回收 / 磁盘满，各在 agent 的输入里产生一条带 `event_type` 的平台事件；②断言 agent 读到的字符串里不含裸 HTTP 状态码；③全仓没有一处按时长自动改变机器绑定或自动换机的路径 |
| **I26** | 一个 fallback 的可见度，和它掩盖的那次失败一样高 | 在 `except` / `if x is None` / `or 默认值` 之后继续往下跑，必须在同一个函数里产出一条进入**某个人或某个 agent 视野**的记录。出口只有四种：propagate、report、被监控的死信、一条反馈。`logger.*` 不算 |
| **I27** | 掉档只能掉到「拒绝」或「可见的等待」，不能掉到另一个也能跑的东西——**花钱的、署名的、认身份的、换脑子的**四类尤其（结论 3；第四出口见结论 35） | 守卫抓不到，靠 4.6 那张四类清单逐点钉住。**供给降级不许悄悄换模型**是这条在模型这一侧的形状 |
| **I28** | `None` 不许当默认分支的入口 | 一个 `get()` 的返回值若被用来做**放行 / 授权 / 记账 / 路由 / 认身份**这五类选择，`None` 必须 raise 或走一个显式命名的「未知」分支 |

（「propagate, report (#445-style channel), or land in a dead-letter that something monitors」），

## 1. 概念模型

每个给：一句话定义 / 持久层 / 拥有什么 / **不**拥有什么 / 谁创建谁销毁。
**「拥有」= 这个事实的唯一声明处在它这里，别处只能读。**

### 1.1 参与者 Actor 〔L0〕

**是什么**：在平台上说话和做事的一个身份。人和 agent 都是它，没有第二种。
**它们唯一的区别是谁拥有它**：人拥有自己，被邀请到哪就去哪；
agent 实例由建它的项目拥有，只在那个项目有席位，别的项目不能邀请它。[已定] 结论 1。

- **拥有**：一个 handle（署名键，签过的名永不重写）、一份展示资料、一条投递方式、它的收件箱、
  （人）**一份关于自己的资料**——跨项目可读、只有他自己能改 [已定] 结论 10，形态见 1.12；
  （agent）它的记忆目录（2.1）。
- **不拥有**：角色与权限（属于席位）、**模型与骨架**（属于这条活的资源绑定与部署设置）、任何机器、任何会话。
- **生**：人由注册创建；agent 实例由项目里的人从一个 agent 类型建出来时创建。
  **灭**：都不真的销毁，只停用——它签过的名要一直解析得出来。

#### 身份级 / 席位级

这两层今天在代码里都有，但名字容易混，必须分清：

| | 身份级 | 席位级 |
|---|---|---|
| 是什么 | 这个参与者是谁 | 它在某个房间担什么角色 |
| 载体 | handle + 展示资料 + 记忆目录 | 席位行（1.2） |
| 跟着谁走 | 跟着参与者 | 跟着 (参与者, 房间) |
| 谁能改 | 只有它自己/它的拥有者 | 房间的 owner/admin |

今天 `identity/handles.py` 铸两种 agent handle：
`agent_instance_handle`（**身份级**，从实例 id 派生，docstring 逐字说明了为什么不能从房间派生——
「A room is a collaboration space and may seat several agents, so an agent's identity cannot be
derived from a room — the same derivation would give two agents in one room the same name,
and the same agent two names in two rooms.」）
和 `topic_agent_handle`（**房间派生**，`cheese-<12 位 hex>`）。
后者是 `cheese split` 那个第二身份的来源，按结论 31 要退场（1.5）。

#### agent 的类型与实例

[已定] 结论 2。**类型**=出厂设置（人设提示词、技能），不属于任何项目，像岗位说明书，可跨项目复用；
**实例**=某个项目从某个类型建出来的参与者，唯一身份、自己的记忆、只在该项目有席位。
今天 `agent_type/`（`presets/*.md` + `library.py`）加 `agent_instance/models.py:AgentInstance`
（`__tablename__ = "agent_instances"`，`project_id` + `handle` + `type_name` + `configuration`）已经是这个形状。
**差的是配置里那两个字段**：`agent_instance/configuration.py:30-36 class AgentConfiguration`
今天带 `model: str` 和 `harness: str`，`agent_type/schemas.py:19/21` 也各带一个——按结论 3、28 都要拿掉。

**拿掉之后，实例配置逐字段还剩什么**（今天这六个字段是 `body` / `model` / `harness` / `skills` / `mcp_servers` / `effort`）：

| 字段 | 归谁 | 为什么 |
|---|---|---|
| `body`（人设提示词） | **类型**，实例**不得**覆盖 [我提的] | 结论 2 把人设写成出厂设置。实例能覆盖它，等于每个实例都是一个新类型，结论 5 的判据（区别只是 system prompt 就不该是两个 agent）当场失效 |
| `skills` | **类型**，实例**不得**覆盖 [我提的] | 同上；1.5 那六句默认也住在 skill 里，它是岗位说明书的一部分 |
| `mcp_servers` | **类型**，实例**不得**覆盖 [我提的] | 同上。项目自己的 MCP 从项目 `.mcp.json` 来（3.1），不从实例配置来 |
| `effort` | **活**（从实例配置移走）[我提的] | 它是模型那一侧的旋钮。按结论 3，模型是这条活的资源绑定，跟它同一层的东西不能留在参与者身上 |
| `model` | **删** | 结论 3 |
| `harness` | **删** | 结论 28 |

**一个岗位最多声明对脑子的要求**（如需要看图），解析时满足，**不钉型号** [已定] 结论 3。
这条要求是**类型的出厂设置的一部分**，实例继承它，一条活在绑模型时必须满足它——
所以它不是上面那两行「删」的例外：它声明的是能力要求，不是一个型号。

#### 模型不是 agent 的属性

[已定] 结论 3、44。**分参与者的判据是岗位（role）。模型不是 agent 的属性，也不是分参与者的理由——用第二个 agent 换模型是错放。**
模型是**工作的资源绑定**，与机器（地点）同形：
卡上并排显示「在哪台机器、用哪个模型、现在在做什么、花了多少」。展开是 2.5、4.6 与 8.1。

**项目级只有两样：默认模型和启用列表** [已定] 结论 44。
「超档要人点头」不是第三样配置，它是启用列表之外那一档在投递上的形状（结论 3，8.1）；
**「档位策略」也不是第三样——它就是启用列表按费用分出来的那几档**，本稿凡说「档位」都指这个。

#### 什么时候才该是两个 agent

[已定] 结论 5（搬自 8 月多 agent 设计文档）：
**两个 agent 的区别只是 system prompt 就不该是两个 agent；区别必须是能力/凭据、记忆/专长、责任之一。**
记录里没有「一个房间两个 agent」的真实需求，只有用第二个 agent 换模型这种错放；
一房多队友是 #1180 之后的**能力**，不是**要求**。

#### 平台芝士不存在

[已定] 结论 4。没有跨项目的「平台芝士」参与者：
每个项目自动有一个芝士类型的实例（今天的默认 `cheese` handle），是完整参与者，记忆全部关在项目里。
[已定] 结论 18：没有跨项目的全局房间，也不需要跨项目的芝士。

#### 将来「人带自己的助理」

[已定] 结论 6。= 人拥有实例、席位跟着人走，模型里不加新概念。
**这个形状不进本稿的概念表**，但设计不能把它排除掉：1.1 开头把「谁拥有它」
写成参与者的一个属性、而不是写死成「agent 归项目」，正是为了不排除它。

#### 今天已经对了的一半

`identity/actor.py` 的模块 docstring 写着
「Humans and agents resolve to the same `Actor` shape so domain services never branch on `if is_agent`」；
`identity/models.py` 的 `AgentBinding` 把「是不是 agent」做成**派生**的（有绑定行即是），不是 user 上的一列。
**错的那一半**：`actor.py:48` 的 `Actor` dataclass 自己带着一个 `is_agent: bool` 字段——
模块 docstring 说不分岔，类型上却给了分岔的钩子。

### 1.2 席位 Seat 〔L0〕

**是什么**：「某个参与者在某个房间里，担某个角色」。**这是全系统唯一的授权载体。**

**术语消歧**：**席位角色**（owner / admin / member，住在这条席位行上）与**岗位**
（一个 agent 类型所描述的 role，如设计、测试，住在类型上，1.1）是两个词，英文里都叫 role。
本文一律分称「席位角色」与「岗位」。
**分 agent 的判据只有岗位一个** [已定] 结论 44：席位角色管的是它在这个房间能做什么，岗位管的是它是干什么的，
模型两边都不在——它在这条活上（1.5、4.6）。

- **拥有**：席位角色（owner / admin / member）、加入时间。
- **不拥有**：身份（在参与者上）、**出厂设置**（在 agent 类型上，1.1）、**资源绑定**（在这条活上，1.5）。
- **生/灭**：房间的 owner/admin；平台在建房时播种；移出即撤权。

[已定] `agent-principles` 二、三（凭证是认证的机械需要，不是授权的分级；agent 的权限不从任何人身上流下来，作用域是房间/项目）。

名册的 model 是有的，在 `topic/models.py:252 class TopicMembership`
（`topic_memberships` 表，`member_handle` + `role`，`UniqueConstraint("topic_id","member_handle")`），
docstring 逐字：「The roster is the foundation of 『话题 = 群聊』」。
`topic_membership/services.py` 的 `ensure_agent_seat` docstring 已经把「席位即授权」写成了实现意图
（「The seat is the grant: an action is attributable to the agent that holds one,
and de-authorizing it is a single row delete rather than waiting out a token's TTL」）。

**但今天还有第二条授权线**：`Actor.via` + 路由级 cheese-gate（`api/auth.py`）——
它答的是「这张凭证是真的吗」，不该再答「它能干什么」。

### 1.3 项目 Project 〔L0〕

**是什么**：一个源仓库、一份名册、一套配置的合称——协作的最外层单位。

- **拥有**：
  - **恰好一个源仓库（git）** [已定] 结论 26。`workspace/service.py:236 ensure_repo` 对**每个**项目无条件建一个平台侧 git 仓库，与绑不绑外部仓库无关——所以不存在「无 git 项目」这种**存储**形态，只存在「用户不看见 git 的项目」。**不是三种项目，是一个仓库配三个托管方。**
  - **一个资料库**（git 之外，`write_library_file` 在 `workspace/service.py:860`，#1209 带进来的）：
    只增不改、原名寻址、同名不覆盖（#1085 结论一）；**删除是一个显式动作**
    （`delete_library_file`，`:887`，#1247 加的），删掉之后旧引用如实报「这份资料已经不在资料库里」（`:840`）。
  - **一份产物清单**：文件型的源进源仓库；**引用型只记指针与运行记录** [已定] 结论 26（「资料库和引用型产物在它之外；办公文件走资料库进、产物出」）。
    **流向是一条直线**：办公文件从**资料库**进来，产出作为**产物**出去，**两端都不进源仓库** [已定] 结论 26。
  - 成员名册、agent 实例、默认地点、托管方绑定、**默认模型与启用列表**（含它按费用分的那几档）[已定] 结论 44。
- **不拥有**：机器、会话、房间里发生的事、**一个共享记忆池**（结论 7，见第 2 节）。
- **生**：人建；**建的同一刻平台播种一个芝士类型的实例，并在项目总览给它一条席位** [已定] 结论 4。
  **灭**：人删，带导出承诺（结论 27、I19b）。

**源仓库固定是 git，不抽成接口** [我提的]：今天没有第二个实现，也没人提要有；
会变的那根轴（改动最后落在哪、谁回答能不能合）已经由托管方接口承担。
git 在这里只当**版本化的存储**——文档用户看到的「差异」是文件自带的修订（#1086），
二进制源的冲突不走 git 合并而是在新基线上重做（#1085 结论六）。

**「本地文件」不是第四种存储** [已定] 结论 26：它只是连接器的输入输出通道，
**agent 不在用户文件系统里就地改**。

**平台是唯一副本时，导出和备份是架构义务** [已定] 结论 27。

[已定] 他 2026-09-17T01:04「我觉得左侧的**永远应该是个项目 而不是一个课程**」——当场否掉了按项目类型分叉的**侧栏**。
**这条只覆盖导航，不覆盖功能层**；功能层要不要为师生分叉，他 2026-09-16T12:05 明说「嗯 我们得有个设计然后讨论」，留在第 11 节。

### 1.4 房间 Room 〔L0〕

**是什么**：一条时间线的容器，里面坐着若干成员，其中一些是 agent。

- **拥有**：时间线（事件序列）、名册（席位集合）、实况文档、归档状态。
- **不拥有**：**一个 agent**、一台机器、一个会话、任何清理计划。
- **生**：任何有席位的参与者，包括 agent。**灭**：只有人能归档；归档不删时间线，归档是回收的触发器。

[已定] #1180：「A room is a collaboration space. It holds members. Some of them are agents.
**A room cannot point at an agent** — asking it for "its agent" can only mean picking one out of however many it holds.」

今天房间只有两种生法：人建（`POST /topics`），和**私聊里一条消息被升级**

### 1.5 活 Work 〔L0〕

**是什么**：房间里一件要交付的工作：一条分支、一张提案卡、一个唯一负责人。

- **拥有**：分支名、提案卡与它的合并状态、负责人、自己的会话、自己的进度清单、**它这一轮绑的模型**。
  **不含地点**：这一轮跑在哪里的唯一声明处是会话（1.6），而**它用的机器就是房间那一台** [已定] 结论 38。
- **不拥有**：自己的名册（**房间有名册，活只有唯一负责人**——今天已经写对了，
  `topic/services.py:956-959` 逐字：「A thread does NOT get one: 唯一的主 is the whole difference between
  a piece of work and the room it happens in, and copying the room's roster onto it would be re-buying
  the cost this design exists to drop」）；也不拥有托管方的实现细节（PR 号是外部标识，不是活的身份）。
- **生**：房间里的任何参与者，人或 agent，同一条规则。**灭**：采纳或放弃，不删除。

#### 负责人

[已定] 结论 32。负责人是**卡上的参与者（一个 handle）**，说的是**问责**，不是进程数。
子 agent 是芝士的线程，在卡上都是「芝士」。

#### 活是平的

[已定] 结论 33。**房间里的活没有子卡；谁能开活不受限。**
`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`（今天 `harness/claude_code/device_launch.py:403` 写死 `"1"`）
是**骨架设置**，不是设计约束——它管的是一个骨架进程里能起几层子进程，不是产品里活能嵌几层。

#### 活用房间的机器

[已定] 结论 38。**活永远用房间的那台机器**，一条活不声明自己的环境，子 agent 也不声明。
**要另一台机器，那就是另一个房间。**

这条把地点从活身上彻底摘掉：租约挂在房间上（1.7、6.1），活在它上面只有一个工作区检出（见本节「工作区是活在某个地点上的缓存」）。
它和结论 43 的「子 agent 与父进程同生同死」是同一件事的两面——
父进程在哪台机器上，子 agent 就在哪台机器上，全路径只有一次地点解析。

#### 开一条活 = 分支 + 卡 + 负责人

[已定] 结论 31。`cheese split` 今天那个形状整个干掉：

| 今天有 | 在哪 | 按结论 31 |
|---|---|---|
| 第二身份 `cheese-<hex12>` | `identity/handles.py:37 topic_agent_handle`（`TOPIC_AGENT_PREFIX = "cheese-"`，`_TOPIC_AGENT_HEX = 12`），`runtime.py:512` 逐字「`cheese split` under her own `cheese-<hex12>` handle」 | **无**。分身不是第二个参与者 |
| 第二会话 / 屏幕 / 地点 | 分身自己的 screen 与租约 | **无** |
| kickoff | `runtime.py:784-806`（`author="system"`，内容是 `KICKOFF_PROMPT`，`summon=True`） | **无**。平台不发起一轮（I12） |
| `cheese_bind` | `harness/prompt.py:152/176` 两处提示词教它「起完分身立刻 `cheese_bind`」 | **无** |

**留下的只有**：分支 + 卡 + 负责人。**谁来做是负责人的事。**
子 agent 做完是**给父线程的内部便条**（结论 11 那条通道，见 1.6 与 5.5），不是一次平台自召唤。

#### 派活是 agent 对骨架的一次工具调用

[已定] 结论 43。**agent 派一条活，调的是骨架自己的原生 subagent 工具，不走平台。**
平台在这件事上只认一样东西：**卡**。

- **先开卡，再起子 agent**：卡是这条活在平台上唯一的存在形式。
- **归属靠线程标识**：子 agent 的事件带一个可归到卡的线程标识，hook 按它把事件挂上那张卡。
- **结束写结论**：子 agent 做完把结论写回卡，给父线程的那条便条走 5.5。
- **人对卡的操作投递给父线程执行**：人在卡上改指令、按停，收件人是**父线程**（8.1）；
  平台不直接去动那个子 agent——它在平台这一侧没有句柄。
- **子 agent 与父进程同生同死**：它不是第二条会话（1.6）。父进程没了，恢复的办法是**从分支重派**，
  不是把那条线程接回来。
- **所以「边干边 commit」是 skill 的硬要求**，不是习惯：分支上的提交是这条活唯一活过父进程的东西。

这条契约的骨架那一侧（起子 agent 并指定模型、事件带线程标识、改指令、停止）写在 4.2。

#### 验证留证是 skill 的要求，不是平台的机制

[已定] 结论 41。验证型的活，由 **skill** 要求 agent 把验证过程截图或录像留下来，
留下来的东西作为**引用型产物**挂在那张卡上（产物清单在 1.3，引用型只记指针与运行记录）。
**平台不为它造机制**：没有「验证留证」这个平台概念，没有它自己的表、状态或按钮。
判据和 1.5 那六句默认一样——它住在 skill 里（`agent-principles` 十），
在平台这边它只是产物清单上的一条引用型条目。

#### skill 里的默认（不是规则，不进 system prompt）

**改仓库文件只能在一条活的工作区里**；**边干边 commit**；**验证型的活要留下验证过程的截图或录像**。

### 1.6 会话 Session 〔L1〕

**是什么**：一个 agent 在一个**线程位**（房间主线，或房间里的一条活）上的连续 transcript。
键是 (线程位, agent handle, harness)。
**「线程位」是会话的槽位，不是概念 7 的地点**——地点是机器使用权（1.7），
本节以下每一处「地点」都只作那一义。

- **拥有**：会话身份、续跑凭据（对平台不透明）、**transcript 的权威副本**、它的代际号、
  **它当前租着哪一个地点**——placement 的唯一声明处就在这里，活不声明它，轮次也不声明它。
- **不拥有**：**机器**。会话记在平台上，跑在某个地点上；地点换了，会话还是同一个。
- **生**：第一次有人点名这个 agent 时；**它的建立不需要任何执行机在线**——这是「agent 先启动」的可检查形式。
- **灭**：它的线程位（房间主线/活）被销毁，或人显式丢弃。**机器消失不销毁会话。**

**一条活的会话不自己解析租约**：它读房间主线那条会话的 placement，活的会话行上没有 placement 列——
这是结论 38 在这张表上的形状，所以一个房间里同时跑着多少条活，解析出来的都是同一份租约（4.1、6.1）。

**同一个 handle 的多条线程是一个参与者** [已定] 结论 11：
它在房间主线、在每一条活上各有一条会话，**这些线程共享身份和记忆**，
线程之间走**内部便条**（5.5）。会话是线程的载体，不是第二个身份。

**agent 自己起的子 agent 不建第二条会话** [已定] 结论 43：
它是父会话里的一条线程，靠线程标识归到卡上（1.5），**与父进程同生同死**。
一条活上有独立会话，是有人在那条活上被点名的时候；
子 agent 跑掉的那条活，恢复靠从分支重派，不靠接回一条会话。

[已定] `agent-principles` 十四「续跑就是把 transcript 接回来，平台自己不续」。

**这条地基今天就在库里，而且上游按错的那一份写**：

- `agent_session/models.py` 已经把会话做成后端的一行，键是 `(topic_id, task_id, agent_handle, harness)`，
  两条 partial unique index，注释逐字（`:44`）「One session per agent per PLACE,
  and a place is a room's main line or one thread in it」——这句里的 place 是线程位，不是概念 7 的地点。
- `device/models.py:153 DeviceTopicRow` 的 docstring 仍然逐字写着
  「the topic's work tree + **resumable claude session live on that one machine**,
  so every later turn MUST return to it」。

**两段 docstring 字面互斥，而目标形状的那张表已经在库里。**
所以这不是「造一个新架构」，是「把箭头掉过来，让上游读已经对的那张表」。

**「权威副本在平台」今天为什么是个空壳，机械原因在这里**：
后端**收着字节**（`agent/event_drain.py` 每轮 PUT 增量分片回后端，`:59` 的 `"PUT"`、`:94 collect_transcripts`
docstring 逐字「Send original bytes, preserving progress after each acknowledged chunk」），
**却没有任何一条回放路径**——全仓唯一的搬运是
`harness/claude_code/remote_execution/launch.py:92 transfer_history`，
它只有一个调用点（`central_provider.py:236`），被 `if not previous` 圈住，**只在首次 placement 时跑，而且只走机器→机器**。
结论 29 把「权威副本在平台、恢复从平台副本恢复」写成了**骨架契约的一条**，这条空壳因此不再是实现细节。

**「对话」与「轮次」的寿命不同，而今天挤在一个列名里**：
`topic/models.py:144 session_placement` 这个名字里，「session」是长期的、「placement」是易失的；
两个寿命不同的事实挤在一个 JSON 列上，于是换机就报错。

### 1.7 地点 Place 〔L2〕

**是什么**：一段**有期限、可归还、可休眠**的机器使用权——agent 的一双手。

- **拥有**：一个平台足迹根、一个进程树、一份只在租期内有效的凭据、它的健康账、它的能力声明。
- **不拥有**：会话、活、房间、身份、工作成果的权威副本。它是被借用的，不是被拥有的。
- **生**：人接入，或一轮需要手时平台按需开一台。
  **灭**：平台开的（`supply=cloud`）平台可销毁；人接入的（`supply=self_hosted`）平台只能停止使用。
  **它的销毁是常态事件，不是故障**（结论 24）。
- **它有三态，不是两态** [已定] 结论 39：**在用 / 休眠 / 已归还**。
  **休眠只对 Cloud**：闲置到点就快照后停机，reconnect window 之内醒来是**同一台机器、工作区原样**；
  window 过了才走归还，归还前的收据规则一个字不改（6.5、I19）。
  自托管没有这一态——那台机器不是平台的，停不停机是机主的事。

[已定] #282「真正的分界在**这台机器是怎么来的**」。

**为什么在架构层叫「租约」而不是「机器」**：
今天 `DeviceTopicRow` 是一条**没有期限、没有归还动作**的 1:1 绑定（docstring 逐字「1:1 — `topic_id` is the primary key」），
它在结构上表达不了「这双手可以换」。有期限、可归还、可休眠，才表达得了「机器可以死」。

**hosted machine 没有独立用途；三档只差物理事实** [已定] 结论 25。
所以功能矩阵必须满，例外只有 4.4 那三条物理码；用途最多影响默认值。

### 1.8 骨架 Harness

**是什么**：在一个地点上驱动一个 agent 的程序（Claude Code / pi / Codex）。

- **拥有**：它自己的事件格式、它自己的会话状态目录、它能不能拿订阅凭据这类物理事实。
  **起不起得了子 agent 不在这一行**：按结论 43 那是契约的硬性要求，不是一个可以声明「我没有」的字段（4.2）。
- **不拥有**：**任何产品语义**。进度清单、子 agent 归属、提问、提醒、同步、搜索，都不是骨架的财产。
- **生/灭**：部署（注册表里加一行）。用户不创建骨架。

**骨架不是产品概念，是开发者选项** [已定] 结论 28：
**不在类型上，不在实例上，是部署/项目级的开发者设置；普通用户看不到。**
所以 `AgentConfiguration.harness` 与 `agent_type/schemas.py:21` 的 `harness` 都要拿掉（1.1），
今天界面上那个「运行方式」下拉也随之收起（8.1）。

### 1.9 托管方 Forge

**是什么**：改动最后落在哪里，以及谁回答「能不能合」。**平台自己的仓库也是一个实现**，不是「没接 GitHub」这个状态。

- **拥有**：合并这个动作的执行、外部提案的身份、外部检查结论的读取、**写一个外部远端的凭据**。
- **不拥有**：**检查本身**（平台不跑检查，forge 跑、平台读结论）、活的身份、产品文案。
- **生/灭**：项目配置绑定或解绑。

[已定] `agent-principles` 五、六；#363：「provider 要**显式声明自己能不能报 checks**……
**不要写成 `if 是 GitHub`。判据是加第三个 provider 的时候，采纳流程一行都不用改**」。

### 1.10 事件 Event 〔L0〕

**是什么**：发生过的一条不可变事实。一条消息、一次工具调用、一次采纳、一次机器离线，都是事件。**它是这个系统的脊柱。**

- **拥有**：时间、作者（一个参与者，或平台）、**它「关于」的那个东西**、一个类别码。
- **不拥有**：**收件人**——谁被点到是从事件**算**出来的；也不拥有「状态」——状态是从事件序列算出来的；
  更不拥有唤醒语义（「唤醒」「召唤」不是平台概念）。
- **生**：任何层的状态变化。**灭**：不灭。历史是历史。

**「关于」决定它落在哪**（结论 14，I10），展开在第 5 节。
一句话：**PR 绿了不是一条消息，是卡的状态变了**，然后按 I11 通知验收人。

**投递是事件的派生函数，不是第十一个概念**：
从「一个事件」到「它点到了哪些参与者」是一条纯函数（I11 那条唯一规则），
把它送到每个收件人手上的动作按**到达方式**分派——人 → 站内 + 推送 + 邮件；agent → 起一轮。
**这个分派是全系统唯一一处可以合法出现「这是人还是 agent」的代码**，因为它是物理事实
（人有浏览器，agent 有一个会话），不是规则差异。

[已定] #1180：「**Notification is the general mechanism.** A member is notified; what they do next is theirs.
A person may read it and reply. **An agent's notification is what triggers it to send a message.**
So "waking" and "summoning" are not concepts the platform needs」。

### 1.11 轮次 Turn（不占顶层槽位，但必须写下来）

**是什么**：一次「被点名 → 它说话/做事 → 停下」的循环。**一切易失状态的唯一容身处。**

- **拥有**：它自己的进程、**它这一轮持有的租约句柄**（从会话的 placement 解析而来，不另存）、
  它的临时凭据、**它这一轮实际用的模型**。
- **不拥有**：**任何要活过它的东西**；也不拥有「这一轮在哪跑」这个事实本身（在会话上，1.6）。
- **生**：一条点名了它的事件投递。**灭**：它自己说完、失败，**或被一次显式打断结束**（4.2 的 `interrupt`）。
  **平台不重跑一轮，也不发起一轮**（I12）。

**判据**：一样易失的东西该挂在轮次上还是会话上，问一句「它比这一轮活得久吗」——
不久就挂轮次，久就挂会话，两者都不久于地点。

### 1.12 文档（不占顶层槽位，但必须写下来）

**是什么**：人和 agent 都看得见的那一层字。结论 7 废掉共享记忆池之后，**它是两边唯一的共同视野**；
`agent-principles` 十一给它和记忆划了界：**文档是规矩，记忆是观察**。

它不是一个新概念，而是**若干份别人的财产**——所以逐类列清谁拥有、谁能写、
agent 写它算不算一条事件（I10），否则「写进文档」这个动作没有落点：

| 这一份 | 谁拥有 | 谁能写 | agent 写它算不算一条事件 |
|---|---|---|---|
| **项目总览的实况文档** | 项目（住在根房间上，1.3、1.4） | 项目里任何有席位的参与者 | 算：一条**关于这个项目**的事件，落项目总览（5.1） |
| **房间的实况文档** | 房间（1.4） | 这个房间里任何有席位的参与者 | 算：一条**关于这个房间**的事件，落房间时间线 |
| **活的进度清单** | 活（1.5） | 这条活的负责人那条线程 | 算：一条**关于这条活**的事件，落那张卡 |
| **源仓库里的 `docs/` 与 `CLAUDE.md`** | 项目的源仓库（1.3） | 只能在一条活的工作区里改（结论 34 第四句），经采纳落地 | 不另算：它是那条活的一次改动，随卡与采纳留痕 |
| **关于一个人的资料** | **那个人**（1.1 的「拥有」） | **只有他自己**；任何项目的芝士都读得到，谁都不能替他写 [已定] 结论 10 | 不适用：agent 只读不写 |

**一条观察该写进哪一份，与事件落点（I10）、回忆规则（I16）是同一条轴：问它「关于谁」。**
关于这个项目怎么运转 → 项目总览的实况文档；关于这个房间在干什么 → 房间的实况文档；
关于这条活做到哪了 → 它的进度清单；关于这个仓库的代码约定 → `docs/`/`CLAUDE.md`，走一条活；
关于某一个人 → 那是 agent 的**观察**，进它对这个人的那些记忆文件（2.1），不进文档，
除非那是**他自己**定的偏好，那就是他那份资料，由他写。

**这五份都在用户的暴露面上**（8.1）：文档是共同视野，共同视野必须看得见。

## 2. 记忆

[已定] 结论 7、8、9、10、42。

### 2.1 记忆是文件：三个目录加一份资料，两条轴

**agent 的私有记忆是文件** [已定] 结论 42，判据是 I15③。六句把形状说完：

- **一个事实一个文件**，文件自带两样元数据——**关于谁**、**何时观察到**——上面压一份自动索引。
- **一个实例一个目录**，目录下按「关于谁」分三个子目录：**这个项目 / 某个人 / 自己**。
- **存在平台侧，不进项目 git 仓库**：它是 agent 的观察，不是仓库的规矩（`agent-principles` 十一）；
  而且真进了仓库，一条观察就要经过一条活和一次采纳才落得下去。
- **版本由平台给**：翻历史、看一条事实什么时候被改写过，都不需要项目仓库参与。
- **在任何地点都读得到**，走平台工具那条通路（3.1，结论 21）——
  这正是 6.3 那条能力事件敢写「记忆可用」的机械原因：记忆不在那双手上。
- **整理就是 agent 重写自己的文件**，没有第二套管道。

**没有项目记忆池** [已定] 结论 7，判据是 I15①。
人和 agent 共同看的只能是**文档**——哪几份、各归谁、谁能写，在 1.12
（`agent-principles` 十一：**文档是规矩，记忆是观察**）。
agent 观察到值得所有人知道的事，动作是**写进那几份文档之一（留痕）**，不是写进共享池。

**记忆全是某个 agent 实例自己的** [已定] 结论 8。三个子目录，全部随实例关在项目里：

| 子目录 | 关于谁 | 今天的 `MemoryScope` | **今天的键** | 按结论 8 该跟着谁走 |
|---|---|---|---|---|
| 这个项目 | 这个项目 | `agent_project` | `<project_id>:<agent_handle>`（`memory/models.py:72`），已经对了 | (实例, 项目) |
| 某个人 | 那个人 | `user` | **人的 handle，仅此而已**：`memory/models.py:31` 的注释逐字「个人记忆: 跨项目, 跟着人走」，`chat.py:4323-4324` 取的 scope_id 就是那个 handle，与是哪个 agent 实例无关——**跨项目、不按实例分，与结论 8 正相反** | (实例, 人)，键要变成 `<project_id>:<agent_handle>:<person>` |
| 自己 | 它自己 | `skill` | `<name>`（`openviking_store.py:17`）。枚举里有，产品路径上零读写点 | 实例 |

**第四种不是 agent 的记忆**，而是**关于一个人、他自己能改的一份资料** [已定] 结论 10：
一个人的偏好要跨项目跟着他，任何项目的芝士都读得到，**只有他自己能改**。
它在架构上的位置是**参与者的一件财产**（1.1 的「拥有」），形态与其余四份文档并列在 1.12——
今天那个跨项目的 `user` 池被换成按实例分之后，它是「跨项目跟着人走」这件事唯一的承载处。
**它和「对某个人的记忆」是两样东西** [已定] 结论 42，分界还是 `agent-principles` 十一那条：
**这份资料是他定的规矩，那个目录里的文件是 agent 的观察。**

**两条轴**，这是这一节的全部结构：

- **谁的**：永远是某一个 agent 实例的。没有共享池，所以没有「谁写坏了谁的」这个问题。
- **关于谁/什么**：项目、某个人、它自己。这条轴同时决定**一个文件落进哪个子目录**（2.4）
  和**什么时候读它**（2.2）。

### 2.2 回忆规则

[已定] 结论 9：**一个池被读出来，当且仅当它「关于」的那个东西在现场。**（I16）
**记忆改成文件不动这条** [已定] 结论 42。

- 房间里有这个人 → 读「某个人」目录下关于他的那些文件。**今天只在私聊里读，是缺口**：
  `chat.py:4323-4324` 只在私聊分支里 `recall_pools(memory, [(MemoryScope.user, private_owner)])`；
  一个多人房间里 agent 对每个人记的东西一条都不上场。
- 在这个项目里 → 读「这个项目」目录。今天对（`agent_instance/services.py:61 memory_pool`）。
- 永远 → 「自己」目录。

读错只是没用上，**写错会把「对张三的观察」写进项目目录然后到处上场**——所以真风险在写入侧，2.4。

### 2.3 可见性：profile 里的一页

[已定] 结论 42。**每个 agent 的 profile 上有一页「记忆」**，它是这些文件唯一的用户入口：

- **项目成员可看、可翻历史、可删、可标记**。翻历史靠的就是 2.1 那条「版本由平台给」。
- **关于某个人的文件只对当事人可见**。这是这一页上唯一一条按人分的可见性规则，
  也是「agent 对人记了什么，人要能看见、能删」（结论 9 末句）落在界面上的形状。
- **不进房间、不进时间线、改了不通知、搜索不默认覆盖**。
  记忆是观察不是发言：把它推到房间里，等于让 agent 每整理一次就说一次话。

这是一条产品要求，不是一个设置，所以它在普通用户的暴露面上（8.1），判据是 I16③⑤⑥。

### 2.4 写入分类规则

[已定] 结论 42。**任何提到某个人的判断，只能进那个人的那个文件。**

这条是 2.1 那两条轴在写入侧的唯一约束，由整理（dream）的分类规则守。
它要挡的是同一件事的两个方向：把对张三的观察写进项目目录（于是它对谁都上场），
以及把关于张三的判断写进李四的目录（于是张三在自己的记忆页上看不到它，2.3 的可见性当场失效）。
判据是 I16④。

### 2.5 记忆和模型的交界

这一条放在这里，因为它是结论 3 唯一一处会被误读成记忆问题的地方：
**换模型不换记忆。** 记忆挂在 (实例, 关于谁) 上，与这一轮用哪个脑子无关。
「解不了 → 换个强的」在设计上是**交给一条活去解**（结论 3），
那条活是同一个 agent 的另一条线程，读同一批文件——所以换脑子从来不会丢上下文，
这正是「不在聊天里换脑子」代价很低的原因。

## 3. 组件与边界

用「能力」描述，不用实现。

| 组件 | 它回答的问题 | 它绝不回答的问题 |
|---|---|---|
| **后端** | 谁是参与者、谁有席位、房间里发生了什么、一个事件关于什么、这一轮该不该要手、在哪个地点用哪个骨架跑、这条活绑哪个模型、改动落到哪个托管方、每一句用户看到的话是什么 | 这台机器上装了什么（agent 自己去看）、某个项目的配置是什么意思、这次检查该不该过 |
| **连接器 cli** | 这台机器在线吗、开一个屏、把文件放进去、跑一条命令、把字节流接出来、走的时候删掉自己那一个根 | 任何意义。`cli/internal/host/host.go` 开头就写着「The host wires those together and **ascribes no meaning to any of it**; all behavior lives in the server」——**这是今天做得最干净的一条边界，架构上不要动它** |
| **骨架** | 把一段输入送进一个 agent，把它做的事变成事件；声明自己的物理限制；起一个子 agent 并给它的事件带上可归到卡的线程标识 | 产品概念长什么样；这一轮跑不跑；这一轮用哪个模型；这条活派给谁（那是 agent 的工具调用，结论 43） |
| **执行机** | 工作树在这里、命令在这里跑、我现在能看到什么 | 会话在哪（会话可以不在这台机器上）、这一轮跑不跑 |
| **托管方** | 合并、外部提案、检查结论、推不推得回外部远端、有没有写那个远端的凭据 | 检查本身、卡面文案 |
| **模型供给与计量**（4.6，**不是第四个接口**） | 这一轮的模型请求走哪条供给、花了多少记在谁头上 | 这一轮在哪跑（那是地点）、这一轮由什么驱动（那是骨架）、**换不换模型**（那是这条活的绑定，供给不许自己改） |
| **前端** | 把平台给的码渲染成界面 | 任何产品判断。今天两处反例：`ProjectSettingsView.vue` 自己算「哪几条规则能改」；`api/routes/chat.py:180` 的 `summon` 是浏览器算出来的布尔，决定这一轮**跑不跑** |

### 3.1 平台 MCP 与项目工具的分界

这是结论 21、22 的正文。

**平台的 MCP 永远在 claude 进程所在的机器上（会话侧）** [已定] 结论 21。
六样：`chat_send`、`cheese ask`、反馈、**要一台机器**（在工具表上是「开一台机器」和「换到 Cloud」两个动作，6.3）、同 handle 便条、定时投递。
它们要的是**平台**，不是文件系统——一台执行机掉线，这六样一样都不该少。

今天的物质基础已经对：`agent/cli_worker.py` 的模块 docstring 逐字
「平台 CLI 在机器上的那一份：一棵 argparse 树，一个预加载进程……
Claude Code serves them through its MCP transport, pi registers them as extension tools」，
而且它「is shipped to a **session machine** as a loose script」。
所以「平台工具住在会话侧」不是要造的东西，是要**守住**的东西。

**其他一切工具一定在开出来的手上** [已定] 结论 22：
`Read` / `Edit` / `Write` / `Bash`、项目 `.mcp.json` 里的 MCP、项目自己的 CLI。
项目 `.mcp.json` **由仓库自带**，平台在 `harness/claude_code/remote_execution/bootstrap.py:228`
**读**它（`mcp = work / ".mcp.json"`，存在就把 `mcpServers` 交给执行器配置），全仓没有一处写它——
所以支撑结论 22 的论据不是「平台把它放在工作区侧」，而是**它跟着工作区检出走，地点没了它就没了**。

**地点没了它们就是不可用，如实标出来**——
不在会话侧做替身，也不把项目工具搬到中心机。展开在 6.3。

## 4. 三个提供者接口

这三个接口在今天的代码里都已经存在，而且是这个仓库里写得最好的三处抽象：
`harness/channel.py:31 class Channel`、`harness/__init__.py:413 @dataclass Harness`、`review/forge.py:33 class Forge(ABC)`。
问题只有一个，而且三处一模一样：**接口声明了能力，上游没人读，于是上游按名字重新分了一遍岔。**
所以这份设计的主体不是「造什么」，是「把做选择的那几行代码搬到接口上，然后钉死」。

### 4.1 地点接口

今天叫 `Channel`，已经是能力声明式的：`embeds_images`（`:50`）、`provisions_machine`（`:77`）、
`builds_model_env`（`:97`）、`sandbox_memory_mb`（`:103`）。
`builds_model_env` 那段注释（`channel.py:85-97`）是全仓最好的一段论证：
「A capability, not a name. The turn path decided this by NAME twice, and each time
**the name aged into a list of the channels that happened to have the trick on the day it was written**」。

**要加的能力位**（都是物理事实或用户授权，不是产品功能）：

| 能力位 | 它说的事实 | 今天在哪 |
|---|---|---|
| `supply` | 这台机器是平台开的还是人接入的 → 谁有权销毁它 | 有，但在 `DeviceRow.supply`，不在接口上 |
| `visibility` | 这一轮看得见整台机器，还是只看得见自己的工作树 | 有，但在 `DeviceTopicRow.visibility`，不在接口上 |
| `lease_expiry` / `release()` | 这段使用权什么时候到期、怎么归还（结论 24） | **不存在**。`DeviceTopicRow` 是无期限 1:1 绑定 |
| `sleep()` / `wake()` / `reconnect_window` | 闲置快照后停机，window 之内醒来是同一台机器、工作区原样——**租约的第三态，只有 `supply=cloud` 的实现给得出**（结论 39） | **不存在**。今天一台机器只有在用和没了两种样子 |
| `footprint_root()` / `evacuate()` | 平台放在这台机器上的一切在哪个目录下；卸载 = 删它 | **不存在**。今天平台写两个根，而根名有**两种形状、四个文件五处声明**：二元组 `(".cheese", ".claude")` 写了两遍（`environment_runner.py:84`、`resource_cleanup.py:25`；`private_chat.py:14` 是 import，不算第三份），另有三个单根常量（`machine_launcher.py:57`、`bootstrap.py:22/23`） |
| `provisioning_state` | 「这台机器还没好」——一个**可见的等待**，不是一次失败 | 只有 Cloud 有，挂在 `machine/repositories.py:101 list_ready_topic_devices` 上（docstring 第一个词就是「Cloud leases」，五个条件全在 `ProjectMachine` 表上）；自托管**没有那张表的行** |

**两个不要的能力位**：

- `waits_for_owner` **不要**：它逻辑上等于 `supply`，一个可由另一个字段推出的事实被单独声明一遍，正撞 I4a。
- `hosts_session` / `hosts_workspace` **不要**，改成另一种形状：
  原提法把「中心会话机包住执行机」这**一个当前部署安排**编进了接口
  （今天由 `cloud_provider.py:31 CloudChannel(DeviceChannel)`、`central_provider.py:76 CentralChannel(DeviceChannel)` 隐式表达）。
  正确形状是：**需求在轮次这一侧声明，不在地点这一侧声明**——
  一轮显式说明它需要几种地点（一个会话地点、零或一个工作区地点），地点解析返回 0–2 个租约。
  这正好也是结论 21、22 那条分界在解析路径上的形状。
  **那个工作区地点是房间的那一个** [已定] 结论 38：活不声明自己的环境，子 agent 也不声明，
  所以一个房间里同时跑着多少条活，地点解析的结果都是同一份租约。

**三个实现**：

| 实现 | supply | visibility | 用户看到的一句话 |
|---|---|---|---|
| 平台开的机器（今 `CloudChannel`） | cloud | host | 「平台为这个房间开一台机器，第一次要等几分钟」 |
| 你接入的机器 · 整机（今 `DeviceChannel` + `visibility=host`） | self_hosted | host | 「跑在你自己的机器上，它能看到整台机器」 |
| 你接入的机器 · 沙盒（#358 里的第三种机器形态；今天没有传输层实现） | self_hosted | isolated | 「跑在你自己的机器上，只看得到这个房间的工作树」 |

**本节最重要的一句诊断**：这三档在代码里是**两种机制**——
「平台开的 / 你接入的」是 `market.py:29-30` 的两个 pool 名（`COMPUTE_DEVICE` / `COMPUTE_CLOUD`），
「整机 / 沙盒」是绑定表上的一列（`DeviceTopicRow.visibility`）。
同一个轴，用户在界面上当成一件事挑，代码里走两条完全不同的路。
`CloudChannel(DeviceChannel)` 是这个错位的直接后果：Cloud 不得不继承 device，因为它其实就是 device 的一个取值。
而 `compute.py:364` 的 `isinstance(c, DeviceChannel)` 因此**恒为真**——读起来像一条能力规则，实际什么都没排除。

**这不推翻 #442**：#442 反对的是「code models them as one kind of thing with **two independent switches**」——
两个互不约束的开关。本设计给的是一个接口、一张能力表、一张封闭的差异码表，销毁权照旧只从 `supply` 推出来。

### 4.2 骨架接口

今天是 `AgentRuntime` + `Harness` 注册表，能力位三个：
`speaks_gateway`（`__init__.py:437`）、`carries_subscription`（`:441`）、`draws_on_its_screen`（`:453`）。
五个动词的契约（`ensure / send / backlog / interrupt / close`）写在文件开头，论证也是对的：
「Reading from a cursor is what makes recovery a reconnect instead of a salvage operation」。

#### 契约对所有实现、所有语言一样

[已定] 结论 29。三句：

1. **会话身份和 transcript 的权威副本在平台**，每轮结束前增量交上来；**恢复从平台副本恢复**。
2. **pi 满足它的路径倾向和 Claude Code 同一条**：进程在中心机、工具走执行器。
   今天 pi 不是这样——`harness/pi/channel.py:204-209` 把会话位置写进 `room.session_placement`，
   会话记在执行机上，执行机重启会话就没了。
3. **契约测试要盖到 pi 的 TypeScript 侧**（`harness/pi/platform.ts`）：
   pi 的机器侧算一个实现 [已定] 结论 29。

这三句合起来把「agent 不死」从「Claude Code 房间的一个特性」变成**骨架契约的一条**，
而不是两类房间各有各的命。

#### 硬性要求：原生 subagent

[已定] 结论 43。**派活是 agent 对骨架原生 subagent 的一次工具调用，不走平台**（1.5）。
骨架这一侧因此有四条**硬性要求**，不是一个可以声明「我没有」的能力位：

1. **能起一个子 agent，并指定它用哪个模型**——模型是这条活的资源绑定（1.5、4.6），
   起不了带模型的子 agent，这条绑定就落不下去。
2. **子 agent 的事件带一个可归到卡的线程标识**，平台的 hook 按它把事件挂上那张卡。
3. **父线程能改它的指令。**
4. **父线程能停掉它**——「停掉」就是本节那五个动词里的 `interrupt`，
   和「人在卡上按停」（8.1）是同一个动词的两个调用者，不另立第二条停止通路。

**为什么是硬性要求而不是矩阵上的一格**：派活整个住在骨架里，平台在那条路径上只有卡。
一个起不了子 agent 的骨架不是「少一项功能」，是**派不了活**，而派活是这个产品的主干。
按 4.4 那张表自己的准入判据，能进去的是平台修不掉的世界状态或用户的授权边界；
「这个骨架接不接得上主干」是接入资格，不是一条差异。
**结论 30 曾把它写成另一个样子**——一条「后台分身应当支持」的能力位，并给起不了的骨架留了一条差异码「这种房间做活期间不可答话」；
[已定] 结论 43 取代了那个措辞（它逐字写着「本条取代第 30 条里『后台分身应当支持』的措辞」）：
起不了子 agent 的骨架接不进来，那条码不存在（4.4）。

**平台这一侧的对应项同样是硬的**：先开卡再起子 agent、hook 按线程标识归卡、结束写结论、
人对卡的操作投递给父线程执行（1.5）。
**子 agent 与父进程同生同死**，所以恢复不是把那条线程接回来，是**从分支重派**——
「边干边 commit」因此是 skill 的硬要求，分支上的提交是这条活唯一活过父进程的东西。

#### 准入判据：能力位只能描述骨架的物理事实，不能描述产品功能

- `carries_subscription` **合格**：订阅凭据为一个骨架铸造，别的骨架物理上拿不了。
  今天 `agent_instance/configuration.py:104-113 _drives()` 的注释逐字说明了这个方向
  （「The credential, not the shape」，注释在 `:107-109`，读能力位的那一行在 `:110`）。
- `draws_on_its_screen` **合格**：TUI 在屏幕上画东西，跑 runner 的骨架那面屏永远是空的。
- **起子 agent** 不上这张表（结论 43）：它不是一个可以声明有无的能力位，是接入资格，见上一小节。
- 「有没有进度清单」**不合格**：那是产品概念。今天它钉死在 Claude Code 的四个工具名上
  （`chat.py:569 _TASK_TOOLS = {"TaskCreate", "TaskUpdate", "TaskList", "TaskGet"}`，
  `chat.py:3271` 是 `TopicProgress` 唯一写入口）。后果见 7.2 那张表。
- 「每轮结束自动同步」**不合格**：只有 Claude Code 有
  （`harness/claude_code/device_launch.py:303` 的 `exec cheese sync --all` 脚本 + `:767` 的 `sync_on_stop`）。
- 「太久没说话要提醒」**不合格**：同一件产品功能有两个产生方——
  平台侧 `chat.py:1533 remind_silent_turns`，机器侧 `harness/pi/platform.ts:624 QUIET_LIMIT`。见 9.4。

#### 消费判据：每个洞必须至少有一个上游读者，且所有读者读同一个判定函数（I7）

`carries_subscription` 今天全仓只有三处命中——定义（`__init__.py:441`）、赋值（`:457`）、
**唯一的读者是下拉菜单**（`agent_instance/configuration.py:110`）；
而修法正是让启动路径也读它。今天的后果：一台只跑 pi 的机器照样拿到订阅凭据，正确性靠一条 `NO_PROXY` 撑着。

#### 「产品概念由平台 CLI 提供，并且把骨架自带的那个关掉」

仓库里已经做对过一次 [已定]：
`harness/claude_code/cli.py:15` 的 `DISALLOWED_TOOLS = ["AskUserQuestion"]`，
docstring 逐字说明了为什么（「`cheese ask` is the platform's equivalent……
so the native tool is denied outright rather than left as a trap」）。

而「关掉」这个动作**在接口上今天不存在**：在 Claude Code 上是 `--disallowedTools`（cc 独有的命令行开关），
在 pi 上没有对应物——pi 一共只注册了五个钩子（`platform.ts` 的 `:186 before_agent_start`、
`:586 session_start`、`:602 session_shutdown`、`:628 turn_end`、`:640 context`），没有任何 todo / 提醒入口可翻。
**它该长成什么样**：一个骨架**声明**它自带哪些产品概念（`provides_natively`），
平台在启动时对每一项要么要求一个关闭动作、要么把那一格记成 4.3 的 `暂缺`；
关闭动作本身是**适配层的实现**，接口只负责断言「已关」。
**抽象形式仍未定，进第 11 节。**

**公共通路那一半是有实证的**：`cli_worker.py` 的 docstring 已经写明三个骨架取的是同一棵 argparse 树
（`backend/sandbox/cheese:935 build_parser()`，31 个顶层子命令）。

### 4.3 功能矩阵怎么保证一致

三个接口各有一张表。行是**产品能力**，列是**实现**，每一格只有三种合法值：

- **有**——并且这一格在契约测试里有一条对所有实现跑同一套断言的用例；
- **一条差异码**——来自封闭枚举 `Difference`（4.4），由平台翻译成一句用户语言；
- **`暂缺(issue, 到期日)`**——到期之前 CI 绿，到期之后 CI 红，且加它必须带一个 issue 号。

第三种值不是「还没做也算合法」：矩阵一上线就会有一批真实的空格（pi 的进度清单、pi 的每轮同步），
红着不修就是把守卫训练成噪音。带到期日的 `暂缺` 既让空格当场可见，又让它不能无限期存在。

新增一个实现而不填满它那一列，CI 红。照抄仓库里已经落过一次的守卫形状：
`tests/contract/test_api_addressing_contract.py`（#370 收尾时落的，双向失败）。

**这不违反 `agent-principles` 十二**：矩阵是一道守卫，不是产品功能、不是一种轮次、不是状态机。
它跑在 CI 里，用户和 agent 都看不见它。

### 4.4 `Difference`：封闭的差异码表

**准入判据**：一条码要么是**平台修不掉的世界状态**，要么是**只有用户能改、平台不得代改的授权边界**。
**平台自己能补上的缺口不许进这张表**——按 `agent-principles` 九，
把一个缺口写进封闭枚举，等于给它发一张永久居留证。

| 码 | 类别 | 差异 | 用户看到的话 |
|---|---|---|---|
| `machine_is_yours` | 物理 | 这台机器不是平台开的，平台无权销毁它 | 「这台机器是你的，平台只会停止使用它」 |
| `machine_must_be_built` | 物理 | 用之前要先造出来 | 「正在为这个房间开一台机器」 |
| `screen_has_no_picture` | 物理 | 这个骨架不在屏幕上画东西 | 「这种运行方式没有可以旁观的画面，改用施工记录」 |
| `credential_is_single_harness` | 物理 | 订阅凭据由供应商为一个骨架铸造 | 「这个模型只有某一种运行方式能用」 |
| `boxed_to_workspace` | 授权 | 机主只授权了这个房间的工作树 | 「它只看得到这个房间的工作树」 |

**不进这张表的两条**，以及它们落在哪：
「这个托管方不跑检查」是 `reports_checks=否` 这个能力位本身，用户那句话由平台文案目录按能力位渲染；
「没有外部远端」是**项目的状态**，不是实现之间的差异。

**五条之外的任何差别都是 bug 或缺口，不是配置。** 加一条新码需要人评审。
「这个骨架起不了子 agent」进不了这张表 [已定] 结论 43：它是接入资格，不是一条差异（4.2）。

### 4.5 托管方接口

今天是 `Forge` ABC（`review/forge.py:33`），四个操作 + 一个能力位 `has_external_checks`（`:35`），
两个实现：`GitHubForge`（`:87`）、`PlatformForge`（`:120`）。

**要改的形状**：能力位从一个变成五个 [我提的]，上位依据是 #363 那张 provider 表；
并且 `resolve()`（`:153`）不再问「这个 URL 像不像 github.com」。

| 能力位 | 它说的事实 |
|---|---|
| `reports_checks` | 这个托管方跑不跑检查、平台能不能读到结论 |
| `hosts_proposals` | 改动在外部有没有一个可以被人打开的提案页 |
| `can_write_remote` | 我们有没有写那个远端的凭据（去问 `domain/agent_credential/`，165 行） |
| `pushes_to_external_remote` | 有 upstream ∧ `can_write_remote` |
| `identity` | 提案与合并署谁的名（用户的，还是平台的 App） |

| 实现 | reports_checks | hosts_proposals | pushes_to_external_remote | 对应哪种项目 |
|---|---|---|---|---|
| GitHub | 是 | 是 | 是 | 绑了 GitHub |
| **外部远端（新）** | 否 | 否 | **是** | 有 git 远端但不是 GitHub（gitee、校内 GitLab、自建） |
| 平台 | 否 | 否 | 不适用 | 什么都没绑 |

**中间这一档今天在代码里根本不存在**：
`review/services.py:3181 _github_bound()` 的判据是「App installation **且** `parse_github_repo(upstream)` 解析成功」，
它作为回调传进 `forge.resolve(is_github_bound=...)`（`services.py:3177` → `forge.py:153-167`），
所以**判据在 `services.py`，接口在 `forge.py`**——gitee / 校内 GitLab / 自建一律 False，落 `PlatformForge`。

**能发生的后果**：一个用校内 GitLab 的老师填了自己的仓库地址、点了同步、看见历史进来了，于是合理地认为这是双向的。
此后每一次采纳都只落在平台自己的仓库里，他的 GitLab 一个 commit 都收不到，**没有任何一句话告诉他**。
反过来，一个填了地址但没给我们写权限的项目，会拿到一个永远推不上去的 forge——
所以 `can_write_remote` 和「有没有 upstream」必须是**合取**，缺一半就是同一个坑的镜像版本。

### 4.6 模型供给为什么不是第四个接口

**结论：它不是第四个提供者接口。** 理由是它的决定变量里没有「在哪跑」：
[已定] 他 2026-09-09T21:44「model」「和harness」「是分开的吧」——
**供给按 `(骨架, 模型)` 决定，不按机器形状决定**。
今天 `agent_instance/configuration.py` 的模块 docstring 已经把这个方向写对了：
「**a harness is what can drive a model**, never the other way round……
`model_choices` 答『这个项目能跑什么』，`harness_choices` 答『每个 harness 能被指向哪些模型』」。
这句里的 `model_choices` 就是结论 44 那份**启用列表**在代码里的位置——项目级只有它和默认模型两样（1.1）。

所以它分成三块，各归各的主人：

| 这一块 | 归谁 | 今天在哪 |
|---|---|---|
| 「这个骨架能不能拿到供应商为它铸的订阅凭据」 | **骨架接口的一个能力位** | `Harness.carries_subscription` |
| 「这一轮的模型请求走哪条供给」 | **一张 `(骨架, 模型) → 供给` 的注册表**，不是接口 | `domain/llm/`（1136 行）+ `core/config.py` 的 `agent_harness_models` |
| 「这一轮花了多少、记在谁头上」 | **事件（1.10）的一种**，落在这条活的卡上，记在项目的账上 | `domain/usage/`（705 行） |

#### 四类不许静默降级（I27）

[已定] 结论 3 把不许静默降级的类别定为四类：
**供给降级只能拒绝或可见等待，不悄悄换模型**——否掉网关按可用性换模型那种 fallback。

- **花钱**：正例 `api/routes/llm_proxy.py:211`（拿不到项目虚拟 key 就拒绝，理由逐字「would bill every project to one bucket」）。
- **署名**：反例 `review/github_pr.py:1448`，docstring 逐字
  「Falls back to the App on any failure: a PR that exists under the wrong name beats no PR at all,
  and **the fallback is invisible to everything downstream**」——
  用户的 GitHub 授权一失效，此后所有 PR 悄悄署成 bot 的名。
  `agent-principles` 五所依赖的「谁写的/谁要的/谁批的」从这一刻起是错的。
- **认身份**：`Actor.via` + 路由级 cheese-gate 那条第二授权线（1.2）。
- **换脑子**（新）：一条活绑了哪个模型，是**这条活的事实**。供给不可用时的两个合法出口是
  「拒绝」和「可见的等待」，第三个出口（换一个能跑的）不存在。

**第三档「可见的等待」的依据** [已定方向] #442 decision 2 明写
「that wait must be **a visible provisioning state, not a failure**」。

## 5. 投递

### 5.1 事件落在它「关于」的那个东西上

[已定] 结论 14（I10）。落点是一张封闭表，不是每个调用点自己挑一个 `topic_id`：

| 事件 | 落在哪 | 例子 |
|---|---|---|
| 关于一件活的 | **那张卡** | PR 绿了、检查红了、上游冲突、这一轮换了模型、**一次打断** |
| 关于一个房间的 | **房间时间线** | 机器离线、成员加入、有人说话 |
| 关于一个项目的 | **项目总览**（1.4） | 房间创生、房间归档、主干新提交、名册变化、巡检到点 |

**机器状态也是一条事件，而且收件人里有 agent** [已定] 结论 40：
平台把「这台机器够不着了」送到 agent 面前（6.3 那条能力事件），处理它的是 agent 不是平台。
落点按同一条规则——它关于的是这个房间的那台机器，所以落房间时间线。

**一次打断也是一条事件**（1.11、4.2 的 `interrupt`），按同一条规则落点：
打断的是卡上那条活的一轮 → 落那张卡；打断的是房间主线的一轮 → 落房间时间线。
它不是一次失败，也不回滚——打断之前这一轮已经做的事照常留在 transcript 里（8.1）。

**「PR 绿了」不是一条消息，是卡的状态变了**，然后按 5.2 通知验收人。
这条区分是整节的支点：一旦事件先落在它关于的东西上，
「谁该被通知」就变成一个从状态迁移算出来的问题，而不是一个每处各写一遍的 if。

### 5.2 收件人规则：对每一种事件都是同一条

[已定] 结论 15（I11）。
**从「下一步在平台手上」转入「下一步在某个参与者手上」的那一刻，通知那个参与者，一次。**

这条明确取代了「一律告诉人」。**它收紧的是 `agent-principles` 十四的「谁被告知」，不动「不重跑」**——
第 10 节写明这处修订。

寻址结果 `(事件, 收件人集合, 原因)` 只允许由两个产生方算出来，两者共用 `room_task/awaiting.py` 的判据：

1. **一次列变化**——一件活从「下一步在平台手上」转到「下一步在某个参与者手上」（`room_task/presentation.py` 的 `Column` 迁移）；
2. **一次点名**——一条事件里的 @ 解析出的 handle 集合。

这样 @ 是同一条规则的一个实例——**同一条规则的两个产生方，一个出口**，而不是两条规则。

**策略闸门产生的提议走的也是这一条** [已定] 结论 40：
agent 调「开一台机器 / 换到 Cloud」，撞上项目策略（换到另一台自托管要机主同意、超费用档位要人点头），
这次调用就自动变成一条**给人的提议**——下一步从平台手上转到了那个人手上，按同一条规则通知他一次。
它不是第三个产生方，是「一次列变化」的一个取值。

**今天三套并行**：`presentation.Column` 在读的时候算「该谁动」却不发通知；
`agent/announce.py` 在散落的调用点发通知却不读 `Column`；`chat.py:4183` 的 @ 自己发一条 `AlertKind.mention`。
而 `announce.py:143` 的 `if meta.get("who") != WHO_HUMAN:` → raise
**在代码里把「agent 不能是收件人」写成了不变量**（I9 的正主）。

### 5.3 总览与调度

[已定] 结论 16。**总览里的芝士就是调度者，没有 scheduler 部件。**
拆解见 1.4。这一条的设计理由是 `agent-principles` 十二：
「如果一件事在『你开口让 agent 干』时它本来就会干，那它不该被做成平台的一个功能、一种轮次、一个状态机。」
巡检正是那张表里已经列过的一个实例（「定期巡检（心跳）：平台替它想起来该催人」）。

### 5.4 平台从不发起一轮

[已定] 结论 13（I12）。**平台只投递。** 今天 5 处平台自召唤全部改写成「事件 + 收件人」：

| 今天 | 在哪 | 改写成 |
|---|---|---|
| kickoff（分身开局） | `runtime.py:784-806`，`author="system"`，内容 `KICKOFF_PROMPT`，`summon=True` | **不存在**了：结论 31 把第二身份和第二会话一起去掉，结论 43 把起子 agent 定成 agent 对骨架的一次工具调用——平台既不投递它的第一轮，也没有 kickoff 可发 |
| 定时 | `scheduler/service.py:445` | 一条定时投递（5.6），收件人是请求它的那个参与者 |
| 上游冲突 | `workspace/upstream_conflict.py:140` | 一条**关于这条活**的事件（5.1），收件人按 5.2 算 |
| 工具通道恢复后重发 | `runtime.py:1408` | 一次**重新投递**，不是新一轮 |
| 延迟重发 | `runtime.py:1441` | 同上。它自己的 docstring 已经写明「It is a re-delivery, not a 'pick up where you left off' nudge」 |

**`SELF_STARTED_AUTHOR` 那种轮次也退场**（结论 13）：
`runtime.py:821` 今天有 `SELF_STARTED_AUTHOR = "session"`，注释逐字「an interval the SESSION opened for itself……
nobody wrote its prompt, so there is nothing to re-send」。
按结论 11，一个 worker 做完唤醒主线程，那是一条**同 handle 便条**（5.5），有明确的发件人和收件人，
不需要一个「谁也没写它」的作者值。

还有客户端那一半：`api/routes/chat.py:180` 的 `summon = bool(payload.get("summon", False))`
是浏览器算出来的布尔，决定这一轮跑不跑（I13）。它和平台自召唤是两件事，两件都要没。

### 5.5 同 handle 便条

[已定] 结论 11。同一个 handle 在一个项目里是一个参与者，它在房间主线与各条活上的那些线程之间走**内部便条**：

- **读侧是投递**：走 `chat.py:1605 notify_running_turn` 那条通道，**不进时间线**。
  今天这条通道已经在用（`api/routes/topics.py:1246` 用它把文档变更递给正在跑的那一轮），
  所以它不是新机制，是给它一个正式的收件人语义。
- **写侧是平台 MCP 上的一个工具**，形状像 Claude Code 的 `SendMessage`。按结论 21 它住在会话侧。

**不同 handle 之间只走 chat，agent 对 agent 也是** [已定] 结论 12（I14 后半）。
没有第二条私下通道——两个 agent 要说话，就在房间里说，人看得见。
这是 `agent-principles` 四（安全靠可见）在多 agent 下的直接推论。

### 5.6 定时投递原语

[已定] 结论 17。平台提供**一个**原语：**任何参与者可以请求「某时刻把这条投递给我」**。

它是一条原语而不是一个功能，判据在 `agent-principles` 十二：
平台不替任何人想起来该干什么，它只是在被要求的时刻把一条事件递出去；
想起来要设这个闹钟的是参与者自己。收件人就是请求者，所以它不需要第二条收件人规则。

`domain/scheduler/` 那 615 行退场之后，这个原语是它唯一留下的东西。

## 6. 生命周期与机器离线

### 6.1 谁先谁后

```
参与者 ───────────────────────────────────────────────────────────  年   L0
  └ 席位（参与者 × 房间）─────────────────────────────────────      月   L0
      └ 会话（agent × 线程位）───────────────────────────           周   L1
          └ 轮次 ───────                ───────                    分钟
              └ 租约：一个地点 ──          ──                        分钟~小时
                  └ 工作区检出 ─            ─                        分钟~小时  L2
骨架（部署期就在，不随任何对象生灭）
模型（这条活的一个绑定，随活改，不随参与者改）
```

**规则：上面的东西的生死，不由下面的东西决定。这一条就是「agent 不死」的全部内容。**

**租约那一层挂在房间上** [已定] 结论 38：活不在这张梯子上另开一层，
它用房间的那台机器，所以一个房间里同时跑着多少条活，租约都只有一份。
**要另一台机器，那就是另一个房间。**

**会话先于地点**，这是本设计与今天最大的一处倒置。
一轮的执行顺序应当是 `解析被点名的参与者 → 取/建会话 → 问 needs_place → 需要才去租一双手`；
今天是反的：`central_provider.py:89-100 precheck` 确认中心机在线之后**无条件**
`return await self.executor.precheck(...)`。

**`needs_place`——这一轮需不需要手？** 今天没有任何地方问这个问题，所以每一轮都去要手。
这个问题的归属在骨架接口上：只有骨架知道这一轮解析出来的动作要不要文件系统。

### 6.2 各自的生灭

| 对象 | 生 | 灭 | 它死了谁不受影响 |
|---|---|---|---|
| 参与者 | 注册 / 从一个类型建实例 | 不销毁，只停用 | 全部 |
| 席位 | 加入房间 | 移出即撤权 | 它签过的名、它写过的事件 |
| 项目 | 人建；**同一刻播种一个芝士实例并在项目总览给它席位**（结论 4） | 人删（带导出承诺，结论 27、I19b） | 参与者 |
| 房间 | 任一有席位的参与者 | **只有人能归档**；归档是回收触发器 | 参与者、项目、记忆、产物 |
| 活 | 人或 agent，同一条规则（结论 33） | 采纳或放弃 | 房间、参与者 |
| 会话 | 第一次被点名，**不需要机器在线** | 它的线程位（房间主线/活）被销毁，或人显式丢弃 | **地点换了，会话不死** |
| 地点 | 人接入 / 平台按需开 | 平台销毁（仅 cloud）/ 人拔掉 / **租约到期归还**。**休眠不是灭**（仅 cloud，结论 39）：停机而已，reconnect window 内醒来是同一台 | **房间、会话、名册、通知、事件，全都不受影响** |
| 工作区检出 | 活开始时 | 随租约 | 源分支（权威副本在仓库上） |

### 6.3 机器离线：状态在哪、谁被通知、agent 拿到什么

| 情形 | 状态存在哪 | 谁被通知（按 5.2） | agent 拿到什么 | 下一步由谁 |
|---|---|---|---|---|
| **轮次中途机器掉线** | L0 全在库里一行不动；会话身份在 `agent_sessions`，transcript 增量已在后端 | 房间里一条事件 + 这个 agent；自托管还要加机主 | 一条能力事件（下面给文本），不是一个 HTTP 状态码 | 这一轮结束，**不重跑**；再点名才有下一轮 |
| **轮次开始前机器不在（自托管）** | 同上 | **机主**——下一步在他手上（他去开机）。房间里写「正在等这台机器」 | 同上；不需要手的轮次照常跑完 | 不换机器、不改绑定，但照记健康账、照告知在等 |
| **Cloud 机器正在开 / 已死** | 同上 | **不通知任何人**——下一步在平台手上；房间里留一条可见的等待事件 | 同上 | 平台：另开一台并把会话搬过去 |
| **Cloud 机器在休眠中**（结论 39） | L0 全在库里；工作区快照原样躺在那台机器上 | **不通知任何人**——下一步在平台手上 | 一条可见的等待事件，不是一次失败 | 平台：window 内唤醒同一台，工作区原样；window 过了才走归还与收据（6.5） |
| **换到了另一台机器** | 会话跟着走（rehome） | 房间 + 这个 agent | 「换机器了，工作区已按分支状态重建，未提交的改动没有跟过来」 | 正常继续 |
| **中心会话机离线** | L0 不动；会话身份与 transcript 增量在库；**会话的躯壳没了** | 房间里一条「正在等一台会话机」的等待事件；不通知任何人 | 同上 | 平台：等它回来，或 rehome 到另一台会话机 |
| **后端重启** | L0 在库；**L1 的躯壳在机器上继续活着**；L2 不受影响 | 无 | 无（它没掉线） | 靠重新发现接回；在途的一轮发一次事件然后停下，**不重跑** |

**中心会话机是一个单点，而他已经明确接受了现阶段**：`settings.agent_session_device_id` 是一个部署级常量；
[已定] 他 2026-09-17T02:15「这意味着 绑死了一个project的所有rooms 的claude进程都得在一台机器上」「**当然现阶段也不是不行了**」。
本设计不要求池化，只要求 placement 是会话的属性、且可被改写。

**「后端重启不带走任何东西」今天基本是对的，本设计保留它**——
`central_provider.py:132-133` 明写「Finish consuming turns that began before this deployment.
Their next opening transfers the transcript; **no new prompt starts on the old host**」。

#### agent 拿到的那条事件

[已定] 结论 23。**它是一条事件，不是一次工具报错**（I25），内容是三句能力话：

> 「这台机器现在够不着：**文件、命令、项目 MCP 不可用；对话、记忆、平台工具可用**。」

而且**那一轮的工具表里项目工具直接标不可用，不让它们各自超时**——
这是结论 21/22 那条分界的直接兑现：
平台工具在会话侧，所以它们照常；项目工具在那双手上，所以它们当场标死。

**不解释是什么故障**，不给它一份平台内部术语表（`agent-principles` 八）。
今天它读到的字面是 `executor_transport.py:324` 的 `f"Executor HTTP request failed: {response.status}"`——
后端已经写好的 `X-Device-Id` 头和中文 body 全丢了。

**平台不替 agent 处理它**：给它事实和一条它够得着的通路，不是一套平台替它做的恢复流程。

#### 机器离线由 agent 处理

[已定] 结论 23、40。平台做的只有一件：**把机器状态作为一条事件送到 agent 面前**（上一段）。
处理它的是 agent，手段是平台 MCP 上的两个工具（结论 21 那六样里的「要一台机器」，3.1）：

- **开一台机器**
- **换到 Cloud**

**策略闸门让这次调用自动变成一条给人的提议** [已定] 结论 40：
换到另一台自托管要那台机器的主人点头，超出项目费用档位要人点头。
闸门没放行的调用**不是一次失败**，是一条投递给那个人的提议（5.2），下一步在他手上；
Cloud 且在档位内的，平台自己开，不问谁。

**平台不设等待超时器** [已定] 结论 40。没有「等 N 分钟还不好就自动换一台」这种东西：
状态变了就再送一条事件，什么时候放弃这台、什么时候换一条路，是 agent 的判断。
这是 `agent-principles` 十二在机器这一侧的取值——平台不替它想起来该干什么。

**换成功后告知丢了什么**（一张收据，结论 23）。

这整条都不是「平台自己续跑」：agent 自己开口要资源，平台给或不给，然后照常投递。

### 6.4 会话搬家（rehome）

会话既然不属于机器，换机器就必须是一个**正常操作**而不是一个错误。
接口形式：`Session.rehome(new_place)`。
**它的完成判据不是接口存在，是**：`transfer_history` 的源可以是**平台存的 transcript**（结论 29），
而不只是另一台机器，且它的调用点不再只有「首次 placement」这一处。

**一句必须写进定稿的消歧**：**rehome 不是「平台自己续跑」**——
它只保证下一次有人点名时接得回同一份 transcript，平台不会自己发起那一轮。
**换机器是资源层的事，续跑是点名层的事。**

### 6.5 回收与收据

[已定] 结论 24。**机器随时可回收：地点是有期限、可归还的租约。**
**#442 第 3 条（「A Cloud machine is reclaimed when its topic is archived. No idle sweeper, no new timer」）
是旧模型的决定，不再是设计约束。**

**休眠不是回收** [已定] 结论 39。Cloud 的租约闲置到点是快照后停机，
reconnect window 之内醒来是同一台机器、工作区原样，**这条路上一张收据都不取**；
window 过了才转成归还，那时下面三张一张不少。把休眠也套上收据，等于每次闲置都跑一遍记忆整理。
**这条闲置计时是租约自己的，不是 6.3 否掉的那种等待超时器**——它不替任何人决定换不换机器，
只把没人用的机器停下来；「等 N 分钟就替 agent 换一台」那种计时器一个都没有。

**回收前三张收据**（I19）：

1. transcript 落库；
2. 记忆整理跑过（[已定] #1078「整理这件事……时机也对：**沙箱回收之前跑，因为只有那台机器上才有代码可以对照**」）；
3. 未提交工作已推。

形式是一个**函数**而不是一段散文：所有回收路径（归档清理、Cloud 释放、容器回收、会话机 drain）
走同一个 `receipts_ready()`，收据不齐就保持 pending 并说明理由。

**代际号**是「一个对象一条命」（I20）在时间维度上的解：
任何跨进程的延迟操作（停止、删除、清理、回收）携带它作用对象的代际号出发，不匹配就丢弃。
[已定方向] #927。今天只有 `topics.resource_id` 是这个东西，而全仓只有
`topic/services.py:721` 一处会 bump 它——而且它长在房间上，按本设计应该在会话和地点上各一份。

## 7. 三条统一

**他给的判据**：「现在代码 too many fallbacks」；他一贯的「no fallback glue, genuine unification」。
**收成的那条判据** [我提的]：**同一个接口、同一张表、同一条规则；差异只允许是 4.4 那张封闭表里的一条码。**
凡是需要兼容层、`if 是 X`、或者「两种形状各走各的」才能成立的，都不算统一。

**一句诚实话**：下面三条里，**只有 7.3（托管方）今天真的收敛成「一个接口」**；
**7.2（骨架）是「一个接口加三层适配」，7.1（地点）居中。**

**一个现成的、最生动的反例**：前端 `TopicMembers.vue:97` 的 `[...people, ...agents]`——
两份名册在**渲染时**拼起来。这就是「用兼容层把两个形状粘起来」的样子。

### 7.1 三种算力档 = 地点接口的三个实现

见 4.1 和 4.4。**功能矩阵必须满**，例外只有 `machine_is_yours`、`machine_must_be_built`、
`boxed_to_workspace` 三条码所对应的格子。
[已定] 结论 25：**hosted machine 没有独立用途；三档只差物理事实。** 用途最多影响默认值。

**一处今天就成立的不对称**：同一个处境（「我的机器还没好」），
Cloud 是一条持久的等待事件 + 连接器上来就自动重投，自托管是一次 turn 失败。
而那套自动重投挂在 `machine/repositories.py:101 list_ready_topic_devices` 上，
它的五个条件全部挂在 `ProjectMachine` 表上，**自托管设备根本没有这张表的行**。
所以「自托管也给一条可见的等待」不是复用，是给地点接口加一位 `provisioning_state` 并写第二个实现——
这与 4.1 的整体形状一致；把自托管塞进 `ProjectMachine` 则是在数据模型上重新合并 #442 刚拆开的东西。

**命名**：用户面不要给这三档起三个产品名，改用两句话描述：
**谁的机器**（你的 / 平台的）和**看多远**（整台机器 / 只看这个房间）。
理由是名字会反噬功能一致——一旦叫三个名字，用户就会预期三种能力。

### 8.1 普通用户看到

项目、房间（含项目总览与私聊）、成员（人和 AI 队友在**同一张名册**里，同一种行、同一套角色菜单）、

**关于模型，用户只在一个地方碰到它，而且看多于设** [已定] 结论 3：
**卡上**，与机器并排——「在哪台机器、用哪个模型、现在在做什么、花了多少」。
四条细则：

- **聊天（房间主线程）用一个稳定的模型**：项目默认，普通成员不碰；主线程不换模型，缓存一直热。
- **做事按活配脑子**：agent 派一条活时自己选（难的强、粗活便宜），在项目策略允许的档位内；
  超档要人点头就**提议**（一条投递，下一步在人手上）。
  **人可以在卡上改，也可以在卡上按停**——这个操作**投递给父线程执行** [已定] 结论 43，
  由它调骨架契约的 `interrupt`（4.2），和主线程停掉自己起的子 agent 是同一个动词；它结束这一轮（1.11），
  落一条关于这条活的事件（5.1），**打断之前这一轮已经做的事照常留在 transcript 里**，不回滚、不重跑。
- **每一轮实际用的模型随用量记在卡上**，显示**从记录算**，不是被 set 的状态（I17 第三条）。
- **改绑定下一轮生效**：同一份 transcript、一条事件；换脑子的一次性预填代价在改的地方亮出来。

机器同样只在两种时刻出现：**选一台**和**等一台**。
界面上允许出现的只有两句关于算力的话：**谁的机器**、**看多远**。

**看不到**：**骨架名与「运行方式」下拉**（结论 28：harness 是开发者选项）、
pool 名（`device` / `cloud`）、可见性枚举（`isolated` / `host`）、
托管方名（除非项目里真的有一个外部仓库，那时它的名字是那个仓库的名字）、机器 id、
`merge_method` 原值、`session_placement`、代际号、内部英文名。

   今天 `cheese uninstall` 停并卸载服务、删 `~/.config/cheese`、删掉自己那个二进制
   （`cli/internal/daemoncmd/daemoncmd.go:380-401`，它打印的「service, config, and binary removed」三样都真做了），
   **唯独不碰 `~/.cheese`**——claude build、toolchain、每个房间的会话 home 和工作树全部原地留着。
   平台在别人机器上占的是**两个根**，卸载只认得其中一个，这正是「足迹根必须唯一」的理由。
2. **接口上没有任何方法的实现可以提权**（I22）。
   今天 hosted 路径上确实没有 sudo，要钉住的是它继续成立。
   `#1034` 那半边「机器能力检查」搬过来时会撞上它（补装用 `sudo -n apt-get install`），
   所以只能是「检查与安装分开」。
3. **可见性与足迹是两个独立字段，永远不许互相推导**（`agent-principles` 十六）。

### 8.3 agent 看到

一个参与者需要四样东西才能参与：
**这里有谁** / **有什么在等我** / **我现在能干什么** / **怎么说出「这条路被平台挡了」**。

| | 人有什么 | agent 有什么（实测） |
|---|---|---|
| 这里有谁 | 名册面板 | `cheese members` 有。**但喂给模型的那份 roster 是错的**——见下 |
| 有什么在等我 | `GET /awaiting-me`、通知列表、未读数 | **没有任何读通知的命令**。`cheese notify` / `tell` / `ask` 全是写侧 |
| 我现在能干什么 | 界面上有什么按钮 | 一堆散落的报错字符串。没有「能力清单」这个东西 |
| 说出「这条路被平台挡了」 | 反馈（今天也没有） | 没有 |

**roster 那条的机械原因**：`agent/chat.py` 的 **2768 / 3194 / 3644 / 4339** 四个读点全部走
`ProjectRepository.list_members(project_id)`，而 `project/repositories.py:116 list_members` 只拼
`ProjectMember` 行 + owning team + owner_handle，**一个 agent 都不含**；
而 `agent_instance/services.py:257 ensure_identity` **只建 user 行，不建 `ProjectMember` 行**。
**后果**：一个房间坐两个 AI 队友，它们**互相连名字都拿不到**——
所以「你得 @ 他才行」这条规则在 agent→agent 方向上**物理上不可执行**，它不知道要 @ 谁。
按结论 12（不同 handle 只走 chat），这条缺口是那条结论今天唯一的实施障碍。

**agent 手上的平台工具表，这两条结论各加一句**：

- **机器状态是它自己处理的** [已定] 结论 40：工具表上有「开一台机器」和「换到 Cloud」（3.1、6.3）。
  撞上策略闸门的调用变成一条给人的提议，不是一次报错；平台不设超时器，也不替它决定什么时候换。
- **派活不在这张表上** [已定] 结论 43：起子 agent 是它对**骨架**的工具调用。
  平台这边它只做两件事——先开卡，结束写结论；中间的归属靠事件上的线程标识（1.5、4.2）。

**要补的四件，都不是新机制**：

1. 四个读点从项目名册换成**房间名册**（`topic/models.py:252 TopicMembership`）。
2. **agent 的收件箱 = 人的 `/awaiting-me` 换一个 `who`**，共用同一份 `room_task/awaiting.py` 判据，
   加一个 `cheese inbox`。**不许为 agent 另造一套接口**——那正是 `agent-principles` 十二否掉的做法。
3. **能力清单**：把今天散在 `platform_failures.py` / `ScreenSetupError` 文案里的东西，
   收成一份「这一轮你能做什么」，在轮次开场给出（6.3 那条事件是它的一个实例）。
4. **反馈**（结论 35，下节）。

**agent 的词表就是 `cheese` CLI 的动词表**，而它今天已经基本中立：
`backend/sandbox/cheese:935 build_parser()` 下 **31 个顶层子命令**
（`chat doc split worktree sync bind close-task push-fix fetch lock unlock decision title
remember recall notify ask accept-request describe ready tell milestone members gh-token status
serve library artifact convert recalc api`）。
`github` 的命中有三处——`cheese gh-token`（`:1356`）、一条写死的 GitHub PR URL 正则（`:728`）、
`/sandbox/github-token` 这条端点路径（`:245`）。
[我提的] 把 `gh-token` 改成托管方中立的动词，把那条正则改成由平台下发提案页地址。

按结论 31、43，`split` 与 `bind` 这两个动词也要重新长：
`split` 从「开第二个身份」变成「开一张卡」——**起子 agent 那一半不在 CLI 上，它是骨架自己的工具**；
`cheese_bind` 整个消失，归属改由事件上的线程标识给出。

agent **看不到**：平台对某个项目配置的解释。
[已定] `agent-principles` 八「平台提供的是**通路，不是知识**」。

### 8.4 反馈：一个东西，一个入口，两种写法

[已定] 结论 35。**人走界面，agent 走平台工具**（结论 21 那六样之一）；
**agent 遇到平台限制或 bug 提反馈而不是绕**。

反馈是**一个东西**：同一张表、同一套状态，两个入口。

设计上要守的三条：

- **形状对**：`author_handle`（发现者）与 `submitted_by_handle`（按下按钮的人）是两个字段，不合并——
  与验收卡「谁提的 / 谁采纳的」同形。**agent 只能提案，人按一下才成立**，既是产品判断也是安全判断。
- **不新造接口**：它是 CLI 那棵 argparse 树上的一个叶子命令，三个骨架同时就有了（4.2）。
- **它是 I26 的第四个出口**：一个被吞掉的失败，除了 propagate / report / 被监控的死信，还可以落成一条反馈——
  这正是「该修的限制不要拿去广播」（`agent-principles` 九）的兑现：
  把该修的东西送到能修它的人手上，而不是写进一份给 agent 的限制清单。

它今天一行代码都没有；设计稿与前端原型在开着的 PR #1222 里。

### 8.5 运维看到

三张 conformance 矩阵的当前状态（含每一个 `暂缺` 的到期日）、地点健康账与租约账本、
**收据看板**（哪些回收在等 transcript、等记忆整理、等未发布的工作）、死信队列、
以及每一条被吞掉的失败落在哪里。

死信队列里的东西从哪来——是 I26。没有 I26，「死信队列」就是一个没有生产者的看板。

**运维面是唯一允许出现内部名字的地方**，因为看它的人就是知道内部机制的人。
[已定] #450 ③「No swallow without a sink」+ #489「Fail visibly, not just in a log file」。

### 8.6 平台文案目录

**用户看到的每一句话来自一份目录，实现只返回码**（I8）。这是「三个接口止步于能力」在文案上的那一半：
一个实现能声明的是一条差异码（4.4），不是一句给用户看的话；那句话由平台按码渲染，所以换实现不换措辞。

**三类豁免**——它们不是用户看的字，所以不进目录、不受守卫管：

1. **docstring**：写给读代码的人。
2. **给模型的 system prompt**：写给 agent 的字，措辞本身是产品行为的一部分
   （1.5 那六句 skill 默认住在 skill 里，也算这一类）。
3. **给 agent 的 git 约定文案**：分支名、commit 约定这类字，agent 照着写，人只在仓库里见到它。

守卫的形状与棘轮性质见 I8；后端这道与 #1167 的前端闸门是同一件事的两面，全仓只许有这两道。

### 对十四条的修订（结论 15）

十四条今天的原文里，「谁被告知」这一栏写的是：

> 平台自己不续：一轮失败、超时、被判卡住，各发一次事件（`who=human`）然后停下，不重跑

**修订**：删掉 `who=human` 这个固定收件人，改成 I11 那条唯一规则——
**从「下一步在平台手上」转入「下一步在某个参与者手上」的那一刻，通知那个参与者，一次。**

- **改的是什么**：收件人不再一律是人。
  Cloud 正在开机 = 下一步在平台手上，**不惊动任何人**；
  自托管离线 = 下一步在机主手上，收件人是**机主**，不是房间里的所有人；
  一轮失败而下一步回到了点名它的那个参与者 = 通知那一个。
- **不改的是什么**：**「不重跑」一个字不动。** 这条修订只动收件人，不动平台要不要自己再发起一轮——
  后者由结论 13 从「不重跑」进一步收紧成「从不发起」，方向一致，没有放松。
- **为什么要改**：6.3 那张表在不收紧的前提下写不出来。
  「一律告诉人」在只有一种机器、一种失败的时候是对的；
  有了 Cloud 的可见等待和自托管的机主之后，它会把「平台正在处理」也播成一条告警，
  而 `agent-principles` 九说的正是这种广播该被修掉。
- **一个前提**：这条修订成立的前提是「下一步在谁手上」全仓只有一个答法；
  今天有三个互不引用的答案（9.4）。

**除这一处外，本文不推翻也不修订任何一条。**

**一条与记录看起来冲突、实际不冲突的**：#442 说 Cloud 与自托管「are two different kinds of thing」，
本设计把它们做成同一个接口的两个实现。不冲突——#442 反对的是
「code models them as one kind of thing with **two independent switches**」，即两个互不约束的开关；
本设计给的是一个接口、一张能力表、一张封闭的差异码表，销毁权照旧只从 `supply` 推出来。
（#442 第 3 条已由结论 24 正面废掉，见 6.5。）

### 已定二：骨架的行为声明，对着钉住的版本（结论 48）

[已定] 他 2026-09-19：「a 吧，我们写个不同 harness 的行为说明，表上版本，因为和 pin 的版本也有关系，每次 upgrade 都要改」。
每个骨架的适配层带一份**行为声明**：它自带哪些产品概念（提问、待办、提醒、自动同步……）、每一项平台怎么关掉、
以及这份声明是对着哪个**钉住的版本**验证过的。三条判据：
① 钉住的版本号全仓只写一处，声明引用它；升级 pin 而没有重验声明，CI 红。
② 真正的验证是契约测试对着钉住的二进制跑（今天的 `harness-contract.yml`）；`claude-canary.yml` 每夜对 @latest 跑同一套，提前预告下一版会变什么。
③ 提供不了关闭动作的项，4.3 的矩阵那一格标「暂缺」，谁都看得见。
4.2 末尾那条「关掉这个动作在接口上不存在」由此有了落点：它是声明里的一项，不是各适配层各自记得的事。

### 已定三：模型供给由后端统管，入口形态沿用 #218 已落地的两种传输（结论 46）

[已定] 这是 2026-08-10 #218 的重申，不是新决定：后端看到每一个请求，在唯一必经点做准入、记账、拒绝；ccproxy 只是容量池。
**入口不是一个 base URL**：订阅流量不能设 `ANTHROPIC_BASE_URL`（Claude Code 会退出订阅模式；后端若重发请求，指纹不符会触发订阅风控），
所以它走 `HTTPS_PROXY` 的 CONNECT 到平台的透明计量代理（`deploy/metering-proxy/`），代理向后端 `/llm/admission` 问准入后**原样转发**给 ccproxy；
API-key 供应商走 `ANTHROPIC_BASE_URL` 指向的网关（`provider_env.py` 的两组环境变量互不重叠）。一个控制点，两种传输，都不重发请求。
机器上只有平台签发的、可撤销的 ccproxy 假票，真凭据既不在机器也不在后端（他 2026-08-15）。
I27 的拒绝点就是 `/llm/admission`：卡上的模型绑定在这里解析，选不到就拒绝并说出来，不换池。
**目标是只剩一种启动形状**（结论 46 补定）：机器永远以订阅形状起，分流发生在代理里（`deploy/metering-proxy/billing_addon.py:272 _route_to_gateway`，按 admission 的答复改写到网关，今天已在）。
还留着的第二种形状——`device_provider.py:1421` 按 API-key 供给以 base URL 起 Claude Code——要删；它存在的唯一原因是订阅形状的启动依赖 Anthropic 的非模型端点（设置、策略、额度、事件上报）能应答，没有真订阅时会 401。
处置是让代理自己应答这些端点（不碰 Anthropic，无风控问题），并实测 Claude Code 在固定应答下行为正常；这是这条统一上唯一未验证的事实。
