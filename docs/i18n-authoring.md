# 把一个界面抽进词表（操作手册）

三份文档分工不同，别搞混：

| 文档 | 管什么 |
|---|---|
| [`i18n.md`](i18n.md) | **规范**：目录怎么切、键怎么起名、缺翻译怎么办、有哪些机器闸门 |
| [`i18n-glossary.md`](i18n-glossary.md) | **尺子**：平台自己的概念用哪个英文 |
| 本文 | **操作**：今天怎么把一个 `.vue` / `.ts` 里的中文抽进词表，并且证明自己没抽错 |

本文假定你已经读过 `i18n.md` §2（命名空间）和 §5（闸门）。下面的命令都在 `frontend/` 下跑。

---

## 0. 一个切片 = 一个界面

**一次提交只动一个页面，或一组会同时出现在同一屏的字符串。** 不按文件大小切，不按「顺手把这几个也改了」切。

理由不是洁癖：半翻的屏幕比全中文更难看——用户看到的是一句话里中英各一半，像渲染坏了。切片以「同一屏」为界，
就是为了让每一次提交之后，任意一屏要么原样、要么整片换语言。

同时抽 `src/lib/mergeState.ts` 这种被多个界面共用的工具模块是**允许**的，前提是它整个模块的词都属于同一屏的语义
（合并态徽标只出现在验收卡上，所以它跟着验收卡走）。判断标准还是那句：会同时出现在同一屏吗。

## 1. 开工前数三件事

```bash
# 1) 这个文件欠多少行？棘轮会按文件报出来
node scripts/i18n-cjk-ratchet.mjs | grep <文件名>

# 2) 本切片会碰到哪些术语？查尺子，别凭语感
#    docs/i18n-glossary.md —— 尤其 §5 的遗留分歧

# 3) 新词条放哪个命名空间？问：它和已有的某个命名空间会同时出现在同一屏吗？
#    会 → 并进去。不会 → 才考虑新建（命名空间按「界面属于谁」切，不按「文件现在放在哪」切）
```

**还没定论的术语不要翻。** 尺子 §5 第 4 条记着：团队 / 队伍 / 小队是同一个概念的三件中文外衣，等产品主拍板统一之前，
**任何 team 相关的键都不许翻**——翻错的那个词会被所有人看见。这类键留在 `untranslated.json` 里，把「欠着」摆明。

## 2. 写词条

### 值里放占位符，不要拼字符串

```jsonc
// 好：整句在词表里，语序是译文自己的事
"acceptCard.pending.approvedCount": "{done}/{total} approved"

// 坏：中文语序被烧进代码，译文只能照着中文的语序拼
`${done}/${total} 已批准`
```

**用 `@` 要转义。** vue-i18n 的消息语法里 `@` 是「链接到别的键」（`@:some.key`），一个裸 `@` 会让这件事变成解析错误。
词表里已有的写法是把它包成字面量：

```jsonc
"teams.compute.screenRunning": "运行中 · {'@'}{handle}"   // 不是 "@{handle}"
```

更省事的办法是不让值里出现 `@`：把 `@昵称` 整个当占位符传进来（`{ who: '@' + handle }`），
验收卡就是这么做的。两种都行，别第三种。

### 复数：英文写三截，中文只有一截

`|` 分隔，最多三截，对应「零 / 一 / 多」：

```jsonc
// en
"spaces.discussions.repliesCount": "No replies | 1 reply | {count} replies"
// zh-CN —— 不写管道，一个形式就够了
"spaces.discussions.repliesCount": "{count} 条回复"
```

调用时把数传进去：`t('spaces.discussions.repliesCount', { count: n }, n)`。
**注意 `catalog.spec.ts` 目前只比占位符的集合，不比每一截**——所以「第三截忘了写 `{count}`」这类错闸门抓不到，
写的时候自己数一眼。

### 别翻「不是文案」的字符串

模板里 `<option :value="...">` 的值、路由名、`localStorage` 键、CSS 类名常常长得像中文标签，但它们是**数据**：
翻了会让前后端对不上。典型反例是筛选器的下拉框——显示的是中文标签，绑定的值必须是后端认的枚举。
**抽之前先确认这个串会渲染到屏幕上**，不渲染就不是文案。

## 3. 改代码

### `t` 有两个来源，选错会静默渲染成空

| 写法 | 什么时候用 | 代价 |
|---|---|---|
| `const { t } = useI18n()` | 组件自己装了 i18n 插件的常规情况 | 没装插件时**抛异常**（`Need to install with app.use`） |
| `import { t } from '@/i18n'` | 组件嵌在**还没翻译**的父组件里，而那个父组件的用例不装插件 | 无（模块级的 `t` 不依赖插件，在模板和 computed 里照样是响应式的） |

选第二种时留一句注释说明为什么，否则下一个人会「顺手改成规范写法」然后砸掉一堆用例。

`<i18n-t>`（用来把 `<strong>` 这类标签嵌进句子里）**要求插件在场**。父组件的用例不装插件时它会安静地渲染成空字符串——
不是报错，是空白，最难查。这种地方用第 4 节的三截拼接。

### 模板里拼一句话：Vue 会吃掉换行处的空白

模板改成

```html
{{ t('acceptCard.gate.blockedBody1') }}<strong>{{ t('acceptCard.gate.blockedVerdict') }}</strong
>{{ t('acceptCard.gate.blockedBody2') }}
```

- **元素之间含换行的纯空白节点会被 Vue 删掉**，所以三截紧挨着写就能拼成原来那一句；把 `</strong>` 和 `>` 拆开
  只是为了过 prettier 的行宽，不影响渲染。
- **空格该放哪，由译文决定**：英文那两截自带宽窄（`"…so it says "` + `"nothing"` + `" about…"`），
  中文两截一个空格都不带——中文原来那句本来就没有空格，屏幕上看到的间隔是 flex 的 `ga-1` 给的。
  **「渲染出来跟翻译前一模一样」是验收标准**，不是「看着差不多」。

### 动态拼出来的键，扫描器看不见

棘轮的「调用可解析」闸门是**按字面量**扫源码的。写成下面这样，键等于不存在，闸门会认为 catalog 里那些键没人用：

```ts
// 坏：扫描器只看见 'acceptCard.pending.'
needsPr ? t(`acceptCard.pending.createPr`) : t(`acceptCard.pending.accept`)

// 好：两个完整字面量
needsPr ? t('acceptCard.pending.createPr') : t('acceptCard.pending.accept')
```

三元、模板字符串拼前缀、从数组里取键名——一律展开成字面量调用。

## 4. 验证

按顺序跑，前面便宜的先跑：

```bash
npx prettier --write <改过的文件，含 json>          # 仓库的 prettier script 不含 json，json 要单独指定
npm run lint:i18n                                  # 棘轮：确认这个文件的欠账真的降了
npm run lint:i18n:update                           # 更新 i18n-cjk-baseline.json（连同基线一起提交）
npx vitest run src/i18n/catalog.spec.ts            # 词表闸门：键对齐、清单诚实、占位符、英文无中文
npx vue-tsc --noEmit                               # 注意：`npm run typecheck` 是棘轮，不报真实错误，这里要 raw 的
npx eslint . --fix                                 # 改 import 顺序这类会自动修
npx prettier --check "src/**/*.{ts,vue,json}"
npx vitest run                                     # 全量
```

`--update` 之后棘轮会报 `total: N, baseline allows N`——**N 必须是你这次的成绩**。凭空更新基线会把别人的欠账一起洗白。

## 5. 写用例

抽完一个页面，给它补一份 `<组件>.i18n.spec.ts`，至少覆盖：中文那屏、英文那屏、切一次语言。

**测试的默认语言是 `en`，不是 `zh-CN`。** happy-dom 报 `navigator.language = 'en-US'`，
`resolveInitialLocale()` 据此选出英文。所以**任何断言中文值的用例，必须在 `beforeEach` 里 `setLocale('zh-CN')`**，
否则失败信息长得像「文案没抽干净」，实际是语言没钉住。仓库里的先例：`Compute.spec.ts`、`Knowledge.spec.ts`。

**改已存在的用例时，给它们补上同一句 `setLocale('zh-CN')`。** 那些断言本来是照着硬编码中文写的，
翻译之后走词表，不钉语言就会变成英文而失败。

**验「拼接得一个空格都不多」时，别用会折叠空白的辅助函数。** 常见的
`const pageText = (el) => el.textContent.replace(/\s+/g, ' ')` 会把多余空格吃掉，
拿它去断言「拼出来跟原来一模一样」等于什么也没验。这种地方用不折叠的 `rawText`。

这条是**负向对照逼出来的**：往三截之间插一个空格，中文那句红了、英文那句没红，才发现英文的断言是空的。

## 6. 负向对照：证明用例不是摆设

新写的用例必须证明它**拦得住**它声称要拦的那类错。做法是**故意引入那个错，跑一遍，确认恰好预期的那几条红**，
然后还原。

本仓库已用过的两条：

| 故意引入的错 | 应该红的 |
|---|---|
| 把某个 `t('...accept')` 改回硬编码 `'采纳'` | 英文那两条（一个汉字都不剩 / 切语言） |
| 往三截拼接之间插一个空格 | 中文那句 + 英文那句 |

**只有「恰好那几条红」才算数**：全红说明用例之间不独立，一条没红说明这条错没人管。
还原之后**用 `md5sum` 确认还原到位**——别用 `git checkout`（会连同这个切片其他改动一起丢），
也别凭记忆 `cp` 一个备份回来：备份目录里放的可能是翻译前的版本，抄回来就把整个切片抹了。

## 7. 收尾要动的三份清单

| 文件 | 这次要做的 |
|---|---|
| `frontend/i18n-cjk-baseline.json` | `lint:i18n:update` 自动改，**必须一起提交** |
| `frontend/src/i18n/untranslated.json` | 翻了哪个键就删哪个。**它只记叶子**，不记子树 |
| `frontend/src/i18n/unused.json` | 顺手救活的死键要从这里删掉；抽的过程中发现某个键已没人用，删键或登记进来 |

**不要为了让闸门变绿而建一个空的英文命名空间**，也不要就这么留着欠账——两条路都比「有但为空」诚实。

## 8. 已知的、还没解决的

抽的时候会撞上，先知道就少绕一圈：

- **在 `setup` 里算一次的文案不会跟着换语言。** zod 的校验消息在组件挂载时构建，
  挂载后切语言，已经建好的那些消息还是旧语言。列表刷新或重挂载才会变。
- **组件通过 props 收进来的字符串抽不动。** 调用方传的是硬编码中文时，这个组件自己翻了也没用——
  要把调用方一起翻（例如 `Edit.vue` 传给 `TaskForm` 的 `submitButtonText`）。
- **`赛题` / `任务` 在 catalog 里有过混用**，尺子 §5 第 3 条记着这个坑，抽到相关词条时对一眼。
- **占位符闸门不比复数分截**，见 §2。
