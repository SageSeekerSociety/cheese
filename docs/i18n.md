# 中英双语与词条目录

这份文档管**字符串怎么存、怎么命名、缺翻译怎么办**。它不管**字该写成什么样**——中文文案的风格在
[`design-system.md` §8](design-system.md#8-文案)，那份是给人读的规范，**没有机器闸门**；这份是给人和机器都读的结构规范，第 5 节列了全部闸门。

代码落点只有一处：`frontend/src/i18n/`（`languages.ts` 是唯一的例外，见第 5 节）。

---

## 0. 一句话原则

> **缺翻译必须是可见的。**

这个项目的英文曾经不是「还没做」，而是「做了一半没人知道」。2026-09-09 合并的 PR #929 把落地页和账号流程翻了英文，
但 `frontend/src/i18n/messages/en/` 下**只有 `website.json` 一个文件**，`zh-CN/` 下有 9 个；`fallbackLocale` 是 `'zh-CN'` 且没开
`missingWarn`，于是英文访客点进工作台看到的是一屏中英夹杂，**界面上没有任何东西提示这是没翻译**。这份文档和第 5 节的闸门就是为了让那种状态不再无声存在。

---

## 1. 三个内容面，三套政策

仓库里的「文字」是三种东西，受众不同，别用一套规则：

| 内容面 | 位置 | 语言 | 说明 |
|---|---|---|---|
| **产品界面** | `frontend/src/**` | **中英双语，机器校验** | 见第 2–5 节 |
| **内部工程文档** | `docs/` | **中文** | 写给改代码的人，不翻译 |
| **仓库门面** | `README.md` 等 | **英文** | GitHub 上第一眼看到的东西 |

`docs/` 不翻译是**决定**，不是拖欠：内部文档的读者全是中文母语者，翻译它只会产生一份没人看、还会陈旧的副本。

---

## 2. 目录与命名空间

两个语言目录**结构镜像**，这是硬要求：

```
frontend/src/i18n/messages/
  zh-CN/
    index.ts        ← 桶文件：把下面的 json 汇总成一个对象
    global.json     ← 跨界面通用：按钮、状态词、通用错误
    navigation.json ← 导航项（顶部导航、侧栏共用）
    publicSite.json ← 未登录的公开站点：落地页、首页布局
    account.json    ← 账号流程：登录、注册、验证、找回密码
    <业务命名空间>.json
  en/
    index.ts
    (同名文件，一一对应，未翻译的见第 4 节)
```

**命名空间按「界面属于谁」切，不按「现在放在哪」切。** 反例就是 #929 留下的 `website`：
它被 17 个文件引用，实际覆盖登录/注册/找回密码、落地页、布局、顶部导航、传输错误文案——
名字回答不了「新词条该加到哪」，所以下一个人只能猜。拆分后 `publicSite` 与 `account` 的分界线，和
`frontend/src/router/` 里 `home.ts` 与 `account.ts` 的分界线是同一条。

判断一个新命名空间该不该建，问一句：**「它和已有的某个命名空间，会同时出现在同一屏吗？」**
会，就说明该并进去。

## 3. 键名

**格式：`命名空间.组件.角色`，语义化、稳定、可 grep。**

```json
{
  "account.signIn.submit": "登录",
  "account.signUp.emailTaken": "该邮箱已被注册",
  "publicSite.hero.title": "一起把想法做出来"
}
```

**不用英文原句当键，也不用句子碎片当键。** 这是 #929 最贵的那个选择：它的键长这样——
`equipYourTeamWithModelsAndCloud`、`workOnItWithYourTeamAnd`（在句子中间被截断）。
问题不在难看，在于**改文案就要改键**：中文文案一旦返工，键名要么跟着改（译文全部脱钩），
要么不改（键名和内容越差越远）。

语义化键把这个耦合切断：**改中文不必碰键，因此也不必碰译文。**

| 好 | 坏 | 坏在哪 |
|---|---|---|
| `account.signIn.submit` | `signIn` | 不说清是哪个界面的哪个元素 |
| `publicSite.hero.title` | `equipYourTeamWithModelsAndCloud` | 原句当键，改文案即失联 |
| `global.loadFailed` | `failedToLoadPleaseTryAgainLater` | 原句当键，且和已有的 `loadFailed` 重复 |

## 4. 缺翻译怎么办

**运行时**：缺的键回落到 `zh-CN`，界面显示中文而不是裸键名。这是有意的降级——
半翻译的屏幕应该还能读。开发构建里 `missingWarn` / `fallbackWarn` 是开的，缺哪个键会打到控制台。

**但那只是降级，不是交代。** 交代在下面这两份清单里，它们是**唯一**允许「缺」的出口：

| 文件 | 含义 |
|---|---|
| `frontend/src/i18n/untranslated.json` | `zh-CN` 有、`en` 还没有，**并且确实会渲染**的键 |
| `frontend/src/i18n/unused.json` | catalog 里有、没有任何源码引用的键（死键，不用翻译） |

**两份清单都只记叶子，不记子树。** `global.formValidation` 是五个键的子树，不是一条；写子树等于一行盖住五条欠账，
是第 0 节那种「有但为空」的换皮。`catalog.spec.ts` 会把 catalog 递归拍到叶子再比。

**两份清单互斥。** 没人渲染的键不是翻译欠账——把它算进去只会虚报还剩多少活。所以：

```
[i18n] untranslated: 301 / 672 keys
```

是**真的要翻的量**。当前仓库的实际状态：`zh-CN` 有 672 个叶子，`en` 有 274 个，
其中 97 个是死键，剩下 301 个是待翻译的欠账。

两份清单都由 `catalog.spec.ts` 双向校验：**漏登记的会失败，登记了但已经不成立的也会失败**
（键已经翻译了却没删、键已经有人用了却还挂着、同时躺在两份清单里）。
所以它们只能被显式修改，不会腐烂成一个没人敢删的地址簿。

**永远不要为了让检查通过而建一个空的英文命名空间。** 空文件让「缺」变成「有但为空」，
正是这份文档第 0 节要防的那种无声。要么写译文并把键从清单里删掉，要么让它待在清单里被数出来。

## 5. 机器闸门

全部在 `frontend/src/i18n/catalog.spec.ts`，随 `pnpm exec vitest run` 跑，零新增依赖：

| 闸门 | 拦什么 |
|---|---|
| 键对齐 | `zh-CN` 的每个键要么有英文，要么在 `untranslated.json` 里 |
| 反向键对齐 | `en` 里不能有 `zh-CN` 没有的键（那种键永远不会被渲染） |
| 清单诚实 | 两份清单里不能有已翻译的、已使用的、或悬空的条目 |
| 占位符一致 | 同一个键在两个 locale 的 `{占位符}` 集合必须相同——否则译文会渲染出 undefined |
| 英文无中文 | `en` 的值里不能出现中日韩字符。**没有例外**——语言自称就不在 catalog 里，见下 |
| 注释不算引用 | 只统计真正的调用点：注释里的 `t('...')` 不是调用，注释掉的调用也不会让用户看到裸键名 |
| 调用可解析 | 源码里按名字调用的键必须存在于 catalog——**这条上线当天就抓到一个真 bug**：`ReplyInput.vue` 调用 `global.replyFailed`，而 catalog 里只有 `replySuccess`，回复失败时用户看到的是字面量 `global.replyFailed` |
| 无死键 | catalog 里的键必须有源码引用，或在 `unused.json` 里 |

**语言自称不进 catalog。** 语言切换按钮上的「中文」「English」，以及它们的无障碍名字，
在任何 UI 语言下都必须一模一样——看不懂当前语言的人正是靠它找到切回去的路。
一个不该随 locale 变的串不是译文，所以它是 `frontend/src/i18n/languages.ts` 里的常量，
不在 `messages/` 下。写两份一样的值只会给它们一个分头漂移的机会，也会逼上面那条闸门开一个例外；
没有例外，就没有藏身处。

**闸门不检查什么**：它不看文案写得好不好，不看译文地不地道，也不看某个键该不该叫这个名字。
第 6 节那条流程性要求就是为此存在的。

## 6. 改词条的流程要求

**动笔之前先查 [`i18n-glossary.md`](i18n-glossary.md)。** 平台自己的概念（话题 / 空间 / 成果 / 邀请……）用哪个英文，那里说了算，依据是代码里已有的标识符，不是语感。

**改词条表的 PR，需要一个目标语言的母语者看过渲染后的界面**，而不是只看 diff。

#929 是 1410 增 / 422 删 / 35 个文件，**在零条人类评审意见下合并的**（唯一的评论是一个被限流的自动评审工具）。
第 5 节那些闸门能拦住「结构坏了」，拦不住「英文读起来像机器翻的」——那需要有人真的打开页面看。

PR 描述里请写清楚：**哪些译文经过了母语者过目，哪些还是机器翻译**。别让后者混进去当定稿。

## 7. 明确不做

| 不做 | 为什么 |
|---|---|
| 引入 Crowdin / Weblate / Transifex | 两种语言、几百个键的规模，瓶颈是评审不是工具链；这类平台会在仓库里制造 bot PR 噪音 |
| 用 Vale 之类做中文术语检查 | 那类工具依赖分词边界，对中文效果差；中文术语检查应退化成对词条值做子串匹配 |
| 命名空间懒加载 / 哈希 id / 语言包分包 | 几百个键，用不上 |
| 同页中英对照 | 查过的六个大型文档站（k8s / MDN / Vue / Docusaurus / VitePress / Next.js）**没有一家**这么做，全是切到平行目录的切换器 |
| 给 `docs/` 做双语镜像 | 见第 1 节 |
| 用英文原句当键 | 见第 3 节 |
