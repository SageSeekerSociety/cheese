# Canonical living-document data contract

How the living document is stored, who may write it, and through which path.

## Source to implementation

- Node reconciliation and persisted contribution events live in `block/documents.py:DocumentWriter.record`, called only by the store. The original block-level `SequenceMatcher` reuse and SQL `set_doc_content` are preserved, not replaced with rendered-text round-tripping.
- Existing route `topics.py:edit_topic_doc` performed mention canonicalization and post-commit notifications. It lives in `api/routes/living_docs.py`; PUT still canonicalizes friendly references before handing the content to the collaboration service. Restore hands over the stored raw snapshot without a second whole-document canonicalization.
- Supplied `cheese-doc-ai-handoff-20261001/reference/cheese-doc-comments-permission-design.md`, sections “幂等与异步恢复” and “原文范围”: stable verified actor/document/action/op key, separate fingerprint, claim/effect/result transaction, exact source coordinates. `living_doc/services.py` implements room lock + operation claim + receipt; `source_span.py` defines UTF-8 byte offsets only. These primitives do not authorize AI acceptance by themselves.

## Stored contract

The living document is a Yjs document held live by the collaboration service (`frontend/collab/`, a Hocuspocus server built from the frontend package so it runs the editors' own schema, `frontend/src/lib/docSchema`). The editors (`usePanelDoc → PanelDocView → DocSurface`, which the charter page renders too) bind to it over one WebSocket each, with a ticket from `GET /topics/{id}/doc/ticket`; nothing in the browser saves.

The service stores the document back a few seconds after the typing stops: `PUT /internal/collab/documents/room:{id}` carries the Yjs state, the Markdown exported from it and the handles whose changes it holds. That store (`api/doc_store.py`) is the one path that records a version: one transaction under `living_doc_locks` writes `living_doc_states`, the root content, the node tree, the raw history row, the conversation event and, for an idempotent write, the operation receipt. The Markdown is derived: it is what `cheese_doc_get`, version history, AI selection and export read.

Every other writer goes through the service, because the live document would overwrite a database write at its next store: HTTP PUT (the editors' old path, 芝士's `cheese_doc_set`, the generic `platform_request`), restore, and accepting an AI proposal call `living_doc/collab.replace`. The service applies the change only while the live document still reads the version the writer based it on; otherwise it stores whatever was typed meanwhile and answers 409 with the current version. It computes the change on a copy, stores it, and only then merges it into the live document, so a write is never live without being recorded. A write in Markdown from outside an editor (PUT, so `cheese_doc_set` and `platform_request`) is checked by the service first (`frontend/collab/writeCheck.ts`): converting it may respell it, but if it would lose visible text — a footnote or link reference definition, a table row with more cells than its header — it is refused unapplied with a 422 that names the line and the fix. Restore and AI acceptance carry stored or derived text and are not checked. Brief seeds still write the database directly: they run in the transaction that creates the room, before any client can open its document.

A document that has Markdown and no state is converted when the service first loads it, and the state is stored at once, before anyone edits. If the converted document exports different text, that text is stored as a version of `system`'s with no conversation event, and the document keeps its author: a respelling is nobody's edit. A version's actor is the handle with the most changes in the store. A run of edits is one conversation event: while the room's last line is this document's edit event, touched within the last ten minutes, a new version extends it — it names everyone in the run, its diff spans the run, it moves to now, and open pages get it as a `block_updated` frame. Anything said in between, or a longer pause, starts a new event. What it tells 芝士 is about the newest store only.

`living_doc_operations` uniquely claims `(room_id, verified live account id, action, operation_id)`. The room identifies the single canonical document, including absent-document creation. Payload fingerprint is a separate column. Write routes look for a completed receipt without the lock and otherwise hand the operation to the service; the claim and its receipt are made in the store's transaction, so no request holds the room lock across the call to the service. Same key/payload returns the original JSON receipt, even if another writer has advanced. Different payload returns 409.

The verified credential resolves the handle. `body.author` cannot provide operation authentication. The ticket carries the handle and whether the connection is read-only (no verified credential, archived room or project); the service enforces read-only and overwrites the identity a client puts in its presence state with the ticket's.

Pre-journal deployed snapshots are seeded on the first recorded update. Earlier unavailable versions are not fabricated. New brief seeds are journaled without inventing a conversation contribution event. PostgreSQL rejects updates/deletes of history while its document exists; deleting the document may cascade its retained journal. Historical event ids are evidence values, so event deletion cannot mutate history through SET NULL.

After a store commits, the room gets the event block and a `state`/`doc` frame; the frame refreshes what derives from the stored version (comment anchors, the AI source, the overview). Editors do not need it: they already hold the text.

A deferred PostgreSQL constraint refuses an operation transaction that commits without its receipt, rolling back root/nodes/history/events together. Operation-specific authorization is enforced even when the legacy room-auth flag is disabled.
