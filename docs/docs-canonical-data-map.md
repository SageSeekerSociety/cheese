# Canonical living-document data contract

How the living document is stored, who may write it, and through which path.

A document is a row of `documents` (`living_doc/models.py`), owned by a project. A channel or a private chat has no document of its own. A document is a task's when a `tasks` row points at it (`tasks.document_id`, made empty the first time it is asked for, `GET /topics/{task}/document`: a task is a conversation addressed by its own id); it is read by whoever may enter the task's channel and written only by the task's owner and the task's own session, while the task is open. The project's overview is the one `projects.overview_document_id` points at (`GET /projects/{id}/overview`). Any other document is the project's own: a member makes one empty, with Markdown, or as a copy of what another document says now (`POST /projects/{id}/documents`), and the project's library lists them (`GET /projects/{id}/documents`); only these are renamed or deleted on their own. The library's search (`GET /projects/{id}/documents/search`) finds them by title and text, and the documents of the tasks in the channels the caller may read, and the overview, by text. When 芝士 makes or changes one from a conversation (a channel, a 支线 or a task), with the credential its session there runs with, that conversation gets an event carrying the document (`meta.document`, `doc_created`, `doc_edits`; `api/doc_store.tell_origin_room`). Every route that reads or writes a document names it by its id (`/documents/{id}/…`) and asks `api/doc_access.py` who may: a task's document follows its channel's roster, any other its project's members and 芝士 working in any of the project's conversations (`doc_access.authorize_in_project`). `GET /documents/{id}/compare?before=&after=` returns two versions' contents side by side (version 0 is the empty document); a task's page compares the version recorded when it started (`tasks.started_doc_version`) with the current one. Every other document table hangs off `documents.id`, comments included (`document_comments`, `document_threads`; see `docs-comment-thread-contract.md`).

## Source to implementation

- Persisted contribution events live in `block/documents.py:DocumentWriter.record`, called only by the store. The version-conditional write and the node reconciliation (a block-level `SequenceMatcher`, so an unchanged node keeps its id and author) are `living_doc/services.py:Documents.write`.
- Existing route `topics.py:edit_topic_doc` performed mention canonicalization and post-commit notifications. It lives in `api/routes/living_docs.py`; PUT still canonicalizes friendly references before handing the content to the collaboration service. Restore hands over the stored raw snapshot without a second whole-document canonicalization.
- Supplied `cheese-doc-comments-permission-design.md`, section “幂等与异步恢复”: stable verified actor/document/action/op key, separate fingerprint, claim/effect/result transaction. `living_doc/services.py` implements document lock + operation claim + receipt.

## Stored contract

The living document is a Yjs document held live by the collaboration service (`frontend/collab/`, a Hocuspocus server built from the frontend package so it runs the editors' own schema, `frontend/src/lib/docSchema`). The editors (`usePanelDoc → PanelDocView → DocSurface`, which the charter page renders too) bind to it over one WebSocket each, with a ticket from `GET /documents/{id}/ticket` (a room's document id from `GET /topics/{id}/document`); nothing in the browser saves. Each connection also names the document schema its page was built with (`DOC_SCHEMA_VERSION` in `lib/docSchema/version.ts`, a query parameter on the socket URL); the service refuses any other before the document is loaded or synced, because a page on another schema drops what it cannot parse and the drop would be written back for everyone. Such a page asks to be refreshed.

The service stores the document back a few seconds after the typing stops: `PUT /internal/collab/documents/doc:{document id}` carries the Yjs state, the Markdown exported from it and the handles whose changes it holds. That store (`api/doc_store.py`) is the one path that records a version: one transaction under `document_locks` writes `document_states`, the document's content, its node tree (`document_nodes`), the raw history row (`document_versions`), the conversation event and, for an idempotent write, the operation receipt. The Markdown is derived: it is what `cheese_doc_get`, version history, search and export read. A pending suggestion is not part of it (the Markdown is the text with every suggestion rejected); every store also carries the suggestions still pending, kept in `document_states.suggestions` and listed by `GET /documents/{id}` as `pending_suggestions`.

Every other writer goes through the service, because the live document would overwrite a database write at its next store: HTTP PUT (the editors' old path, 芝士's `cheese_doc_set`, the generic `platform_request`) and restore call `living_doc/collab.replace`. Passage edits — `POST /documents/{id}/edits` (芝士's `cheese_doc_edit`, including when someone asks the AI teammate in a comment thread or from a selection, and a person restoring one change) — call `living_doc/collab.edit`, which changes only the blocks the passages touch, directly or as suggestions, and never erases another pending suggestion (`frontend/collab/edit.ts`). Whether an agent's edit is made or suggested, and for whom, is decided in `api/doc_edits.py`; an edit made with a question's delegated credential is made directly, for the person who asked. The service applies the change only while the live document still reads the version the writer based it on; otherwise it stores whatever was typed meanwhile and answers 409 with the current version. It computes the change on a copy, stores it, and only then merges it into the live document, so a write is never live without being recorded. A write in Markdown from outside an editor (PUT, so `cheese_doc_set` and `platform_request`) is checked by the service first (`frontend/collab/writeCheck.ts`): converting it may respell it, but if it would lose visible text — a link reference definition, a table row with more cells than its header — or writes a block in the wrong shape — a `:::` container without its closing line, a timeline item without its `|`, a footnote with no definition, a chart cell that is not a number, a mermaid pie, xychart or timeline that a document block draws instead — it is refused unapplied with a 422 that names the line and the fix. Restore carries stored text and is not checked; a passage edit is checked like a PUT. Brief seeds still write the database directly: they run in the transaction that creates the room, before any client can open its document.

A document that has Markdown and no state is converted when the service first loads it, and the state is stored at once, before anyone edits. If the converted document exports different text, that text is stored as a version of `system`'s with no conversation event, and the document keeps its author: a respelling is nobody's edit. A version's actor is the handle with the most changes in the store. A run of edits is one conversation event: while the room's last line is this document's edit event, touched within the last ten minutes, a new version extends it — it names everyone in the run, its diff spans the run, it moves to now, and open pages get it as a `block_updated` frame. Anything said in between, or a longer pause, starts a new event. What it tells 芝士 is about the newest store only. A version the agent made at someone's request records them (`requested_by`), and its event says who asked (meta `doc_requested_by`, `doc_edits`); proposed changes record no version, only an event (meta `doc_suggested`, `doc_suggestions`). Each of the three kinds of event extends only one of its own kind, a requested edit only the same person's.

`document_operations` uniquely claims `(document_id, verified live account id, action, operation_id)`. Payload fingerprint is a separate column. Write routes look for a completed receipt without the lock and otherwise hand the operation to the service; the claim and its receipt are made in the store's transaction, so no request holds the document lock across the call to the service. Comment-thread mutations claim receipts on the room document the same way. Same key/payload returns the original JSON receipt, even if another writer has advanced. Different payload returns 409.

The verified credential resolves the handle. `body.author` cannot provide operation authentication. The ticket carries the handle and whether the connection is read-only (no verified credential, archived room or project); the service enforces read-only and overwrites the identity a client puts in its presence state with the ticket's.

History reaches every document's current version (migration `41a261d02e9e` recorded the current version of documents that predate the journal); earlier unavailable versions are not fabricated. New brief seeds are journaled without inventing a conversation contribution event. PostgreSQL rejects updates/deletes of history while its document exists; deleting the document may cascade its retained journal. Historical event ids are evidence values, so event deletion cannot mutate history through SET NULL.

After a store commits, the room gets the event block and a `state`/`doc` frame; the frame refreshes what derives from the stored version (the overview). Editors do not need it: they already hold the text.

A deferred PostgreSQL constraint refuses an operation transaction that commits without its receipt, rolling back the document, its nodes, history and events together. Operation-specific authorization is enforced even when the legacy room-auth flag is disabled.

The database enforcement is three triggers (`document_history_immutable`, `document_receipt_complete`, `document_receipt_immutable`), from `f7a31e6b920c` and recreated on the current tables by `41a261d02e9e`. Production migration execution is normal CI/CD only.
