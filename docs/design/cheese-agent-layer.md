# 芝士接入层设计（Cheese Agent Layer）

本文件是一份自包含的设计说明：描述如何在现有业务后端之上，接入一个全程参与项目的 AI 队友「芝士」，把平台从"老师发题、学生做题、老师审核"的业务系统，扩展成一个多人 + AI 协作、过程自动留痕的项目协作平台。阅读本文件不需要任何其他文档。

---

## 1. 这是什么

平台的核心是让一个 AI 队友（芝士）全程参与到每个项目里：它在项目中干活、维护文档、回答"现在什么状态"、按需提醒该处理的事。工作本身在平台上发生，过程因此自然留下来，不需要任何人额外填表。

一条贯穿全文的原则：**AI 干得越多，人看的越少。** 人的注意力是系统里最稀缺的资源。芝士的"施工过程"（推理、调试、执行细节）默认不展示，想看随时能看；只有芝士刻意发出的消息、提醒、需要人拍板的决策才会推到人面前；成果必须经过人的验收才算数。

芝士不是从零写的 AI，而是**一个通用的编码 agent（如 Claude Code、Codex 等命令行 agent）+ 平台专属的技能与工具 + 一层多会话调度**。底层模型与 agent 框架都不绑定：平台通过一套稳定的、结构化的接口驱动 agent，换模型、换 agent 框架都不影响平台代码与技能。

---

## 2. 名词

- **项目（Project）**：一个团队协作的容器，等于一个根话题，等于一个代码仓库。项目自管自己的策略（AI 模式、验收规则、主分支保护）。
- **话题（Topic）**：一件事。等于芝士的一个持续会话，等于一条 git 分支。话题可以嵌套成树。
- **子话题（Sub-topic）**：话题下的话题，由芝士的"分身"异步推进，做完结论回流父话题。
- **块（Block）**：平台上所有内容的统一载体——一条消息、一段文档、一个决策、一个附件都是块。块用两棵树组织（见 §4）。
- **文档（活文档）**：话题的持续状态摘要，随时反映"现在什么情况"。人改文档 = 给芝士下指令；芝士改文档 = 向人汇报。
- **现场（施工现场）**：芝士干活的完整过程记录（agent 会话的原始画面/日志）。默认隐藏，按需查看。
- **本体 / 分身**：根话题里的芝士是本体（协调全局）；子话题里的芝士是分身（专注做一件事）。技术上各是一个独立会话。
- **芝士引擎（Agent Engine）**：服务端负责驱动 agent 的整个子系统——编排器、抽象 Agent 接口、各适配器、连接器的服务端、工具、记忆、技能、角色。它是"业务"与"AI 怎么实现"之间的解耦层。
- **连接器（Connector）**：部署在客户机上的组件，把客户机上的 agent 接入平台。由两个平行组件组成：`cheesed`（守护进程）与 `cheese`（命令行工具）。
- **机器管理器（Machine Manager）**：服务端负责供给与回收执行环境（开发环境、预览、算力）的子系统。既服务 agent 执行，也服务人用的工作台。
- **客户机**：运行 agent 的 Linux 机器（Proxmox 上的 VM/LXC、自定义 SSH 机器、或用户自带的机器）。

## 3. 整体架构

服务端（Cheese App Service）分成三个平面，客户机上只放一层薄薄的连接器。下图只用左侧连接符（避免中文宽度撑坏右边框）：

```
Cheese App Service（服务器）
│
├─ 业务层 domain/*          纯业务，完全不知道 AI 怎么实现
│    ├ 现有：user · space · task · team · notification · …
│    └ 2.0 ：block · topic · document · project · review · milestone · …
│         ↕  编排器直接调用业务函数（非事件总线），并在此刻按 agent 权限鉴权
├─ 芝士引擎 agent/*         业务与"AI 怎么实现"之间的解耦层
│    ├ orchestration        每话题串行队列 · 巡检 · 完成检测 · 汇报安全网
│    ├ tools                注解 Python 函数 → schema / CLI / 权限（暴露给芝士的能力）
│    ├ interfaces           抽象 Agent 接口（start / stop / send …）
│    ├ adapters             cheesed_codex（有机器）· naive_api（无机器，进程内直连端点）
│    ├ connector            连接器服务端：控制通道 · 现场代理 · 工具 RPC · 接管仲裁
│    └ memory / skills / roles   记忆三层 · 技能（灵魂）· 专家角色
│         ↕  抽象 Agent 接口
└─ 机器管理器 compute/*     供给 / 回收执行环境（也供人用的工作台预览 / 终端）

     两条跨机通道（cheesed 主动向后端拨号）：
       · 控制通道：长活 + 心跳，承载下行注入、控制命令、现场终端中继
       · 工具 RPC ：一次性请求/响应，cheese-cli 直连，独立于终端通道

客户机 · 连接器 Connector          薄 · 通用 · 带版本 · 零业务逻辑
├─ cheesed                 私有 tmux 托管 agent 会话 · 执行后端下发的注入 · 现场终端中继
└─ cheese（CLI）           agent 通过它调用平台工具；schema 由后端下发、动态生成

agent 运行时：Claude Code / Codex / …   跑在 tmux 会话里（每话题一个）
```

三条解耦缝，都是"只增不改"的接口：

1. **业务层 ↔ 芝士引擎**：编排器**直接调用业务函数**（不套事件总线），并在这一刻按 agent actor 的真实权限鉴权。业务层不感知 AI。
2. **编排器 ↔ 适配器**：抽象 `Agent` 接口。任何"能收消息、能被驱动、有生命周期"的东西都能被适配成一个 `Agent`。当前两种实现：`cheesed_codex`（经连接器驱动客户机上的 agent）与 `naive_api`（无机器项目，进程内直连模型端点）。换 agent 框架只改适配器，工具、技能、业务代码不动。
3. **连接器 ↔ 后端**：冻结的公共协议（见 §11）。

模型能力经统一的 OpenAI/Anthropic 兼容网关取得，可按场景与成本选择模型；使用官方订阅的 agent 也可直接使用其自带额度。

## 4. 数据模型

所有内容是一池「块」。块以追加为主、不修改。下面的结构体只作示意（无右边框，不依赖对齐）：

```
Block {
  id; content; author; author_kind (human | ai | system); created_at;
  kind (message | doc | decision | attachment | event);
  reply_to;        // 对话树：谁回复谁
  struct_parent;   // 文档树：在文档结构里的位置
  refs[];          // 引用：依据哪个决策 / 提交 / 现场记录 / @谁 / #哪个话题
}
```

两棵树 + 时间 + 引用，驱动四种查看方式：按时间看是消息流；按文档树看是结构化文档；按对话树看是 thread；按引用点击跳到来源。一个块可以同时在两棵树里（对话里的一句话被钉进文档某章节）。

核心实体（均为 PostgreSQL 表、SQLAlchemy 2.0 async 模型）：

| 实体 | 关键点 |
|---|---|
| **block** | 万物皆块。双树（`reply_to` / `struct_parent`）、`refs`、`kind`、`author`(→user 或 agent)、可升级为话题 |
| **topic** | 话题 = 会话 = 分支。`parent_id` 自引用树、`kind`(root/topic/subtopic)、`status`、agent 会话引用、`branch_name`、私聊标记、验收/归档时间 |
| **project** | 项目 = 根话题 = repo。`ai_mode`(autonomous/collaborative)、`root_topic_id`、`expert_role`、一页纸摘要、策略设置、成员与角色 |
| **memory_entry** | 记忆条目。`scope`(project/user/skill)。是块树的投影，可从块树重建；主记忆源始终是块与活文档 |
| **notification** | `level`(默记/轻提/强提醒)、`kind`(变更提醒/决策请求/验收请求/巡检/提及)、目标或广播、已读/已解决/反馈 |
| **accept_card** | 验收卡状态机：reviewer、路由理由、状态(待/通过/驳回/撤回)、决定人与时间 |
| **milestone** | 里程碑：截止日期、状态、来源话题 |
| **resource_usage** | 每轮的模型/token/成本记账 |

活文档不是独立的表，而是块按文档树（`struct_parent`）的一种投影；验收（accept）也不额外存正文，产出本身就是话题分支里的文件，采纳即 merge。`topic`（本设计的话题）与现有业务里作为标签的 topic 属于不同语义，需命名空间隔离，避免冲突。用户身份统一走现有 `user` 体系（`author` 为对 user 的引用，agent 作者以 agent 会话表示）。

## 5. Agent 运行模型（连接器）

这是整个接入层的核心，也是与"传统 AI 后端"最不同的地方。

### 5.1 agent 跑在客户机的 tmux 里，长活、agent 无关

每个话题对应客户机上一个 tmux 会话，里面跑一个交互式编码 agent（Claude Code / Codex / …）。tmux 是持久层：agent 在里面可以连续跑几天，进程与上下文都活在会话里，注入新消息即可继续，不必每轮倒腾会话令牌；只有会话/进程死亡时才从 agent 自身的会话记录恢复。

cheesed 用**私有 socket** 起 tmux（`tmux -S <私有路径>`），托管会话跑在一个独立的 tmux server 上——用户在自己机器上 `tmux ls` 看不到它，也无法误连。tmux 二进制随 cheesed 一起分发（可执行文件同级目录优先，再退回 PATH），从而保住"一个自包含的包 scp 过去就能跑"的无环境依赖优势。

平台对 agent 的假设只有两条，因此天然兼容任意此类工具：(a) 它能执行 shell 命令（用来调用 `cheese` 工具），(b) 它接受注入的输入（模拟人在提示符里打字）。

### 5.2 下行：注入（平台 → agent）

平台向 agent 传递的一切——用户新消息、@提及、"改文档即指令"、巡检提醒——都表现为**向该话题的 tmux 会话注入一段输入**（等价于人在提示符里打字并回车，实现上是 `send-keys`）。这是单向的：平台只往下发，不要求 agent 在这条通道上回传任何东西。

注入**由谁决定是后端的事，cheesed 只负责执行**：cheesed 不含任何"何时该发什么"的业务判断，它只把后端下发的按键送进会话（见 §5.5、§11）。

### 5.3 上行：只有工具调用（agent → 平台）

agent 影响平台状态的**唯一**方式，是调用平台工具（通过 `cheese` CLI，见 §7）。agent 的自然输出（推理、旁白）不经这条通道回传，只留在本地屏幕（即"现场"）。这样"上行的信号"只有一种：结构化的工具调用。平台绝不通过解析 agent 的自然语言来感知它的意图。

### 5.4 现场：按需接屏（"逻辑只读"是编排层的概念，连接器不认识只读）

- 默认不传输现场；只有当用户在前端打开"现场"时，才把该 tmux 会话的画面回传显示。用成熟的终端栈实现：tmux 负责持久、`webtty` 帧协议负责中继与重连、`xterm.js` 负责浏览器渲染（见 §6）。
- **cheesed 是一个透明的、永远可读写的中继，它没有"只读"这个概念。** 它把 agent 的输出往上推、把手里拿到的输入（按键或鼠标滚动的转义序列）原样送进 tmux pane。绝不用 `tmux attach -r`，也绝不在 cheesed 上"丢弃观众输入"来实现只读——那会把滚动也一起杀掉。
- 用户看到的"只读"，本质是**编排器对命令发射权的仲裁**，实现在后端：
  - 默认（未接管）：**编排器**掌握命令发射权（自动应答、下发驱动指令）。人只**看**，不能改变 agent 的状态，避免混乱。
  - 前端有一个显式的"接管"开关。开启后，后端通知 cheesed **暂停自动发射**（免得和人抢），并开始把**这个前端的输入**转发给 cheesed；设自动释放超时，避免永久占用。
- **滚动在任何状态都能用，而且滚动就是真的向终端发转义序列。** 两种机制并存：(a) 每个观众的 xterm.js 保留充裕的本地回滚缓冲，随时像在自己电脑上一样上下翻已收到的历史；(b) 接管者的鼠标滚轮帧会被转发给 agent，用于 agent 自身 TUI 的原生滚动。非接管者的输入由**后端**决定不转发（这才是"逻辑只读"的落点），cheesed 自身始终不知道这回事。
- 现场历史：直接使用 agent 自带的历史会话浏览能力；平台也可将会话记录拷出作为珍贵的数据留存（受数据留存协议约束）。

### 5.5 状态检测与完成信号（机制在客户机，决策在后端）

平台不消费 agent 的输出流，因此"这一轮干完了"要另找信号。这里严格区分**机制**与**决策**：

- **机制（cheesed 提供）**：cheesed 通过 `capture-pane` 读出屏幕内容，做与具体 agent 界面无关的通用**静默检测**（一段时间无新输出 = 空闲），并把屏幕状态 / 空闲信号回报后端。它也**只**提供 `send-keys` 这个执行原语。
- **决策（后端拥有）**：屏幕里出现某种提示该回什么、该不该驱动下一步、接管锁归谁——这些都是业务判断，全部在编排器里做，通过控制通道下发给 cheesed 执行。检测规则、应答策略绝不硬编码进连接器。

完成的语义由**刻意的工具调用**给出（干完活发一条变更提醒）。作为安全网：当后端检测到 agent 已空闲、且自上次发言以来确实有工作发生（工具调用/文件变更）、但一段时间（如 30 秒）内没有对外说任何话时，编排器自动注入一条命令，要求 agent"若有值得团队知道的就报一句，否则保持沉默"。

## 6. 通信与信道

客户机与服务器之间有两条通道，职责分明：

1. **控制通道（cheesed ↔ 后端）**：长期保活、带心跳、可靠、支持断线重连。由 cheesed 主动向后端拨号建立。一条 WebSocket 上复用两类消息，按帧类型分流：**文本帧 = 控制 JSON**（拉起/挂起会话、注入按键、开关现场、接管、resize），**二进制帧 = 终端数据**（`webtty` 帧：agent 屏幕输出上行、接管者输入下行）。浏览器侧的现场也走同一套 `webtty` 帧协议：`浏览器 xterm.js ↔ 后端 ↔ cheesed`，后端把输出帧扇给所有观众、只把当前接管者的输入帧转给 cheesed。
2. **工具 RPC（cheese-cli → 后端）**：一次性请求/响应，独立于终端通道，走可靠的 HTTP。agent 每次调用工具，`cheese` CLI 向客户机本地的 cheesed（固定的五位环回端口）发一次请求，cheesed 附上 session token 转发到后端；结果同步返回并作为命令输出回注给 agent。

两条通道都必须当作**长期冻结的公共 API** 来设计：带版本号、只做加法、向后兼容（见 §11）。选用 `tmux + webtty + xterm.js` 这套成熟组合，正是为了把重连、屏幕缓冲、渲染这些易错的东西交给久经考验的库，连接器自己只保留最少的粘合逻辑。

## 7. 工具：后端的注解 Python 函数

平台提供给 agent 的每个工具，就是**后端上一个带类型注解的 Python 函数**（位于 `agent/tools/`）。函数的签名（参数 + 类型）产出入参 schema，docstring 产出说明，返回值约定产出输出。围绕它自动投影出多种形态：

- **schema**：由函数自省生成（`{name, description, input_schema, output_schema}` 形状，与 JSON Schema 兼容）。
- **cheese CLI**：`cheese` 从后端拉取 schema，据此把工具暴露成 `cheese <命令> --参数 值 --标志` 的友好形式，输出简洁的非-JSON 文本，并能生成 `--help` 与子帮助。帮助文本一律由 CLI 库生成，不手工拼接。
- **适配器视图**：有机器项目经 cli/RPC 调用；无机器项目可由同一批函数投影成 function-calling 规格并在进程内直接执行——一份定义喂多种适配器。

约定：

- **agent 参数与平台注入的上下文分离。** 只有 agent 提供的参数才成为 cli 标志 / schema 字段；`actor / project / topic / session` 由 RPC 的 session token 解析后注入，**绝不作为 agent 可填的参数**。
- 工具函数是 `async` 的。
- 输出的人话文本要有确定来源（结果里带 `message`/摘要字段，或 schema 里带渲染提示），cli 据此打印，不对结构化结果瞎猜。
- schema 每会话拉取一次并缓存。

初始工具集（大致）：`chat`（往话题发一条消息）、`notify`（分级变更提醒/决策请求）、`doc`（读/写活文档）、`split`（拆子话题）、`conclude`（子话题结论回流）、`decision`（记决策）、`title`（起/改话题标题）、`remember`（写记忆）、`accept-request`（递验收卡）、`milestone`（钉里程碑）、`members`（列成员）。

## 8. 编排器与业务层

- **直接函数调用，不用事件总线。** 同步路径（一条用户消息触发一轮、一次工具调用执行）都是普通 async 调用。
- **每话题串行队列。** 保证同一话题不并发跑两轮 agent；不同话题并发。V0 单 worker 用进程内串行即可，多 worker 时改用现有的 Redis/taskiq 队列。
- **异步/主动路径复用现有基建。** 定期巡检发通知、子话题结论回流、决策被隔天回答、推送前端等发后即忘的事，走现有的 taskiq 队列 + WebSocket 推送 + 通知表，不另包一层"事件"抽象。
- **调度分两层**：确定性的（消息路由、定时、生命周期）由平台代码做；需要判断的（该催谁、该拆什么、有什么风险）由根话题的芝士（巡检）判断。

## 9. 说话 vs 干活

- **agent 的自然输出只属于"现场"**（默认隐藏）。它不是一条聊天消息。
- **一切对外表达都是工具调用**：普通发言走 `chat`，分级提醒/决策走 `notify`。房间里可见的每一句话，都是 agent 刻意调用工具产生的。
- 因此聊天消息落成 message 块（携带显式的 `level`/`reply_to`/`mentions` 等参数），现场则是会话原始记录（轻量存储，不逐句落块）。
- 这把重量压在**技能（对话风格 skill）**上：技能必须教会 agent"普通输出是只在现场可见的工作记录；要对团队说话必须调工具；没值得占用注意力的事就闭嘴"。§5.5 的汇报安全网是对"干完忘了说"的兜底。

---

## 10. 权限与安全

- **session token 只表身份**（哪一次 agent 运行、绑定哪个项目/话题），**不携带任何权限**，放在请求 header（不放 query string），并限定到该话题 + 有限工具集 + 短 TTL。
- **授权在编排器派发到业务函数那一刻强制**：检查主体是**这个 agent 会话（agent 作为一等 actor）**，其权限范围来自项目策略（AI 模式、所在话题）与硬规则（如"AI 不能验收自己做的东西"）。后端**绝不因为 token 合法就放行**。
- 复用现有权限系统：每个 `@tool` 函数声明自己需要的 `(action, resource)`，编排器以 `actor = agent 会话` 调用现有的权限检查器。召唤 agent 的用户只作归属/审计信息，不是权限来源。
- 因此 token 即便活在用户可控的客户机环境里也安全：泄露的爆炸半径 = 该会话本就被允许做的事。
- 审计天然免费：git 历史 + 块的记录构成审计链——谁做了什么、AI 自主还是人指挥、谁验收的，全有记录。

## 11. 连接器冻结原则（一等约束）

一旦发布，要求客户机更新连接器是很麻烦的事。因此：

> **连接器是一个瘦的、通用的、带版本的客户机宿主，且不含任何业务逻辑。一切易变的东西——工具、prompt、专家角色、模型、用哪个 agent、状态检测规则、命令发射与接管锁——都从后端当配置/数据拉取或由后端决定。连接器 ↔ 后端的协议当作冻结的公共 API 设计：带版本、只做加法、向后兼容。再留一个自更新钩子作为逃生阀。**

为什么零业务逻辑是硬约束：**业务更新必须无需用户更新客户端就能生效。** 只要有一条业务规则（发什么、何时发、谁能接管）活在客户机二进制里，改一次规则就要逼所有客户机重装一次。

落实要点：

- **工具靠后端下发的 schema 动态生成**：加/改工具只动后端，`cheese` 这个 schema 驱动的通用 CLI 一行不改。
- **cheesed 是通用宿主 + 纯机制**：只做"在私有 tmux 里跑某个 agent、执行注入、通用空闲观测、终端中继"这套稳定原语；跑哪个 agent、检测规则、应答策略、接管仲裁、环境、模型等全部由后端在会话中决定与下发。
- **协议从第一天就版本化**：连接器上报自身版本，后端兼容旧版本，变更只增不改。
- **自更新钩子**：连接器可被命令自更新，把"要求客户升级"从人工变为推送。

自动安装（把连接器 Copy & Install 到裸机并拉起）由机器管理器（§12 `compute/`）负责，不在本设计的首期范围；先假设连接器已在客户机上以受管方式安装就绪。

## 12. 代码组织

服务端分三个平面 + 客户机一层连接器。芝士引擎（`agent/`）与机器管理器（`compute/`）都不是业务域，各自独立于 `domain/`（下方目录树只有左侧连接符，注释不依赖对齐）：

```
cheese-backend-py/
├── backend/app/
│   ├── domain/               业务层：纯业务，不感知 AI
│   │   ├── block/            §5 万物皆块：双树 + refs，数据地基
│   │   ├── topic/            §6 话题：块升级、树、生命周期、采纳=merge
│   │   ├── document/         §7 活文档：块的文档树投影、docs-in/docs-out
│   │   ├── review/           §4.4 验收：reviewer 分配、accept、主分支保护
│   │   ├── milestone/        §7.2 里程碑 / 日历
│   │   ├── project/ space/ task/ team/ user/ notification/   现有域，2.0 复用 / 扩展
│   │   └── …                 其余现有域（answers / questions / … legacy 共存）
│   ├── agent/                芝士引擎：业务与 AI 实现之间的解耦层
│   │   ├── interfaces.py     抽象 Agent 接口（start / stop / send …）+ SessionHandle
│   │   ├── orchestration/    编排器：每话题串行队列、巡检、完成检测、汇报安全网
│   │   ├── authorization/    编排器→业务/工具 边界的 per-actor 授权（安全支点）
│   │   ├── tools/            暴露给芝士的注解 Python 函数 → schema / CLI / 权限投影
│   │   ├── adapters/         cheesed_codex/（经连接器）· naive_api/（无机器直连）
│   │   ├── connector/        连接器服务端：控制通道、现场代理、工具 RPC、接管仲裁

│   │   ├── provisioning/     PVE LXC/VM 生命周期、Copy&Install cheesed
│   │   ├── preview/          反向代理预览、code-server
│   │   └── quota/            算力调度、项目额度、排队
```

## 13. 分期与范围

**首个纵切片（V0）**——在一台客户机上打通最难、最不确定的那条链路，作为架构的验证：

1. cheesed 在私有 tmux 里拉起一个 agent，并能可靠地向其注入输入（`send-keys` 进交互界面）；
2. 后端据屏幕静默判断"在跑 / 干完"；
3. 一次工具调用的完整往返（`cheese` → cheesed → 后端业务函数 → 结果回注 agent），产生可见的平台状态变化；
4. 前端经 `webtty / xterm.js` 接屏、可接管、滚动顺畅。

跑通即证实架构与库选型。此后在冻结的接口背后扩展业务功能。

**不在本设计范围内**（作为后续独立工作）：机器管理器的自动建机与回收（Proxmox）、复杂 SSH 与反向隧道、网页版开发环境（code-server）、无机器项目的直连适配器、外部额度中转站的对接、跨机全量日志汇聚。

## 14. 必须遵守的约定（实现红线）

1. 平台只通过**结构化工具调用**感知 agent；**绝不 regex 解析自然语言输出**。
2. agent 的自然输出只属于"现场"（默认隐藏）；一切对外表达走工具。
3. 工具 = 后端带注解的 Python 函数；schema / CLI / 权限 / 校验都从函数投影；**agent 参数与注入上下文分离，actor 绝不来自 agent 参数**。
4. 工具 RPC 的授权在**编排器 → 业务函数**处按 agent actor 的真实权限强制；session token 只表身份、放 header、限 scope + TTL；**绝不因 token 合法就放行**。
5. **客户机上的二进制（cheesed / cheese）零业务逻辑**：薄、通用、带版本；工具、检测规则、命令发射、接管锁等一切易变逻辑都在后端；协议只增不改、向后兼容，让业务更新无需客户端更新。
6. **"逻辑只读"是后端仲裁，不是 cheesed 的只读**：cheesed 是透明全双工中继、永远可读写；只读 = 后端不转发非接管者的会改状态的输入；滚动在任何状态都必须可用（本地回滚 + 接管者滚轮转发），绝不用 `tmux attach -r`。
7. 编排器与业务层**直接函数调用**；每话题**串行队列**，同一话题不并发跑两轮。
8. 芝士引擎（`agent/`）与机器管理器（`compute/`）**独立于业务域 `domain/`**；编排器、适配器、连接器服务端都放 `agent/` 下，不塞进 `domain/`。
9. 块**只追加不修改**；文档可编辑 = 下指令；成果**须经人验收**。
10. 数据与存储沿用现有约定（PostgreSQL + SQLAlchemy 2.0 async + Alembic 迁移）；新话题模型与现有标签 topic **命名空间隔离**。
