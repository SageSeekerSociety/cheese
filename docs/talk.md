### 1.1 后端重构：多仓收敛为 `cheese-backend-py` ⭐

- **背景问题**：原来同一个产品拆在三个仓（NestJS cheese-backend + Kotlin cheese-backend-nt + Vue 前端），**对新人不友好、对 AI 也不友好** —— Codex / Claude Code 在多仓里上下文切换会丢太多信息，新同学要同时看 TypeScript 和 Kotlin 才能干活
- **做了什么**：用 Python / FastAPI **把多后端迁移合并到单一仓 `cheese-backend-py`**，保留 Kotlin 仓为线上生产（eTrip 在用）
- **为什么是面向未来的基建**：
  1. AI coding 在单一代码库里才能真正发挥（后面 §2 讲 AI coding 内置时直接依赖这层）
  2. 梯队大一大二**上手一个 Python 仓**远比同时学 NestJS + Kotlin 现实
  3. 是后面所有动作（梯队 / AI coding / 阿里合作）的**结构性前提**
- **现状**：仓库 3 月初建成，**636 个集成测试全通过**，功能与 Kotlin 仓对齐；线上暂保留 Kotlin 仓运行不动 eTrip

## 2. 产品方向系统性重定位（5-7 min）

详细版见 `docs/vision.md`（v0.6）。今天讲三层。

### 2.1 定位升级

- 从"协作 / 进度管理平台" → **"广义科研 / 开发的全过程平台"**
- 关键姿态：**工作本身在知是上发生**，不是在外部做完来填周报
- 参考：北邮有个类似平台叫"智链"，我们要做出差异化

### 2.1a "广义科研"的边界 —— **这里有个概念 gap，要说清楚**

> "两位老师做的科研是 paper-driven 的学术研究，知是讲的'研究'范围比这更宽。我特意把它叫**广义科研 = 项目 / 问题解决的全过程**。"

**为什么要扩展到广义：**

| 场景 | 是 paper-driven 科研吗 | 是"项目 / 问题解决"吗 |
|---|---|---|
| 高瓴博士生做 Agent 研究 | ✅ | ✅ |
| 信院创研课本科生 | ❌（一般不出 paper） | ✅ |
| 明理书院创新项目 | ❌（偏创业 / 应用） | ✅ |
| eTrip 校企合作（阿里 / 华为赛题） | ❌（纯解问题） | ✅ |
| 大一大二用 AI 写功能（梯队本身） | ❌ | ✅ |

**扩展的两层理由：**

1. **知是面向的真实用户大部分是右列而非左列** —— 狭义 paper-driven 科研只是我们光谱的一个高端子集，不是全部
2. **但狭义科研是"广义科研"的最高阶形态** —— 如果我们把"项目/问题解决的全过程"做扎实，窦老师高瓴学生的 paper-driven 工作流自然是其中一等公民

**这个扩展对 §6 数据论点的含义**：
- **paper-driven trajectory** 稀缺、学术价值高（对顶级研究 AI 的训练）
- **广义项目/问题解决 trajectory** 更 scale、更普遍（对 AI 服务更广用户的能力训练）
- **两种数据对 AI 训练都稀缺，而且角度互补** —— 知是同时积累这两类，是它的独特之处

> 给两位的暗示：我们不是绕开科研讲应用，我们是在"科研"之外开了一条更宽的路，但**高瓴的 paper-driven 科研是这条路上最高价值的用户场景**。

### 2.2 核心叙事 —— 学生在一个项目里的 6 个环节

这 6 个环节对 paper-driven 科研和对"广义项目/问题解决"**都适用**，只是每一环的深度不同：

`选题 → 文献 → 讨论 → 动手 ⭐ → 沉淀 → 汇报`

**这一节是我最想请窦老师从学术 / 带学生经验判断"有没有漏 / 有没有多"的部分。**

---

**① 选题 (Onboarding to a project)**
- **数据源多样**：老师发的课题 / 企业需求（eTrip） / 书院项目 / 学生自发 / 基于订阅的推荐
- **同一个界面、不同数据源** —— 学生不用切换"找课程作业 / 找科研机会 / 找实习项目"三种不同工具
- **角色自适应**：只要匹配不要过程的老师（如商学院）直接看极简的"发需求 + 看应征"控制台

**② 文献 / 调研 (Before you start doing)**
- **Paper 中文 TLDR 订阅** —— 学生关注话题后每日 TLDR + 周度趋势总结
- **老师自动学术主页** —— 爬取 paper + 近期动态聚合；**高瓴场景最重**（招生 / 选导师 / 对外展示）
- **项目内 References** —— 从全局订阅"钉"相关 paper 到项目，形成项目文献库
- **AI 助手** —— 基于 Project 上下文找相关工作、生成综述骨架

**③ 讨论 (Making sense of what to do)**
- Discussion 模块（@mention / reactions / 嵌套回复）已有
- **行内 @AI** —— 任何评论里 @AI 带**项目级记忆**参与讨论
- **Project Assistant 抽屉** —— 项目页右侧常驻 AI Chat，单独问关于这个项目的任何事
- **三层 AI 记忆**：Thread / **Project**（项目级 ⭐ 这是差异化） / Personal

**④ 动手 ⭐ (Where the real work happens) —— 新核心**
- **AI coding 内置** —— 每人一个 coder 实例 + Claude API（通过阿里 coding plan 合作接入）
- **GitHub 关联深化** —— 从现有 `github_repo` 字段升级到双向同步 + PR 风格评审
- **实验记录** —— 结构化 run / result / notes 日志
- **和"GitHub + Notion 组合"的根本差别**：工作真的在平台上发生，不是做完来填周报

**⑤ 沉淀 (What stays after)**
- Knowledge 模块（labels / upvotes / 全文搜索，支持从 Discussion 转化）已有
- **Project 成果页** —— 对外可见的项目主页，"项目即简历"的载体
- **跨项目弱链接** —— 同一篇 paper / 同一位老师 / 同一话题形成汇聚点（类似轻量研究图谱）

**⑥ 汇报 / 评审 (External evaluation)**
- **Progress Stream + Milestone** —— 结构化进度记录，update_type 分 PROGRESS / BLOCKER / ACHIEVEMENT / NOTE
- **AI 周报** —— 基于 Progress 自动生成给导师 / 企业方 / 学院管理层
- **老师 / 企业 Dashboard** —— Space 下所有项目的健康度总览
- Discussion 作为评审媒介（评委评论、学生答复、答辩）

---

**其他结构要点：**
- **匹配不是独立产品**，是发现（环节 ①）的一种 flow
- **Space（横向组织）/ Project（纵向项目）是同一份数据的两种切片**，老师主场看 Space，学生主场看 Project

### 2.3 战略 insight ⭐：广义科研协作过程即训练数据

> "这是我这几个月最想和两位讨论的一个判断。现在 AI 往 Agent / 研究能力方向发展的瓶颈不是模型，是数据 —— 而最稀缺的那类数据，恰好是我们正在积累的。"

**现有 AI 训练语料的三个结构性缺口：**

1. **社交信号（social signals）** —— 人在协作里的微观信号（让步、追问、推辞、如何把模糊想法推进到行动），几乎不在代码 / 论文 / 技术文档里
2. **任务拆解轨迹（task decomposition traces）** —— 把"做一个 RL 新方法" 或 "写一个赛题方案" 这种模糊目标**一步步拆成可执行子任务**的中间推演，通常只在研究者脑子里
3. **长周期研究 / 项目（long-horizon research & projects）** —— 现有 code / agent benchmark 基本是几分钟到几小时的短任务；**几周到几个月**的研究或项目 trajectory 在公开数据集里几乎空白 —— **这是 AI 从"会写代码"到"能做科研"的鸿沟**

**知是天然承载这三类数据（paper 科研 + 广义项目两种 trajectory 都能采集）：**

| 缺口 | 知是上的自然产生处 |
|---|---|
| 社交信号 | Discussion（@mention / reactions / 嵌套）+ 评审评论 |
| 任务拆解 | Milestone + Progress Stream + commit 历史 + AI coding session 的指令轨迹 |
| 长周期研究/项目 | Project 全生命周期（从选题到汇报的完整 6 环节）+ 跨学期延续 |

**关键**：这些数据是用户**正常使用的副产品**，不需要打标签、不需要改工作流。

**活体样本已经在产生：**
- **梯队自己** —— 大一大二在知是上讨论、AI 辅助实现、PR、review、合并的完整链路（每月 6-7 个改动）
- **eTrip** —— 学生团队做阿里 / 华为赛题的跨周 trajectory
- **未来高瓴博士生** —— 如果 pilot 起来，paper-driven 科研的 trajectory 就能被系统化采集（这恰好是现在公开 benchmark 最缺的部分）

**对阿里合作的定位升级**：
> 从"用 Claude API 的客户" → "为下一代 AI 的**研究能力 / Agent 能力**生产稀缺训练数据的合作方"
> 合作逻辑从"阿里资助 + 我们买 API" → "**共同构建数据飞轮**"
