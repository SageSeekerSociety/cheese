# 看板 {#boards}

项目的任务列表（「全部任务」和「总览」里的「谁在做什么」）、跨项目的「待我处理」、平台看板的三个分类，以及它们共同的一条纪律：这些数都不存，每次从当下的事实现算。

> 讲：每一块读哪几张表、判据在哪、窗口和口径怎么定。不讲：任务落在哪一列的判据本身（见[任务与工作目录](/dev/tasks)），交付链路上每一步的顺序（见[任务 → 分支 → PR → 验收合并](/dev/delivery)），通知怎么发出去（见[通知与待办](/dev/notifications)）。

## 任务列表：列是推出来的，不是挑出来的 {#board}

「全部任务」按列分组，列只有一条规则，在 `room_task/presentation.py`：**判据是「该谁动」**，不是「事情进行到哪一步」。所以同一个客观事实会因为下一步在谁手上而落在不同的列——快检红了，平台已经派芝士去修是「修复检查」（`delivering`），那个红没人能清掉是「检查未通过」（`needs_you`）。

| 列 | 意思 | 属于它的短语 |
|---|---|---|
| `building` 进行中 | 在做，还没递出交付 | 芝士在做、在等结果、进行中、空闲（房间）、草稿（房间） |
| `delivering` 检查中 | 下一步在平台/芝士手上 | 检查运行中、等待检查、修复检查、解决冲突、平台更新分支 |
| `needs_you` 待处理 | 下一步在人手上 | 检查未通过、待审阅、已退回、待回答、卡住了 |
| `done` 已关闭 | 已采纳，或已关闭 | 已采纳、已关闭（关闭时留没留结论都是这一句） |
| `archived` 已归档 | 房间才有；任务不归档 | 已归档 |

每一列只说属于自己的话，而这一条不是靠注释守的：每个短语是它那一列专属枚举的成员，列由成员的类型查出来（`_COLUMN_OF` / `_show`），`COLUMN_PHRASES` 也由同一张表推出来、不手写第二遍。没有任何一处分别挑一个列和一个短语，所以「显示了一句不属于本列的话」结构上写不出来。前端不再做第二张映射表（`frontend/src/cx_types.ts` 明写了这一点）——两次映射，两边就会各说各的。

`GET /projects/{id}/tasks` 一次把「全部任务」、「总览」和侧栏要的东西拼出来（`api/routes/projects.py`）：任务的列表、每条任务最新那张卡（`latest_cards_by_task`）、哪几条停在一个未回答的提问上（`tasks_awaiting_an_answer`）——三次批查询，不是每条任务三次。一个项目一百多个房间，按房间的形状（`/topics/{id}/tasks`）画一次侧栏要发一百多次请求。

两个刻意的细节：**一次只取一个「现在几点」**（`now = datetime.now(UTC)`），逐行取 now 会让同一批数据里两条本该一样的活分到不同格子，而那种差别没人再能复现；**任务的会话在跑是事实，队友报的进度只填空**：这条活自己那位队友的会话在跑（`TaskFacts.teammate_runs`，`agent.teammate_runs` 读 `session_states`，`worker_status` 为 running，每个在跑的会话在哪一次跑由 runner 说）而它在这一次跑里没报过别的（`TaskFacts.progress_run` 不是其中一次），就是在做；其余时候在做、在等、卡住读的是 AI 队友自己报的进度（`TaskFacts.progress`，即 `Task.progress_state`）。房间的任务列表（`/topics/{id}/tasks`）和房间快照每行另带的 `session_running` 只说它的会话此刻是不是在干活，会话开着但闲着也是 false；房间自己那一格的「运行中」读的也是它自己那条线的 `session_states`（同一个 `running_conversations`）。事实被收窄成显式的小结构（`CardFacts` / `TaskFacts` / `RoomFacts`）再交给纯函数，这样这层测得起来，也说清了它到底读了哪几个字段。

## 待我处理 {#awaiting}

「全部任务」回答「这个项目现在有什么在等人」，「待我处理」（`GET /awaiting-me`）回答「**我**现在要处理什么」。两者读的是同一个 `presentation`、同一份收件人判据（`addressing.py` 的 `address()`），差别只有范围：从一个项目扩到我能看见的全部项目。

`room_task/awaiting.py` 只给形状，不碰 I/O——拉哪些项目、房间、卡是 API 那一层的事（`api/awaiting_deps.py` 的 `waiting_items`，要问六个地方，和项目任务列表那两份是同一个形状）。这有两个硬理由：

- **不能读通知表**。通知是一条条**事件记录**，不是状态：卡递上来发一条，之后它被驳回、作废、或者别人先处理掉了，那条记录还躺在表里，从它身上读不出它已经不作数了。「还没处理完的有哪些」必须从当下的事实重算。
- **判据只有一份**。「点到的是谁」曾经在这里有一份、投递那侧另有一份，那个形状就是列表显示「待处理」而没有人被通知到。现在清单和投递都调 `address()`：通知负责把人叫回来，清单负责他回来之后不用自己翻。

一个容易写错的地方：房间里那张卡要看 `task_id is None` 才是**房间自己**的（`_room_cards`）。一条活递的卡把房间记在 `topic_id` 上，不过滤的话，一条活在等验收会让它上面那个房间也显示成等验收。哪些状态算「还没结算」不在这里数，那张表由 `review/archive.py` 的 `OPEN_CARD_STATUSES` 维护。访客拿到空列表、不是错误——这个清单的定义就是「点到我的那些」，而没有身份的调用者没有被任何一件事点到。

## 平台统计 {#platform-stats}

`domain/platform_stats/` 是管理员看板，三个分类（反馈 / 用量 / 平台）在页面上是三个控件，切到哪一类才拉哪一类，所以是**一个服务被三条路由各问一次**（`/admin/stats/{feedback,usage,platform}`），不是一条接口把所有东西一次吐出来——一次吐出来意味着切到第二、三类时读的是几十秒前的数，而那三类里有两类读的是全平台增长最快的表。（另有 `performance` / `pipeline` / `product` / `integrations` 四条，各读各的。）

两条纪律写在 `services.py` 的模块说明里，都是可检验的：

- **窗口是必填的，不是默认值**。`resource_usage` 每调一次 `/v1/messages` 就长一行，没有 `WHERE` 的全表聚合在页面上一次都不允许出现。窗口由 `utc_day_window` **一处**算出来（半开的 `[since, until)`，UTC 的天），三个方法都从这里拿。`days` 在路由上就收口（`Query(default=7, ge=1, le=90)`）。
- **序列一律补齐到 `days` 天**（`dense_series`）。缺天不补的话折线会把 7 天画成 5 天，而且没有人看得出来——断点处是一条平滑的线，不是一段空白。`prev` 是上一个**等长窗口**（`[since-days, since)`）的合计，给 KPI 卡的环比差用，前端自己算不出来。pipeline 不配 prev：它以存量指标为主，没有可环比的流量合计。

上界也是查询的一部分而不是优化：按项目、按模型、按人的 top-N 都同时收窗口和 `limit`（`TOP_PROJECTS` / `TOP_MODELS` / `TOP_USERS` 都是 10，最近的调用列 `RECENT_CALLS` 50 行），少任何一个都会让这个读在全平台最长的表上无界。

用量那一屏还回答谁在用、什么时候用、缓存命中多少，口径写在 `platform_stats/usage_detail.py` 的模块说明里：

- **缓存命中率** = 缓存读 ÷ 输入（输入在每条通路上都含缓存读写）。只算记了缓存的行：同一通路、同一 `kind` 的行从窗口里第一次记下缓存读起算，之前那几行的 0 可能只是没记（网关按天结算的那条路在开始记录缓存之前一律是 0）。一类行一次缓存读都没有就没有命中率（`null`），不写 0%；没算进去的输入量单独给出。
- **按人**是谁**触发**了多少：项目里的行按 `turn_id` 找到发起那一轮的那条人发的消息，取它的署名；项目外的行本来就记了 `user_id`。平台自己发起的轮次不算在任何人头上，合计在 `unattributed`。这是触发了多少消耗，不是贡献（#394）。
- **每小时**的序列（北京时间）只在窗口不长于 7 天时给，补 0 只补到当前这个小时；更长的窗口是 `null`。
- **金额**是按单价估算的标价，不是实付：订阅路按同一模型的单价估算，网关里自托管的模型也按价目表计价。

**口径是那一段的全部内容**，所以每个方法把自己的口径写在最前面。反馈那一块的例子值得记下：看板数的是**整个板子**（`admin_board_counts`），不是公开那一臂——此前卡片走 `FeedbackService.counts`（它被 `PUBLIC_ONLY` 收窄，因为那是给匿名读者看的数）、旁边的曲线走全量，于是卡片上的「进行中」和曲线下的「进行中」是两个口径，两边各自都看着对。`unread` 仍然走 `counts` 且只取那一个键：它问的是**这个管理员**读到哪儿了，人各一份，和板子多大无关。

用量那一屏还有一块**不在库里**：订阅通路身后的 Claude 账号池（响应里的 `claude_accounts`）。池子只活在跑计量代理的那台机器上，后端跟它没有通路，读数来自代理写在用量账本旁边的一份快照文件（[计量代理](/dev/metering-proxy#pool-snapshot)）。所以这一块有三种画法，判据在 `lib/adminPool.ts`：有行就画行（账号名 + 状态，冷却的带解冻时刻和连续失败次数）；一行都没有就画**为什么看不见**——后端给的是 `not-configured` / `missing` / `unreadable` / `malformed` 四个代号之一，界面翻成话（后端写中文句子的话，英文界面里会漏出中文）；快照旧了照常画行，另注明它写于何时。底下那句总述数一遍各状态，有账号冷却时再给出最早恢复的时刻——全部冷却时这是看板上唯一说得清的话，那会儿 token 曲线只会显示「今天用量下降」。

## 项目概览与个人页 {#dashboard}

`domain/dashboard/services.py` 是「往上抽一层」的读汇总（spec §7.2/§7.3），**只读**，数据仍然归各领域的表所有。

- 项目卡片（`_project_card`）：频道数按状态分、最近一次活动、人/AI 贡献比。
- **贡献比读署名，不读事件行的档位**：档位只分得出「参与者」和「平台」，而这张活跃度问的正是参与者里的哪一种——按档位分组再滤掉平台事件，剩下的全是同一个档，两个数字都归零。判据是 `looks_like_agent_handle(author)`。
- 机构看板（`space_board`）：这个空间下每个团队一行。它走 **Space → 赛题 → 项目**（`list_ids_for_space_tasks`），不再走 Space → 模板 → 任务 → 关联表那条和赛题平行的层级（#370）。
- 个人页（`user_profile`）：一年的热力图按 UTC 天、按项目，每个项目再切出最近 12 周的 sparkline（`_SPARKLINE_WEEKS`），和 `day_windows.py` 用的是同一个「一天」。私人一对一聊天不算任何频道列表的一部分，在本人自己的页面上也不算（`_listed_topic`）。

## 边界与坑 {#traps}

- **任务列表不存状态，每一列都是当时算的**。没有哪张表记着「这条活现在在待处理列」——存一份就有一个必须在每条路上记得改的地方。
- **列与短语绑死**。加一个短语就是加一个枚举成员，它自动落进它那一列、自动进 `COLUMN_PHRASES`；想让它出现在别列，只能改它的类型，而那是唯一一处。
- **管理员看板的每个数都绑定在一个窗口上**。看到「新增 3」时说的是那个 `days` 窗口里的 3，而不是总量；卡片的总量和曲线的窗口是两套口径，方法说明里会分开写。
