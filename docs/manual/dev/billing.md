# 计费流程 {#billing}

用量怎么计、记在谁头上、用完了怎么办。

> 讲：两处计量、折算、两道刹车，云端算力怎么计。不讲：请求怎么走，见[模型调用流程](/dev/llm)。

## 额度从哪来 {#grants}

额度以「算力额度」（credits）为单位，一笔一笔的额度包（`compute_grants` 表）只挂在团队上，不发给团队里的个人。准入、扣费和余额都走 `usage/` 里的账本 `Ledger` 这一处：只读的一半在 `usage/ledger_queries.py`，写入和发放的一半在 `usage/ledger.py`；计划的时间窗口、费率、付款方和余额规则各在 `usage/windows.py`、`usage/rates.py`、`usage/payers.py`、`usage/balance.py`。每个包记着：

- `source`：来源。方案按期发放（`plan_period`）、题目发给项目的定向额度（`task_earmark`）、购买（`purchase`）、管理员发放（`admin_grant`）。
- `project_id`：有值时只给这个项目用。
- `expires_at`：到期后不能再用；为空的不过期。

一次调用由它发生的地方决定扣哪个团队：团队项目扣该团队；项目之外的调用和本人名下的项目扣本人名下的个人团队，名下项目里别人召唤芝士也扣所有者的。按月发放的方案按这个顺序扣，前一类用完再扣下一类，最后一次调用允许透支（按时间窗口限额的方案见[方案](#plans)）：

1. 题目发给这个项目的定向额度
2. 付钱团队本期的方案额度
3. 另购或管理员发放的额度，先到期的先扣

额度用完之后记录仍在，新建项目也绕不过去。包都过期之后才到账的花费，记在这个团队最近的一个包上。

每一行 `resource_usage` 都记下付钱的团队（`team_id`）和这一行扣了多少额度（`credits`），由 `Ledger.record` 一并写入和扣除；不知道花了多少 token 的那种行（`:unmetered`）也一样，额度记 0。

## 方案 {#plans}

每个团队挂在一个方案上（`team.plan_key`，指向 `plans` 表），新建的个人团队和共享团队都是 Free。方案是表里的记录，不写在代码里：计费方式、允许哪些档位的模型、适用于个人、团队还是两者、排序（`rank`）。计费方式二选一：按月发放（`credits_per_period`），或按时间窗口限额（`windows`）；两样都填或都不填的方案，管理接口拒绝保存，只有不限量的方案两样都没有。迁移建了两条：Free（按月发放，每月 500 额度，即 5 美元；只许 included 档，订阅的 Claude 模型都不在其中）和 Reserve（不限量、不限模型，只给平台自己的团队）。方案改了从下一期起生效，本期已发的包不变。没有团队在用的方案可以删除，新团队默认的方案（Free）不能删。

- **按月发放**：本月的方案包在本月第一次扣费时写入，`(team_id, period_start)` 上的部分唯一索引保证并发时也只写一条；在那之前，余额已经把它算在内，所以读余额从不写库。到平台时区的下月初作废，不结转。准入（`Ledger.admit`）在余额用完时拒绝，说明哪天重置（「本月额度已用完，11月1日重置。」）。
- **按时间窗口限额**：不发包，每个窗口在一段时间内最多用多少。窗口有两种：`{hours, credits}` 从团队第一次调用开始计时，到点清零，下一次调用再开新的一轮；`{calendar: "week" | "month", credits}` 在平台时区的周一 0 点、每月 1 日 0 点清零。每个团队每个窗口这一轮的开始时间和已用额度记在 `plan_window_use`，扣费时一条 upsert 写入，过期的一轮由这次扣费重开，并发的两笔都会记上。扣费先扣题目给这个项目的定向额度，剩下的计入每个窗口；有窗口满了之后，剩下的改扣另购或管理员发放的额度，这两类都不计入窗口。准入在所有窗口都没满时放行；有窗口满了，还有定向、另购或发放的额度就放行，没有就拒绝，说明那个窗口何时清零。方案从按月发放改成按时间窗口时，本月已发的方案包不再动用。
- **余额**：按时间窗口限额的方案，最满的那个窗口还能用多少，和其他额度包一起算进余额，所以项目网关 key 的预算上限照样能算出来。
- **Reserve**（`unlimited`）：方案本身不限量、不发包、不扣包，用量照样记；项目和成员预算仍然适用。
- **模型档位**：网关模型的档位由管理员在模型管理页设（`cheese_tier`），订阅模型的档位写在 `_SUB_MODELS` 里。闸门（`domain/policy/gate.py`）对模型先看方案允许的档位，超出一律拒绝（「当前方案不能使用模型「…」。」），不变成提议；项目设置只能在方案范围内再收紧。机器的档位不受方案影响。模型选择（`GET /projects/{id}/default-model` 的 `choices`）给每个模型标出方案是否允许（`allowed`），不允许的标出排在最前、允许它的方案名（`requires_plan`，`usage/model_access.py`）；只算这个团队能挂的方案（个人团队不算只给团队的方案），没有就为空。方案还没有价格，顺序由管理员设的排序（`rank`）决定，只给管理员的方案排在最后。设为项目默认、分身默认或队友的模型时，方案不允许的一律拒绝。
- **需开通的模型**：Claude、GPT、Gemini 这类模型（网关模型标 `cheese_overseas: true`，订阅的 Claude 模型一律算）只有平台管理员开通过的团队能用（`overseas_model_approvals`，一个团队一行）；开通一个人就是开通他的个人团队。没开通的团队在模型选择里看不到它们，设为默认或队友模型按「目录里没有」拒绝；已经绑在这种模型上的项目，闸门在轮次开始前拒绝（「模型「…」需要平台管理员为这个团队开通后才能使用。」）。档位规则照旧叠在上面。管理员在额度后台的团队详情里开关（`PUT /admin/teams/{id}/overseas-access`），每次写落 `credit_admin_audit`（`team.overseas`）；网关模型在模型管理页勾「需开通」。

方案、团队挂哪个方案、给团队发额度都只能由平台管理员在 `/admin/plans`、`/admin/teams` 下操作，每一次写都记进 `credit_admin_audit`（谁、对什么、改前改后），`/admin/credits/audit` 和 `/admin/teams/{id}/history` 读它。管理员发的额度可以写一句原因，只有管理员看得到。

## 项目和成员预算 {#project-budgets}

`usage/budgets.py` 在同一本账上检查两种累计上限，不另扣一笔额度。`project_credit_budgets` 保存项目总预算，`member_credit_budgets` 保存项目内各人的任务上限；两者从项目创建时开始累计，不随方案窗口重置。设置上限不发额度，清空上限不清空用量。

`TaskService.credit_owner` 依次选取任务的人类负责人、人类创建者、项目所有者和团队所有者。`AgentTurnRepository.open` 为新执行在 `work_credit_owners` 记录该人员归属。同一执行重复打开保留原归属，转交后的新执行记录新归属。`Ledger.record` 按执行 ID 把归属写入 `resource_usage.credit_owner_handle`。

任务的网关 key 和用量检查点按任务及额度归属人分别保存，避免并行任务或频道费用混账。订阅调用通过准入获得当前执行 ID，计量代理将执行 ID 写入用量日志；任务准入不缓存执行 ID，因此并行席位、转交和长任务的收据保留各自归属。旧日志按时间匹配只能用于统计执行次数，不根据时间匹配结果扣个人上限。

已识别为任务的模型调用在准入服务不可用时返回可重试的 503，等待重新确认费用归属，不沿用上一次的人员网关 key。频道对话沿用原有公共开销的故障处理策略。

这些归属记录保留到项目删除，任务删除后仍可结算。删除会话将用量的会话引用置空，已支付的费用和人员归属保留。

频道对话、共享环境算力和平台维护调用不计入个人上限，仍计入项目总预算。没有执行归属的历史费用不倒推给任务当前负责人，接口单列为未归属费用。

`Ledger.admit` 检查项目总预算，任务启动和 `/llm/admission`、`/llm` 请求还检查执行归属人的上限。项目额度摘要与网关预算取团队可用余额和项目剩余预算中的较小值。上限按已结算用量判断，没有请求前预留；在途调用、准入缓存和延迟收取会使实际用量超出上限。

项目成员可读 `GET /projects/{id}/credit-budget`，项目所有者和管理员可用 `PUT` 修改。更新只应用请求包含的上限，成员上限为 `null` 时移除该限制；只能给项目中的人设置上限。

## 内测奖励与团队申请 {#rewards}

个人额度页可领取一次 500 点内测体验额度。反馈管理员可在反馈详情中采纳并发放 100 点奖励；直接提交的反馈奖励作者，由人将 AI 提案提交为反馈时，奖励发放给提交者。奖励进入个人团队的额度包，`credit_rewards.key` 在数据库中去重，与额度发放在同一事务内提交。重复领取或重复采纳不再发放。

团队额度页的 Team 方案和充值均为申请入口。提交申请不扣款、不发放额度；同团队同类型只保留一条待处理申请。平台管理员在额度后台核对付款或试用安排后，选择已经约定的实际方案，或按申请点数发放 `purchase` 额度包。处理时锁定申请记录，重复确认不重复发放；`credit_admin_audit` 记录处理人和结果。方案和报价由双方在开通前确认。

## 个人额度 {#personal}

不在项目里、由本人发起的 AI 调用（文档站和题目页的问芝士、发布页和改题页的芝士）扣本人名下个人团队的额度。

- 个人团队能用的就是它的方案给的（月度包或时间窗口）加上另购和发放的额度，和名下项目共用。
- 调用前先过准入（见[方案](#plans)），不放行就拒绝并写明何时恢复；调用后按实际花费扣，所以余额最多被最后一次调用透支一次。
- 按网关上这个模型的单价折算，和网关自己算花费的方式一致：缓存命中的输入 token 按缓存价、其余输入按输入价、输出按输出价，合计的美元再除以每额度的价格（0.01 美元）。不同模型扣得不同。模型没配缓存价时，缓存命中的 token 按输入价算。没有单价时无法计费，调用被拒绝。
- 题目页的芝士不自己算：每个人有一把自己的网关虚拟 key，芝士的每次模型调用都走它，而且只在这个人的一个问题正在回答时才放行。每次提问后读这把 key 上新增的花费（和项目 key 一样按天、按模型读累计差值，只消费一次），直接按网关算出的美元扣（[个人芝士](/dev/assistant#ask)）。
- 每次调用写一行 `resource_usage`：`project_id` 为空，`user_id` 是发起的人。平台看板的项目额度燃尽不算方案包。

## 平台替项目发起的调用 {#platform}

任务命名、旧记忆搬迁、环境准备失败时的「让芝士看看」和记忆整理（dream）都是平台为某个项目做的事，和项目里的其他调用一样记到项目上、扣项目所在团队的额度，团队的用量页把它们算进「协作」。每一行带 `project_id` 和团队，`kind` 写明是哪件事（`topic_naming`、`memory_migration`、`environment_diagnosis`、`memory_dream`）。

- 任务命名、旧记忆搬迁和「让芝士看看」各走平台的一把服务 key（各带一份平台设的预算），`cost_usd` 取网关在响应头里给的价格，由 `Ledger.record_project_call` 按项目的付款方写一行并扣额度。
- 记忆整理的每一份（team 一份，每个有 private 的人一份）都是后端在项目的整理 key（`project.settings["llm_gateway_dream_key"]`，同样由项目付费、同样带项目的预算）上直接发的一次调用。几份都跑完后当场按 `memory_dream` 结算这把 key 的新增花费（读不到时 20 秒后再读一次）；什么都没收到时写一行 `memory_dream:unmetered`，说明这一次跑过。房间的轮次只结算项目的第一把 key，所以拿不走整理的花费。整理的触发阈值按 `kind` 把整理自己的花费剔掉。

## 三处计量 {#metering}

| 路 | 谁记 | 怎么进账 |
|---|---|---|
| 网关路 | LiteLLM 逐次记在项目虚拟 key 上 | 主 API 读取 LiteLLM 按 key、按天、按模型记的累计值（`/user/daily/activity`），只消费差值，每笔只消费一次。一次收取每个模型写一行，行上的 `calls` 是这段时间里这个模型答了几次（`successful_requests` 的差值），所以看板上的调用次数是 `calls` 之和，不是行数 |
| 订阅路 | 计量代理每个 `/v1/messages` 响应写一行 `usage.jsonl` | 主 API 定时把新行收进 `resource_usage`，和检查点在同一个事务里推进，只收一次（`subscription_ingest.py`） |
| 成员自己的 Claude Code | 会话在每轮结束时自报（stream-json `result` 的 `usage`、`total_cost_usd`） | 一轮结束时写一行，`route` 是 `own`，额度记 0：用的是主人自己的登录或账号里保存的 key，项目不付钱（`chat._close_hook_work`） |

前两条路只在流量经过的地方计量：Claude Code 每轮自报的用量在这两条路上不算，算了就是同一轮扣两次。成员自己的 Claude Code 的请求两处都不经过，它的自报是唯一的记录，只记不扣。

## 折算成额度 {#credits}

两条路用同一把尺子（`backend/app/domain/usage/credits.py` 的 `spend_to_credits`）：**额度 = 这次调用的美元花费 ÷ 0.01**（`CREDIT_USD`）。1 额度就是 1 分钱，界面上叫「点」。

- **单价**：都写成美元，账本和每把 key 的预算都按美元算。用人民币结算我们账户的服务商（DeepSeek、智谱、月之暗面、小米），单价取它的中文价目表，按 7.1 元兑 1 美元折算，并在 `deploy/gateway/config.yaml` 那一行写明页面和读到的日期；它英文页上的美元价是另一种账户的价格，不是我们付的。
- **网关路**：花费是网关按模型单价算出来的。网页搜索也在这条路上：`cheese_web(action=search)` 在调用方自己的网关 key 上搜（DeepSeek 的搜索接口接在网关里，`deploy/gateway/deepseek_search.py`），每次搜到结果按 ¥5 / 1000 次 ÷ 7.1 = 0.000704 美元计，没搜到不计；它和这把 key 的模型调用一起收取，落成 `route = "search"`、`kind = "web_search"` 的行，不算模型调用。Claude Code 的 WebSearch 由模型的上游执行，每次搜索按同一个价钱算进那次模型调用。LiteLLM 的 `prompt_tokens` 已经含缓存读和缓存写，所以 `input_tokens` 和订阅路一样记全部输入，`cache_read_tokens`、`cache_write_tokens` 取它按天累计的 `cache_read_input_tokens`、`cache_creation_input_tokens` 的差值；缓存写不分有效期，`cache_write_1h_tokens` 记 0。
- **订阅路**：订阅按月付费，调用本身没有账单，所以按同一个模型在网关价目表里的单价估算。价目表在 `deploy/gateway/config.yaml`：订阅用到的 Claude 模型各有一条只记价格的条目（`model_info.blocked: true`，网关拒绝路由，也没有凭证），单价取 Anthropic 公开的 API 价格。计量代理的日志里 token 是分开记的：新输入、输出、缓存读、缓存写，缓存写再按有效期分成 5 分钟和 1 小时两部分；入库时 `input_tokens` 记全部输入（新输入、缓存读、缓存写之和），`cache_read_tokens`、`cache_write_tokens` 记其中的缓存部分，`cache_write_1h_tokens` 记缓存写里 1 小时的那部分。各部分按各自的单价计价：缓存读按缓存读价，不当新输入算；1 小时缓存写按 1 小时的价，比 5 分钟的贵。日志里的模型名带日期后缀（`claude-haiku-4-5-20251001`）时，按去掉后缀的名字查价。
- 计量代理开始分开记录缓存写的有效期之前写下的日志行没有这一拆分，这些行的缓存写全部按 1 小时的单价算：Claude Code 用的是 1 小时缓存，而且估算宁可多算不少算。
- 价目表里查不到的订阅模型：这一行用量照记，花费为 0、不扣额度，每一轮收取在日志里列出这些模型和行数。缺价是平台配置的问题，不该让团队因此被拒；补上价格即可。读不到价目表（网关配置了但连不上）时这一轮不收取，检查点不动，下一轮再收，不会把一段日志按 0 记掉。

## 云端算力 {#compute}

云端的算力也扣额度，和模型用量是同一本账（`usage/compute.py`）：同样的额度包、同样的付款方（`ledger.payer_for_project`，项目所在的团队，名下项目是本人的个人团队）、同样的拒绝。算力没有单独的额度上限；平台为保护 MicroCloud 集群设的主机数上限（`CLOUD_POOL_MAX_HOSTS`）是平台内部的，用户看不到。

- **云端沙箱**：按运行时长收费，从启动到空闲释放，每个沙箱每小时 `CLOUD_SANDBOX_CREDITS_PER_HOUR` 额度。每个沙箱的资源上限都一样，所以不按实际 CPU 和内存用量计。沙箱等主机开出来的时候不计。
- **云虚拟机**：按规格乘时长，从创建到释放，因为这段时间平台一直在为它付钱。规格按核数和内存的 GiB 数命名（`4c8g`，`usage.compute.vm_spec`），每小时的价格写在 `CLOUD_VM_CREDITS_PER_HOUR`（`{"4c8g": 每小时额度}`）。没列出的规格不能创建，会话得到「云虚拟机暂时无法启动：平台还没有设定这种规格的价格」。
- **用户自己的设备**：不收算力费，也不计量。

**价格没有默认值。**两项都没设时，云端沙箱一律不启动：工具调用得到「云端环境暂时无法启动：平台还没有设定云端算力的价格」，后端日志里有一条 error 写明要设哪一项。算力不会因为没人设价格而白跑。

计量按「运行段」记（`compute_runs` 表）：一个沙箱（或一台云虚拟机）从开始运行到停下是一段。哪些沙箱在运行由 `machine/metering.py` 每次巡检（`cloud compute metering`，间隔同 `MACHINE_ENROLL_INTERVAL_SECONDS`）对照沙箱的状态来定：沙箱在平台还持有的、已登记的主机上，没有在被释放，也没有在等准备，就算在运行；没有运行段的开一段，停了的收起，停的时刻取生命周期开始释放它的时间，沙箱已被删掉或开始等待的取发现的时刻。云虚拟机由同一次巡检记：创建时间起开一段，释放时收起，记在为它创建的项目上；创建前 `HostPool` 按它的规格过 `admit_start`。额度用完时云虚拟机不会被停下，空闲后照常推送并释放。

扣费按整分钟：运行中的每 10 分钟（`SETTLE_EVERY`）结算一次已满的整分钟，停下后把最后不足一分钟的部分向上取整再结算一次。每次结算写一行 `resource_usage`（`route` 是 `compute`，`kind` 是 `sandbox` 或 `vm`，`model` 是规格名，token 和 `cost_usd` 为 0）并扣额度，和模型调用一样走 `Ledger.record`，所以一个沙箱一天只写几十行。这些行不算模型调用：平台看板的调用次数、token、按模型和按通路的拆分，以及频道和项目的「N 次运行 · N token」都把它们排除在外；团队和个人用量页按额度读，把它们算成单独的一类「算力」。

**额度用完时**和模型用量一致：新的沙箱不启动（`HostPool.place` 在启动前调 `admit_start`，拒绝时工具调用得到账本那句拒绝理由）；已经在运行的沙箱不打断当前这一轮，房间里没有在跑的回合时就释放（`metering.unpaid_sandboxes`，每分钟查一次），对话里出现「额度已用完，环境已释放……」。额度补上后，下一条消息开一个新沙箱。

## 两道刹车 {#brakes}

```demo-sim
title: 两道刹车读同一份额度
note: 按每额度 0.04 美元折算，拖一拖看两道刹车各自什么时候拦
vars:
  - key: usd
    label: 已经花掉的钱
    unit: 美元
    min: 0
    max: 4
    step: 0.1
    value: 1.2
  - key: total
    label: 团队给的额度
    unit: 额度
    min: 10
    max: 100
    step: 10
    value: 50
derived:
  - key: spent
    expr: usd / 0.04
  - key: left
    expr: total - spent
rules:
  - label: 额度用完
    when: 'left <= 0'
    text: 准入拒绝，房间里出现平台提示；项目虚拟 key 的 max_budget 也已经在网关上把调用挡住了。
    tone: bad
  - label: 放行
    text: 准入放行，网关那边也还没到 max_budget。两道刹车读的是同一份额度，一个按额度数、一个按美元。
    tone: ok
out:
  - label: 已用，折算成额度
    expr: spent
    unit: 额度
  - label: 还剩（负数即超了）
    expr: left
    unit: 额度
```

1. **准入**：每个请求之前，主 API 比较已用额度和总额度，用完就拒绝。这一道在计量代理那边是软的：拿不到准入答案时放行，由订阅路自己的滚动 token 上限兜底。
2. **网关预算**：项目虚拟 key 的 `max_budget` 设为「这把 key 已记账的网关花费 + 项目还能花的额度 × 0.01」，每轮开始时按这个数改写，网关直接拒绝超额调用。方案不限量且未设项目总预算时不设，key 上原有的上限会被清掉。

两道刹车读的是同一份额度，一个按额度数、一个按美元。
