# 验收与采纳 {#accept}

芝士做完一条任务、递交成果后，频道里会出现一张「验收卡」。验收就是先看改了什么，再决定采纳还是退回；采纳之后，这些改动才算进了项目。

## 进入验收 {#open-acceptance}

验收横条在任务页输入框上方，写着「待你审阅」，右边是「退回」和「采纳」；也能从「待办」或「全部任务」的「待处理」里打开这件任务。

1. 在「待办」或「全部任务」的「待处理」里打开这件任务。输入框上方有一条「待你审阅」。
2. 点「待你审阅」这几个字。右侧面板切到「改动」页签：最上面是这次交付的标题、检查和合并的情况，以及芝士写的审阅重点；下面是每个改了的文件的差异，一个接一个排下来。左边的文件列表点哪个文件，就跳到哪一段。
3. 要看一个文件的全文或者改它，点那一段右边的「打开」，看完点左上角的返回。不在改动里的文件，点「打开其他文件」按名字找。<!-- 待确认：新版「改动」页的截图还没有补 -->

完成后：看过全部改动，就可以决定采纳还是退回。

只有卡上点名的那位审阅人能采纳或退回。不是你的时候，在「改动」页顶部的「⋯」里点「改由他人审阅」。

## 采纳交付 {#is-merge}

改动符合要求时，点输入框上方那一条上的「采纳并完成任务」或「采纳」。芝士递交时会说明这一版是不是任务的最后一步，按钮跟着变：

- 「采纳并完成任务」：这一版是最后一步。完成后：改动合入项目主线，任务显示「已采纳」。芝士随后更新任务文档，在任务里发一条总结，之后任务结束，在「全部任务」里点「已关闭」能看到它。
- 「采纳」：后面还有步骤。完成后：改动合入项目主线，任务继续进行，芝士从项目最新的代码接着做下一步，做完再递交一张新的验收卡。频道里的任务卡写着「已采纳 N 次」。

每次采纳的结果都会发回任务原来那条支线。任务结束后需要接着改，负责人可以在任务页的 ⋯ 里点「重新打开任务」，见[任务页](/tasks#task-page)。

合并后的两个小时里，平台会查看项目主线上这次合并的检查。某项检查在合并前通过、合并后未通过，任务会重新打开，由芝士修复，负责人会收到通知；合并前就未通过的检查不算这次改动的。仓库在 GitHub 上记录部署时，任务里会多一行「已部署到 dev」这样的记录；部署失败时写「部署到 dev 失败」，并通知负责人。

这颗按钮在几种情况下名字不同：

| 按钮 | 什么时候出现 |
|---|---|
| 采纳并完成任务 | 一般情况，这一版是任务的最后一步 |
| 采纳 | 一般情况，后面还有步骤 |
| 创建 PR | 项目连着 GitHub，这条任务还没开合并请求（PR）；点了先建 PR，再采纳 |
| 重新采纳 | 上一次采纳时和主线冲突，芝士解决冲突后重新递交 |
| 仍要采纳 | 平台检查没通过，但你确认可以放行；在「改动」页顶部的「⋯」里，只有项目设置里「人工放行的人」能点。任务要先创建 PR（项目连了 GitHub 仓库）才有这一项 |

检查还在跑、或者芝士还在修的时候，横条上只写现在在等什么，没有采纳按钮，等轮到你时才出现。

如果项目设置了「需要几个人批准」且大于 1，「改动」页顶部会显示「N/M 已批准」，点开它有一颗「批准」按钮。凑够人数后才会真正合入。

同一个频道里的多条任务，各有自己的分支和验收卡，要分别验收。一次交付里的多个文件是一起采纳的。

## 退回交付 {#reject-delivery}

改动不符合要求时，点横条上的「退回」。输入框的位置换成退回理由，写清楚哪里不对、期望是什么（选填，但写了芝士改得更准），再点「退回」。

完成后：芝士重新处理时，任务在「全部任务」的「进行中」里，显示「运行中」。没有人在改时，任务显示「已退回」，排在「待处理」里，负责人的「待办」里也会出现这一件。芝士再次递交后，会出现新的验收卡。

## 补充要求 {#leave-note}

任务的负责人在[任务页](/tasks#task-page)左边的对话里直接对芝士写补充要求，点「发送」。其他人在频道里说。这些话不是 PR 评论，不会出现在 GitHub 上。

## 查看交付规则 {#delivery-settings}

项目的合并规则在「项目设置 → 合并规则」。常用的几项：

- 「合并前必须通过的检查」：检查没过，采纳不会合并。
- 「合并前分支须与 main 同步」：分支落后时，平台先把它更新到最新，再合并。
- 「需要几个人批准」：大于 1 时，要凑够批准人数。
- 「人工放行的人」：检查没过时，谁可以点「仍要采纳」（任务已创建 PR 时才有）。

## 采纳按钮是灰的 {#accept-blocked}

「采纳」点不了（灰的）时，平台检查没过，这一版现在采纳不会合并。鼠标停在按钮上，提示写明「现在采纳不会合并：〈原因〉」，比如「必须通过的检查未通过：lint」；更早的卡上还可能写着「平台检查未通过」或「平台检查未能执行」。

- 横条上写着「芝士正在处理」时，这一版还得它改，等它重新提交后再看。为什么现在合不了，点「改动」页顶部的合并那一项就能看到。
- 确认可以放行、且任务已经创建 PR（项目连了 GitHub 仓库）时，项目设置里「人工放行的人」可以在「改动」页顶部的「⋯」里点「仍要采纳」并写明理由，见[采纳交付](#is-merge)。
