# 验收与采纳 {#accept}

芝士写好组会报名说明后，由一个人查看芝士改了哪些文件，再决定这份说明能不能加入项目。

芝士把做好的结果交给人查看，称为提交审阅；这次提交的内容称为一次交付。

查看交付的人是审阅人。审阅人满意时点采纳，交付的改动加入项目；不满意时点退回，芝士按意见修改后重新提交。

一步步的操作见[检查结果：采纳或退回](/working-with-cheese#review-result)。这一页说明每个按钮的意思和背后的规则。

## 审阅人 {#reviewer}

每件任务有一位审阅人，在[任务负责人](/tasks#roles)点「开始」时确定。项目设置的「默认审阅」填了人时，由这个人审阅。没有填时，负责人点「开始」后，任务页提示先在「审阅人」中选一位。

芝士提交审阅后，任务页输入框上方出现一条审阅栏。审阅人看到的是「待你审阅」，右侧有「退回」和采纳按钮。频道里的其他人看到的是「待 @林晓 审阅」这样的一行，没有按钮。

频道里的任何人都可以更换审阅人：在「改动」顶部的「⋯」里点「改由他人审阅」，选一位项目成员。新的审阅人要在这个频道里。这次交付被采纳、退回或[作废](#void)之后，不能再更换。

## 查看一次交付 {#open-acceptance}

平台检查是项目设置的自动检查，例如检查代码格式和类型；没有设置时不出现。合并指把交付的改动加入项目文件。

等你审阅的任务列在「待办」的「等你处理」里，也列在「全部任务」的「待处理」里。点一条打开任务页，再点审阅栏上的「待你审阅」，右侧切换到「改动」。

- 最上面是「这次交付」：标题、平台检查和合并的情况，以及芝士写的「审阅重点」。
- 下面依次列出每个文件改了哪些行。点文件列表里的文件名，跳到那个文件。
- 点一个文件右侧的「打开」，查看它的全文。
- 这次没有改动的文件，点「打开其他文件」按名字查找。

## 采纳 {#is-merge}

采纳是把这次交付的改动合并进项目。采纳之前，报名说明只存在于任务里，项目文件不变；采纳之后，报名说明才加入项目文件。

芝士提交时说明这次交付是不是任务的最后一部分，采纳按钮的名字随之不同：

- 「采纳并完成任务」：最后一部分。采纳后任务显示「已采纳」，芝士更新任务文档并写一条总结，任务随之关闭。
- 「采纳」：后面还有部分。采纳后任务继续进行，芝士在项目最新的文件上做下一部分，完成后再次提交审阅。频道里的任务卡写着「已采纳 N 次」。

```demo-panel
title: 分几次交付时的「采纳」
caption: 点「采纳」后，这一部分加入项目，任务继续进行。
parts:
  - kind: head
    room: 综合
    title: 组会报名说明
  - kind: bars
    lines: 2
  - kind: msg
    who: 芝士
    say: 报名说明的正文写好了。下一步补报名表链接。
  - kind: line
    text: 「组会报名说明」的这次交付已采纳，任务继续进行
    at: 1
  - kind: review
    text: 待你审阅
    actions: 退回 | 采纳
    pressing: 采纳
    press: 1
    until: 1
  - kind: composer
    placeholder: 给芝士发消息
    at: 1
```

另外三种情况下，采纳按钮的名字不同：

- 「创建 PR」：项目的代码放在 GitHub 上，这次交付还没有合并请求（PR，GitHub 上记录一次合并的条目）。点了先创建 PR，再采纳。
- 「重新采纳」：上次采纳时，这次交付和项目里别人已经采纳的改动改了同一处。芝士解决冲突后重新提交。
- 「仍要采纳」：平台检查没有通过，但确认可以放行，见[采纳按钮是灰的](#accept-blocked)。

### 谁能采纳 {#who-accepts}

只有审阅人能采纳和退回。点下采纳的那个人还要满足下面几条：

- 项目要求几个人批准时，批准的人数要达到要求。采纳的人自己算一位。
- AI 队友不能采纳，采纳必须由人操作。
- 从赛题创建的项目里，赛题可以规定某个频道的交付由外部成员采纳。这样的频道里，只有项目的外部成员能采纳。

### 采纳之后 {#after-accept}

采纳后两小时内，平台还会查看项目里这次合并之后的平台检查。合并前通过、合并后没有通过的检查，由芝士修复。任务已经关闭的，会重新打开，并通知负责人。

同一个频道里的几件任务，各自提交、各自采纳。一次交付里的几个文件一起采纳。

## 退回 {#reject-delivery}

退回是让芝士按意见修改这次交付。点审阅栏上的「退回」，输入框的位置换成退回栏；在「退回理由（可选）」中写明要改哪里，再点栏内的「退回」。

芝士修改时，任务在「全部任务」的「进行中」里，显示「运行中」。没有人在修改时，任务显示「已退回」，排在「待处理」里，也出现在负责人的「待办」中。芝士修改后重新提交，审阅栏再次出现。

## 对着具体几行写批注 {#comments}

批注是写在「改动」里某几行旁边的意见，退回时和退回理由一起交给芝士。任务的负责人、协作者和审阅人可以写批注。

- 写一条：鼠标移到一行上，点行号旁的「+」，在「写批注」中写意见，点「添加批注」。
- 选一段：点「+」后按住 `Shift` 再点另一行。
- 给出改法：打开「修改建议」，把选中的几行改成想要的样子。

写好的批注标着「未发送」，只有自己看得到。点「退回」时，退回栏写着「一起送出 N 条」。某一条想留到下次，点它旁边的「这次不送」。

芝士重新提交后，每条批注标着「已处理」或「未处理」，「改动」顶部写着「上一轮批注 N / M 已处理」。已删除的行不能写批注。

## Word、表格和幻灯片 {#office}

交付里的 Word 文档、Excel 表格和 PowerPoint 幻灯片，在「改动」里直接打开查看，不用下载。在 Word 和幻灯片里选中一段文字写批注；在表格里点一个单元格写批注。

点「对比上一版」查看改了什么，点「回到这一版」返回：

- Word 分「之前」「现在」两栏，按段落对齐。
- 表格列出有变化的单元格和原来的值。
- 幻灯片标出「已改」「新增」「已删除」的页。

第一次交付与任务开始时的版本比较，退回之后的交付与退回时的那一版比较。审阅期间，Word 里的修订只能查看，不能接受或拒绝。不想要的修订，写一条批注说明。

## 作废 {#void}

作废直接结束这次审阅：改动不合并，芝士也不会收到修改意见，之后可以重新提交审阅。作废时，在「改动」顶部的「⋯」里点「作废」，在「作废理由（可选）」中写一句原因，再点「作废」。

审阅人和[项目管理员](/rooms#rooms)可以作废。

## 合并规则 {#delivery-settings}

项目的合并规则在「项目设置 → 合并规则」，常用的几项：

- 「合并前必须通过的检查」：列出的平台检查没有通过时，采纳不会合并。
- 「需要几个人批准」：大于 1 时，「改动」顶部显示「N/M 已批准」。频道里的其他成员点开「N/M 已批准」，再点「批准」；批准的人数达到要求，才能采纳。
- 「人工放行的人」：平台检查没有通过时，可以点「仍要采纳」的人。留空时是项目所有者和负责人。
- 「默认审阅」：任务没有指定审阅人时，由这个人审阅。

## 采纳按钮是灰的 {#accept-blocked}

采纳按钮是灰的，点不了。鼠标停在按钮上，提示写着「现在采纳不会合并：〈原因〉」，例如「必须通过的检查未通过：lint」，lint 是一项代码格式检查的名字。

原因是这次交付还不满足项目的[合并规则](#delivery-settings)。审阅栏写着「芝士正在处理」时，芝士正在修复，等它重新提交即可。

确认可以放行时，「人工放行的人」在「改动」顶部的「⋯」里点「仍要采纳」，写明理由后合并。这一项只在交付已经创建 PR 时出现。操作人、时间和当时的检查状态都会记录下来。
