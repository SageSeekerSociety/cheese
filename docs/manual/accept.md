# 验收与采纳 {#accept}

芝士做完一条任务、递交成果后，频道里会出现一张「验收卡」。验收就是先看改了什么，再决定采纳还是退回；采纳之后，这些改动才算进了项目。

## 进入验收 {#open-acceptance}

验收卡在任务页输入框上方，写着「改动 待你审阅」；也能从「待办」或「全部任务」的「待处理」里打开这件任务。

1. 在「待办」或「全部任务」的「待处理」里打开这件任务。输入框上方有一条「改动 待你审阅」。<!-- 待确认：这一条展开后的完整验收卡（推荐理由、合并后的提交标题）在任务页里的位置，只核对了代码 -->
2. 点「审阅」。右侧面板切到「改动」页签，左边是改了哪些文件，每个文件带增删行数。
3. 选中一个文件，在它的「差异」和「编辑」两个视图之间切换（只读文件显示「全文」）。

![一条活的验收卡：显示待审阅人、推荐理由、合并后的提交标题，以及「审阅」「创建 PR」「退回」按钮](/images/task-card.jpg)

完成后：看过全部改动，就可以决定采纳还是退回。

只有卡上点名的那位审阅人能采纳或退回。不是你的时候，可以点卡上的「更换」，改由别人审阅。

## 采纳交付 {#is-merge}

改动符合要求时，点验收卡上的「采纳」。

完成后：改动合入项目主线，任务显示「已采纳」并结束，在「全部任务」里点「已关闭」能看到它。

这颗按钮在几种情况下名字不同：

| 按钮 | 什么时候出现 |
|---|---|
| 采纳 | 一般情况 |
| 创建 PR | 项目连着 GitHub，这条任务还没开合并请求（PR）；点了先建 PR，再采纳 |
| 重新采纳 | 上一次采纳时和主线冲突，芝士解决冲突后重新递交 |
| 仍要采纳 | 平台检查没通过，但你确认可以放行；只有项目设置里「人工放行的人」能点。任务要先创建 PR（项目连了 GitHub 仓库）才有这颗按钮 |

如果项目设置了「需要几个人批准」且大于 1，卡上会显示「N/M 已批准」和一颗「批准」按钮。凑够人数后才会真正合入。

同一个频道里的多条任务，各有自己的分支和验收卡，要分别验收。一条任务里的多个文件是一起交付、一起采纳的。

## 退回交付 {#reject-delivery}

改动不符合要求时，点「退回」，写清楚哪里不对、期望是什么（选填，但写了芝士改得更准）。

完成后：芝士重新处理时，任务在「全部任务」的「进行中」里，显示「运行中」。没有人在改时，任务显示「已退回」，排在「待处理」里，负责人的「待办」里也会出现这一件。芝士再次递交后，会出现新的验收卡。

## 补充要求 {#leave-note}

任务的负责人在[任务页](/tasks#task-page)左边的对话里直接对芝士写补充要求，点「发送」。其他人在频道里说。这些话不是 PR 评论，不会出现在 GitHub 上。

## 查看交付规则 {#delivery-settings}

项目的合并规则在「项目设置 → 合并规则」。常用的几项：

- 「合并前必须通过的检查」：检查没过，采纳不会合并。
- 「合并前分支须与 main 同步」：分支落后时，平台先把它更新到最新，再合并。
- 「需要几个人批准」：大于 1 时，要凑够批准人数。
- 「人工放行的人」：检查没过时，谁可以点「仍要采纳」（任务已创建 PR 时才有）。

## 采纳按钮是灰的 {#accept-blocked}

「采纳」点不了（灰的）时，平台检查没过，这一版现在采纳不会合并。鼠标停在按钮上，提示写明「现在采纳不会合并：〈原因〉」，比如「必须通过的检查未通过：lint」；更早的卡上还可能写着「平台检查未通过」或「平台检查未能执行」。

- 卡上标着「芝士正在处理」时，这一版还得它改，等它重新提交后再看。
- 确认可以放行、且任务已经创建 PR（项目连了 GitHub 仓库）时，项目设置里「人工放行的人」可以点「仍要采纳」并写明理由，见[采纳交付](#is-merge)。
