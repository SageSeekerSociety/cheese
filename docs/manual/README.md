# Cheese 用户说明书维护规范 {#manual-guide}

`docs/manual/` 中的用户页面用于帮助实际使用 Cheese 的人完成任务；本 README 面向文档维护者，规定信息架构、页面职责、写作方式、事实验证和构建发布要求。

用户页面与 `docs/` 下的开发、设计文档分开维护。用户网页、Agent 读取的 Markdown 和 `llms.txt` 使用同一份内容源，不另存一套给模型使用的答案或索引。

## 信息架构 {#information-architecture}

用户文档按「开始使用 / 教程 / 使用 Cheese / 常见问题」组织，分别解决入门、完整流程、功能查询和排障四类需求。

```text
首页 index.md
├── 搜索、第一次使用、功能入口、常见问题入口
│
├── 开始使用
│   ├── 快速开始 quickstart.md
│   └── 与芝士协作 working-with-cheese.md
├── 教程（按任务分组，一篇教一件事；分组和顺序以 docs/site/src/structure.mjs 为准）
│   ├── 组队协作：team-project / invite-to-project / join-a-team / split-work
│   ├── 做题目：solve-a-challenge / ask-about-a-challenge / team-challenge / resubmit
│   ├── 出题目：publish-a-challenge / guide-the-teammate
│   ├── 成果：review-changes / publish-a-site
│   └── 工作电脑：use-your-computer
├── 使用 Cheese
│   ├── 赛题 challenges.md
│   ├── 团队 teams.md
│   ├── 项目 projects.md
│   ├── 频道 rooms.md
│   ├── AI 队友 agents.md
│   ├── 任务与看板 tasks.md
│   ├── 文件与成果 files.md
│   ├── 提交 submissions.md
│   ├── 验收与采纳 accept.md
│   ├── 设备与工作电脑 devices.md
│   ├── 额度 quota.md
│   ├── 反馈中心 feedback.md
│   └── 发布成果 sites.md
└── 常见问题
    └── 常见问题与排障 troubleshooting.md
```

教程按任务组织，不按身份组织：一篇教程教一件具体的事，标题就是这件事。按身份介绍「谁拿知是做什么」的用例页放在官网，不在文档里。

快速开始用于建立 Cheese 的基本工作方式，并完成「创建项目 → 自动进入第一个频道 → 让芝士处理任务 → 找到成果」的最小闭环。教程带用户走完一条具体业务流程；「使用 Cheese」提供长期查询的功能说明；常见问题回答用户卡住时可以怎么处理。

## 页面职责与单一权威主页面 {#page-responsibilities}

每个功能只在一个权威主页面完整解释，其他页面只保留完成当前任务必需的步骤，并链接到该功能主页面。

功能发生变化时，先更新权威主页面，再检查引用它的快速开始、教程和排障摘要是否需要同步。不要在多个页面完整维护同一套配置、权限、限制或操作步骤。

### 开始使用 {#getting-started}

开始使用页面帮助第一次接触 Cheese 的用户尽快建立基本认识，不承担功能参考页的全部职责。

| 页面 | 负责什么 | 边界与相关页面 |
|---|---|---|
| `quickstart.md` | 创建项目、自动进入第一个频道、让芝士处理任务并找到成果的最小闭环 | 不绑定具体角色，不展开赛题流程或全部设置；深入内容链接项目、频道、AI 队友和教程 |
| `working-with-cheese.md` | 描述目标、提供上下文、补充要求、查看进度、调整方向、验收结果的方法 | 不做按钮大全，不重复队友配置和设备连接；链接 AI 队友、任务与看板、验收与采纳 |

### 教程 {#tutorials}

教程（Tutorial）是一条可以跟着完成的真实路径，一篇只教一件事，不是功能目录或概念合集。教程按任务所属的领域分组（组队协作、题目……），不按读者身份分组。

教程遵循以下规则：

- 开头用一个场景说明用户将完成什么，以及完成后会得到什么结果。
- 主流程使用一条经过验证的默认路径从头走到尾，尽量不要在正文中同时展开多种可选方案。
- 主体是要对芝士说什么、它会交回什么；界面路径压成一行，完整点击步骤留在功能页。
- 用户分不清自己是否走对的地方，说明此刻应该看到什么。具体写法见 `cheese-docs-writing` skill 的「教程」一节。
- 只解释完成当前流程必需的概念；更完整的设置、权限、限制和替代路径链接到对应功能主页面。
- 教程必须能够独立带用户完成当前任务，不能只给出一串功能页链接。

| 页面 | 负责什么 | 边界与相关页面 |
|---|---|---|
| `team-project.md` | 建团队、拉同学进来 → 在「综合」里转为任务 → 和芝士写任务文档 → 开始 → 中途改要求 → 验收 → 交出去 | 团队、项目、任务、验收的完整规则链接功能页 |
| `invite-to-project.md` | 不建团队，按用户名或邮箱把一个人邀请进项目 | 项目成员规则见 `projects.md` |
| `join-a-team.md` | 用链接申请、搜索申请或在「待办」接受邀请加入团队 | 团队规则见 `teams.md` |
| `split-work.md` | 同一频道里每人负责一个任务，用协作者、转交、「全部任务」和看板推进 | 任务规则见 `tasks.md` |
| `solve-a-challenge.md` | 加入空间 → 看题 → 领取 → 在题目建的项目里和芝士做 → 提交 | 详细规则链接空间与题目、提交 |
| `ask-about-a-challenge.md` | 在题目页用「问芝士」弄懂题目、要提示不要答案 | 额度见 `quota.md` |
| `team-challenge.md` | 以团队身份领取团队题目，一起做、一起交 | 详细规则链接空间与题目、团队、提交 |
| `resubmit.md` | 看评审结果，和芝士改完，提交新版本 | 提交规则见 `submissions.md` |
| `publish-a-challenge.md` | 建空间、发邀请码、发布题目、批准领取、评审提交 | 详细规则链接空间与题目、提交 |
| `guide-the-teammate.md` | 写整块板和单道题的「给 AI 队友的指导」 | 字段说明见 `challenges.md` |
| `review-changes.md` | 找到待审阅的改动，审阅、追问、采纳或退回 | 按钮的完整说明见 `accept.md` |
| `publish-a-site.md` | 让芝士做网页、预览、采纳、发布和更新网站 | 限制见 `sites.md` |
| `use-your-computer.md` | 可选：接入自己的电脑或服务器，给频道或任务换工作电脑 | 接入与隔离的完整说明见 `devices.md` |

### 使用 Cheese {#feature-pages}

功能主页面围绕用户实际操作组织内容，并明确与相邻功能的职责边界。

| 页面 | 完整解释的内容 | 不负责的内容与去向 |
|---|---|---|
| `challenges.md` | 赛题分类与全部赛题、详情、参与 / 领取、从赛题创建项目、材料呈现、参与状态与权限、发布与审核 | 项目设置见 `projects.md`；提交见 `submissions.md` |
| `teams.md` | 创建团队、邀请成员、加入申请、已发送邀请、团队成员管理、招募广场当前边界 | 项目成员归 `projects.md`；AI 队友归 `agents.md` |
| `projects.md` | 创建项目、与赛题的关系、所属团队、项目成员与邀请、主要入口、上游仓库、项目与成果的关系 | 文件操作归 `files.md`；队友配置归 `agents.md`；赛题提交归 `submissions.md` |
| `rooms.md` | 新建频道、默认 AI 队友、页面区域、频道成员、重命名与归档、消息与执行的关系、工作电脑入口、右侧文档 | 队友配置与触发规则归 `agents.md`；设备和环境规则归 `devices.md`；看板归 `tasks.md` |
| `agents.md` | 创建与配置 AI 队友、真实表单字段、设置默认队友、在频道成员中调整队友、触发处理消息、运行方式、模型、已验证限制 | 不承担完整入门流程、设备连接或进度管理；不承诺未验证的记忆机制 |
| `tasks.md` | 看板入口、当前列名与状态、任务名称、任务详情、与频道执行过程的关系 | 不重复项目介绍、队友配置或最终提交 |
| `files.md` | 上传及限制、文件进入时间线、查找生成文件、查看与编辑成果、单文件下载、成果相关的「改动 / 现场 / 预览」入口 | Site 发布归 `sites.md`；赛题提交归 `submissions.md`；不编造整个项目打包下载 |
| `submissions.md` | 学生提交条件、入口、表单与文件要求、已验证的提交限制；发布者查看提交与提交记录 | 与 Agent 交付的验收与采纳分开；不把单一赛题的限制推断成所有赛题通用规则 |
| `accept.md` | Agent 交付后的验收、采纳、实际入口与操作结果 | 不负责赛题提交或普通文件下载；未验证的验收与合并关系不能写成正式规则 |
| `devices.md` | 设置 → 设备、添加与安装、登录、网页批准、在线 / 离线状态、AI 队友的工作电脑及更换 | 不解释 tokens；不能把选择设备写成选择本地目录 |
| `quota.md` | 团队「额度」页、个人「芝士额度」、耗尽提示和当前可操作范围 | 设备连接归 `devices.md`；不编造自行调整或发放额度入口 |
| `sites.md` | 导出与发布中的 Site 发布、发布结果与管理入口、当前能力和限制 | 普通文件下载归 `files.md`；不承诺整个项目导出 |

上表定义的是页面职责，不代表其中每一个字段、状态、权限和限制都已经完成事实验证。正文只能写入经过验证的行为。

### 常见问题与排障 {#troubleshooting-scope}

一个问题的处理办法只写在负责它的功能页里，`troubleshooting.md` 只做索引：每节是一种现象，一句话说明它是什么，再链到功能页里写处理办法的那一节。

功能页里的排障小节按「现象 → 意思 → 处理」组织，标题用提示原文或现象，锚点稳定，例如 `devices#device-offline`、`quota#quota-exhausted`、`files#upload-failed`。`troubleshooting.md` 的各节沿用同名锚点，首页的常见问题从这些小节的第一段读取答案。

恢复操作必须实测。产品 Bug 单独跟踪，不把临时绕过方案长期写成正常流程；确需临时说明时，应写明适用范围和移除条件。

## 事实验证原则 {#fact-verification}

用户文档只描述目标用户当前能够实际完成的操作，事实依据优先级为「当前真实界面实测 > 当前截图或录屏 > 当前代码实现 > 旧文档 > 推测」。

代码可以帮助核对实现，但不能单独证明当前用户已经有入口、权限或可用流程。只存在于后端、仍在开发、尚未开放或根据经验推测的能力，都不能写成正式步骤。

验证一个行为时，建议记录验证时间、环境或版本、角色与权限、真实入口、按钮或标签原文、操作结果、限制和必要截图。产品版本变化、证据不足或结论冲突时，重新核验对应项。

事实状态可以使用「已验证 / 不存在 / 功能不完整 / 无法确认」标记。待验证内容保留在维护记录或变更说明中，不把猜测混入正式用户步骤；无法确认的行为先不写，或只写已有证据支持的范围。

教程完成后，应使用目标角色从头走通一次完整流程。提交次数、文件大小、权限等限制必须注明适用场景，不能把某个赛题、入口或角色下的行为扩展成全平台通用规则。

## 语言风格与正文结构 {#writing-style}

正文使用简洁、明确、正式、自然的语言，优先告诉用户从哪里进入、做什么、完成后看到什么。

- 保留「芝士」「AI 队友」等产品名称，少用“它才会动”“插进来”“攒下记忆”等拟人化表述；不使用宣传口吻、空泛过渡或无助于操作的设计动机。
- 一句话表达一个重点，条件、限制和例外分开说明。已确认不支持的操作直接写明，不能用“建议谨慎选择”代替实际限制。
- 页面、按钮和标签使用当前界面原文，例如「项目设置 → AI 队友 → 编辑」和「让它现在就动」，不要自行改成界面上不存在的名称。
- 概念解释只保留帮助用户正确操作的部分，不展开数据库、沙箱内部结构、后台调度或内部工作区路径。
- 正式产品流程要求用户执行的命令可以写，例如设备安装和 `cheesehost auth login`；须按当前界面核验命令、前提和结果，不沿用过时命令或加入开发运维操作。

例如，不要沿用“没有 @ 的消息它收不到”这类已经与当前行为不一致的说法。应只描述经过验证的行为，并把完整触发规则集中维护在 `agents.md`。

操作型功能页通常包含：一句话目标、开始前的条件、操作步骤、完成后的结果、限制和相关排障入口。`working-with-cheese.md` 可以按协作方法组织，常见问题按问题组织，不必机械套用同一模板。

## 内容源、frontmatter 与导航 {#source-and-navigation}

`docs/manual/*.md` 是用户文档的唯一内容源，新增页面通过 frontmatter 提供标题、标识和导航信息。

```yaml
---
title: 快速开始
slug: quickstart
group: 开始使用
order: 1
---
```

`title` 用于导航和索引显示，`group` 决定分组，`order` 决定组内顺序。页面文件名与 `slug` 保持一致；如果当前配置仍按文件名生成侧边栏链接，不能假定单改 frontmatter 的 `slug` 就能更换 URL。

目标分组顺序为「开始使用 / 教程 / 使用 Cheese / 常见问题」。新增或重排分组时，需要同步调整 `.vitepress/config.mts` 中的分组配置，并检查未知组是否由拼写错误导致。

`llms.txt` 必须使用与网站相同的分组和顺序；导航发生变化时同步核对 `scripts/emit_llms.py`。`index.md` 是首页，`README.md` 是维护规范，两者不进入侧边栏和 `llms.txt`。

## 稳定 slug、摘要与链接 {#stable-links}

用户文档每个标题都显式声明稳定 slug，每节第一句话应能独立概括本节内容。

```markdown
## 连接已有仓库 {#connect-repo}
```

标题 slug 使用小写字母、数字和连字符，全页唯一。修改标题文字时保留原 slug，避免中文标题自动生成的锚点随措辞变化失效。

页面改名、拆分或删除时，先检查产品入口、其他文档、Agent 引用和外部链接是否仍指向旧地址。只有已被实际引用的旧地址需要保留兼容入口或配置重定向；未正式发布且没有任何引用的页面，可以在更新内部链接后直接迁移。

`llms.txt` 按标题、Markdown 地址和节首摘要帮助模型定位答案。每节先写有信息量的摘要句，不以列表或“首先我们来看一下”开头。核心步骤应能独立看懂，链接提供进一步说明，不能代替答案本身。

源码中的站内链接使用 `/projects#projects` 这类不带 `/docs` 前缀的形式。VitePress 根据 `base: '/docs/'` 补全前缀；重复写入可能产生 `/docs/docs/...`。链接只指向已存在的页面与锚点，尚未创建的页面不要提前挂到用户可见入口。

构建时，提供给模型单独读取的 `.md` 应把站内链接和图片地址转换为完整地址；每份 `.md` 开头应指向 `llms.txt`，方便继续查找完整目录。

## 图片 {#images}

截图用于帮助用户定位入口或理解复杂界面，图片放在 `docs/manual/public/images/`，正文使用 `/images/xxx.png` 引用，不带 `/docs` 前缀。

截图必须来自当前真实版本，页面、按钮和操作路径与正文一致；不需要每一步都配图。alt 文字须独立说明图中主要信息，例如“新建团队表单中的名称输入框和创建按钮”，不要只写“截图”。

Agent 仅读取 Markdown 时依靠 alt 获取图片说明，因此核心步骤也必须用文字表达，不能依赖截图才能理解。

守卫应检查图片文件存在；发布前还要在预览中确认图片实际显示。

## 构建、检查与发布维护 {#build-and-release}

文档使用 VitePress 构建网页，再由 `scripts/emit_llms.py` 生成 `llms.txt` 和逐页 Markdown，生成结果不作为另一份源文件手工维护。

在完整仓库根目录执行：

```bash
task docs:dev      # 本地预览，修改后自动刷新
task docs:build    # VitePress + scripts/emit_llms.py
python3 .claude/scripts/check-manual-anchors.py
```

构建产物包含 HTML、每页对应的 `.md` 和文档站根目录的 `llms.txt`。例如 `/docs/quickstart` 对应网页，`/docs/quickstart.md` 对应 Markdown，`/docs/llms.txt` 提供索引。导航、搜索、暗色和移动端展示由 VitePress 处理。

维护时应确保 `check-manual-anchors.py` 继续检查显式合法 slug、重复锚点、节首摘要、站内锚点引用和图片文件。不能以本地预览正常代替守卫检查。

独立复制出的 `manual` 文件夹不包含仓库级 `scripts/emit_llms.py`、`.claude` 守卫、前端和 CI 配置，不能据此声称完整构建或发布检查已通过。相关验证应在完整仓库中完成。

### 前端发布集成要求 {#release-integration}

如果仓库继续采用当前集成方式，文档发布应满足以下要求；配置发生变化时同步更新本节。

1. **输出目录。** 文档输出到 `frontend/public/docs/`，随前端构建进入镜像；`.vitepress/config.mts`、`package.json`、`Taskfile.yml` 和索引生成脚本应解析到同一目录。
2. **clean URL。** 保留 `cleanUrls`；`frontend/nginx.conf` 的 `/docs/` 路由需要支持 `$uri.html`，使 `/docs/quickstart` 等地址可以直接访问和刷新，避免进入应用 SPA 兜底页。
3. **Markdown MIME。** nginx 对 `.md` 返回 `text/markdown`，避免被当作二进制下载；正确 MIME 不代表所有 Agent 客户端会采用相同读取策略。
4. **构建顺序与版本。** 前端流程应在 Docker 构建前生成文档；Node、Corepack、pnpm 版本和锁文件规则与仓库配置保持一致。
5. **产物断言。** 静态资源检查应确认 `docs/index.html` 与 `docs/llms.txt` 存在；缺少关键文档产物时应让构建失败。
6. **PWA 与 lint。** 文档目录应避免被应用的 PWA 预缓存、导航兜底或 lint 流程错误接管；生成文件按仓库约定处理。

正式上线或发布更新前，应验证 `/docs/`、各页 clean URL 的直接访问和刷新、章节锚点、Markdown 内容与 MIME、`llms.txt`、搜索、图片、移动端展示和产品内帮助链接。

如后续接入站内问答或 Agent 文档检索，应继续使用同一份官方文档内容源，并分别验证可访问的构建产物、回答效果、来源链接和当前配置，不能维护第二套模型专用答案。

## 提交前检查 {#pre-submit-checklist}

提交文档变更前，按变更范围完成以下检查，并在变更说明中如实记录尚未完成或无法执行的验证。

- [ ] 页面符合所属内容类型和职责；教程按任务组织，一篇一件事，共用功能主页面。
- [ ] 教程有明确目标和预期成果，使用一条可跟随的默认路径，并在关键步骤说明完成后应看到什么。
- [ ] 相关步骤已由目标角色在当前真实界面走通；页面、按钮、字段和操作结果与实际一致。
- [ ] 没有把旧文档、代码结构、计划功能或推测当作已上线能力；未确认项没有写成承诺。
- [ ] 当前限制及其适用范围明确，赛题提交与 Agent 验收采纳没有混淆，Bug 绕过方案没有成为常规流程。
- [ ] 语言简洁、正式、自然；说明了前提、步骤与结果，内部实现只保留用户操作必需的内容。
- [ ] 同一功能没有多处完整维护；引用主页面的简述与其一致，教程仍能独立完成当前流程。
- [ ] frontmatter、文件名、页面 slug、分组和顺序一致；新增页面、首页入口、导航和索引同步。
- [ ] 标题 slug 合法、唯一且稳定，每节有独立摘要句；页面迁移时只为实际仍被引用的旧地址保留兼容。
- [ ] 站内链接与锚点有效，无重复 `/docs` 前缀，无指向未创建页面的用户可见入口。
- [ ] 图片存在、来自当前版本、与文字一致且 alt 有效；核心步骤不依赖截图才能理解。
- [ ] 在完整仓库运行 `task docs:build` 和锚点守卫并通过；预览核对导航、搜索、链接和截图，核对 `.md` 与 `llms.txt` 产物。
- [ ] 发布状态与实际部署和验收一致，不在文档中提前声明尚未完成的上线能力。
