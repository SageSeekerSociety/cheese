# 一轮活跑在哪台机器上

芝士干活需要一台机器。这份文档说清楚今天到底有几种机器、一轮活怎么被分配到其中一台、以及**「能选的」和「实际跑的」不是同一件事**。

面向零前置知识的读者。

---

## 一、三条执行路，全部接着

代码里装配了三个，都是活的（`agent/compute.py` 的 `build_compute_pool`）：

| 路 | 机器是什么 | 谁的 |
|---|---|---|
| **平台自己的盒子** | 平台所在主机上起的一个 docker 容器 | 我们的 |
| **自托管设备** | 用户自己接进来的机器（笔记本、常驻服务器） | 别人的 |
| **Cloud** | 按话题现开的一台云主机，用完释放 | 我们开的，一次性 |

Cloud 只在配了云平台的地址和密钥时才可用；另外两条总是装上。

## 二、但菜单里只有两个

项目设置里能选的算力（`agent/market.py` 的 `compute_listings`）只列**自托管设备**和 **Cloud**。平台自己的盒子**不在菜单里**，这是刻意的——那段代码的注释说明了理由：人要选的是「谁的机器来跑」，而「我们的」是他不选时的结果。

## 三、落差在这里：菜单不是执行层

**执行层从不读菜单。**

一轮活落在哪，由 `build_compute_pool` 的这一行决定：

```python
default_name = DeviceChannel.name if settings.agent_backend == "device" else TmuxChannel.name
```

而 `agent_backend` 的默认值是 `"tmux"`（`core/config.py`，`.env.example` 里也写着 `AGENT_BACKEND=tmux`）。

**所以：没有显式配 `AGENT_BACKEND=device` 的部署，凡是没有钉住某台设备的话题，全部跑在平台自己的盒子上——那个你在界面上根本选不到的东西。**

一句话记住：**能不能选，和实际跑在哪，是两个独立的答案。**

## 四、这个落差今天的后果

平台自己的盒子有一个性质，另外两条路都没有：**它会被平台自己整个杀掉。**

三件事会让它被 `docker rm -f`（无宽限期，`TmuxChannel._ensure_container`）：

1. 沙箱镜像变了
2. 路由相关的环境变量漂了
3. CLI 挂载失效了

第一条最要紧：**镜像跟着部署走，所以每次部署都可能触发。** 而一个盒子现在服务一整个房间，所以它一死，那个房间里每个话题都跟着死——里面正在跑的轮次当场没，连同这一轮起的所有后台进程（开着的开发服务器、正在跑的测试）。

自托管设备和 Cloud 不受影响：那些机器不随平台部署重建。

**所以「部署会不会打断正在干的活」，取决于那台部署的机器上 `AGENT_BACKEND` 设成了什么。** 这在代码里看不出来，要上机器查环境变量。

## 五、可见性：两档里只有一档能跑

选定机器之后还有第二个问题：这一轮能看见那台机器上的多少东西。

| 档 | 意思 | 状态 |
|---|---|---|
| `host` | 看得见整台机器，能操作上面的服务、进得去其他房间的容器 | **唯一能跑的** |
| `isolated` | 只看得见自己那棵工作树 | **没有传输层，等于不存在** |

`has_runnable_transport` 只对 `host` 返回真，而默认档是从「哪档真能跑」推导出来的（`device/supply.py` 的 `default_visibility`），所以今天**每个话题实际都是整机可见**。

这一档不是遗漏，是明确推迟的决定（2026-08-18）：接进来的机器目前全是队友的，威胁模型是误操作不是攻击，而一个做错的沙箱比没有沙箱更糟。**重新考虑的触发条件是：第一台不属于队友的机器接进来。**

## 六、已定但还没做完的

**平台自己的盒子要真删掉。** 它已经从菜单撤了，但代码路径还在、而且是默认——这正是 CLAUDE.md 说的「删除必须落到决定行为的那一层」的反例。删掉之后，上面第四节整节消失。

**芝士自己提交、推送、开 PR。** 平台不再替它写工作树。详见 `docs/plans/2026-08-27-retire-jj-design.md`。
