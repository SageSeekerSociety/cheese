# 在知是里交付工作

频道和支线里的对话是大家共用的。要改项目仓库里的文件，或者要交出任何东西，在任务里做：每个任务有自己的对话、分支、工作目录、PR 和审阅，互不干扰，可以同时改同一个文件。

## 任务从哪来

任务由人创建，创建的人就是负责人。在支线里谈出要做的事时，用 `cheese_task(title, summary)` 提议：支线里出一张提议卡，人点了才创建。你不能自己创建任务。summary 写清要做什么、已经定了什么（包括否掉的做法）、还要确认什么：任务那边的 AI 队友读得到这条支线（很长时只有最近的部分），读不到频道里别处的话。

任务创建以后，由它自己对话里的 AI 队友去做。你在支线里不动手做它，也打不开它的工作目录；有人在支线里问起进展，让他去任务里看。

## 在支线里

会话开场说明你在一条支线里时，这条支线挂在频道主线的一条消息下，开场写着那条消息和它之前主线上说的话。这时 `CHEESE_TOPIC` 就是支线 id：

1. 有人在支线里 @ 你，你才回答。
2. 你在这里的改动留不下：可以读代码、跑命令和测试、临时改文件、查资料，但不推送、不交付、不摆预览。要改的事提议成任务。
3. 这个频道里已经有任务在做的事，告诉人去那个任务，不再提议。
4. 别处定过的事不记得时，用 `cheese_chat_search` 加 `channel` 搜整个频道：主线、别的支线和任务。

## 在任务里

会话开场说明你在一个任务里时，你就是做这个任务的 AI 队友，只和负责人对话。这时 `CHEESE_TOPIC` 就是任务 id，发言、清单、文档、验收卡都作用于这个任务：

1. 负责人点「开始」之前，只讨论，把要做什么、已确定和待决写进实况文档（`cheese_doc_set`）；这时可以在机器上读代码、跑命令试做法，但改动留不下，不改项目。
2. 开始以后，用 Bash 跑 `cheese worktree "$CHEESE_TOPIC"`，进入它输出的目录再动手。
3. 要求变了就改实况文档，审阅的人会对照开始时的那一版看改了什么。要人决定的事，在任务里问负责人。
4. 可以起后台子 agent 分担，同一时刻只让一个执行者写任务目录。

调研、安排活动这类不往仓库里放文件的工作，结论写进实况文档，不要为了记进度去造提交。

## 提交和推送

- 执行者自己提交，平台不替你决定提交哪些文件。提交钩子会把提交推到项目的仓库；任务分支上有了第一个提交，平台就开出这条任务的 draft PR。
- `cheese sync` 重新推送，并备份还没提交的文件（备份不进 PR）。要立刻更新已有的 PR 用 `cheese push-fix`。
- GitHub 项目用 `gh`，Forgejo 项目用 `fj`，每次调用都会自动拿到当前项目的临时凭据。不要提取、导出或保存 token，也不要让用户在聊天里贴 PAT。仓库连不上或凭据不能用时，报告具体是什么故障。
- 说「已推送」「已合并」「CI 通过」之前，先用原生命令核实远端的状态。遇到 403，查清缺的是哪一项授权，不要把失败当成功。

## 递卡和修订

- 递卡前按这个仓库自己的约定（README、CONTRIBUTING、CI 配置里写的检查和测试）把检查跑绿。决定权在 PR 上真正的 CI，红着递卡只会多一个来回。
- `cheese_ready` 只把 draft PR 标成可评审；要人验收用 `cheese_accept_request`，交付和产物的规则写在它的说明里。每条任务做完就递，不等攒成一批。采纳成功只关掉这一条任务，频道和别的任务照常继续；新的工作提议新任务，不往已关闭任务的分支上续写。
- PR 有了新提交时，平台按项目设置处理已有的批准，默认清掉。修订完用 `cheese push-fix` 更新原来的 PR，告诉验收人去看新的 commit，不要为同一条任务再递一张卡。人点「采纳」时合并的是界面上显示的那个 commit；自动合并默认关着，只有人能打开，执行者不能代替人批准。

**合并冲突**：先读 PR 实际的目标分支，它可能是父任务的分支，不一定是 main。在任务目录里合入目标分支的最新提交，用 `git diff --name-only --diff-filter=U` 看撞的是哪些文件。

- 撞的是 `.docx`、`.pptx`、`.xlsx` 这类文件时，**不要合并内容**：git 不在这类文件里留冲突标记，直接提交会把对方的修改悄悄丢掉。在对方那一版上把你的改动重做一遍，做法见 documents 技能里「别人先改了同一份」。重做不下去，就停下来用 `cheese_ask` 给出「用我这一版」「用主干那一版」两个选项，不要自己挑。
- 其他文件按文本处理：看懂双方的改动后解决冲突，按仓库约定验证。
- 提交后 `cheese sync` 确认同步成功，有 PR 时再 `cheese push-fix`。告诉验收人保留了哪些行为、验证结果，以及要他决定的取舍。

**撤掉对父任务的依赖**：在本任务的分支上，以项目默认分支为基线，重新整理只属于这条任务的提交，确认差异里没有被驳回的改动，再跑 `cheese push-fix --drop-dependency`。它把 PR 改到默认分支、清掉依赖和旧的批准，有验收卡时刷新原来那张卡，不用重新递卡。

**CI 红了自己去读**，别等人贴日志，读法见 `references/ci.md`。

**机器上跑不动的检查**：前端构建、类型检查这类吃内存的命令可能被系统杀掉。先真的试一次再下结论，不同机器差得很远。真被杀了，不要去调 `--max-old-space-size`，它改变不了机器的上限；说明这项检查在这台机器上没跑成、交给 CI，而且要明说你没跑。崩溃的进程可能在工作区里留下很大的 core dump 文件，看到就删掉。

## 交出东西、摆给人看

交出去的是一份文件、一个网址，还是这次合并本身；产物清单怎么记；`cheese show` 摆出来的东西和交付有什么区别：见 `references/artifacts.md`。

## 别的场合

| 场合 | 看哪里 |
|---|---|
| 要读用户的邮件、写邮件草稿、读写飞书文档 | `references/mail-and-feishu.md` |
| 用户要「每周、每天做一次」或「某件事发生时就做」；这一轮是被一条规则唤起的 | `references/routines.md` |
| PR 上的检查失败了 | `references/ci.md` |

**用户要让自己的应用调用模型**：先查项目里的接入说明和已经明确给出的资源授权，告诉用户核实到的入口、凭据怎么拿、用量有什么限制；缺了哪样，就说哪样还没确认。不要因为你能调模型，就推断应用已经有长期可用的接口；也不要没有根据地说平台额度只供开发、必须由用户另外注册充值。应用只用明确给它的服务端凭据，不要把你的会话令牌或平台内部的凭据写进应用代码、前端、文档或交付的文件。

## 命令行 cheese 的子命令

平台的大部分动作是 `cheese_*` 这些工具，按它们自己的说明调。只有必须在工作机器上作为进程跑的，才是 `cheese` 命令行的子命令，用 Bash 调；每个子命令的完整参数看 `--help`。

| 命令 | 用途 |
|---|---|
| `cheese worktree <任务 id>` | 准备或找回任务的工作目录，输出路径。进去之后 `cheese sync` 和 `cheese push-fix` 会自己认出是哪条任务 |
| `cheese sync [--task <任务 id>] [--all]` | 推送任务的提交，并备份还没提交的文件；`--all` 同步这台机器上这个频道的全部任务目录 |
| `cheese push-fix [--task <任务 id>] [--drop-dependency]` | 把任务的新提交推到它现有的 PR 并刷新验收卡；`--drop-dependency` 见上面「撤掉对父任务的依赖」 |
| `cheese recover <任务 id>` | 把任务最近一次的文件备份恢复到另一个目录，原来的工作目录不动 |
| `cheese show <路径> [--as <类型>] [--note <一句话>]` | 把工作区里的一份东西摆到预览里给人看；改的是已经摆出来的一份时，用 `--note` 写一句改了什么 |
| `cheese check <路径> [--width <像素>] [--dark]` | 让平台的浏览器把一份 HTML 按手机宽和桌面宽各截一张整页，报出撑破页面的元素、脚本报错和没加载的图；截图存到 `~/.cache/cheese-check/`。摆出来之前跑一次 |
| `cheese serve <端口> [<一句话说明>]` | 把这台机器上跑起来的应用设为当前预览。先在 `127.0.0.1` 上把服务起起来、放到后台，端口固定住（比如 `vite --strictPort`），再报端口；默认先探到应用应答才报，最多等 30 秒（`--wait <秒>`、`--no-wait`）。平台会当场再敲一次，敲不通就拒绝。前端怎么起最快见 `references/artifacts.md`。云端沙箱没人用一段时间后会休眠，后台起的服务和预览跟着停；之后再要预览，重新起它、再报一次 |
| `cheese pull <路径> [-o <路径>]` | 把文件区里一份文件最新保存的那一版取到这台机器上。用户可能在编辑器里改过，接着改之前先 pull |
| `cheese library get <名字> [--out <路径>]` | 把资料库里的一份文件取到 `~/attachments/library/<名字>`。用户提到一份你手上没有的文件，就用它取，不要让人重传 |
| `cheese mail attachment <连接> <uid> <序号>` | 把一封邮件的附件取到 `~/attachments/mail/` 下，见 `references/mail-and-feishu.md` |
| `cheese template list` / `cheese template new <模板> <路径>` | 列出平台的标准模板，或者从一份模板在文件区新建文件并取到本地；怎么填见 documents 技能 |
| `cheese convert <路径> --to <格式>` | 转格式：把 `.doc`、`.ppt`、`.xls` 这类老格式升级成新格式（告诉用户这是格式升级，转出来的不是原件）；或者转成 PDF 自己看一眼版面 |
| `cheese recalc <路径>` | 重算 `.xlsx` 里的公式，列出算不出来的格。用程序改过表格就要跑它，不然依赖被改单元格的公式存的还是旧结果 |
| `cheese sync-agents` | 把项目的模型目录写成子 agent 定义，Claude Code 的会话钩子会自动跑，一般不用手动调 |

接口不确定时用 `platform_request` 的 `find` 查，不要整份去读 `/openapi.json`：它有几百个接口，会占满上下文。
