# 交出东西、摆给人看

## 这一版交出去的是什么

递卡（`cheese_accept_request`）时说清楚，三种选一种：

- **这次合并本身**：`deliver` 和 `deliver_url` 都不给。代码仓库这类项目交的就是主干往前走一步，没有可下载的东西。这种交付**不声明产物**：交出去的是这个项目的仓库，一个项目只有一个，平台认得出是清单上哪一项。传了 `artifact`、`new_artifact` 或 `about` 都会被打回。所以一个代码项目的产物清单上通常只有一项，不管同时推着多少条分支。
- **一份文件**：`deliver=<任务工作目录里的相对路径>`，比如论文的 PDF、幻灯片、改过的那份 .docx。平台在递卡这一刻把它读下来留一份快照，以后永远拿得到当时交出去的那一份。单份不超过 80MB。交文件也要任务分支上有改动了文件的提交，否则会被打回（「没有可交付的改动」）：把文件的源放进仓库，成品留在工作目录里交。快照只在递卡这一下留，构建产物过了这一轮就没了，所以先构建出来再递卡。
- **一个地址**：`deliver_url=<网址>`，比如网站、看板，要以 `http://` 或 `https://` 开头。平台只记这个指针。

交文件或地址时，再说清动的是产物清单上哪一项：

- `artifact=<id>`：清单上那一项的新一版。给 id，不给名字。每一项的 id 印在系统提示词里清单那一行的末尾，照抄。
- `new_artifact="项目官网"` 加 `about="对外的产品介绍站"`：做出了一样清单上还没有的东西。名字用用户自己的说法（《结题报告》《项目官网》），不是文件路径。返回里带着这一项新的 id，以后交它用这个 id。这是少见的动作，对话里会当场公告；名字已经在清单上时会被打回。

只认 id，是因为名字写错不会报错：「报告」和「结题报告」都是合法名字，按名字认的话，手滑一次清单上就多出一项看着像重复的东西。

## 哪些算一项

会交给项目外的人、跨任务跨轮次仍是同一样东西、而且它有源。《结题报告》算一项，某一轮顺手生成的 `tmp/预览.pdf` 不算；网站算一项（交出去的是网址），报告里的一张插图不算（交出去的是报告）。几个文件凑成一样交付物时，它们是一项，一版就是一次交付。

三条缺一条，它就不是一项，也就不该递卡交它：不要为了交它新建一项产物。摆出来给人拿走，任务用 `cheese_close_task` 写明结论结束。

**`about` 那一句**：说这样东西本身是什么、给谁的。下一次交付靠它判断「我做出来的是不是它的新一版」。三条检验，起名字也用第一条：

1. 这句话在第 1 版和第 20 版都成立。一交新版就得改的，就是写错了。
2. 换到清单上另一项头上也说得通，就是白写，重写。
3. 不要把这一版的改动标题抄进来。这一版做了什么在 `subject` 上，抄过来会被打回。

**成品从源构建出来。** 源进仓库，成品不进，任何时候都能重建。一版是一次交付，不是一次保存：「第七版」指的是那次交付的那个提交。是不是产物，由声明决定，不由它放在哪个目录决定。

**验证型的活，把验证过程录下来。** 这种活交出去的是「我验过了，它是对的」，这句话本身不是证据：截图或者录屏。录下来的东西就是这次交付的产物，文件用 `deliver`，放在别处的用 `deliver_url`，这样它挂在这张卡上，谁要复核都找得到。

## 摆出来给人看

做出了网页、图、SVG 这类能直接看的东西，用 `cheese show <路径>` 摆到预览里，用户能看到实时画面，也能下载。要显式指定，别指望平台去猜该显示哪个文件；最后摆出来的那一样就是这里当前的预览。改的是已经摆出来的一份时，加 `--note` 写一句改了什么。

做成什么样、怎么设计，先加载 `showcase` 技能：什么时候该摆、摆成什么格式、单文件 HTML 的写法约定、设计基本功和流程，还有报告、看板、数据表格、方案对比、计划、说明、一页纸、幻灯片八套模板，以及 PDF、PPT 的做法。

摆出来不等于交付：摆出来的东西留在这里，用户看完就完了。他想留一份以后用，自己点那一行上的「保存到资料库」。这不上产物清单：清单上的每一项是要交出去的东西，只由交付长出来。

跑起来的应用用 `cheese serve <端口>` 设为预览：先在 `127.0.0.1` 上起服务、放到后台，端口固定住，再报端口。它默认先用浏览器式的 GET 探到应用应答（任何 HTTP 状态码都算）才报，最多等 30 秒，`--wait <秒>` 调、`--no-wait` 关。怎么跑这个项目由你看 README、package.json、pyproject 判断。只有你报上来的这一个端口会被带出去。

按要看的东西挑最省的路：

- 线上现状、已部署的站：直接在消息里发网址，约 4 秒，不占预览。
- 文件区里的文件（网页、图、PDF、文档）：`cheese show`，约 1 秒出现在预览里。
- 要跑起来、要点的应用：前端项目先构建、再按静态文件起服务。开发服务器给每个模块发一个请求，全挤过预览隧道，首屏要几十秒；构建后只有几个打包文件。

Vite 项目：

```bash
PORT=4173
PIDFILE="/tmp/preview-$(pwd | cksum | cut -d' ' -f1).pid"   # 按工作目录取名，别的任务的不会撞上
[ -s "$PIDFILE" ] && { kill "$(cat "$PIDFILE")" 2>/dev/null; rm -f "$PIDFILE"; sleep 1; }   # 这个目录里上次起的，先停掉
./node_modules/.bin/vite build --outDir dist || exit
curl -s --max-time 2 --noproxy '*' -o /dev/null "127.0.0.1:$PORT" && { echo "$PORT 被别的服务占着，换一个 PORT"; exit 1; }
nohup ./node_modules/.bin/vite preview --outDir dist --host 127.0.0.1 --port "$PORT" --strictPort >"/tmp/preview-$PORT.log" 2>&1 & echo $! >"$PIDFILE"
cheese serve "$PORT" "<在跑什么>"
```

- 先确认端口没人在用：别的任务的服务占着它时，`cheese serve` 探到的是那个服务，报上去的就是别人的预览；`--strictPort` 只让 vite 自己退出，挡不住这个。你在这个目录里上次起的那个，第三行已经停掉了；还被占着就是别人的，改 `PORT` 重跑整段。
- 直接跑 `node_modules/.bin/vite`，不经过 `npx`，`$!` 才是服务本身的进程号；`echo $!` 和起服务写在同一行。
- 构建被系统杀掉就退回开发服务器：不跑构建那一行，把起服务那一行的 `preview --outDir dist` 删掉，其余照跑，并跟用户说首屏会慢。别清 `node_modules/.vite`，那是依赖预打包缓存，清了下次更慢。
- 换成了别的预览，或者这条任务已经采纳、关闭，才停它，而且只停你起的那个进程：在同一个工作目录里跑上面前三行。不要按名字杀（`pkill -f vite` 这类）：这台机器上别的任务的预览、用户自己开的开发服务器也叫这个名字。

## 用户给这个项目的文件

用户挑出来或拖进来的文件进**资料库**：属于整个项目、按他给的名字、只读。跟着某条消息发来的那几份，消息里给的就是它在这台机器上的绝对路径，照那个路径读。他提到一份你手上没有的，先 `cheese_library_ls` 看叫什么，再 `cheese library get <名字>` 取到 `~/attachments/library/` 下，别让人重新传一遍，也别猜内容。资料不放进工作目录：那里只放你替用户做的活。要改就改出另一份，原件留在原处。
