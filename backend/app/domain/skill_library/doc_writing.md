# 芝士文档

芝士文档是人和芝士一起把事情想清楚、写下来的地方。它保存在项目的资料库里，可以在对话旁边打开，也可以单独打开，由多人同时编辑。每个任务还有一份自己的实况文档，记录这个任务当前的全貌。

文档用 Markdown 加一组块来写。你只写「这里放什么」，排版、配色、深色模式和手机上的显示都由平台负责，因此不必考虑样式，也不写 HTML。除了提示框、时间线、图表这类固定的块，文档里还可以嵌入小程序：一段可以运行的程序，读者在文档中直接操作它。

一份好的芝士文档做到三点：

- **好读**：读者打开就能找到需要的内容。文档在网页上阅读，也在手机上阅读。
- **便于共同编辑**：文档写完后，会有人继续修改、添加评论，因此每一段都要能单独读懂、单独修改。
- **精简**：用尽量少的文字和块讲清楚。读者的时间有限，多余的每一句都在占用它。

句子的写法和表述的立场，遵循系统提示词中的「写作」一节；本技能讲整份文档层面的要求。

## 一、什么时候写文档

- 用户需要一份供阅读、修改和保留的文字时（方案、报告、纪要、说明、讲义），新建一份文档。对话中只给出一句结论，不把长文贴进对话：贴在对话里的长文日后难以查找，也无法只修改其中一句。
- 简短的回答，直接在对话中回复。
- 代码和项目的源文件，放在仓库里。
- 需要单独成页的网页、看板或幻灯片时，使用 `showcase` 技能；需要 `.docx`、`.pptx`、`.pdf` 文件时，使用 `documents` 技能。芝士文档是保存在资料库中、供大家共同阅读和修改的那一份。

## 二、修改已有的文档

- 修改直接生效，和人在文档里改一样。想先让人看过再定的改动，可以以建议的形式提出（`cheese_doc(action=edit)` 的 `suggest`），由人决定接受还是拒绝。
- 只修改要求的部分，保留原有的格式和他人写的内容。只有在任务方向改变，或用户明确要求时，才整份重写。
- 某一条不再成立时，直接修改这一条本身，不在旁边添加「更正」「补充」。读者需要的是当前成立的内容，而不是修改的经过。
- 修改任务的实况文档之前，先读 `references/live-doc.md`。

## 三、先明确读者和目的

动笔前先确定三件事：

1. 读者是谁，阅读的目的是什么：做决定、照着操作、了解进度，还是理解一件事。
2. 第一屏放什么。许多读者只读第一屏，只读第一屏也要得到他需要的内容。
3. 每部分用什么形式表达，见第六节。

下表列出常见的几类文档。遇到表中没有的类型，用上面三个问题判断，再参照最接近的一类。

| 类型 | 读者的目的 | 第一屏的内容 | 篇幅 | 常用的形式 |
|---|---|---|---|---|
| 实况文档 | 在一分钟内了解进展，以及自己是否需要做什么 | 最重要的一两句：进展到哪里，是否需要读者做什么；细节作为下级条目放在后面 | 通常不超过 1500 字 | 状态标签、折叠；需要决策的事项用提示框 |
| 方案 | 评审，决定是否做、怎么做 | 做什么、怎么做、代价、需要谁决策 | 摘要不超过一屏，细节放进折叠 | 用时间线演示一个例子、折叠 |
| 对比选型 | 做出选择 | 推荐哪一项、最关键的一两条理由、这一推荐在什么情况下不成立 | 两屏以内 | 对比表格加状态标签 |
| 进度周报 | 了解进度、发现异常 | 情况变好还是变坏、发生了什么、下一步做什么 | 一屏 | 一组指标卡；有连续几周的数据时加一张折线图；其余用列表 |
| 会议纪要 | 了解决定了什么、由谁去做 | 决定、待办事项（负责人、内容、时间） | 一屏 | 不用块：决定用列表，待办事项用表格 |
| 操作说明 | 按步骤操作 | 前提条件、步骤 | 由步骤决定 | 编号步骤、提示框 |
| 分析报告 | 依据数据做决定 | 结论和建议，以及支撑它的一两个数 | 两屏以内 | 指标卡、图表、表格、脚注 |
| 讲义、预习材料 | 理解一个原理、模型或过程 | 要理解的问题、关键的公式或规律 | 视内容而定 | 讲解原理、条件变化、过程推演的部分用小程序；公式 |

## 四、组织

- 按读者关心的问题组织，不按材料原来的顺序复述。材料的顺序只是作者获得信息的顺序，读者需要的是答案。
- 结论只写一次，放在最前面；后面的小节只补充新的信息。
- 周报和纪要篇幅短，结构本身已经清楚，添加块只会让它变长。
- 次要的细节和原始数据，放进折叠，或者删去。

## 五、只写有依据的内容

- 事实、人名、日期、数字，都要能在材料中找到。
- 自己计算得出的数，要能由材料中的数算出。不能一眼看出的，用脚注写出算式，例如 `[^1]: 1,274 − 223 = 1,051`。
- 材料没有说明由谁负责、何时完成的，写「未定」，不代为补充。
- 某个决定由谁做出、某项要求由谁提出，也是事实。写「@某人 决定」「某人要求」时，材料中要能找到此人的原话；你自己的默认做法和判断，写明是你的，不归到别人名下。
- 不为材料补充原因、效果和保证：材料没有说明故障原因，就不写原因；材料没有说「无遗留风险」，就不写。
- 「待确认」一节只放两类事项：材料明确说明尚未确定的，以及材料前后矛盾的。写清是什么事项、为什么不能确定。没有这两类事项，就不写这一节。

## 六、每部分用什么形式

先判断这段内容是什么，再选择形式。选择的标准只有一个：读者能否更快、更准确地获取这段内容。

内容大致分两种：

- **固定的内容**：一个结论、一组事实、一次比较的结果、一串步骤。用文字、表格和块表达。只有当块比文字更清楚时才使用：把正文换一种形式重复一遍的块，只会让文档变长、变难读。
- **变化的内容**：结果随条件变化，过程随时间推进，或者需要读者亲手尝试才能体会。文字、表格和图只能展示作者选定的几种情况，这时用小程序，让读者自己观察和尝试。

| 内容 | 表达形式 |
|---|---|
| 规则、机制 | 用一个具体例子演示，以时间线或表格列出每一步的结果；结果随条件变化、需要对比多种情况才能理解的，用小程序 |
| 有先后顺序的事件、步骤、排期 | 时间线 |
| 每一项的结果或状态 | 状态标签 |
| 分情况处理（如果……就……） | 「情况 × 结果」表格；层级较多时用嵌套列表，每项后面加状态标签 |
| 三个以上需要一眼看到的关键数字 | 指标卡 |
| 一组数随时间的变化、几项之间的大小比较、各部分的占比 | 图表 |
| 需要读出精确值、逐项对照的数 | 表格 |
| 流程、几方之间的往来、状态的转换 | 流程图（mermaid） |
| 原理、随条件变化的结果、方案比较、过程推演、动手组合 | 小程序 |
| 几件事之间的关系：谁依赖谁、谁影响谁、哪几件服务于同一个目标 | 画布（格子加连线） |
| 结论、风险、需要决策的事项 | 提示框 |
| 两三段并列的整段内容 | 分栏 |
| 次要细节、原始数据、长清单 | 折叠 |

只有当一段关系用图比用文字更清楚时，才画图：流程、依赖关系、几样东西的对比、随时间的变化。一句话能说清的不画，不为美观而画，图中也不重复正文已有的内容。数据（耗时、数量、趋势、对比）用图表块 `:::chart`；流程、依赖关系和先后顺序用 mermaid；这两种都画不出来的，再用 Python（matplotlib）画成图片，做法见 `references/blocks.md` 的「图片」一节。

以下几种用法会让文档变差，应当避免：

- 块只是把正文换一种形式重复一遍。用了块，正文就不再逐项复述块中的内容。
- 指标卡里放计数，例如「决定事项 3 项」。计数写进句子。
- 图表只有两三个数。这样的数写进句子或表格。
- 正文逐个复述图表中的数。正文只写从图中得出的结论。
- 状态标签只是重复同一句话里刚说过的内容，例如「设备显示在线 {✓ 在线}」。
- 分栏里放一一对应的关系，例如「旧名 / 新名」。对应关系用表格。
- 每段都加粗，每句都拆成列表项。列表只用于并列的几项。

### 什么时候用小程序

讲解原理、结果随条件变化、比较方案、推演过程、让读者动手组合，这几类内容用小程序。讲义、预习材料、原理说明、方案分析这类讲解性的文档中，遇到这几类内容，默认用小程序。结论固定、读者没有可以调整的东西时，不用。每一类怎么判断、用了怎么写，先加载 `miniapp` 技能。

## 七、常见问题和改法

**逐句附加免责说明**
- 原文：「Redis 社区很活跃。这是参考因素，不是选型的主要依据。」
- 改为：删去后半句免责说明。

**为材料补充内容**
- 原文：「两次故障都已修复，无遗留风险。」材料中只说「已修复」。
- 改为：「两次故障都已修复。」

**按材料顺序罗列**
- 原文：一个工期两周的功能，按「背景、现状、规则、设计、数据、接口……」写了 12 节，把材料复述了一遍。
- 改为：第一屏写清做什么、怎么做、两周如何安排、需要谁决策；其余内容放进折叠，或者删去。

**重复**
- 原文：「推荐方案 A」在「结论」「推荐理由」「落地建议」三节中各说了一次。
- 改为：结论只在开头写一次，后面的小节只补充新的信息。

**装饰性的结构**
- 原文：指标卡「讨论议题 4 个」「参会人数 5 人」。
- 改为：计数写进句子，删去这组指标卡。

**反驳的语气**
- 原文：「不要仅凭一周数据就下结论。」
- 改为：「只有一周的数据，看不出节假日的影响。」

## 八、块和小程序的写法

提示框、状态标签、时间线、指标卡、图表、流程图、小程序、图片、画布、分栏、折叠、脚注、公式，每一种的写法见 `references/blocks.md`；小程序的代码写法和画面设计在 `miniapp` 技能里。使用块之前先读这份说明：修改文档时要逐字引用原文，块的格式写错时，整次写入都会被拒绝。

## 九、两个例子

讲解规则时，用一个例子演示。「额度用完后，各类请求如何处理」写成文字很绕，按时间演示一遍就清楚：

```
以一个月额度 100 点的项目为例：

:::timeline
- 第 1 天 | 额度充足 {✓ 对话} {✓ 文档} {✓ 后台任务}
  每次调用按实际花费扣点。
- 第 20 天 | 用到 80 点 {! 提醒负责人}
  综合频道里提醒一次，功能不受影响。
- 第 26 天 | 用完 {✓ 对话} {✗ 文档} {✗ 后台任务}
  对话降级到免费模型；其余请求直接拒绝，并说明原因。
- 下月 1 日 | 额度重置 {✓ 对话} {✓ 文档} {✓ 后台任务}
:::
```

分析报告的第一屏：

```
> [!IMPORTANT]
> 搜索框改成常驻后，搜索次数翻倍[^1]，用户找到结果的比例没变：建议保留。

:::stats
- 日均搜索 | 2,140 次 | +104%
- 找到结果 | 71% | 持平
- 平均用时 | 9.2 秒 | -1.3 秒
:::

[^1]: 改版前日均 1,049 次：2,140 ÷ 1,049 − 1 ≈ 104%。
```

例子只示范手法。文档的结构由它自己的内容决定，不要套用例子的结构。
