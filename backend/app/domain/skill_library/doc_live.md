# 实况文档

实况文档写给谁、如何组织、如何修改，系统提示词中的「实况文档」一节已经说明。这里补充三点。

## 哪些内容不写进实况文档

- **已完成的事**：合并的 PR 会由平台显示在「相关」中。一件事完成后，从文档中删去，不改写成「已完成……」。
- **过程**：排查经过、被推翻的猜测、交接经过、每天做了什么，现场里都看得到，不写进文档，也不搬进聊天。
- **证据细节**：测试数量、提交哈希、截图核对，写进 PR 描述或任务卡。文档只写结论，并附一个指向证据的链接。
- **无关的事**：平台的问题写进反馈；与本任务无关的待办事项不写。
- **粘贴的原文**：命令输出、聊天记录、长代码块，都不放进文档。

## 什么时候修改

- 以下内容发生变化时才修改：为什么做、进展到哪里、谁在做什么、决定了什么、还有什么没有确定。简短的问答留在聊天中；没有新结论的等待不用写。
- 任务方向改变时，重写整份文档，不在末尾追加「此前的方向」。
- 某一条不再成立时，直接修改这一条本身，不在旁边添加「更正」「补充」。
- 全文超过 1500 字时，写入仍会成功，但会返回警告，此时要立即删减到 1500 字以内。

## 块的用法

- 已确定和尚未确定的事项后面，可以加一个状态标签；需要他人决策的事项放进提示框。
- 理由、依据这类细节，作为下级条目放在它所说明的那一句下面；读者多半不会展开的大段内容，放进折叠块。
- 折叠块放在顶层，不放进列表项：列表项中的折叠块保存后会多出只含空格的行，之后修改它时必须原样引用这些行。
- 只有确实要交代几个有先后顺序的步骤时，才用时间线。
- 引用要能点击打开：频道写 `@频道名`，工作区文件写 `<&路径>`；需要通知某人时才写 `@名字`。

## 示例

```
九个页面的新界面已经完成，等待 @张衡 在预览中查看后反馈意见。{! 等待反馈}

- @张衡：打开本任务的「预览」，用 alice / demo12345 登录，查看九个页面，回复需要修改的地方。
  - 预览需要工作机在线才能打开。如果打不开，在任务中告知，我改为发送单文件 HTML。
- 这项任务是重做后台管理（五个页面）和反馈（四个页面）的界面，统一框架和布局，与工作台的风格一致，以前端工作为主。
- 已确定：
  - 网关不可达时，模型页的「新增模型」保持禁用，与主干一致。@张衡 决定 {✓ 已确认}
  - 看板的分类页签和时间窗口只调整外观，仍使用按钮。这是我的判断。
    - 改用共用的页签组件会使现有的端到端测试失败。
- 尚未确定：提交说明中的 Co-authored-by 一行是否删除。我建议保留，它不影响合并；由 @张衡 决定。

<details><summary>未采用的做法</summary>

- 网关不可达时也允许新增，先保存为草稿：需要另做一套草稿状态，这次不做。

</details>
```
