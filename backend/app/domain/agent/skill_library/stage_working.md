# 当前阶段：这件事正在做（还没递卡）

## 开工第一件事

**确认你的分支基于最新 main。** 沙箱是现拉的，但房间的容器可能是长期运行的——不确认就动手，最常见的后果是照着旧代码做出一份已经被人改掉的方案。

临时文件放 `/tmp` 下的 scratchpad；**要留下的产物一律写工作区里的相对路径**，别在工作区建 `.probe-*` 之类的实验目录。

## 验证：闸门不替你跑测试

递卡后平台跑的机器闸门是 `check_command`，它带 `--no-tests` ——**只跑 lint/类型检查，不跑测试**。测试第一次真正跑起来是在 PR 的 Actions 上，那已经是采纳之后的事了。

所以**测试得你自己在沙箱里跑通**。跑不动的检查（缺网、缺数据库）照实标注是环境限制，写清楚哪几项真跑绿了、哪几项没跑，**不要硬磕，也不要含糊带过**——"检查都过了"而实际上一半被 SKIP，是验收卡被打回最常见的原因。

## 什么时候递卡——不一定是"任务做完"

这条最反直觉，但它会改变你对"做完了没有"的判断：

**你的沙箱只有一个只读的 GitHub token**（`actions`/`checks`/`metadata`）。你**永远不能**自己推代码、开 PR、重跑 workflow。你的产出到达 GitHub 的**唯一路径**是：

> 递卡 → 人采纳 → 平台用**采纳人的** token 去推

所以除了"做完了"，还有一类递卡时机：**当你需要的下一步动作只有采纳人的 token 才能做时**——比如需要真正跑一次完整 CI、需要开 PR 让检查跑起来——**即使你觉得还没完全做完，也应该递卡**，并在理由里**写明"递这张卡是为了拿到 X"**。攥着一个已经验证到沙箱极限的产出继续空转，不会让它变得更可靠。

## 采纳者的 token 怎么"用"——不是直接用，也不是一次性的

你拿不到那个 token，也不该拿到。你是通过递卡让平台**代你用**。

而且**采纳不等于这张卡结束了**：卡进入 `pr_open` 之后，你在本地分支上的**每一次新提交，平台都会用采纳人的 token 自动重推到 PR**（60 秒轮询一次）。所以采纳的真正含义是——**从现在起你有了一条通往 GitHub 的通道**。继续在本分支改就行。

## 递卡前：确认采纳人连了 GitHub 账号

PR 这条路要求**采纳人本人**连过 GitHub 账号（项目设置页的「连接 GitHub 账号」）。没连的话，采纳会**降级成本地直接合并**——照样能合，但你就拿不到 PR，也拿不到那次真实 CI。

你**查不到**别人连没连（连接状态只有本人能看）。所以要确认就直接问，用按钮别让人打字：

```
cheese ask "递卡前确认一下：走 PR 路径需要你先在项目设置页连接 GitHub 账号。连好了吗？" \
  --option "连好了，递卡吧" --option "还没连，我这就去连" --option "先不连，本地合并就行"
```

用户点完，答案下一轮自动带回给你。

事后也有信号：如果卡被采纳后**没有**进 `pr_open` 而是直接 accepted，就是降级了——**降级原因平台已经写在卡的 note 上**（如「批准人未连接 GitHub 账号」），`cheese status` 能看到，照着它说，别猜。

## 递卡怎么写

`cheese accept-request <handle> "<理由>" --subject '<提交标题>' --body '<为什么>'`

理由要**逐条对着验收标准给证据**，不是"做完了"。递卡前先自己把检查跑绿，省一个来回。

**`--subject` 不是给人看的说明，是这次改动留在 git 历史里的那一行**：递卡开 PR 用它当标题，采纳时整个分支被压成一个提交，标题还是它。**它是必填的**——不给就递不出去，后端会当场打回并把写法告诉你。

写法：Conventional Commits，英文祈使句，≤72 字符，结尾不加句号——`fix(accept): open the PR as the requester, not the bot`。`--body` 写**为什么**（根因、为什么这么修），不写做了什么的清单，也不写"测试全绿"这种废话；显而易见的改动可以不写 body。格式不对平台会当场打回并告诉你该怎么写。
