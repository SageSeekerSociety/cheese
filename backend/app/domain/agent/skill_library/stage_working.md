# 交付：这批活还没递卡

## 开工第一件事

**确认你的分支基于最新 main。** 沙箱是现拉的，但房间的容器可能是长期运行的——不确认就动手，最常见的后果是照着旧代码做出一份已经被人改掉的方案。

临时文件放 `/tmp` 下的 scratchpad；**要留下的产物一律写工作区里的相对路径**，别在工作区建 `.probe-*` 之类的实验目录。

## 验证：平台不替你跑测试

递卡前，lint、类型检查和测试按**这个仓库自己的约定**跑；平台不在递卡后替你跑任何检查，PR 上的真 CI 是唯一的裁决。

所以**测试得你自己在沙箱里跑通**。跑不动的检查（缺网、缺数据库）照实标注是环境限制，写清楚哪几项真跑绿了、哪几项没跑，**不要硬磕，也不要含糊带过**——"检查都过了"而实际上一半被 SKIP，是验收卡被打回最常见的原因。

## 什么时候递卡——不一定是"任务做完"

这条最反直觉，但它会改变你对"做完了没有"的判断：

**你的沙箱的推送 token 是只读的**。你**永远不能**自己推代码、开 PR、重跑 workflow。平台替你做这两步：

> 这批活的**第一个提交** → 平台用 **App 的** token 推分支、开一个 **draft PR** → 真 CI 开始跑
>
> 递卡 → 同一个 PR 从 draft 翻成 ready，卡是它的视图 → 人点采纳 = 当场合并

所以「有东西就有 PR」：你提交了，PR 就在了（draft 是 GitHub 里「进行中」的意思），CI 也已经在跑。想在递卡之前就说一句「这份东西可以看了」，跑 `cheese ready`——它只翻这一件事，不递卡、不合并。

所以除了"做完了"，还有一类递卡时机：**当你需要真 CI 才能验证时**——比如要跑那几个沙箱里跑不动的检查——**即使你觉得还没完全做完，也应该递卡**，并在理由里**写明"递这张卡是为了拿到 X"**。攥着一个已经验证到沙箱极限的产出继续空转，不会让它变得更可靠。

## 递卡之后：改动怎么上 PR

递卡后你在本地分支上的新提交**不会自动上 PR**——改完跑 `cheese push-fix`，平台把它推上去，检查重新跑。注意：PR 上来新提交会**作废已有的采纳批准**（分支保护默认开），所以修完说一声，让验收人重新看。人点采纳＝**当场合并**他看到的那个 commit。

## 递卡怎么写

`cheese accept-request <handle> "<理由>" --subject '<提交标题>' --body '<为什么>'`

理由要**逐条对着验收标准给证据**，不是"做完了"。递卡前先自己把检查跑绿，省一个来回。

**`--subject` 不是给人看的说明，是这次改动留在 git 历史里的那一行**：递卡开 PR 用它当标题，采纳时整个分支被压成一个提交，标题还是它。**它是必填的**——不给就递不出去，后端会当场打回并把写法告诉你。

写法：Conventional Commits，英文祈使句，≤72 字符，结尾不加句号——`fix(accept): open the PR as the requester, not the bot`。`--body` 写**为什么**（根因、为什么这么修），不写做了什么的清单，也不写"测试全绿"这种废话；显而易见的改动可以不写 body。格式不对平台会当场打回并告诉你该怎么写。
