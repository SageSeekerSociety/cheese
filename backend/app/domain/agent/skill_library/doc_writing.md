# 写文档

文档在网页上读，也在手机上读。写完会被人接着改、被评论，所以每一段都要能单独读懂、单独修改。

## 一、动笔前先定三件事

1. 这是哪类文档。
2. 读者来干什么：做决定、照着做，还是了解进度。
3. 第一屏放什么。读者只读第一屏，也要拿到他要的东西。

| 类型 | 读者来干什么 | 第一屏放什么 | 篇幅 | 常用的块 |
|---|---|---|---|---|
| 方案 | 评审，决定做不做、怎么做 | 做什么、怎么做、代价、要谁拍板的问题 | 摘要一屏；细节放进折叠 | 走一遍例子的时间线、折叠 |
| 对比选型 | 做选择 | 推荐哪个、最关键的一两条理由、这个推荐在什么情况下不成立 | 两屏以内 | 对比表格配状态标签 |
| 进度周报 | 了解进度、发现异常 | 变好还是变坏、出了什么事、下一步 | 一屏 | 一组指标卡；其余用列表 |
| 会议纪要 | 知道定了什么、谁去做 | 决定、待办（谁、做什么、何时） | 一屏 | 不用块：决定用列表，待办用表格 |
| 操作说明 | 照着做 | 前提条件、步骤 | 步骤本身决定 | 编号步骤、提示框 |
| 分析报告 | 根据数据做决定 | 结论和建议，加支撑它的一两个数 | 两屏以内 | 指标卡、表格、脚注 |

正文按读者的问题组织，不按材料原来的顺序复述。周报和纪要短，结构本身就够清楚，加块只会变长。

## 二、只写有根据的事

- 事实、人名、日期、数字，都要在材料里找得到。
- 自己算出来的数，要能从材料里的数算出来。不是一眼能看出的，用脚注写出算式：`[^1]: 1,274 − 223 = 1,051`。
- 材料没说谁负责、什么时候做，就写「未定」，不替人补。
- 不替材料补原因、效果和保证：材料没说故障原因，就不写原因；没说「无遗留风险」，就不写。
- 「待确认」一节只放两种事：材料里明说还没定的，材料前后对不上的。写清是什么、为什么拿不准。没有这两种事，就不写这一节。

## 三、能看的先给看

先想这段内容画出来是什么样，再决定写不写成文字。

| 内容 | 怎么表达 |
|---|---|
| 规则、机制 | 拿一个具体例子走一遍，用时间线或表格列出每一步的结果 |
| 有先后的事件、步骤、排期 | 时间线 |
| 每一项的结果或状态 | 状态标签 |
| 分情况处理（如果……就……） | 情况 × 结果的表格；层级多时用嵌套列表，每项后面跟状态标签 |
| 三个以上要一眼看到的关键数字 | 指标卡 |
| 比大小、看趋势 | 表格 |
| 结论、风险、要拍板的事 | 提示框 |
| 两三段并列的整段内容 | 分栏 |
| 次要细节、原始数据、长清单 | 折叠 |

不要这样用：

- 块只是把正文换个形状再说一遍。用了块，正文就不再逐项复述块里的内容。
- 指标卡里放计数，比如「决定事项 3 项」。计数写进句子。
- 状态标签只是重复同一句话里刚说过的事，比如「设备显示在线 {✓ 在线}」。
- 分栏里放一一对应的关系，比如「旧名 / 新名」。对应关系用表格。
- 每段都加粗、每句都拆成列表项。列表只用于并列的几项。

## 四、句子

- 说明句不超过 45 字；步骤句不超过 35 字。
- 一句只说一件事。一段只讲一件事，不超过 5 句。
- 用主动句。步骤写成祈使句：「打开设置」，不写「用户需要打开设置」。
- 同一个东西始终用同一个词。项目里的自造词和缩写，第一次出现时说明它是什么。
- 写数字、名字、例子，不写「较大」「显著」「非常」。
- 不写铺垫、过渡和收尾总结：「下面介绍」「综上所述」「值得注意的是」。

## 五、立场

- 直接下判断。拿不准的事按第二节写进「待确认」，正文里不逐句免责。
- 不预设读者有误解。不写「不是 X，而是 Y」，不写「不要仅凭……」。直接写对的是什么。
- 同一个结论只写一次。不替读者总结刚读完的内容。

## 六、常见毛病和改法

**逐句免责**
- 原句：「Redis 社区很活跃。这是参考因素，不是选型的主要依据。」
- 改：删掉免责的那半句。

**替材料补内容**
- 原句：「两次故障都已修复，无遗留风险。」材料只说「已修复」。
- 改：「两次故障都已修复。」

**流水账**
- 原句：一个两周工期的功能写了 12 节，按「背景、现状、规则、设计、数据、接口……」把材料讲了一遍。
- 改：第一屏写做什么、怎么做、两周怎么排、要谁拍板。其余放进折叠或删掉。

**重复**
- 原句：「推荐方案 A」在「结论」「推荐理由」「落地建议」里各说一次。
- 改：结论只在开头说一次。后面的小节只补新信息。

**装饰性结构**
- 原句：指标卡「讨论议题 4 个」「参会人数 5 人」。
- 改：计数写进句子，删掉这组指标卡。

**反驳性语气**
- 原句：「不要仅凭一周数据就下结论。」
- 改：「只有一周数据，看不出节假日的影响。」

## 七、块的写法

照下面的样子写，空格和换行也照抄：改文档时要逐字引用原文，文档存下来就是这个样子。写错了，写入会被拒，返回里写着哪一行、正确的写法是什么。

提示框：

```
> [!IMPORTANT]
> 推荐方案 A：现成的扩展最多，一个月能上线。
```

类型：NOTE（补充）、TIP（建议）、IMPORTANT（结论、决定）、WARNING（风险）、CAUTION（会出事的操作）。一篇文档里提示框不超过三个。

状态标签：`{✓ 文字}` 表示是、通过、会发生；`{✗ 文字}` 表示否、不通过、不会发生；`{! 文字}` 表示有风险、待定。正文、表格、时间线里都能用。

时间线（每项：时间或序号 | 标题，下一行缩进两格写一两句说明，说明可以不写；标题后面可以跟状态标签）：

```
:::timeline
- 10:02 | 提交合并请求 {✓ 单元测试} {✗ 类型检查}
  类型检查报了 2 处错误。
- 10:15 | 修好后重新提交 {✓ 单元测试} {✓ 类型检查} {! 等待评审}
:::
```

指标卡（每行：名称 | 数值 | 变化，变化可以不写；最多六项）：

```
:::stats
- 活跃项目 | 128 | +12%
- 首字时间 | 6.1 秒 | -27%
:::
```

分栏（两到三栏）：

```
::::columns
:::column
**方案 A**

一个月上线。
:::
:::column
**方案 B**

两周上线。
:::
::::
```

折叠：

```
<details><summary>原始数据</summary>

这里写 Markdown 内容。

</details>
```

脚注：正文写 `[^1]`，文末单独一行写 `[^1]: 说明`。脚注只做两件事：解释一个名词，写出一个数的来源或算式。免责、补充论点、「仅供参考」都不写进脚注。

公式：行内写 `$...$`，单独一段写

```
$$
E = mc^2
$$
```

金额里的 `$` 照常写：`$` 后面紧跟数字的不算公式。

除了 details、summary、sub、sup、kbd、br、mark，不要用其他 HTML 标签。

## 八、两个例子

讲规则时走一个例子。「额度用完后，各类请求怎么处理」写成文字很绕，走一遍就清楚：

```
以一个月额度 100 点的项目为例：

:::timeline
- 第 1 天 | 额度充足 {✓ 对话} {✓ 文档} {✓ 后台任务}
  每次调用按实际花费扣点。
- 第 20 天 | 用到 80 点 {! 提醒负责人}
  综合频道里提醒一次，功能不受影响。
- 第 26 天 | 用完 {✓ 对话} {✗ 文档} {✗ 后台任务}
  对话降级到免费模型；其余请求直接拒绝，并说明原因。
- 下月 1 日 | 额度重置 {✓ 对话} {✓ 文档} {✓ 后台任务}
:::
```

分析报告的第一屏：

```
> [!IMPORTANT]
> 搜索框改成常驻后，搜索次数翻倍[^1]，用户找到结果的比例没变：建议保留。

:::stats
- 日均搜索 | 2,140 次 | +104%
- 找到结果 | 71% | 持平
- 平均用时 | 9.2 秒 | -1.3 秒
:::

[^1]: 改版前日均 1,049 次：2,140 ÷ 1,049 − 1 ≈ 104%。
```

例子只示范手法。照着文档本身的内容决定结构，不要套用例子的结构。
