# 芝士文档

文档在网页上读，也在手机上读。写完会被人接着改、被评论，所以每一段都要能单独读懂、单独修改。句子怎么写、立场怎么摆，按系统提示词里的「写作」一节。

## 一、动笔前先定三件事

1. 这是哪类文档。
2. 读者来干什么：做决定、照着做，还是了解进度。
3. 第一屏放什么。读者只读第一屏，也要拿到他要的东西。

| 类型 | 读者来干什么 | 第一屏放什么 | 篇幅 | 常用的块 |
|---|---|---|---|---|
| 实况文档 | 一分钟内知道到哪了、要不要自己做什么 | 五块：目标、现状、需要谁做什么、已确定、待决 | 1500 字以内 | 状态标签；要人拍板的事用提示框 |
| 方案 | 评审，决定做不做、怎么做 | 做什么、怎么做、代价、要谁拍板的问题 | 摘要一屏；细节放进折叠 | 走一遍例子的时间线、折叠 |
| 对比选型 | 做选择 | 推荐哪个、最关键的一两条理由、这个推荐在什么情况下不成立 | 两屏以内 | 对比表格配状态标签 |
| 进度周报 | 了解进度、发现异常 | 变好还是变坏、出了什么事、下一步 | 一屏 | 一组指标卡；有连续几周的数时加一张折线图；其余用列表 |
| 会议纪要 | 知道定了什么、谁去做 | 决定、待办（谁、做什么、何时） | 一屏 | 不用块：决定用列表，待办用表格 |
| 操作说明 | 照着做 | 前提条件、步骤 | 步骤本身决定 | 编号步骤、提示框 |
| 分析报告 | 根据数据做决定 | 结论和建议，加支撑它的一两个数 | 两屏以内 | 指标卡、图表、表格、脚注 |

正文按读者的问题组织，不按材料原来的顺序复述。周报和纪要短，结构本身就够清楚，加块只会变长。

## 二、只写有根据的事

- 事实、人名、日期、数字，都要在材料里找得到。
- 自己算出来的数，要能从材料里的数算出来。不是一眼能看出的，用脚注写出算式：`[^1]: 1,274 − 223 = 1,051`。
- 材料没说谁负责、什么时候做，就写「未定」，不替人补。
- 不替材料补原因、效果和保证：材料没说故障原因，就不写原因；没说「无遗留风险」，就不写。
- 「待确认」一节只放两种事：材料里明说还没定的，材料前后对不上的。写清是什么、为什么拿不准。没有这两种事，就不写这一节。

## 三、能看的先给看

先想这段内容画出来是什么样，再决定写不写成文字。

| 内容 | 怎么表达 |
|---|---|
| 规则、机制 | 拿一个具体例子走一遍，用时间线或表格列出每一步的结果 |
| 有先后的事件、步骤、排期 | 时间线 |
| 每一项的结果或状态 | 状态标签 |
| 分情况处理（如果……就……） | 情况 × 结果的表格；层级多时用嵌套列表，每项后面跟状态标签 |
| 三个以上要一眼看到的关键数字 | 指标卡 |
| 一组数随时间怎么变、几项谁大谁小、各占多少 | 图表 |
| 要读出精确值、要逐项对照的数 | 表格 |
| 流程、几方之间的来回、状态怎么转 | 流程图（mermaid） |
| 结论、风险、要拍板的事 | 提示框 |
| 两三段并列的整段内容 | 分栏 |
| 次要细节、原始数据、长清单 | 折叠 |

不要这样用：

- 块只是把正文换个形状再说一遍。用了块，正文就不再逐项复述块里的内容。
- 指标卡里放计数，比如「决定事项 3 项」。计数写进句子。
- 图表只画两三个数。两三个数写进句子或表格。
- 正文把图表里的数逐个复述一遍。正文只写从图中得出的结论。
- 状态标签只是重复同一句话里刚说过的事，比如「设备显示在线 {✓ 在线}」。
- 分栏里放一一对应的关系，比如「旧名 / 新名」。对应关系用表格。
- 每段都加粗、每句都拆成列表项。列表只用于并列的几项。

## 四、实况文档

五块各写什么、怎么改，系统提示词里「实况文档」一节已经写了。这里补三件事。

什么不进实况文档：

- **做完的事。**合进去的 PR 平台会挂在「相关」里。事情做完，就从「需要谁做什么」里删掉，不改写成「已完成……」。
- **过程。**排查经过、推翻过的猜测、换人接手的经过、每天做了什么，留在聊天里。
- **证据细节。**测试数量、提交 hash、截图核对写进 PR 描述或任务卡。文档写结论，再给一个指回证据的链接。
- **别的事。**平台的毛病写进反馈卡；和本任务无关的待办不写。
- **粘贴的原文。**命令输出、聊天记录、长代码块都不进来。

什么时候改：

- 目标、现状、分工、决定、待决变了才改。简短问答和没有新结论的等待留在聊天里。
- 任务换了方向时，重写整份文档，不在末尾追加「此前一轮」。
- 一条不成立了，改掉它本身，不在旁边加「更正」「补充」。
- 全文超过 1500 字时写入照样成功，但会带回警告，要当场删到 1500 字以内。

块：已确定和待决的每一条后面可以跟一个状态标签，要人拍板的那一件放进提示框。时间线只在确实有几步先后要交代时用。引用要能点开：频道写 `@频道名`，工作区文件写 `<&路径>`，要通知本人时才写 `@名字`。

一份实况文档的样子：

```
## 目标

重做后台管理（五页）和反馈（四页）的界面，统一框架和布局，贴合工作台风格。以前端为主。

## 现状

设计已完成，等 @张衡 在预览里看完九个页面给意见。

## 需要谁做什么

- @张衡：打开本任务的「预览」，用 alice / demo12345 登录，看九个页面，回复要改的地方。预览要工作机在线才打得开；打不开时在任务里说一声，改发单文件 HTML。
- @<你的名字>：按意见修改；确认后把 PR 标为可评审，递验收卡。

## 已确定

- 看板的分类页签和时间窗口只改外观，仍用按钮 {✗ 不换共用页签}：换成共用页签组件会打断现有的端到端测试。
- 网关不可达时，模型页的「新增模型」保持禁用，与主干一致，@张衡 已定 {✓ 已确认}。

## 待决

- 提交里带的那行 Co-authored-by 要不要删？建议保留，它不影响合并。由 @张衡 定 {! 待定}。
```

## 五、常见毛病和改法

**逐句免责**
- 原句：「Redis 社区很活跃。这是参考因素，不是选型的主要依据。」
- 改：删掉免责的那半句。

**替材料补内容**
- 原句：「两次故障都已修复，无遗留风险。」材料只说「已修复」。
- 改：「两次故障都已修复。」

**流水账**
- 原句：一个两周工期的功能写了 12 节，按「背景、现状、规则、设计、数据、接口……」把材料讲了一遍。
- 改：第一屏写做什么、怎么做、两周怎么排、要谁拍板。其余放进折叠或删掉。

**重复**
- 原句：「推荐方案 A」在「结论」「推荐理由」「落地建议」里各说一次。
- 改：结论只在开头说一次。后面的小节只补新信息。

**装饰性结构**
- 原句：指标卡「讨论议题 4 个」「参会人数 5 人」。
- 改：计数写进句子，删掉这组指标卡。

**反驳性语气**
- 原句：「不要仅凭一周数据就下结论。」
- 改：「只有一周数据，看不出节假日的影响。」

## 六、块的写法

提示框、状态标签、时间线、指标卡、图表、流程图、分栏、折叠、脚注、公式，每一种的写法都在 `references/blocks.md`。用块之前先读它：改文档时要逐字引用原文，块写错了形状，写入会被整次拒绝。

## 七、两个例子

讲规则时走一个例子。「额度用完后，各类请求怎么处理」写成文字很绕，走一遍就清楚：

```
以一个月额度 100 点的项目为例：

:::timeline
- 第 1 天 | 额度充足 {✓ 对话} {✓ 文档} {✓ 后台任务}
  每次调用按实际花费扣点。
- 第 20 天 | 用到 80 点 {! 提醒负责人}
  综合频道里提醒一次，功能不受影响。
- 第 26 天 | 用完 {✓ 对话} {✗ 文档} {✗ 后台任务}
  对话降级到免费模型；其余请求直接拒绝，并说明原因。
- 下月 1 日 | 额度重置 {✓ 对话} {✓ 文档} {✓ 后台任务}
:::
```

分析报告的第一屏：

```
> [!IMPORTANT]
> 搜索框改成常驻后，搜索次数翻倍[^1]，用户找到结果的比例没变：建议保留。

:::stats
- 日均搜索 | 2,140 次 | +104%
- 找到结果 | 71% | 持平
- 平均用时 | 9.2 秒 | -1.3 秒
:::

[^1]: 改版前日均 1,049 次：2,140 ÷ 1,049 − 1 ≈ 104%。
```

例子只示范手法。照着文档本身的内容决定结构，不要套用例子的结构。
