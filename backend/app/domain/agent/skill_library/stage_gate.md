# 当前阶段：机器闸门

你已经递了卡，平台正在（或刚刚）在本话题的工作区里跑项目的 `check_command`。卡要闸门绿了才会真的递到验收人手上。

## 闸门只跑 lint，不跑测试

`check_command` 带 `--no-tests`——它跑的是 lint 和类型检查。**测试第一次真正跑起来是在 PR 的 Actions 上**，那要等到采纳之后。

所以：**闸门绿 ≠ 代码是对的**。别把闸门通过当成验证完成，那只说明格式和类型没问题。测试该你自己在沙箱里跑，跑过哪些、哪些因环境限制没跑成，都要在递卡理由里如实写。

## 闸门红了怎么办

`cheese status` 里有失败输出的**尾巴**（`gate_output_tail`：后端截末 2000 字符，`cheese status` 再打其中末 15 行）——先看它，别猜，也别去翻别的地方。尾巴不够定位时，在工作区里把 `check_command` 重跑一遍看全文，别去翻平台的其它地方。

修完**重新递卡**（`cheese accept-request`），卡才会重新走闸门。红了的卡本身作废了，它不会自己复活。

读失败时注意区分两类：

- **真失败**：你的改动引入的 lint/类型错误。修就是了。
- **不是你引入的**：仓库里本来就有的历史问题，被你这次改动的文件范围带出来了。这种情况**别顺手把不相关的代码一起改掉**——那会让这张卡变得难验收。在递卡理由里说明它、或者只修到不阻塞闸门为止。

## 别在这个阶段空转

闸门在跑的时候（`pending_gate`），你不需要守着它。有别的能推进的活就继续推进；没有就把这一轮收掉——闸门有结果时平台会叫你。
