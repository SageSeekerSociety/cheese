# 实况文档怎么写

实况文档是一页状态页。它有三个读者：

- 来看进展的人：发起人、要拍板的人、刚加入的人。他们没看过聊天，要在一分钟内知道到哪了、要不要自己做什么、要自己定什么。
- 下一轮的你：文档每轮都会注入，你靠它接着干。
- 项目总览：每个活跃话题后面显示的那一句，取自这份文档的「现状」。

三个读者都要短、新、结论在前。细节在聊天、任务卡、PR 和代码里，文档只给链接。

## 五块

按这个顺序写，标题用 `##`：

1. **目标**：这件事为什么做、做到什么程度算完，不超过 3 句。
2. **现状**：一句话，说到哪了、卡在哪。总览取的就是这一句。
3. **需要谁做什么**：每条是 `@谁`、做什么、怎么做（带链接）。要人做的排在前面。
4. **已确定**：查清的事实和做出的决定，只收会影响后续做法的。每条一句结论，加一句理由或依据。
5. **待决**：每条写问题、可选的做法、你的建议、由谁定。

「相关」一块由平台自动挂上任务卡、PR 和子话题，不用手写。

## 什么不进文档

- **做完的事。**合进去的 PR 平台会挂在「相关」里。事情做完，就从「需要谁做什么」里删掉，不改写成「已完成……」。
- **过程。**排查经过、推翻过的猜测、换人接手的经过、每天做了什么，留在聊天里。
- **证据细节。**测试数量、提交 hash、截图核对写进 PR 描述或任务卡。文档写结论，再给一个指回证据的链接。
- **别的事。**平台 bug 写进反馈卡；和本话题无关的待办不写。
- **粘贴的原文。**命令输出、聊天记录、长代码块都不进来。

## 维护

- **变了就替换。**一条不成立了，改掉它本身，不在旁边加「更正」「补充」。
- **房间开始做另一件事时，重写整份文档。**不在末尾追加「此前一轮」。
- **有持久变化时才更新**：目标、现状、分工、决定、待决变了才改。简短问答和没有新结论的等待留在聊天里。
- 更新前先用 `cheese_doc_get` 读当前版本，保留仍成立的内容。改其中几处用 `cheese_doc_edit`；重写整份才用 `cheese_doc_set`，它整份覆盖，要按你读到的那一版写，读到的是旧版会被拒。
- 全文不超过 1500 字。超了写入照样成功，但会带回警告，要当场删到 1500 字以内。
- 引用要能点开：话题用 `@话题标题`，工作区文件用 `<&路径>`。要通知本人时才用 `@名字`。
- 提示框、状态标签、时间线这些块的写法见 doc-writing 技能。不写链接引用定义，表格每行格数和表头一致。会丢掉文字或块写错的写入会被整次拒绝，返回里写着哪一行、怎么改。
- 写法按系统提示词里的「写作」一节。

## 示例

```
## 目标

重做后台管理（五页）和反馈（四页）的界面，统一框架和布局，贴合工作台风格。以前端为主。

## 现状

设计已完成，等 @张衡 在预览里看完九个页面给意见。

## 需要谁做什么

- @张衡：打开本话题的「预览」，用 alice / demo12345 登录，看九个页面，回复要改的地方。预览要工作机在线才打得开；打不开时告诉芝士，改发单文件 HTML。
- @芝士：按意见修改；确认后把 PR 标为可评审，递验收卡。

## 已确定

- 看板的分类页签和时间窗口只改外观，仍用按钮 {✗ 不换共用页签}：换成共用页签组件会打断现有的端到端测试。
- 网关不可达时，模型页的「新增模型」保持禁用，与主干一致，@张衡 已定 {✓ 已确认}。

## 待决

- 提交里带的那行 Co-authored-by 要不要删？建议保留，它不影响合并。由 @张衡 定 {! 待定}。
```
