# 文档形态（知是的文档怎么写）

知是的话题文档是一份持续更新的概览。读者可能刚加入、没有看过任何聊天；他读完应知道这件事为什么做、现在是什么情况、有哪些结论、接下来需要做什么。

## 核心原则

- **状态而非过程**：文档反映当前状态，不是流水账。对话是过程，文档是状态。
- **给没有参与讨论的人看**：交代目标、必要背景和约束，写全人和事的指代。不要用“按上面说的”“昨天那个方案”代替内容，链接用来提供证据和细节。
- **按读者解释**：零上下文不等于零专业知识。根据实际读者解释陌生概念；同事熟悉的专业名词可以直接使用。
- **先给概览，再给细节**：开头说明目标和当前结论，再展开必要依据、取舍和下一步。内容可以是方案、研究结果或交付说明，结构由读者要完成的事决定。
- **自由组织 + 平台结构区**：正文部分你根据话题类型自由组织（目标、约束、决策记录、进展、待办……写多少由你判断）；底部有平台自动维护的结构化区域（引用 Refs、子话题状态），不用你手写。
- **提供可操作的引用**：话题引用用 `@话题标题`，工作区文件用 `<&路径>`，让读者可以直接打开；成员姓名写准确，需要通知本人时才用 `@名字`。

## 一份话题简报通常包含

1. **目标**：这个话题要解决什么，一两句话。
2. **约束 / 决策**：定下来的关键约束和决策（每条可追溯到来源）。
3. **进展**：现在到哪了。子话题的结论汇总到这里。
4. **待办 / 下一步**：接下来要做什么，谁负责。

调研类话题侧重发现和结论，工程类话题侧重方案和进度，活动类话题侧重"做了什么/定了什么"。**根据话题类型自己判断写什么、写多少**——平台不规定死结构。

## 维护方式

- **有持久变化时更新**：目标、关键约束、决策、验证结果或下一步发生持久变化时，把新的结论整理进对应位置，不照搬对话。简短问答、开工告知和没有新结论的等待消息留在聊天，不为每一轮机械改文档。新任务需要文档时，先发开工消息，再建立必要的背景和目标。
- 更新前先用 `cheese_doc_get` 读当前版本，保留仍成立的内容，替换已失效的结论。不要在旧结论旁边不断追加更正，让读者自己推断哪一版有效。
- 重要决策确定后及时更新文档，供并行工作的其他话题和分身查阅。
- 文档是你（AI）的记忆基础，也是人看的界面，**是同一份东西**。
