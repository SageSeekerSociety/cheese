# 当前阶段：任务有合并冲突

从卡取得任务 id，`cheese_worktree(task_id)` 返回目录，`cd` 进去。有 PR 时读取 PR 的目标分支；未连接 GitHub 时读取任务的目标分支。依赖其他任务时目标可能是父任务分支，不能固定使用 main。平台已准备冲突提交时，先保留本地工作并合入平台任务分支，不能假定本地目录已自动更新。

取回目标分支的最新提交，用 `git diff --name-only --diff-filter=U` 看清撞的是哪几个文件。

撞的是 `.docx` / `.pptx` / `.xlsx` 这类文档时**不要合并内容**：办不到，而且 git 不在二进制文件里留冲突标记，它把你这一版留在工作目录里，直接提交等于把对方那次修改静默丢掉。这类文件的做法是在对方那一版上把本轮改动重做一遍，再用 `validate --base 两边共同的那一版` 证明别的地方一个字没动；步骤见 documents 技能「别人先改了同一份」，那里也写了为什么基准是共同起点而不是对方那一版。重做落不下去（`edit` 找不到原文、本轮不是用 `edit` 改的、两边各自重写了整份文档）就停下，用 `cheese_ask` 给出「用我这一版」和「用主干那一版」两个出口，不要自己挑一边。重做前那一版留着，验收的人要两版对着看。

其余文件按文本处理：理解双方改动后解决冲突，按仓库约定验证并提交。

两条路都是提交之后用 `cheese_sync` 同步任务并确认成功；有 PR 时再用 `cheese_push_fix` 更新它。对验收人说明保留了哪些行为、验证结果和需要决定的取舍。双方目标互斥而任务要求不能决定时，用 `cheese_ask(question="问题", option=["选择 A", "选择 B"])` 提出具体选择。

PR 有新提交时，按项目设置处理已有批准，默认清除旧批准。修复后让人查看新 commit；需要重新批准时由人采纳，执行者不能代替人批准。
