# 当前阶段：任务执行

房间保留对话与会话。要交付仓库改动，即使主 agent 自己只改一行，也先创建任务。每条任务拥有自己的工作目录、分支与 PR。

`cheese task <标题> --brief <简报> --reviewer <handle>` 返回任务 id、工作目录和这条活的线程标识。只有项目已配置默认验收人时才可省略 `--reviewer`，派活时检查返回的人选。任务依赖尚未合并的另一条任务时，加 `--base-task <父任务 id>`。

任务可以由人、主 agent 或原生后台分身执行；`cheese task` 不会启动执行者。自己执行就进入返回目录。派给分身时，把简报、已核实的证据、任务目录和返回的线程标识一起传入其 prompt：平台从这段 prompt 上读出标识，把它干的每件事记进这条活的时间线。同一任务目录只交给一个执行者写。分身停止只记录它的说明，不关闭任务。

中途补充要求，直接给正在运行的分身发消息；要停掉它，用骨架自带的停止工具按起它时给的那个名字停那一条，同一条会话里的其他分身照跑。已停止且没有后台进程继续写任务目录时在房间会话中重新派遣，新分身的 prompt 里照旧写同一个线程标识。需要留在任务记录里的说明用 `cheese tell <这条活> <说明>` 保存，它不唤醒执行者。

执行者在自己的任务目录按仓库约定完成检查并提交。项目仓库连接就绪后，首个提交同步会创建该任务的 draft PR。执行者用 `cheese ready` 标记可评审；需要请人验收时用 `cheese accept-request --subject "fix(scope): describe the change" --body "原因、验收证据和未完成检查"`；交出去的是这次合并本身时**不声明产物**——交出去的是项目那个仓库，平台自己认得出是清单上哪一项。交出去一份文件（`--deliver`）或一个地址（`--deliver-url`）时才接着说清动的是哪一项：`--artifact <清单上那一项的 id>`，或者做出了清单上还没有的东西时 `--new-artifact <新的真名>`，返回里带回它的 id。每条任务独立请求验收，不等待房间凑齐一批。

调研和活动安排等不交付仓库文件的工作，直接使用来源资料和平台文档，不必为了更新进度制造代码提交。
