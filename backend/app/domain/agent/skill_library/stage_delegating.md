# 当前阶段：拆活

本话题是个**房间**。房间里的一条「活」不是另一个话题，也不在别的机器上——它是**你这个会话里的一个分身**（用你自己的 Agent 工具起的后台子代理）。你和它共用同一个工作区、同一条分支、同一份已经装好的依赖。

## 派活是三步，不是一步

`cheese split` **只建一行活和它的简报文档，不会有任何人开始干**。起分身是你的事：

```
1. cheese split "标题" --brief "<简报原文>"   → 拿到 task id
2. 用你的 Agent 工具起一个分身，把简报原文放进它的 prompt
3. cheese bind <task_id> <分身的 agent_id>    → 告诉平台这条活归谁
```

**第 3 步不做，后果是无声的**：界面上这条活永远显示「没人做」，而分身干的每一件事都记在你（房间）头上，谁也分不出来。

**分身不会自己去读简报文档。** `--brief` 存的那一份是给人看的、也是这条活的档案；分身只看得到你放进它 prompt 的字。两处都要有。

## 简报里必须有的五段

1. **目标**——要什么产出，不是"研究一下 X"，而是"产出 X，满足 Y"。
2. **已核实的事实 + 证据**——你已经查清楚的东西全写进去，并注明是**怎么**核实的（读了哪个文件、跑了什么命令）。明确写「别重新调研」。让分身重跑一遍你已经做过的调研，是这个机制最常见的浪费。
3. **禁区**——明确不做什么。分身看不到房间里的上下文，不写禁区它就会按自己的判断扩大范围。
4. **验收标准**——逐条、可检验。这是它交活时逐条给证据的对象。
5. **范围不清楚就问回来**——简报难免有没覆盖到的地方。明说这几种情况必须问、不许自己拍板：**简报里某条前提它核实下来是错的**、**要做的东西别处已经有了**、**要动简报没提到的模块 / 改公共配置 / 引入新依赖**。反过来，简报范围内的技术判断是它的。分不清就看一条：这个决定改变的是"怎么做"还是"做什么"？前者它定，后者问回来。

## 中途要追加要求：直接跟它说

分身在你的会话里，你**直接给它发消息**就能插话（不用停掉重派）。它已经收工了，就照原来的简报重起一个，再 `cheese bind` 一次。

跟它说过什么、它回了什么，值得留痕的用 `cheese tell <task_id> "..."` 写到那条活上——**盯着那条活的人够不着分身，那儿是他们唯一看得到的地方**，下周翻开这条活的人也是。

## 并行改同一棵树

几个分身共用一个工作区和一条分支。两条活整块改同一个文件，后写的会**无声**盖掉先写的；`cheese split --paths` 把各自要碰的路径划开，中途还能 `cheese claim` 追加。

## 收活：完成信号不等于活干完了

一个分身可以报**好几次**完成（它把长命令丢进自己的后台再停下来等，也算一次完成），而且平台还会收到来路不明的完成通知。所以完成是给你看的信号，不是结论：

**验过货之后**，由你 `cheese conclude-task <task_id> "<结论>"` 替它把结论落成一张结论卡。递验收卡也是你的事——一棵树=一个分支=一个 PR=**一批**活，攒够了整个房间递一次。
